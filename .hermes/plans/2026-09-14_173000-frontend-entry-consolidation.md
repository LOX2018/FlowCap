## 三、缺陷修复方案（对应需求 A）

### Task 1：统一任务中心两个表格的列宽契约

**问题**：两表列数不同（9 vs 7），`table-layout: auto` 让浏览器按各自内容分配，导致"账号""结果条数"等**同名列出现在不同位置**。

**方案（三选一，推荐 A）**：

- **方案 A（推荐）：共用 `<colgroup>` 比例契约**
  抽一个 `TASK_COLS` 常量（如 `[14, 11, 12, 18, 9, 9, 9, 6, 12]` 百分比），两个表格各自渲染 `<colgroup>`，
  同名列用同一比例。改列只改一处。
  - 优点：彻底解决；列宽可读可控（不依赖内容）
  - 成本：给 `tasks.tsx` 加 colgroup（约 30 行）

- 方案 B：`table-layout: fixed` + 每列 `w-[Npx]`
  - 优点：简单
  - 缺点：列宽散落在 th 上，9+7 处，易漂移

- 方案 C：抽一个 `<DataTable columns={...} rows={...}>` 通用组件
  - 优点：一劳永逸，其它页（logs/accounts）也能用
  - 缺点：改动面大（本轮不宜）

**推荐 A**：改动局部、见效直接、与"统一调度/资源复用"的体系化思维一致。

**验收判据**：
- 实测两表**同名列的 left 坐标差 ≤ 1px**（"账号""状态""结果条数""操作"四处）
- 表格总宽不变（1138）
- `npx tsc -b` EXIT=0
- 实机截图对比

**涉及文件**：`frontend/src/pages/tasks.tsx`

### Task 2：建立"列表类组件"检查清单（防复发）

用户说"这些类型都有异常"——"这些类型"暗示**一类问题**。在动手修 Task 1 前，
先做一次**全站列表/表格体检**，输出一张"异常清单"，避免只修了截图里那一个。

**体检对象**：所有 `<table>` 与列表渲染（tasks / logs / accounts / live / messages / kb / platform / notify）

**体检项**：
1. 同页多个表格的同名列是否对齐
2. 表格是否有横向溢出（`scrollWidth > clientWidth`）
3. 空状态是否水平居中
4. 列表行的操作列是否右对齐一致

**产出**：`docs/frontend_list_audit.md`（异常清单 + 每项实测数值）

**这符合用户的"体系化"要求**：不是修一个 bug，而是建立一类问题的检查机制。

### Task 3（待定）：② ③ 两个"疑似异常"的进一步确认

- ②知识库：实测已推翻 Vision 的说法。**需用户确认**是否确有观感问题（如换个窗口宽度复现）
- ③私信中心：需用户**指认具体位置**（红框里是哪个元素、什么不对）

## 四、功能入口整合方案（对应需求 B）

### 4.1 设计目标

> **共享的设定只有一个"总入口"（可写）；其他页面只保留"选择/引用"（调用口，不可写）。**

### 4.2 现有问题定位

```
设置页（唯一总配置，但埋在 12 项里）
├── 通用配置        ┐
├── 私信发送        │
├── 直播监听        ├─ UnifiedConfigSection（共享参数）
├── 捕获与存储      ┘
├── AI 与 Agent     ── ModelHubSection + AgentSection（共享模型/模版）
├── 配置标签        ── TagSection（共享发送策略）
└── 通知与指令      ── NotifySection（共享通知模型）

AI 获客页  ── 也能改"回复话术"（与设置页重叠）❌
知识库页    ── 全功能知识库管理（与设置里"AI与Agent"概念重叠）⚠️
直播页      ── RoomConfigManager（房间级覆盖，设计意图，保留）
```

### 4.3 整合方案（推荐"两层结构"）

**核心思路**：把侧栏从"12 项扁平"改为"**业务页 + 1 个设置中心**"两层。

```
第一层·业务操作（不含配置编辑）
  总览 · 私信 · 直播 · 采集 · 内容 · AI 获客 · 知识库 · 账号 · 任务 · 通知 · 日志

第二层·配置中心（唯一可写入口，侧栏底部独立入口）
  ⚙️ 设置中心
     ├── 通用          （前端/系统行为）
     ├── 私信发送      ┐
     ├── 直播监听      ├ 共享参数（原 UnifiedConfigSection）
     ├── 捕获与存储    ┘
     ├── 模型链路中心  ── 模型/提供商/避障（唯一真源）
     ├── Agent 与话术  ── Agent 模版 + 账号绑定 + 回复话术
     ├── 配置标签      ── 按账号差异化策略
     └── 通知与指令    ── IM 通知 + 指令解析模型
```

**各业务页的"调用口"改造**：

| 页面 | 现状 | 改为 |
|---|---|---|
| **AI 获客** | 可编辑回复话术 | **只读展示**当前 Agent/话术；提供 `[去配置]` 按钮 → 设置中心 | 
| **知识库** | 全功能编辑 | 保留（它是**业务页面**，不是"共享设定"）；但从设置页移除重复概念 |
| **直播** | RoomConfigManager | 保留（房间级覆盖是业务需求）；但"全局直播参数"只在设置中心 |
| **私信** | 无配置项 | 增加一个只读的"当前生效配置"摘要 + `[去配置]` |
| **账号** | 无 | 增加每账号的"生效 Agent/标签"选择器（**这就是"选择配置的调用口"**）|

> **关键**：`账号`页的"为每个账号选择 Agent / 配置标签"正是用户说的**"选择配置的调用口"**——
> 配置本身在设置中心维护，账号页只做**选择**。

### 4.4 需要用户拍板的三个决策点

| # | 决策 | 选项 |
|---|---|---|
| D1 | **设置入口的位置** | A) 侧栏底部独立按钮（推荐，与"收起"并列）<br>B) 侧栏"系统"组内但视觉加强<br>C) 顶栏右侧齿轮图标 |
| D2 | **AI 获客页的编辑能力** | A) 全部移除，只留只读+跳转（推荐，最符合"调用口"）<br>B) 保留"商家名/档位/延迟"等高频项，其余跳转<br>C) 不动 |
| D3 | **知识库页的定位** | A) 保持业务页（推荐）<br>B) 并入设置中心 |
