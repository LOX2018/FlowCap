## 2026-08-06 修复账号 .env 路径双重 accounts 前缀导致扫码写盘失败

**文件**：`auto_dm/accounts.py`

**现象**：点“重新扫码”报 `[Errno 2] No such file or directory: '...\\auto_dm\\accounts\\accounts\\四川工伤-张老师\\.tmp_xxx'`，
最终“扫码未完成或失败”。根因是 `dotenv.set_key` 写临时文件时目标目录不存在。
**根因**：`add_account` 把索引 rel 存成了 `os.path.join("accounts", name, ".env")` 即 `accounts/<name>/.env`（带前缀），
而 `current_env_path / list_accounts / remove_account` 又用 `os.path.join(_ACCOUNTS_DIR, rel)` 拼接，
导致最终路径变成 `auto_dm/accounts/accounts/<name>/.env`（双重前缀），该目录从未被创建 → 写盘失败。
**改动**：
1. `add_account` 的 rel 改为 `os.path.join(name, ".env")`（相对 _ACCOUNTS_DIR，无前缀）。
2. `_load_index` 增加一次性兼容性修正：若索引里 rel 以 `accounts/` 开头，则归一化为 `<name>/.env`，
   并把旧错误路径下已生成的 .env 用 `os.replace` 迁移到正确位置、清理旧双重目录；修正后回写 accounts.json。
3. 顺手修了两处替换引入的 IndentationError（auth_helper 的 with 块、accounts 的 _load_index 残留 return）。
**校验**：py_compile 通过；自测 `current_env_path()` 输出 `auto_dm/accounts/四川工伤-张老师/.env`（无双重前缀），
正确路径文件存在、旧 `accounts/accounts/...` 目录已无残留。

## 2026-08-06 修复“重新扫码”未唤醒浏览器（仅读现有凭证）

**文件**：`dy_apis/login_api.py`、`auto_dm/auth_helper.py`、`auto_dm/gui.py`

**现象**：用户在 GUI 账号管理页点“重新扫码”，并未弹出浏览器，而是读回了当前账号已有凭证。
**根因**：`on_account_rescan` 调 `enrich_auth`→`get_login_auth`，而 `get_login_auth` 逻辑是
“ticket 存在且 get_my_uid 探活通过就 return 跳过扫码”。对已有效账号点重新扫码 → 探活通过 → 直接
return，根本不进 `login_grab_ticket`，故不唤醒浏览器。
**改动**：
1. `login_api.py` `get_login_auth` 新增 `force=False` 参数：`force=True` 时跳过一切判定，
   直接 `login_grab_ticket` 重新扫码（文案改为“强制重新扫码（忽略现有凭证）”）。
2. `auth_helper.py` `enrich_auth` 透传 `force` 给 `get_login_auth`（含 ThreadPoolExecutor 分支，
   顺手修复该分支 lambda 缩进缺失的 IndentationError）。
3. `gui.py` `on_account_rescan` 调用 `enrich_auth(..., force=True)`，文案改为“强制重新打开浏览器扫码”。

**原因**：满足“重新扫码=强制重新走扫码流程”的语义，无论当前凭证是否有效都应唤醒浏览器。
**校验**：py_compile 通过（exitCode 0），lint 0 错误。

## 2026-08-06 修复“失效 ticket 不触发扫码二维码”

**文件**：`DY_Spider_base/dy_apis/login_api.py`、`DY_Spider_base/auto_dm/run.py`

**改动内容**：

     探活通过（cookie 非空且能拿到 uid）才跳过扫码，否则记 warning 并 **强制重扫**。
   - 新增 import `from dy_apis.douyin_api import DouyinAPI`。
2. `run.py` `_build_auth`：在调 `enrich_auth` 前，若缺签名则打印明显提示
   “将弹出浏览器扫码登录窗口，请在浏览器中完成抖音扫码”。
3. `run.py` `_run`：签名仍缺失（扫码超时/未成功）的兜底报错文案改为

**原因**：对齐用户“失效则提示重新扫码”的约定，把“有 ticket”升级为“有 ticket 且有效”，

**校验**：`py_compile` 三个文件通过（exitCode 0）。待用户实测：启动后若 ticket 失效会看到

## 2026-08-05 直播间号解析主引擎改造（reflow 两步换发）

**背景**：用户要求学习 DouyinLiveRecorder 项目解析真实直播间号的技术，并将其作为

不要动 `py/` 文件夹。

**改动内容**：
1. 新增主引擎 `resolve_via_reflow(raw, auth=None)`：
   - 复用 DouyinLiveRecorder 思路：分享短链/直播链接/用户主页
     -> `_follow_redirects` 拿最终 URL -> 抽 `room_id`(live.douyin.com/<id>) 与

     verifyFp/type_id/live_id/room_id/sec_user_id/app_id/msToken，

3. reflow 成功时把主播 sec_uid 记入日志（可直接用于私信/主页，无需再查 get_user_info）。

**关键位置**：
- `_REFLOW_URL = "https://webcast.amemv.com/webcast/room/reflow/info/"`

## 2026-08-05 修复 reflow 主引擎解析失败（缺登录态 + 缺项过严）

**现象**（用户实测日志）：
`resolve_via_reflow` 报"无法从链接提取 room_id + sec_user_id，转备用"，
随后浏览器兜底也失败，最终 `[解析] 失败`。

**根因**：
1. `gui.py` 的 `on_resolve`/`_resolve_to_live_id` 调 `resolve_live_id` 时**未传 auth**，
   导致 `_follow_redirects` 与 reflow 请求都是**无登录态**（无 cookie）。抖音短链/直播页
   在无 cookie 时被风控页拦截或重定向目标不含 `sec_user_id`，主引擎拿不到所需参数。
2. reflow 主引擎原逻辑要求 `room_id AND sec_user_id` 同时存在，太严苛：
   - 直播页链接 `live.douyin.com/<id>` 只有 room_id、没有 sec_user_id → 直接被拒；
   - 用户主页只有 sec_user_id、没有 room_id → 直接被拒。

**改动**：
- `link_resolve.py`：
  1. `_follow_redirects(url, cookies=None)` 带登录态 cookie + 完整 PC UA / Referer
     （提升短链重定向出 sec_user_id 的概率）。
  2. 新增 `_extract_room_id_from_html(html)` 用 `\\"roomId\\":\\"(\d+)\\"` 正则从 HTML 抽 roomId。
  3. `resolve_via_reflow` 放宽缺项：
     - 有 room_id 缺 sec_user_id → 用基座 `DouyinAPI.get_live_info(auth, room_id)` 补全 sec_uid；
     - 有 sec_user_id 缺 room_id（用户主页）→ 请求主页 HTML 抽 roomId 补全；
     - 二者皆有才调 reflow。补全都要求 `auth is not None`（无 auth 时不补全，直接转备用）。
- `gui.py`：
  1. 新增 `_build_auth_for_resolve()`：从 `.env` 的 `DY_COOKIES` 读 cookie 构造
     `DouyinAuth`（不开浏览器），供解析用。
  2. `_resolve_to_live_id` 把该 auth 传给 `resolve_live_id(raw, ..., auth=auth)`。

**关键位置**：
- `link_resolve.py`：`resolve_via_reflow` 中情形A（get_live_info 补全 sec_uid）、
  情形B（主页 HTML 补全 room_id）。
- `gui.py: _build_auth_for_resolve` / `_resolve_to_live_id`。

**校验**：lint 0 错误；本机无可用 Python 解释器，未跑 py_compile，已人工核对语法。

**待实测确认**：带上登录态后短链能否重定向出 `sec_user_id`；get_live_info 补全路径是否
稳定（依赖基座 HTML 正则未被抖音改版）。若仍失败，最可能仍是 cookie 过期/未登录，
需先在中控台或浏览器完成一次登录。

## 2026-08-06（续）昵称仍显示 ** 且导致漏发 + 日志需落盘本地

**文件**：`auto_dm/live_hook.py`、`auto_dm/gui.py`、`auto_dm/run.py`

**现象**：用户反馈「四川工伤-张老师」有 992931212705 管理员权限、网页版能看到完整昵称，但日志仍显示 `**`
且加密用户"导致失败"（漏发）。此外日志只在 GUI 文本框可见，关掉/未运行时看不到，要求每次启动都落盘本地。

**根因**：
1. 上一版对加密昵称采用「补全失败就 `continue` 跳过」——但私信是**按数字 uid / sec_uid 直发**（`sender.send_target`
   优先 `user_id`，昵称只用于日志展示，见 `auto_dm/sender.py:81` 与 `core.py:17` 去重用 `user_id or sec_uid`）。
