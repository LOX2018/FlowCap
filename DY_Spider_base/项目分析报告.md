# DYAutoDM 项目全面分析报告

> 生成日期：2026-08-13
> 分析范围：`DY_Spider_base/` 全部前后端代码、工作记忆文档、构建配置
> 目标：理清前后端联动机制，定位"测试时各种 bug 不断"的根因

---

## 一、项目定位

**抖音直播间自动私信控制台**（DYAutoDM）：监听指定直播间的弹幕/评论，对发言人按延迟队列发送私信，附带账号管理、内容采集、直播互动、会话查看等功能。

- 当前版本：约 CS0.43 – CS0.45
- 形态：**pywebview 桌面应用**（不是 Web 应用）
- 部署：PyInstaller 打包成单一 exe，双击运行

### 3.3 轮询频率（性能压力源）

| 页面 | 接口 | 间隔 |
|---|---|---|
| App.js 全局 | `getOverview` | 3s |
| overview | `getAccounts` + `getStats` | 3s |
| live | `getTasks` + `getStats` | 2.5s |
| live | `getLiveStream` | 2s |
| live | `getAccounts` | 5s |
| messages | `getConversations` | 3s |

## 四、后端架构分析

### 4.1 WebBridge API 清单（34 个方法）

所有方法返回 `{ok: bool, ...}`。前端通过 `window.ApiBridge.<method>` 调用。

| 类别 | 方法 | 说明 |
|---|---|---|
| 概览/统计 | `getOverview` `getStats` `getLiveStream` `exportStats` | 引擎/守护状态、实时统计、导出 xlsx |
| 搜索/互动 | `search` `diggVideo` `favoriteVideo` `sendDanmaku` `doLike` `requestDm` `resolveLive` | 走监测账号 auth 调抖音接口 |
| 私信会话 | `getConversations` `getConversation` `sendDm` | 转发到 recv_daemon HTTP |
| 账号 | `getAccounts` `checkAccount` `setCurrent` `setRoles` `addAccount` `scanLogin` `removeAccount` | 多账号管理 |
| 守护进程 | `startBrowserDaemon` `stopBrowserDaemon` `startRecvDaemon` `stopRecvDaemon` `refreshBrowserDaemon` | 拉起/停止子进程 |
| 引擎控制 | `start` `pause` `resume` `stop` `setMaxTarget` | AutoDM 主控 |
| 配置 | `getTasks` `saveConfig` `saveDmPool` | 读写 config.py |

### 4.2 AutoDM 主控状态机

存在 **3 条并行线路** 与 **5 个标志位**：

```
监听线路（WS 弹幕）：listen_active
私信线路（队列）：    hard_stopped / no_new / paused
整体运行：           _running
```

`is_running()` 判定：
```python
def is_running(self):
    if self._running: return True
    if self.dispatch and not self.dispatch.hard_stopped and self.dispatch.queue_size() > 0:
        return True  # 软停止后队列仍在发
    return False
```

**问题**：软停止后 WS 已关但队列仍在发，`is_running()=true`，前端显示"运行中"，与用户感受不一致。

### 4.3 DispatchCenter 调度逻辑

- 双来源：LiveChatHook（WS 弹幕）+ web_probe（DOM 扫描，默认关）
- 跨来源去重：`sent_ids` / `sent_sec` / `sent_names` 三套集合
- 延迟队列：`_queue = [(send_at_ts, key, target)]`，后台线程到点消费
- 延迟配置：`SEND_DELAY_SEC = (40, 65)` 随机抖动
- 发送间隔：`SEND_INTERVAL = 60s`
- 上限：`MAX_TARGET = 3`（默认）
- 状态记录：`records` 数组，每次捕获留"已捕获"占位，发送后更新该 key

### 4.4 端口分配算法

[accounts.py](auto_dm/accounts.py) 用 `zlib.crc32(账号名) % 500` 映射：
- browser_daemon：10000-10499
- recv_daemon：10500-10999

**风险**：理论哈希冲突；调试时端口不直观；多账号时 `getAccounts` 每账号做 socket 探活 + HTTP 探活，N 个账号就是 2N 次探测。

### 4.5 守护进程 HTTP 路由

#### browser_daemon（凭证守护）
| 路由 | 方法 | 返回 |
|---|---|---|
| `/status` | GET | `{alive, logged_in, sign_ready, uid, account, last_refresh}` |
| `/refresh?account=X` | POST | `{ok}` 强制重扫码 |
| `/quit` | POST | `{ok}` 退出并清凭证 |

#### recv_daemon（私信接收守护）
| 路由 | 方法 | 返回 |
|---|---|---|
| `/status` | GET | `{ok, accounts:{name:{connected,error,conv_count,total_unread}}}` |
| `/conversations?account=X` | GET | `{ok, conversations:[]}` |
| `/conversation?account=X&conv_id=Y` | GET | `{ok, conversation:{}}` |
| `/send` | POST | `{ok, error?}` body=`{account,conv_id,text}` |
| `/quit` | POST | `{ok}` |

## 五、前后端联动关键链路

### 5.1 启动自动私信

```
前端 tasks.js 点"启动"
  → api.start(cfg)
  → WebBridge.start(config)
    → 写 C.LIVE_URL/MAX_TARGET/... （仅内存）
    → self.adm = AutoDM(config_overrides)
    → adm.start()  # 起后台线程
      → _build_one_auth(监测账号 env)  # 可能弹浏览器扫码
      → _build_one_auth(发送账号 env)
      → _verify_credential (create_conversation 探活)
      → check_room_live (判断是否开播，未开播轮询等待)
      → LiveChatHook.start_ws  # WebSocket 连直播间
      → DispatchCenter 后台线程消费延迟队列
  → 返回 {ok:true, status}

前端轮询 getOverview（3s）观察 running/sent/limit
前端轮询 getStats / getLiveStream 看实时数据
```

### 5.2 账号校验

```
前端 accounts.js 点"引擎校验"
  → api.checkAccount(name)
  → WebBridge.checkAccount
    → accounts.verify_account(name, dm_loopback=True)
      → wp 引擎：account_status + 守护 /status
      → dm 引擎：对自身 uid 发真实回环私信
    → 写 _dm_verify_cache[name] (120s)
  → 返回 {ok, name, verify:{wp, dm}}

⚠️ 关键：getAccounts 轮询时用 dm_loopback=False，会把 dm 状态重置回 idle
   靠 _dm_verify_cache 在 120s 内透传，避免覆盖回环结果
   ——这是 CS0.42 才修的 bug，机制脆弱
```

### 5.3 私信发送（双来源 + 去重 + 延迟）

```
来源 1: LiveChatHook WS 收到 WebcastChatMessage
来源 2: web_probe DOM 扫描（默认关闭）
   ↓
DispatchCenter.submit(target)
  → 跨来源去重（user_id / sec_uid / nickname 三套集合）
  → records 留"已捕获"占位
  → 计算 send_at = now + SEND_DELAY_SEC（默认 40-65s 随机）
  → 入 _queue
   ↓
_loop 后台线程到点消费
  → _do_send(key, target)
    → send_target(auth, target, content)  # imapi 私有接口
    → 更新 records 该 key 的 status/content/send_ts
    → count++ ；达上限置 reached_limit
    → sleep(SEND_INTERVAL)  # 默认 60s
```

### 5.4 通信机制总结

| 通道 | 用途 | 方向 |
|---|---|---|
| pywebview JS-Python 桥 | 前端 ⇄ WebBridge | 双向同步调用 |
| HTTP 127.0.0.1 | WebBridge ⇄ 守护进程 | 同步 |
| WebSocket | LiveChatHook ⇄ 抖音直播 | 后端单向收 |
| 长连接 | recv_daemon ⇄ frontier-im | 后端单向收 |

**注意**：前端与后端**无推送**，全靠 3s 轮询。

## 六、不适配点与 Bug 源（重点）

### 6.1 历史 Bug 演进（暴露出的模式问题）

| 版本 | Bug | 根因模式 |
|---|---|---|
| CS0.30 | `_loop` Condition.wait 报 RuntimeError | 锁/条件变量使用错误 |
| CS0.31 | stop_keep_queue 后存量私信被静默丢弃 | **三态（hard/soft/pause）没区分** |
| CS0.40 | s_v_web_id 风控占位污染凭证 | 风控字段处理不彻底 |
| CS0.41 | 账号管理"全部校验"黑屏 | **前端访问 undefined 字段** |
| CS0.41 | 引擎校验无反馈 | **catch 吞错误 + 后端无 logger** |
| CS0.42 | 监听账号无选中标识 | 状态字段未双向绑定 |
| CS0.42/43 | Grid 布局垂直堆叠 | **手写 React.createElement + grid 脆弱** |

**反复出现的 4 个根因模式**：
1. **前端访问 undefined 字段** → 整棵 React 树卸载黑屏
2. **`.catch(() => {})`** 吞掉所有错误 → 用户看不到反馈
3. **后端方法无 logger** → "后台无日志"无法排查
4. **多态标志位（stopped/hard_stopped/no_new/paused/listen_active/_running）相互覆盖** → 状态错乱

### 6.2 当前仍存在的潜在问题

#### B1. 前端 mock 桥时序问题
[framework.js:229](web/framework.js#L229)：
```js
window.addEventListener('pywebviewready', function () {
  Object.assign(window.ApiBridge, window.pywebview.api);
  window.ApiBridge.ready = true;
});
```
CS0.42 工作记忆明确记录：mock 模式下 `ready=false` 时 useEffect 提前 return，之后注入真实桥**不会触发 load() 重跑**（api wrapper useMemo 空依赖）。真实 exe 中 pywebview 在页面加载前就 ready，正常；但**任何时序异常都会导致页面空白**。

#### B2. 状态字段协议脆弱（中文字符串作为协议）
[live.js:70](web/pages/live.js#L70)：
```js
dmStatus: r.status === '已发送' ? 'sent' : r.status === '已捕获' ? 'wait'
        : r.status === '发送失败' ? 'fail' : 'un',
```
后端用**中文字符串**作为协议字段，前端用字符串相等比较。后端 `_do_send` 失败时 status 是 `f"发送失败({reason})"`，**前端比较 `=== '发送失败'` 永远不匹配**，会落到 `'un'`（未私信），与实际状态相反。

#### B3. scanLogin 是 fire-and-forget
[web_bridge.py:852](auto_dm/web_bridge.py#L852)：扫码在后台线程跑，立即返回 `{ok:true, msg:"已弹出"}`。结果只能靠轮询 `getAccounts` 的 `loggedIn/signReady` 间接推断。用户关掉浏览器未扫码时，状态会卡在"扫码中"直到下次操作。

#### B4. scanLogin 与 browser_daemon 保活心跳竞态
- `scanLogin` 后台调 `DYLoginApi.get_login_auth(force=True)` 写 .env
- `browser_daemon` 每 300s 也调 `refresh(force=False)` 写同一 .env
- 两者**无协调**，可能同时写文件造成凭证损坏

#### B5. 前端错误几乎全被吞
所有 API 调用都是 `.then(d => {...}).catch(() => {})`，**catch 内没有任何反馈**。这是用户感觉"点了没反应"的直接原因。

#### B6. 轮询架构压力
- 直播页 + 总览页同时活跃时，每秒 1-2 次后端调用
- `getAccounts` 是重操作（每账号 verify + 2 次 socket + 2 次 HTTP）
- 多账号场景下 `getAccounts` 3-5s 一次会拖慢前端
- 后端 `_http_get` 默认 timeout=3s，守护未启动时**每次都要等 3s 超时**，前端表现为"卡顿"

#### B7. is_running 与 UI 不一致
软停止后队列仍有私信在发，`is_running()=true`，前端 Header 显示"运行中"，但 WS 监听已关，用户感受是"明明停了还在跑/明明在跑却没新数据"。

#### B8. 配置写回路径脆弱
`_write_config_file` 字符串匹配 config.py，打包态依赖 exe 旁有可写 `auto_dm/config.py`。若 PyInstaller onefile 模式资源在 `_MEIPASS`，写回会失败/写错位置。

#### B9. browser_daemon 启动阻塞
`browser_daemon.main()` 启动时立即 `keeper.refresh(force=False)`，**会阻塞数秒**（甚至弹浏览器扫码），期间 `/status` 返回的 `sign_ready` 可能为 false，前端误判"未就绪"。

#### B10. launcher 模式 fallback 静默
[launcher.py:46](auto_dm/launcher.py#L46) 未知 mode 统一回退 web，无日志，调试时不易发现参数错误。

#### B11. 前端 useEffect 清理不彻底
多个页面（live/accounts/messages）的 setInterval 在组件卸载时清理逻辑不完整，tab 频繁切换可能造成**定时器累积、内存泄漏、重复请求**。

#### B12. tasks.js 本地模拟数据
[tasks.js](web/pages/tasks.js) 在未连接后端时用 setInterval 模拟任务进度，**与真实数据无关**，可能误导用户以为任务在跑。

## 七、为什么"测试时各种 bug 不断"——根因总结

1. **架构选型与功能复杂度不匹配**：用 pywebview + 原生 http.server + 手写 React.createElement 应对"多账号 × 多守护 × 多状态机"的复杂业务，**抽象层级不足**，每个新功能都要在 5+ 个文件间手动保持一致。

2. **协议层脆弱**：前后端没有 schema 约定，靠中文字符串、可选字段、隐式默认值联动。后端字段一改前端就崩，崩了又 catch 吞掉，表现为"无反馈"。

3. **状态机复杂但无显式建模**：监听线路、私信线路、守护进程、扫码流程各自有状态，互相通过标志位影响，**没有单一真源（single source of truth）**，每次修改都引入新的状态错乱 bug。

4. **错误处理全面缺失**：前端 catch 吞错误、后端方法缺 logger、守护进程超时无重试反馈，**问题发生时用户和开发者都看不到任何信号**，只能"猜"。

5. **测试方式局限**：CS0.42 工作记忆明确写"MCP playwright 验证失败是验证局限不是 bug"，说明**前端 mock 桥与真实桥行为不一致**，本地难复现 exe 中的问题，导致 bug 只能在打包后实测发现。

6. **轮询而非推送**：3 秒延迟 + 多页面独立轮询 + 重操作 `getAccounts`，造成 UI 卡顿与状态不一致，用户操作和反馈之间有秒级延迟，容易误以为"没反应"又重复点击，触发更多问题。

## 八、改进建议（按优先级）

### P0（立即修复，低成本高收益）

| # | 建议 | 文件 | 收益 |
|---|---|---|---|
| 1 | 前端所有 `.catch(() => {})` 改为 `.catch(e => push('失败:' + (e?.message\|\|e)))` | web/pages/*.js | 立即可见所有错误反馈 |
| 2 | 后端 WebBridge 每个方法首行加 `logger.info`，异常 catch 加 `logger.error` | web_bridge.py | 排查"无日志"问题 |
| 3 | 修复 [live.js:70](web/pages/live.js#L70) 的 `r.status === '发送失败'` 比较（改用 `startsWith`） | live.js | 修复"发送失败显示为未私信" |

## 十、结论

项目业务逻辑完整、技术选型可行，但**工程化程度不足**是"bug 不断"的根本原因：

- **协议层**靠中文字符串和隐式默认值联动，脆弱且不可校验
- **状态机**用多个标志位组合，没有单一真源，每次改动都引入新错乱
- **错误处理**前端 catch 全吞、后端方法缺 logger，问题发生时无任何信号
- **测试方式**mock 桥与真实桥行为不一致，本地难复现 exe 中的问题
- **性能**全靠 3s 轮询，重操作 getAccounts 在多账号下拖慢前端

**最小代价的改进路径**：先做 P0 四项（错误反馈 + 日志 + 状态枚举化），可立即消除"无反馈"类 bug 的大部分；再做 P1 拆分 getAccounts 和增加 scanStatus，解决卡顿和扫码卡死；中长期再做状态机重构和协议 schema 化。
