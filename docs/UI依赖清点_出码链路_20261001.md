## 2. 视口尺寸（代码事实）

- **硬编码 1600×1000**，三处：
  - `login_remote.py:1000`（`prepare_qr_login`）
  - `login_remote.py:1168`（`bridge_qr_login`）
  - `login_remote.py:1489`（`do_sms_login`）
  - 代码：`await page.set_viewport_size({"width": 1600, "height": 1000})`
- **另有账号档案视口**：`vbrowser.py:432 _viewport_for_account()` → `utils/fingerprint.py:393 viewport_for(account)`；在 `vbrowser.py:1085 / 1190 / 1247` 传入 `launch_persistent_context(viewport=...)`。
- **冲突（事实）**：`launch_async` 用的就是带 `viewport=` 的启动分支，随后 login_remote 又用 `set_viewport_size(1600x1000)` **覆盖**了账号档案视口 ⇒ 指纹层「单源化」被破坏（`errcode_data.py:663` 把「viewport_for 未走」列为错误码根因；`services/env_audit.py:365-369` 会报 `screen 不一致`）。

## 3. 「登录」按钮定位逻辑 + 稳定 id

- **当前主路径（bridge）不用 id**：`login_remote.py:1181-1188` 是**纯文本匹配**（`==='登录'`）后取 rect 中心坐标 —— 未用任何 id。
- **仓库已有的稳定 id 锚点常量**（`login_remote.py:107-129`）：
  - `#douyin-login-new-id`（面板）
  - `#douyin_login_comp_scan_code`（扫码组件）
  - `#animate_qrcode_container`（二维码容器）
  - `#douyin_login_comp_mobile_code`（验证码登录 tab）
  - **`#douyin_login_comp_btn_id`（`SEL_ONE_CLICK_BTN`，:127）——「登录」主按钮，文本实测就是「登录」**
  - `#douyin_login_comp_normal_input_id` / `#douyin_login_comp_button_input_id`
- **是否被当前点击逻辑使用？** 分两处：
  - `click_login`（短信路径，:784）**不用** `#douyin_login_comp_btn_id`，只在**兜底**分支通过 `dom_locator` 的 `btn_submit` 目标间接用到（见下条）。
  - `bridge_qr_login._try_click_login`（**当前默认出码路径**）**完全不用**，只做文本+坐标。
  - `do_sms_login` 只在「验证码登录 tab」用了稳定 id（:1506）。

## 4. 自适应兜底 `dom_locator.py`（代码事实）

- 位置：`backend/auto_dm/dom_locator.py`。基于 **Scrapling 自适应 parser**（`from scrapling.core.storage import SQLiteStorageSystem`，:39-50），`available()` 在 scrapling 缺失时返回 False 优雅降级。
- 能力：
  - `LOGIN_TARGETS`（:203-217）五个目标：`tab_scan` / `tab_sms` / `input_phone` / `input_code` / **`btn_submit`**。
  - **`btn_submit` 的 css = `div[id="douyin_login_comp_btn_id"]`**，`want_text=("登录","立即登录","登 录")`，`text_mode="exact"`（:214-216）⇒ **「登录」按钮的自适应定位能力已存在**。
  - 策略链：旧选择器自适应 → 确定性校验（`validate()`，tag / 文本 / 属性 / scope）→ 唯一性铁律，输出 XPath。
  - 门面：`locate_xpath(page,key)`（:367）、`click_adaptive(page,key)`（:389，注释明确说时序已对齐 login_remote 的 move→0.12→down→0.06→up）。
- **是否被当前点击逻辑调用？**
  - `login_remote.py:75-83 _adaptive_xpath` → 调用点仅 4 处：`click_by_text`（:682）、`click_login` 兜底（:807）、`fill_phone`（:924）、`fill_code`（:950）。
  - **`bridge_qr_login._try_click_login`（默认出码路径）零调用** —— 这是最大缺口。
  - 且 `_TEXT_TO_KEY`（:72）只映射了 `扫码登录/验证码登录`，**没有「登录」→ btn_submit** 的映射（所以 `click_by_text(page,"登录")` 走不到自适应）。

## 5. 脆弱性评估（场景：分辨率变化 / 跨设备·移动端布局 / 抖音改版）

| 依赖 | 分辨率变化 | 跨设备/移动布局 | 抖音改版 | 现有缓解 |
|---|---|---|---|---|
| #1 bridge 坐标点击（默认路径） | **不失效**（rect 实时算，无绝对常量） | **部分风险**：元素在视口外/被遮挡时 rect 中心不可点；`r.width<8` 只滤极小元素 | **失效**：文本变『登录/立即登录/登 录』任一改动即找不到 | 3 轮重试（:1209）+ 未出码重点（:1218）+「未找到」时仅告警继续被动等（:1222） |
| #2 硬编码偏移 -40/-25 | **低风险**（仅轨迹） | 小屏下可能移到视口外 | 不受影响 | 无 |
| #3/#6 文本+最大/最小面积启发式 | 不失效 | 布局变则「最大者」可能变**外层容器**而非按钮 | **失效**（文本/层级变） | #4 自适应兜底（仅短信路径） |
| #9 获取验证码（computed color 判启用） | 不失效 | 不失效 | **失效**（文案/配色变，`rgba(...,0.34)` 判据即失真） | 12s 轮询等启用 + 6s 结果识别（cooldown/太频繁） |
| #10 二维码锚点 | 不失效 | 不失效 | **已失效过一次**（2026-09-30 改版，旧 `img` 锚点恒 0；现靠容器截图） | 多锚点轮换（:119-123）+ cv2 机械校验（:374-404）+ 放大二值化重试 |
| #11 枚举方形（**硬编码 130/700/70 像素**） | **失效**：小视口下二维码 <130px 直接落选；大视口 >700 也落选 | **失效**（移动端码更小） | 部分 | 仅作最后兜底 |
| #13 input name 选择器 | 不失效 | 不失效 | **已失效过**（一键登录面板下不存在） | 自适应 xpath 兜底 + 读回值校验 |
| #15 风控检测 | — | — | **失效**（HTML 前 4000 字 + 关键词） | 仅告警，不阻断 |
| #16 modal_id=login 深链 | — | — | **失效**（深链被改则弹窗不挂载） | 桥内清陈旧 cookie 促弹窗（:1135-1166） |

**结论（推断，非代码事实）**：默认出码路径的**唯一硬依赖是「文本===登录 + rect 中心真鼠标」**。分辨率变化本身**不会**让它失效（坐标是运行时算的）；真正的脆弱点是**抖音改版改文案/结构**，以及**元素出视口/被遮挡**。用户担心的「分辨率/跨设备」在这条路径上属**低风险**；风险集中在改版。

## 6. 不依赖 UI 的替代路径（已存在但非默认）

- `login_remote.py:1585 spawn_api_qr_login` → 子进程跑 `backend/login_qr_api_runner.py`（或冻结态 `--qr-api-runner`），调 vendor `login_api_vendor.get_qrcode()`（:250-273）纯 HTTP 出码 + `check_qrcode` 轮询，交接靠 `status.json` / `result.json`（`poll_api_qr_login` :1623，`reap_api_qr_login` :1679）。
- 编排入口 `api/accounts.py:495 _api_scan_login`，由 `api/accounts.py:226` 门控。

**未默认启用的代码内理由（原文摘录）**：

1. `api/accounts.py:198-206`：
   > 「① API 扫码（**仅当显式开启** DY_LOGIN_QR_BACKEND=api；纯协议、零浏览器）… ## 为什么默认 RPA 而不是 API（2026-09-30 身份审查 + 实机实测）：API 路径用 **Chrome 151 UA + curl_cffi(chrome150)**，与本机 **Camoufox(Firefox 152)** 的日常会话构成**跨信号身份矛盾**（H-27「凭证 3 小时失效」同族根因）。而 RPA 在本机 Camoufox 内完成，**TLS/JS/指纹天然同一身份**」
2. `api/accounts.py:223-224`：
   > 「开启条件：环境变量 `DY_LOGIN_QR_BACKEND=api`。默认**不启用**（见函数文档的「为什么默认 RPA」：API 是 Chrome 身份，与账号的 Firefox 会话跨信号矛盾）。」
3. `login_remote.py:31`（旧实测结论，已被 2026-10-01 的桥推翻）：
   > 「| 接口方案 | ❌ 未登录态被反爬挑战页拦截（`get_qrcode` 返回 HTML），**不用** |」
4. `api/accounts.py:496`：
   > 「API 扫码（纯 HTTP，子进程隔离）。**默认不启用**（见 `_rpa_scan_login` 文档）。」
5. `login_api_vendor.py:120-125`（另一条硬约束）：
   > 「[AUTH-073] API 备用路径在本进程不可用…同进程无法隔离（vendor 与 backend 有 5 个同名顶层包…）。请改用 RPA 路径（`auto_dm/login_remote.py`），或在**干净子进程**中调用本适配层。」

**注意（推断）**：`login_remote.py:31` 的「接口方案不用」与 :1171-1175 的「必须用真实鼠标点登录才发 get_qrcode」**互相矛盾**（后者说明接口桥是可行的，只是需要页面发请求）。第 31 行是 2026-09-26 的旧结论，未随 2026-10-01 的桥修复更新 —— 属**文档漂移**，不是代码缺陷。
