### 1.2 关键实测发现（"吉祥物"证据）

**发现 1：`browser_gate` 的独占让出是空壳**

```python
# services/browser_gate.py L112-120 —— PURPOSE_EXCLUSIVE 分支全文
    # 已在线 → 复用（不新开）
    if purpose == PURPOSE_AUTO:
        logger.info(f"[gate][{account}] 复用 BCC 容器 ...")
    else:
        if not st["exclusive"]:
            logger.info(f"[gate][{account}] 独占用途 {purpose}：需先令 BCC 让出 profile")
            # ↑ 只打日志
    return {"ok": True, "owner": "bcc", ...}   # ↑ 直接返回成功！
```

⇒ 声称"要求 BCC 让出 profile"，**实际没有任何让出动作，却返回 `ok=True`**。
调用方以为拿到独占，实际什么都没发生 —— **比报错更糟（完全无感）**。

**发现 2：`/exclusive` 端点根本不存在**

BCC 实际端点只有 14 个：
`/status /cookie /user_info /capture_userinfo /user_info_by_uids /resolve_url
 /exec_js /linkmic_run /wp_messages /wp_send /scan_login /refresh /show /quit`

**没有** `/exclusive`、`/release`、`/lease`。
⇒ gate 的"让出"承诺**在协议层就没有对应接口**。

**发现 3：真正的独占机制藏在 BCC 内部，而非调度器**

BCC 里已有 `ContainerBusy` + `_scan_exclusive` + `_is_busy()`（L92/105/723-730），
`scan_login` 期间其他端点返回 `{ok:false, busy:"scan_login"}`。

实测日志（2026-09-13）：
```
18:43:28 BCC-033 | [bcc] /wp_messages 失败: 容器被独占操作占用: scan_login
18:53:41 BCC-033 | [bcc] /wp_messages 失败: 容器被独占操作占用: scan_login

```

⇒ **调度职责在 BCC 里（且做得比 gate 完整），gate 只是个转发壳**。
这是"调度器是吉祥物"的**结构根因**：调度逻辑不在调度器里。

## 二、根因分析（为什么调度器会沦为吉祥物）

### 2.1 结构原因：没有"资源所有权"的单一事实源

浏览器所有权（谁能用这个 profile）目前**三处各自判断**：

| 判断者 | 判据 | 问题 |
|---|---|---|
| `accounts.ensure_bcc` | 端口是否 open | 端口 ≠ 所有权 |
| `browser_gate.bcc_state` | 端口 + `/status.alive` | 同上，且 exclusive 字段无人维护 |
| `browser_daemon` 内部 | `_lock` + `_scan_exclusive` | **真正的所有权，但只有它自己知道** |

⇒ 没有单一事实源 ⇒ 每个调用方都在"猜"，猜错就分叉。

### 2.2 机制原因：约束靠"约定"，不靠"强制"

单例/门禁全部是**文档约定 + 调用方自觉**：
- "所有启动路径统一走同一入口" = 约定（12 处调用点各自遵守）
- "只允许一个 BCC" = 约定（`main()` 此前无守卫）

**约定无法防止新增代码破坏它**。这就是为什么我一写脚本就绕过了。

### 2.3 反馈原因：绕过是静默的

- gate 的 EXCLUSIVE 空壳 → `ok=True`（无感）
- `dispatch.py` 回退直发 → 只在 warning 里（可被忽略）
- 直开审计 `BCC-042` → **仅观测不阻断**（设计如此，但一直没收紧）

⇒ 绕过了没人知道 ⇒ 没有修正压力 ⇒ 机制自然腐化为吉祥物。

## 三、优化设计

### 3.1 设计原则（三条）

1. **资源所有权单一事实源**：任何资源的"当前持有者"只有一个权威记录，
   且**由持有者自己维护**（不是外部推测）。
2. **约束强制化，不靠约定**：关键约束做进**资源层自证**（谁想直接用资源，
   资源自己挡），而非写在文档里要求调用方遵守。
   *（已按此原则实施 BCC 单例硬守卫：profile 锁 + 端口双判据，`SystemExit(3)`）*
3. **绕过必须响**：任何绕过要么**阻断**，要么**显式告警到用户可见处**，
   绝不静默降级。

### 3.2 目标架构：分层调度器 + 资源租约

```
┌─────────────────────────────────────────────────────────────┐
│ L0 资源层（自证，不可绕过）                                  │
│   profile 锁文件（SingletonLock/lockfile）= 浏览器所有权真源  │
│   端口哈希 = 进程身份                                        │
│   → BCC 启动前自检：已有实例/锁 → SystemExit(3)  【已实施】   │
├─────────────────────────────────────────────────────────────┤
│ L1 租约层（唯一事实源，持有者维护）                          │
│   **新增 BCC 端点**：/lease /release /lease_status           │
│     · acquire(holder, purpose, ttl) → {granted, lease_id}   │
│     · 租约 = 全局互斥（同一时刻仅一个 holder）               │
│     · 到期自动释放（防死锁）                                 │
│   → 所有需要浏览器的操作**先取租约**，再干活                  │
├─────────────────────────────────────────────────────────────┤
│ L2 调度层（browser_gate 变实，不做事只决策）                 │
│   ensure_browser(account, purpose, holder) → 租约            │
│     · 串行化排他资源（同一账号浏览器是单例）                  │
│     · 优先级仲裁（用户显式 > 更新会话 > 后台保活）            │
│     · 拿不到就**显式失败/排队**，绝不"再起一个"               │
├─────────────────────────────────────────────────────────────┤
│ L3 业务层（只消费，不碰资源细节）                            │
│   capture_all / scan_login / wp_send / cookie 刷新 /         │
│   linkmic / 直播发送 ...                                     │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 与现有代码的对应关系（最小改动优先）

| 设计件 | 现状 | 改法 |
|---|---|---|
| **L1 租约端点** | ❌ 无（`_scan_exclusive` 是私有变量） | 新增 `/lease` `/release` `/status` 暴露 `lease` 字段 |
| **L1 所有权真源** | 🟡 `_lock` + `_scan_exclusive`（内部） | 提升为显式 lease 对象（holder/purpose/ttl/lease_id） |
| **L2 gate 变实** | 🔴 EXCLUSIVE 空壳 | 改为真正取租约；拿不到就失败/排队 |
| **L2 优先级仲裁** | ❌ 无（谁先到谁排队） | 加优先级队列（用户显式操作 highest） |
| **L3 调用点收敛** | 🟡 12 处 | 全部改为 `ensure_browser()` 取租约（含 `dispatch.py:328` 回退直发） |
| **L0 资源自证** | ✅ BCC 单例已做 | 保持；`accounts.ensure_bcc` 的端口判断改为查租约 |
| **发送闸门** | 🟡 在 recv_daemon 内（`_send_gate_acquire`） | 可保留（同机单进程无竞争），但**去掉 dispatch 回退直发** |

### 3.4 关键设计点

**① 租约（Lease）而非"让出"**

原设计的思路是"BCC 让出 profile"（gate 无法实现，因为 BCC 是独立进程、profile 由它持有）。
更正确的抽象是**租约**：

```
BCC 持有全局互斥锁（它本来就是唯一所有者，不需要"让出"）
   ↓
业务操作向 BCC 申请租约（holder="capture_all", purpose="auto", ttl=180）
   ↓
BCC 授予 → 该操作独占浏览器；其它操作排队或快速失败
   ↓
操作结束 → release（或 ttl 到期自动 release）
```

**好处**：不需要"交出 profile"这种跨进程不可能的操作，BCC 始终是所有者；
调度器只需**仲裁谁拿到租约**。

**② 优先级分类（避免保活挤掉用户操作）**

| 优先级 | 用途 | 例子 |
|---|---|---|
| P0 用户显式 | 用户点了按钮 | 更新会话、打开浏览器、扫码 |
| P1 业务自动 | 有用户在场触发的自动行为 | AI 回复、私信发送 |
| P2 后台保活 | 无人在场的周期任务 | keepalive 探活、昵称预热、uid 探测 |

规则：**P2 不得占用租约超过 N 秒**；P0 申请时 P2 立即让出。

**③ 绕过必须响（收紧观测）**

| 绕过 | 现状 | 改法 |
|---|---|---|
| `dispatch.py` 回退直发 | 静默 warning | **改为不发送 + 记 SEND 错误**（回退直发绕过风控闸门，风险最高） |
| `DY_ALLOW_STANDALONE_LAUNCH=1` | 免审计 | 改为**记录审计但仍放行**（保留逃生，但不静默） |
| 直开审计 `BCC-042` | 仅观测 | 稳定后**收紧为阻断**（或前端显式告警条） |

**④ 一致性校验：租约 ID 贯穿全链路**

每个业务请求带 `lease_id`，BCC 校验是否持有租约 ——
防止"没取租约就直接调 BCC"的路径（新增代码最容易犯）。
