## 一、证据闭环：为什么 gate 是空壳（三层证据）

```python
# services/browser_gate.py  L112-120
    if purpose == PURPOSE_AUTO:
        logger.info(f"[gate][{account}] 复用 BCC 容器 (port=..., alive=..., exclusive=...)")
    else:
        if not st["exclusive"]:                       # ← 读 st["exclusive"]
            logger.info(f"...需先令 BCC 让出 profile")  # ← 只打日志
    return {"ok": True, ...}                          # ← 直接返回成功
```

**证据 1（字段来源）**：`st` 来自 `bcc_state()`，其赋值是
`out["exclusive"] = j.get("exclusive")`，即读 BCC `/status` 的 `exclusive` 字段。

**证据 2（实测 `/status` 真实返回）**：
```json
{"alive": true, "account": "尚进工伤小助理", "profile": "C:\\temp\\...",
 "uid": 316276709526638, "last_refresh": 1789305978,
 "logged_in": false, "version": "0.43.3"}
```
**没有 `exclusive` 字段** ⇒ `j.get("exclusive")` **恒为 `None`**。

**证据 3（字段无维护者）**：全仓 `exclusive` 只出现在
`browser_gate.py`（读）与 `bcc_state()`（透传），**没有任何代码写入 `/status.exclusive`**。
BCC 内部真正的独占标志叫 `_scan_exclusive`（私有 dict），也**未对外暴露**。

⇒ 结论：`if not st["exclusive"]` **恒为真** → 永远走"只打日志"分支 → 永远 `ok=True`。
**完整空壳，且静默**。

## 二、真实现状：独占机制（要被整合，不是并存）

```python
# daemon/browser_daemon.py
class ContainerBusy(Exception):            # L92  独占期异常
    def __init__(self, holder: str = "scan_login"): ...

_scan_exclusive = {"holder": None}         # L98  全局单变量：None=空闲
def _is_busy() -> bool:                    # L101
    return _scan_exclusive["holder"] is not None

@app.exception_handler(ContainerBusy)      # L105 统一转 JSON（HTTP 200）
async def _container_busy_handler(...):    # → {ok:false, busy:holder, msg:...}

async def _exec(self, coro_factory):       # L716 锁 + busy 检查（11 端点走它）
    ...
    if _is_busy():
        raise ContainerBusy(_scan_exclusive["holder"])    # L724
    async with self._lock:                                 # L725
        if self._switching:
            raise ContainerBusy("切换可见性中（context 重建），请稍后重试")  # L730
```

**`_exec` 覆盖的 11 个端点**（`/status` `/quit` `/refresh` 不走）：
`/cookie /capture_userinfo /exec_js /resolve_url /linkmic_run /wp_messages
 /show /refresh(部分) /user_info /scan_login /(其余)`

**`_scan_exclusive` 的使用**：仅 `scan_login`（L1259 置位 / L1306 finally 清空）。

### 2.1 现有机制的四个缺口（细节问题，必须补）

| # | 缺口 | 后果 |
|---|---|---|
| 1 | **只有 holder 一个字段**（无 purpose/prio/lease_id/ts） | 无法区分用途与优先级；无法追溯谁持有了多久 |
| 2 | **无 TTL / 无自动释放** | 持有者若崩溃/超时未清 `finally` → **永久独占**，容器死锁（现仅靠 `finally` 兜底） |
| 3 | **无优先级** | 后台保活（P2）能与用户操作（P0）争抢；谁先到谁占 |
| 4 | **未对外暴露** | `/status` 不含它 → 调度器无从判断 → gate 只能猜（且猜错了） |

## 三、租约设计（细节）

### 3.1 数据结构

```python
_lease: dict = {
    "holder":     None,   # 持有者标识，如 "gate:update_conv" / "scan_login" / "keepalive"
    "purpose":    None,   # "auto" | "exclusive" | "keepalive"
    "prio":       None,   # 0=用户显式  1=业务自动  2=后台保活
    "lease_id":   None,   # uuid4().hex[:12]，校验"确实持有"
    "acquired_at": 0.0,
    "ttl":        0.0,    # 本次租约时长（秒）
    "expires_at": 0.0,    # acquired_at + ttl
    "renew_count": 0,
    "waited":     0.0,    # 为拿到它等了多久（可观测性）
}
```

### 3.2 端点契约（新增 3 个）

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/lease` | `{holder, purpose, prio, ttl, wait?}` | 成功 `{ok:true, lease_id, expires_at, waited}` / 失败 `{ok:false, busy, prio, retry_after}` |
| POST | `/lease/renew` | `{lease_id, ttl}` | `{ok:true, expires_at}` / `{ok:false, reason:"not_holder"\|"expired"}` |
| POST | `/lease/release` | `{lease_id}` | `{ok:true}` / `{ok:false, reason:"not_holder"}` |
| GET | `/lease_status` | — | `{holder, purpose, prio, lease_id, expires_at, remaining, renew_count}`（空闲时全 None） |

**同时修 `/status`**：新增 `"lease": {...}` 子对象（**保留全部旧字段**，不破坏现有读取）。

### 3.3 状态机

```
                ┌──────── acquire(prio=P) ────────┐
                │                                 ▼
   ┌─────────┐  │ 授予                      ┌───────────┐
   │  FREE   │──┴─────────────────────────▶│   HELD    │
   │ holder= │                             │ holder=H  │
   │ None    │◀────────────────────────────│ ttl=T     │
   └─────────┘   release / TTL 到期        └───────────┘
                                                  │
                                          acquire(prio=Q) 来时：
                                          Q == 持有者prio → 拒绝 busy（或 wait 限时）
                                          Q  > 持有者prio → 拒绝 + retry_after=remaining
                                          Q  < 持有者prio → 拒绝 + retry_after=remaining
                                          （统一策略：不抢占，见 §3.4）
```

### 3.4 关键决策：**不做真抢占**（细节规划的核心取舍）

**候选方案**
- A. **真抢占**（高优先级强制打断低优先级）：会中断正在执行的浏览器操作
  （如 capture 滚到一半、wp_send 已输入未发送）→ **状态不一致**，风险高。
- B. **不抢占 + 短 TTL + 快速失败**（推荐）：低优先级自己限制 TTL（≤30s），
  高优先级拿不到就 `retry_after` 短等（因为低优先级很快就会释放）。
  **任何操作都不会被半途打断**，语义最干净。
- C. 抢占但等安全点：复杂度高（需定义"安全点"），收益不抵复杂度。

**选定 B**。理由：
1. 浏览器操作大多**不可中断**（DOM 流程、context 重建）；
2. "抢占"要解决的其实是"P2 霸占"问题，而 **P2 限时**已足够解决；
3. 与现有 `_scan_exclusive` 语义一致（scan_login 独占期内其他**立即失败**，不抢占）。

**配套**：P0 拿不到时的 `retry_after` 必须**短**（因 P2 ttl ≤ 30s），
前端体验为"稍等片刻自动重试"，而非报错。

### 3.5 优先级与 TTL 上限（硬约束）

| prio | 名称 | 用途 | **TTL 上限** | 拿不到时的行为 |
|---|---|---|---|---|
| 0 | 用户显式 | 更新会话 / 打开浏览器 / 扫码 / 手动发送 | 300s | `retry_after` 短等（≤30s）后重试 |
| 1 | 业务自动 | AI 回复 / 私信发送 / 凭证刷新 | 180s | 短等 → 失败则**降级**（如走 WS 通道） |
| 2 | 后台保活 | keepalive 探活 / 昵称预热 / uid 轮询 | **30s（硬上限）** | 直接跳过本轮（下轮再来） |

**规则**：`ttl > 该 prio 上限` → **拒绝 acquire**（`{ok:false, reason:"ttl_exceeds_limit"}`），
防止调用方写出"P2 持 10 分钟"这种把调度器架空的行为。

### 3.6 与 `_exec` 的关系（最小侵入的关键）

**设计：租约做进 `_exec`，成为其前置门**——11 个走 `_exec` 的端点**自动纳入调度**，
无需逐个改造。

```python
async def _exec(self, coro_factory, holder="", purpose="auto", prio=2, ttl=30):
    # 未声明 holder 的调用方 → 视作后台保活（P2），保守授权
    lid = _lease_acquire(holder or _auto_holder(), purpose, prio, ttl)  # 冲突则 raise ContainerBusy
    try:
        async with self._lock:
            if self._switching:
                raise ContainerBusy("切换可见性中（context 重建），请稍后重试")
            return await coro_factory()
    finally:
        _lease_release(lid)
```

**两类使用方式**：

| 类型 | 场景 | 做法 |
|---|---|---|
| **单次调用** | capture_userinfo / exec_js / cookie / wp_send… | 走 `_exec` 自动租约（**零改造**） |
| **跨调用窗口** | scan_login（关 context → 扫码 → 重启）、更新会话全程 | 显式 `POST /lease` + `release`，`_exec` 检测到"已持有"则复用（同 lease_id） |

**关键细节**：`_exec` 需支持**租约继承**——若当前线程/请求已持租约（同 holder），
则复用它而非再次 acquire（否则自己和自己冲突）。

### 3.7 失败模式与边界（逐条规划）

| 场景 | 行为 | 错误码 |
|---|---|---|
| 持有者进程崩溃，TTL 未到 | TTL 到期**自动释放**（`_lease` 读取时惰性判定 `now > expires_at` → 视为空闲） | `BCC-046`（到期释放日志） |
| 调用方忘记 release | 同上层（TTL 兜底） | 同上 |
| 未持租约直接调受保护端点 | 走 `_exec` 时自动 acquire（**不算违规**，但记 debug）；**若显式传了 lease_id 却对不上** → 拒绝 | `BCC-047` |
| 同一 holder 重入 | 复用现有租约（`renew` 而非新建） | — |
| `renew` 超过 prio 上限累计时长 | **拒绝 renew**（防"续租绕过 TTL 上限"） | `BCC-048` |
| scan_login 期间其它请求 | 立即 `{ok:false, busy:"scan_login"}`（**保持现有行为**） | `BCC-033`/`ContainerBusy` |
| 租约被 `preempt`（本设计不做） | — | — |
| `DY_LEASE_MODE=off` | 全部回退旧行为（仅 `_scan_exclusive`） | — |

**惰性 TTL 判定**（无需后台定时器）：
```python
def _lease_current():
    if _lease["holder"] and time.time() > _lease["expires_at"]:
        logger.warning("BCC-046", f"[lease] {_lease['holder']} 租约超时，强制释放")
        _lease_reset()
    return _lease if _lease["holder"] else None
```

### 3.8 可观测性（排查必备）

- `GET /lease_status`：当前持有者/用途/优先级/剩余时间
- `/status.lease`：同上（供 gate 与前端读）
- 日志：acquire 成功（含 waited）、busy 拒绝（含 retry_after）、TTL 到期、renew 拒绝
- **调度统计**（可选）：每 prio 的 acquire 次数/平均等待/拒绝率 → 判断调度是否合理

## 四、`browser_gate` 变实（消除空壳）

```python
def ensure_browser(account, purpose=PURPOSE_AUTO, holder="", prio=None, ttl=None, wait=False):
    """取租约 + 返回句柄。拿不到就显式失败/短等，绝不'再起一个'。"""
    st = bcc_state(account)                    # 含 lease 字段（修好后）
    if not st["online"]:
        ensure_daemons_for(account, wait=True)  # 唯一拉起入口
        st = bcc_state(account)
        if not st["online"]:
            return {"ok": False, "msg": "BCC 未就绪…"}   # 显式失败
    # 真取租约（替换原来的"只打日志 + ok=True"）
    r = _lease_acquire_http(st["port"], holder, purpose, prio, ttl, wait)
    if not r["ok"]:
        return {"ok": False, "busy": r["busy"], "retry_after": r["retry_after"],
                "msg": f"浏览器正被 {r['busy']} 使用（约 {r['retry_after']}s）"}
    return {"ok": True, "owner": "bcc", "port": st["port"], "lease_id": r["lease_id"]}
```

**关键**：`purpose` 决定 prio 默认值；`ttl` 由 prio 上限兜底校验。

## 八、待拍板的细节（4 题）

1. **不抢占（方案 B）是否认可？** —— 高优先级拿不到时"短等 + 重试"，
   而不是打断正在进行的低优先级操作。（推荐理由见 §3.4）
2. **TTL 上限表（P0=300s / P1=180s / P2=30s）是否合理？**
   尤其 P2=30s：keepalive 含 uid 探活 + 页面级检查，30s 是否够？
3. **`dispatch.py` 去掉回退直发**：会导致"dm_dispatch 不可用时**不发**"（而不是绕过闸门直发）——
   语义更安全，但可能表现为"少发"。是否接受？
4. **实施节奏**：S2.0→S2.8 逐步（每步一次构建验证），还是合并为 2~3 批？
