## 十四、「更新会话」端点与引擎校验职责收敛（2026-08-29）

### 14.1 职责边界（铁律，勿再混用）

| 入口 | 触发 | 做什么 | 耗时 | 可否高频 |
|---|---|---|---|---|
| **引擎校验**（账号页） | `POST /api/accounts/{name}/check` | **只判守护活性**：wp=凭证四件套+探活，dm=recv_daemon/browser_daemon 端口 | **~2.6s** | 可 |
| **更新会话**（私信页按钮） | `POST /api/messages/{account}/refresh` | 真跑 `capture_all`：拉会话列表+聊天记录写库 | ~9~42s | 否（用户点按钮） |

**历史问题**：引擎校验的 dm 分支原会触发 `capture_all`，导致点一次校验要等 60~180s
（BCC 滚动截昵称 + 首包解析 + 301 补全）。用户明确要求收敛为
「只保留校验守护凭证和私信守护的有效性」→ dm 分支改为纯端口活性检测。

### 14.2 引擎校验 dm 分支新逻辑（`accounts.verify_account`）

```python
if dm_loopback:
    bport = browser_daemon_port(name)
    rport = recv_daemon_port(name)
    ensure_daemons_for(name)          # 幂等拉起（端口已开则跳过）
    b_ok = _port_open(bport, timeout=0.5)
    r_ok = _port_open(rport, timeout=0.5)
```

| recv_daemon | browser_daemon | level | label |
|---|---|---|---|
| ✅ | ✅ | ok | 私信守护正常 |
| ✅ | ❌ | warn | 私信守护在，凭证守护缺失（昵称关联可能失效） |
| ❌ | ✅ | warn | 凭证守护在，私信守护缺失（实时新消息不入库） |
| ❌ | ❌ | fail | 私信守护未运行 |

`dm_loopback=False`（列表轮询场景）仍沿用 wp 结果作轻量近似，不探端口。

### 14.3 更新会话端点（`api/messages.py`）

```python
@router.post("/{account}/refresh")
async def refresh_conversations(account, body: RefreshConvsRequest | None = None):
    ensure_daemons_for(account)                 # 捕获依赖 BCC 常驻浏览器
    n_conv, n_msg = capture_all(account, with_browser=use_browser)
    return {"ok": True, "n_conv": n_conv, "n_msg": n_msg, "elapsed": ...}
```

**风控边界**：昵称仍只来自 BCC 被动截获 `im/user/info`，后端零主动批量查昵称；
聊天记录走首包(2043) + 长会话 cmd 301 补全（见 §十三）。

### 14.4 前端改动

- `client.ts`：`api.refreshConversations(account, withBrowser=true)`
- `messages.tsx`：会话列表标题行「＋ 新建会话」**左侧**加「⟳ 更新会话」按钮
  - 禁用态：无选中账号 / 更新进行中（防重复点击）
  - 反馈：`push(...)` 提示 + `a.addLog(...)` 写日志
  - 完成后 `convsQ.refetch()` 立即刷新，不等 5s 轮询
  - **注意**：messages.tsx 里 API 实例是 `a`（= `props.api`），
    不是 accounts.tsx 那种 import 的裸 `api`，别写错。
- `accounts.tsx`：引擎校验「校验中…」detail 改为
  「正在检测私信守护与凭证守护的有效性（不拉取会话列表）」

## 十五、聊天记录「解析成功但前端不显示」根因与修复（2026-08-29 实测）

### 15.1 现象

后端 capture_all 明明解析并写入了聊天记录（实测「转角遇到」46 条，
库内 dm_messages 按会话 50/44/39 条），但私信页点开会话，聊天框恒空。

### 15.2 根因（两条叠加，实测定位）

| # | 位置 | 问题 |
|---|---|---|
| 1 | 后端 list_conversations（列表接口） | 构造 conv 时**硬编码 messages 为空数组** —— 列表接口从不携带消息体 |
| 2 | 前端 messages.tsx 的 openConv | 点进会话只做 setActive(id)，**从未调用详情接口**拉真实聊天记录 |

**后端**：详情接口 `GET /api/messages/conversation` 补前端消费命名，

- role（me / them）、text、msg_type —— 后端原生命名
- dir（out / in）、type、time（HH:MM）—— 前端 Msg 接口命名

**前端**：openConv 点进会话时调 getConversation，用
`qc.setQueryData(["msg-convs", activeAcct], ...)` 回填该会话的 msgs。

### 15.4 踩坑（已踩两次，勿重犯）

- messages.tsx 里 API 实例是 **`a`**（= `props.api`），**不是** accounts.tsx
  那种 import 的裸 `api`。写 `api.addLog(...)` 会编译失败。
- 用 `qc.setQueryData` 需先 `import { useQueryClient }` 并声明
  `const qc = useQueryClient()`。
- 列表接口保持 messages 为空是**有意的**（222 个会话全带消息体会很大），
  **不要**改成列表带消息；正确做法是点进会话再拉详情。

## 十六、列表乱跳 / 回执刷屏 / 启动自动抓包（2026-08-29 实测，v0.31.1）

### 16.1 启动自动抓包（风控问题，用户指出）

**现象**：用户没点「更新会话」，日志却显示 `get_message_by_init` + 20 次
cmd 301 补全 —— 每次开软件都在抓包。

**根因**：`main.py` 在 lifespan 里启动 `_nickname_sync_background` 守护线程，
sleep 45s 后自动调 `capture_all(with_browser=True)`。

**修复**：改为开关控制，**默认关闭**。私信页纯读库，需要更新时点「更新会话」。

- 开启方式：环境变量 `DY_AUTO_CAPTURE_ON_START=1`
- 铁律：**私信页读取 = 纯读 SQLite，绝不触发任何网络捕获**。
  网络捕获只允许两个入口：用户点「更新会话」按钮，或账号页引擎校验（仅探守护端口）。

### 16.2 会话列表乱跳 + 点开后聊天记录变空

**现象**：列表每 5s 自动重排（前 20 名全换一批），点开的会话聊天框变空。

**两条根因叠加**：

| # | 位置 | 问题 |
|---|---|---|
| 1 | `api/messages.py::list_conversations` | 仅 `ORDER BY last_ts DESC`，大量会话 last_ts 相同/相近时**顺序不稳定**（依赖 SQLite 内部扫描顺序，而表持续被 WS 写入） |
| 2 | `messages.tsx` 列表项 id | `id: "rc" + i` 用**数组下标**当 id，排序一变下标就变 → `active` 失配 |

**实测**：连续 4 次列表轮询（间隔 5s），前 20 名**每次都完全不同**。

**修复**：

```sql
-- 加二级排序键，保证顺序确定
ORDER BY last_ts DESC, conv_id ASC
```

```tsx
// id 用会话唯一标识，不随排序变化
id: c.conv_id || "rc" + i,
```

同时 `send()` 的会话有效性校验从 `conv.id.indexOf("rc") !== 0`
改为 `!conv.conv_id`（id 语义已变）。

**铁律**：列表项 React key / 选中态标识**必须用业务唯一键（conv_id）**，
禁用数组下标 —— 任何会重排序的列表用下标都会导致选中态错位。

### 16.3 「对方已读」回执刷屏挤掉真实聊天记录

**现象**：聊天框里大量重复无意义内容，真实对话被挤掉。

**根因**：`msg_type=50001`（「对方已读 标号 X」回执）经 WS 反复写入：

- 无 msg_id → `uniq_dmmsg` 唯一索引（要求 msg_id NOT NULL）**管不到**
- 每次 WS 同步重复写入 → 实测全库堆积 **2368 条**（占当时总量 80%）
- 且不断刷新会话 `last_ts` → 加剧 16.2 的排序抖动

**修复**（双管齐下）：

1. `recv_daemon.add_message` 对 `msg_type == "50001"` **直接不落库**
   （仅 `get_or_create` 维持会话存在，不写 dm_messages、不刷 last_ts）
2. 详情接口查询加过滤 `AND msg_type <> '50001'`
3. 已清理历史脏数据 2368 条（真实消息 586 条保留）

### 16.4 「分享视频」卡片的来源（非脏数据）

`recv_daemon.py` 对 `msg_type == 8` 解析为 `[分享视频] 视频ID xxx`。

这是 **WS 推送的真实内容**（对端真的分享了视频），不是脏数据，
与 16.3 的 50001 回执性质不同 —— 不要一并过滤掉。
若嫌展示简陋，应改进渲染（显示为视频卡片），而非过滤。

> ⚠️ **2026-09-16 实机修正（设计漂移）**：尽管本条早已写明"不要过滤"，
> 后续 `_NOISE_PATTERNS` 仍加了裸 `"[分享视频]"` 子串 ⇒ **带 ID 的真实分享
> 也被写侧拦截**；读侧 SQL `NOT LIKE '[分享视频]%'` 同样滤掉。已改为：
> 只拦**整条等于** `"[分享视频]"`（无 ID 的解析噪音），带 ID 的放行。
> 顺带修复 `_pull_conversations_api` 两处 INSERT **缺 msg_id 列** ⇒ 补拉与
> WS 写入同一条消息时 uniq_dmmsg 管不到 → 重复入库（实测 id=1638/1655
> 两条同文本并存）。**教训：所有写 dm_messages 的路径必须带 msg_id。**

### 16.5 消息类型速查

| msg_type | 含义 | 处理 |
|---|---|---|
| `text` | 文本 | 正常展示 |
| `8` | 分享视频 | 真实内容，正常展示（可优化为卡片渲染） |
| `27` | 图片 | 真实内容（URL 存 text） |
| `50001` | **对方已读回执** | **不落库、不展示** |

### 16.6 版本号

前后端均改动 → 版本 `0.31.0` → **`0.31.1`**（package.json / tauri.conf.json / Cargo.toml）。

提交：`2bd8c36`。

## 十七、聊天记录被列表轮询清空（2026-08-29 实测，v0.31.2）

### 17.1 现象

用户反馈：**「确实没乱跳了，但聊天记录也没了」**。

（上一版修好乱跳后立刻暴露 —— 原先「乱跳」掩盖了这个问题。）

### 17.2 根因

上一版把会话详情消息用 `qc.setQueryData(["msg-convs", acct], ...)` 写回
**列表缓存**，但列表 query 带 `refetchInterval: 5000`：

- 每 5s 用后端新数据**整体覆盖** `["msg-convs"]` 缓存
- 而列表接口 `/conversations` 的 `messages` **恒为 `[]`**
- → 点开会话时消息能显示，**5 秒内就被下一次列表轮询清空**

### 17.3 修复

聊天记录改用**独立 query**，与列表缓存解耦：

```tsx
const detailQ = useQuery({
  queryKey: ["msg-detail", activeAcct, conv.conv_id],
  queryFn: async () => { /* GET /api/messages/conversation */ },
  enabled: !!ready && !!activeAcct && !!conv.conv_id,
  staleTime: 3000,
});

const convMsgs: Msg[] = detailQ.data || conv.msgs || [];
```

配套改动：

- `openConv` 只做 `setActive(id)`，**不再手动拉取与回填**
- 渲染数据源从 `conv.msgs` 改为 `convMsgs`
- 移除已不再使用的 `qc`（useQueryClient）及 import

### 17.4 铁律（本次核心教训）

> **凡是被轮询（`refetchInterval`）覆盖的缓存，绝不能往里塞需要长期保留的数据。**
> 派生数据 / 详情数据必须用**独立 queryKey**。

典型错误模式（勿重犯）：

```tsx
// ❌ 错：写进轮询缓存，5 秒后被清空
qc.setQueryData(["msg-convs", acct], (old) => /* 塞 msgs */);

// ✅ 对：独立 queryKey，不受列表轮询影响
useQuery({ queryKey: ["msg-detail", acct, convId], ... });
```

### 17.5 三个相关问题的因果链

```
列表 id 用数组下标
  └─> 排序变化导致 id 错位 ──> 会话「乱跳」+ 聊天框变空
        └─> 改用 conv_id 修好乱跳
              └─> 暴露「回填消息被 5s 轮询覆盖」──> 记录消失
                    └─> 改用独立详情 query 修好
```

版本：`0.31.1` → **`0.31.2`**。提交：`83d1fc6`。

## 十八、空会话霸占列表顶部，点开的会话永远「暂无消息」（2026-08-29，v0.31.3）

### 18.1 现象

用户反馈「依旧没有聊天记录」。

先排除部署问题（这是怀疑的第一方向，但**不是**原因）：

```
md5sum DYAutoDM_v2_0.31.2.exe
       target/release/dyautodm-v2.exe
-> 两者一致，且 exe 内含新 dist bundle 文件名
```

**md5 比对是排查「是否部署成功」最快的手段**，比看时间戳可靠。
（exe 内前端 bundle 是压缩存储的，grep 搜不到源码标识符如 msg-detail，
不要据此误判「没部署」—— 应比对 md5 或搜 dist 产物文件名。）

### 18.2 根因（实测）

用 computer_use 实机截图，确认选中的会话确实显示「暂无消息」。查库：

| 项 | 实测 |
|---|---|
| 总会话 | 222 |
| **空会话（0 条消息）** | **180** |
| 有真实消息的 | 42 |

**空会话的 `last_ts` 反而更大**（被 WS 同步/回执刷新）。

上一版（§十六）为修「乱跳」把排序改为 `ORDER BY last_ts DESC, conv_id ASC`
—— 顺序确实稳定了，但**排序依据 `last_ts` 本身是脏的**：

```
空会话   max_last_ts = 1787980449.5
有消息会话 max_last_ts = 1787980326.8   <- 更小，排在后面
```

结果：180 个空会话霸占列表顶部，用户从上往下点，点到的永远是空会话。

实测列表前 10 名**全部 0 条**：

```
用户8924329957748  0 条
抖音知识观察员      0 条
妍宝              0 条
老男人，阿坤        0 条
...
```

而有消息的（蛋蛋后 44 / 地上跑 39 / 转角遇到 38）全被挤到后面。

### 18.3 修复

列表排序改为「**有真实消息的会话优先**」：

```sql
SELECT c.conv_id, c.peer_id, c.peer_name, c.short_id,
       c.last_ts, c.unread, c.avatar
FROM dm_conversations c
LEFT JOIN (SELECT conv_id, COUNT(*) n FROM dm_messages
           WHERE account=? AND msg_type <> '50001'
           GROUP BY conv_id) m
  ON m.conv_id = c.conv_id
WHERE c.account=?
ORDER BY COALESCE(m.n, 0) DESC, c.last_ts DESC, c.conv_id ASC
```

注意：SQL 里有两个 `?`，参数要传 `(account, account)`。

三条排序键各有职责，**缺一不可**：

| 排序键 | 作用 |
|---|---|
| `COALESCE(m.n,0) DESC` | 有消息的排前面（本次新增，修 18.2） |
| `last_ts DESC` | 同级内按活跃度 |
| `conv_id ASC` | 保证顺序确定，避免 5s 轮询乱跳（§十六） |

### 18.4 实测（新排序）

```
44 条 蛋蛋后
39 条 地上跑
38 条 转角遇到💕
28 条 殇秋
27 条 承 诺
...
42 个有消息的会话全部排到列表前列
```

### 18.5 教训

- **排序依据的字段必须验证其语义是否可信**。修「顺序不稳定」时只想着加二级键，
  没意识到 `last_ts` 会被无消息的事件（WS 回执/同步）刷新，
  导致「稳定地把错误结果排在前面」—— 比乱跳更隐蔽。
- 排查「前端看不到数据」时，先把**后端返回的实际数据**打出来看，
  确认是「接口没返回」还是「前端没渲染」，不要凭现象猜。

### 18.6 排查「是不是没部署」的标准流程

```bash
# 1) md5 比对部署文件与构建产物（最可靠）
md5sum <部署目录>/DYAutoDM_v2_<ver>.exe <源>/target/release/dyautodm-v2.exe

# 2) 确认 exe 内含新的前端 bundle（搜 dist 产物文件名，不是源码标识符）
grep -c "index-<hash>" <部署 exe>

# 3) 确认源码里确有该改动
grep -c "<特征串>" frontend/src/pages/xxx.tsx
```

## 十九、富媒体消息解析与气泡渲染规范（2026-08-29，v0.31.4）

### 19.1 四类消息必须区分渲染

| 类别 | 判定 | 渲染 |
|---|---|---|
| 普通对话 | 有真实文本 | 左(对方) / 右(我) 气泡 |
| **系统提示** | `你已确认聊天` / `Recall Content Hided` / `消息已撤回` 等 | **居中**虚线小气泡（`.msg.sys`） |
| 图片 / 表情包 | 文本含媒体 URL | `<img>` 缩略图预览 |
| 撤回 | `Recall Content Hided` | 归入系统提示 |

**关键**：系统提示**不是对话内容**，不能按 dir 左右分列，
否则「你已确认聊天，对方可继续向你发送消息」会被当成"我发的消息"。

### 19.2 富媒体 URL 丢失的根因（重要）

后端首包解析（`conversation_capture.parse_init_protobuf`）原逻辑：

```python
text = obj.get("text") or obj.get("tips")
if not text:
    continue          # <- 图片/表情/语音没有 text 字段，整条被丢弃
```

抖音的**图片/表情/语音/视频卡片消息没有 `text` 字段**，
只有 `resource_url` / `url` / `itemId`。
结果：这类消息被整条 `continue` 丢弃，或只剩「图片」二字（无 URL）。

**修复**：新增 `_extract_media_text(obj)`，按类型提取媒体 URL：

```python
resource_url.origin_url_list[0]  ->  "[图片] <url>"
url.url_list[0]                  ->  "[表情包] <url>"
itemId                           ->  "[分享视频] 视频ID <id>"
兜底                              ->  "[未知媒体] <json前200字符>"
```

实测：

```
图片           -> [图片] https://p.img/abc.jpeg
图片仅url_list -> [图片] https://p.img/only.jpeg
表情包         -> [表情包] https://p.img/sticker.webp
分享视频        -> [分享视频] 视频ID 7300000001
纯文本         -> 你好
```

### 19.3 WS 侧同样要修（recv_daemon._extract）

`t == 5`（表情）/ `t == 27`（图片）的原兜底分支也会丢 URL。
改为按优先级取：`origin_url_list` → `url_list` → 才退化占位。

**不能只修首包解析** —— 两条链路（HTTP 首包 + WS 实时）都要覆盖。

### 19.4 前端渲染

```tsx
function extractImageUrl(text: string): string {
  const m = (text || "").trim().match(/https?:\/\/\S+/);
  return m ? m[0] : "";
}
```

- 有 URL → `<a class="imgbubble"><img src={url}></a>`（最大 220×240，点击看原图）
- 无 URL 的历史数据 → `[图片]（无图链，需重新捕获）`

### 19.5 时间对齐

`.msg .mtm` 原为 `align-self: flex-end`（贴气泡底部），改为 `center` 垂直居中。

### 19.6 消息类型速查（更新版）

## 二十、抖音 IM 图链是私有加密格式，不能内嵌预览（2026-08-29 实测）

### 20.1 现象

把图链直接塞进 `<img src=...>` 后，界面显示**报错/破损图片图标**。

### 20.2 实测根因

取一条真实图链（如 `https://p11-sign.douyinpic.com/tos-cn-o-00061/...`
`~tplv-x-get:.image?lk3s=...&x-expires=...&x-signature=...`）直接请求：

```
HTTP: 200
Content-Type: application/octet-stream
总字节: 369293
前 64 字节: e2fdd402 3e2c47f3 1c1f2837 930a45be 9e8580d4 878c6d0c ...
```

**关键**：在**全部 369293 字节**里搜索标准图片魔数，**一个都没有**：

| 格式 | 魔数 | 出现位置 |
|---|---|---|
| JPEG | `ffd8ff` | -1（不存在） |
| PNG | `89504e47` | -1 |
| WebP | `RIFF` | -1 |
| GIF | `GIF8` | -1 |
| HEIC | `ftyp` | -1 |

抽 3 条不同图链，首 8 字节各不相同且都不是标准格式：

```
e2fdd4023e2c47f3
d3aa3b25f7e135ec
6ef25b2a9fa4f29c
```

**结论**：抖音 IM 的图片是**私有加密/封装格式**（不是加了私有头的 JPEG，
而是整段数据流都非标准），浏览器 `<img>` 无法解码。

### 20.3 结论与处理

**图链预览这条路技术上不可行** ——
除非逆向抖音的解密算法（成本高、且主动解密属高风险操作，违反风控红线）。

**正确做法：降级为可点击链接 + 明确说明**

```tsx
// 不能用 <img src={url}>，会显示破损图标
<div className="bubble medialink">
  <span className="mlabel">[图片]</span>
  <a href={url} target="_blank" rel="noreferrer">点击查看原图</a>
  <span className="mhint">（抖音加密格式，不支持内嵌预览）</span>
</div>
```

用户点击后在浏览器打开：抖音服务器会返回该 URL，
至于能否在浏览器里正常显示取决于抖音自己的解码能力，
但**在本应用内嵌渲染是不可行的**。

### 20.4 排查方法（可复用）

拿到媒体 URL 后，**先验证是否真的可渲染**，不要想当然：

```python
d = urllib.request.urlopen(req, timeout=15).read()
for name, sig in [("JPEG", bytes.fromhex("ffd8ff")),
                  ("PNG", bytes.fromhex("89504e47")),
                  ("WEBP", b"RIFF"), ("GIF", b"GIF8"),
                  ("HEIC", b"ftyp")]:
    print(name, d.find(sig))     # 全为 -1 => 非标准格式
```

若 `Content-Type: application/octet-stream` 且无任何图片魔数，
即可判定为私有格式，**不要**尝试 `<img>` 渲染。

### 20.5 顺带：过滤「[未知媒体] {}」噪音

空媒体对象（解析出 `{}`）会被兜底逻辑存成 `[未知媒体] {}`，
污染聊天记录。三层防护：

1. `_extract_media_text()` 遇空 dict 返回 `None`（调用方丢弃）
2. 后端详情接口 SQL 加 `AND text NOT LIKE '[未知媒体]%'`
3. 前端 `detailQ` 加 `.filter(m => !/^\[未知媒体\]/.test(m.text))`

版本：`0.31.5` → **`0.31.6`**。提交：`1e1be3d`。

## 二十一、图片消息解析根因与图床方案（2026-08-30 实测，`0.31.7`）

> 本节全部结论来自实机探针 + 首包原始字节离线分析（首包 1,304,194 字节，
> 存于 `C:\temp\dyautodm_design\ws_capture\init_raw.bin`），**不是代码推断**。

### 21.1 图片数据到底存在哪（决定性结论）

**图片既不是 DOM 捕获，也不是 HTTP 拉取——是内嵌在 protobuf 消息体里。**

解析出的图片消息 JSON（实测 8418 字节，35 个字段）关键结构：

```json
{
  "inline_pic":  "UklGRroQAABXRUJQVlA4IK4QAADwPQCdASpJAKAA...",  // base64，5898 字符
  "inline_sign": "db1b414e42a987d841bf0df371826be739bd2d43...",
  "md5":         "b068dc0f90e57fea539a185479bafe73",
  "cover_width":  1206,
  "cover_height": 2622,
  "resource_url": {
    "data_size":       292635,
    "thumb_url_list":  ["https://p3-sign.douyinpic.com/...~tplv-x-get:thumb.image?..."],
    "medium_url_list": [...],
    "large_url_list":  [...],
    "origin_url_list": ["https://p5-ex-gddgtc-sign.douyinpic.com/...~tplv-x-get:.image?..."],
    "long_url_list":   [],
    "md5":  "0eeacbbe45da557ec5325721fb4586a0",
    "skey": "d7f38a76ddcbe5743a2376667c6136e56077ea580ced378b8bf675695cfcd1bd"
  }
}
```

| 来源 | 实测结论 |
|---|---|
| **`inline_pic`** | **图片本体**。base64 编码的**标准 WebP**（`RIFF....WEBP`）。实测 27/35 条可用，平均 3.5KB，典型 160×213。零请求、零风控 |
| `resource_url.*_url_list`（thumb/medium/large/origin 四组） | **全部为抖音私有加密格式**。实测 HTTP 200 但 `Content-Type: application/octet-stream`，**熵 7.955~7.999 / 8.0**，256 种字节值均匀分布，**无任何标准图片魔数**。浏览器 `<img>` 必报破损图标 |
| `skey` | 远程图的解密密钥。**未逆向**（高风险，且违反风控边界） |

**与用户 `图链地址.md` 的相互印证**：用户从抖音网页复制图片得到的
`data:image/png;base64,UklGR...`，其 `UklGR` 前缀 = base64 的 `RIFF`，
与 `inline_pic` 前缀**逐字符一致**——证明网页显示的就是 `inline_pic` 解码产物。

**解释了此前全部疑点**：
- 前端为何从不发图片 HTTP 请求（探针实测 `fetch.img=0` / `xhr.img=0`）→ 字节已在消息里
- 远程图链为何解不开 → 那是备用引用且加密
- 前端网络面板出现 `blob:https://www.douyin.com/...` → 解密后包成 Blob 给 `<img>`

### 21.2 两个解析 bug（图片消息解析后为 0 条的真因）

首包原始字节里 `inline_pic` 出现 **40 次**、`resource_url` 出现 **44 次**，
但 `parse_init_protobuf` 解析后**图片消息 0 条**。两个独立 bug：

| # | 位置 | 问题 | 证据 |
|---|---|---|---|
| 1 | `_parse_message_text` | 只接受含 `"text"` 的字符串，且 `obj["text"]` 非空才返回。图片消息**没有 text 字段** → 第一关 `continue` 丢弃 | spy 挂载确认 `_extract_media_text` 被调用 **0 次** |
| 2 | `_extract_str` | 有 `if 1 <= len(s) <= 800` 硬上限（原为过滤短噪音设计）。图片消息 content JSON 实测 **8KB+**（含 inline_pic base64）→ 整条被过滤 | 构造 8418 字节消息测试，只提取到 **1 个长度=1 的字符串** |

**修复**（`backend/auto_dm/conversation_capture.py`）：
1. 新增 `_extract_long_str(b, min_len=200, max_len=200000)` —— 只放宽长度上限，
   其余提取规则与 `_extract_str` 一致。**单独提供，不动 `_extract_str` 的短串语义**
   （避免影响依赖它的其他逻辑）。
2. `_parse_message_text` 改**双路径**：先走原短串路径（文本消息行为完全不变），
   失败后用 `_extract_long_str` 重试富媒体（匹配 `resource_url` / `inline_pic`）。

**修复后实测**：图片/表情类消息从 **0 条 → 23 条**。

### 21.3 图床方案（imgbb）

**动机**：`inline_pic` 虽能渲染，但把数千字节 base64 塞进每条消息会让 SQLite
迅速膨胀（35 条图片消息合计 94KB，规模化后 MB 级），且前端每条都要解析长串。

**实测验证（`C:\temp\dyautodm_design\_test_imgbb.py`）**：

| 验证项 | 结果 |
|---|---|
| 上传 | HTTP 200 ✅ |
| 返回图链 | `https://i.ibb.co/PsHHS7cP/d0757376afa5.webp` |
| Content-Type | `image/webp`（标准格式）✅ |
| 下载字节 | 4290B，**与原图完全一致** ✅ |
| `expiration` | **0 = 永久保存** ✅ |

**实现**：新增 `backend/auto_dm/image_host.py`
- Key 走 `settings.imgbb_api_key`（env `IMGBB_API_KEY`，从 **`backend/.env`** 读），**不硬编码**
- SHA1 去重缓存（同图只传一次）
- 超时 20s；**失败降级保留内联 base64**，绝不干扰主捕获流程
- 未配置 Key 时静默跳过（仅首次提示一次）

**隐私提示（已向用户确认接受）**：imgbb 图床链接**公开可访问且 expiration=0 永久保存**。

**已知限制**：imgbb 为境外服务，偶发 SSL 握手超时（实测 23 条中 1 条），
自动降级为内联 base64，功能不受影响。

### 21.4 输出格式与前端渲染

后端 `_extract_media_text` 输出（按行）：

```

[原图] https://p5-ex-gddgtc-sign.douyinpic.com/...  ← 原图远程引用（加密，仅跳转）
```

前端 `messages.tsx` 新增 `parseMedia(text)` 拆双 URL，`MediaInfo` 类型：

```ts

// inline = data: URI 或 i.ibb.co 图床链 -> 可直接 <img> 渲染
// 其余（抖音 p*-sign.douyinpic.com）-> 降级为可点击链接
```

### 21.5 实测排障方法（可复用）

1. **验证媒体 URL 能否渲染**：请求后检查前 16 字节魔数
   （JPEG `ffd8ff` / PNG `89504e47` / WebP `52494646` / GIF `GIF8` / HEIC `ftyp`）。
   全不匹配 + `Content-Type: octet-stream` → 私有加密。
2. **算香农熵**：接近 8.0 且 256 种字节值均匀 → 完整加密，非"加了个头"。
3. **解析结果对不上原始字节**时，先统计原始字节里关键词出现次数
   （如 `raw.count(b'inline_pic')`），再对比解析后条数，差值即被丢弃量。
4. **定位"函数没被调用"**：monkey-patch 该函数做 spy，统计调用次数 + 采样入参。
5. **提取字符串被截断**：检查提取函数的长度上限（`_extract_str` 的 800 是典型坑）。
