## 〇、为什么这是第一优先

`00_爬虫项目说明.md` 列出七项必备机制（M1~M7）。**实测本项目的 M1/M3/M7 全部为零**：

| 机制 | 实测 | 后果 |
|---|---|---|
| M1 能力探针 | **0 个** | 只能等用户发现失效；改完不知效果是否还在 |
| M3 不确定性三态 | **0 处** | 抓到 37/44 不知算好还是坏 |
| M7 效果基线 | **无** | 无法判断改动是变好还是变坏 |

**这带来一个真实的历史代价**：2026-09-14 那轮「全解除」架构改动后，**无人敢回退**——
因为没有探针，任何回退都无法验证「业务效果是否还在」。同理，任何重构（P3）都无法验收。

> **结论：不先建 M1，P3 架构重构无法进行**（因为无法验证重构没破坏效果）。

## 一、效果定义的通用形式（三态 + 覆盖率）

### 1.1 禁止二态

```
❌ 现在：成功 / 失败
✅ 应为：确认成功 / 部分成功（带覆盖率与置信度）/ 确认失败
```

判定「部分成功」必须携带两个数字：**覆盖率**（拿到多少 / 应该有多少）与**置信度**（这些数据有多可信）。

### 1.2 置信度分级（对齐 `00_爬虫项目说明.md` §3.3）

| 级 | 来源 | 可否作结论 |
|---|---|---|
| A | 真实运行实例现场取证 | ✅ 可 |
| B | 官方协议/结构化响应解析 | 需 A 验证 |
| C | 页面结构/DOM/文案推断 | ❌ 仅线索 |
| D | 旧文档/旧日志/旧定性 | ❌ **必须重验** |

**探针输出的置信度 = 其数据来源的最低级**。例如「昵称来自 DOM 推断」→ 探针只能报 C 级，不得报健康。

### 2.1 会话更新与捕获（`更新会话`）

| 指标 | 定义 | 判据 | 健康阈值 | 当前值 |
|---|---|---|---|---|
| **会话覆盖率** | 落库会话数 / 抖音侧实际会话数 | 与 DOM 滚动枚举数比对 | ≥ 95% | 未知 |

## 三、探针的实现要求（M1）

### 3.1 每条业务链一个探针，输出三态

```python
# 伪代码：探针契约
{
  "capability": "conversation_capture",
  "state": "healthy | degraded | failed",     # 三态，非二态
  "coverage": 0.0..1.0,                        # 覆盖率
  "confidence": "A|B|C|D",                     # 置信度（数据来源最低级）
  "measured_at": "ISO8601",
  "evidence": ["...硬证据..."],                # 判据留痕，禁止无证据报健康
  "baseline_delta": -0.02                      # 与上次基线差值（M7）
}
```

### 3.2 硬性要求

1. **必须真的执行**（发起一次真实链路），不是读缓存/读旧日志。
2. **必须留证据**：报告 `healthy` 时，`evidence` 不能为空。
3. **必须能被动触发**：不仅用户点击时可跑，还应能定期跑（发现"悄悄坏了"）。
4. **必须与基线比对**（M7）：报 `baseline_delta`，劣化即告警。
5. **不得用二态**。部分成功必须报 `degraded` 并带覆盖率。

### 3.3 接入点

| 位置 | 作用 |
|---|---|
| 后端启动后自检 | 开机即知各链路状态 |
| 关键动作后自检 | 「更新会话」完成后立即报覆盖率 |
| 定时巡检 | 发现"悄悄坏了"（当前**完全没有**） |
| UI 展示 | 用户一眼看到五链路的健康度 |

## 四、最低可用的第一步（建议）

不要一次全建。**先建一条：会话更新的覆盖率探针**。

理由：
1. 它是本项目**最核心的能力**（会话+昵称+消息是全系统的数据源）。
2. 它**最近刚发生过静默失效**（昵称 0 个、14/44），最需要防复发。
3. 它的判据已经明确（会话覆盖率 / 昵称覆盖率 / 幂等性 / 不降级性）。
4. 它为后续所有重构（P3）提供验收手段。

**验收判据**：人为制造一次失效（如临时断网/改错选择器），探针必须**先于用户**报出 `degraded/failed`。

## 六、已落地的探针（v0.44.26，M1 首版）

**入口**：`GET|POST /api/probe/run`（`?account=`/`capability=` 可选）与
`GET /api/probe/capabilities`。实现：`backend/services/probe.py`；测试：`backend/test_capability_probe.py`（20 项）。

| 能力 | 判据（全部来自本地事实） | 三态规则 |
|---|---|---|
| `conversation_capture` | 库内会话数/真实昵称率 **＋ 最近一次捕获日志的自身关联率** | 无数据→failed；超 `probe_capture_stale_sec`→failed；**有效关联率 = min(库内率, 最近一次率)** <失败线→failed，介于两线→degraded，≥健康线→healthy |
| `message_integrity` | `msg_id` 覆盖率 + (conv_id,msg_id) 重复行 + 无消息的会话骨架 | 无消息→failed；有重复→failed；覆盖率<0.8→degraded |
| `credential_identity` | 落盘 `.env` uid ↔ 库内 conv_id 共同项（复用 **AUTH-050**，不新发明） | 不一致→failed；数据不足→unknown |

**零风控硬边界（源码级测试守护）**：探针**只读** SQLite + 本项目运行日志，
**绝不发起网络请求、绝不触碰/启动浏览器（BCC）**。真实链路验证仍由
`POST /api/messages/{account}/refresh`（用户显式动作）负责。

### 6.1 关键设计判据：**「最近一次」优先于「库内历史」**

🔴 实测（2026-09-21 22:24，本项目自身数据）发现的**探针假健康**：
- 尚进 22:24 那次捕获：`昵称命中 uid关联=0 未命中=44/44`（**链路已失效**）
- 而库内 `nickname_ratio=0.9775`（**历史快照仍是好的**）
- 若只看库内比例 → 探针报 `healthy`，把「已失效的链路」伪装成健康。

⇒ **规则**：关联类探针必须同时看「最近一次捕获自身的关联率」与「库内历史比例」，
取 **min** 作为有效判据；**禁止**用库内历史比例单独判健康。
（这不只是本项目的坑，是所有「读快照」型探针的通用失效模式。）

### 6.2 阈值（唯一来源：配置中心 `capture.probe_*`）

| 键 | 默认 | 含义 |
|---|---|---|
| `probe_min_convs` | 10 | 低于此数判 degraded |
| `probe_nickname_healthy` | 0.95 | ≥ 判 healthy（对齐 §2.1 的 95%） |
| `probe_nickname_degraded` | 0.50 | < 判 failed；中间判 degraded |
| `probe_capture_stale_sec` | 3600 | 最新捕获超此秒数未更新 → failed |

### 6.3 覆盖率口径（诚实标注）

`conversation_capture.coverage` **恒为 null**：真正的分母是「抖音侧实际会话数」，
只有独立观测源（DOM 枚举）才有。本探针**不臆造分母**，只按绝对量 + 有效关联率判档，
并在 `coverage_note` 里写明。**填入外部观测数的那一天，才允许把 coverage 设为真值。**
