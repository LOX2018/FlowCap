## 三、BCC 拉起的坑（本次实测教训）

1. **源码目录直接拉 BCC 二进制会找不到账号**：报「账号 .env 未登记」——`app_root()` 解析到源码目录而非部署目录。必须从**部署目录**（`C:\temp\dyautodm_design\binaries\`）spawn，或走后端 `ensure_bcc()`。
2. **⚠️ profile 锁未释放时拉 BCC = 浏览器无限新开窗口（抱死）**：查看模式有头 chrome 占着 profile 时，BCC `_launch` 启动失败 → `_ensure_alive` 判定 context 失活不断重启 → 无限开窗。**拉 BCC 前必须先释放 profile 锁**：`POST /api/accounts/<名>/stop-browser`（优雅，走守护自身 /quit）或确认 chrome 已全退（`tasklist | grep -c chrome` = 0）。**绝不 Stop-Process 强杀**。
3. 止损顺序：BCC `POST /quit`（优雅，context.close + os._exit）→ stop-browser → 确认 chrome 进程数归零。

## 三·补、评论区末级链路收敛（2026-09-28，v0.45.69）

**症状**：内容中心点开视频播放时，右侧评论区**一直处于加载/刷新**；独立「采集」页采评论正常。

**根因（末级链路分叉）**：同一业务在项目内有两套实现——
- 采集页 `crawl-page.tsx` → `api.crawlComments()` → `/api/crawl/comments` → `features.work_comments()`（**一级评论**，实测 16.5s/100 条）；
- 内容中心 `comment-panel.tsx` → `platformApi.commentsFull(with_inner=true)` → `/api/platform/comments/full` → `get_work_out_comment` 翻页 **再逐条串行 `get_work_all_inner_comment`（楼中楼）**（实测 27.9s）。

后者耗时随一级评论数**线性增长**，叠加播放器取址并发 ⇒ 浏览器侧长时间拿不到可渲染数据 ⇒ 观感即「一直加载」。

**修复（用户 2026-09-28 拍板「直接照搬一级目录」）**：内容页评论区改走**与采集页同一实现**（`api.crawlComments()`，只取一级评论），移除楼中楼串行放大链。**后端零改动**；`/comments/full` 及其客户端定义**保留不删**（ADR-018 F3 记录在案）。

**验证**：`tsc --noEmit` exit=0；新代码所调用的 `/api/crawl/comments` 实测 `ok=true`/100 条；版本门禁 6 处齐平 v0.45.69。详见 `cases/2026-09-28_内容中心评论区恒加载_末级链路分叉修复_case_v0.45.69.md`。

**教训（体系级）**：同一业务的**末级取数链路**必须收敛为单一实现；分叉会在最后一公里产生截然不同的用户体验。可用「grep 同一业务概念是否命中 >1 个取数端点」作为巡检判据。

## 九、内容页播放与媒体取址（2026-09-21，v0.44.19）

> 完整取证过程见 `cases/2026-09-21_内容页播放失败与接口缺口_secsdk签名与流代理_v0.44.19.md`。

### 9.1 播放链路的两层根因（必须两层都过）

```
作品卡点击 → POST /api/platform/media/stream-ticket
             └→ media_resolve → media_request.pick_quality → 跟随 302
           → GET /api/platform/media/stream?u=…（本机同源反代，支持 Range）
           → <video src="http://127.0.0.1:8000/...">
```

| 层 | 契约 | 违反后果 |
|---|---|---|
| 取址 | `play_addr.url_list` **前两位是会话签名直链**（`tk=webid`/`signature`/`policy`），脱离取址会话必 403 | 播放器 403 黑屏 |
| 播放 | 前端**不得**直连 CDN —— webview 跨域受 CORS/Referer 约束 | 后端 200 但播放器仍失败 |

**判据口诀**：诊断播放问题必须**分层验证**——
「后端能否拉到字节」与「播放器实际发起的请求能否成功」是**两个独立问题**，
只验后端就会得到「已修好」的假象（本次实测踩中）。

### 9.2 无签名入口（唯一可靠取址方式）
```
play_addr.url_list = [
  "https://v26-web-prime.douyinvod.com/...?tk=webid&signature=…&policy=…",  ← ① 会话签名，裸取 403
  "https://v11-web-prime.douyinvod.com/...tk=webid...",                     ← ② 同上
  "https://www.douyin.com/aweme/v1/play/?video_id=…",                       ← ③ ★无签名入口
]
```
③ 是 **302 跳转入口**，跟随即得真实流（实测 200 / `video/mp4` / `ftyp isom`）。
判据函数：`media_request.is_session_signed()`（host 命中 `*-web*.douyinvod.com` 或 query 含 `tk=`/`signature=`/`policy=`）。

**探测必须用 GET + `Range: bytes=0-0`，禁用 HEAD** ——
抖音 CDN 对 HEAD 与 GET **校验不一致**（HEAD 200 而 GET 403），
用 HEAD 探测会把「必然失败」谎报成「已修好」（实测 6 条里误判 3 条）。

### 9.3 secsdk web-signature（部分接口的强制签名）
抖音主站部分接口由 secsdk `webSign` 策略保护，**缺 `x-secsdk-web-signature` 直接 403**。
本项目实现：`utils/secsdk_web_sign.py`（**移植自上游 `DouYin_Spider_git`**，未改算法）
+ `builder/params.py: Params.signed_url()`。

```python
url = params.signed_url(f'{DouyinAPI.domain_for(api)}{api}', auth)
requests.get(url, headers=..., cookies=...)   # ★ 不能传 params=（会再编码，签名失配）
```

受保护清单见 `secsdk_web_sign.PROTECTED_PATHS_GET`。**实测差异（重要）**：
- `/aweme/v1/web/mix/aweme/` → **严格**，不加签必 403
- `/aweme/v1/web/aweme/favorite/`、`/aweme/v1/web/aweme/post/` → 服务端**容错**，不加签可通

⇒ **不要**因为"在清单里"就给所有接口加签（引入无谓风险）；只对**实测需要**的加。

### 9.4 合集 vs 短剧 vs 收藏夹（三个易混实体）

### 9.6 推荐流与站内通知：两个「多态信封」解包铁律（2026-09-30）

> 起因：用户报「推荐流有空视频噪音、且只有 6 个、没有刷新按钮；站内通知全是噪音」。
> 根因均为**适配层用单一固定路径解包上游的「多态信封」**。案例：
> `cases/2026-09-30_推荐流空视频与站内通知噪音_根因修复_v0.45.124.md`。

**① 推荐流 `feed` —— `refresh_index` 是「换一批」旋钮，必须透传**

| 事实（实测 2026-09-30） | 值 |
|---|---|
| 不同 `refresh_index` | 返回**互不重复**新批次（ri=1..12 共 **58 条、0 重复**） |
| 同一 `refresh_index` 连取两次 | 结果会变 ⇒ 是**刷新种子**，非稳定游标 |
| 单次返回条数 | **2~6 条，与 `count` 无关**（count=5/10/20/50 → 5/2/6/6） |

⇒ 上游签名 `get_feed(auth, count, refresh_index)`；**`refresh_index` 必须由前端透传**
（`FeedReq.refresh_index`，默认 2），「换一批」= 递增该值。**禁止写死默认值**。

**② 推荐流 `aweme_list` 是「多态信封」，不得假设 `video` 必存在**

上游会混入**非作品卡** —— 实测 `aweme_type=101` 的**直播推荐卡**
（顶层带 `cell_room`、含流地址，但**无 `video` 子树**）。
判据（看 payload 事实，**别猜 magic 号**）：有 `video.play_addr.url_list`
或 `video.bit_rate`，或 `images` 非空 ⇒ 可播/可展示；否则剔除。
剔除须**如实上报 `filtered`** 并在 UI 提示（禁假成功）；整批皆噪音时**保留原批**，
不得静默成「暂无内容」。

**③ 站内通知 `notice_list_v2` 文案随 `type` 变化，必须按 type 分派**

通知**没有顶层 `content`**，文案分散在 type 专属子对象：

| type | 语义 | 文案 / 发起者位置（实测） |
|---|---|---|
| `33` | 新粉丝（`follower_status=1` 证「对方关注了我」） | `follow.from_user.nickname` |
| `31` | 评论 | `comment.comment.text` + `...user.nickname` |
| `41` | 点赞 | `digg.aweme.desc` + `...author.nickname` |

实测 47 条：新粉丝 24 / 点赞 13 / 评论 10。**只读 `digg` 会漏 34/47**（旧实现即如此）。
上游确实无文本（如部分 41 的 `desc=null`）时给**方向中立**兜底
（「点赞通知（平台未提供作品信息）」），**不得编造方向语义**。
