## 二、缺陷清单

### P1-3　`--use-fake-ui-for-media-stream` 启动参数实际缺失（设备红线「缺一不可」）

- **位置**：`backend/vbrowser_args.py:12-17`
- **证据**：铁律要求四条 fake media 参数缺一不可，实际只有三条 + 一条无关项：
  ```python
  _FAKE_MEDIA_ARGS = [
      "--use-fake-device-for-media-stream",
      "--allow-file-access-from-files",
      "--mute-audio",
      "--deny-permission-prompts",
  ]
  ```
  `--use-fake-ui-for-media-stream` **仅出现在 `vbrowser.py:53` 的注释里**，全仓（含前端/tauri/rs/json）无任何实际传参点。
- **影响**：缺该参数时页面请求麦克风权限会弹系统授权框；配合 `--deny-permission-prompts` 会被直接拒绝，连麦等需音频授权的链路可能拿不到流。**不触碰真实硬件**（`--use-fake-device` 已保证虚拟采集源），故为 P1 而非 P0。
- **修复方向**：在 `_FAKE_MEDIA_ARGS` 补入 `--use-fake-ui-for-media-stream`，与 `vbrowser.py:52-57` 注释所述设计对齐。

### P2-4　BCC 守护 HTTP 端点无鉴权（含任意 JS 执行面）

- **位置**：`backend/daemon/browser_daemon.py:2825`（`uvicorn.run(app, host="127.0.0.1", ...)`）
- **证据**：19 个端点全部无 token/鉴权，其中高风险面：
  - `/exec_js`（`:2421`）—— 在**已登录抖音页面上下文**执行调用方传入的任意 JS；
  - `/linkmic_run`（`:2468`）、`/wp_send`（`:2533`）、`/cookie`（`:2282`）、`/scan_login`（`:2557`）、`/quit`（`:2607`）。
- **影响**：仅监听 `127.0.0.1`，属本机信任边界；`/exec_js` 的注释也明确了风控边界（只读取数、禁遍历用户信息）。但**同机任意本地进程**可无凭据调用，等价于拿到该账号的完整浏览器操作权（含发私信 `/wp_send`）。
- **修复方向**：加本机 token（启动时写入文件或由主进程注入环境变量），或改用命名管道/localhost + 随机端口 + 一次性 token。

### P0-2　WS 通道方向判定违反铁律：空 sender 判成 `them`（与另两通道相反）

- **位置**：`backend/daemon/recv_daemon.py:941`
- **证据**（已亲验）：
  ```python
  role = "me" if sender and str(sender) == str(self.inbox.my_uid) else "them"
  ```
  → `sender` 为空时落 `them`；且 `my_uid` 尚未就绪（`:409` `_refresh_my_uid()` 失败静默返回 False）时，**任何** sender 都判 them。
- **三通道对照**（均已亲验，证明不一致是真实的）：

  | 通道 | 位置 | 空 sender 处理 |
  |---|---|---|
  | WS（本缺陷） | `recv_daemon.py:941` | ❌ `them` |
  | WP | `wp_recv.py:161-165` | ✅ `me` |
  | 首包捕获 | `conversation_capture.py:469-473` | ✅ `me` |

  `wp_recv.py:150-158` 的注释甚至明确记载了这个分歧应当统一为「空 sender → me」——**说明是已知未修**。
- **影响**：本号自己发出的 WS 回声被判成对方消息 → 未读数虚高（`:662` `unread +1 if role=="them"`）、昵称回写被误触发。**同一条消息走 WS 与走 WP 得到不同 role**，前端展示方向错乱。
- **修复方向**：改为
  `role = "them" if (sender and self.inbox.my_uid and str(sender) != str(self.inbox.my_uid)) else "me"`
  并把 `my_uid` 未就绪作为**告警**而非静默。
- ⚠️ **更正**：我在阶段一曾把「方向判定」列为 A 档「通过」——**那条结论错了**。我当时只读了 `recv_daemon.py:941` 这一行，看到"用 sender UID 判定"就判通过，**没有对照另两个通道、也没有验证"空 sender"分支**。这是本轮最重要的自我更正。

### P1-7　MCP 管理面无管理员分级：任意已登录会话可自签票据、取明文令牌、清审计

- **位置**：`backend/api/mcp.py:64-162`（含 `:88-97` `reveal_token`、`:134-141` `confirm`）
- **证据**（已亲验）：`main.py:560-567` 的 `_MEMBER_EXEMPT` 不含 `/api/mcp`；`main.py:578-599` 中间件只判 `member_ctx.get_session(token)` **存在性**，`mcp.py` 全部端点均未再读 `request.state.member`。
  ```python
  @router.post("/token/reveal")
  async def reveal_token() -> dict[str, Any]:
      token = cfg.reveal_token()
      return {"ok": True, "token": token, ...}
  ```
- **影响**：任意已登录会话可 ① 把 `allow_write_actions` 改成 true；② 用 `/api/mcp/confirm` **给自己签一次性票据**；③ 删 `/api/mcp/audit` 抹审计痕迹。写工具的「双重闸门」被同一会话自签自销。当前 `send_dm` 仍是占位实现，故为**设计缺陷而非已利用漏洞**。
- **修复方向**：管理端点加管理员角色校验；`reveal_token` / `rotate` 加二次确认或本机校验。

### P1-8　LLM 输出被当作可信意图，提示词注入可启停引擎

- **位置**：`backend/notify/cmd_parser.py:186-188`；执行面 `api/notify.py:192-197`
- **证据**（已亲验）：`DESTRUCTIVE = {INTENT_CREATE, INTENT_RECAPTURE}`——**`start_task` / `stop_task` 不在待确认集合**；`intent` 直接取 LLM 返回，未做白名单校验。
  用户原文（`inbound.py:226`）**未脱敏直传** LLM（`:117-120`），无长度限制、无分隔符。
- **影响**：攻方发一句提示词注入文本，诱导 LLM 输出 `{"intent":"start_task"}` 即可在 admin/operator 权限下**直接启停引擎**，无二次确认。执行面被 `_execute` 固定分支兜住，无法越界到系统命令，故定 P1。
- **修复方向**：`intent` 加白名单校验；把 `start_task`/`stop_task` 纳入确认集；LLM 输入做长度限制与分隔符包裹。

### P1-4　会员加密写盘失败会静默降级为**明文**写 `.env`

- **位置**：`backend/dy_apis/login_api.py:495-509`
- **证据**（已亲验）：
  ```python
  try:
      if member_ctx.is_member_env(env_file):
          member_ctx.write_env_file(env_file, set_values, merge=True)
          return os.path.abspath(env_file + ".enc")
  except RuntimeError:
      raise
  except Exception:
      pass                      # ← 吞掉
  from dotenv import set_key
  for key, value in set_values.items():
      set_key(env_file, key, value, quote_mode="never")   # ← 明文落盘
  ```
  `set_values` 含 `DY_COOKIES / DY_TICKET / DY_PRIVATE_KEY / DY_WEB_PROTECT / DY_KEYS`。
- **影响**：会员空间本应整文件 Fernet 加密写 `.env.enc`；一旦加密路径出现**非 RuntimeError** 故障（导入失败、`is_member_env` 误判等），全部敏感凭证（含 PEM 私钥、完整登录 cookie）**明文落盘且无任何告警**。
- **修复方向**：降级前必须 `logger.error` + 显式开关；生产默认禁止明文降级，宁可失败。

### P1-5　会员主密钥包裹只用单轮 SHA-256，无盐（可离线爆破）

- **位置**：`backend/services/member_store.py:148-153`
- **证据**（已亲验）：
  ```python
  wrap_key = base64.urlsafe_b64encode(
      hashlib.sha256(password.encode("utf-8")).digest())
  return Fernet(wrap_key).encrypt(master_key.encode("ascii"))
  ```
  对比同文件 `:118` 的 `_derive_key` 用的是 **600,000 轮 PBKDF2 + 16B 盐**。
- **影响**：`registry.json` 被拖走后，攻击者可用**廉价单轮 SHA-256** 离线爆破 `wrapped_key`，**绕过 600k 轮设计**；且无盐可跨会员预计算。与文件头「拖走文件读不出任何凭证」的设计声明**不符**。
- **修复方向**：改用与 `_derive_key` 同规格的 PBKDF2（600k 轮 + 盐）。

### P1-6　登录链路 9 处 `requests` 带 cookie 且 `verify=False`

- **位置**：`backend/dy_apis/login_api.py:1044 / 1070 / 1109 / 1122 / 1164 / 1229 / 1285 / 1290 / 1295`
- **证据**（已亲验）：全部形如
  `requests.get(self.base_url + api, headers=..., cookies=auth.cookie, params=..., verify=False)`
- **影响**：SSO 登录 / 验证码 / quick_login 链路关闭 TLS 校验，局域网 MITM 可直接拿到 `Set-Cookie`（sessionid / sid_tt / passport_csrf_token）。属**传输层**凭证暴露，与存储加密无关。
- **修复方向**：改为 `verify=True`；若确因证书环境需例外，应集中配置并限定到特定域名。

### P2-12　本地发送落库不带 `msg_id`，与 WS 回声双写（同一条消息存两行）

- **位置**：`recv_daemon.py:1513 / 1565 / 1640`；索引定义 `database.py:216-230`
- **证据**（已亲验）：三处 `/send`、`/send_by_uid`、`/send_image` 调 `add_message(..., "me", ...)` **均不传 `msg_id`**；
  `uniq_dmmsg` 是**部分索引** `WHERE msg_id IS NOT NULL`，`msg_id=NULL` 的行只能靠 `uniq_dmmsg_fallback(account,conv_id,role,text,CAST(ts*1000 AS INT))` 兜底。
- **影响**：本地发送写入（`msg_id=NULL`，ts=本地时刻）与 WS 回声写入（`msg_id=server_message_id`，ts=WS 到达时刻）**毫秒时间戳不同** → 兜底索引不命中 → 同一条自己发的消息**存两行**。这是当前唯一未被 `INSERT OR IGNORE` 覆盖的重复入库路径。
- **修复方向**：发送后等待 WS 回声按 `server_message_id` 入库；本地先占位再更新，不依赖客户端时间戳去重。

### P2-13　MCP `restart` 从不关闭旧服务，端口/线程泄漏

- **位置**：`backend/api/mcp.py:112 / 121-124`
- **证据**：`_RUNTIME["httpd"] = True`（丢弃了 `start_background` 返回的真实 httpd）；`_stop_runtime()` 只置 None，**未调 `httpd.shutdown()`**。
- **影响**：每点一次「重启」遗留一个 `ThreadingHTTPServer` 并占住回环端口；多次重启后多实例并存，而 `_status()` 只显示最后一次的 `bound_port` → 管理员以为旧实例已停，实际仍在服务。
- **修复方向**：保存真实 httpd 引用并在 `_stop_runtime()` 调 `shutdown()` + `server_close()`。

### P2-14　MCP 令牌落盘失败被静默吞掉，轮换承诺的核心不变式失效

- **位置**：`backend/mcp/config.py:93-98`（已亲验 `except Exception: pass`）
- **证据**：`os.replace(tmp, self._p)` 失败即静默。
- **影响**：`ensure_token(rotate=True)` 声称「旧令牌立即失效」，若落盘失败则**内存失效而磁盘仍是旧令牌** → 重启后旧令牌复活，违反该文件头部承诺。
