## 一、用户报障原话

> 「实时弹幕的表格会突然之间发生变化，将发言人的表格变宽；单位内容明显不属于工商的，
> 就不用发了。这些都不属于意向客户；发送失败，既没有显示失败缘由，也没有进入错误统计；
> 显示已送达，却没有对应的文案。这些问题都是属于系统性的 AI 回复发送功能性障碍」

---

## 二、设计意图（Debug 第一步：回归设计契约）

| 模块 | 设计契约 | 期望行为 |
|---|---|---|
| `delivery_state_of` | 返回值即「**该目标最近一次投递的真实结局**」 | 只反映**本次**发送的结局，不得混入历史 |
| `displayStatus` | 「异常 = 展示档 tone=danger」，过滤与渲染**同一真源** | 失败行必须呈现为失败，不得被任何证据遮盖 |
| 直播发送链 | 目标筛选 + 发送 + **可观测**（缘由/计数/时间） | 未发送必须有可读理由；失败必须计数 |
| 意向判定（本次新增） | 归属 **Agent 层**；引擎只做「匹配」这一通用动作 | 未配置=零回归；配置了=未命中即不发 |

## 三、根因（5 个独立缺陷，含 1 个顺带抓出）

| # | 症状 | 根因（file:line 级） |
|---|---|---|
| **a** | 表格突然变宽 / 发言人列变宽 | `live-page.tsx` 与 `LiveReviewMode.tsx` 两处 `<table>` **均无 `table-layout`** ⇒ 浏览器按内容自动分配列宽；查阅模式 `<Th>` **一个宽度都没写** ⇒ 切换视图即「结构突变」 |
| **b** | 非意向内容照样发 | `live_hook` 的提交唯一条件 = `target.get("nickname")`（:415）⇒ **零意向过滤**；项目既有的 `high_value_keywords`（阈值默认 0 ⇒ 恒真）与 `uid_sink` 窗口（默认 0）**全部休眠** |
| **c1** | 发送失败无失败缘由 | `_do_send` 失败时 `rec.content = None`（:476）⇒ 表格「私信文案」格只渲 `dmText` ⇒ **只剩一个红标签**；缘由只在查阅模式展开行可见（`LiveReviewMode.tsx:332`） |
| **c2** | 发送失败不进错误统计 | 页面「错误」读 `aiSt.errors`（`live-page.tsx:520`）→ `/api/ai/status`（`api/ai.py:1036`）→ **`ai_reply.WORKER.status["errors"]`（AI 会话回复 worker）**；而直播发送失败走 `dispatch.records[].status=FAIL`（`dispatch.py:500`）⇒ **两条链不通，恒为 0** |
| **d** | 显示已送达却无文案 | `api/tasks.py:181` 只传 `uid=` ⇒ 走宽匹配 `conv_id LIKE '%uid%'`（`delivery_verify.py:225-232`）且**无时间锚** ⇒ 该 uid **历史上任何一次**回声帧/投递标记都把本次全部记录判 `delivered`；`displayStatus` 又让 `delivered` **优先于** `fail`（`live-shared.tsx:30-32`）⇒ 失败行渲染成绿色「已送达」而 dmText 空 |
| **e** | （顺带）私信时间列恒空 | 后端下发键名 `send_ts`（`api/tasks.py:200`），直播页读 `r.sent_at`（`live-page.tsx:277`）⇒ **契约漂移**，列恒 "—"（查阅模式读 `send_ts` ⇒ 两处口径还不一致） |

### 过程中由门禁抓出的**真问题**（不是夹具问题）

1. **`dispatch.py` 的 `attempted_content` 在并发回滚中丢失** —— 早前为清理一次失败补丁执行了
   `git checkout HEAD --`（一次覆盖 5 个文件），把已落盘的 `_attempted` 一并还原掉了；
   G5 当场报 `None != '要发的文案'` 抓出。**教训**：`git checkout HEAD -- <file>` 是**破坏性**操作，
   在多步补丁流程中会把**先前成功的段落**一起抹掉；清理应逐段确认而非整文件还原。
2. **`test_live_lead_contract.test_g7b` 是真回归** —— 它要求直播页直接使用共享常量
   `DM_PREVIEW_CHARS`。本次把截断收敛进了**新的共享助手** `dmPreviewText`（更严格的单一真源），
   旧断言的**代理指标**（字面常量名）随之失效 ⇒ 按 superseded 更新判据为断言新助手的使用
   （常量本身仍由 G7 守住）。
3. 🔴 **`delivery_marker` 行缺 `extra.kind`（H-29 单一出口契约违反）** —— 全量回归
   `test_h29_message_schema.test_g7_all_rows_labeled` 报 **8/1156 行未标注**，实测这 8 行全部是
   `msg_type='delivery_marker'`、写入时刻 **2026-09-30 12:46~12:55**（**早于本会话任何改动**，
   本批新写入的行本就带 kind）⇒ 定性为**既有生产缺陷**。根因：`delivery_verify` 用裸 SQL 写入，
   不经 `message_schema` 单一出口。已修写侧 + 按 id 逐条回填 + 门禁复跑绿。
4. 🟠 **补丁脚本重复执行 ⇒ 字典重复键（我的工具缺陷，门禁抓出）** —— 早前一次 `p2a` 批量执行中，
   前两个文件的写入被同一次调用重复应用，产生**相邻重复块**：`ai_agent.py:83-87`、
   `ai_reply.py:218-225` 各多出一份 `intent_scope_enabled`/`intent_scope`（Python `last-wins`
   会**静默丢弃**前者），另 `intent_scope_words`/`intent_in_scope` 各多出**第二份函数定义**。
   `test_no_dup_dict_keys` 当场精确报出行号 ⇒ 已去重并 AST 复核（top-level 与 class 内重名 def +
   dict 字面量重复键）全清。**教训**：字节级补丁脚本必须**幂等**（本次已统一改为
   「`old` 不存在但 `new` 已在 ⇒ 跳过」），且批量执行后应跑一次 AST 查重。

## 七、边界与遗留（诚实标注）

- **意向门为子串匹配**，不做 LLM 精判（`judge_high_value` 项目已有，**未接线**到门）。
- **未做真机端到端**（需开播 + 用户授权写接口）；本轮为「离线门禁 + 真实库只读实证 + 前端类型检查」。
- 前端判据是**源码级**（本项目无前端单测资产，沿用 `test_h20` 既有范式）。
- 时间锚依赖 `dm_messages.ts`（WS 到达时刻）；写入延迟跨过 `sent_at` 时可能**少判送达**
  （方向安全：不谎报送达）。
