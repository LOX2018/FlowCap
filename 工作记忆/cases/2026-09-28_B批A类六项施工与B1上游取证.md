## 1. 本案例值得归档的两个「反常识」

### ① 审计的「431 行」是假的 —— 事实核查救了派工

前瞻审计 §7 称 `features.py` **431 行、24 个能力**，是本项目「最大已建未用」。
动工前实测：**实际 136 行**（24 个能力属实）。若非动手前核了一遍，据此估的改动面/风险
会整体偏大。**教训**：审计报告的**行数/规模数字也要核**，不能只核「是否零 import」这种
结论性判断。

### ② 「孤儿模块零 import」≠「可以删」——必须补动态证据

A-6 删除 3 个模块前，除静态 grep 外，另做了三重对照：
- 字符串动态导入（`importlib.import_module` / `__import__` / `getattr` / `pkgutil`）；
- 包 `__init__.py` re-export 检查；
- **实测能否 import**（`douyin_recv_msg.py` 直接 `ModuleNotFoundError: douyin_api`
  ⇒ 它是「上游顶层绝对导入」的未接线快照，佐证确未接线）。

只靠 `grep 模块名` 判「零引用」在**动态导入**存在时有假阴性风险。删除是 git 可恢复的，
但**删错**会以 `ImportError` 在运行期才爆。

## 3. 两项**故意不做**（判据，不是偷懒）

- **A-7 最小全局熔断**：属**新增子系统**（跨 AI provider + 抖音出站的依赖状态机），
  非「已有部分改良」。随手实现会引入新的单点故障与「隐式自动降级」，与用户
  【显式配置原则】冲突 ⇒ 只出设计，进待拍板。
- **A-9 前端最小行为门禁**：审计**未给可判定不变量**。造无依据的门禁 = 第 N 个
  「假绿门禁」（见 ADR-019）⇒ 延后，待先定法条。

**判据边界**：A 类 = 立足本项目**已有代码与契约内**的改良；引入外部新东西 / 新子系统
= B 类或需设计决策。**不因为是「审计列在 A 栏」就照做。**

## 6. 可迁移判据（提炼）

1. **审计报告的行数/规模数字也要事实核查**，别只核结论性判断。
2. **「零 import」判孤儿需补动态导入证据**（`importlib`/`__import__`/`getattr` + 试 import）。
3. **接线「统一封装层」时，`{"ok":False}` 必须重新上抛**，否则等于制造新的静默失败。
4. **门禁必须真会红**：新增判据要附负控；判据来源解析为 0 条必须 FAIL，禁静默 SKIP。
5. **并发写者零重叠时**：逐文件 add + 升版前重读 + 提交后核验零夹带 —— 三件缺一不可。
