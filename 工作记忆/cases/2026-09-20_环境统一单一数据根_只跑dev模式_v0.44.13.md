## 一、表面现象 vs 真因

**现象**：用户打开设计环境目录，看到的是一堆构建产物，**没有**一键 dev 脚本；
而他在之前的会话里明确要过「一键 dev」。

**真因**（两层，均为事实取证）：

1. **dev 脚本此前只建在测试环境**：`C:\temp\dyautodm_test\dev.ps1`（46 行转发器）已就位，
   但 `C:\temp\dyautodm_design\dev.ps1` **从未创建** —— 用户实际只用设计环境。
2. **设计环境里堆着整包产物**：`DYAutoDM_v2_0.44.12-debug.exe` + 3 份 sidecar
   + `_internal/`（398M），合计 923M。这是 `build_all.py` 的默认部署行为
   （`--app-root` 默认就指向 `C:\temp\dyautodm_design`），**但 dev 模式根本不需要它**。

## 二、关键事实（决定性取证，非推断）

### 2.1 dev 模式不依赖 app root 里的构建产物

| 证据 | 内容 |
|---|---|
| `src-tauri/tauri.conf.json` | `externalBin: ["binaries/dyautodm-backend", ...]` —— 指向 `binaries/` |
| `src-tauri/target/debug/binaries` | **符号链接** → 源码树 `src-tauri/binaries`（实测 `ls -la` 为 `lrwxrwxrwx ... -> /c/.../src-tauri/binaries`） |
| `src-tauri/src/sidecar.rs::resolve_sidecar` | 搜索顺序：① exe 同目录 `binaries/<full>/<full>.exe` → ② `binaries/<full>.exe` → ③ **Tauri externalBin（开发态 src-tauri/binaries 回退）** |
| `target/debug/` 实测 | 已有 `dyautodm-backend.exe` / `dyautodm-browser-daemon.exe` / `dyautodm-recv-daemon.exe`（Tauri dev 自己准备） |

⇒ **`tauri dev` 的 sidecar 来自源码树**，与 app root 里有没有 exe 无关。

**实测验证**：删除全部构建产物后跑 `dev.ps1` → 后端 `{"backend":"0.44.12","frozen":true}`、
前端 `HTTP 200`、进程齐备（`dyautodm-v2.exe` + 3 sidecar + camoufox）⇒ **dev 零依赖产物**。

### 2.3 「源码树疑似污染」的正确判读

源码树里有 `data/ accounts/ backend/data/ backend/accounts/ logs/` —— **非本次 dev 运行造成**：

- **mtime 判据**：`data/dyautodm.db` = 14:40（早于 17:14 启动）；`accounts/` 为空目录；
  `backend/accounts/` 是源码包（含 `__init__.py`）。
- **gitignore 判据**：`git check-ignore` 命中 `DYAutoDM_v2/data/` 与 `DYAutoDM_v2/logs/`。
- ⇒ 判定污染须同时看 **时间 + gitignore + 是否源码包**，不能只看目录名存在。

## 五、顺带记录的两个坑

1. **转发器不能加 `[CmdletBinding()]`**：它会拒绝未声明的具名参数（`-EnvOnly`/`-Stop`）→
   `NamedParameterNotFound`，参数透传不到源码树脚本。只留 `param()` + `$args`。
2. **`patch` 工具与行尾**：对**纯 LF/纯 CRLF** 文件安全；对**混合行尾**文件会整文件归一化
   （本项目 `errcode_data.py` 已踩过）。判据始终是
   `git diff --numstat` vs `git diff --ignore-all-space --numstat` 是否接近。

## 七、追加：源码树污染事故（本轮实测发现，已加固）

**性质**：这是**验证过程中意外发现**的真缺陷 —— 说明「源码树零污染」这条铁律
此前**只存在于文档，没有任何机械检查**，被破坏时无人察觉。

### 7.1 发现过程（不是猜，是实测）

`git status` 里出现一个陌生未跟踪项 `DYAutoDM_v2/src-tauri/%SystemDrive%/`。
排查后共发现**两处**真实污染：

| # | 位置 | 内容 | 规模 |
|---|---|---|---|
| ① | `DYAutoDM_v2/src-tauri/%SystemDrive%/ProgramData/Microsoft/Windows/Caches/` | `cversions.2.db`(16384) + 2 个 `{GUID}.2.ver0x*.db`(309024 / 662848) | 3 文件 |
| ② | `DYAutoDM_v2/data/` | 6 张真实 `origin_images`（heic/jpg）+ 0 行业务 DB + `config.json` | 8 文件 |
| ② | 空目录 | `DYAutoDM_v2/accounts/`、`src-tauri/data/`、`src-tauri/accounts/` | 0 文件 |

### 7.2 根因判定（逐条取证，非推断）

**污染①（未展开的环境变量被当路径）**：

- 三个文件与 `C:\ProgramData\Microsoft\Windows\Caches\` 下的真实文件
  **大小逐字节一致**（16384 / 309024 / 662848）⇒ 是**同源复制/重定向**，不是随机数据。
- 本机环境变量**正常**：`SYSTEMDRIVE=C:`、`PROGRAMDATA=C:\ProgramData`、
  `SYSTEMROOT=C:\Windows` ⇒ 不是环境被我改坏。
- `grep -rn "SystemDrive"` 在 **项目源码、camoufox、playwright、patchright 内均无命中**
  ⇒ 不是本项目代码，也不是浏览器框架代码。
- 目录 mtime = 17:38:53，与 `tauri dev` 启动时刻吻合。
- ⇒ 判定：**构建/编译期间某外部工具（wc.exe 类 Windows 字体缓存服务）以字面量
  `%SystemDrive%` 作为路径写入**，恰好落在 CWD（`src-tauri/`）。

**污染②（源码树运行期 data）**：

- `data/dyautodm.db` mtime = 14:40（早于本轮 17:14 启动）⇒ **历史遗留**，非本轮产生。
- 6 张图片在 design 环境 `origin_images/` 中**不存在** ⇒ 是**真实数据**，不能删。
- `data/`、`logs/` 虽在 `.gitignore`（`git check-ignore` 命中），但 `data/origin_images/`
  与 `accounts/`、`src-tauri/data/`、`src-tauri/accounts/` **均未被覆盖**。

### 7.3 处置（保留数据，满足铁律）

| 动作 | 内容 |
|---|---|
| 移出（不删） | `DYAutoDM_v2/data/` → `C:\temp\_srctree_data_moved_20260920_174649`（8 文件完整保留） |
| 删除 | `%SystemDrive%/` 污染目录（缓存垃圾，无价值）+ 3 个空目录（未被 git 跟踪） |
| 保留 | `src-tauri/gen/`（Tauri 生成）、`src-tauri/logs/`（运行日志，在 gitignore 内） |

### 7.4 加固（自守卫 —— 让不变式能机械检查）

1. **`dev.ps1` 新增「源码树污染自检」**（step 6.5）：启动前扫描
   `data/`、`accounts/`、`src-tauri/data|accounts/`、`src-tauri/%SystemDrive%|%ProgramData%|%SystemRoot%/`，
   命中即告警并列出文件数。
2. **两处 `.gitignore` 补规则**（根 + `DYAutoDM_v2/`）：未展开变量目录
   （`**/%SystemDrive%/` 等 5 条）、源码树运行期 data/accounts（3 条）、
   `.bak.<时间戳>` 备份（2 条，解决知识库备份长期挂在 `git status` 的问题）。

### 7.5 验收（门禁必须能"报真"也能"报无"）

| 判据 | 结果 |
|---|---|
| 加固后首跑（污染仍在） | 门禁**正确报出** `DYAutoDM_v2\data (8 文件)` ⇒ 不是恒真 |
| 清出源码树后复跑 | `[OK] 源码树无污染目录` ⇒ 不是恒假 |
| gitignore 三条规则 | `git check-ignore -v` **逐条命中**验证 |
| `git status` 未跟踪项 | 32 → **6**（余项均为无关的历史未跟踪目录） |
| dev 实例 | 优雅停止，残留进程 0，端口空闲 |

### 7.6 教训（写进铁律）

- **不变式必须机械化**：「源码树零污染」写了很久但无检查 ⇒ 真被破坏了两处仍无人知。
  凡声称「必须/禁止」的规则，都要能回答**「谁来跑这个检查」**（hook / 启动门禁 / 脚本自检）。
- **环境变量不展开的目录名是特征信号**：见到 `%VAR%` 形式的目录名，直接判为
  「某工具把字面量当路径」，不要去查自己的配置。
- **判定源码树污染的三重判据**：mtime 是否晚于本次启动 + 是否被 gitignore +
  是否为源码包（如 `backend/accounts/` 含 `__init__.py`）。只看目录名会误报。
- **真实用户数据（图片/DB）不能因"在错误位置"就删** —— 先查是否别处已有，没有就**移出**而非删除。
