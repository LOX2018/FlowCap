## 一、设计意图（Step 1 回归设计理念）

凭证的职责**不是**「让直播流能连上」（直播本身支持匿名观看），而是
**「部分直播间昵称加密时的解密权」**：只有服务端承认该会话，WS 帧才下发
真实 `uid` / `nickname` / `sec_uid`；否则下发脱敏数据
（`uid=111111` + 昵称 `威***` + `sec_uid` 空），且**与完全不带 cookie 的真匿名逐字相同**。

⇒ 因此「有没有 cookie」是**代理信号**（本项目 §〇·己·3 明令禁止），
判据必须落在真实业务通路。

## 二、当前状态与偏差（Step 2）

| 项 | 内容 |
|---|---|
| 观察到的行为 | 直播弹幕昵称长期脱敏（`uid=111111`）；UI 提示「无解密权，请重新扫码」 |
| 期望行为 | 有解密权的账号应收到真实 `uid`/`sec_uid`；无解密权时必须说明**是哪一类**失效 |
| 偏差 | ① 判据只用「会话活性」单侧，把「会话被拒」**等同于**「身份漂移/无解密权」；② `uid_probe.get_uid()` 返回 `None` 时，调用方**无法区分**「探活失败（取不到证据）」与「AUTH-050 身份漂移（已确认）」，两态被混同 |

## 三、执行链溯源（Step 3）

```
账号 .env(.enc) cookie
  ├─(a) 主站 user/profile/self/  → status_code=8 用户未登录  → 会话活性被拒
  └─(b) query/user 探活 uid      → uid ∉ 历史 conv_id       → 身份漂移（AUTH-050）
                    ↓
        core/auto_dm.py:562 / :1003  仅用 (a) 决定 _live_session_ok
                    ↓
        LIVE-035 文案「无直播昵称解密权」+ UI「请重新扫码」
                    ↓
        LiveChatHook.session_ok → _has_credential() → WS 建连是否带账号 cookie
                    ↓
        终端症状：uid=111111 / sec_uid 空 / desensitized_nickname 有值
```

**关键代码事实（改动前实测）**：
- `core/auto_dm.py:552-580`、`667-672`、`995-1011` 三处**只用** `probe_live_identity`；
  `_uid_consistent_with_history` 在 live 链路 **0 调用**（仅用于写盘门禁 1.5、探针、
  camoufox、browser_daemon 凭证回写）。
- `test_live_session_decrypt_authority.py` 13 项**全部**是 `profile/self` 三态
  （no cookie / 未登录 / 已登录 mock），**无任何 `uid≠conv_id` 样本**。
- `LIVE-035` 当时**不存在于任何 .md / .json 契约文件**（只在代码字符串与 `cases/` 叙事里）。

## 四、根因分析（Step 4）

两类**独立**失效被折叠成一个判据：

| 失效类型 | 判据 | 语义 |
|---|---|---|
| 会话活性被拒 | `user/profile/self/`（严格，容忍陈旧会话差） | 「服务端不承认这次登录」 |
| 身份漂移 | 探活 uid ∈ 历史 conv_id（宽容，容忍陈旧会话） | 「登录的是**别人**/旧身份」 |

`auto_dm/accounts.live_session_state()` 的 docstring **自己写明**边界：
> 「本判据只覆盖「会话活性/能力授权」；**身份漂移**用 `query/user` + 历史 conv_id 判
> （`_uid_consistent_with_history`）；二者结论**互不代替**。」

⇒ 根因 = **消费方超载了判据**（把单侧判据当双侧结论用），
不是探测本身错。这属「设计漂移」：取消/收窄某判据时，消费方未同步。

---

## 五、修复（含取舍上报）

**台账原措辞**：「以 AUTH-050（身份）为主，`profile/self`（会话活性）降为辅助」。

**实现取舍（已显式上报用户）**：按**合取（AND）**落地，而非「主/辅替代」：

> 有解密权 ⟺ ① 会话被服务端承认 **且** ② 身份未漂移

理由：两判据覆盖**不同失效**。若按「替代」实现（只用身份判据），
会把「会话被拒」的账号判成有解密权 —— 正是缺陷本体。合取是唯一同时满足
「故障侧判无权限」与「健康侧判有权限」的形式。

**落地物**：

| 位置 | 内容 |
|---|---|
| `services/uid_probe.py` | 新增三态出口 `uid_verdict()` + `invalidate_verdict()`；`get_uid()` 每条出口写结论（AUTH-050 分支写 **False** 而非 None）——**零新增打网、不绕过 300s TTL 与同账号串行锁** |
| `auto_dm/accounts.py` | 新增 `uid_identity_verdict()` → `(state, reason, label, detail)`；`reason ∈ {ok, not_logged_in, uid_drift, no_credential, unknown}` |
| `core/auto_dm.py` | 两处消费点改用新出口；三态不再布尔折叠；新增 `LIVE-036` 的未知态留痕；UI 文案改用 `label`（标明是哪一类失效） |
| `errcode_data.py` | `LIVE-035` 六段契约重写（合取 + 五态 reason）；`LIVE-036` 补 H-3 后语义 |
| `docs/design-contracts/C-05-live-monitoring.md` | §2·Ⅰ4 入册；§7 已知缺口更新（原交接卡引用已失效） |
| `backend/test_live_identity_verdict.py` | 新增守卫 19 项（真值表 + 三态出口 + 旧二元契约零回归） |

## 八、本轮同批修复（同源缺陷：**判据面 / 覆盖面错位**）

本案例所属的更大模式 —— 「判据面错位」在本轮共暴露 5 处，均已于 v0.44.32 修复：

| 项 | 判据面错在哪 | 修法 |
|---|---|---|
| H-3 解密权 | 单侧判据当双侧结论 | 合取 + 五态 reason |
| `/api/overview` 守护存活 | 读「默认账号」端口（`hash(None)` → 10288/12258 无监听）→ 恒报 `alive:false` | 改「任一已登记账号在监听」聚合判定 |
| 契约门禁自净 | `classify()` 文件级**前缀**匹配 → 同文件未登记端点一并豁免 | 改**逐端点精确匹配**（反证：注入未登记端点 → FAIL） |
| `test_member_smoke` | 模块级顶层断言 → 导入即崩 → 占位 `_FailedTest`，内部断言**从未执行** | 重写为 10 项 `unittest.TestCase`（每用例独立沙箱） |
| `test_model_hub_v2` | 模块级 `DY_APP_ROOT` 泄漏 → 复用他人 DB 连接 | 按 `test_config_isolation` 加每用例重导入隔离 |

**教训（可迁移判据）**：凡「某判据被收窄/取消」或「读数与文件对不上」时，
**先查判据面是否错位**（查错了对象/文件/账号语境），再查逻辑本身。
本轮 5 处全部是「逻辑没错、判据面错」。
