## 二、判据设计：两条由实测约束的决定

### ① AST 判定，不用 grep

实测踩到（H-40 修复现场）：在测试文件里写了一条说明**注释**，其中含字面量
`os.environ.setdefault("DY_APP_ROOT", ...)` ⇒ grep 假报 3 个高危，
而实际全是已修复文件。

注释/字符串里的字面量在 AST 里**不会成为 Call 节点** ⇒ AST 天然免疫。
本轮再次独立验证：17 处 `setdefault` 全部是**真实 Call 节点**，无一处来自注释。

### ② 不能「一律禁止 setdefault」（台账 M-31 原建议不成立）

台账原建议是「断言测试文件内不得出现 `setdefault("DY_APP_ROOT")`」。实测：

| 事实 | 数据 |
|---|---|
| 全库真实 `setdefault("DY_APP_ROOT")` 调用 | **17 处 / 16 个文件** |
| 其中与业务表删除**同文件**的 | **0 处** |
| 其中**故意**指向部署根 `C:\temp\dyautodm_design` | **5 处**（直播类测试需真实凭证，无法隔离到临时库） |
| 死代码（同文件已有 `env_isolate` 覆盖） | **0 处** |

⇒ 照原建议落地：门禁**一上线就 16 个文件变红**，且被迫改坏 5 个有意的测试
= 典型假门禁（`mechanical-gate-verification` 的反模式）。

**改成分层：**

| 规则 | 判据 | 分级 |
|---|---|---|
| **R16** | 含「无 WHERE 全表 DELETE <业务表>」的测试文件必须显式做数据隔离（`env_isolate` / `isolate` / 显式 `os.environ["DY_APP_ROOT"]=`） | **阻断** |
| **R16-B** | `setdefault("DY_APP_ROOT")` 存量写法（危险但已知债务） | **警告**（WARN_ONLY） |

R16 才对应事故本体（**删库 + 没隔离**）。有隔离则删的是自己的临时库，无害——
判据必须贴着事故的因果链，不是贴着某个字面量。

### 表清单 SSOT

业务表清单**动态抽取自 `backend/*.py` 的 `CREATE TABLE`**，不写死清单
（写死就是下一个漂移点）。排除系统表 `kv_store` / `sqlite_sequence`
（删它们是运维行为，如 `scripts/clear_convs.py`）。

⇒ 扫描面**必须**限定 `backend/test_*.py`：`scripts/clear_convs.py` 等运维脚本
有意裸删 `kv_store` / `sqlite_sequence`，纳入即误伤（实测 21 个脚本命中）。

## 三、双向 selftest 证明（门禁必须能变红）

### 3.1 内置 selftest 抓到的两个缺陷

**缺陷 1：负控样本本身是错的，导致负控形同虚设。**
首版 selftest 把表名真源写成裸 SQL（`CREATE TABLE ...`），而 `_business_tables()`
先对每个 `.py` 做 `_ast.parse`（语法无效则不信它的 CREATE TABLE）⇒ 表清单为空
⇒ **R16 恒绿**。selftest 第一跑就报红：`R16 在违规样本下没有变红 = 形同虚设`。
修法：表名真源写成合法 Python（`SCHEMA = 'CREATE TABLE ...'`，与真仓 database.py 同形）。

**缺陷 2：正控会在真仓执行 `os.remove`（生产破坏）。**
首版正控块放在还原 `BACKEND` **之后**，实际对**真仓**跑 `os.remove('test_evil_delete.py')`。
恰好真仓无该文件而未出事，但判据结构是错的。
修法：正控块移到还原 `BACKEND` **之前**（用 `fake_backend`），并加显式警告注释。

⇒ 这两个缺陷都是「只有负控」抓不到的：**负控绿、结构错**。
必须「负控变红 + 正控复绿 + 豁免面精确」三向断言。

### 3.2 独立负控验证（临时目录，不动真仓）

在临时目录复制真仓 137 个测试文件 + `scripts`，逐态验证：

```
基线         → [PASS] R16  全表删业务表的测试均有数据隔离（11 个受保护，无违规）
撤 env_isolate → [FAIL] R16  全表删业务表的测试均有数据隔离（10 个受保护: test_task_detail.py）
还原         → [PASS] R16  全表删业务表的测试均有数据隔离（11 个受保护，无违规）
```

⇒ R16 **跟着数据走**，非写死红灯；且豁免判据**精确**（只认隔离，不误伤）。

### 3.3 负控纪律（skill 要求：先造负控证明它会红，再信它报绿）

| 负控 | 预期 | 实测 |
|---|---|---|
| 新写测试文件含无 WHERE `DELETE FROM tasks`、无隔离 | R16 变红 | ✅ |
| 同文件加 `env_isolate(...)` | R16 复绿 | ✅ |
| 注释里写 `setdefault("DY_APP_ROOT")` 字面量 | **不**计入 R16-B | ✅ |
| 自造负控断言 `count == 1` | 替换失败即中止 | ✅ |

## 五、顺带闭环：H-33 版本号分位数超限

H-33 原建议「0.45.152 → 0.46.01」，但版本号已行进至 `0.46.60`——
**分位数 60 已超上限 50**（规则 2026-10-01 设定，见 `dyautodm-version-sync`），
即 H-33 暴露的**同类问题复发**，只是从 152 变成 60。

按进位规则：分位数 = 50 时再 +0.01 → 次版本号 +1、分位数从 01 起。
`0.46.60` → **`0.47.01`**（顺带把 0.46.01 这个已失效的中间态跳掉）。

**教训**：H-33 之所以一直没修，是它被登记为「下次升版时同步」——
**没有载体去执行「下次」的待办**。本轮首次出现真实升版需求，H-33 才被顺带清掉。

**根治（v0.47.02，同轮追加）**：把分位数上限做进 `check_version_sync.py`
（`PATCH_LIMIT = 50`，`_check_patch_limit` 在六处齐平后检查 patch ≤ 50，
超限 ⇒ exit 1 并提示应进位的目标版本）。**双向负控**：
纯函数 6 用例（`0.47.51`/`0.45.152`/`0.46.60` 均报红、`0.47.01`/`0.47.50` 报绿）
+ 端到端（六处齐平 `0.47.51` ⇒ exit 1，还原复绿）。
⇒ 分位数超限**不可能再静默复发**（门禁每次升版必跑，机械拦截）。
