# 2026-09-21 直播监听：流与 AI 正常，但前端进程控件全部失效（v0.44.17）

> 错误码：`ENG-015`
> 分支：`design/better-douyin`　环境根：`C:\temp\dyautodm_design`
> 现象上报用户原话：「实测当前直播监听直播流获取正常，AI生成回复内容正常，
> 但页面对直播监听的前端进程控件全部失效，不会随着监听任务启动而变化」

---

## 一、设计契约（被违反的那条）

| 项 | 契约 |
|---|---|
| 模块 | `AutoDM._on_dispatch_idle`（core/auto_dm.py）+ `DispatchCenter._loop`（core/dispatch.py） |
| 不变式 | 「队列空」**只在 WS 监听已建立之后**才可能代表「任务该收尾」；**启动握手窗口内队列空是必然的正常中间态**，不得据此收尾 |
| 预期行为 | 引擎启动后 `engineState` 单调走 `starting → running`，前端徽章与「暂停/继续/停止监听」控件随之可用 |

### 「控件失效」的准确含义

前端 `live-page.tsx:109~128` 完全由 `engineState` 驱动：

```ts
const engineState = ls?.engineState || "idle";
const engineBusy = ["starting","running","paused","stopping"].includes(engineState);
// 暂停按钮 disabled={engineState !== "running"}
// 继续按钮 disabled={engineState !== "paused"}
// 停止按钮 disabled={!engineBusy}
```

`engineState` 一旦停在 `stopped`：**三个按钮恒灰、徽章恒显示「直播引擎未运行」**。
而弹幕流与 AI 生成走的是**另一条独立路径**（WS on_message → dispatch.submit →
gen_dm_message），与 `state` 无关 —— 所以「流正常、AI 正常、控件全死」可以同时成立。
**这个组合本身就是「状态机被写坏、而非采集链路坏了」的强判据。**

## 三、根因（两处连坐，缺一不可）

### 源头 ①：调度器把「只触发一次」这个上层语义硬编码进了自己

`core/dispatch.py` `_loop()`：

```python
except asyncio.TimeoutError:
    if self._queue.empty() and not self.pending and self.on_idle:
        await self.on_idle()
        self.on_idle = None          # ★ 调度器自行解绑
```

队列空在**启动握手窗口内是必然的正常中间态**（还没捕获到任何目标）。于是这次
**唯一的**触发机会被握手窗口吃掉；后续真正发空时已无回调可用 —— 自然关播的
任务会永远停在「运行中」（另一方向的假象）。

### 传播 ②：存活判据在握手窗口内恒为假

`core/auto_dm.py` `_on_dispatch_idle()`：

```python
live_active = (
    self.live is not None
    and getattr(self.live, "ws", None) is not None   # ★
    and not getattr(self.live, "_should_stop", False)
)
```

`self.ws` 由 `dy_live/server.py` 的 `run_forever()` **内部**赋值，握手窗口内恒为
`None` → 正在启动的监听被判成「已死」→ 直接落 `STOPPED`。

**同一判据在 `snapshot()` 里还有一份副本**（前端 `/api/tasks/current` 读它），
`/api/live/stream` 也有第三份 —— 三处必须同源，否则前端徽章会与真实状态相反。

## 四、修复

| 文件 | 改动 |
|---|---|
| `dy_live/server.py` | 新增 `_ws_alive` 存活标记。`start_ws()` 入口即置活（**覆盖握手窗口**）；置死仅在两处：主动停止分支、`get_live_info` 失败早退分支。**重连空隙保持 True**（那是活跃生命周期，不是停止） |
| `core/auto_dm.py` | 抽出 `_listen_line_active()` 作**唯一真源**；`_on_dispatch_idle` 与 `snapshot()` 共用；收尾成功后调 `detach_on_idle()` |
| `core/dispatch.py` | 调度器**不再**自行解绑（只通知「队列空了」这一事实）；新增 `detach_on_idle()` 把解绑权交回上层 |
| `api/live.py` | `/api/live/stream` 的 `running` 判据对齐同一真源 |

### 为什么「置活点在 start_ws 入口」而不是 on_open

`on_open` 只在 TCP+HTTP Upgrade **成功之后**才触发。若置活只在 `on_open`，
「发起连接 → 连上」这一整段窗口仍是 False，本 bug 原地复发。
**判据必须覆盖「意图已发起」到「确认已连上」的全部区间。**

| 全量 `python -m unittest discover` | 406 项，仅 `test_member_smoke` 失败 = **存量环境问题**（模块导入期跨会话密钥解密失败），与本改动无关 |
| 前端 `npx tsc -b` | 0 error |

测试覆盖的四类不变式：
1. 握手窗口内（`_ws_alive=True`、`ws=None`）**不得**收尾；
2. 重连空隙**不得**收尾；
3. 真停止（`/ 从未发起连接 / live 为 None`）**必须**仍能收尾（防矫枉过正）；
4. 调度器**不得**自行解绑 `on_idle`（跨两次 1s 超时仍应收到 ≥2 次回调）。

## 六、踩坑与通用判据

### 6.1 「流程还在跑」≠「状态字段是对的」

本例弹幕捕获、AI 生成、私信发送三条链路全部正常，唯独状态机被写坏。
**排查「前端控件不跟着变」时，先查状态字段的真源，不要先去查那些正常工作的链路**
—— 它们正常恰恰说明故障在状态层。

### 6.2 判据必须覆盖「已发起 → 已确认」的完整区间

凡「某资源是否可用」的判据，都要问：**在意图已发起但尚未确认的窗口里，
这个判据返回什么？** 返回 False 就等于把「正在启动」判成「已死」。
本项目同类形态：`ws is not None`、`_port_open`、`pid_exists`。

### 6.3 回调的「一次性」语义属于上层状态机，不属于通知方

通知方（调度器）只该报告「队列空了」这一事实；**何时不再关心这个通知，
只有状态机知道**。把 `on_idle = None` 写在通知方，等于让通知方替状态机做决策。

### 6.4 同一判据散落多份 = 前后端给出相反答案的温床

`_on_dispatch_idle` / `snapshot()` / `/api/live/stream` 三处各写一份判据，
改一处漏两处就会出现「页面显示等待启动、实际在监听」。
**修法：抽成单一方法，三处调用。**

### 6.5 写回归测试必须做「回退验证」

新测试全绿**不等于**它在守不变式 —— 可能是断言写错了恒真。
本例做法：临时把修复回退 → 必须变红（实测红 3 项）→ 还原变绿。
**这一步是「测试有效」的唯一硬判据。**
