# 案例 · 直播监听启动「提示占用/要求换房」——前端无请求锁 + 409 文案误导

- **日期**：2026-09-29
- **版本**：v0.45.91（`0a764c4`）
- **严重度**：error（阻断用户操作，且**误导用户中断已正常运行的监听**）
- **触发**：用户报障「点击直播监听的时候提示占用，要求换房」

---

## 一、设计意图（回归契约）

| 项 | 设计契约 |
|---|---|
| 启动按钮 | 同一账号**一次点击 = 一次启动请求**；请求进行中按钮必须禁用 |
| `disabled` 语义 | **请求期间**即为真（客户端自证），不依赖服务端状态回传 |
| 409 文案 | 如实描述当前状态；不得把用户引向"停掉重来" |
| 通知失败分级 | 协议层固有限制 ≠ 故障，不得按 WARNING 淹没真信号 |

**架构铁律引用**：这与项目既有范式冲突 —— `engine-cards.tsx` 用**独立 `loading`**
保证请求互斥（正确范式），而 `live-page.tsx` 用**轮询派生的 `engineBusy`**（错误范式）。

---

## 二、观测偏差

- **偏差类型**：timing（时序）
- **偏差点**：前端 `live-page.tsx` 启动按钮 → 后端 `POST /api/engine/start`
- **现象**：用户点启动后看到 409「该账号已在监听…**如需换房请先停止**」，
  遂以为启动失败 → 点「停止」重来 → **中断了本已正常运行的监听**

---

## 四、根因分析（RCA）

### 根因① 前端启动按钮**无请求锁**（真缺陷）

```jsx
// 修复前 —— live-page.tsx
const engineBusy = ["starting","running","paused","stopping"].includes(engineState);
//                                   ↑ engineState 来自 ls?.engineState（后端轮询）
<button disabled={engineBusy || ...}
  onClick={() => { ...; api.start(cfg).then(...).catch(...) }}  // ← 从不设 pending 锁
/>
```

`engineBusy` **由后端状态轮询派生**，从点击到下次轮询（2~5s）之间为 `false`
⇒ 按钮**不禁用** ⇒ 连点第二下必被后端 409 拒绝。

**对比正确范式**（`engine-cards.tsx`）：
```jsx
const [loading, setLoading] = useState(false);   // 独立于轮询
onClick={() => { setLoading(true); act(...).finally(() => setLoading(false)) }}
```

### 根因② 409 文案把人引向"停掉重来"

原文：「该账号已在监听（… state=starting）—— **如需换房请先停止**」

在「第一次已成功、第二次是连点」场景下，该文案**反向诱导用户中断运行中的监听**。

**归因（标注为推断）**：日志显示三次软停止都在启动后 9~43 秒，
与「被误导 → 点停止重来」的行为链吻合。但**日志无调用方标识**，
故此项为**推断**而非定论（已在提交说明标注）。

## 五、修复（v0.45.91）

| 项 | 文件 | 修法 |
|---|---|---|
| 前端无锁 | `frontend/src/components/live/live-page.tsx` | 新增 `engineReqBusy`：onClick 首行 `if (engineReqBusy) return` 早退 + 请求前 `setEngineReqBusy(true)` + `.finally` 释放 + 计入 `disabled` |
| 409 误导 | `backend/api/engine.py` | 按 `state` 分支：`starting` ⇒「正在启动中，请等待就绪，**无需重复点击**」；`running` ⇒「已在监听中，如需切换直播间请先点停止」 |
| NTY 噪音 | `backend/notify/channels.py`、`notifier.py` | 新增 `is_protocol_limit` 判据（**只放行** iLink 协议限制文案），`NTY-012/014/015` 降 debug；真故障仍 WARNING |

## 六、实机验证（动态，非静态）

### 6.1 并发双 `/start` 真机复现（复刻用户连点）

对部署版 v0.45.91（`frozen:true`）发两个相隔 50ms 的 `/start`：

```
[req0] HTTP 200: {"ok":true,"state":"starting","acct":"四川工伤张老师"}
[req1] HTTP 409: "该账号正在启动中（acct=四川工伤张老师）—— 请等待就绪，
                  无需重复点击；若确要切换直播间，请先点「停止」再启动"
```

判据：① 有且仅一个 200 + 一个 409 ✅ ② 含「正在启动中」✅
③ 含「无需重复点击」✅ ④ 旧文案「如需换房请先停止」消失 ✅

### 6.2 通知静默的**负控**单测（防"恰好没推送"的空证明）

实机日志只证明"本轮没出现 NTY"，若恰好未触发则是**空证明**。
故用合成 `ChannelResult` 直接驱动判据（8 用例）：

- 协议限制 4 条（缺 ctx / 额度用尽 / 窗口过期 / ret=-2 prepare failed）→ 全 `True` ✅
- **负控**真故障 4 条（HTTP 401 / timeout / ret=-5 鉴权 / 空）→ 全 `False` ✅
- 真故障泄漏为协议限制：**无** ✅

## 七、踩坑留痕（判据自身的缺陷）

**G5 首版用「源码 grep」判"文案是否含旧串"** —— 结果在**注释里复述的旧文案**
上误命中，产生**自造假红**。改为 **AST 只扫字符串字面量**后正确。

> 本项目同类坑已第 3 次（「注释/文档里复述敏感串污染文本判据」）。
> **定式**：判"代码里是否有某文案"时，必须用 AST/字节码常量，或至少排除注释行。

另：PYZ 内是**字节码**（`ZlibArchiveReader.extract()` 直接返回 code object），
不能 `b[16:]+marshal.loads`（首版据此全 MISS，是**判据缺陷**不是产物缺陷）。
正解 = 递归扫 `co_consts`。
