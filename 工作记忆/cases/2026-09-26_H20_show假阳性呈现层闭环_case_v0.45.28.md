# 2026-09-26｜H-20 呈现层闭环：`/show` 假阳性根治的最后一环（v0.45.28）

> 关联：**H-20**（v0.44.67 后端已修一半 → 本轮补齐呈现层）· 缺陷编号 **UI-020**
> 案例性质：**假阳性根治未闭环**（后端已改文案，但前端仍能凭 `ok` 宣称「已打开」）
> 严重级：🟡 中（不损坏数据，但 **UI 谎报成功** —— 用户据此以为窗口在，实际不在）

---

## 1. 设计意图（Step 1）

| 项 | 内容 |
|---|---|
| **模块** | `POST /api/accounts/{name}/open-browser` 端点 + `accounts-page.tsx` 呈现层 |
| **设计契约** | `/show` 是**异步受理**（`daemon/bcc_routes.py:616`）。**`ok=true` 只代表「已受理」，不代表「窗口已就绪」**（后台重建可能失败，实测 `BCC-058`） |
| **预期行为** | 用户点「打开指纹浏览器」后，UI **如实**表述：已就绪 / 已受理尚未就绪；**绝不得**把「受理」说成「已打开」 |
| **设计假设** | 达成态必须**结构化**透出（`settled`/`switching`），前端据字段分档；靠 msg 文案不可靠 |

## 2. 当前状态偏差（Step 2）

| 项 | 内容 |
|---|---|
| **偏差类型** | **data（契约面）** —— 达成态未结构化，前端只能猜 |
| **偏差点** | ① `backend/models/account.py:32` `ScanLoginResponse` 仅有 `ok` / `msg`；② `frontend/.../accounts-page.tsx:327` 硬编码完成态措辞 |
| **偏差表现** | `push(`已打开指纹浏览器 · ${name}`)` + `api.addLog("SUCCESS", …)` —— **无条件**，与 `settled` 无关 |

**v0.44.67 已做但未闭环的两件事**（本次实测确认）：

1. 后端已把达成态写进 **msg 文案**（`settled=True → （窗口已就绪）` / `False → （已受理…尚未就绪）`），逻辑**正确**；
2. 但达成态**没有结构化字段**，且前端**自拼文案**（`d.msg || '已打开指纹浏览器'` 之外的 `addLog` 恒用「已打开」+ `SUCCESS`）。

⇒ **假阳性从另一条路复发**：用户看到绿色 SUCCESS 日志「已打开指纹浏览器」，屏幕上却无窗口。
这正是 H-20 台账所记的开放项：**「前端若直接读 `ok` 展示成功，需同步改为读 `settled`」**。

## 3. 执行链追踪（Step 3）

```
[现象] 用户点「打开指纹浏览器」→ 弹「已打开指纹浏览器」+ SUCCESS 日志 → 屏幕无窗口
   ↓
[入口] accounts-page.tsx:319 onOpenFingerprint(name)
   ↓
[调用] api.openFingerprintBrowser(name)  →  POST /api/accounts/{name}/open-browser
   ↓
[后端] api/accounts.py:604 → 转发 BCC /show（intent=observe）→ 拿到 out{ok,settled,switching,changed}
   ↓
[断点①] accounts.py:736 return ScanLoginResponse(ok=True, msg=…hint…)   ← 只有 2 字段
   ↓
[断点②] client.ts:782 返回类型 Promise<{ok, msg}>                        ← 类型层丢字段
   ↓
[断点③] accounts-page.tsx:326 push(d.msg …) 但 327 行 addLog("SUCCESS","已打开指纹浏览器…")
         —— addLog 恒用**完成态**措辞，与 settled 完全无关 ⇒ 谎报 SUCCESS
```

**根因**：达成态**只在文案里、不在契约里**。契约（2 字段）无法表达「受理 ≠ 就绪」，
前端自然只能按「ok 就成功」处理 —— 这是**契约缺字段**导致的呈现层被迫说谎，不是前端不小心。

---

## 4. 根因分析（Step 4）

**为什么链在此断裂？** 因为「异步受理」这一语义**没有进入数据契约**。

- 后端 v0.44.67 的修复是**文案级**（把诚实信息塞进 `msg`）—— 治了后端自述，但没治**消费侧**；
- 前端要如实表述，必须有能力**区分**两态；而契约只给了 `ok`（恒为 True，因为受理确实成功）；
- ⇒ 前端在信息不足时，用「成功」兜底 = 唯一能写的东西就是谎话。

**同类隐患（结构性）**：凡「异步受理」类端点，若契约只有 `ok`，消费侧必然产生假阳性。
本项目的 `/show` 是第一个被记录的例子。

## 7. 教训（写入反面教训清单）

1. 🔴 **「诚实降级」必须落到契约，不能只落到文案**：把真实状态写进 `msg` 而契约不给字段 ⇒ 消费侧无法据实表述，必然假阳性。**判据：凡 UI 要分档展示的语义，必须在响应模型里有对应字段。**
2. 🔴 **异步受理类端点，`ok` 恒为 true，不可作就绪判据**：`/show`、`/scan` 等「已受理」语义的端点，必须额外返回**达成态字段**；`ok` 只表达「请求被接受」。
3. ✅ **前端呈现层的假阳性要靠门禁锁死**：仅改后端文案不足以闭环 —— 前端仍可自拼成功措辞。**负控正则**（禁「无条件完成态措辞 + SUCCESS」）是有效判据。
4. ✅ **`hide` 与 `show` 的同步性不同**：`show` 异步（需 `settled` 三态），`hide` 同步（返回即已切回，`settled=ok`）。同一端点族内不可套用同一语义。
