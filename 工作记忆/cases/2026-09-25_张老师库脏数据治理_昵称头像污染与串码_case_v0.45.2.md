## 三、根因（链路溯源，非现象层）

### ① 昵称/头像污染
`daemon/recv_daemon.py::_extract_peer_uid` 原实现：
```python
if self.my_uid and uid_a == self.my_uid: return uid_b
if self.my_uid and uid_b == self.my_uid: return uid_a
return uid_b            # ← 无 my_uid 兜底
```
实库 conv_id 形态为 **`0:1:<对端uid>:<本号uid>`**（本号段在 idx=3，**136/136 实测**）
⇒ my_uid 未就绪时兜底返回 **uid_b = 本号自己** ⇒ `_enrich_nicknames_once` 用本号 uid
去 IndexedDB 取到**本号昵称/头像**并回填。

**双重失效**：该兜底**永不返回 None**，使更正确的 `_infer_peer_by_common_uid`
（90% 覆盖率推断本号）被整体绕过 —— 两道防线一起失效。

**同因修复不对称**：`auto_dm/conversation_capture.py:409-413` 已于 **2026-09-07（D 方案）**
修过同一根因（注释原文：「peer_uid 恒取 uid_a → 32/77 个会话的 peer_uid 被写成自己，
peer_name 全填成本账号昵称」），但 **recv_daemon 与 api/messages 两处未同步** ——
正是 `services/conv_identity.py`（v0.43.39 契约）点名的「同一件事在 5 处独立重写」。

### ② 串码
`conversation_capture._parse_media` 按设计把小图内联 base64 写进 `text`（前端 `<img>`
渲染需要，2.9KB 级、零网络）；而 `ai_reply._build_history` 只对 `msg_type=='27'` 走
图片描述分支 ⇒ `msg_type='text'` 的 `[图片] data:image…` **原样进 prompt**。

### ③ 系统提醒
`conversation_capture` 按 `a:biz` 映射生成 `[系统提示]`/`[系统消息]` 写入 text
（正确：不透出内部英文串）；但 `api/messages.py` 详情 SQL 与 `_build_history`
**均未排除这些前缀** ⇒ 前端显示 + 进 AI prompt。

## 四、修复（六步闭环）

1. **写侧收敛（根因）**：`recv_daemon` / `api/messages` 两处 `_extract_peer_uid` 改为
   委托 `services.conv_identity.peer_uid`（SSOT），**my_uid 未知时返回 None（不猜）**；
   `recv_daemon._infer_peer_by_common_uid` 也收敛到 `conv_identity.infer_my_uid_from_conv_ids`。
2. **富化自愈**：`_enrich_nicknames_once` 补「凭证不可用 → 会话池统计推断本号 uid」；
   覆盖判据加「=本号 uid / =本账号昵称」（存量污染纳入可自愈集合，真昵称不覆盖）；
   加**自证门禁**：对端 uid 必须存在且 ≠ 本号 uid，否则跳过。
3. **判据 SSOT**：`services/verdicts.is_placeholder(_name)` 增 `self_name` 维度
   （=本账号昵称即判为污染）。
4. **AI 读侧**：`ai_reply._build_history` 加噪音前缀排除（`_HISTORY_NOISE_SQL`）+
   内联 base64 剥离（`_sanitize_history_text`，降级为 `[图片]` 占位）。
5. **前端读侧**：`api/messages.py` 详情 SQL 补排除 `[系统提示]% / [系统消息]% /
   [未知类型%`；`_enrich_with_db_nicknames` 的 `db_map` 排除「peer_id==本号」行，
   切断存量污染在读侧二次扩散。
6. **存量清洗**：`scripts/repair_conversation_identity.py`（默认 dry-run、写前自动备份、
   逐条判定、复用 SSOT 判据）。

## 六、教训（可迁移判据）

1. **同一根因的多处副本是「隐性回归源」**：D 方案 2026-09-07 只修了 3 处中的 1 处，
   另外 2 处**静默带着缺陷跑了 18 天**，直到存量数据暴露（136 会话）。
   ⇒ 收敛判据时**必须列全副本清单**（`conv_identity` 契约已点名 5 处），
   收一处漏一处 = 缺陷按最弱的那份存活。
2. **「永不返回 None 的兜底」比「返回 None」危险**：它让更正确的推断路径**永远拿不到控制权**。
   ⇒ 判据型函数在证据不足时应返回 unknown/None（诚实降级），把控制权交给更强的判据，
   而不是用一个貌似合理的弱值顶掉整条防线。
3. **降级值必须「零信息」，不得「错误信息」**：拿不到真昵称时回退**裸 uid**（项目既定），
   绝不能用本号身份冒充对端 —— 后者是**主动误导**（用户看到「张老师」以为是本人会话）。
4. **测试脚手架必须复用生产形态**：mock 库连接不设 `row_factory=Row` ⇒ 被测函数抛
   `tuple indices must be integers` → 返回空 → **假失败/假绿**。本案例两个失败用例中，
   一个是真缺陷（my_uid 未知仍返回本号），一个是**探针缺陷**（同项目「复现保真」纪律）。
   ⇒ 门禁失败先分「产品缺陷 vs 探针缺陷」，两者都要修，但**不能混淆归因**。
5. **读侧不删 base64 是设计而非遗漏**：前端 `<img>` 依赖它渲染；治理点在 **AI 读侧剥离** +
   前端读侧**只滤系统类**。清洗时**不得**一刀切删 `text LIKE '%data:image%'`。
6. **探针证据（`[投递验证]`）与用户内容必须视觉可分**：写侧正确形态是
   `msg_type='delivery_marker'`，但历史遗留 48 条写在 `text` 前缀 —— 读侧按**前缀 + msg_id
   前缀 + msg_type** 三条判据取并集排除，**不清除数据**（保留审计价值）。
