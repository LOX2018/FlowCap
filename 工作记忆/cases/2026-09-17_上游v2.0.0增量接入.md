## 二、接入项（4 项，全部实测）

### 1. protobuf 新字段解析（f14 / f4 / f18）

`im_protobuf.py` 新增三个纯解析函数（**只解析、不请求**，不越昵称红线）：

| 函数 | 字段 | 语义 |
|---|---|---|
| `_parse_message_sec_uid` | f14 (len/UTF-8) | 发送者 sec_uid；**校验 `MS4wLjAB` 前缀 + 长度**，噪声值返回 None |
| `_parse_message_created_at_us` | f4 (varint) | 服务端序号；量级校验 1.5e15~2.0e15 |
| `_parse_message_reply` | f18 (len) | `f1=被引用 server_id`（**varint**，对 len 线型亦容错）+ `f2=JSON(content/nickname/refmsg_sec_uid/refmsg_content)` |

**踩坑（写入即验证才发现）**：我最初用 `dict((f,v) for ...)` 收 f18 的 sub 字段，
而 `f1` 是 **varint**，前者只留 len 线型的 bytes，`ref_msg_id` 被错解成 `b'\x89\x06'`。
改为**按线型分别取值并归一成十进制字符串**，varint / len 两种形态均通过单测。

### 2. 落库契约扩展（`dm_messages.extra`）

`extra` 由 `{skey, origin_url}` 扩展为可选含：
`sender_sec_uid` / `created_at_us` / `reply` / `voice_uri` / `voice_skey`。
**原有键位与语义不变**（解密链路依赖）。补写沿用既有「UPDATE 优先 + 幂等」写法：
仅当旧行 extra **不含该新键**时才 UPDATE，重复跑不覆盖已有正确值。

### 3. 排序键（**实测修正了我的实现**）

上游 README 称 `created_at_us` 是「单调递增序号」。**本机真实首包实测**（`init_pkg.bin`，19 条）：

```
f4 取值 ≈1.79e15（微秒量级），相邻步长 10ms，19 条中 7 条并列
→ 它不是逐条严格单调的序号，而是 10ms 粒度的服务端时间序号
```

所以：**ts 必须作次级键**；且缺失 f4 时**不能填 0**（会排到最前），必须与 f4
同量级（`ts × 1e6`）。后端 `ORDER BY` 用 `CASE WHEN ... THEN f4 ELSE ts*1e6 END, ts`，
Python 侧同口径。**对照实验**（4 条混合样本）证明修复必要：

```
真时间序:           a(0.0) d(0.1) b(0.2) c(1.0)
旧键(f4 or 0)  ->   ['d','b','a','c']   ★错：无 f4 的排最前
新键(量级对齐) ->   ['a','d','b','c']   ✓
```

### 4. 语音转文字（v2.0.0 真增量）

新增 `backend/services/voice_transcribe.py`：

- 端点 `POST https://www.douyin.com/aweme/v1/web/im/message/audio/recognition/`
- 请求体 `{"req_list":[{uri,sec_uid,uuid,message_id,message_type:7,skey,conv_short_id}]}`，
  **每批 ≤10**（上游实测 `status_code=5` 上限）；`skey` 允许空串；`message_id` 用 server_id（去掉 `srv_` 前缀）
- `uuid` 在**页面上下文**探测（`mainOptions.deviceId || mainOptions.uuid`）
- **风控边界（铁律 §一/§二）**：请求在**账号自己的 BCC 容器页面上下文**发出
  （`fetch(..., {credentials:'include'})`）—— 复用浏览器自身登录态，代码里**不出现任何
  cookie/token 变量**；只处理语音消息，不查昵称；已有转写跳过；取不到 uuid **不硬发**（省配额）
- 新增端点 `POST /api/messages/voice/transcribe`（`{account, conv_id?, limit?}`）
- 前端：会话工具栏「语音转写」按钮 + 语音气泡下方展示转写文本（无结果不显示占位）

### 5. TLS 原生信任库（v2.0.0 真增量，低风险）

`utils/tls_policy.py` 增 `install_truststore()`：`truststore.inject_into_ssl()`
接入**原生 OS 信任库** + 叠加 `certifi`，尊重 `SSL_CERT_FILE`/`SSL_CERT_DIR`。
**只增加信任来源，绝不关闭校验**（与既有 `DY_TLS_INSECURE` 正交）；`DY_TLS_NO_TRUSTSTORE=1` 可回退；
未装 truststore 自动降级。`main.py` lifespan 调用一次（best-effort）。
`load_verify_locations`/`SSLContext` 改**惰性导入**，避免打包后缺模块直接炸。

## 五、复盘教训

1. **读上游必须先读基线版本**：只说「源项目更新了」时，第一步是**建立 v_old→v_new 增量**，
   而不是拿 v_new 静态对照。Release 页日期≠tag 提交日期（本项目三个 Release 是补录的）。
2. **断言前先取真实字节**：上游注释说「单调递增」，我直接照抄进理由；
   实测 19 条里 7 条并列 → 若照抄会留下一个「排序看着对了但同 10ms 内抖动」的隐患。
   **上游注释是线索，不是证据。**
3. **自己引入的缺陷要靠对照实验抓**：新排序键「缺失 f4 填 0」是我引入的，
   用 4 条混合样本对照一次就暴露。
4. **`git stash` 收尾必须校验**：第二次 `stash pop` 失败时我把 stderr 吞了，
   一度以为改动丢失（实际在 stash 里）。**收尾命令的退出码与输出都要看**。
5. **关停要收尾**：backend 强杀会留孤儿 `recv_daemon`（本轮残留 pid 4452 占 12726），
   已按技能流程用 `/quit` 优雅退 BCC + 定点清理该 pid，复查三端口全 down。
