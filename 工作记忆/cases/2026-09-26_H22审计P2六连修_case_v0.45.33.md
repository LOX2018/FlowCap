## 1. P2-①/② `settled` 语义对（idx6 假阴性 + idx7 假阳性）

### 设计契约（H-20 建立的观测态契约）
`/show` 与 `/hide-browser` 必须**据实表述**：`settled=True` ⇔ 可见性已达成；
`settled=False` ⇔ 仅受理/切换中。**绝不把「受理」说成「已达成」**。

### 根因（一对反向缺陷，同一个接口歧义）
**BCC `set_visible` 的 4 个 return 里，`settled` 只在 1 处显式出现**：

| 分支 | 原 return | 问题 |
|---|---|---|
| 去重（切换中） | `{ok, headless, changed:False, switching:True, deduped:True, msg}` | **缺 settled** |
| 同步已达成 | `{ok, headless, changed:False}` | **缺 settled**（这里是**已达成**却读不到 True） |
| 窗口同步切换 | `{ok, headless, changed:True, switching:False, mode, msg}` | **缺 settled**（同为已达成） |
| 后台重建 | `{ok, accepted, settled:False, ...}` | 唯一显式 |

**idx6（假阴性）**：`accounts.py` `/show` 写 `settled=(settled is True)` +
`if settled is True:` ⇒ 所谓「窗口已就绪」分支**永不可达** ⇒ 即便容器**确实已就绪**，
也永远报 `settled=False`，前端恒显「尚未就绪」（把 H-20 的诚实修复反向做成了永久假阴性）。

**idx7（假阳性）**：`/hide-browser` 假定「hide 是同步切换」，硬编码
`settled=bool(out.get("ok"))` / `switching=False`。实测：**有头→无头与无头→有头走同一条
异步后台重建路径**（camoufox 下窗口操作失败即回退重建），返回
`{ok:True, settled:False, switching:True, changed:True}` ⇒ 把「已受理」当「已切回」，
正是本项目刚根除的假阳性。

### 修复
- **BCC 侧三处 return 显式补 `settled`**（去重路径 `False`；两处同步达成路径 `True`）
  ⇒ 接口不再有「缺键」歧义。
- **`/show` 增缺键兜底**：既非 True 也非 False 时，诚实告知「BCC 未返回达成态，无法确认」。
- **`/hide-browser` 改为按 BCC 真实 `settled` 如实表述**（去掉「hide 必同步」的错误前提）。

### 验证
门禁 G1 断言 `set_visible` **每个状态型 return 都含 settled 键**（负控：缺键形态判红）；
G2 断言「无 `settled=bool(ok)` 形态 + 确有缺键兜底」（负控判红）。

## 2. P2-③ `platform.py` —— `_login_state_reason` 同步阻塞事件循环

### 根因（调用链实证）
`_login_state_reason` 是**同步函数**，直接调用
`verify_credential(account, lightweight=False)` —— 这是**全量双引擎校验**
（WP 探活 + DM 写探针 + 身份漂移检测，`timeout=8`，且 `auto_fix=True` 可能触发
浏览器重捕获的**写副作用**）。它被 **6 个 `async` 处理器**
（`favorite`/`liked`/`notice_list` 等）**同步调用**，而本文件其余同类调用
**一律 `await asyncio.to_thread(...)`** ⇒ 每个降级请求阻塞事件循环最长 ~8s。

### 修复
`_login_state_reason` 改 `async def`，阻塞体 `await asyncio.to_thread(verify_credential, ...)`；
**六个调用点全部加 `await`**。

### 验证
门禁 G3：断言函数为 async + 含 `asyncio.to_thread` + **无未 await 调用点**且 ≥6 处 await。
（负控：同步形态 + 裸调用判红。）

## 3. P2-④ `vbrowser_camoufox.py` —— reap 在事件循环里同步阻塞

### 根因
`close_camoufox_context` 是 `async def`，其 `finally` 里**同步**调用
`_reap_camoufox_processes(_ud)` —— 该函数 `psutil.wait_procs` 阻塞
（默认 3s + 12s）。5 个生产调用点都 `await` 本协程且在真实事件循环上
（`bcc_audit.py:163`、`bcc_login.py:251`、`bcc_routes.py:201/685`、`browser_daemon.py:700`）
⇒ **整条 FastAPI/daemon 事件循环被卡住**（实测 **3.14s**，无残留进程时也有 1.04s）。

### 修复
`await asyncio.to_thread(_reap_camoufox_processes, _ud)` —— 保持「清理完成再返回」
的语义，但不阻塞事件循环。

### 验证
门禁 G4：断言 reap 走 `asyncio.to_thread`（负控：同步调用判红）。

## 4. P2-⑤ `notify/channels.py` —— `send_image` 最终 POST 异常泄漏

### 根因
`send_image` 的最终 `sendmessage` POST **没有 try/except**（同文件 `send()` /
`_upload_media` 均返回 `ChannelResult`），且 `resp.status` 在 `async with` 退出后
才解引用 ⇒ 网络异常或响应体非 JSON 时 `await resp.json()` **直接抛出**本方法，
与「失败返回 ChannelResult、不抛异常」的同文件约定不一致。

> 订正：审计意见另称「`resp.status` 在 `async with` 外解引用」是问题，但同文件可用方法
> `_do_send` 也是同样写法 —— **真正的问题只是未被 try/except 包裹**。（子任务已验证此点。）

### 修复
用 `try/except` 包住 POST 及其状态判定，异常统一返回
`ChannelResult(False, ..., f"sendmessage 异常: ...")`。

### 验证
门禁 G5：断言 `send_image` 内存在 `except Exception` 且 `try:` 紧邻 `async with s.post(`（负控判红）。

## 5. P2-⑥ `dy_apis/login_api.py` —— `phoneMain` 状态契约永不可达

### 根因
`phoneMain` 声明的返回契约含 `'send_failed'` / `'ok'` 等结构化状态；但它**第一步**
就调用 `dyGeneratePhoneVerificationCode`（:1315），而该函数
**无条件 `raise NotImplementedError`**（其依赖 `generateSecretPhoneNum` 全仓不存在）；
`dyPhoneVerificationCodeLogin`（:1378）同病。⇒ 声明的状态契约**永不可达**，
调用方会被误导把 SMS 分支当可用链路接线。

### 修复
在调用不可用链路**之前**显式 fail-closed，抛带错误码 `AUTH-062` 的可读异常，
说明「链路不可用 + 请改用扫码分支」。

### 验证
门禁 G6：断言 `AUTH-062` 的 fail-closed **早于** `dyGeneratePhoneVerificationCode` 调用（负控判红）。

## 8. 教训（写入）

1. **「可选字段」是接口歧义的温床**：同一返回的 4 个分支里只有 1 个带 `settled`，
   调用方无论怎么读都会错一半。**多分支 return 的字段集合应齐平**，
   否则必须在使用侧显式处理缺键。
2. **一对反向缺陷可以同源**：同一个「缺 settled 键」既造成 `/show` 的**永久假阴性**，
   又（叠加错误前提）造成 `/hide` 的**假阳性**。修接口比修调用点更根本。
3. **`async def` 里出现同步阻塞调用 = 事件循环级故障**，影响面远大于单请求。
   判据：凡是 `async` 函数体里直接调用可能阻塞的 IO/等待函数，必须走线程池。
4. **对外声明的状态契约若不可达，必须显式 fail-closed**，不能让它「走到一半才炸」——
   后者会被调用方误当成「可用链路」。
