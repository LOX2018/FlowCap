- **日期**：2026-10-01
- **分支**：`design/better-douyin`
- **触发**：用户两个质疑（均指向我此前的认知边界）

## 一、用户质疑（原文要点）

> ①「通过接口桥实现的凭证更新在应用当中是能用的，但浏览器内依旧显示无登录态 ——
>    这个桥到底是将浏览器的内容显示到前端，还是只是利用了浏览器的指纹层、通过 API 处理？」
> ②「为什么你断言 API 无法实现登录？上游既然有这个方案，那肯定是有用的。」

---

## 二、质疑 ①：桥的机制 + 「应用能用、浏览器未登录」根因

### 桥到底是什么（代码决定性证据）

**桥 = 用真实浏览器（Camoufox）在页面里真登录，然后把浏览器 cookie jar 抄回应用凭证。**

| 用户猜测 | 判定 | 证据 |
|---|---|---|
| 「把浏览器内容显示到前端」 | ❌ | 前端二维码由**接口响应体渲染**的 PNG，非截屏 |
| 「只用指纹层 + API 处理」 | ❌ | 登录**真发生在浏览器里** |
| **真实机制** | ✅ | `poll_bridge_confirmed` L48：`cookies = await context.cookies()` |

### 「应用能用、浏览器未登录」根因（实测取证）

```
浏览器 profile `_camoufox/cookies.sqlite`：54 个 cookie
  sessionid            — 不存在
  sid_tt               — 不存在
  sid_guard            — 不存在
  uid_tt               — 不存在
```

**根因链**：桥为弹出登录框，**出码前先清登录态 cookie**（必要步骤，日志实证
`已清陈旧登录态 cookie 10 个`）⇒ 登录成功后凭证**只写应用 `.env`**，**未回填浏览器**
⇒ 浏览器 profile 长期无登录态。

**连锁技术影响**（不止 UX）：
> 上游 `dyGenerateInitData` 因此报 **AUTH-062：`keys 有效=False`**
> （取不到 security-sdk）⇒ API 路径缺签名四件套。

### 修复
新增 `_persist_cookies_to_browser()`，在 `_finalize_login_and_verify` 校验通过后回填
登录态键（`domain=.douyin.com`），复用项目**既有** `context.add_cookies` 范式
（`login_remote.py:1166`），幂等、失败不阻断（ACC-039）。
**顺序已核对**：回填在 `return True` 前、`finally` 关 handle 前 ⇒ context 仍有效。

## 三、质疑 ②：API 通道结论订正（**用户质疑成立**）

### 我此前的表述有问题

| 说法 | 判定 |
|---|---|
| 「API **无法完成登录**」 | ❌ **过度概括** —— 断言了方案本身 |
| 「API **当前跑不通**」 | ✅ **精确** —— 只断言状态 |

### 上游复核（支持用户的质疑）

`dy_apis/login_api.py:1483 qrcodeMain`：
```python
# 成功判据：redirect_url / status in (2,'2')
if _cd.get('redirect_url') or _cd.get('status') in (2, '2'):
    return {'status': 'ok', ...}
```
且 `dyGenerateInitData` **自建 P-256 密钥对** ⇒ **设计上确实能完成登录**。

### 但实测「完整上游链路」仍失败（决定性）

```
auth 就绪 55.8s（cookie 54 个，说明它确实启了浏览器做 bootstrap）
→ status = no_qrcode     ← 连码都出不来
```

**两条已证成因**：
1. **该路径走 plain `requests`**（非已装的 `curl_cffi` 0.16.3）⇒ TLS 指纹暴露
   ⇒ `get_qrcode` 返回 **HTTP 200 + 10168 字节 HTML** ⇒ `safe_json` 降级 None
   （日志：`[IM-001] 响应非 JSON（HTTP 200, 10168 字节）`）
2. **AUTH-062**：`keys 有效=False`（账号未登录 ⇒ 取不到 security-sdk）⇒ 缺签名

⇒ 三项交叉印证，结论订正为「**当前跑不通**」。修 ① 后 `keys` 前置有望满足，**可再测**。

### 处置
- 配置中心 label：`API（实验·仍无法登录）` → **`API（实验·当前跑不通）`**
- 门禁断言同步更新（"跑不通" or "无法"），**守门意图不变**：禁止把实验通道包装成可用通道
- 代码注释写全两条成因 + 「结论应表述为当前跑不通，而非方案无用」

## 五、教训（重要）

1. **结论要区分「方案无用」与「当前跑不通」** —— 前者断言方案、后者断言状态。
   用户一句「上游既然有这方案肯定有用」直接纠正了我的过度概括。
   **判据：写下否定结论时，问自己「这是断言方案本身，还是断言当前状态」。**
2. **「A 能用、B 不能」的现象要查两者状态是否同步** —— ① 的根因就是
   两个存储（应用 .env 与浏览器 profile）**只写了一个**。
3. **表象 UX 问题可能藏着技术连锁** —— 浏览器无登录态不只是「看着别扭」，
   它直接导致上游 `keys` 缺失、API 路径缺签名。
4. **整体测试集合会挂起时，逐文件跑** —— 两次整体集合卡在 64%，
   逐文件跑既快又能精确定位（本项目既有测试含会挂起的用例）。
