## 一、核心教训：上一轮审计「跑了 52 分钟却零产出」

用户要求「重新审计最近变动」的直接原因——上一轮审计实际**失败**，且症状会被误读成「引擎坏了」。

### 现象（三段，缺一段就会误判）

| 证据 | 值 |
|---|---|
| 组进度 | `session_end`: `review_item_done=13` / `review_item_failed=37`，共 50 组 |
| 失败原因 | `llm_error`: `{"duration_ms": 300001, "error": "context deadline exceeded"}` —— 8 个文件一组，整组被 15min 硬超时掐死 |
| 次生症状 | `code_search`/`file_read` 报 `git grep failed: exit status 0xc0000142`（**Windows DLL 初始化失败**） |
| 产物 | `-o artifacts/audit/ocr_v0.43.81-88.json` → **0 字节**；`session_end.results` → 空 dict |

### 根因（两层，第二层是次生）

1. **主因**：`ocr review` 默认 `--timeout 15`（15 分钟/组）。本仓单文件体量极大
   （`api/messages.py` 1644 行 / `messages-page.tsx` 1354 行 / `browser_daemon.py` 2700+ 行），
   一个 8 文件组远超 15 分钟 → **整组硬失败**。
2. **次生**：超时把子进程池耗尽后，引擎自身派生的 `git` 子进程开始 `0xc0000142`
   （DLL 初始化失败）——**看起来像 git 环境坏了，实际是资源被拖垮**。
   这层假象最危险：会让人去修 git 而不是调超时。

### 修复与验证（同一范围复跑对照）

| | 默认参数 | `--timeout 60 --concurrency 4` |
|---|---|---|
| 组结果 | 13 done / **37 failed** | **50 done / 0 failed** |
| 工具调用 | 大量 `0xc0000142` | **684 次，失败 0** |
| 耗时 | 52m35s（白跑） | **10m18s** |
| 报告 | 0 字节 | **109,885 字节 / 77 条** |

⇒ **`ocr review` 默认超时对本仓不适用**，必须显式 `--timeout 60 --concurrency 4`。
⇒ **判断「上一轮是否真出结果」的判据**：`session_end.results` 是否为空 + `-o` 文件字节数。

## 二、本轮发现（分诊结论：真 13 + 半真 1 + 误报 4）

### P0 · 能力不可用 / 风控面（**最高价值：全是我方本轮新写的代码**）

#### ① `*_JS` 页面脚本「对象解构 vs 数组传参」不符 —— **三处同坑**

```python
# 定义（对象解构）
RESOLVE_URLS_JS = """async ({path, tkeys}) => { ... tkeys.map(...) }"""
# 调用（传数组）→ Playwright 把整个 list 当作单个 arg
res = exec_js(RESOLVE_URLS_JS, [BATCH_PLAY_INFO_PATH, keys])
```
**Node 实跑复现**：数组参数 → `TypeError: Cannot read properties of undefined (reading 'map')`；
对象参数 → 正常返回。⇒ **取址链路恒失败，返回 `{err}` 后被上层当「换取失败」**。

**同坑三处，必须同修**（这是本项最关键的一点——只修一处等于没修）：

| 文件 | JS 常量 | 调用点 | 影响 |
|---|---|---|---|
| `services/cenc_video.py:274` | `RESOLVE_URLS_JS`（`{path, tkeys}`） | `:331` 传 `[path, keys]` | IM 视频取址恒失败 |
| `services/nickname_fallback.py:44` | `FETCH_JS`（`{path, ids}`） | `:207` 传 `[path, ids]` | 昵称兜底恒失败 |
| `services/merged_forward.py:63` | `WEB_FETCH_JS`（`{path, body}`） | `api/messages.py:1348-1349` 传 `[path, json.dumps(b)]` | **合并转发正文补抓恒失败** |

⚠️ **单测抓不到**：`test_upstream_p4.py` 只 stub 了 `exec_js`（Python 层），
**从不真正执行 JS** → JS 签名错在 Python 侧永远测不出来。
**这类「跨语言边界（Python→JS 参数形状）」的缺陷必须实跑 JS 才能证伪。**

#### ② 昵称兜底失败路径不计限流（`nickname_fallback.py:208-216`）
两个失败 return 均无 `_mark_run`；`_mark_run` 只在 200 响应后（`:218`）调用。
⇒ 持续 401/403/429/超时**永不进入冷静期、不累计日额** → 调用方可死循环重试，
**恰好击穿本模块存在的唯一理由（风控限速）**。

#### ③ 环境基线未按 `ok` 门控（`browser_daemon.py:1740-1744`）
`env_baseline.py:10-11` 契约原文：「基线**只在**【凭证真判据通过】时记录…
**绝不**在凭证存疑时写入（否则把失效环境当基线）」。
实际调用**无 `if ok:`** → 探活失败时把存疑环境写成基线 → 后续真实漂移
**不会再告警**（`BCC-063` 假阴性）。**契约与实现直接冲突，是本轮最清晰的 DbC 违约。**

## 三、方法论沉淀

1. **同一缺陷模式要全仓 grep 同源实现**：`*_JS` 只在修 `cenc_video` 时发现「数组/对象」不符，
   全仓扫其余两个 `_JS` 常量 → **三处同坑**。只修报告点出的那一处 = 漏 2/3。
2. **判「缺校验」追到消费点**：schema 缺 `min/max` ≠ 可绕过；`_cfg()` 有 clamp 即安全。
   **报告只看定义侧，改造影响在消费侧。**
3. **判 SQL/迁移缺陷必须实跑 + 枚举写入路径**：`ALTER ADD COLUMN DEFAULT` 让「IS NULL」分支
   在主路径永不命中；数据损坏效果只在**特定写入路径**下显现 → 据「理论正确性」定级会误判优先级。
4. **跨语言边界（Python→JS）必须实跑对侧解释器**：Python 侧 stub 掉 JS 的单测，
   对「参数形状/解构」类缺陷**零检出能力**。
5. **「假成功」是本仓最高频的真实缺陷形态**（已第 4 次出现）：
   `/status` 读不存在字段恒真 · `mark()` 查表失败裸 return · `ok:True, path:""` ·
   失败路径不记限流计数。审查时专项 grep「`ok:True` 紧跟 `if not <值>:`」。
