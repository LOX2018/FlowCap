## 0. 一句话

P4 两条都是**「静默」型缺陷**：一条是**静默半坏**（拿到缺方法的对象，调了才炸），
一条是**静默降级**（操作者的受限意图被无声推翻）。修复方向一致 —— **把它变成显式失败**。
P4 收口即 **H-22 全库审计 22 条真缺陷全部处置完毕**。

## 1. P4-① `login_api_vendor.py` — vendor 导入的命名空间碰撞（idx3）

### 设计契约（ADR-017 §8.1）
「扫码登录 → **API 路径**（上游 vendor，`auto_dm/login_api_vendor.py`）· ✅ 保留可用」。
适配层自带 DbC：`P1 vendor 目录存在`、`C2 失败时抛带错误码的异常，**绝不返回半成品**`。

### 根因（实测复现，非推断）
上游 `vendor/douyin_spider_upstream/dy_apis/login_api.py` 用**顶层绝对导入**：

```
from dy_apis.login_api import ...     (适配层入口)
from builder.auth import DouyinAuth
from utils.http_client import ... as requests
from utils.dy_util import ...
from utils.fingerprint import ...
```

而 **vendor 与 backend 有 5 个同名顶层包**（`dy_apis` / `builder` / `utils` / `dy_live` / `static`）。
`_ensure_path()` 只做 `sys.path.insert(0, VENDOR_DIR)` —— 但**应用进程里项目同名包早已加载**
（全仓大量模块级 `import dy_apis.*`），`sys.modules` **命中优先于 `sys.path`** ⇒
拿到的是**项目** `dy_apis.login_api.DYLoginApi`（**没有** `bootstrap_auth` / `get_qrcode` /
`check_qrcode`）⇒ 调用即 **`AttributeError`**。

**性质 = 静默半坏**：适配层声明「可用」，导入看起来成功，**直到调用那一瞬才炸**；
调用方拿到一个「长得像但缺方法」的对象，排查成本极高。
（审计限定：该适配层当时**无任何调用方** ⇒ 潜在缺陷，按 ADR-017 接线即必现。）

### 为什么不能「同进程修好」
同进程**无干净解**：清 `sys.modules` 会破坏**项目自身**（项目正在用这些包）。

### 修复（处置顺序是关键）
1. **暴露共享包清单** `_SHARED_TOP_PKGS = (dy_apis, builder, utils, dy_live, static)`（逐个校验，不能只查 `dy_apis`）。
2. `_import_upstream()` 改为**先判后插**：
   - ① 任一共享包**已加载**且来自项目 ⇒ 抛 **AUTH-073**；
   - ② 任一共享包**在当前 `sys.path` 下会解析到项目** ⇒ 抛 AUTH-073；
   - ③ 确认干净后，**才** `_ensure_path()` 并导入上游。
3. `_ensure_path()` 补：**保证 VENDOR_DIR 在 `sys.path` 最前**（原实现只在「不在 path」时插入）。

> 🔴 **实测踩到的关键坑**：最初把「解析判定」放在 `_ensure_path()` **之后** ——
> 结果 `_ensure_path` 先把 vendor 插到 `sys.path[0]`，**反向遮蔽了项目包**，
> 连判定用的 `importlib` 查找都被劫持（报出 `AUTH-071` 而非 `AUTH-073`）。
> ⇒ **必须先判后插**：任何 mutate `sys.path` 的动作都不得先于碰撞判定。

### 验证（行为级，双场景对照）
| 场景 | 期望 | 实测 |
|---|---|---|
| **A 应用态**（cwd=backend，项目包就绪） | 显式 **AUTH-073**，且 **不劫持** `sys.path` | ✅ 报 AUTH-073；`sys.path[0]` 未被插成 vendor |
| **B 干净子进程**（仅 vendor 在 path） | **放行**到真实导入 | ✅ 越过 guard，仅报 AUTH-071（`curl_cffi` 未装，契约明示前置） |

场景 B 证明 guard **有判别力**（不是无脑拦），且 B 正是**设计推荐的隔离形态**。
> 备注：B 曾被我构造成「把 backend 也放进 path」—— 那本就**该**拦，属构造错误而非缺陷。

### 剩余（本次不做，需环境/需求）
- 真正端到端跑通 vendor 扫码需 **`curl_cffi`**（未装）+ 真机扫码；
- **冻结态（PyInstaller sidecar）无独立解释器**，故「子进程隔离」目前只能在**开发态**
  达成（需把上游依赖打进包 / 用 `multiprocessing` 方案）—— 按用户「不擅自扩张范围」原则，
  **本次不实施**，与 H-30 的 ADR-017 主路径（RPA）一并推进。

## 2. P4-② `mcp/registry.py` — scope 空解析静默回落全量（idx14）

### 设计契约（ADR-010 S5）
「未知 scope ⇒ **启动失败并报错**（**不静默回落全量** —— 否则隔离形同虚设）」。

### 根因
`set_active_scope` 对 `--scope " "` / `--scope ","` 这类**显式提供但解析为空**的取值，
走 `if not items: items = ("full",)` ⇒ **静默回落全量工具面**。
`__main__.py` 只在 `_scope` 为**真值**时调用（`' '` 是真值 ⇒ 会进入）⇒ 操作者以为「受限了」，
实际拿到的是**全量面**。现有门禁只覆盖 `'full,,nope'`（含非法项 → raise），**未覆盖纯空项**。

### 修复
`None` / `""` 仍走「未提供 → 默认 full」（既有契约不破）；但**显式提供而解析为空** ⇒
抛 `ValueError`，报错文案含原值与可用取值，并提示「或省略 `--scope` 以使用默认 full」。

### 验证（行为级）
6 类显式空项（`' '` / `','` / `'  ,  '` / `['','  ']` / `(' ',)` / `{'  '}`）**全部拒绝** ✅；
`None`/`''` 仍 `('full',)` ✅；合法值 `full` / `debug` / `full,debug` 不变 ✅；
**拒绝后作用域不被改变** ✅（既有门禁语义保持）。

## 5. 教训（写入）

1. **「同进程修改 `sys.path`」是与宿主进程争抢命名空间的危险动作**：
   把 vendor 插到 `sys.path[0]` 会**遮蔽**项目同名包。凡此类动作，
   **判定必须在 mutate 之前** —— 否则判定自身都被污染（本次实测踩到，报错码错成 AUTH-071）。
2. **顶层绝对导入的 OSS 组件无法与同构项目共享进程**：上游用 `from builder.auth import ...`
   这类扁平导入时，任何「注入 path」的方案都挡不住 `sys.modules` 优先级；
   **唯一干净解是子进程隔离**。选型阶段就该问：「它的导入形态能否与我的包共处一个进程？」
3. **「静默半坏」比「显式失败」危险一个量级**：返回一个缺方法的对象，
   错误被推迟到调用点、且离根因极远。**契约应写成「宁可立刻炸，不可带着缺陷往下走」**。
4. **空解析 ≠ 未提供**：配置解析里「用户没给」与「用户给了但给空了」是**两种意图**，
   后者通常表达「我要受限」；把它当默认值处理就是**无声推翻用户意图**。
5. **位置关系型判据的锚点要排除 docstring**：用 `find("func()")` 会命中注释里的同名提及，
   必须锚定实际调用行的缩进形态（或用 AST）。
