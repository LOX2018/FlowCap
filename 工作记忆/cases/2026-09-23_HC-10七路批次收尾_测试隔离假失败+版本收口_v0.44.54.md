## 1. 设计意图（Design-First Law）

**模块**：`backend/test_delivery_verify.py`（P0-1 投递验证闭环的回归守卫）

**设计契约（隐含，本次才显式化）**：
1. `unittest discover` 把**全部** `test_*.py` 导入**同一进程**（本仓既定事实，见
   `test_config_isolation.py` 模块 docstring）。
2. 任何测试在**临时卸载/重载模块**（`sys.modules.pop` + `importlib.reload`）后，
   **必须在退出时逐键还原**，否则：
   - 其它模块**已由 `from X import Y` 持有的旧模块对象**与其后
     `sys.modules["X"]` 里的**新对象**脱钩；
   - 后续测试的 `mock.patch.object(旧对象, ...)` **打不中新对象** ⇒ 打桩静默失效。
3. **模块身份唯一**（REG-01 定式）：同一进程内一份源码只允许一份模块实例。

**不变式**：测试集合的**执行顺序不得改变任一用例的结果**（顺序无关性）。

## 2. 观测偏差（Observed Deviation）

| # | 现象 | 读数 |
|---|---|---|
| ① | `test_p2_live_guards` **单跑全绿** | `Ran 26 … OK` |
| ② | `test_p2_live_guards` **与 `test_delivery_verify` 同跑变红** | `FAILED (failures=1)` |
| ③ | 失败用例 | `TestDeleteStrategyOrdering.test_unbind_failure_aborts_delete_and_reports_not_ok` |
| ④ | 断言 | `assertFalse(r["ok"])` 得 `True`（解绑失败却回 ok=True） |

**判定结果（两条对照实验，铁律要求）**：

- **对照 A（顺序）**：`test_p2_live_guards` 单独 ✅ / `test_delivery_verify` 在前 ❌
  ⇒ **与执行顺序相关**，非产品缺陷。
- **对照 B（成对排除）**：`p2 + 其余 6 模块` 逐一配对 **全绿**；只有
  `test_delivery_verify → test_p2_live_guards` 这一对触发 ⇒ **污染源唯一锁定**。
- **可复现性**：同组合连跑 2 次稳定复现（非抖动）。
- **假失败自证**：单跑该用例时，日志出现
  `[LIVE-023] … 为不留悬空引用**将不删除该策略**: 模拟解绑失败`
  （= mock **生效**、按设计拒绝删除、`ok=False`）；
  组合跑时**无此日志**且 `ok=True`（= mock 落空、走真解绑分支）。

> ⚠️ **这一条是本案例的核心**：若只看「全量回归 FAILED」，会把它当成
> **P1/P2 批次引入的真实回归**而回滚正确改动 —— **假失败比真失败更贵**。

## 3. 执行链上溯（Execution-Chain Traceability）

```
unittest discover 同进程加载 test_delivery_verify
  └─ TestMarkerFilteredOut._fetch()      [旧实现 L245-251]
       ├─ sys.modules.pop(所有 "api.*" 与 "database")     ← 卸载 API 层
       ├─ import api.messages as M; importlib.reload(M)
       └─ ❌ 函数返回时**不还原** ────────────────────────┐
                                                          │
test_p2_live_guards 在【模块导入期】执行                     │
  └─ from api import live_config, live_rooms   ← 拿到【重载后的新对象】
       （持有于模块全局，此后不再刷新）                     │
                                                          │
执行期：mock.patch.object(live_rooms, "unbind_strategy")    │
  └─ live_config.delete_strategy() 内部 import 的 live_rooms ← 是【同一个新对象】…
       ⚠️ 但真正的断点在下方 ──────────────────────────────┘
```

**根因（精确到对象身份）**——两条链路：

- **链路①（对象脱钩）**：`_fetch` 把 `api.messages` / `api.live_rooms` / `api.live_config`
  **全部卸载重载**并**不还原**。凡在**导入期**已把 `live_rooms` 绑进自己命名空间的模块
  （`test_p2_live_guards` 的 `from api import live_rooms`、以及**产品模块**
  `api.live_config` 的 `from api import live_rooms`），其绑定**永远指向被丢弃的旧对象**；
  而 `delete_strategy` 内部**再次 import** 取到的是 `sys.modules` 里的**新对象** ⇒
  `mock.patch.object(旧对象).unbind_strategy` 对 `delete_strategy` 调的**新对象**无影响。
- **链路②（同源实例）**：`test_delivery_verify` 与 P0-1 的 `_mark_send_delivery` 引用同一
  `sys.modules.pop` 手法；该手法在本仓**已被 `test_config_isolation.py` 记录为历史事故**
  （2026-09-09：首个导入 `database` 的文件决定 DB 路径 → 互相看到对方写入）。

**结论**：不是产品缺陷，是**测试文件未遵守自己项目的隔离定式**（临时卸载后不还原）。

## 4. 修法（最小改动，正交）

`test_delivery_verify.py::_fetch()` —— **临时卸载 + 用后逐键还原**：

```python
_saved = {k: v for k, v in sys.modules.items()
          if k.startswith("api.") or k == "database"}
try:
    for k in list(_saved):
        sys.modules.pop(k, None)
    import api.messages as M
    importlib.reload(M)
    return asyncio.run(M.get_conversation("acc1", "0:1:me:p1"))
finally:
    # 清掉本次新导入的键，再把调用前的对象**原样装回** ⇒ 其它模块的绑定不脱钩
    for k in [k for k in list(sys.modules)
              if k.startswith("api.") or k == "database"]:
        if k not in _saved:
            sys.modules.pop(k, None)
    sys.modules.update(_saved)
```

**为什么这不是「改测试迁就代码」**：修复的是**测试自身违反隔离契约**的缺陷
（设计契约 §1·2「用后必须还原」），产品代码零改动；且修后**原失败形态不再出现**、
被测断言仍具判别力（见 §5 负控）。

## 6. 诚实标注（未验证 / 不可归因部分）

1. 🟡 **全量 `discover` 另有 4 个异常（`test_capability_probe` ×2 / `test_upstream_p4` ×2）**
   —— 已定位为**测试隔离缺陷族**，**非本批代码回归**，证据：
   - `test_upstream_p4` **单跑 27/27 OK**（隔离根）；
   - 根因①：`test_capability_probe` 硬钉**固定共享根** `%TEMP%\dyautodm_cfgtest_root`，
     **不随 `DY_APP_ROOT` 走** ⇒ 与**并行测试进程**争 SQLite 写锁
     （日志逐字：`[db] conv_type 回填失败: database is locked`、

   - **判定**：与 P0-1/A~F 改动**无关**（受影响文件未被本批触碰）；属**项目级测试卫生债**。

**规范沉淀（可复用定式）**：

> **定式 · 测试隔离还原**：凡在用例内 `sys.modules.pop` + `importlib.reload`，
> **必须**把调用前的模块对象快照并在 `finally` 里 `sys.modules.update(快照)`
> 还原；否则「导入期 `from X import Y`」的绑定会与 `sys.modules` 里的新对象脱钩，
> 使后续 `mock.patch.object` 静默失效 ⇒ **顺序相关的假失败**。
> **判据**：任一测试模块，若单独跑绿、与别的模块组合跑红，**先查模块身份/绑定脱钩，
> 不要先怀疑产品代码**。
