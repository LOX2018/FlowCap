# 案例 · 昵称关联「归零」实为探针误报 + 探针假健康镜像（v0.44.29）

> 归档：2026-09-21/22　分支 `design/better-douyin`　环境根 `C:\temp\dyautodm_design`
> 类型：**探针自身缺陷**（非产品链路缺陷）　严重度：中（每天误报 failed，掩盖真信号）

---

## 一、现象与初始误判

**用户/探针给的信号**：`conversation_capture` 探针（尚进账号）state=failed、score=0.0，
且 kv 基线显示 `best=0.9775 → prev=0.0` 断崖。

**我的第一误判**：读 DB `dm_conversations` 得「真实昵称 87/89 = 97.8%」→ 一度以为「归零是陈旧数据、其实健康」。
❌ 这正是探针设计要防的**假健康** —— 库内比例是历史快照，不能代表链路当前状态。

## 二、Execution-Chain 追踪（沿数据流上游）

```
探针 probe_conversation_capture
  ← latest_capture_facts() 扫 logs/*.log 取「最新写库完成」行
      ← 正则 _RE_WRITE 匹配 `写库完成：…uid关联=N sec_uid关联=M 未命中=x/y`
          ← 日志由 conversation_capture.capture_all() 末尾 logger.info 落盘
              ← capture_all(with_browser=?) 两路调用方：
                  · recv_daemon._safe_capture(name)      → with_browser=False（设计不抓昵称）
                  · api/messages refresh / main._nickname_sync → with_browser=True
```

**关键分叉**：`with_browser=False` 走 `capture_all` 时**根本不会**调
`capture_userinfo_via_browser` → `_userinfo_by_uid` 为空 → `uid关联=0` **是预期行为**。
但日志行**不含** `with_browser` 字段，探针无法分辨 → 把它当成「昵称链路失效」。

## 三、实证（Live-Instance Verification）

| 证据 | 结果 |
|---|---|
| 09-14~09-21 各日 `uid关联>0` 次数 | **全部为 0**（86 次写库） |
| `recv_daemon` 19:30:42 的 `[capture] 经 IndexedDB 取到用户信息: 94 条` | ✅ 抓到了 |
| 手动跑 `capture_all(with_browser=True)`（23:37） | **`uid关联=44 未命中=0/44`** ← 链路完全正常 |
| 后端 `[nickname]` 线程日志全库计数 | **0 条**（该后台昵称线程从未运行） |
| 后端侧 `经 IndexedDB 取到用户信息` 计数 | **1 条**（仅 22:21 人工手动跑那次） |

**结论**：昵称能力**本身正常**（浏览器路径 44/44）；`uid关联=0` 全部来自
`with_browser=False` 的启动前移捕获。**探针是假失效（误报）**。

## 四、根因（RCA）

探针 `latest_capture_facts` 两处缺陷叠加：

1. **不区分 `with_browser`** —— 把「按设计不抓昵称」的捕获当作昵称能力证据。
2. **按文件顺序覆盖而非时间戳比较** —— `out.sort()` 按文件 mtime，跨文件时后处理文件覆盖先前文件，
   「最后一条」不保证是时间最新（同一账号多路径写日志时尤其危险）。
3. 附带：探针**永不报 unknown 用于「未被验证」** —— 缺证据时直接判 failed。

## 五、修复（v0.44.29）

| # | 改动 | 位置 |
|---|---|---|
| 1 | 日志行追加 `with_browser={1|0}` | `auto_dm/conversation_capture.py` |
| 2 | `_RE_WRITE` 增可选组 `(?:\s*with_browser=(?P<wb>[01]))?`（**向后兼容**：旧行 → None） | `services/probe.py` |
| 3 | `latest_capture_facts(..., with_browser=None)` 过滤参数 + **时间戳比较** | `services/probe.py` |
| 4 | 新增 `latest_capture_facts_filtered()` | `services/probe.py` |
| 5 | 判定分流：`with_browser=0` → 取最近**带浏览器**证据；无则 `unknown`（**不得 failed**） | `services/probe.py` |

**关键实现坑（测试抓到）**：`if _f2:` 判断 truthy —— 但只含首包的 dict 也是 truthy
（无 `n_conv`）→ 会被当成「有昵称证据」→ **又变假健康**。必须判 `_f2.get("n_conv") is not None`。

## 七、遗留（诚实记录）

1. **未重打包 sidecar**：`recv_daemon`(pid 7624) 与 `browser_daemon`(pid 15324) 正在运行，
   PyInstaller `--clean` 覆盖安装目录有破坏运行态风险 → 需**停进程后重打包**并让新代码生效
   （生效后才会有带 `with_browser` 字段的新日志行）。
2. **`main._nickname_sync_background` 从未运行**（全库 0 条 `[nickname]` 日志）——
   「backend 启动即后台补昵称」这条路径可能根本没被调用。需查 `main.py` 是否注册该线程。
3. 探针在 `with_browser=0` 且无带浏览器证据时报 `unknown` —— 这会让**从未跑过浏览器捕获**
   的环境长期停在 unknown。属**诚实降级**（不冒充健康/失败），但应配一条明确指引。
