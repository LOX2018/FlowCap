# 案例归档 · H-29 消息落库 Schema 治理（ADR-012，v0.45.3 → v0.45.4）

---

## 1. 触发：用户的批评（原话）

> 「本次修复张数据的问题，同时暴露出了数据库字段管理的问题，在面对新类型数据时，
> 并没有形成规划……总是依赖发现问题再进行补救，不是良好的开发习惯，
> **应该在规划和设计层次，就一并考虑好这些问题**」

对应的标准概念：**契约先行 / Schema-as-Code** + **前向兼容（forward compatibility）**。

---

## 2. 调查链

### 2.1 设计意图
- 模块：`dm_messages` 落库。
- 契约：`text` 承载**纯语义**；载荷走 `extra`。
- 期望：新类型数据到来时有**归类规则**，而非塞进已有字段。

### 2.2 当前状态（实测基线，生产库 `m17db0f8209156f26`，账号「四川工伤张老师」）

| 证据 | 数值 |
|---|---|
| `dm_messages` **写入点** | **7 处**（`conversation_capture` ×2、`recv_daemon` ×3、`wp_recv`、`database`），**各自手写列名** |
| `msg_type` 取值 | **8 种**：`text`755 / `7`112 / `delivery_marker`29 / `1`4 / `0`2 / `50010`1 / `27`1 / `15`1 |
| **从未规划过的类型** | **5 种**、36 条（全是「来了就塞」） |
| 本次新发现系统文案 | **183 条**（两种模板，含 `{{0}}` 占位符，全 `role='me'` + `msg_type='text'`） |

### 2.3 执行链
```
新类型数据 → 无归类规则 → 塞进 text
  → _build_history（白名单按 msg_type='text' 放行）→ 进 AI prompt
  → 前端 / 导出
  → 被发现 → 读侧加黑名单 → 又出现新形态 → 再加黑名单   ← 死循环
```

### 2.4 根因（RCA）
- **直接**：7 处分散写入，无单一出口 ⇒ 没有地方能强制「类型必须登记」。
- **深层**：读侧是**黑名单**（排除已知坏），而黑名单只能覆盖**已见过**的形态。
  本次 183 条就是证据：它们 `msg_type='text'`（白名单内）且**无方括号标记**，
  绕过了 H-25（一）的全部前缀黑名单。
- **⇒ 决定性洞察**：真正要防的**不是某个类型**，而是**未知类型**。
  治理目标应改为：**未登记类型必须走安全降级，绝不以「疑似用户消息」形态写进 text。**

## 3. 决策：三层 Schema-as-Code（ADR-012）

| 层 | 内容 |
|---|---|
| **1 类型注册表** | `services/message_schema.py`：`MSG_TYPES`（每类型 → kind）、`SYSTEM_TEXT_PATTERNS`、`classify` |
| **2 单一写入出口** | `MessageRecord.build()` + `.tuple()`（与 `dm_messages` 八列同序）；未知 → `text` 只写语义标签 + `extra.raw` 存原文 |
| **3 机械门禁** | `test_h29_message_schema.py` 16 项（G1~G8 + 负控 N1） |

**字段契约扩展**：新增 `extra.kind`（读侧白名单依据）与 `extra.raw`（未知降级回溯）。

**读侧从「排除已知坏」转为「只放行已知好」**：白名单 = `{user_text, media}`，
未知类型天然被挡在外面，无需事后补黑名单。

## 6. 遗留（诚实标注）

- **7 处写入点仅收敛 3 处**（`wp_recv`、`capture` ×2）。剩 4 处：`recv_daemon` ×3（含 `1460`/`1487` 两处与 `769` 的 init 路径）+ `database.py:455` 迁移路径。
  ⇒ **G6 门禁已就位**：新增裸写会被拦，故剩余收敛不紧急但**必须做**（已登记台账 H-29）。
- **平台提示模板靠样本归纳**（本次两种）。抖音若新增模板会被降级为 `unknown` —— 危害已从「污染」降为「不认识」，但需补注册表才恢复展示语义。

## 7. 教训（写给未来）

> **黑名单式补救永远补不完。** 这次 183 条的发现就是证明：它绕过了 H-25（一）
> 建立的全部前缀黑名单，因为它的 `msg_type` 在白名单内、且没有方括号标记。
>
> 正确的治理位置在**写入前**（注册表 + 单一出口），不在读出后（黑名单）。
> 判据：如果一条新数据需要你「先看见它长什么样」才能拦住它 —— 那这个设计就是错的。
