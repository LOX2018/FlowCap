## 1. P1-① `services/ai_reply.py` —— 图片描述缓存整 dict 读-改-写无锁

### 设计契约（ADR-008 决策 2/3）
`_img_desc_get/_known/_mark` 维护 `ai_img_desc` 缓存；ADR-008 决策 3 开启
`reply_concurrency` 线程池后，不同会话**并发**调用 `_describe_image`。

### 根因
三函数各自 `_kv_get(整 dict) → 本地改 → _kv_set(整 dict 覆盖)`，**无任何锁** ⇒
并发 last-write-wins，互相**静默丢弃**已写入的条目（淘汰排序同样竞争）。

### 实测证据
```
无锁（修复前）: 8 线程×30 = 期望 240 条  实际保留 50 条   ← 丢失 190 条(79%)
带锁（修复后）: 期望 240 条            实际保留 240 条  ← 丢失 0
```
（另注：并发下 KV 层自身也会报 `cannot commit - no transaction is active`，
印证并发面比纯 dict 竞争更广。）

### 修复
新增模块级 `_IMG_DESC_LOCK = threading.Lock()`，三函数**全体**进入临界区（含淘汰与写回）。

## 2. P1-② `notify/inbound.py` —— 重登后 `ch.token` 未同步

### 设计契约
iLink 会话过期（ret=-14）→ 自动重登 → 取得**新 token** → 继续轮询并回复入站消息。
轮询走闭包局部 `token`，**回复走 `ch.send()` → `WeixinOCChannel._do_send` → `self.token`**。

### 根因
重登成功只执行 `token = logged`（**闭包局部变量**），**未回写实例** `ch.token` ⇒
`ch.send()` 仍用过期的旧 token ⇒ 会话恢复后**回复仍失败**（同会话两路径 token 分裂）。

### 实测证据（驱动真实 `_run_ilink`）
```
修复前: getupdates 已用 NEW_TOKEN，但 ch_send_tokens_used = ["OLD_TOKEN"]
修复后: getupdates 用 NEW_TOKEN，   ch_send_tokens_used = ["NEW_TOKEN"]   ✅
```

### 修复
登录成功后 `ch.token = token`（带回滚保护的 try/except）。

## 3. P1-③ `services/kernel_truth.py` —— TTL 与真值采样门限不匹配

### 设计契约
`kernel_truth` 的使命是让**指纹档案跟随浏览器内核真值**，根除「档案≠内核两层脱节」。
`get_kernel_truth()` 超 TTL 判 `stale` → `fingerprint_profile` **静默回落项目预设**。

### 根因（调用链实证）
原 `_MAX_AGE_SEC = 1800`，注释以「保活心跳 300s」推定 30 分钟足够；但**真正触发真值写盘的
不是心跳**，而是 `daemon/bcc_login.py:513` 的 **3600s 门限**：
```
if _now2 - self._last_env_audit_at >= 3600:  ... env_audit_snapshot()
```
且 `record_kernel_truth` 的唯一入口是 `bcc_audit.env_audit_snapshot`（:397），
**容器启动路径不写快照** ⇒ 每次写盘后有 **30~60 分钟区间** TTL 已过、真值却未刷新 ⇒
每小时约**一半时间**判 stale，正是本文件要根除的脱节**周期性复现**。

### 实测证据
```
时点     旧 TTL=1800      新 TTL=7200
T+1700   fresh            fresh            两者一致
T+3000   stale(误判!)     fresh            🔴 旧缺陷窗口（1800~3600）
T+8000   stale            stale            超 2×门限，判 stale 正确
```

### 修复
`_MAX_AGE_SEC 1800 → 7200`（= 2×采样门限），保证「采样周期内恒 fresh」；
超过 2×门限仍未刷新才判 stale（那时保活巡检可能已停，判 stale 是正确的）。

## 4. P1-④ `dy_apis/client_user.py` —— 失败缓存写在 HTML 回退之前

### 设计契约
`get_my_sec_uid` 主路径（`profile/self`）失败 → **HTML 回退**（保留兼容）→ 仍失败才抛。
失败缓存语义：`(ts, "")` 表示「60s 内已失败，不再重试」。

### 根因
主路径两次失败后**立即**写 `_sec_uid_cache[key] = (time.time(), "")`，
**但此时 HTML 回退尚未执行**。回退一旦取到合法 sec_uid 并 `return`，缓存里
却留着**污染的空值** ⇒ 60s 内下一次调用被读侧（L345-349）判为已失败直接 `raise`，
尽管上一次其实**解析成功**。

### 实测证据
```
主路径失败 + HTML 回退成功：
  修复后: 返回合法 sec_uid，缓存项 = None（无污染）   ✅
  对照  : 若缓存被污染 ⇒ 下次调用立即 raise「60s 内已失败过，暂不重试」  ← 这就是旧形态后果
```

### 修复
删除早写；把失败缓存**移到 HTML 回退也确定失败、即将 `raise` 之前**（全路径仅一处）。

## 7. 教训（写入）

1. **「整 dict 读-改-写」在并发下必然丢条目** —— 凡 KV 里存**聚合结构**并被多个执行体
   读改写，必须加锁或改为**每项独立键**。判据：并发测试直接数「写入 N 次后键还剩几条」。
2. **「局部变量已更新」≠「实例状态已更新」** —— 同一实体的两条访问路径（闭包 vs 实例字段）
   必须同步；判据是**看最终消费点用的是谁**（本例 `ch.send → self.token`）。
3. **TTL/超时的取值依据必须锚定「真实的刷新触发点」**，不能锚定「看起来相关的周期」。
   本例把心跳周期当刷新周期 ⇒ 半个周期处于误判态。
4. **失败缓存的写入时机必须晚于「所有可能的成功路径」** ——
   提前写失败 = 把一次成功判成失败，且会**持续 60s 污染**后续调用。
