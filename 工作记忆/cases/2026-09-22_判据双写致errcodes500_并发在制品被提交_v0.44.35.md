# 案例：判据双写致 `/api/errcodes` 500 + 并发下「在制品被他人提交」（2026-09-22）

> **类型**：① 判据双写（数据层）② 多会话并发（协作层）
> **产物**：`errcode_data.py` 契约整形 + 全后端重复键门禁 + 7 个僵尸脚本退役
> **关联**：`01_铁律与红线.md` D-05（一条码一条记录）· 用户级 skill `persistent-resource-manager`

---

## 一、观测偏差（Step 2）

| 项 | 实测 |
|---|---|
| 现象 | `GET /api/errcodes`（**会员门禁豁免端点**）必然 500；`all_codes()` 直接抛异常 |
| 复现 | `python -c "from errcode import all_codes; all_codes()"` → `KeyError: 'meaning'` |
| 危险度 | 端点**免鉴权**（`main.py:_MEMBER_EXEMPT` 含 `/api/errcodes`），且前端错误码查询页依赖它 |

## 二、链路溯源（Step 3）

```
errcode_data.py 的 ERRCODES 字典内，"ACC-017" 被定义两次：
    行 185  单行记录 {meaning, file, line}      ← 业务代码真正使用的那条语义
    行 333  六段契约 {design, contract, ...}    ← 抄写时放错字典（应为 CODE_DESIGN）
  ↓ Python 字面量重复键 = last-wins（无告警）
  ↓ 生效的是行 333 那条 → 缺 "meaning"
  ↓ errcode.lookup() 第 56 行 c["meaning"] → KeyError
  ↓ all_codes() → 逐个 lookup → 首个缺 meaning 的码即崩
  ↓ GET /api/errcodes → 500
```

**注意链路方向**：终端症状在 HTTP 500，源头在**数据字面量的键覆盖**，
中间隔着 `lookup()` 的取值假设「每个 ERRCODES 条目必有 meaning」。

## 三、根因分析（Step 4）

**为什么断在这一点**：`ERRCODES` 与 `CODE_DESIGN` 两个字典**都没有表达力**去说明
「一条码的完整定义应当只写在哪里」——于是同一码的两个片段被分别写进两个字典，
作者按直觉选错宿主即静默失效。这是**契约 host 不明确**，不是某个人的疏忽。

**第二个根因（让缺陷逃逸的）**：既有的防重复键门禁 `test_no_dup_dict_keys.py`
的扫描目标**硬编码为单个文件**（`services/app_config_schema.py`）——
同一缺陷形态在别处**完全无防护**。缺陷存在期间，该门禁**一直全绿**。

## 四、修复（Step 5 实机验证）

| 动作 | 证据 |
|---|---|
| ACC-017 契约按**真实语义**重写（落盘失败为可降级旁路），迁入 `CODE_DESIGN` | `lookup('ACC-017')` → meaning/design/contract/chain/root/verify 六项齐、`has_contract=True` |
| 丢弃误附的「所有权锁」文本 | 该文本描述的事件实由 ACC-022/023/024 承担（各有契约），照抄会**劫持邻居编号语义** |
| ACC-018~021 幽灵契约**不回填** | 实测：ERRCODES 内从无条目、业务代码 **0 处**发出；回填会造出 4 条永不触发的契约 |
| 门禁扩为**全后端扫描** | `test_whole_backend_has_no_duplicate_dict_keys`：先量现状（224 文件 / 0 命中）再收紧 |
| 门禁**有效性反证** | 用「改前备份」喂 `find_dup_keys()` → 报出 `dict@163: 'ACC-017' 行 [185, 333]`；修复后 0 |

**验证读数**：

```
all_codes() -> 361（修复前：KeyError 崩溃）
lookup('ACC-017').has_contract -> True；ACC-018~021 -> None（确认存在于 ERRCODES 的才是真码）
全量回归: Ran 562 tests, OK（3.14 与 3.11 各一次）
门禁: check_version_sync EXIT=0 / check_contracts EXIT=0 / test_no_dup_dict_keys 3 项 OK
行尾: numstat 与 --ignore-all-space numstat 逐文件相等（零污染）
```

## 五、并发事故：在制品被另一会话提交并构建部署

**事实（时间线）**：

| 时刻 | 事件 |
|---|---|
| 15:30 | 我备份原文件、开始改 `errcode_data.py`（试了 3 版字节编辑，中途把文件留在半成品态） |
| **16:04** | **另一会话提交 `e43d153`（v0.44.34）**，其 diff **含 `errcode_data.py`（我改到一半的状态）** |
| 16:08 | 该会话构建三个 sidecar |
| 16:10 | 部署到 `C:\temp\dyautodm_design\DYAutoDM_v2_0.44.34-debug.exe` |
| 16:14 | 我发现版本已从 0.44.33 变 0.44.34，且我的 `git add` 因**一个不存在的路径**整体失败 |

**核对结论**（不臆断）：

- 其提交的 `errcode_data.py` **无重复键**（对 HEAD 提交态跑门禁确认）⇒ **500 已不存在**，属"已修好"。
- 但 HEAD 中 **ACC-017 出现 2 次**（ERRCODES 一条 + CODE_DESIGN 一条）⇒ 六段契约**双host**（非致命，但正是要根治的形态）。
- HEAD 仍含 **4 条幽灵契约** ACC-018~021 与**误附的「所有权锁」文本**。
- ⇒ 我的工作区版本更干净，属**正当的前向修复**（非回退他人成果）。

**机理（比个案更重要）**：并行工作线的「commit」会**快照整个工作区**，
因此另一条线提交时会把**你未写完的在制品**一起带走。与 `multi-session-collaboration`
已记载的「逐文件 add 保护不了文件内他人 hunk」互为镜像 ——
**同一工作区并行改代码，无论谁提交，都会把对方的中间态夹带进去**。

**唯一可靠的解法**：改文件前**先声明所有权**；做不到就**给写者隔离副本**
（`git worktree` 或每会话一份源码树）。在共享工作区里"改一半放着"是**高风险动作**。

## 七、可迁移判据

1. **同一事实只允许一个宿主**，且宿主必须**显式**（哪个字典、哪一层）。两个字典都能放 = 迟早放错。
2. **读侧假设要写进门禁**：`lookup()` 假设「条目必有 meaning」——那就应该有门禁**证明**该假设。
3. **门禁的扫描范围本身就是判据的一部分**：只扫一个文件的门禁，等于对其它 N 个文件没有门禁。
4. **删除前先备份到仓库外**：被 `.gitignore` 忽略的资产，`rm` 之后在 git 里**没有副本**。
5. **共享工作区里不要留半成品**：别人一次 commit 就会把它带走并可能**构建部署**出去。
6. **发现版本号/暂存区异常，先查并发**（`git log` 时间线 + `ls -l` 产物时间），
   再决定是"重升版"还是"等对方收工"；**不要**盲目再升一次（会撞号）。
