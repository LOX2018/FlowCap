# 私信中心工具栏重排 + 分隔线 ID 显示移除（v0.43.92）

- **日期**：2026-09-19
- **分支**：`design/better-douyin`
- **版本**：v0.43.91 → **v0.43.92**
- **改动文件**：`DYAutoDM_v2/frontend/src/components/messages/messages-page.tsx`（唯一源码改动）
- **需求原话**：私信中心的「会话列表」工具栏只保留「更新会话」和「搜索」，删除「新建会话」按钮；
  其他功能都移动到「聊天记录」框「导出会话」的左侧；并删除原「导出会话」左侧的会话 ID。

## 一、设计意图回归（Step 1）

| 位置 | 设计职责 |
|---|---|
| **会话列表工具栏**（左栏 Section actions） | 只承载**会话列表这一侧**的操作 |
| **聊天记录框头**（右侧 Card 头） | 承载**当前会话内容**的操作 + 「导出会话」 |

由此推出本次重排的**归属判据**（不是审美偏好，是作用域判据）：

- 「更新会话」= 拉取会话列表 + 聊天记录 → **列表侧**，留在左栏 ✅
- 「搜索」= 按昵称过滤会话列表 → **列表侧**，留在左栏 ✅
- 「新建会话」= 主动向目标发起私信 → **既不是列表操作、也不是当前会话操作**，
  且与「下拉列表 → 点会话 → 聊天」主流程无关 → 用户判定为**删除** ✅
- 「语音转写 / 导出长图 / 选区导出 / 导出 ChatLab / 检索消息」= **全部作用于当前会话内容**
  → 归属**聊天记录框头**，统一放在「导出会话」**左侧** ✅
- 「会话 ID {conv.id}」= 分隔线右侧的裸 ID 显示 → **删除**（用户明确要求）✅

**契约不变式**：会话列表工具栏的按钮数 == 2（更新会话 / 搜索）；聊天记录框头按钮 == 6
（语音转写、导出长图、选区导出、导出 ChatLab、检索消息、导出会话），且「导出会话」恒在**最右**。

## 三、实施手法（避坑）

### 3.1 文件是**全 CRLF**，必须字节级替换

`messages-page.tsx` 实测 `CRLF=1394 / bareLF=0`。用 `patch` 或普通文本写回会把整文件
行尾统一 → **整文件 diff**（§〇·庚 已有记录）。本次改用 Python：
`open(...,newline="")` 读 → 字符串级精确替换（`\r\n` 显式）→ `open(...,"wb")` 写回。
结果：`git diff --numstat` 只有 **274 增 / 332 删**（而不是整文件），行尾仍 `bareLF=0`。

### 3.2 插入片段时锚点行会被复制 → 多出一个 `</div>`

把检索面板插到 `data-dm-scroll` 之前时，锚点串本身以 `</div>\r\n` 开头，导致那个 `</div>` 被
复制了一份 → `tsc` 报 `JSX element 'Card' has no corresponding closing tag`。
**修法**：锚点只取后半段（`<div className="flex min-h-0 ...`），不要连前一行 `</div>` 一起取；
出错后用它自己的报错行号定位（`TS17008` → 对应行）。

### 3.3 改动是纯前端 → 按分支现行纪律**仍升版本号 + 重打 sidecar**

本分支实测 v0.43.84/85/89/90/91 等纯前端提交**都升了版本号**，且 `deploy.py` 校验2
（sidecar 内嵌 `_build_version.py` == `tauri.conf.json`）会拦下「升了版本却没重打 sidecar」。
故本次按同一纪律执行：五处版本齐平（`package.json`/`frontend/package.json`/
`tauri.conf.json`/`Cargo.toml`/`backend/_build_version.py`）→ `build_sidecar.py --onedir`
→ `tauri build --no-bundle` → `deploy.py`。

### 3.4 打包白名单：用正式版口径（不带 `--debug-whitelist`）

`build_sidecar.py` 仅在显式传 `--debug-whitelist` 时注入测试白名单（限制私信只能发给白名单目标，
是「防误发真人」的护栏）。生产功能验证应走**正式口径**（`_TEST_WHITELIST` 空壳、
`TEST_WHITELIST_ON=False`，白名单逻辑物理不执行）。本次即按此口径构建，构建后复查
`backend/services/dm_dispatch.py` 注入区仍为合法空壳（`restore_whitelist` 生效）。

### 3.5 🔴 部署被目录占用打断：`deploy.py` 的 `_internal` 清理链

`deploy.py:248-250` 是 `shutil.rmtree(dst_i, ignore_errors=True)` **紧跟** `copytree`。
当目标 `C:\temp\dyautodm_design\_internal` 正被进程占用（本次：上一次**源码模式** backend
`python main.py --port 8017` 在 17:10 拉起的 BCC / recv_daemon / `patchright` 的 `node.exe`
都从该目录加载），`ignore_errors=True` 会**静默吞掉失败**，随后 `copytree` 抛
`FileExistsError [WinError 183] 当文件已存在时`，部署在拷 `_internal` 这一步**中断**。

**症状排序（为何容易误判）**：
1. 校验1/2/3 全绿 → 看起来一切正常；
2. 主程序 exe 已按真实版本拷好、旧版 exe 已删 → **看起来已部署**；
3. 但 `_internal` 半删半留（实测残留 47 条，其中 `.pyd`/`.dll` 报
   `PermissionError WinError 5`）→ 应用**必然起不来**。

**处置（顺序不可颠倒）**：
1. **先算进程归属**（§三·丁）：`Get-CimInstance Win32_Process` 按 `CommandLine` 过滤
   `dyautodm_design`，看 `ParentProcessId` —— 父进程是开发用的源码 backend 即**非用户桌面端**；
2. **停 BCC / 守护只走 `POST /quit`**（逐个端口），**绝不 taskkill** ✅ 实测三个守护都返回 `{"ok":true}`
   且**无复活**（父 backend 未被 `_dreg` 重新拉起，说明该退出路径会清理注册表）；
3. 用 **`os.walk(topdown=False)` + `chmod` + 逐个 `remove`/`rmdir`** 清掉半删残留
   （**不要**再 `rmtree(ignore_errors=True)`，那会再次静默失败）；
4. 确认 `basename(_internal)` 条目数 == 构建产物条目数（本次 123）；
5. 重跑 `deploy.py` → 三条 md5 全绿。
6. `node.exe`（patchright driver）由 BCC 派生，**随 BCC 退出而释放**；它就是
   `_internal` 被占用的直接持有者，单独找它没用，要停的是 BCC。

**推广规则**：`deploy.py` 这套「`rmtree(ignore_errors=True)` + `copytree`」在 Windows 上
**不保证幂等**。凡部署前，先验证目标环境**无任何进程从该目录加载**（尤其 `_internal`）。
