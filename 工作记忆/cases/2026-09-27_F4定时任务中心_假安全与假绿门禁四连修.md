- **日期**：2026-09-27
- **版本**：v0.45.51 → **v0.45.52**（单批）
- **提交**：`12ce3fa`
- **来源**：全库审计 `artifacts/audit_2026-09-27/`（区间 `c9db81e..HEAD`）
- **处置方案**：用户拍板 **A**（先修门禁 → 再修缺陷 → 最后接线）

---

## 1. 为什么这个案例值得单独归档

它是本项目「**声明式规则 = 空架子**」教训的**第 N 次复现，且这次最反讽**：
门禁**自己**写得很认真（有负控、有注释反思「初版判据不行，已改成锚定执行分支」），
但判据**全部是源码字符串匹配** —— 于是它守护的对象全坏，它却 **7/7 全绿**。

**更危险的是这组组合**：
- 缺陷让功能**看起来安全**（闸门恒拒 ⇒ 发不出去）；
- 门禁让缺陷**看起来不存在**（7/7 全绿）；
- 两者叠加 ⇒ 同时骗过「功能是否可用」与「是否安全」两个判断。

若不交叉验证（三份子代理报告 + 主链亲验），会得出「F4 合规」的结论。

## 2. 四条缺陷（互锁）

| # | 级别 | 缺陷 | 危害 |
|---|---|---|---|
| **TS-9** | P0 | 门禁 G1~G7 全是**源码字符串匹配** | 让下面三条**不可见** |
| **TS-2** | P1 | `ok, why = quota.can_send()` —— 而它返回 **3 元组** | 三重闸门**100% 恒拒**（假安全） |
| **TS-3** | P1 | `getattr(res,"ok")or getattr(res,"accepted")` 当 `delivery_verified` | **入池冒充投递成功** |
| **TS-8** | P2 | `Task.__init__(enabled=True)` | 违反 D1「逐任务默认休眠」 |
| **TS-1** | P0 | `register_builtin_handlers`/`start` **全仓 0 调用点** | F4 是**空壳** |

### 🔴 必须记住的互锁关系

**TS-2 的「发不出去」是假安全。单独修 TS-2 会让 TS-3 从「被掩盖」变成「真漏洞」**
—— 因为闸门一放行，`_auto_dm` 就会带着 `delivery_verified=True`（假的）真发出去。

⇒ **TS-2 与 TS-3 必须同批修**。本案例即同批。

## 3. 修法要点

### TS-9：门禁改为**行为断言**（v2，B1~B7）

v1 vs v2 的关键差异：

| v1（字符串匹配） | v2（行为断言） |
|---|---|
| `"can_send()" in s` | **真调** `_gate_for_send`，注入**记录调用**的假 quota，断言 `can_send`/`can_stranger_first` **都被调用**且**解包不抛** |
| `"if needs_send and REQUIRE_DELIVERY_VERIFY:" in s` | **真调** `_auto_dm`，断言 `accepted=True` 时 `delivery_verified is not True` |
| 匹配 `_env_bool(..., False)` 文本 | 读**运行时值** `ts.TASK_SCHEDULER_ENABLED is False` |
| — | 新增 B7：**真构造** `Task`，断言 `enabled is False` |

**v2 首跑即报红 4 项**（B3/B4/B6/B7）—— 这正是「门禁真的在看行为」的证据。

### TS-2：按**各自真实签名**解包

```python
_cs = quota.can_send()            # (ok, reason, 还需等待秒数) —— 3 元组
if not _cs[0]: return False, ...
_cf = quota.can_stranger_first()  # (ok, reason) —— 2 元组
if not _cf[0]: return False, ...
```
**教训**：两个「看起来同类」的 API 返回元数不同，**不可一刀切**。

### TS-3：承认「本层拿不到证据」，返回**诚实三态**

关键依据是**仓库里早已存在的架构注释**（`core/sender.py:258-261`）：
> 投递验证标记**只在持有服务端证据的一侧写入**（`sender_direct` / `recv_daemon`）；
> `dispatch`/`dm_dispatch` 侧的「盲标记」**已删除**（它们拿不到证据）。

调度器走异步队列（`submit_by_uid`）⇒ **同样拿不到服务端消息号** ⇒ 不可能产出证据。
故返回：
- `True` —— 仅当持有证据（本层**不会**出现）
- `False` —— 明确知道失败
- **`None` —— 未验证（本层的正确值）**

**教训**：**先 grep 仓库里既有的架构注释**，它往往已经写明了正确分工（本项目铁律：
「动手修 bug 前不自造轮子，同一仓库里很可能已有该能力」）。

### TS-8：`enabled: bool = False`（D1 是**逐任务**语义）

模块级双总开关（默认 False）**挡得住**「全自动外发」，但**总开关是粗粒度的**：
用户按 ADR-018 打开调度中心（**正常用法**）后，所有历史 `enabled=True` 的外发任务
会**同时复活** ⇒ 必须在**任务粒度**默认休眠。

### TS-1：接线（先注册 handler，再尝试 start）

```python
_reg = _ts.register_builtin_handlers()   # 先注册：让任务有执行体
_st = _ts.start()                        # 再启动：总开关关则 fail-closed
```
**接线实测**：出厂态 `start() ok=False` 且 `_timer is None`（**零副作用**）；
显式开总开关后 `ok=True` 且 `handler_kinds=['auto_dm_send','hot_comment_crawl']`。

## 4. 本批踩到的**装置自身**的坑（都记下来）

### 坑 1：负控脚本的 `importlib` 缓存（假失败）

`--selftest` 篡改源码 → 跑 → 还原。但 `task_scheduler` 一旦 import 就进
`sys.modules` **缓存** ⇒ **磁盘还原了，内存里的类仍是旧版** ⇒ 下一轮读到
上一轮篡改的代码 ⇒ **假失败**（实测：全部用例通过 + 磁盘字节一致，
但「还原后复跑」仍报 B7 红）。

**修法**：篡改后与还原后**都调 `importlib.reload`**。
**判据**：凡「改写源码后重跑」的装置，**必须显式 reload** ——
不能假设「文件还原了 = 行为还原了」（与「资源释放是异步的」同类错误）。

### 坑 2：负控锚点会随修复失效（静默跳过）

修好 TS-2 后，负控里「把 `ok, why = quota.can_send()` 改坏」的锚点**不存在了**
⇒ 用例**跳过**。而**跳过 = 该判据没有负控覆盖** —— 比报错更危险。

**修法**：负控锚点必须**同步换成当前代码形态**的「改坏」写法（每修一次实现就换一次）。
**判据**：负控脚本的「跳过」分支应被视为**待办信号**，不是正常路径。

### 坑 3：负控锚点行尾不匹配（CRLF vs LF）

本仓 `services/*.py` 是 **CRLF**，`api/*.py` 是 **LF**。负控锚点只写 `\n`
⇒ 在 CRLF 文件上「命中 0 次」⇒ **又是静默跳过**。

**修法**：负控锚点**按目标文件行尾自适应**（`_fix()` 转换）。
（此坑在本项目**已第二次踩到** —— 前次在 `test_f1_d1_d3` 的负控脚本。）

### 坑 4：写「坏形态」时写错了 —— 没真坏

我把 `_cs = quota.can_send()` 改成 `_cs, _bad = quota.can_send(), None`
—— 这**仍然是正确解包**（`_cs` 拿到 3 元组），所以门禁不报红。
**负控脚本正确地报出了「门禁未覆盖该形态」**，我据此改成真会抛异常的形态
（`_a, _b = quota.can_send()`）。

**判据**：写负控时要**自问「这个改动真的会让被测行为变坏吗」**，
并**依赖负控脚本的自检**（它必须能报出「未变红」）。

## 7. 可迁移判据

1. **门禁锚定「行为」而非「源码文本」**：字符串存在 ≠ 逻辑正确；
   更糟的是**缺陷本身往往就写在那个字符串里**（本案例 G6 即如此）。
2. **负控的「跳过」= 覆盖缺口**，必须当待办处理，不能当正常路径。
3. **凡「改写源码后重跑」的装置必须 `importlib.reload`**。
4. **负控锚点要行尾自适应**（本仓 CRLF/LF 混用，已两次踩到）。
5. **写负控要自问「这改动真会让行为变坏吗」**，并靠脚本自检兜住。
6. **修之前先 grep 仓库既有注释**：架构分工往往已写明（本案例 TS-3 的正解
   就来自 `core/sender.py` 的既有注释，不需要自造）。
7. **「假安全 + 假绿门禁」组合必须交叉验证才能发现**：单一视角（只跑门禁、
   或只读代码）都会得出「合规」的错误结论。
8. **同批修复互锁缺陷**：修 A 会暴露 B 时，A/B 必须同批（本案例 TS-2 ↔ TS-3）。
