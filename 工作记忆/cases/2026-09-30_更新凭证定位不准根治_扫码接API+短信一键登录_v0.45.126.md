- **日期**：2026-09-30
- **报告人**：用户（LOX）实测报障
- **触发原话**：
  > 「目前凭证更新依旧使用未修复的二维码和短信通道，先尝试修复，如果不能就变回最初的弹出浏览器用户手动更新」
  > 「我点击的是凭证校验区域的**立即处理**按钮，以及上方的**更新凭证**按钮他都是用这个逻辑来处理的，
  >   但是现在感觉**定位是有问题的**，所以没有办法精准找到**二维码和短信登录的入口**」
- **版本**：v0.45.125 → **v0.45.126**

## 1. 报案现象

| # | 用户可见现象 |
|---|---|
| 1 | 点「更新凭证」/「立即处理验证」，两条「定位不准」：**二维码抓不到、短信登录进不去** |
| 2 | 短信「提示发送失败」或一直卡住（实际卡在更早一步） |

```

   ↓

   ↓

   │                                            ⇒ 界面上根本没有该输入框
   └─ 实测日志：16:19:51 短信登录失败于 fill_phone: 手机号填入失败（input[name="normal-input"]）
```

## 4. 根因收敛

1. **界面分支未枚举** —— `do_sms_login` 假定「任何 profile 状态下都有手机号表单」；
   已记住账号的 profile 弹的是「一键登录」面板 ⇒ 100% 卡在 `fill_phone`。
2. **契约漂移（第二次复发同型病）** —— 处理函数 `handle_one_click_login` 写好了但**没接线**
   （与 H-30「`login_remote.py` 是全仓零调用孤儿模块」同型）。
3. **硬编码锚点被外部改版打废** —— 二维码 `<img>`→SVG、tab 具名→哈希类名。
4. **更优能力未接线** —— ADR-017 拍板的 API 扫码路径从未落地。

## 5. 修复（见 ADR-034 §4）

- 扫码：**优先上游 API（纯 HTTP，子进程隔离 + 文件交接）**，RPA 容器栅格化降为兜底；
- 短信：`do_sms_login` **第一步**接 `handle_one_click_login`（判据改为决定性的「登录其他账号」），
  tab 改点稳定 id；
- 凭证写盘：唯一入口 + 写前备份 + **四件套硬门禁** + 三重校验（磁盘/服务端/身份），
  不过就**还原并回落**；
- 环境：API 代理**只由账号配置显式决定**，不探测本机。

## 9. 【2026-09-30 续】用户指正：改为「接口桥」形态（v0.45.133）

### 9.1 用户原话（本轮的真正指引）
> 「先暂停……我的意思是说，先起个无头浏览器，然后把 API 使用的方法在无头浏览器上面
>   进行监测。这样的话，就不需要在浏览器上面就进行实际扫码，而是相当于一个桥梁，
>   把浏览器上面的接口暴露给前端」

### 9.2 这不是"换个取码方式"，而是**正确性层级**的差别

| 形态 | 二维码来源 | 身份 | 判据 |
|---|---|---|---|
| DOM 截图 + cv2 解码 | 像素（会随改版失效） | 同 Firefox ✅ | 脆弱（锚点/改版） |
| 纯 API 子进程 | 协议响应 | 🔴 Chrome⊗Firefox 矛盾 | 出码可，但身份存疑 |
| **接口桥（本轮）** | **页面自己发的 `get_qrcode` 响应** | 同 Firefox ✅ | **改版免疫 + 身份一致** |

### 9.3 真机实测（bridge_probe2 + bridge_verify，全部实机，非推断）

```
深链 ?modal_id=login（唯一能唤出接口的入口）：
  30s 面板挂载 → 40s 页面自发 get_qrcode(error_code=0, token, qrcode_index_url)
  → 页面自维持 check_qrconnect 轮询（计数 2→3→5→7）
首页 + 点「登录」：get_qrcode = 0   ⇒ 入口必须是深链（硬判据）
```
```
bridge_verify（桥本体）：
  B1 ok=True via="bridge"  qr_url=https://api.amemv.com/.../scan_code_login...  token=cafbddf3…
     耗时 21.3s（对比 DOM 截图 ~40s）
  B2 渲染 PNG 3259 字节                      ✅ 前端可直接展示
  B3 无人扫码 ⇒ 正确超时(ok=false, status=new)  ✅ 不谎报成功 + 证明监听生效
```

### 9.4 落地
- `login_remote.bridge_qr_login`（被动 `context.on("response")` 截 `get_qrcode`）
- `login_remote.poll_bridge_confirmed`（被动截 `check_qrconnect` 的 `status=confirmed`）
- `_rpa_scan_login`：**桥优先 → 截图兜底**
- `scan-status` 增 `qrUrl`（二维码原始 URL 直接暴露给前端）

### 9.5 本轮新增的可迁移判据
1. **"只被动监听、不主动构造请求"** 是身份的天然保证：页面自己发的请求 = 与真人操作等价，
   不存在 API 路径那种「参数/头/缺 dtrait/身份矛盾」。
2. **深链 ≠ 首页点登录**：实测同一站点，深链页面自发接口、首页点击不发 ⇒
   入口必须按**实测**选，不能按"看起来更稳"选。
3. **早采样会把"慢挂载"误判成"不存在"**：面板 30s 才挂载；我一度据此得出
   "面板不存在"的错误结论（后被长观察推翻）——**结论前必须给足时间窗**。
4. **无人操作时的正确行为是"如实超时"**：桥在无人扫码时返回 `ok=false, status=new`，
   这正是"不谎报"的判据（与 §10 的假成功根治同源）。
5. **`count()` 判元素存在会假阴性**：`#animate_qrcode_container` 的 `count()==0`
   但元素截图/监听照样成功 ⇒ 用 `count()` 判"有没有"不可靠。

## 8. 可迁移判据

1. **「能力已实现」≠「已接线」**：文档/模块声称的能力，必须机械检出**调用点**。
2. **同名顶层包 ⇒ 只能子进程隔离**（同进程 `sys.path` 操作无解）。
3. **改版免疫的定位顺序**：确定性接口 → 稳定 id → 容器栅格化/机械解码 → 文本兜底。
4. **界面分支必须显式枚举**，否则必在某分支 100% 失败。
5. **落盘类子进程必须顶层兜底写盘**，否则失败只剩「进程消失」。
6. **凭证写盘硬门禁**：四件套不全**绝不落盘**（缺件会反派生旧签名 = 假成功）。
