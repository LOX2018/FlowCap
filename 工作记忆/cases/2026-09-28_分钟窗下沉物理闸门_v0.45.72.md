# 案例：分钟窗下沉到 recv_daemon 物理闸门（v0.45.72）

- 日期：2026-09-28
- 关联：ADR-021（修订段）、`daemon/recv_daemon.py`、`api/messages.py`、`frontend/src/{api/client.ts, components/messages/*}`
- 前序案例：`2026-09-28_发送回执类型化+分钟级限流+AI获客治客服腔_v0.45.68.md`

## 1. 起因

用户原始诉求（v0.45.68 已部分落地）：「投递回执分辨失败类型 + 发送频繁冷静 10 分钟 +
**每分钟 2~3 个**」。
本轮「继续」= 补齐 ADR-021 明确登记的**唯一残留**：
「图片发送仍走各账号闸门，**未接入账号级分钟窗**」。

## 2. 链路取证（为什么分钟窗能绕过）

```
文本手动发送  → api/messages /send → services/dm_dispatch.submit（调度器）
                → AccountQuota.can_send(min_interval, per_minute)  ← 分钟窗在这里
                → recv_daemon /send → _send_gate_acquire（仅 min_interval）

图片发送      → api/messages /send_image → recv_daemon /send_image
                → _send_gate_acquire（仅 min_interval）           ← 完全不过调度器
```

**结论**：分钟窗只在**调度器策略层**；图片发送**不过调度器**，故完全不受分钟窗约束。
§recon 实测：用户 2026-09-25 曾一次发出 **26 条**（现网 dm_messages `role='me'`）。

## 3. 设计决策（分层，非叠加）

| 层 | 职责 | 手动豁免？ |
|---|---|---|
| 调度器 `AccountQuota`（策略层） | 最小间隔 + 陌生人首发 + 分钟窗 | 是（铁律：不拦用户显式操作） |
| `recv_daemon._send_gate_acquire`（**物理兜底**） | 最小间隔（打 5 折）**+ 分钟窗（新）** | **否** |

**为什么物理层不豁免手动**：
① 覆盖「不过调度器的图片发送」与「绕过调度器的直发」——**任何路径都无法绕过**；
② 分钟窗正是用户显式要求的「每分钟 2~3 条」风控约束，不是「拦用户的误操作」；
③ 用户一次连发 26 条的实测正是本项要防的**极端风控敞口**。
（`minor` 代价：手动发送也受每分钟上限约束 —— 若用户很在意「手动狂点」，可把
`per_minute_limit` 调高到 5~6，或置 0 关闭；已在配置 hint 写明。）

## 4. 实现

1. `_FALLBACK_PER_MINUTE = env DY_SEND_PER_MINUTE / 3`；`_cfg_per_minute()` 读配置中心
   （`send.per_minute_limit`，与调度器**同一 SSOT**）。
2. `_send_gate_minute: dict[account, list]` 滑窗，与 `_send_gate_last` 共用
   `_send_gate_lock` ⇒ 三端点**汇总计数、无并发滑窗**。
3. 超限**快速失败**（不忙等：等满 60s 只会堆死事件循环），返回
   `{ok:False, error:"rate_limited", error_kind:"rate_limited", reason_code:"minute_limit", msg:"已达每分钟发送上限 N 条…"}`。
4. `_gate_error()` 统一生成可归因失败返回，三端点（`/send`、`/send_by_uid`、
   `/send_image`）共用。
5. 前端：`SendDmResp` / `sendDm` / `sendImage` 补 `msg`/`reason_code` 字段；
   两处失败提示改为 `r.msg || r.error`（可读原因取代裸 `rate_limited`）。
