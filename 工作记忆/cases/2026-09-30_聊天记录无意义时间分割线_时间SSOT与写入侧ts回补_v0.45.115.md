# 聊天记录「无意义时间分割线」脏数据

- **日期**：2026-09-30
- **版本**：v0.45.111 → **v0.45.115**（见末节「版本说明」）
- **提交**：`3f2b087`
- **触发**：用户截图反馈「聊天记录当中会经常出现这种无意义的时间脏数据，且这个日期和时间不固定」

## 一、症状与用户原话

截图红框内，右侧会话详情区出现两条分割线，且**下方没有任何消息气泡**：

```
───────── 00:45 ─────────
───────── 2026-09-16 ─────
```

用户强调的关键判据：**「日期和时间不固定」** —— 这一条是定位根因的钥匙
（见 §三「为什么'不固定'是决定性线索」）。

## 二、设计意图（Step 1：回归设计契约）

`messages-page.tsx:967` 注释明示契约：

> `mt 格式 YYYY-MM-DD HH:MM:SS` —— `slice(0,10)` 取日期做分割线，
> `slice(11,16)` 取时分显示在消息右侧。

后端 `api/messages._fmt_ts` 亦声明返回完整 ISO 时间。
⇒ **契约是「定长 19 的完整时间串」**，任何不符此形状的值都不应被当成时间。

## 三、链路溯源（Step 3）

### 3.1 决定性线索：为什么"不固定"

`mt` 若来自真实消息，同一会话的日期/时分**不可能每次刷新都变**。
唯一能解释"漂移"的是：该值**在渲染时现算**。

仓库里唯一"现算当前时刻"的函数是 `components/ui.tsx:25` 的 `nowHM()`：

```ts
export function nowHM(): string {          // 返回 "HH:MM" —— 没有日期！
  const d = new Date();
  return p(d.getHours()) + ":" + p(d.getMinutes());
}
```

而 `messages-page.tsx` 两处这样用它：

```ts
mt: m.time || nowHM(),                     // ← 兜底
```

⇒ 当 `m.time` 为空 ⇒ `mt = "01:01"`（无日期）⇒ `slice(0,10)` 把整条
`"01:01"` 当成日期 ⇒ 渲染出无意义分割线；且每次渲染重算 ⇒ **漂移**。

**实测复现**（探针跑真实后端 `_fmt_ts`）：

| 输入 | 后端 time | 前端 mt | `slice(0,10)` 分割线 |
|---|---|---|---|
| ts=1694832000.0 | `2023-09-16 10:40:00` | 同左 | `2023-09-16` ✅ |
| **ts=0** | `""` | **`01:01`** | **`01:01`** ❌ |
| **ts=None** | `""` | **`01:01`** | **`01:01`** ❌ |

### 3.2 上游真因：ts 为什么是空

`api/messages._fmt_ts` 对 falsy ts 返回 `""`（这一侧是对的）。
空值的来源在**写入侧**——4 处把缺失时间落库为 `0`：

| 位置 | 写法 |
|---|---|
| `daemon/recv_daemon.py:1257` | `rec._tuple(..., ts=ts or 0, ...)` |
| `daemon/recv_daemon.py` `_msg_tuple` | `ts=m.get("ts", 0)` |
| `auto_dm/conversation_capture.py:2027,2040` | `ts=m.get("ts") or 0` |

而 `ts=0` 本身**永远不会被报错** —— 它就是"看起来合法"的假值。

### 3.3 同族副本（修类不修点）

全仓排查发现**同一件事有三份实现、三种格式**：

| 位置 | 格式 | ts 缺失时 |
|---|---|---|
| `api/messages._fmt_ts` | `%Y-%m-%d %H:%M:%S` | `""` ✅ |
| `services/chat_render._fmt_ts` | `%Y-%m-%d %H:%M`（无秒） | **`1970-01-01 08:00`** ❌ |
| `services/chat_render_png` | 复用上者 + 裸切片 | **`1970-01-01`** ❌ |

实测证实：导出链路会把 ts=0 渲染成「1970 年」的日期分割线 ——
与前端那条是**同族缺陷**（缺失时返回具体值而非零信息），只是形态不同。

## 四、根因（RCA）

**一条判据同时违反了两条已被项目明文记录的规则：**

1. **「兜底不得返回貌似合理的具体值」**（`debug-first-methodology`）
   —— `nowHM()` 返回当前时刻、导出链路返回 1970-01-01，都是把
   "我不知道"伪装成"我知道"，一箭双雕：下游看到有值、更强的判据永不接管。

2. **「零信息降级」** —— 正确降级是空串（不显示），不是造一个值。

**为什么长期未被发现**：两种假值在 UI 上都表现为"正常显示了一行时间"，
无异常、无日志。只有用户肉眼发现"日期不对"才暴露。

## 五、修复

### 5.1 建立时间格式 SSOT（单一真源）

| 层 | 文件 | 内容 |
|---|---|---|
| 后端 | `backend/services/message_time.py` **（新增）** | `fmt_mt` / `mt_date` / `mt_time` / `is_valid_mt` |
| 前端 | `message-shared.tsx` | `isValidMt` / `mtDate` / `mtTime`（同判据） |

契约：`mt` 定长 19；**不合契约 ⇒ 空串**（日期空 ⇒ 不插线；时分空 ⇒ 不显示）。

### 5.2 收敛三条链路（消除同族副本）

- `api/messages._fmt_ts` → 委托 `fmt_mt`
- `services/chat_render._fmt_ts` → 委托 `fmt_mt`（格式从无秒改为带秒，统一口径）
- `services/chat_render_png` / `chat_render` 的裸切片 `[:10]`/`[11:16]` → `mt_date`/`mt_time`

### 5.3 移除根因

- 前端两处 `mt: m.time || ""`（删掉 `nowHM()` 兜底）；`nowHM` 的 import 一并移除
- 会话列表末条时间从"整条 mt"改为 `mtTime(...)`

### 5.4 写入侧根治：`resolve_message_ts`

在**唯一出口** `MessageRecord.tuple()` 集中处理，4 个写入点自动受益：

```
1. ts 有效（>0 且非 NaN）        ⇒ 直接用
2. 否则取 extra.created_at_us     ⇒ 真实服务端时间（微秒→秒）
3. 都没有                         ⇒ 返回 0，**不用 time.time() 兜底**
```

选 `created_at_us` 的依据：它是 protobuf f4 的**服务端单调微秒序号**，
本就由该链路写入 `extra`，此前只用于排序、未被用于补 ts —— 是**已有的真实数据**，
不是编造值。
