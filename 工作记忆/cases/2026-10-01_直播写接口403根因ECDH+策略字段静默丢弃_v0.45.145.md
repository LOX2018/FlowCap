## 一、缺陷 1：直播策略的 9 个自动化字段**保存即丢失**

### 现象（用户报告）
「直播策略里面对弹幕文案和点赞的配置点击保存之后前端渲染依旧没有保存」

### 设计意图（Design Contract）
- `POST /api/live/config-tags` 的契约：按 id upsert，传什么存什么。
- 前置条件：`StrategyBody`（Pydantic）声明的字段即可持久化。
- 后置条件：保存成功后 `GET /api/live/config-tags/{id}` 能回读到同样内容。

### 观测偏差（决定性对照实验，**绕过前端直接打后端**）

```python
POST /api/live/config-tags  （含 9 个自动化字段）
→ HTTP 200, {"ok": True, "config": {...}}
→ 返回 config 的键: ['id', 'name', 'updated_at']        # ← 只有 3 个
🔴 被丢弃: danmaku_pool / danmaku_timer_enabled / danmaku_timer_min /
          danmaku_timer_max / like_batch_enabled / like_batch_total /
          like_batch_steps / like_batch_step_max / like_batch_cooldown_sec

GET /api/live/config-tags/{id}
→ danmaku_pool = ❌ 不存在（其余 8 个同）
```

**判定：后端丢弃，不是前端渲染。** 前端 `RoomConfigPage.save()` 走的是同一个
`api.saveRoomConfig()`，无本地态覆盖（已 grep 确认）。

### 根因（Execution Chain）
```
StrategyBody（Pydantic，9 字段已声明）          ← 校验通过 ⇒ 返回 ok=True（假成功）
      ↓
save_strategy()  api/live_config.py:214
      ↓
for k in ("max_target","interval","delay",      ← ★ 白名单只有 7 个旧字段
          "dm_pool","acct","auto_link_mic","link_mic_mode"):
      ↓
upd[k] = v                                       ← 9 个新字段从未进入 upd
      ↓
_save_all(data)                                  ← 落库时已被丢弃
```
**性质：声明与落库两处不一致 ⇒ 静默数据丢失，且对调用方谎报成功。**

### 修复
`api/live_config.py` 白名单补 9 个字段（`git diff`：5 增 1 删，无 EOL 污染）。

### ⚠️ 关键教训（可迁移判据）
**「Pydantic 模型声明了字段」≠「该字段会被持久化」。**
凡「新增配置字段」，必须同时检查三处：
1. Pydantic/模型声明；
2. **写入白名单 / 序列化循环**（本例的漏网点）；
3. 回读验证（`GET` 回读，不能只信 POST 的 `ok=True`）。
⇒ 判据：**保存后必须回读**，`ok=True` 不是落库证明。

## 二、缺陷 2：弹幕/点赞写接口 **HTTP 403**

### 现象（用户真机日志，`C:\temp\dyautodm_design\logs\run_20261001_021024.log:111`）
```
02:50:56 [LIVE-002] [danmaku] 发送异常 account=尚进工伤小助理
         room=7691351186244258594:
         接口返回空响应（HTTP 403），通常是签名参数不对或被风控拦截。
         logid=20261001025056F331362C4705A53BCBE8
```

**⚠️ 关键观察：报错形态已变。**
v0.45.143 修的是 `Empty string does not encode a sequence`（弱载入器 / ticket 守卫）。
本轮是 **403**，说明**上一轮确实修好了**，问题推进到了下一层。

### 排除过程（决定性对照实验，**不是推断**）

| 检查项 | 实测读数 | 结论 |
|---|---|---|
| cookie 键数 | 78 | ✅ |
| sessionid / ttwid / UIFID / odin_tt | 均有 | ✅ |
| 私钥含**真实换行** | True（非字面 `\n`） | ✅ |
| ticket | 49B，形如 `hash.mgTYBN0...==` | ✅ |
| ts_sign | 133B，`ts.2.` 前缀 | ✅ |
| client_cert | 92B，**`pub.` 新版证书** | ✅ |
| `generate_bd_ticket_client_data` 本地生成 | 成功，424B | ✅ |
| web_rid→room_id 归一化 | `218293658526` → `7691351186244258594` | ✅ |
| **只读 `get_live_info`（同账号同刻）** | **成功** `room_status=2` | ✅ |

⇒ **只读通、写就 403** ⇒ 不是账号态、不是风控、不是 room_id，是**写接口专属**。

### 根因（Open-Source Provenance：与上游 `cv-cat/DouYin_Spider` 逐行对账）

本项目 `utils/bd_ticket.py` 原仅 **90 行**，**完全缺失 ECDH/HMAC**
（全仓 grep `ecdh` / `derive_ecdh_key` / `fetch_server_cert` / `get_req_sign_hmac`
**零命中**）。

| 项 | 本项目（修前） | 上游 | 后果 |
|---|---|---|---|
| client-data 签名 | **恒 ECDSA**（从不传 ecdh_key） | 传 ecdh_key → **HMAC**，无则回退 ECDSA | 本项目是 `pub.` 新版证书，服务端按 HMAC 校验 |
| base64 | `urlsafe_b64encode`（`-_`） | `b64encode`（标准 `+/`），上游注释明写「浏览器用 btoa()」 | 编码形态不符 |
| 返回值 | 单 str | tuple `(client_data, algo_type)` | 调用方无法感知实际算法 |

**自相矛盾（核心）**：
`builder/header.py:63-64` 已按 `client_cert.startswith('pub.')` 把
`bd-ticket-guard-web-sign-type` 标成 **`'1'`（= hmac）**，
但 client-data 实际是 **ECDSA** 签的。
⇒ **头声明 HMAC、载荷实为 ECDSA** ⇒ 服务端按 HMAC 校验必然 403。

这正是「只读通（`with_bd_readonly` 不走 client-data）、写就 403」的机理。

上游 `builder/header.py:45-53`：
```python
ecdh_key = auth.ecdh_key(aid=aid, origin=origin)
client_data, algo_type = generate_bd_ticket_client_data(
    api, auth.ticket, auth.ts_sign, auth.private_key,
    ecdh_key=ecdh_key, timestamp=timestamp,
    t_trust=1 if trust_cookie else None)
```

### 修复
移植上游能力到 `utils/bd_ticket.py`（90 → 335 行）：
`_pem_body` / `_server_pub_point` / `_hkdf_sha256` / `derive_ecdh_key` /
`get_req_sign_hmac` / `fetch_server_cert` / `GET_CLIENT_CERT_API`；
`generate_bd_ticket_client_data` 改标准 base64 + 支持 `ecdh_key`；
`builder/header.py::with_bd` 用 `algo_type` **驱动** `web-sign-type`
（消除「声明 HMAC / 实际 ECDSA」的矛盾），并让 `origin` **真正生效**。

### ⚠️ 关键教训（可迁移判据）
**「头声明的算法」与「载荷实际使用的算法」必须同源。**
凡「两套算法可回退」的签名体系，**禁止**用「证书形态」去**猜**算法，
必须由**实际签名函数返回值**驱动声明头。
另外：`with_bd(origin=...)` 这类**收了参数却不使用**的签名是**伪装成能力的空操作**，
本轮才暴露——**参数存在 ≠ 功能生效**。
