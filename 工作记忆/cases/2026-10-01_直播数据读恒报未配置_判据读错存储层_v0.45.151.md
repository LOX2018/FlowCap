# 直播数据读恒报「未配置」—— 判据读错存储层（v0.45.151）

> 类型: **判定缺陷根治**（非凭证问题）　日期: 2026-10-01　版本: **v0.45.151**
> 关联: 知识库 `06_凭证与签名.md` §「2026-10-01 续·根治」

---

## 一、用户原话（本案例的起点）

> 「我通过抖音首页和抖音私信页，将凭证已经更新了，目前 WP 引擎和实体引擎都正常，
> 但是凭证校验依旧显示**直播数据读(弹幕/礼物/贡献榜) 未配置**这到底需要什么凭证？该如何获取」

用户已经**重扫过凭证**（按界面暗示做的），问题依旧 ⇒ 说明界面在**误导**。

## 二、决定性实证：**不需要任何额外凭证**

用 `live_id=live_room_ref()` 对两账号**真探测**（`force=True`）：

| 账号 | static | session | identity | im_write | live_read |
|---|---|---|---|---|---|
| 尚进工伤小助理 | ok | ok | ok | ok | **ok（贡献榜 1 条）** |
| 四川工伤张老师 | ok | ok | ok | ok | **ok（贡献榜 1 条）** |

三项用途（弹幕昵称解密 / 私信发送 / 直播数据读）**全部「可用」**。

> 附带发现：**尚进此前的「账号级只读态」已被用户重扫解除** —— `im_write` 由 `fail` 转 `ok`
> （`cmd 609` 建会话被接受）。即台账 H-11 / H-15 可按实机证据标注为「已由用户重扫解除」。

## 三、根因：两套存储没同步，判据读了**空的那一套**

| 存储 | 值 | 谁在写 |
|---|---|---|
| `kv config.live_url`（**用户配的**，持久） | `https://www.douyin.com/jingxuan/search/工伤?live_web_rid=697879973787` | 策略保存 / 目标直播间 |
| `settings.live_url`（**判据读的**，运行时） | **`''`** ← 空 | `api/live.py:505` 只在会话内写 |

判定链（`auto_dm/accounts.py`）：

```
_live_read 面 ──► _rid = live_id 参数  ──(空)──► settings.live_url ──(空)──► "unset"
                       ▲
                       └── api/accounts.py:1186 调用时**根本没传** ⇒ 必然走 unset
```

且该分支是**零网络跳过** —— 连问都没去问抖音，直接判「未配置」。

**复现（修复前实测，自相矛盾一眼可见）**：
```
复现条件：settings.live_url = '' | 调用方不传 live_id
用途结论: {'danmaku_decrypt': '可用', 'im_write': '可用', 'live_read': '未配置'}
```

### 为什么这是**高危**缺陷（不只是显示错）

1. **二阶危害**：所有面板都通，界面却报「未配置」⇒ 用户被驱动去**重扫凭证**；
   而重扫触碰 **passport 验证 = 最强风控信号**。
2. **自相矛盾**：同一份 cookie 能解密弹幕、能建会话发送，唯独"直播数据读"判未配置 ——
   任何有经验的用户都该起疑，但普通用户会照做（去重扫）。
3. **恰好违背设计初衷**：能力矩阵 2026-10-01 立项的**唯一理由**就是「根治无效重扫」，
   结果它自己制造了一次无效重扫的驱动。

## 四、修法（两条**同族**缺陷，一次修完）

| # | 位置 | 修法 |
|---|---|---|
| ① | `backend/auto_dm/accounts.py` | 新增 **`live_room_ref(live_id="")` = 生效直播间唯一真源**。<br>优先级：**显式入参 > `kv config.live_id/live_url` > `settings.live_id/live_url`**。<br>支持三种形态：搜索页 `?live_web_rid=<数字>`（**用户实际配的是这种**）、直播间页 `live.douyin.com/<数字>`、裸数字。 |
| ② | `backend/api/accounts.py` | check 端点**显式传** `live_id=live_room_ref()`（不再依赖那个空的 `settings.live_url`）。 |

**为什么要解析搜索页形态**：`api/live_config.py::resolve_live_url` 只认
`live.douyin.com/<数字>`，而用户在「目标直播间」用的是**精选搜索页 URL**
（`…?live_web_rid=697879973787`）⇒ 光复用它仍会漏。实测该正则**一次命中**。

**配套（防再次误导用户）**：

| 项 | 修前 | 修后 |
|---|---|---|
| 用途 `state_label` | `未配置`（模糊） | **`未配置直播间`**（指明缺什么） |
| 该面 `hint` | 「配置直播间后自动覆盖此面」 | 加 **「**不是凭证问题**」** 前缀 |
| `actions` | 无 unset 专属条目 | 新增：**「…**这不是凭证问题，勿因此重扫**」** |
| 前端 | 只显示 `state_label` | `unset` 时把该面 `detail` 作为副标题显示 |

## 六、我自己的缺陷（诚实标注）

1. **M6 门禁首版假设错了**：我写了 `assertEqual(live_room_ref(""), "")`，
   但函数在**无入参**时会回退到 kv —— 而 kv **确实有值**，于是返回 `'697879973787'`。
   ⇒ **是我的测试假设错，不是实现错**。已改为「清空 kv/settings 后再验纯形态解析」。
   *（教训：测「回退优先级」时，必须先控制被测的回退源，否则测的其实是环境。）*
2. **负控打桩过宽**：第一次把 `get_kv_json` 整个打桩成空 ⇒ 连带把**账号查找**也打挂，
   `capability_matrix` 提前返回「账号不存在」，出现 `IndexError`。
   ⇒ 改为**只清 `config` 键**（其余照常）。
