## 一、任务与设计意图

**设计意图（来自 `02_效果定义与探针.md`）**：本项目是**对抗性爬虫**，失败是常态，
判定成败只能看「当前能否真实达成业务效果」（D1）。而 M1 能力探针实测 **0 个** ——
这是 2026-09-14「全解除」改动后**无人敢回退**的真实原因（无探针 → 无法验证业务效果是否还在）。

**本案例目标**：落地首批能力探针，且**判据必须可证伪**（人为制造失效，探针须先于用户报出）。

**契约（预置）**：
- 三态（healthy / degraded / failed / unknown），**禁止二态**；
- 报 `healthy` 时 `evidence` 不得为空；
- 探针**只读本地事实**（SQLite + 本项目日志），零网络、零浏览器（风控红线）；
- 输出覆盖率 + 置信度 + **基线差值（M7）**。

## 四、本案例的核心发现（3 条，全部来自实测）

### 4.1 🔴 探针假健康：「库内历史比例」会掩盖「最近一次已失效」

**实测**（2026-09-21 22:24，尚进工伤小助理）：
- 最近一次捕获日志：`写库完成：会话 44，昵称命中 uid关联=0 sec_uid关联=0 未命中=44/44`
  ⇒ **本次链路关联完全失败**；
- 同期库内：`nickname_ratio = 0.9775`（历史快照仍是好的）。

若探针只看库内比例 → 报 `healthy`，把已失效的链路伪装成健康。**首版即踩此坑**
（`verify_probe_api` 实测输出 `conversation_capture@尚进 = healthy`，与日志矛盾）。

**修正判据**：`有效关联率 = min(库内历史比例, 最近一次捕获自身关联率)`；
`< 失败线 → failed`，介于两线 → degraded，`≥ 健康线` 才 healthy。
修正后同一份数据立即正确报 `failed`（有效关联率 0.0，并触发不降级性告警 −0.9775）。

**通则（可迁移）**：**读快照型的健康探针都有此失效模式** ——
「快照停在一个好状态」与「链路此刻仍好」是两件事。关联率/覆盖率类探针必须
额外读取**最近一次运行的自身指标**，并取 min。

### 4.2 🔴 首次发现「M1 完全缺失」导致的隐性代价可被量化

探针落地当天即报出**尚进昵称关联归零**这一真实劣化 ——
而该现象此前只能靠人逐行读 `recv_daemon_*.log` 发现（本项目历史上正是这样漏掉过 14/44）。
判据：`conversation_capture = failed` 且 `reason` 明写「不得用库内历史比例冒充健康」。

### 4.3 🟡 本项目要求 **Python 3.14**，而终端默认 `python` 是 3.11（环境坑）

- 证据：部署产物含 `_internal/_*.cp314-win_amd64.pyd`；源码 `auto_dm/__pycache__/accounts.cpython-314.pyc`。
- **我因此误判了一次**：用 3.11 导入 `auto_dm/accounts.py` 报
  `NameError: name 'Dict' is not defined`（该文件用了 PEP 649 的延迟注解，3.14 才容忍），
  我据此**推断出「预存致命缺陷」——该推断是错的**，已撤回。
- **规则**：本项目的 `python` 一律显式用
  `%LOCALAPPDATA%\Programs\Python\Python314\python.exe`；
  **在 3.11 下得出的任何 ImportError/NameError 结论都不可信**（会污染根因判断）。

## 五、自伤事故与止损（必须留痕）

### 5.1 行尾符事故（LF→CRLF 整文件改写）

- **现象**：一次 `patch` 之后，`git diff --stat` 显示 `errcode_data.py` **1051 插入 / 1034 删除**
  （本意仅 +17 行）。判据：`git diff --ignore-cr-at-eol --stat` 显示真实改动只有 **+18/−1**。
- **根因**：`patch` 工具在 LF 文件上补行时**整体重写了行尾**（HEAD 该文件 105 ALF 行 + 1034 CRLF 行混合）。
- **止损**：以 `git show HEAD:<file>` 的**原始字节**为基准，按其原生行尾插入新内容后回写；
  复核 `git diff --stat` 归零为「17 insertions, 0 deletions」。**未丢失任何内容**
  （去空白字符数 61285 → 61890，差额 = 新增段）。
- **铁律**：**改动行数远超本意的 diff 必须停下来查**（可能是行尾/编码级联改写）；
  验证工具 = `git diff --ignore-cr-at-eol`。**禁止**在这种情况下继续下一步写操作。

### 5.2 验证脚本误启守护（真实副作用，已消除）

- **现象**：为实测 `GET /api/probe/run` 起了一个 backend（`uvicorn`，端口 18080）。
  `main.py` 的 lifespan **自动 spawn 了 recv_daemon + browser_daemon(BCC/Camoufox)**，
  并对两账号各跑了一次真实捕获（22:24:19–22:24:35，含对外请求）。
- **证据**：`recv_daemon_20260921.log` 22:24 段、`browser_daemon_20260921.log` 22:24 段。
- **消除**：`taskkill /T` 收尾 → 复核**无残留进程**（含 camoufox/firefox）、**端口全释放**。
  副产物：两账号各多一条 22:24 捕获记录（DB 未劣化；尚进那次 `uid关联=0` 成为 §4.1 的实测样本）。
- **铁律**：**验证「只读端点」不要起整个应用**。
  - 进程内直调（bypass 中间件）即可验探针输出；
  - 路由注册查 `/openapi.json` 即可（401 也算已注册）；
  - 确需 HTTP 验证时，必须预估 lifespan 副作用（本项目 lifespan 会拉守护）。
  - 这与 `ENG-018` 卡记录的教训同族：「不要从后台会话启动用户的应用」。
