# 案例：上游追踪机制整体失效 —— 代理写法致 GitHub 恒定 400（v0.43.73）

> 类型：工具链缺陷（非业务）｜发现日：2026-09-17｜修复版：v0.43.73
> 触发场景：按用户指令核查 `TeamBreakerr/douyin-chat-export` v2.0.0 更新，
> 例行「排查前先跑上游追踪」时，脚本对**所有**源项目恒报失败。

---

## 一、六步闭环（对照用户调试方法论）

### 步骤 1｜回归设计意图

| 项 | 内容 |
|---|---|
| 模块 | `DYAutoDM_v2/scripts/track_upstream.py`（源项目追踪） |
| 设计契约 | 读 `docs/upstream_sources.json` 清单 → 逐项查 GitHub API 的 `pushed_at` + `head_sha` → 与 `docs/upstream_baseline.json` 比较 → 输出「有更新 / 无变化」。**只读写 docs/ 下两个 JSON，不碰业务代码**（脚本 docstring 明示）。 |
| 预期行为 | 11 个项目逐项给出状态；首次运行 → 🆕新建基线；`--update` 落基线；此后同状态 → ✅无变化 |
| 设计假设 | GitHub API 可达（直连或经 `DY_UPSTREAM_PROXY` / 自动探测的本地代理）；HTTP 非 2xx ⇒ 仓库层问题 |

### 步骤 2｜定义当前状态

- 观测：`python scripts/track_upstream.py --only douyin_chat_export` →
  `[⚠️ 失败] HTTP 400（仓库不存在/改名）`
- 期望：`🆕 新建基线`（基线为空）或 `🔔 有更新`
- 偏差：`deviation_type = data`（错误判据），`deviation_point = _get() 的代理分支`

### 步骤 3｜追踪执行链

```
main() 逐项目 → _get("https://api.github.com/repos/<repo>")
   → _pick_proxy(): DY_UPSTREAM_PROXY 未设 → 探测 PROXY_PORTS
        10808 OPEN（本机常开）→ proxy = "http://127.0.0.1:10808"
   → req.set_proxy(proxy, "http")          ← ★断点
   → build_opener(ProxyHandler({...}), HTTPSHandler(CTX)).open(req)
   → GitHub 前置 CDN 回 HTTP 400 "Bad request"（HTML，非 API JSON）
   → except HTTPError: e.code != 403 → 落入 else 分支
        reason = "HTTP 400（仓库不存在/改名）"   ← 误判，把网络层说成仓库层
```

### 步骤 4｜根因分析（RCA）

**为什么链在此断** —— 不是 GitHub 不通，而是**请求被自己改坏了**：

`Request.set_proxy(host, "http")` 把 URL 改写成绝对形式交给 http 代理
（`selector` 变成 `http://127.0.0.1:10808/https://api.github.com/...`），
而 `ProxyHandler` 同时生效，GitHub 前置 CDN 把这种畸形请求判为
`Bad request` → 400。

**关键对照实验**（同 URL、同请求头，仅改代理写法）：

| # | `req.set_proxy` | `ProxyHandler` | `/repos` |
|---|---|---|---|
| ① 现行 | ✅ | ✅ | **400** |
| ② 修复 | ❌ | ✅ | **200** |
| ③ 对照 | ✅ | ❌ | **400** |

⇒ 归因到 `set_proxy` 单行；`ProxyHandler` 本身工作正常（正是它让 ② 走通代理）。

**放大为「整体失效」的机理**：
`_pick_proxy()` 顺序是 `DY_UPSTREAM_PROXY` → 端口探测，而 10808 在本机常开
（实测 OPEN）⇒ **auto-probe 必命中** ⇒ 无需任何环境变量，11 个项目全部 400。
基线文件因此**从未落过 sha**，恒为 `{"projects": {}}`，`prev` 永远为空
⇒ 即使请求成功也只会报 🆕，**永远判不出「有更新」**。

**为何长期未被发现（三层都「看着对」）**：
- 脚本无 `--only` 时输出量大，失败被淹没；
- 报错文案「仓库不存在/改名」把注意力引向**清单地址**（而清单地址是对的）；
- 09-14 首次运行恰好用 `--only` 跑过、且当时确有 3 处地址错误被修正，
  「修好 3 个 404」的成功叙事掩盖了「其余项其实也全 400」。

### 步骤 5｜实机验证

- 单项目：`--only douyin_chat_export --commits 3` → 🆕 新建基线，
  读到 `pushed_at 2026-09-17T08:24`、`head_sha 2b3ed23ac4`、3 条提交 ✅
- 全量：`--update` → 10/11 成功（第 11 项撞 GitHub 匿名限流 60/h，属预期），失败 0
- 基线：由 `{"projects": {}}` → 落 `pushed_at` + `head_sha` ✅
- 幂等：复跑 → `✅ 无变化`（证明「有更新」判定链路真正接通）✅

### 步骤 6｜版本与归档

- 版本：v0.43.72 → **v0.43.73**（patch +0.01，六处齐平，门禁 exit 0）
- 归档：本文件 + `2026-09-17_上游v2.0.0增量接入.md`

## 二、修复内容

| # | 位置 | 改动 |
|---|---|---|
| 1 | `_get()` 代理分支 | **删除 `req.set_proxy(proxy, "http")`**，只保留 `ProxyHandler`；写明对照实验数据，防后人「优化」回去 |
| 2 | `main()` HTTPError 分支 | 400 等**非 404** 不再报「仓库不存在」；拆出 404 专述、其余带响应体摘要（「非 404：多为网络/代理层问题」） |
| 3 | `docs/upstream_baseline.json` | 首次成功落基线 |

## 三、教训（可复用）

1. **「修复成功」不等于「机制可用」**：09-14 那轮修好了 3 个 404，
   但**没有任何一次成功写入 sha** —— 验收标准应是「基线里出现了 sha」，
   而不是「脚本跑完没报错」。
2. **失败文案会把排查带偏**：把 400 一律写成「仓库不存在/改名」，
   等于在代码里内置了一个错误假设。错误分类必须**先按 HTTP 语义分层**
   （网络层 / 鉴权层 / 仓库层），再给结论。
3. **本机常开的代理是「隐形默认值」**：auto-probe 命中本地代理时，
   脚本行为与「直连」完全不同。凡带代理分支的脚本，**代理路径与直连路径
   必须各跑一次**才算验证（本次即直连 200、代理旧写法 400）。
4. **改 URL 的工具函数要单变量对照**：`set_proxy` + `ProxyHandler` 双写是
   常见轮子，容易相互破坏。判据要能区分「代理不可用」与「请求被写坏」。
