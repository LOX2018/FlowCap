## 二、用户指出的语义歧义（本案例的起因，用户原话要点）

> 「如果凭证有效，快速杀（有头）…应该是应对于**引擎校验**这个入口…
> 但是**双击打开浏览器**应该是用户作为**观测者**来使用该 profile 浏览器，
> 核心目的并不一定是为了更新凭证…
> 引擎校验入口打开的有头浏览器在凭证有效快速写回后可以杀死有头转成无头，
> 但双击打开浏览器可以监测凭证的更新状态，并自动写回，
> 但**不可自动杀死有头浏览器的用户手动操作**，然后再执行转无头的流程。」

## 三、设计意图回归（Step 1）

项目**早有该契约**（`api/accounts.py:632`）：

> ① 凭证有效 + 有任务在跑 → **禁止**打开有头浏览器
>    （**有头是观测态，不是运行态**）
> ② 凭证失效 → 允许并引导：用户双击打开有头浏览器作为**观测态**

**契约正确，但实现未收口**：只在「打开前」做了门禁，
**打开后没有任何状态标记** ⇒ 自愈/探活路径无从区分发起方。

## 四、当前状态与偏差（Step 2）

| 项 | 期望 | 实际（修复前） |
|---|---|---|
| `/show` 返回 `ok:True` | = 可见性**已达成** | = **请求已受理**（异步） |
| 用户双击打开的窗口 | 不被自动关闭 | 无任何保护机制 |
| 发起方语义 | 显式可区分 | **无字段区分** |

实测事故：用户双击 → 弹窗「已显示该账号浏览器窗口」
→ 屏幕无窗口 → 日志实为 `BCC-058` 重建失败。

## 五、执行链追踪与 RCA（Step 3-4）

```
用户双击 → /open-browser → POST /show {"visible": true}
                                        ↑ 无 intent 字段
   → set_visible() → 关旧 context → 后台 _do_switch_background
   → 【立即返回 ok:True + "窗口就绪后自动完成"】   ← 假阳性在此
   → 后台重建失败 → BCC-006/BCC-058 只写日志，前端无从得知
```

**Root Cause A（假阳性）**：把「受理」当作「达成」返回，违反 DbC 的
post-condition 定义 —— `ok:True` 的语义未自证其然。

**Root Cause B（语义歧义）**：契约未收口到状态。项目已有"观测态"概念
（代码中 8 处提及），但仅用于日志文案，**未形成可判定的状态位**。

## 六、修复（两处，契约层）

### 修复 A · 假阳性根治
`/show` 返回新增真值位：
- `accepted=True` 受理态
- `settled=False` 可见性**尚未达成**
- `switching=True` 仍在切换
- `msg` 删除一切"已显示/已完成/就绪后自动完成"字样

`/open-browser` 据 `settled` 如实表述，不再宣称"已显示"。

### 修复 B · 观测态契约收口
- `set_visible(visible, url, intent)`，`intent ∈ {observe, verify}`
- `intent=observe` → `_observe_mode=True`
- 探活路径（`browser_daemon._ensure_alive`）观测态下**不重建/不关闭**，
  报 **BCC-080**，凭证仍照常观测回写（不中断）
- `/open-browser` 显式传 `intent=observe`
- 未知 intent → **BCC-079** 并按 `verify` 处理（保守：不擅自保护自动路径）
