# 私信链路根因分析（源项目 cv-cat/DouYin_Spider 2026 最新版 vs 本项目）

**日期**：2026-09-19
**源项目版本**：cv-cat/DouYin_Spider @ master `1712dad`（pushed_at 2026-09-19T10:33Z）
**本地对照**：_ext_repos/DouYin_Spider_git（最新）vs DYAutoDM_v2/backend

## 结论（一句话）
本项目 `builder/proto.py` 的 `build_normal_request` 仍用 **2025 旧 web_protect 信封**，
而抖音 PC IM 已在 **2026 rollout 切换到 bd-ticket-guard 头鉴权的新信封**。
旧信封被抖音判非法 → `create_conversation`（cmd 609）第一步即返回 **INVALID_REQUEST**
→ 所有私信发送（手动 + AI 自动回复）全部失败。

## 第二处缺口：HTTP 头鉴权（builder/header.py）

源项目 2026 版 send 路径新增：
1. `headers.with_bd('/v1/message/send', auth)` —— bd-ticket-guard 客户端数据头
   （`bd-ticket-guard-client-data` / `ree-public-key` / `version` / `web-version` / `web-sign-type` + `x-tt-session-dtrait`）
   - 依赖 `auth.ticket_matches_session()` 强校验（cookie 与 DY_TS_SIGN 必须同源登录）
2. `DouyinAPI.get_identity_security_token(auth)` —— **2026 PC IM send 前置**：
   - 调 `/passport/safe/get_identity_security_token/`（scene=web_im, aid=6383）
   - 返回 `identity_security_token` + `device_id`，塞入 protobuf header map：
     - `request.headers['identity_security_token'] = json.dumps({'token': token})`
     - `request.headers['identity_security_device_id'] = device_id`
   - 注释："tied to the current ticket/dtrait session, so never synthesize it or carry it across Auth instances."
3. send 的 params 顺序：`msToken` → `a_bogus`(host=www.douyin.com) → `verifyFp` → `fp`

本项目 `client_im.create_conversation/send_msg`：
- **无 with_bd**（其注释明写"不叠加 bd-ticket-guard-* 头（叠加反而 INVALID_REQUEST）"——**2026 前旧结论，现已反转**）
- **无 identity_security_token/device_id**
- 保留了 body 内 `reuqest_sign`（源项目新信封注释：`current send envelope has no top-level reuqest_sign`，**但 create 仍保留 reuqest_sign**）

## 第三处缺陷：my_uid 不可确定（并发症状，非首位根因）

生产日志：
```
[CAP-013] [capture][四川工伤张老师] 存量污染订正失败: 本号 uid 无法确定，跳过存量订正
[AUTH-050] [uid-probe] 「四川工伤张老师」探活 uid=1149448411428128 与历史会话不一致 → 不缓存
```
数据：两账号的本号 uid **同时占据 conv_id 的 idx2 与 idx3**
- 张老师 `3887506227210423`：idx2×20 + idx3×260
- 小助理 `316276709526638`：idx2×52 + idx3×32

而 `infer_my_uid_from_conv_ids` 判据要求"位置稳定（只出现在 idx=2 或 idx=3 之一）"→ **判据不满足 → my_uid=""**
→ `peer_uid(conv_id, my="")` 退化为"返回 b"（弱保证）→ 对张老师解析 peer = 自己 → `create_conversation(auth, 自己uid)` → 必然 INVALID_REQUEST（叠加症状）。

另一独立缺陷：生产打包 `_internal` **缺 qrcode 模块** → `uid_probe.get_uid` 探活异常 `No module named 'qrcode'` → my_uid 无回退来源。
（`backend/requirements.txt:21 qrcode>=7.4.2` 已声明，但打包未含。）

## 修复设计原则

**必须整体对齐源项目 2026 协议**，禁止局部打补丁：
1. `build_normal_request` 全面对齐 2026 信封（空 token / 无 ts_sign / 无 sdk_cert / 新 sdk_version+build_number+version_code / 新 headers）。
2. `client_im` imapi 请求补 `with_bd` 头；send 补 `get_identity_security_token` 并写入 protobuf header map。
3. 修 `infer_my_uid_from_conv_ids` 判据：本号 uid 在 idx2/idx3 合计占比最高即判定（不再要求"只在单一位置"）；保留 AUTH-050 门禁。
4. 打包补 qrcode（否则探活回退不可用）。
5. 版本递增 0.43.96 → 0.43.97-debug.1，重新打包，实机验证 AI 回复真落 role=me。
