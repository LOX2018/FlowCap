## 二、缺陷一：弹幕/点赞写接口「异常」—— 两个独立根因

### 取证（**用用户真实操作的日志**，不推断）

部署根 `logs/run_20261001_011001.log`：
```
01:48:18 [LIVE-002] [danmaku] 发送异常 account=尚进工伤小助理 room=7691345987004009258: Empty string does not encode a sequence
01:48:44 [LIVE-042] [like]    发送异常 account=尚进工伤小助理 room=7691345987004009258: Empty string does not encode a sequence
```

### 根因① 弱载入器（`api/live.py::_auth_for`）

调的是 `utils.common_util.load_env`，与项目标准载入器 `DYLoginApi._load_auth_from_env`
有**两处致命差异**（实测）：

| 项 | `common_util.load_env`（弱） | `DYLoginApi._load_auth_from_env`（标准） |
|---|---|---|
| 签名还原 | `perepare_auth(cookies, "", "")` ← **空 web_protect/keys** | `perepare_auth(cookies, web_protect, keys)` |
| 私钥形态 | `_src['DY_PRIVATE_KEY']` **原样** | `_decode_private_key(...)` **还原换行** |

实测 `load_env` 返回的 `private_key`「含字面量 `\n`、无真实换行」⇒ `SigningKey.from_pem`
抛 `Empty string does not encode a sequence`。

⇒ **只有写接口**会解析私钥（`with_bd`→`generate_bd_ticket_client_data`），
只读走 `with_bd_readonly` 不碰私钥 ⇒ 这正是「只读正常、写就异常」那一环。

**同族三处（本项目只修过一处）**：`api/platform.py`（2026-09-14 已修）／
`api/live.py`／`api/linkmic.py`（后两者为**残留**）⇒ 一并收敛到唯一真源。

### 根因② bd-ticket 守卫恒误拦

原：`ticket`/`api` 含 `&` **或** `=` 即 raise。
实测真实 `ticket` 是 **base64**（`hash.mgTYBN0DfPL9gfxlJ…==`，**必含 `=`**）⇒ **恒误拦**。
上游 `cv-cat/DouYin_Spider`（master，`dy_apis/douyin_api.py:1903`）**无此校验**。

修法（按**注入可行性**，不是字符黑名单）：`ticket` 只拦 `&`（`=` 是 base64 padding，
落在首个 `=` 之后不产生新键）；`api` 仍拦 `&`/`=`。

**修复后实测**：两账号 `private_key 真实换行=True`、`cookie=78/72`、
`generate_bd_ticket_client_data` 两条路径均 **OK（424 字节）**。

## 三、缺陷二：只有软着陆，没有硬着陆

**取证**：后端**早已两态** —— `POST /api/engine/stop`（`adm.stop(hard=True)` 立即清队列）
/ `POST /api/engine/stop-soft`（`hard=False` 队列发完）；前端 `api.stopEngine()`
（硬）**也已存在**。**但 UI 只挂了 `stopSoftEngine()`**（`live-page.tsx:988`）。

⇒ 不是"没实现"，是**前端没给入口**。补「强制停止」按钮（破坏性操作 ⇒ 二次确认）。

## 四、缺陷三：红心读不到真实点赞

### 实测（同刻同房间 room_id=7691345987004009258）

| 来源 | 结果 |
|---|---|
| WS 文案（日志 `[房间统计] 30在线观众`）| **不含点赞** ⇒ 旧解析恒 0 |
| WS `LikeMessage` | 只在"有人正在点赞"时推事件 ⇒ 无事件时累计恒 0 |
| 直播页 HTML `like_count` | `0`（且在**商品**上下文）|
| **`reflow/info` → `room.like_count`** | **976** ✅ |

⇒ 新增 `link_resolve.fetch_room_stats()`（**匿名**；实测匿名与带凭证同值，
且带凭证在部分账号被该端点拒 101 ⇒ 只读统计不该被账号态拖累）。

**语义（关键）**：`TOTAL = real(历史累计) + ws_delta(此后新增)` —— **相加，非取 max**
（我第一版误写取 max，被自测抓到：976+5 应 981 却得 976）。
**防重复计数**：刷新 real 成功即重置 ws_delta。
**防降级**：绝不把 likes 从 >0 降到 0。

## 五、新能力：定时弹幕 + 分步批量点赞

**架构决策**：`task_scheduler` 是**同步一次性 + 300s 超时**（T-02 已判定不适合长时任务），
而这两项天然是**无限周期**／**长时跨步** ⇒ 新建 `services/live_automation.py`（常驻线程），
由 `LiveChatHook` 随监听生命周期启停（SoC：`live_hook` 管读，该服务管写）。

**两层配置（优先级：策略层 > 设置页）**：策略层（`RoomConfigPage`，逐房间，与 `dm_pool` 同层）
→ `config.live`；设置页 live 分区（`app_config`，全局兜底）。
⚠️ `app_config` schema **不支持 `list`** ⇒ 弹幕文案库**不能**塞 schema（放策略层）。

**速率**：弹幕 3~6 分钟随机；分步点赞 3000÷4 步（单步上限 1000，超出**自动加步**）；
**步间冷却硬下限 120s**。**默认全休眠 ⇒ 不改配置 = 零出站**。

## 六、过程中我自己的缺陷（全已修）

1. **门禁判据用字符串匹配** ⇒ 匹配到 docstring 里的解释文字（W1/W2/W3 全假红）
   ⇒ 改用 **AST 真调用**判定。
2. **`--timeout=600` 参数**：pytest 未装该插件 ⇒ 回归命令直接失败（重新跑）。
3. **`apply: restart_listen`**：我编了第 4 个值，而白名单只有 hot/restart_daemon/restart_backend
   ⇒ 门禁变红。**没有**去放宽白名单（那会变成"说了要做但没人做"的假标签），
   改用 `hot` + hint 如实写明生效时机。
4. **`"type": "list"`**：schema 只支持 5 种类型 ⇒ 弹幕文案库改放策略层。
5. **CRLF 反复**：多处 `patch` 匹配失败 ⇒ 一律改用**按行号的字节级脚本**。
6. **测试污染**：端到端验证把策略写进了**真实库** ⇒ 已清理复原（`config.live` → null，
   复核自动化读回「默认休眠」）。
7. **中文 `\n` 转义**：`window.confirm` 文案里的 `\n` 被逐层吃掉 ⇒ 改成单行纯文本。

## 八、残留（诚实标注）

- **定时弹幕/分步点赞未做真机端到端**（写接口触风控红线，且需"正在开播"的房间 +
  用户显式启用配置）⇒ 本轮只做到「逻辑 + 门禁 + 打桩装配」层面，**真机留待用户开启后验证**。
