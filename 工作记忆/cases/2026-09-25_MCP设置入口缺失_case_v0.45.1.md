# 案例：MCP 设置入口缺失 —— 「能力在位但不可得」（v0.45.1，2026-09-25）

> 性质：**已交付案例**
> 关联台账：H-26（本案例补完其「前端设置页」开放项）
> 关联前案：H-24（WP 通道静默无效）—— **同型病**
> 版本：v0.45.0 → **v0.45.1**（产品行为 patch，D-02）；提交 `70cad4f`

## 1. 用户诉求（原话，两次提出）

第一次（本会话早期）：

> 「既然这个 MCP 已经规划好了功能的分布，那为什么我在前端页面没有看到关于 MCP 的
> 设置入口，导致我一直都不知道，而且他也没有真正的接入到 Hermes 中，造成友好的工具，
> 我不知道，也没有用，反而一直采用非常传统的手动查询」

第二次（本案例直接起因，措辞更具体 —— 指出真实阻塞点）：

> 「正是因为在社这页面当中没有入口，导致我也不知道 mcp 密钥是多少，鉴权根本就无法使用」

**第一次我做了「可发现性」的书面分析，却没有动手补前端** —— 这是本案例最该记的失误。

---

## 2. 先澄清一个容易误判的前提（避免答非所问）

用户把痛点表述为「鉴权根本无法使用」。**实测先行，避免顺着表述答错**：

```
$ printf '...initialize...tools/list...tools/call...' | python -m mcp serve --scope=debug
  initialize -> dyautodm-mcp 2025-03-26
  tools/list -> 7 个工具，零令牌即可访问
  tools/call -> isError=False，返回真实数据 {"state":"degraded","app_version":"0.45.0"...}
```

⇒ **stdio 模式不需要令牌**（进程边界即鉴权），Hermes 接入走的正是这条，**本就可用**。
但用户拿不到令牌的痛点**完全真实** —— 阻塞的是 **本机 HTTP 模式**。

**教训**：用户的表述可能是**合并的**（把「我拿不到密钥」与「MCP 用不了」并成一句）。
必须先分开验证，再分别回答；否则会给出「其实你不用密钥」这种正确但**没解决他问题**的答复。

## 3. 根因（可直接复跑的判据）

| # | 判据 | 结果 |
|---|---|---|
| 1 | `grep -rn "mcp" frontend/src/` | **零引用** |
| 2 | `settings-page.tsx` 的 TABS | **9 个 tab，无 MCP** |
| 3 | `data/mcp_config.json` | **不存在**（从未生成）|
| 4 | 后端端点 | **7 个，本来就完整** |

⇒ **后端完整、前端零引用**：能力「在位但不可得」。用户既不知道有 MCP，
也无从取得 HTTP 模式所需令牌。

## 4. 与 H-24 的同型性（本案例最值钱的部分）

| | H-24（WP 通道） | 本案（MCP 前端） |
|---|---|---|
| 现象 | 代码在跑、实测**零落库** | 端点齐全、前端**零引用** |
| 潜伏 | **5 天** | 自 v0.44.x（2026-09-14 起） |
| 为何无人知晓 | 无报错、无告警、注释声称有双保险 | 无报错、无入口、验收只测后端 |
| 违反的铁律 | Live-Instance Verification（只验代码能跑） | 同左 |

**共同模式**：验收标准只覆盖「**代码能跑**」，未覆盖「**用户能用到**」。
⇒ 新增能力必须同时过 **发现性 / 可达性 / 默认状态** 三关，且写成可复跑判据。

### 设计要点（三条契约）

1. **讲清两种模式的心智模型**（用户痛点的真正解药）—— 卡片顶部**并列**两块：
   · stdio（Hermes/Codex/Claude Code）：**无需令牌**，进程边界即鉴权
   · 本机 HTTP（127.0.0.1）：**需要令牌**，由「显示令牌」取得
   不并列 ⇒ 用户仍会以为整件事被令牌卡住。
2. **默认关闭且关闭态一眼可见**（对齐 `NicknameFallbackSection` 既有范式，
   也是后端 `DEFAULTS.enabled=False` 的语义）。
3. **写操作按需开启**，打开时显式警告「AI 可对真实账号执行写操作」。

### 一个主动修正（不谎报状态）

卡片状态徽章最初读**表单态** —— 用户改开关未保存时，徽章会显示「已启用」
而实际配置仍是关闭。已改为**读已保存态**，并新增「尚未保存」提示行。

### 验证过程中我自己的 3 个脚本 bug（记录以免重犯）

1. 🔴 **路由桩写 `"/api/" in url`** ⇒ 误伤 `/src/api/client.ts` 源码模块 ⇒
   JS 加载失败、**整页空白**。修法：`urlparse(url).path.startswith("/api/")`，
   或直接把桩限定在后端绝对地址 `http://127.0.0.1:8000/**`。
2. **用 `"**" in body` 判「Markdown 泄漏」** ⇒ 脱敏令牌 `AbCd********WxYz`
   自身就含 8 个星号 ⇒ 假失败。修法：匹配 `\*\*[^*\n]+\*\*`。
3. **`inner_text()` 不含 input 的 `value`** ⇒ 明文令牌断言必假失败。
   修法：`input_value()`。

**通则**：验证脚本先自证「能报对」，否则它制造的是**假缺陷**，比不验证更贵。

## 8. 可复用判据（教训）

1. **「代码在位」≠「能力可用」** —— 必须同时过**发现性 / 可达性 / 默认状态**三关
   （H-24 与本案同型，已两次；第三次触发时应考虑做成门禁）。
2. **用户的痛点表述可能是合并的** —— 先拆开逐项验证，再分别回答；
   顺着一句话答容易给「正确但无用」的答复。
3. **说了要做就要做**：第一次只做了书面分析、没补前端，导致用户第二次反馈。
   分析不等于交付。
4. **验证脚本的假失败必须归因**：3 个失败中 3 个是我脚本的 bug。
   先怀疑 matcher，再怀疑被测对象。
