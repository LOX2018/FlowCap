# 2026-09-26_内容板块视频无法播放_受保护流未带令牌401_case_v0.45.9

> 性质: **Postmortem（调试案例归档）**　实测日期: 2026-09-26　状态: 有效
> 涉及模块: 内容板块播放器（`frontend/src/components/player/player-media-stage.tsx`）
> 版本: v0.45.8（故障态）→ v0.45.9（修复）

---

## 一、设计意图（Design Intent）

内容板块点开作品应能**正常播放视频**。

- 设计契约（DbC）：
  - 前置：已登录（持有 `X-Member-Token`）、后端 media/stream-ticket 可取址成功。
  - 后置：`<video>` 能拿到可解码的字节流（HTTP 206 + `video/mp4` + 有效 `ftyp`）。
  - 不变式：**所有 `/api/*` 业务端点（含媒体流）受会员门禁保护**，
    前端取用受保护媒体必须携带令牌（用户 2026-09-17 拍板 B 方案）。
- 预期行为：点开即播，可拖动进度条（Range）。

## 二、观察偏差（Observed Deviation）

内容板块拉取到的视频**依旧无法播放**（用户报告）。

- 偏差类型：data（媒体字节流取不到）
- 偏差点：前端 `<video>` 与后端媒体端点之间的**鉴权环节**
- 偏差描述：用户看到"取址成功但播不了"；实测后端链路 206 可拉。

## 三、错误码（DSSCC 格式）

```
ERR-PLT-MEDIA-401   受保护流裸地址直连        severity=error
```

## 四、RCA（根因，非症状）

### 根因：`<video src>` 无法携带自定义请求头 ⇒ 直连受保护流必然 401

内容板块播放器（方案 B）把后端 `/media/stream-ticket` 返回的**本机受保护地址**
（`/api/platform/media/stream?u=...`）直接塞进 `<video src>`。

而 **`<video src>` / `<img src>` 无法携带自定义请求头**（`X-Member-Token`），
`main.py` 的 `member_auth_middleware` 对 `/api/*` 强制校验该头
（`_MEMBER_EXEMPT` 不含媒体端点）⇒ **裸地址直连必然 401**。

**项目里早已有成熟解法却未被播放器采用**：`useAuthedMediaUrl`
（`frontend/src/lib/authed-media.ts`）——本地 API 地址带令牌 fetch 成 Blob 再交给
`<video>`；IM 消息视频（`<AuthedVideo>`）已用它，**但 platform 播放器没用**。

### 关键取证（实测三连，推翻「后端坏了」的误判）

| # | 操作 | 结果 |
|---|---|---|
| 1 | 裸请求 `/api/platform/media/stream?t=dummy&s=dummy` | **HTTP 401** |
| 2 | `stream-ticket`（带真实 token）→ `stream`（带 token + `Range: bytes=0-131071`） | **HTTP 206** `video/mp4`，131072 字节，`ftyp` 有效 ✅ |
| 3 | 同一 stream 地址**无 token** | **HTTP 401** ❌ |

### 排除项（避免误修）

- **不是**编码格式问题：实测 `play_addr` 为 **H.264/AVC + AAC**（`ftypisom` 标准 MP4），
  `play_addr_265` 为 H.265/HEVC。前端 `pickKernel` 对 MP4 → `Html5Kernel`，选择正确。
- **不是**「CDN 直链必 403」：实测该前提**只在缺 `Referer` 时成立** ——
  仅 UA → 403；**UA + `Referer: https://www.douyin.com/` → 200/206 完整可播**。
  后端 `resolve_playable()` 与流代理**均已带正确 Referer**，故取址链路健康。
- **不是**后端取址失败：3/3 作品 `resolve_playable → get-range` 成功，
  代理模拟拉流 3/3 返 206 + 有效 `ftyp`。

## 五、修复（Restores Design Contract）

`player-media-stage.tsx` 接入既有 `useAuthedMediaUrl`：

- 媒体 url 为**本地受保护地址** → 带令牌 fetch 成 Blob（`blob:`）再交给 `<video>`；
- **外部地址**（图床 `https://`、`data:`）→ 原样返回，零开销、零改动；
- 在**舞台层统一接入** ⇒ 所有经此舞台播放的受保护媒体自动生效，**调用方零改造**；
- 时序契约：`undefined`=加载中（占位，不误报"无媒体"）；`null`=取失败（走既有降级）；
  `string`=可用。

**后端零改动** —— 不动 `_MEMBER_EXEMPT`，不引入"媒体端点无鉴权"的安全面变化
（豁免一旦放宽，任何知道文件名的人都能取走本地媒体）。

## 八、教训（可迁移判据）

1. **「后端通 ≠ 前端能播」**：受保护端点 + 无法带头的标签（`<video>/<img>`）=
   典型 401 陷阱。**判据**：看端点是否在鉴权中间件保护范围内，再看标签能否带头。
2. **项目已有解法先复用**：`useAuthedMediaUrl` 早已存在且 IM 链路在用，
   新页面接入时**应 grep 既有同类实现**，而不是各写各的（本次 platform 漏接）。
3. **推翻既有假设要实测**：「CDN 直链必 403」是个**只在缺 Referer 时成立**的
   局部事实，被当成普遍规律写进了选型逻辑。带/不带头的 A/B 实测是唯一判据。
4. **媒体编码实测法**：取前 256KB 解 `ftyp` + 扫 `avc1/hvc1/hev1/av01` 盒，
   比看响应头更本质（响应头只说 `video/mp4`，不说编码）。
