# 内容板块「点赞 / 收藏 / 站内通知」三类本人端点不可用 —— 凭证过期被伪装成空数据

- **案例编号**：CASE-2026-09-26-PLT-SC8
- **版本**：v0.45.10（修复）｜ 前一版 v0.45.9
- **提交**：`c9f105a`
- **严重级别**：error（功能不可用 + 错误语义误导）
- **涉及模块**：`backend/api/platform.py`（`/liked` `/favorite` `/notice/list`）、
  `frontend/src/api/platform.ts`、`frontend/src/components/platform/platform-page.tsx`

---

## 一、设计意图（Step 1）

| 项 | 内容 |
|---|---|
| **模块** | 内容板块 —— 本人视角的三个 tab：点赞、收藏、站内通知 |
| **设计契约** | 三端点均以「当前选中账号的登录态」为前置条件；<br>成功返回 `{ok:true, items:[...]}`；<br>**平台侧不可用时必须返回 `unavailable:true` + `reason`（错误语义不得丢失）** |
| **期望行为** | 登录态有效 → 返回真实列表；登录态失效 → **明确告知用户"需要重新扫码"**，绝不显示为"暂无数据" |
| **假设** | ① `feed`/`search` 能用 ⇒ 凭证可用（**该假设后被证伪**）<br>② `status_code=8` 属平台侧"高频临时降权"，稍后自愈（**证伪**） |

## 二、观察到的偏差（Step 2）

| 现象 | 用户原话 |
|---|---|
| 点赞列表取不到 | 「内容板块的点赞，收藏，无法正常获取」 |
| 收藏列表取不到 | 同上 |
| 站内通知读取异常 | 「站内通知读取也是异常的」 |

**关键表现**：三者**都不报错**，而是显示**空列表 /「暂无通知」** —— 用户无法分辨
"本来就没有"与"登录过期了"。

## 三、执行链追溯（Step 3）

```
前端点击「点赞」tab
  └─► POST /api/platform/liked  {account, sec_id:""}
        └─► _auth_for(account)                       ← cookie 有效 ✅
        └─► api.get_my_sec_uid(auth)                 ← ★ 断点
              └─► GET /aweme/v1/web/user/profile/self/
                    └─► HTTP 200 {"status_code": 8, "status_msg": "用户未登录"}
              └─► （回退）GET https://www.douyin.com/user/self 抓 HTML 正则
                    └─► 失败 → raise RuntimeError
        └─► except → 返回 {unavailable: True, reason: "...稍后重试即可"}  ← ★ 错误语义
```

**通知链路**（更严重 —— 断点被静默吞掉）：
```
POST /api/platform/notice/list
  └─► api.get_notice_list(auth, ...)
        └─► GET /aweme/v1/web/notice/
              └─► HTTP 200 {"status_code": 8, "status_msg": "用户未登录"}
        └─► 不抛异常 ⇒ raw = {status_code:8, ...}
  └─► items = raw.get("notice_list_v2")  → None
  └─► for n in (items or []):  → 空循环
  └─► return {items: [], ...}          ← ★ 零提示，伪装成「暂无通知」
```

## 四、根本原因分析（Step 4）

### 4.1 直接根因：**凭证已过期**（实测铁证）

| 判据 | 实测值 | 结论 |
|---|---|---|
| cookie `sid_guard` | `…%7C1790251779%7C51` | exp = **2026-09-24 20:09:39** |
| 当前时间 | 2026-09-26 10:06 | **已过期 ~38 小时** |
| `login_time` | `1790251777226` | 登录于 2026-09-24 20:09:37 |
| `/profile/self` | `{"status_code":8,"status_msg":"用户未登录"}` | 服务端不认登录态 |
| `/notice/` | `{"status_code":8,"status_msg":"用户未登录"}` | 同上 |
| **对照组** `feed` | `status_code=0`，**6 条正常** | ⇒ **凭证未被全盘否决**，仅"本人相关"端点失效 |
| `has_biz_token` | `false` | 旁证 |
| `IsDouyinActive` | `false` | 旁证 |
| `AUTH-050` 探活 | uid=3119773958541104 ≠ 历史 conv_id | 凭证陈旧 |
| `cmd 609` | `unexepcted session length` | web 会话被服务端判**只读** |

**论证**：`feed` 能返 6 条 ⇒ cookie 整体**未失效**（否则 feed 也会被拒）；
而 `profile/self` / `notice` 返 sc=8 ⇒ 区别在于**这两类端点要求登录态**。
⇒ 结论：**登录态本身已过期，而"公开类"端点不受影响**。

### 4.2 设计层根因（为什么用户看到的不是错误）

**旧假设错误**：把 `sc=8` 一律解释为「短时高频访问触发限制，**稍后重试即可**」
（见修复前注释原文）。实测证伪：

- 时间戳铁证显示是**硬过期** → **永远不会自愈**
- 正解是**重新扫码**，而非"重试"

**两类错误语义缺陷**：

| 缺陷 | 位置 | 后果 |
|---|---|---|
| **误导性原因** | `/liked` `/favorite` 的 `reason` | 引导用户"稍后重试" → **永久无效动作** |
| **静默吞掉失败** | `/notice/list` 完全不看 `status_code` | 伪装成"暂无通知" → **用户无从察觉** |

**架构层观察**：`get_user_favorite` / `get_notice_list` **不抛异常**、而是返回
`{"status_code": 8}` —— 这类"HTTP 200 + 业务错误码"的响应，**必须在业务层显式判定**，
不能依赖异常机制。原实现漏了这一层。

### 4.3 上游情报核实（Open-Source Provenance Law）

| 项 | 结果 |
|---|---|
| 上游项目 | `cvv-cat/Douyin_Spider`（本项目基座来源） |
| 取证方式 | GitHub API 列目录 + jsdelivr CDN 拉源码（raw.githubusercontent 超时） |
| 产物 | `dy_apis/douyin_api.py`，**91,947 字节**（与 API 报告 size 一致 → 完整） |
| `get_notice_list` | 端点 `/aweme/v1/web/notice/`、参数 `notice_group=700`、字段 `notice_list_v2` —— **与本项目一致** |
| 结论 | **不是本项目适配错误**；上游同样未处理登录过期语义 |

**⇒ 排除"接口用错"这一假设**，根因锁定在"凭证过期 + 错误语义缺失"。

## 五、修复方案

### 5.1 新增统一判据（复用既有，不自造）

```python
def _login_state_reason(account) -> tuple[str, str]:
    """复用 auto_dm.accounts.verify_credential（项目唯一凭证有效性入口）"""
```

**为什么复用而非新建**：项目已有 `verify_credential` → 若在 platform 里另造判据，
会与「账号管理」页结论**打架**（两处判据漂移是 doc-rot 的前身）。

判据映射：
- `dm.level==fail` 且 detail 含 `609`/`只读` → 「网页登录态为只读」+ **重新扫码**
- `wp.level==fail` 且 label 含「漂移/AUTH-050」 → 「凭证陈旧」+ **重新扫码**

### 5.2 三处端点改造

| 端点 | 改动 |
|---|---|
| `/liked` | `get_my_sec_uid` 失败 → 真实原因；**新增** `_is_not_logged_in(raw)` 判定 |
| `/favorite` | 同上（3 处返回值统一） |
| `/notice/list` | **新增** `_is_not_logged_in(raw)` → `unavailable + reason` |

### 5.3 前端

- `notices` API 类型补 `unavailable?` / `reason?`
- notice 空态：`unavailable` → 显示"暂时取不到站内通知 + 原因"，而非"暂无通知"

## 六、实机验证（Step 5）

**环境**：`dyautodm_design`（design 分支数据根）；后端以**源码实例**启动
（`python -m uvicorn main:app`，非打包 exe）；带真实会员 token 走**前端同款链路**。

```
=== /liked         HTTP 200 ===
  ok= True | items= 0 | unavailable= True
  reason: 该账号的网页登录态已被服务端判为「只读」（读可用、写不可用）。
          请在「账号管理」对该账号执行【重新扫码】重建登录态

=== /favorite      HTTP 200 ===
  （同上，完全一致）

=== /notice/list   HTTP 200 ===
  （同上，完全一致）
```

**判据达成**：
- ✅ 三端点均返回 `unavailable:true`（**不再伪装成空数据**）
- ✅ `reason` 给出**真实原因 + 可行动指引**（不再是"稍后重试"）
- ✅ 三者原因**一致且同源**（都走 `verify_credential` ⇒ 与账号管理页不打架）

**修复前对照**：
- `/liked` `/favorite`：`reason` = "多为短时高频访问触发限制，稍后重试即可"（**误导**）
- `/notice/list`：`items:[]` 且**无 reason**（**零提示**）

## 七、结论与后续

### 7.1 这不是代码 bug（本体）

**用户问题的正解**：在「账号管理」对「四川工伤张老师」**执行重新扫码**。
三个 tab 将立即恢复。

### 7.2 但代码有两个真实缺陷（已修）

把"凭证过期"伪装成"空数据"是**错误语义缺陷** —— 用户因此无法采取正确动作。
修复后：**失败可见、原因明确、动作可执行**。

### 7.3 可迁移判据（写给未来的自己）

1. **"HTTP 200 + 业务错误码"必须显式判定** —— 不能依赖异常机制捕获
   （`get_user_favorite` / `get_notice_list` 都是这类）。
2. **"部分端点可用"不能证明凭证有效** —— 必须区分公开端点与本人端点。
   `feed` 可用 + `profile/self` 返 sc=8 是**常见组合**，不是"降权"。
3. **判断凭证是否过期，优先读时间戳** —— cookie `sid_guard` 的 exp 是**可直接换算的硬证据**，
   比任何"现象推断"都可靠。
4. **降级文案必须是"可行动的"** —— "稍后重试"在**永不自愈**的场景下是**负价值**
   （消耗用户时间 + 让他以为系统会自愈）。
5. **上游取证要用 size 交叉验证** —— `jsdelivr` 拉到的字节数必须与 GitHub API
   报告的 size 一致，否则可能是残缺文件（raw.githubusercontent 在本机超时）。
