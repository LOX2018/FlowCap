## 0. 用户原话（判据来源，逐字）

> 「要知道私信的目的就是留资，这个对方的聊天内容如果是有明确的问题则先针对问题回复
> 体现专业性同时引导留资，但如果是这种对话对象，他的聊天内容没有明确目标的人群
> 直接引导留资就行，别说什么之后再联系，抖音是快平台，客户前一秒还在你这下一秒就去
> 别人那了，根本没有沉淀的必要。」

---

## 1. 设计意图（Step 1：回归设计契约）

| 项 | 应然 |
|---|---|
| 私信的**目的** | **留资（拿到手机号）** —— 不是"答疑"、不是"维护关系" |
| 有明确问题 | 先正面答到点子上（体现专业性）→ **同一轮**收口要联系方式 |
| 无明确问题 | 直接引导留资，**不寒暄、不问伤情、不等消息** |
| 平台特性 | 抖音是快平台 ⇒ **没有"之后再联系"这回事**（放走 = 丢单） |

**违反条款**：Agent prompt 的漏斗把"要联系方式"排在**最后**，并明写「不再索要，安心解答」；
系统侧无任何"这轮有没有索要"的机械判据。

## 2. 观察到的偏差（Step 2）

会话「668」截图逐条：

| 说话方 | 内容 |
|---|---|
| AI | 50天了，工伤认定书下来了吗？… |
| 客户 | 没下来 |
| AI | 没认定就没法评残，也拿不到基金那部分钱 |
| AI | 我看下你的病例 |
| 客户 | 单位给报了工伤，我下午去人社局问问 |
| AI | **好，问问进度。认定书下来第一时间通知我，我帮你算清赔偿清单。** |
| AI | 你联系方式多少 |
| 客户 | 好 |
| AI | **我等你人社局问完的消息，认定书到手我就帮你算清单。** |

⇒ 客户只说「好」「下午去问问」时，AI **两次把线索放走**（等对方回头）。

## 3. 执行链溯源（Step 3~4）

```
AutoReplyWorker._handle
  → _generate_reply(cfg, text, account, conv_id, before_id)
      ├─ ① reply_kb.find_match          ← 命中即回（本次非主因）
      ├─ ② build_system_prompt(cfg)      ← 断点 A：Agent prompt 漏斗 =「最后才要」
      ├─ ③ client.chat_failover(...)
      ├─ ④ validate_reply(raw, cfg)      ← 断点 B：只查长度/违禁词/专业准确性，
      │                                         **没有"这轮有没有索要"的判据**
      ├─ ⑤ 短回复重试（仅当 len < min_reply_len）
      └─ ⑥ fallback_reply(cfg)           ← 断点 C：主池 4 条**全不含索要**
```

**RCA**：不是模型不听话，而是「索要」在**三条路径上都不被要求**：
prompt 把它排在最后、护栏不检查它、兜底池根本没有它。

## 4. 修复（Step 5：实机验证）

见 ADR-027 §3（D1~D6）。核心：

| 落点 | 改动 |
|---|---|
| `_LEAD_DISPOSITION_RULES` | 覆盖式追加进 prompt 最末：有明确问题→先专业**同轮**索要；无明确问题→直接引导留资；**【机械禁止】以后再说式收尾** |
| `lead_first_reply`（新配置） | 「客户无明确问题」专用留资话术 |
| `_is_lead_stalled` / `_has_lead_ask` / `_is_deferring` / `append_lead_ask` | 机械判据 + 追加器 |
| `_generate_reply` + 终末兜底 | 两处接线（`AI-070`）：定向重试 → 追加索要 → 整句替换 |
| `_KV_ASK_COUNT` | 由「预留未用」变为真计数（`max_lead_ask` 获真上限） |

**未触碰**：发送/出队链、`max_reply_len` 语义、留资成功后的确认行为。

⚠️ **实机验证抓出我自己写的 2 个缺陷（诚实记录）**：
① 脚本**绕过 `_generate_reply` 直调模型** ⇒ 看到未治理输出（假失败）；
② 脚本对返回结果**二次 `validate_reply`** ⇒ `max_reply_len=60` 截掉护栏刚追加的索要句（假失败）。
⇒ **教训：验证脚本必须走真实链路，且不得复制真实链之外的校验。**

## 6. 可迁移判据（写入知识库）

1. **「承诺给价值」≠「索要」**：判"有没有推进留资"只能看**是否出现索取动作**，
   不能把「我帮你算清单」这类承诺算作推进（截图原文正是这么被放过的）。
2. **机械规则要落在"输入侧 + 输出判据"两处**：只写进 prompt = 靠模型自觉（长会话必衰减）；
   必须有出口判据兜住，且**降级路径同受约束**。
3. **降级路径必须与主路径同判据**（本项目已两次踩坑：H-24 只修主通道、本次只修主生成链）。
4. **判据过宽会漏判、过窄会误伤**：本判据演进三轮（"无索要且无提问" → "无索要" →
   追加"人称锚定"），每一轮都由真实样本打回；**判据必须由真实样本驱动**。
5. **改写 AI 输出要"保原意"**：整句替换会丢专业回答；优先"追加/补丁"，
   替换只在原句本身矛盾（含放走语）时使用。

## 7. 命中库最短路同受约束（本轮补修，实测发现）

实测：`reply_kb.find_match` 命中后是**直接 `return`** —— 此前**完全绕过**留资护栏
（以及直播场景护栏）。而存量 28 条（**全部 `source=auto`**）实测含：

| 存量条目 | 问题 |
|---|---|
| `Q:没有保守治疗 → A:有等级，工伤10级` | **无依据等级断言**（用户第一轮反馈点名的正是这类，且仍在生效） |
| `Q:拿到认定结果了吗 → A:拿到认定结果了吗` | 退化复读 |
| 多条（如「你找一下入院诊断」） | **不含任何索要动作** |

**修法（D7）**：
- **私信侧**：命中库直回也过留资判据 —— 未索要则 `append_lead_ask`（保留库内专业内容）；
  不可追加才换引导留资话术；
- **直播侧**：命中库直回前过 `_live_guard_violation`，违规即改引导型兜底。
