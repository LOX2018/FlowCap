## 1. P0-① `recv_daemon.py` —— `_extract` 被吞进 `_msg_extra_json`（WS 收消息全废）

### 设计契约
`RecvChannel` 是 WS 实时收取私信的**唯一入口**；`_handle` 解析每条 `content_json`
必须调用 `self._extract(...)` 按 msg_type 转可读文本。

### 现象与根因
`_msg_tuple` / `_ws_tuple` / `_msg_extra_json` 三个**模块级函数**被插在
`RecvChannel` 类体**中间**（类在 L1126 结束，函数从其后的 L1128 起，**缩进 0**），
而紧随其后的 `_extract`（原 class 方法）**仍缩进 4** ⇒ 被 AST 解析为
`_msg_extra_json` 的**嵌套函数**，不再是 `RecvChannel` 的属性。

**后果**：`RecvChannel.__dict__` 无 `_extract` ⇒ `self._extract(...)`（`_handle` 内）抛
`AttributeError`，被 `_handle` 上游的接收回调吞成告警 ⇒ **WS 实时收消息彻底失效**（静默）。

### 实测证据（复现）
```
修复前：RecvChannel 方法表 = [..., '_sync_conversations']  ← 无 _extract
       模块级 _msg_extra_json 内嵌函数 = ['_extract']      ← 被吞
修复后：RecvChannel 方法表 = [..., '_sync_conversations', '_extract']；内嵌 = (无)
```
另有 `ast.parse` + `hasattr(RecvChannel,'_extract')` 双证；实调 `RecvChannel._extract({'text':'hello'}, 1)`
返回 `('[未知类型1] {...}', {})` ✅。

### 修复
把被吞的 `@staticmethod def _extract(...)` 整块（indent 4，L1204–L1298，含前置空行）
**移出** `_msg_extra_json`，插到 `RecvChannel` 类体末尾、三个模块级函数之前
（即 `_sync_conversations` 之后）。字节级搬迁，保留原 CRLF。

## 2. P0-② `conversation_capture.py` —— `tuple()` 漏传 `ts/msg_id/role`（去重+归属错乱）

### 设计契约（ADR-012 层 2）
`_rec_of(m, extra).tuple(...)` 是 `capture_all` 的**唯一写入出口**，八列同序：
`account, conv_id, role, text, msg_type, extra, ts, msg_id`。
`uniq_dmmsg` 是**部分唯一索引**（`WHERE msg_id IS NOT NULL`），依赖 `msg_id` 去重；
`role` 区分 `me/them`（发送方归属）。

### 现象与根因
两处调用 `_rec_of(m, _extra).tuple(name, cid)` **只传前两列** ⇒ 其余走
`MessageRecord.tuple` 默认值 `ts=0.0, msg_id=None, role="them"`。
而消息 dict `m` 明明带真实字段（生产者 L716-725 / L1065-1074）；
另三处同类调用（`recv_daemon.py` 的 `_msg_tuple`/`_ws_tuple`、`database.py` 迁移）**均显式传值**
⇒ 唯此二处漏传。

**后果**（实测）：
- **静默吞行**：`msg_id=None` 使 `uniq_dmmsg` 失效、落 `uniq_dmmsg_fallback(account,conv_id,text,ts)`，
  同会话同文本的多条消息只留 1 条；
- **字段腐坏**：`ts=0.0` 破坏 `ORDER BY ts`（AI 上下文装配 / 前端排序）；
- **收发反转**：`role="them"` 把**自己发出的**消息记成对方发的。

### 实测证据（对照）
```
[修复前] 两条「同会话同 text、不同真实 ts/msg_id」的 me 消息
   → 落库 1 条 (role='them', ts=0.0, msg_id=None)    ← 吞行 + 三字段全腐坏
[修复后] → 落库 2 条
   ('me', 1758880000.0, '7111') / ('me', 1758880600.0, '7222')   ✅
```
（真实表 + `uniq_dmmsg` 部分索引 + `uniq_dmmsg_fallback`，与生产同构。）

### 修复
两处改为显式传 `ts=m.get("ts") or 0`、`msg_id=(str(...) if ... else None)`、`role=m.get("role") or "them"`。

## 3. P0-③ `media_request.py` —— 受保护流 `Referer` 被删（403 回归）

### 设计契约
抖音 CDN **按 Referer 白名单放行**；本仓**所有** CDN 取流/取图请求均带
`Referer: https://www.douyin.com/`（`origin_image_resolver.py:193`、`platform.py:1438`、`login_remote.py:632`）。
同日案例 `..._401_case_v0.45.9.md` 明文：「`resolve_playable()` 与流代理**均已带正确 Referer**，故取址链路健康」。

### 现象与根因
ADR-016「统一 UA」提交 `f54f554` 在重写 `resolve_playable` 的 headers 时
**顺带删除了 `Referer`**（功能回归，非 UA 重构所必需）。

### 实测证据
```
修复前 headers = {"User-Agent": ..., "Accept": "*/*"}          ← 无 Referer
案例 §四 实测：仅 UA → 403；UA + Referer → 200/206 完整可播
```

### 修复
补回 `"Referer": "https://www.douyin.com/"`（并注明来由与一致性契约）。

## 4. P0-④ `ai_reply.py` —— 水位在 in-flight 判定**之前**推进（并发永久丢消息）

### 设计契约（ADR-008 决策 3）
跨会话并行、**同会话串行**。`_tick` 每轮从水位 `last_id` 之后捞取消息；
`_inflight` 标记「该会话正在处理」。水位语义：**水位之前的消息必已被处理**。

### 现象与根因
原实现逐行执行：
```
last_id = max(last_id, r["id"]); _kv_set(_KV_MARKER, last_id)   # ← 先推水位（对每一行，含将跳过的）
...
if _skey in self._inflight: continue                            # ← 再判在途并跳过
```
同一 tick 内同会话后续行 `m.id > 水位` 被 `continue` 跳过，但**水位已被推过它们** ⇒
下一轮 `m.id > last_id` **不再匹配** ⇒ 这些消息**永久丢失**。

### 实测证据（驱动真实 `_tick`）
```
[修复前] 水位(第1轮)=6  第1轮提交=[5]  第2轮是否取回 id6 = False   ← 永久丢失
[修复后] 水位(第1轮)=5  第1轮提交=[5]  第2轮是否取回 id6 = True    ✅
```
（临时库 + 真实 `_tick` 源码；`_handle_session` 桩化以固定「处理中在途」时序。）

### 修复
把水位推进**移到 in-flight 判定之后**（仅对**真正提交处理**的行推进），
并把 in-flight 分支由 `continue` 改为 **`break`**（中断本轮，不越过在途行）⇒
下轮从水位重捞 ⇒ 行 6 必被取回，且本轮未提交其后行 ⇒ **不重复处理**。

## 7. 教训（写入）

1. **模块级函数插进类体中间 = 后续方法被静默吞成其嵌套函数**。
   判据：改类结构后必须 `ast` 复核**目标方法是否仍在类的方法表里**（`__dict__` / AST body），
   不能只看「文件能 import 不报错」——`@staticmethod` 嵌套是**合法语法**，运行期才炸。
2. **写入出口漏传字段 = 走 builder 默认值**。默认值（`ts=0.0/msg_id=None/role="them"`）
   恰好**同时破坏**去重键与归属语义 ⇒ 必须断言「出口调用点显式传关键字段」。
3. **「统一 X」类重构容易顺带删除相邻字段**（本例删 Referer）。
   判据：重构请求头/参数时，**逐字段与重构前 diff**，不得凭「只改 X」的意图放过其它字段。
4. **水位/游标推进必须与「已处理」语义严格绑定**。凡「跳过但推进游标」= 丢数据；
   正确形态是「未处理 ⇒ 游标不动」。
