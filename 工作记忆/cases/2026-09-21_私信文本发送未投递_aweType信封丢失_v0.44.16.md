# 2026-09-21 私信「显示成功但从未投递」——aweType 信封在协议重构中丢失

> 归属：DYAutoDM_v2 · design/better-douyin 分支 · v0.44.16
> 性质：**已定位 + 已修复 + 已实机验证**
> 用户原始报告：「实测ws私信发送异常，从未真实发送」「你说小助理成功的？实际是发送失败的」

---

## 一、现象

日志打印 `私信发送成功 conversation_id=...`，但对方**收不到**。DB 侧形态：

```
09-21 01:28:47 尚进工伤小助理  me  local:528226bc961440c9  '2026-09-21 01:28私信发送测试'
```

- `local:` 前缀 = 本地占位，**没有 server_message_id**
- 对端（张老师，同会员库另一账号）**零对应行**

对照同会话历史：08-04 ~ 09-19 每条成功消息都**双向落库**（`尚进 me` + `张老师 them`，同一 server_message_id）。
⇒ 不是「我看不见成功」，是**真的没投递**。

## 二、定位过程（六步闭环）

### Step 1 回归设计意图
`message_type=7`（IM_TEXT）声明这是富媒体消息，其 content **不是裸文本**，
而是浏览器 SDK 的固定 JSON 信封。

### Step 2 定义偏差
我方发出的 content = 裸文本 `"哈喽…"`；期望 = `{"aweType":700,...}`。

### Step 3 链路溯源 → git 考古找到破坏点
| 时间 | 事件 |
|---|---|
| 09-19 22:28 | DB 中最后一次成功投递 |
| **09-19 23:44** | v0.43.97 提交「私信链路整体对齐抖音 2026 PC IM 协议」 |
| 09-21 | 全部发送只回 OK、无投递 |

`git show 22fae71 -- backend/builder/proto.py` 显示重构时**删掉了信封**：

```diff
-        msg_content = {"mention_users": [], "aweType": 700,
-                       "richTextInfos": [], "text": message}
+        if isinstance(content, (dict, list, tuple)):
+            encoded_content = json.dumps(content, ...)
+        else:
+            encoded_content = str(content)     # ← 裸文本直发
```

调用方 `client_im.py:371` 传的正是裸字符串 → 落入 else 分支。

### Step 4 根因
重构为支持富媒体引入 `content` 参数时，**只覆盖了 dict 分支，裸字符串分支丢信封**。
服务端对裸文本「收妥回 OK 但不投递」—— 与上游两个未关闭 issue 同一形态：
- [cv-cat/DouYin_Spider#44](https://github.com/cv-cat/DouYin_Spider/issues/44)「只能给自己发送私信，返回 OK 好友收不到」
- [#64](https://github.com/cv-cat/DouYin_Spider/issues/64)「私信对方收不到」status_code=10502

### 四来源交叉验证（铁律：单一来源不下结论）

| 来源 | type=7 的 content |
|---|---|
| `zhinjs/douyin-im` `buildDesktopTextContent()` | `{"aweType":700,"type":0,"richTextInfos":[],"text"}` |
| `cv-cat/DouYin_Spider` `send_msg`（origin/master 最新） | 同上 |
| `xiaoxiaodafeng/Douyin_messages` `proto_builder.py` | `aweType:700`（含 mention_users） |
| **本项目 v0.43.97 之前** | 同款 `aweType:700`（被删） |

### 为什么守卫没拦住
`scripts/verify_im_protocol_2026.py` 原 14 项只校验**信封与鉴权字段**，
`grep -c aweType` = **0** —— 对 content 载荷零覆盖。

## 三、修复（v0.44.16）

1. `backend/builder/proto.py`：`message_type == 7` 且 content 非 dict 时，
   包装 `{"aweType":700,"type":0,"richTextInfos":[],"text":...}`。
   富媒体 dict 不受影响（不二次包裹）。
2. `scripts/verify_im_protocol_2026.py`：新增 I8b/I8c/I8d 三项守卫，
   **真实调用构造函数并断言产出**（不用 grep 源码——注释里的 aweType 会造成假绿）。

## 五、新增可复用判据

1. **「返回 OK」≠ 投递。** 判定必须看 `body.100` 的
   `server_message_id`（非空非 0）+ `check_code`（8610=未投递、10502=审核中、8101=已投递）。
   口径来自 `zhinjs/douyin-im` `isMessageDelivered()`。
2. **重构「兼容旧调用」的参数时，必须为每个分支都补等价性验证。**
   本次只覆盖了新增的 dict 分支，旧的字符串分支静默退化——且单测全绿。
3. **协议守卫必须覆盖「载荷」，不能只覆盖「信封」。**
   上层结构正确而载荷错误，是最难发现的一类回归。
4. **判定契约优先跑运行时断言，不要 grep 源码**：注释/文档里的同名字串会造成假绿。
5. **定位回归起点用 git 考古（提交时间 vs DB 最后一次成功时间）**，
   比读代码猜快得多；本次两者相差 76 分钟，直接锁定到单个提交。
6. **全量单测失败必须先用 stash 证明是否与自己相关**，不得含糊汇报「可能有失败」。
