## 一、最核心教训：**跨语言参数形状错，Python 单测永远测不出**

### 现象（三条链路静默恒失败）

```python
# 新增页面脚本（错）
RESOLVE_URLS_JS = """async ({path, tkeys}) => { ... tkeys.map(...) }"""
# 调用方（对，但配合错）
res = exec_js(RESOLVE_URLS_JS, [BATCH_PLAY_INFO_PATH, keys])   # 数组
```

Playwright 把整个 `[path, keys]` 当作**单个 arg** 传入 → 对象解构 `{path, tkeys}`
从数组上取属性 → 两者皆 `undefined` → `tkeys.map(...)` 抛 `TypeError`。

**Node 真跑证据**：

| 形态 | 结果 |
|---|---|
| 修复前（对象解构 + 数组传参） | `{"err":"TypeError: Cannot read properties of undefined (reading 'map')"}` |
| 修复后（`async (arg) => { const [path, tkeys] = arg; }`） | `{"status":200,...}` |

### 为什么单测没抓到（本项最大的方法论价值）

`test_upstream_p4.py` / `test_upstream_p5.py` **只 stub 了 Python 侧的 `exec_js`**
（`def fake(js, arg): ...`），**从不真正执行 JS 字符串** →
「JS 形参形状」这类缺陷在 Python 侧**零检出能力**。

⇒ **规则：凡改动 `exec_js` 类跨界调用（Python→JS），必须把 JS 抽出来用 node 真跑一次**
（本仓正解范式：`services/voice_transcribe.py` 的 `RECOGNIZE_JS`，形参 `async (arg)` +
函数内 `const [a, b] = arg;`）。验收脚本已内置该检查（A1，三条全跑）。

### 同坑三处（只修一处等于没修）

| 文件 | JS 常量 | 影响链路 |
|---|---|---|
| `services/cenc_video.py` | `RESOLVE_URLS_JS` | IM 视频取址（tkey→签名 URL） |
| `services/nickname_fallback.py` | `FETCH_JS` | 昵称兜底查询 |
| `services/merged_forward.py` + `api/messages.py:1348` | `WEB_FETCH_JS` | **合并转发正文补抓** |

**发现方式**：修 `cenc_video` 时全仓扫「其他 `*_JS` 常量怎么写的」，才发现三处同源。
**教训：同一缺陷模式必须全仓 grep 同源实现，不能只改报告点出的那一处。**

### A14 的额外教训：「补个括号」不等于修对

第一版只补了括号。验收脚本用真实 sqlite 跑出**仍然误判**：

```
❌ A14 单聊形态未被误判为群聊  — 被误改: ['0:1:11:22', '0:1:33:44']
```

根因：`WHERE conv_type IS NULL OR (conv_type=1 AND conv_id 纯数字)` 中，
被 **显式插入 NULL** 的行（旧库/异常路径）走的是 `IS NULL` 分支，
**不做形态判定就无条件写成 2**。

正确修法 = **按形态分类**（判据与 `conv_identity.conv_type()` 一致）：

```sql
UPDATE dm_conversations SET conv_type=2 WHERE conv_id GLOB '[0-9]*' AND conv_id NOT GLOB '*[^0-9]*';
UPDATE dm_conversations SET conv_type=1 WHERE conv_type IS NULL AND NOT (<上述形态>);
```

⇒ **规则：SQL/数据修复类改动必须用真实 sqlite 跑一遍「四形态覆盖」用例**，
光读 SQL 语义会漏掉「某个分支没做判据」这类错（且它看起来很安全）。

## 三、契约收敛：群聊判定 3 处重复实现 → 单一真相源

「`conv_id` 纯数字 → 群聊」原先在 **3 处**内联重写：
`api/messages.py`、`auto_dm/conversation_capture.py`、`services/chatlab_export.py`。

`services/conv_identity.py` 的 docstring 首句就是「**会话 ID（conv_id）与账号 UID 的解析，
全项目只允许一处实现**」，且列明了上一轮同类收敛的 5 处重复及其真实故障面
（判定强度不一致 → 行为漂移；修复不同步 → 隐性 bug）。

⇒ 新增 `conv_identity.conv_type(conv_id) -> int`，三处调用方改为取用；
验收脚本用 `conv_type()` 与真实 sqlite 回填结果**逐条比对一致**，
并断言三个文件里**不再有内联判据**。
