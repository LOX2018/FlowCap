## 1. 设计意图（Design-First Law）

### 1.1 M-12：测试集合的**顺序无关性**是不变式

`unittest discover` 把全部 `test_*.py` 导入**同一进程**（本仓既定前提，
见 `test_config_isolation.py` 模块 docstring）。由此推出**两条隐含契约**：

1. **模块身份唯一**：同一进程内一份源码只允许一份模块实例（REG-01 定式）。
2. **打桩必须覆盖消费者的绑定**：若消费者在**导入期**执行 `from database import get_db`，
   把函数固化进自己的命名空间，则「事后改 `database.get_db`」**传导不到它**。

**不变式**：任一用例的结果**不得依赖其它用例是否先跑过**。

### 1.2 H-7 样本①/②：回放层需要**可复现的真实输入**

回放层（`backend/replay/`）的契约：样本来自**真实实拉**、脱敏后经
`recorder` 单通道入库（sha256 冻结），回归跑样本、**零网络零浏览器**。
但两类输入**当前无落盘出口** ⇒ 无法入库 ⇒ 回放层覆盖有缺口：

| 样本 | 为何截不到 |
|---|---|
| ① `cmd301` | 由 `fetch_conversation_history()` 用 `requests` **直发**（`imapi.douyin.com`），**不经浏览器** ⇒ BCC 的 WP hook 截不到 |
| ② `ws_frames` | WS 帧只记 debug 日志，`parse_ws_frame` 对 `B64:` 二进制帧**直接 return**，无任何落盘出口 |

## 3. 执行链上溯（Execution-Chain Traceability）

### 3.1 M-12 · 根因①：**打桩传导不到「导入期固化 get_db」的消费者**

```
test_engine_contract_p1 运行期 import 了 api.messages
   └─ api/messages.py 在【模块导入期】执行 `from database import get_db`   ← get_db 被固化
        ↓
test_upstream_p4.TestConversationSeq.setUp
   ├─ _mkdb() 建内存库
   ├─ sys.modules["database"].get_db = lambda: self.conn        ← 改的是 database 模块的属性
   └─ from api.messages import get_conversation                 ← 拿【已固化的旧 get_db】
        ⇒ get_conversation 读【真实库】⇒ detail = []            ← 打桩落空
```

**实测佐证（对照实验）**：`test_upstream_p4` 单跑 27/27 绿；与
`test_engine_contract_p1` 或 `test_replay_gates` 同跑即 1 failure + 1 error；
与其余 6 个新守卫模块两两配对**全绿** ⇒ **污染源二分锁定**。
`git worktree --detach b455192` 对照证明 **HEAD 上同样失败** ⇒ **既有债，非本批引入**。

> ⚠️ 注意 `test_upstream_p4.py` 的 tearDown 自注（2026-09-18 A16）已正确认识到
> 「删 `sys.modules["database"]` 会让 api.messages 持陈旧绑定」，但**未认识到**：
> 在别处**已先行导入** api.messages 时，「只改 `database.get_db`」同理会失效。

### 3.2 M-12 · 根因②：`ai_leads` 不在清理清单

```
TestAggregation 用例1: INSERT ai_leads(acc1, conv, wechat, wx123)   ← 未删
TestAggregation 用例2: _reset_db() 只 DELETE dm_conversations/dm_messages/kv_store
   ⇒ ai_leads 残留 → 再 INSERT 同键 → UNIQUE constraint failed
```

### 3.3 M-12 · 根因③：`_ROOT` 全局共享 → 跨进程 SQLite 写锁

`test_capability_probe._ROOT = iso._ROOT`（= `%TEMP%/dyautodm_cfgtest_root`）,
任何两个进程同时跑 discover 都争同一 DB 文件 ⇒ `database is locked`
（实测：并行窗口内单次跑 467s）。另：`rm -rf` 该目录在**文件句柄未释放**时
会被 Windows 拒绝 ⇒ 残留旧 DB 被复用（另一条伪失败源）。

### 3.4 H-7 · 落盘出口缺失

读码确认：`_extract_301_page(resp.content)` 直接消费 `resp.content`，
`resp.content` **没有任何落盘分支**；`parse_ws_frame` 对 `B64:` 帧
`logger.debug(...); return out` —— 原始数据**在到达此处后即丢弃**。

## 4. 修法

### 4.1 M-12（三处，均最小改动、正交）

| # | 文件 | 改动 |
|---|---|---|
| ① | `test_upstream_p4.py` `TestConversationSeq` | setUp 中**强制重导** `api.messages`（先 `pop` 存原对象），使其绑定到打桩版 `get_db`；tearDown **换回原对象**（不泄漏打桩副本） |
| ② | `test_capability_probe.py` `_reset_db` | 清理表**补 `ai_leads`**（逐表 try 容错） |
| ③ | `test_capability_probe.py` `_ROOT` | 改 `iso._ROOT/cap_probe_<pid>` ⇒ **按进程隔离**，跨进程不再争锁 |

```python
# ① 定式：打桩 database.get_db 之后，让「导入期固化 get_db」的消费者重新绑定
self._saved_msgs = sys.modules.pop("api.messages", None)
import api.messages          # 重导 → 绑定打桩版 get_db
# tearDown:
sys.modules.pop("api.messages", None)
if self._saved_msgs is not None:
    sys.modules["api.messages"] = self._saved_msgs
```

### 4.2 H-7 样本①/②（一次性开关，**默认关闭**）

| 样本 | 开关 | 落盘 |
|---|---|---|
| ① `cmd301` | `DY_REPLAY_RECORD_301=<目录>` | `{cid-safe}_{page:03d}.bin` + `.meta.json` |
| ② `ws_frames` | `DY_REPLAY_RECORD_WS=<目录>` | `ws_frames.jsonl`（追加；`kind ∈ b64/json/other`） |

**契约遵守**：
- **默认关闭**：未设环境变量时函数**立即 return**，零副作用（实测：目录不会被创建）；
- **不影响业务**：宽 `try/except` 包裹，写盘失败只记日志；
- 挂在**数据出现处**：① 在 `resp.content` 校验通过后、解析前；② 在 `parse_ws_frame` **最前**
  —— 连被跳过的 `B64:` 帧也留证；
- **录完即撤**（不常驻）。

**冒烟实测（合成输入）**：默认关闭 → 无落盘；开启后 → 301 两页各出 `.bin/.meta.json`、
ws 出现 `['b64','json']` 两类记录。**过程中发现并修复一个真 bug**：`wp_recv.py` **缺 `import os`**
（探针抛 `NameError` 被宽 except 吞掉 ⇒ 静默不落盘）。若只做静态审查不会暴露——**必须实跑**。

**规范沉淀（可复用定式）**：

> **定式 · 打桩传导**：打桩「在某消费者**导入期**被 `from X import y` 固化」的函数时，
> 只改 `X.y` **不够**（消费者持有旧引用）。必须让消费者**重新绑定**（pop + 重新 import），
> 且**用后换回原对象**，否则打桩副本会泄漏给后续测试、制造**反向**的顺序相关失败。
>
> **定式 · 测试隔离根按进程取子目录**：任何「固定共享根」的测试模块都与并行进程争锁；
> 用 `<共享根>/<模块名>_<pid>` 即可让单进程内不干扰、跨进程不互锁。
