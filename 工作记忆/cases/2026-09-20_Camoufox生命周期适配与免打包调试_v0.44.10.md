**日期**：2026-09-20
**版本**：v0.44.10（design/better-douyin，`C:\temp\dyautodm_design`）
**提交**：`8092354`（代码 14 文件）+ `83e02df`（知识库）
**性质**：Camoufox 迁移收口 + **开发流程缺失补救**

## 一、用户报的两个症状（同一根因链）

> 「浏览器异常，双击打开浏览器只能看到弹窗没看到浏览器页面」
> 「双击打开浏览器提示占用，是无头转有头机制失效了吗」

**结论：不是原机制失效，是 Camoufox 接入未做生命周期适配。**

## 二、三个根因（逐层）

### 根因 1：BCC 7 处硬编码只认 Chromium

```python
if self._backend == "exe" and self._context is not None:
    await self._context.close()      # Camoufox("camoufox") 永不匹配
```
→ 切换可见性时**旧进程不关闭** → 继续占 `_camoufox` profile →
新有头实例 `Failed to launch the browser process` → 用户「弹窗没窗口」。

**修复**：7 处改 `in ("exe", "camoufox")`；并新增 `close_camoufox_context()`
—— **AsyncCamoufox 必须走 `__aexit__`**，只调 `context.close()` **不结束进程**。

### 根因 2：async 路径用错 API（我引入）

初版 `launch_camoufox_async` 用 `run_in_executor(None, launch_camoufox_sync)`。
Playwright 的「Sync API inside asyncio loop」检测是**进程级**的 —— 换线程无效。
→ BCC 拿不到 context，但**浏览器进程已起** → **孤儿进程**占 profile（用户见「占用」）。

**修复**：改用 `camoufox.async_api.AsyncCamoufox`（真 async）。

### 根因 3：窗口检测跨内核失效

`_window_really_visible` ① 只认 `Chrome_WidgetWin`（Firefox 是 `MozillaWindowClass`）；
② PID 只从 `self._browser` 取，而 Camoufox 返回 **BrowserContext**（`_browser=None`）
→ `pids` 空 → 直接 `return False` → **窗口明明出来却判不可见**。

**修复**：类名按内核分派 + PID 兜底（按 profile 匹配进程）。

## 三、踩到的两个环境陷阱（**重要，易复发**）

| 陷阱 | 现象 | 对策 |
|---|---|---|
| **`wmic` 已被移除** | `FileNotFoundError [WinError 2]` | 改用 `powershell Get-CimInstance Win32_Process` |
| **PowerShell↔Python 中文编码不一致** | 用中文路径匹配**命中数恒 0**（修复形同虚设） | 匹配只用 **ASCII 片段**（`member_id`、`_camoufox`） |

> 第二个陷阱尤其隐蔽：代码"看起来修好了"，但**实际从未命中**。
> 是先用**独立脚本验证命中数**才发现的 —— 印证「实机验证」不可省。

## 五、开发流程缺失（用户明确批评）

> 「这个项目我已经持续跟进2个月了，这两个月的时间居然一直没有提示我正确的debug方式」

**事实**：`package.json` **早就有** `tauri:dev` / `backend:dev`，但**没有任何文档**
提到它们是日常入口；知识库只写了「全量打包 ~12 分钟」→ 把**最慢路径当默认**。

**补救**：新增 `工作记忆/09_开发与构建流程(日常调试优先).md`，确立三模式：
| 场景 | 命令 | 耗时 |
|---|---|---|
| 改前端 | `npx tauri dev` | 秒级 HMR |
| 改后端 | `npm run backend:dev` | 存盘即重载 |
| 打包验证 | `build_all.py`（默认 debug） | ~5min |

**`tauri dev` 的唯一坑**：Tauri 只把 sidecar exe 复制到 `target/debug/`，
**不带 `_internal/`** → `Failed to load Python DLL`。
**修法**：建 junction `src-tauri/target/debug/binaries → src-tauri/binaries`。

## 六、耗时优化（用户要求）

| 优化 | 前 | 后 |
|---|---|---|
| sidecar 构建 | 串行 ~9min | **并行 ~4.6min** |
| tauri Rust | release ~7min | **debug 增量 1m35s** |
| 构建类型 | 靠人记得加参数 | **默认 debug（配置即铁律）** |

**tauri 慢的根因**（回答用户「体积最小为何最慢」）：
`Cargo.toml` 的 `[profile.release]` 开了 `codegen-units=1`（12 核只跑 1 个 rustc）
+ `lto=true`（链接阶段全部依赖 crate 重新优化）→ **产物最小 = 编译最慢**。

## 七、我的方法错误（自省，已记入前序案例）

「4 个同类打包缺陷分 4 次构建」（每次 ~15 分钟，共白等约 1 小时），
违反**迭代止损律**（同类问题第 2 次就该全链扫清）。
第 3 轮起改用「静态扫全 + 最小复现」，才刹住。用户批评原话：
> 「姥姥的，打包了1个小时，你和我说bug没排查完」
