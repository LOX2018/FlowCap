## 一、用户报障（5 条）

1. 验证码登录**只保证 WP 引擎有效性、没处理私信引擎**；
2. 扫码/验证码完成后**没及时刷新凭证有效性**，需手动点「凭证校验」；
3. 扫码更新张老师后，用短信处理小助理时**指纹浏览器弹出占用报错**；
4. 扫码**仍默认走桥通道、没走 API**，这些通道类型**应在配置中心通用里选择**；
5. 桥通道**至少要点两次「登录」才出码**，且**点 3 次后既不出码、前端也无报错**。

---

## 二、逐条定性与处置

### ① 桥「点 2 次才出码」—— 真因**不是点击定位**（三版试错后重新定性）

| 版本 | 做法 | 结果 |
|---|---|---|
| 原状 | 全页文本精确匹配 | 第 1 次点 **(1852,28)**=**顶栏**；第 2 次 (1140,626) 才命中真按钮 |
| 第 1 版 | text 只限定弹窗内 | ❌ 首轮弹窗未挂载 ⇒ 一次都没点到（超时 124s） |
| 第 2 版 | + 全页兜底排除顶栏 | ❌ 仍一次没点到（严格相等漏判「登录/注册」类文本） |
| 第 3 版 | 包含匹配 + 弹窗优先 | ❌ 点满 3 次仍不出码（33.2s） |

**迭代止损后重新取证**（决定性）：
```
cookie 数 69 · 含 sessionid · 服务端探活 ok=True uid=3887506227210423
⇒ 张老师账号【已登录】
```
⇒ **已登录账号不会挂登录弹窗、前端也不发 `get_qrcode` ⇒ 点再多也没用**。
此前全在**已登录账号**上测，故必然失败。**按钮定位不是主因。**

**最终修法**：出码前**先做服务端探活**（复用既有 `_probe_session_valid_by_cookies`）：
- 已登录 ⇒ 立即返回 `via="already-logged"`（不启页面逻辑）；
- 未登录 ⇒ 走原有点击出码。

**实测**：`7.9s · ok=True · via=already-logged · 零异常`
（修复前：点 3 次 + 等 90~120s 仍 `ok=False`）。

> **教训（重要）**：三次都栽在「同一个故障点连续局部修补」。
> 第 1 次就该先确认**被测账号的状态**是否符合前置假设。
> **判据：报障现象若与「账号状态」相关，先验证账号状态，再改代码。**

### ② 「点 3 次后没下文、前端无报错」—— 静默轮询缺陷（已修）

代码事实：3 轮重试耗尽后只 `logger.warning`，随后**静默轮询 30~90s**；
期间 `st` 无 error/stage ⇒ 前端一直转圈、**用户零反馈**。

修：已真实点击 ≥1 次但始终未出码 ⇒ **立即**如实返回失败 + 明确原因（不再空等）。
区分两种情形（避免误伤「页面自己会发接口」的正常场景）：
- 点过但未出码 ⇒ 立即失败；
- 一次都没点到（`not-found`）⇒ 保持原行为继续等。

**实测**：`33.2s` 即返回 `已真实点击「登录」3 次仍未触发 get_qrcode`（旧行为要 90~120s 才报）。

### ③ 更新后不刷新凭证有效性 —— 自动双引擎校验（已修）

新增**共用收口** `_finalize_login_and_verify()`（扫码/短信两条路径共用，防判据漂移）：
复用项目**既有权威** `acct_core.verify_account(name, timeout=8, dm_loopback=True)`
（**wp 引擎 + 私信引擎**双校验，不自创判据），结果写入 `st["verify"] / wpLevel / dmLevel / verifyAt`
⇒ **前端免手点**。校验异常**不推翻已完成的登录**（只记状态）。

### ④ 短信路径「只有 WP、没私信」—— 与扫码路径补齐对称（已修）

代码事实：`_do_sms_scan` 在 `do_sms_login` 返回后**只设 `loggedIn`**，
**既无落盘增强、也无双引擎校验**（而扫码路径有完整三段）⇒ 用户观察属实。

修：补齐 `cookie 落盘 → _enhance_from_live 增强 → _finalize_login_and_verify`，
与扫码路径**完全对称**；落盘/增强失败不推翻已登录（记 `ACC-038` 告警）。

### ⑤ 指纹浏览器「占用」报错 —— 串行残留，非并发冲突（已修）

日志实证（`10:48:29`）：
```
[ACC-025] 小助理 RPA 出码失败 → 回落「弹出浏览器用户手动」
[BCC-074] 关闭后仍残留 2 个进程占用 profile → 清扫 → 才重建成功
[10:48:54] 登录凭证已存 ✅（最终成功）
```
⇒ 无头 context 已 close 但**进程未退净**，紧接着启有头即撞占用。
修：回落切换点**显式** `ensure_profile_released(profile_dir_of(env_path))`
（复用既有能力，不自造）。

### ⑥ 通道不可配 —— 接入配置中心（子 agent 实施）

复用既有 schema 机制（`services/app_config_schema.py` → `SECTIONS["general"]` 的
`select` + `env` 范式）⇒ 前端「配置中心 → 通用配置」**自动渲染下拉框**，未自造 UI。

新增字段 `login_channel`（`env=DY_LOGIN_CHANNEL`，热生效）：
| 值 | 标注 |
|---|---|
| `bridge` | 接口桥（推荐·默认） |
| `api` | API 快速出码（**实验：仅出码快，无法完成登录**） |
| `manual` | 有头浏览器手动（兜底） |

> ⚠️ **如实标注的理由**：API 通道已被实测证明「65 秒短 TTL + P-256 公钥绑定 ⇒
> 跨会话接管不成立」，**只能快出码、完成不了登录**。
> 若与桥并列为等价选项，用户会踩回同一个坑。

读取端改为「优先 app_config，环境变量兼容回退」。新门禁
`backend/test_login_channel_config.py` **17 passed**（含负控）。

## 四、教训

1. **先验证被测对象状态，再改代码**：① 连试三版无效，根因是「被测账号已登录」——
   与代码无关。局部修补前应先证伪前提。
2. **静默等待 = 隐性故障**：② 说明「没报错」不等于「在正常处理」；
   长等待必须给中间反馈。
3. **两条路径必须对称**：④ 的成因就是扫码路径有三段收尾、短信只有一段。
   新增能力时应对照同类路径清单。
4. **如实标注能力边界**：⑥ 的 API 选项若写成等价选项，就是埋坑。
