## 一、用户需求（原话，即为设计契约真源）

> 「直播监听的配置管理修改只能对现有的配置反复覆盖，没有实现多配置标签的功能。
> 目标直播间可以管理，但别放到配置管理中，单独加一个目标直播间管理，
> 在该页面中选择是否绑定配置。」

拆成三条可判定的契约：

1. **配置管理必须支持多配置标签** —— 现状只能对「该直播间那一条」反复覆盖（
   标签键被硬约束为纯数字直播间号），无法并排放多套参数。
2. **目标直播间单独一个管理界面**，**不得**混在配置管理里。
3. **在该（目标直播间）页面中选择是否绑定配置** —— 绑定关系是「选择」，不是复制参数。

## 三、落地方案（职责分离是核心）

```
直播页（子视图三选一）
├── 监听      原页面主体
├── 目标直播间 TargetRoomPage.tsx  ─┐ 监听哪个房间 + 备注 + 是否绑定配置（只存引用）
└── 配置标签   RoomConfigPage.tsx   ─┘ 参数唯一可写入口（上限/间隔/抖动/词库/连麦/重扫/账号）
```

| 关注点 | 归属 | 存储 |
|---|---|---|
| 监听哪个直播间 / 备注 / 启用 | `api/target_rooms.py` | kv `live_target_rooms` |
| 绑定哪条配置（`tag_id`） | 同上（**只存引用**） | 同上 |
| 参数（全部） | `api/live_config.py` | kv `live_room_configs`（沿用旧 key，零迁移） |

**三条铁律**（写进代码 docstring + 测试）：
1. 目标直播间侧**不存任何参数**（只有 `tag_id` 引用）。
2. **解绑 ≠ 删除**：`tag_id=None` 只清引用；删标签由 `live_config` 负责，
   并**反向解绑**引用它的目标直播间（目标记录保留）。
3. **绑定目标必须存在**：`tag_id` 非空时校验 `live_config.get_tag()`，防悬空引用。

### 关键实现点

- **标签键解禁**：旧 `_norm_room_id` 只接受纯数字 → **改为 `normalize_tag_key`**，
  接受「纯数字 / 直播间 URL / 40 字内名称」，空键生成 `lc_<epoch>`。
  这是「多配置标签」的前提（旧实现把非数字输入一律拒绝）。
- **标签体加 `id`，`room_id` 降为兼容别名**（旧前端/脚本读 `room_id`，不破坏）。
- **`live_url` 改为可选**：留空表示「按目标直播间推导」；数字型标签 id 仍自动推导
  （存量数据行为不变）。不再强制把非数字标签键拼成 `https://live.douyin.com/<键>`。
- **端点双前缀挂同一 router**：规范 `/api/live/config-tags` + 兼容 `/api/live/room-configs`
  （旧前端、既有验证脚本、任务中心「复用」入口全部不破，且**同一份存储，不存在第二份**）。
- **`restart_core` 抽成共享函数**，`/{tag_id}/restart` 与 `/{tag_id}/apply` 复用。

## 五、踩坑记录（本轮真实教训）

### 坑 1：验证脚本裸发中文 URL → uvicorn `UnicodeEncodeError` → 500

**症状**：`DELETE /api/live/config-tags/保守-9047` 返回
`{"error":"UnicodeEncodeError: 'ascii' codec can't encode characters..."}`，
**看起来像后端 bug**（代码审查也看不出问题）。

**真因**：RFC 3986 要求 HTTP 请求目标为 ASCII。我在 `urllib.request` 里**直接拼了中文路径**
→ uvicorn 写响应头时编码失败。**前端 `encodeURIComponent` 走的正是编码后路径**，
所以浏览器侧从来不会踩这个坑。

**修法**：`urllib.parse.quote(path, safe="/?&=:@")`；并**补一条断言固化**：
中文标签 id 的 create / restart / delete 必须全通（防止后人再写出裸发中文的探针）。

**教训**：探针报错先分清「被测系统的缺陷」还是「探针自身的协议层缺陷」——
后者会伪造出一个不存在的后端 bug。

### 坑 2：预览 harness 的 `push` 是 `console.log`，不渲染 toast

把「点重启后有反馈」断言成「页面文字变化」→ 恒失败。
且本环境 Playwright 的 `page.on("console")` **捕获不到页面 JS 日志**
（实测注入自己的探针也不出现）。正解：`page.evaluate` 里包装 `console.log`
收集到 `window.__pushed`，再读回 —— 这才拿到组件真实产出的文案。

### 坑 3：新组件用真实 `api` 单例，预览 harness 的 mock props 不生效

页面渲染空白、B2/B7/B9 全失败。真因不是页面缺陷：`RoomConfigPage` / `TargetRoomPage`
（与它们的前身弹窗一致）import 的是 `api/client.ts` 的真实单例，不是 `props.api`。
修法：Playwright `page.route("**/api/live/**")` **按真实契约形状回 fulfill** ——
顺带把「前端消费的字段形状 == 后端契约」也验了。

### 坑 4（流程）：验证用的临时环境残留必须清理

前几次失败运行留下的探针标签（`保守-9047` / `保守-9083`）留在了**用户实际使用的**
design 环境 DB 里。处置：**先 `shutil.copy2` 备份 DB → 逐条精确 key 匹配删除 →
`assert 用户真实配置 992931212705 仍在`**。禁 LIKE/模糊删。
