**日期**：2026-09-20
**版本**：v0.44.2 → v0.44.7（连续 5 轮构建）
**性质**：**方法论错误事故**（非单点 bug）—— 用户批评："打包了1个小时，你和我说bug没排查完"

## 一、用户的批评（原话，必须原样留存）

> 「姥姥的，打包了1个小时，你和我说bug没排查完」

**批评成立。** 这不是"运气不好遇到连环 bug"，而是**我的排查方法错误**。

## 二、我的错误（逐条对照铁律）

| 我实际做的 | 正确做法（铁律要求） | 违反的律条 |
|---|---|---|
| 改一个 → 等 15 分钟 → 发现还缺 → 再改 | **同一类问题第 2 次就该停下来全链扫清** | **迭代止损律** |
| 逐个包试（orjson → apify → camoufox → language_tags → playwright） | 一次枚举**整条依赖链**的非 .py 资源 | 执行链可追溯律 |
| 到第 3 轮才改用"最小复现先验证" | 第 1 轮就该用 | （自省） |
| 没有机械自检，全靠人工遍历 | 应当写自检脚本挂进流程 | 知识新鲜度律（应固化） |

**总代价**：5 轮构建 × ~15 分钟 = **约 1 小时 15 分白等**。

## 三、6 个缺陷（全是"打包态暴露、源码态全绿"）

| # | 缺失项 | 类型 | 报错 |
|---|---|---|---|
| 1 | `orjson.cp314-win_amd64.pyd` | 原生扩展 | `No module named 'orjson.orjson'` |
| 2 | `binaries/_internal` 陈旧 6 天不刷新 | **脚本 bug** | 新增依赖永远进不去（无声） |
| 3 | `apify_fingerprint_datapoints/data/*.zip` | 数据文件 | `FileNotFoundError` |
| 4 | `language_tags/data/json/*.json` | 数据文件（**传递依赖**） | `FileNotFoundError` |
| 5 | `camoufox/*.json`（预设） | 数据文件 | 隐式 |
| 6 | **`playwright/driver/node.exe`** | **Node driver** | **`[WinError 2]`** |

## 四、根因分析（为何源码态发现不了）

| 层 | 源码态 | 打包态 |
|---|---|---|
| 模块解析 | `sys.path` 直指 site-packages | 仅 PYZ 归档 + `_internal` |
| 原生扩展 | 按后缀直接加载 | 必须显式收集 |
| 数据文件 | `Path(__file__).parent/data` | `__file__` 指向归档内，**文件不在** |
| **Node driver** | 直接调 site-packages 里的 `node.exe` | **`subprocess` 找不到 → WinError 2** |
| 传递依赖 | import 时自动解析 | PyInstaller 静态分析**看不到运行时触发的 import** |

## 五、修复

| # | 文件 | 改动 |
|---|---|---|
| 1 | `scripts/build_sidecar.py` | `--collect-all` 覆盖 8 个包（orjson / maxminddb / camoufox / browserforge / apify_fingerprint_datapoints / language_tags / **playwright** / patchright + 3 个 py.typed） |
| 2 | `scripts/build_sidecar.py` | **`_dedupe_internal` 无条件刷新共享 `_internal`**（根治陈旧缓存） |
| 3 | **`scripts/diag/check_packed_resources.py`（新增）** | **机械自检**：比对"源码态每包的非 .py 资源 vs 打包产物"，列出缺失清单 |
| 4 | `scripts/build_sidecar.py` | 打包末尾**自动调用该自检**并打印结果 |

### 为何自检是根治手段（而非又一层补丁）

人工遍历依赖链**必然漏传递依赖**（`language_tags` 不在 `ua_parser` 目录内，
是运行时才 import 的）。自检脚本改为**从"源码态能 import 的模块"反推**，
把"人记"变成"机械判"——**同类事故不可能再靠人发现**。

## 六、验证

- 自检脚本对 0.44.6 产物：**缺 119 个**（含 `playwright/driver/node.exe`）→ 精准命中 WinError 2 根因。
- 自检脚本对 0.44.7 共享 `_internal`：**缺 4 个**（仅 `py.typed` 空标记），
  说明 playwright / camoufox / apify / language_tags / orjson / maxminddb **全部到位**。

## 七、教训（写给未来的自己）

1. **"改一个等一轮"是沉没成本陷阱** —— 同类问题必须一次扫清全链再动手。
2. **最便宜的验证优先**：最小复现（1 分钟）永远先于全量构建（15 分钟）。
3. **把教训变成机械门禁**，不要写成注释就当记住了 —— 本次已落地自检脚本。
4. **"禁止静默回退"直接创造了价值**：正是因为 Camoufox 失败不再降级 Chromium，
   这 6 个缺陷才被迫暴露；否则全会藏在"浏览器能用"的假象下。

## 八、后续补充（2026-09-26，v0.45.12 —— 同主题新增两类"打包态陷阱"）

> 本节由 [ADR-016 D3-A 凭证根因修复] 的打包过程产生。**同属"源码态全绿、打包态失效"家族**，
> 但形态不同：前者是**资源不在包里**，本节是**环境/形态选错**。

### 陷阱 A：解释器环境选错（`sys.executable` 反噬）

**现象**：
```
C:\...\hermes\hermes-agent\venv\Scripts\python.exe: No module named PyInstaller
  ×3（三份 sidecar 各报一次）
→ RuntimeError: 并行构建存在失败项
```

**根因**：`build_sidecar.py` 用 `sys.executable` 选解释器。从 **Hermes 会话**直接跑
`python scripts/build_sidecar.py`，`python` 解析到 **hermes-agent venv**（无 PyInstaller），
而不是项目环境。

**为什么难定位**：错误被埋在**约 200 行** PyInstaller 命令行参数里（`--collect-all` 长列表），
三次失败**内容相同**、只在末尾 `returned non-zero exit status 1`，真正的
`No module named PyInstaller` 在**最前面**、易被 `tail` 掉。

**本机正确环境**（README.md §环境已记载，Store 别名不可用）：
```
C:\Users\LOX\AppData\Local\Programs\Python\Python314\python.exe   （PyInstaller 6.22.0）
```

**已机械化的修复**：`build_sidecar.py::main()` 开头加**前置环境门禁** ——
`import PyInstaller` 失败则打印**当前解释器 + 正确路径 + 可复制的调用命令**并 `EXIT=2`。
**负控实测**：用 Hermes venv 调用 → 立刻给出上述提示，不再让 PyInstaller 失败三次。

### 陷阱 B：构建形态不一致（`--onefile` vs `--onedir`）

**现象**：用 `--onefile` 打包成功，但部署目录是 **onedir 共享 `_internal`** 形态
（`binaries/_internal/` + 三 exe 平铺）⇒ 形态不匹配，部署会缺依赖。

**判据**：`scripts/deploy.py` 显式检测两种形态：
```
A) 共享形态（默认）：binaries/_internal + binaries/<full>.exe 平铺
B) 传统形态（旧）  ：binaries/<full>/（目录内含 exe + _internal）
```
若检测不到 `_internal` 会打印 `→ 请执行完整 python scripts/build_sidecar.py --onedir`

**教训**：**打包前先确认目标形态**（看 `deploy.py` 期望 / 上次部署目录结构），
不要凭记忆选 `--onefile`/`--onedir`。当前项目约定是 **`--onedir`**。

### 本节的正面收获：登记 ≠ 进包（再次验证）

新增 `services.kernel_truth` 时已在 `build_sidecar.py` 登记 `--hidden-import`，
但**登记只表示"告诉了 PyInstaller"，不等于"真进了产物"**。故打包后**必须**用
`scripts/diag/list_archive_modules.py` 查真产物：

```
$ python scripts/diag/list_archive_modules.py src-tauri/binaries/dyautodm-backend-*.exe | grep kernel_truth
    services.kernel_truth      ← ✅ 进了包（3635 个模块中）
```

**这与 §五 的自检脚本同一思路**：**唯一权威是产物本身**，不是构建脚本的入参。
