## 3. 执行链溯源（Step 3）

```
用户改策略 → 无入口 → 只能改代码
   ↓ 实施：新增 SECTIONS["live_orchestration"]（7 字段）
GET /api/settings → ac.get_all() + ac.schema()   ← 后端确已下发
   ↓ 但前端
settings-page.tsx: {section==="live" && <UnifiedConfigSection onlySections={["live"]}/>}
   ↑ **显式白名单**：只渲染白名单内的分区
   ↓ ⇒ 新分区无人索取 → UI 仍看不到 ← **偏差点在此**
```

## 4. 根因（Step 4）

**不是后端缺陷，是 ADR 的一句断言与代码结构不符**：ADR-002 §3.5 写「新增参数只加一项，
前端零改动」。核对后：`UnifiedConfigSection` 自身确为 schema 驱动，**但其调用方
`settings-page.tsx` 对每个 tab 用显式白名单 `onlySections`** ⇒
- 新增**字段** → 真·零前端改动 ✓
- 新增**分区** → 必须把分区名登记进目标 tab 的 `onlySections`（一行）✗（原断言漏了这一层）

## 7. 通用判据（可迁移，供后续复用）

1. **「schema 驱动 = 前端零改动」只在「新增字段」维度成立。** 只要页面用**显式白名单/
   枚举**取分区（`onlySections`/tab 表），**新增分区就必须登记**。判断方法：
   先读**调用方**，不要只读被调用组件 —— 我第一版计划卡正是只读了 `UnifiedConfigSection`。
2. **「接口返回 ok:true」不等于「值被采纳」。** 实测教训：body 形状写错（把
   `{"sections":{...}}` 写成 `{section:{...}}`）时，**pydantic 默认值把非法 body 静默变空**，
   接口照样 `200 ok:true`，配置**未变**。⇒ **配置类写操作必须独立回读验值**，
   不能以 `ok:true` 为准（本项目的「假成功」同族）。
3. **配置面必须先落地、后接线消费时，label 明确标「待接线」**，避免「改了以为生效」。
4. **本轮未做**（沿用既有登记，勿重复建设）：ANON-XXX 匿名模式、§5.5 沉淀池 + 轮转消费点、
   §5.6 前端多任务卡片。

### 🔴 本轮又踩一次同型坑（写进通用判据 #2 的实证）

手工 curl 验「保存」时，我一开始把 body 写成 `{"live_orchestration":{...}}`，
而 API 契约是 `{"sections":{...}}` —— **接口返回 `200 ok:true`，值却完全没变**。
根因：`SaveBody.sections` 有默认值 `{}`，pydantic 把不含 `sections` 的 body 静默变空。
⇒ **佐证判据 #2：配置类写操作必须独立回读验值，「ok:true」不算数。**
（应用自身无此缺陷：`client.ts:1282` 正确发送 `{ sections }`，已核对。）
