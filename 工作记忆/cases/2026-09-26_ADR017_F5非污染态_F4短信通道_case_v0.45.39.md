## 2. 关键判据（⚠️ 差点踩坑 —— 差点自造错判据）

**`dy_apis/login_api.py::_cookie_is_polluted` 已于 2026-08-17 被明确废弃**：
基于 cookie 格式的污染判定（`verify_` 前缀 / 位数 / 前缀）
**会误伤抖音新版合法凭证**（实测：`s_v_web_id` 正常值就是 `verify_xxx` 开头），
故一律放行；**污染由页面风控监测兜底**。

⇒ 若照 ADR 字面实现「cookie 污染检测」，就是**复活一个已被实测否决的判据**。
**实际采用的判据**：
1. F6 页面风控曾命中 ⇒ **拒写**（这才是真正的污染信号）
2. 关键 cookie（sessionid/sid_tt）缺失 ⇒ **告警但不阻断**（由后续服务端探活兜底）
3. 复用既有 `login_capture`（snapshot_old_env + analyze_login_capture）产出旧→新差异报告（可追溯）

**教训**：实现前必须先看**既有实现里已写明的废弃说明**，不能只看 ADR 的验收标题。

## 3. F4 通道设计

```
前端 POST /{name}/sms-login {phone}
   → 后台线程 _do_sms_scan → do_sms_login(code_provider=...)
        └─ code_provider 阻塞在 threading.Event（300s）
前端轮询 /scan-status → needCode=true → 展示输入框
前端 POST /{name}/sms-code {code} → 写 box + event.set()
   → provider 取到验证码 → RPA 填码登录
超时未提交 ⇒ provider 返回 "" ⇒ do_sms_login 按失败处理（不死锁）
```

新增端点：
- `POST /{name}/sms-login` —— 启动短信登录
- `POST /{name}/sms-code` —— 提交验证码
- `GET /qr-image?path=...` —— 下发二维码 PNG（**三重校验**：临时目录白名单 + 目录穿越防护 + `rpa_scan_` 前缀 + 仅 PNG）

`/scan-status` 增字段：`stage` / `needCode` / `rejected` / `captureReport`。

## 5. 🔴 上游情报（本次最有价值产出 · 已订正进 ADR-017 §8.1·乙）

调研 `mkuko52/douyin_spider`（4★，`license=None`，README 明令禁止商用）：

| 能力 | 上游现状 |
|---|---|
| `x-tt-session-dtrait`（820B） | ✅ **已还原**（RSA-2048 + AES-128-CBC） |
| `a_bogus`（真浏览器） | ✅ 实测 `message:success` |
| `a_bogus`（离线 nv8） | ❌ 服务端 `2156` |
| **业务层** | ⚠️ **被 `bd_ticket_guard` 拦（`2156`）** |

**⇒ ADR-017 §8.1「短信 API 禁用」结论不变，但依据更换**：
不再是「dtrait 生成不了」，而是「**即使 dtrait + a_bogus 全还原，业务层仍被
`bd_ticket_guard` 拦在 2156**」。

**⇒ 反向印证 RPA 路线正确**：真浏览器天然携带 dtrait 与 bd_ticket_guard 所需的
全部运行时状态，**无需逆向任何签名**。

**该上游不可采用**（无协议 + 禁商用），**只取情报，未引任何代码**。
