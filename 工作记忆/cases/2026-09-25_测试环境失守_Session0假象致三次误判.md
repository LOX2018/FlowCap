## 一、现象（用户视角的困惑）

用户报告："BCC 有时能开有头、有时不能"；且**明确指出**：
> "当时确实出现了这种情况，但是今天晚上实测的时候又恢复正常，
>  而反馈给你之后，你自己测试每次都失败"

**这句话是真正的线索**：用户环境正常，我的测试 100% 失败 ⇒ **失败的是我的测试环境，不是软件**。
我当时没有立刻据此怀疑测试有效性，而是继续在被测对象上找原因 —— 这是本次事故的核心失误。

## 二、我连续给出的三个错误结论（全部撤回）

| # | 错误结论 | 依据的实验 | 为何错 |
|---|---|---|---|
| 1 | "Camoufox 内核崩溃，考虑换浏览器" | v1（手工启动） | 给所有组都加了 `-juggler-pipe`；且未设 `DY_APP_ROOT` |
| 2 | "真凶是 `-foreground`" | v3/v6 | v7 剔除 `-foreground` 后**仍崩**，证伪 |
| 3 | "图形栈 / GPU 问题" | v8（4 组环境变量） | 全崩，假设未获支持 |

**共同根因**：所有实验都跑在 **Windows Session 0（服务会话，无桌面）**。
有头浏览器在 Session 0 创建窗口 → 必然 `0xC0000005` 崩溃。
⇒ **测的是"无桌面环境下开有头"，与用户场景毫无关系。**

## 三、真实根因（决定性证据）

```
port 8000  backend  pid=14852  sessionId=1     ← 用户双击启动（部署路径）
port 10042 张老师BCC pid=17176  sessionId=1     ← 有桌面 → 有头正常 ✅
port 11231 小助理BCC pid=2680   sessionId=0     ← 无桌面 → 有头必崩 ❌
```

**同一个 backend 的 spawn 结果落在了不同会话**。而 Session 0 那个是我违规用 terminal
直启 backend 造成的 —— **小助理的"唤醒异常"是我制造的**，不是产品缺陷。

对照：用户全程使用**部署路径双击启动**（Session 1），所以他那边"又恢复正常"。

## 四、违反的铁律（逐条对应）

| 铁律 | 出处 | 我的违反 |
|---|---|---|
| **部署与源码环境分离** | 用户铁律（本条由用户明确指出） | 用 terminal 直启部署环境 backend；测试脚本大多未设 `DY_APP_ROOT` |
| **本分支实测须指向本分支环境** | `dyautodm-dev-guards` §三·0 | v1/v3/v4/v7/v8 用系统 temp 下临时 profile 瞎测 |
| **实机验证须在真实运行环境** | 用户铁律（Live-Instance Verification） | 在 Session 0 测 GUI 功能，环境本身无效 |

`cases/2026-09-17` 开篇的预言本次再次应验：
> **规则早已存在却仍被违反**，问题不在「不知道」，而在「长会话中缺乏当场自查」。

## 五、可执行判据（动手前逐条过，本次血泪版）

```bash
# 1) 被测进程在哪个 Windows 会话？（GUI 功能必须 Session >= 1）
powershell -NoProfile -Command "Get-Process -Name '<目标>' | Select-Object Id,SessionId"
#   → SessionId == 0 ⇒ 该环境测不了有头/窗口，任何"崩溃"结论都是假象

# 2) 我是否在用 terminal 直启部署环境进程？
#   → 是 ⇒ 立即停手。终端进程在 Session 0，会污染 spawn 出的子进程

# 3) 我的测试脚本设了 DY_APP_ROOT 吗？指向本分支环境吗？
#   → 未设或指向 FORBIDDEN_ROOTS ⇒ 立即停手

# 4) 用户说"我这边正常、你那边必失败"时
#   → 【第一优先级】怀疑测试环境有效性，而不是被测对象
```

**最优解（沿用 09-17 案例结论）**：脚本自设 `os.environ["DY_APP_ROOT"]`，
永不依赖调用方 export；GUI 相关验证一律要求用户在其桌面会话内执行。

## 七、仍然成立的两个真缺陷（与本次事故无关，未受影响）

1. **假阳性 `/show` 返回 `ok:True`** —— 异步受理即报成功，实际失败只进日志，
   前端无从得知 ⇒ 用户被"提示成功却没窗口"误导。**真缺陷，需修**。
2. **语义歧义：观测态缺标记** —— `/open-browser`（用户双击=观测）与引擎校验共用
   `/show`，无字段区分发起方；项目已有"有头=观测态"契约
   （`api/accounts.py:632`）但仅在打开前门禁，**打开后无标记**，自愈路径可能误关。
   用户 2026-09-25 指出。**真缺陷，需修**。

## 八、新增环境事实（值得长期记住）

> **BCC 必须在 Session ≥ 1 才能使用有头模式。**
> 若 backend 被任何服务 / 计划任务 / 终端方式拉起（落在 Session 0），
> 有头功能会**静默失效**（崩溃码 0xC0000005），而常驻无头功能不受影响。
> ⇒ 这是真实的部署陷阱：症状表现为"某账号有头打不开"，实为会话归属错误。
