## 一、设计意图（Step 1）

| 项 | 内容 |
|---|---|
| **模块** | 内容浏览页 —— 推荐流（feed）+ 站内通知（notice）两个 tab |
| **设计契约** | ① `/feed`：用户点一次即得**一屏可播/可展示**的作品；「换一批」应能取到**新批次**。<br>② `/notice/list`：每条通知都给「**谁 + 做了什么**」的可读文案。<br>③ **禁假成功铁律**：不得把「没取到/取到的是非作品卡」伪装成「暂无内容」或占位噪音。 |
| **期望行为** | 推荐流不含不可播占位；站内通知条条可读（新粉丝/评论/点赞各自取对应子对象） |
| **假设** | ① 上游 `aweme_list` 全是视频作品（**被证伪**：混入直播推荐卡）。<br>② 通知文案只在 `digg.aweme.desc`（**被证伪**：仅占 41 类型）。 |

## 二、观察到的偏差（Step 2）

用户原话：
> 「内容页面的推荐流有空视频噪音，且只有 6 个，并没有刷新按钮；站内通知全是噪音」

实测现象（复现脚本见 §六）：
- 推荐流：单批仅 **6 条**，其中混有**无封面 / 0 赞 / 0 评 / 无描述**的空白卡。
- 推荐流：页面**无任何刷新/换一批入口**。
- 站内通知：47 条中 **34 条显示「（无内容）」**（新粉丝 24 + 评论 10）。

## 三、执行链追溯（Step 3）

### ① 推荐流「只有 6 条 + 无刷新」

```
前端 feedQ → platformApi.feed(account, 20)          ← 不带 refresh_index
  └─► POST /api/platform/feed
        └─► get_feed: api.get_feed(auth, count, "2")   ← ★ refresh_index 被硬编码为 "2"
              └─► GET /aweme/v1/web/tab/feed/
                    └─► 单次返回 2~6 条（与 count 无关），且重复调同一 ri 结果会变
```

**实测富证据**（真实账号，2026-09-30）：

| refresh_index | 实得条数 | 去重累计 |
|---|---|---|
| 1 | 2 | 2 |
| 2 | 6 | 8 |
| 3 | 6 | 14 |
| … | … | … |
| 12 | 6 | **58** |

⇒ 不同 `refresh_index` 返回**互不重复**的新批次（12 批共 58 条、**0 重复**）；
`refresh_index` 是「**换一批**旋钮」，且单次条数不受 `count` 控制（`count=5/10/20/50` 实测 5/2/6/6）。
**原实现把它写死为 `"2"`** ⇒ 前端每次都是同一批、无入口换新。

### ② 推荐流「空视频噪音」

```
上游 aweme_list[i]  ← 实测混入 aweme_type=101 的「直播推荐卡」
  ├─ 顶层带 cell_room（含 stream_url / 直播间标题）
  └─ **没有 video 子树**（keys=48，无关 video）
        └─► _pick_aweme 只读 video.cover → cover=""
              └─► 前端 AwemeCard：无封面 / ♥0 / 💬0 / （无描述）
```

**实测取证**：`aweme_type=4`（1 条）与 `aweme_type=101`（1 条）均属非标准视频；
后者 48 键、含 `cell_room.rawdata`（直播间 JSON），但 `video` 缺失。

### ③ 站内通知「全是噪音」

```
POST /api/platform/notice/list
  └─► get_notice_list → notice_list_v2（19~47 条，type ∈ {31,33,41}）
        └─► 逐条只读 digg.aweme.desc                     ← ★ 仅覆盖 type=41
              └─► type=33（新粉丝）/ type=31（评论）content 恒 ""
                    └─► 前端 {n.content || "（无内容）"} → 占位噪音
```

**实测取证**（type 分布与文案真实位置）：

| type | 语义（实测） | 文案位置 | 条数占比 |
|---|---|---|---|
| 33 | 新粉丝（`from_user`，`follower_status=1`） | `follow.from_user.nickname` | 24/47 |
| 31 | 评论 | `comment.comment.text` + `...user.nickname` | 10/47 |
| 41 | 点赞 | `digg.aweme.desc` + `...author.nickname` | 13/47 |

## 四、根本原因分析（Step 4）

1. **推荐流·换一批被写死**：`get_feed` 路由把上游签名参数 `refresh_index` 硬编码为
   `"2"`，且 `FeedReq` **未暴露**该字段 ⇒ 前端无旋钮可调。
2. **推荐流·噪音未过滤**：上游 `aweme_list` **不是纯视频列表**（混入直播卡），
   而 `_pick_aweme` 假定 `video.cover` 必然存在 ⇒ 缺视频的卡退化为空占位。
3. **通知·文案路径不全**：2026-09-14 的结论「文案在 `digg.aweme.desc`」**只对 type=41 成立**；
   type=33/31 各有自己的子对象，旧实现未覆盖 ⇒ 34/47 条为空。

**架构层观察（可迁移）**：三处同型 —— **上游返回是「多态信封」（不同 type/形态载荷不同），
而适配层用「单一固定路径」解包** ⇒ 非主流形态一律退化为空。适配多态信封必须**按形态分派**，
不能只按一个典型样本假设结构。

### 上游情报核实（Open-Source Provenance Law）

| 项 | 结果 |
|---|---|
| 上游 | `cv-cat/DouYin_Spider`（`vendor/douyin_spider_upstream/dy_apis/douyin_api.py`） |
| `get_feed` / `get_notice_list` | 上游**只做原始请求、不裁剪** ⇒ 缺陷在**本项目适配层**，非上游 |
| 本项目拆分版 | `backend/dy_apis/client_video.py:get_feed` 同样透传原始 `aweme_list` |
| 结论 | 排除「接口用错」；根因锁定在 `api/platform.py` 的解包/裁剪策略 |

## 五、修复方案

| 位置 | 改动 |
|---|---|
| `FeedReq` | 新增 `refresh_index: int = 2`（透传上游换一批旋钮） |
| `get_feed` | ① 透传 `refresh_index`；② 按 payload 事实过滤不可播条目；③ **如实上报** `filtered` |
| `_is_playable`（新） | 有 `play_addr.url_list` / `bit_rate` / `images` ⇒ 可播；直播卡/空壳 ⇒ 剔除 |
| `_notice_type_label`（新） | 31/33/41 → 评论/新粉丝/点赞；未知原样回显 |
| `_notice_actor_text`（新） | 按 type 从**对应子对象**取文案；上游缺文本时给**方向中立**兜底 |
| `notice_list` | 用上述两函数产 `type`/`content`/`nickname` |
| 前端 `platform.ts` | `feed()` 增 `refreshIndex` 参数；`NoticeItem` 补 `nickname?` |
| 前端 `platform-page.tsx` | 推荐流新增「**换一批**」按钮（`refreshIdx` 递增）+ 本批条数/已过滤提示 |

**「禁假成功」落实**：过滤**不静默**（`filtered` 计数上报并在 UI 提示）；
整批都是噪音时**保留原批**而非伪造成空；上游无文本时给**中立兜底**（不编造方向）。

## 七、结论与可迁移判据

1. **上游「换一批/翻页」参数一旦被适配层写死，用户会永久看到同一批** ——
   凡上游签名含 `refresh_index`/`cursor`/`offset` 之类旋钮，适配层**必须透传**，
   不得为「先跑通」而写死默认值。
2. **上游列表是「多态信封」**：同一 `aweme_list` 可能混入直播卡/广告/图文。
   适配层必须**按 payload 事实判可播性**（play_addr / images），**不能假设** video 必存在；
   也不要靠猜 magic `aweme_type` 号（实测既有 4 又有 101）。
3. **通知类接口的文案字段随 `type` 变化**：必须**按 type 分派**取子对象，
   只按一个样本写单一路径必然漏掉大多数（本案漏了 34/47）。
4. **过滤必须留痕**：剔除噪音要**如实上报计数**并在 UI 提示（禁假成功）；
   过滤后为空时应保留原批/明示原因，绝不静默呈现成「暂无内容」。
5. **上游确实无文本时给「方向中立」兜底**，不得编造方向性语义（如「赞了你」），
   方向判据须有实测事实支撑（本案 type=33 的 `follower_status=1` 才证「对方关注了我」）。
