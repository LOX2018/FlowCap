# 案例：验证产能瓶颈 → 离线回放层（2026-09-22）

> **类型**：体系级（非单点缺陷）　**产物**：`backend/replay/`　**分层政策**：`01_铁律与红线.md` D-03
> **范围**：本项目验证体系；**不涉及**任何抖音侧契约变更（回放层不主张契约有效性）

---

## 一、设计意图（Step 1）

| 项 | 内容 |
|---|---|
| 模块 | 验证/回归体系（`backend/test_*.py` + `scripts/diag/*` + 探针判据） |
| 设计契约 | 回归验证应能**在改动后快速判定"有没有把已修好的东西改坏"** |
| 预期行为 | 改一行 → 秒级/分钟级得到"回归/未回归"的判定；判定不依赖外部世界的当前状态 |
| 不变式 | ① 判定必须可重复；② 判定不得污染真实数据；③ 真机资源只用于"确认世界变没变" |
| 设计假设（**后被证伪**） | "每个验证用例都需要真机" —— 隐含假设"无法冻结外部输入" |

## 二、观测偏差（Step 2）

| 项 | 实测 |
|---|---|
| 偏差类型 | **资源（验证吞吐）** |
| 现象 | 功能开发推进缓慢；台账 H 级多项长期未闭环；多会话无法并行验证 |
| 客观读数 | 近 38 小时 42 笔提交中 `fix` 13 笔，其中 **6 笔（46%）在修验证层本身**；`docs:代码 = 23:17`；`v0.44.24→v0.44.33` 2 天 9 个 patch 节点 |

## 三、链路溯源（Step 3）

```
真机验证（唯一验收面）
  ← 三条风控铁律钉死：单 profile / 单 8000 端口 / 单数据根 C:\temp\dyautodm_design
  ← 于是验证产能 ≡ 1（物理上不可并发）
  ← 于是所有回归都排队占用真机
  ← 于是"验证器自身有 bug"时，只能在真机上发现（分钟级、串行、含风控面）
  ← 于是修验证器又产生新提交、又升版、又触发审计红线
  ← 终态：46% 的 fix 花在验证层；docs 与代码开支倒挂
```

## 四、根因分析（Step 4）

**为什么链路断在"真机验证"这一点**：因为**测试金字塔倒置** ——
回归验证被实现为"端到端跑真机"，而端到端**必然**依赖外部世界的当前状态。

判据（本项目自证）：`backend/test_*.py` 共 38 个文件，**只有 5 个**触碰真 BCC/网络。
⇒ "用替身"这条路在本项目中**早已走通**，只是覆盖面不足、且端到端用例被留在了真机上。

**关键区分（世界变了 vs 自家写错了）**：
- 需要判断"**世界变了没有**"（接口/字段/签名）→ **必须实拉**，不可回放；
- 需要判断"**自家代码回归了没有**" → 世界未变，跑回放即可。
两条此前被混为一谈，全部倒向真机。

## 五、修复与实机验证（Step 5）

### 5.4 顺带闭环的陈旧验收（重要）

`backend/scripts/verify_capture_parse.py` 的 **C 段（功能验收）长期是空的**：
它依赖 `<DESIGN_ROOT>/_repro352_fresh/init_live.bin`，该文件随 2026-09-20 测试根删除而消失
⇒ 每次运行都 `[SKIP]` + `check("C0 首包样本存在", False)`。
**即"首包解析修复已验收"从未真正执行过**（A/B 静态断言有效，功能段为空）。
现：C 段明确标注为"空转、不计入通过项"，并由回放用例承接（跑在冻结样本上，真正执行）。

## 六、为什么这层不会退化成"用旧数据骗自己"

四条硬约束（全部有机械门禁）：

1. **不可变**：样本 sha256 进清单，加载即校验；篡改一律拒绝（G3 已实证会拒绝）。
2. **单一写通道**：只能经 `recorder` 落盘（自动登记 sha256/来源/日期），不允许手改样本。
3. **边界显式**：回放**不主张**"抖音契约仍有效"；新契约首次确认**仍须实拉**（D-03）。
4. **敏感性已证**：注入三类历史回归全部变红（未证明会拒绝的门禁 = 假门禁）。

## 七、遗留与未决

| 项 | 状态 |
|---|---|
| 回放样本覆盖 | 现仅 1 个（`init_packet`）。`cmd301` 响应、WS 帧、IndexedDB 昵称表、DOM 会话列表等**尚未录制** |
| 录制成本 | 每个样本需**一次**真机实拉（一次性），之后永久可回放 |
| 未验证项 | 回放层**未**在"真实契约变更"场景下演练过（即：世界真变了时，实拉流程是否顺畅）——**诚实标注为未核验** |
| 审计红线 | H-6 仍挂账；D-02 已把触发口径改为只计产品行为节点 |

## 八、教训（可迁移判据）

1. **验证成本 ∝ 产品复杂度**，除非把外部输入冻结。冻结输入的投入是**一次性**的，收益是**永久**的。
2. **"需要真机"往往不是事实，而是"没有录制通道"的后果**。先问"这个输入能否冻结成一个文件"。
3. **空转的验收比没有验收更危险**：它让"已验收"成为一句无根据的话（本案例中它成立了约 7 天）。
4. **门禁必须证明它会拒绝**（本项目 §四·丙 的教训在本案例再次适用）。
5. **策略冲突要显式取舍，不能靠执行硬扛**：`每改必升 0.01` × `3 节点强制审计` 在数学上互斥，
   挂账 8 个节点即为代价。修法是分流（D-02），不是更努力地执行。
6. **并发下的"逐文件 add"仍可能夹带**：本次 `git add <逐文件>` 时，台账文件内含
   另一会话（HC-02）刚写入的 T-01 冻结段 —— 逐文件粒度**保护了目录**，但**保护不了同一文件内的他人改动**。
   ⇒ 判据升级：`M` 状态文件在 add 前，先 `git diff -- <file>` 逐块确认**哪些 hunk 是自己的**；
   含他 hunk 时，要么等其作者提交，要么在提交信息里显式声明"本笔含他人 hunk + 内容未改动"。
