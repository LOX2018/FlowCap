## 一、缺陷 A：AI 回复了历史消息（用户报障②）

### 1.1 设计意图（应然）

`工作记忆/13_业务域_AI与通知.md` §四 铁律原文：

> **水位防重**：kv `ai_reply_last_msg_id` 记最后处理的消息 id；关闭期间
> 每 tick 推进水位 → **重新开启绝不回历史消息**。

即：AI 只应处理**开启监听之后**新落库的消息。

### 1.2 实测偏离（E4 决定性）

`ai_probe.log` 里进入决策链的 trace（= 消息 id）序列：

```
10:19:06  13598   ← 09-28 18:46「图我看到了哈，稍等我看看再回你」
10:19:26  13599   ← 09-28 18:46
10:19:46  13600   ← 09-28 18:47
10:19:46  13601   ← 09-27 19:23
10:19:46  13603   ← 09-26 15:28
10:20:06  13607   ← 09-26 15:34
10:20:21  13609   ← 09-26 15:35
10:20:46  13611   ← 09-26 15:42
10:20:46  13751   ← 09-27 19:23
...  间隔整 20s（= POLL_INTERVAL）...
10:22:52  13797
```

**17 条 trace 全部是 09-25 ~ 09-28 的历史消息**，而启动时刻（10:18:16）
水位本应是当刻 `MAX(id)`。**「绝不回历史」契约被完全违反。**

### 1.3 根因（两处缺陷）

**A-1 `_run` 水位初始化守卫是「仅当为 0」**（`ai_reply.py:1458-1463`）

```python
def _run(self):
    # 启动时刻打水位：只回开启之后的新消息，绝不回历史   ← 注释如此
    row = conn.execute("SELECT COALESCE(MAX(id),0) FROM dm_messages").fetchone()
    if int(_kv_get(_KV_MARKER, 0) or 0) == 0:            # ← 但只在 0 时才写
        _kv_set(_KV_MARKER, row[0] if row else 0)
```

注释承诺「启动时刻打水位」，实现却是「**只在 kv 为 0 时**才打」。
只要库里有非 0 旧水位（上次运行遗留），本次启动就**沿用旧水位**，
`id > 旧水位` 把关停期间累积的**全部历史消息**捞出并逐条回复。

**A-2 「关闭期间每 tick 推进水位」以 `enabled=False` 为前提**（`ai_reply.py:1479-1482`）

```python
if not cfg.get("enabled"):
    _kv_set(_KV_MARKER, max_id)  # 关闭时推进水位
    return
```

契约写「**关闭期间**每 tick 推进水位」，实现却要求 `cfg["enabled"] == False`。
但本次日志第 8-9 行显示 AI 监听是 **`已按配置自启`（enabled=True）**：

```
10:18:16 | [ai] 获客自动回复监听已启动（全自动模式）
10:18:16 | [startup] AI 获客自动回复已按配置自启
```

⇒ `_run` 的 while 循环**从未进入过 `not enabled` 分支**，
故「关闭期推进水位」这一保护从未生效；配合 A-1，旧水位被原样继承。

### 1.4 与「WS 实时接收」原则的关系（用户报障原话）

用户要求「AI 回复必须遵守 WS 实时接收原则」。实测偏差有二：
- **A**：回复的对象是**历史库消息**（非 WS 实时推送），根因见 §1.3；
- **B**：绕过了实时通道 —— 轮询 `dm_messages` 表（20s 一轮），
  而实时通道是 `frontier-im` WS 推送。二者语义不同，前者会「补课」历史。

## 二、缺陷 B：跨账号互回（最严重的行为后果）

### 2.1 DB 铁证（E5）

同一 `conv_id = 0:1:316276709526638:3887506227210423`
（小助理 316… ↔ 张老师 388…，**两账号互为对端**）：

| id | 时间 | account | role | 文本 |
|---|---|---|---|---|
| 13777 | 10:19:24 | 四川工伤张老师 | **me** | 嗯嗯稍等哈，我问下马上回你 |
| 13779 | 10:19:24 | 尚进工伤小助理 | **them** | 嗯嗯稍等哈，我问下马上回你 |
| 13782 | 10:19:48 | 四川工伤张老师 | **me** | 这个我得确认一下哈，稍等 |
| 13784 | 10:19:48 | 尚进工伤小助理 | **them** | 这个我得确认一下哈，稍等 |
| 13790 | 10:22:22 | 尚进工伤小助理 | **me** | 您好，我是唐律工伤团队的理赔顾问 |
| 13792 | 10:22:22 | 四川工伤张老师 | **them** | 您好，我是唐律工伤团队的理赔顾问 |
| 13795 | 10:22:48 | 尚进工伤小助理 | **me** | 测试消息：小助理凭证回写验证成功 |
| 13797 | 10:22:48 | 四川工伤张老师 | **them** | 测试消息：小助理凭证回写验证成功 |

**因果**：账号 A 的 AI 回复落库 `role=me` → 对端账号 B 的守护把它同步为
`role=them`（B 视角下这确实是"对方发来的"）→ B 的 AI 判定这是**客户消息**
→ 生成回复 → A 又收到 → **两个 AI 无限互回**。

### 2.2 为什么这是设计缺口（而非单纯配置问题）

- 现有护栏只挡**黑名单**（`blacklist_list()`）与 **UID 沉淀池**（同 UID 时效窗）。
  E4 显示 `BLACKLIST result=pass, bl_size=0` ⇒ 黑名单为空，未拦。
- **没有任何护栏识别「对端是本项目自己的另一个账号」**。
  同机多账号是**本项目的常规部署形态**（日志第 16-21 行同时拉起两个 BCC），
  故该缺口在生产环境下**必然触发**。
- 后果：消耗真实发送配额、污染两个账号的会话记录、
  在抖音侧形成两个账号之间的异常高频往返（**风控面**）。

### 2.3 严重性定级

按 Failure 影响面：**可自激放大**（无上限循环）+ **有风控后果** + **污染真实客户会话**
⇒ 定级 **fatal**（本报告最严重项）。

## 三、缺陷 C：直播页 AI 回复统计口径错误（用户报障③）

### 3.1 现状

`api/ai.py:991-1002` 直接下发 `ai_reply.WORKER.status`，前端
`live-shared.tsx:52-56` 展示四项：

```
已回复 {st.replied} · 留资 {st.leads_total} · 处理 {st.processed} · 错误 {st.errors}
```

### 3.2 三处口径问题

**C-1 「处理」把历史消息也算进去了（与用户观察一致）**
`processed` 在 `_handle_session` 成功即 +1，**不区分**该消息是历史还是实时。
本次 17 条历史消息全部计入 ⇒ 明明在「刷历史」，统计却显示正常处理，
**给出"运行良好"的错误信号**。这正是用户感觉"统计有问题"的直接原因。

**C-2 `processed` ≠ `replied`，语义未在 UI 区分**
`processed` 含：被护栏拦下走兜底的、未生成回复的、图片兜底的。
本会话 3 条走 `FALLBACK`（E4 `FALLBACK result=used`），
即「AI 原始输出被护栏拦下」（`AI_RAW raw="我在的"` → `GUARD blocked`）。
⇒ `processed` 会显著高于 `replied`，UI 并列展示易被误读为"回了这么多"。

**C-3 内存态，重启即归零**
`self.status` 是**进程内 dict**（`ai_reply.py:1386`），无持久化。
应用重启 → 统计清零，但库里 AI 回复记录仍在 ⇒
**统计与事实脱钩**（用户会看到"已回复 0"却有回复记录）。

### 3.3 正确的统计口径（建议，待拍板）

以**库为真源**，而非内存计数：
- 已回复 = `dm_messages WHERE role='me' AND source/extra 标记为 AI 回复`（按时间窗）；
- 处理/错误 = 保留内存态用于"本进程运行期"，但须**显式标注"本次运行"**；
- 或：为 AI 回复落库时打 `extra.source='ai'`，统计直接 `COUNT(*)` 聚合（可跨重启、可核对）。

## 四、缺陷 D：私信发送失败信息不可诊断（用户报障①）

### 4.1 现象

用户原话：「私信状态一直显示发送失败，但没有体现具体的失败原因」。

### 4.2 日志里的三种"失败"，成因完全不同

| 时间 | 错误码 | 原因 | 性质 |
|---|---|---|---|
| 10:23:56 起 ×5 | `SEND-008` | `UID 沉淀池: 仍在聚合窗口（剩余 185s）` | **本可预期**（防重护栏） |
| 10:21:46 起 ×多 | `SEND-037` | `调度器限流: 冷静期内（剩余 515s）` | **本可预期**（风控冷静期） |
| 10:23:56 起 ×5 | `SEND-040` | **`name 'ai_reply' is not defined`** | 🔴 **真缺陷**（NameError） |

### 4.3 根因（SEND-040 NameError —— 代码缺陷）

`core/auto_dm.py:598-602`（`_make_live_ai_gen` 内的 `_gen` 闭包）：

```python
text, source = await asyncio.to_thread(
    ai_reply.generate_dm_for_live,      # ← ai_reply 在此作用域未定义
    ...)
```

`ai_reply` **只在该文件另一个方法 `evaluate_live_ai`（第 458 行）内局部导入**：

```python
try:
    from services import ai_agent, ai_reply   # ← 局部作用域，仅本方法可见
```

⇒ `_gen` 闭包拿不到该名字 ⇒ 每次调用抛 `NameError`
⇒ 被 `except Exception`（第 609 行）吞掉，仅记 `SEND-040` 并**回落词库**。

**后果**：直播私信文案的 AI 生成**从未生效过**（每次都 NameError → 回落词库），
而日志只显示"AI 文案生成失败，回落词库"，**不指向代码缺陷**。
这解释了：为何日志里既有 `[live-ai] 私信文案已接入 AI 生成`（§106，接线判定通过）
又有 `SEND-040 回落词库`（§175 起）—— **判定通过、生成必败**。

### 4.4 「没说清具体原因」的双层成因

- **后端层**：`SEND-040` 文案 `AI 文案生成失败，回落词库` 属**粗粒度**，
  不区分「模型链路不可用 / 配置缺失 / 代码异常」。真正的异常文本
  （`name 'ai_reply' is not defined`）只附在日志尾部，UI 拿不到。
- **前端层**：`live-shared.tsx` 的失败弹窗按 `reason` 文本做关键词分类
  （`localClassifyFail`，第 248-301 行）。**"UID 沉淀池仍在聚合窗口"**
  不含其任何关键词（沉淀/聚合窗口不在表内）⇒ 落到 `other` → 提示
  「未能归类的失败」。用户因此「看不到具体原因」。
