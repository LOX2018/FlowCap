## 1. 背景与设计意图

ADR-018 F1（标签配置中心接线）留了三个子决策 D1/D2/D3，其中：

- **F1-D2**（私信 WS 只管频率）：子代理实测**现状已天然符合**
  （`dm/send` 载荷全是频率字段，内容在 `ai_reply`）⇒ **无需改码**。
- **F1-D1**（`live_rooms` 加 `tag_id`）：让直播参数可**按房间**差异化。
- **F1-D3**（新建采集策略 schema）：给采集域补上参数复用载体。

D1/D3 均**会改产品运行时行为**，故当初处 H-22 冻结期时只出方案。本次解除冻结后落地。

## 2. 现状（改前实测）

| 事实 | 位置 |
|---|---|
| `scope_of` 只有两级：板块级 > 整账号级 | `services/config_tag.py:188` |
| 标签体系有 `capture` 板块，但**无消费者** | `MANAGED_SECTIONS = ("send","live","capture")` |
| 采集端点全部即时调用、自带全参数 | `api/crawl.py` 4 个端点 |
| `live_rooms` 存 kv（非 SQLite 表），经 `RoomBody` pydantic 校验 | `api/live_rooms.py:85` |

⇒ 两个缺口：**直播参数粒度停在账号**、**采集无参数载体**（F4 定时任务无载荷可取）。

## 3. 改动

### F1-D1（房间级标签）

- `RoomBody.tag_id: str = ""` —— **可清空**字段（与 `strategy_id` 同类语义）
- `_FIELDS` 白名单加 `tag_id`（**漏这一步 = 写成功但读不到**）
- `save_room`：`pick("tag_id", clearable=True)` + **引用完整性校验**
  （悬空标签拒写 —— 否则 `scope_of` 判空静默回落，用户以为绑了实际没生效）
- 新增 `_tag_exists()`（与既有 `_strategy_exists` 同构）
- `scope_of(account, section="", room_tag="")` → **三级优先链**
  - ① 房间级 ② 板块级 ③ 整账号级；都没有 → `None`（读全局）
  - 每级都校验 `get_tag(...)["name"]`：**悬空引用回落**而非返回空 scope
  - 不传新参数 ⇒ 与改造前逐字一致（零回归）

### F1-D3（采集策略）

- 新建 `api/crawl_policy.py`：kv `crawl_policies`，4 端点
  （list / get / save / delete / resolve）
- **零身份字段**（不存关键词、aweme_id）—— 与 `live_config.py` 同一条设计约束
- 非法枚举**拒绝写入**（不静默改写为默认值）
- 数值收敛：`num` 1..50 / `max_rounds` 1..100
- `POST /{pid}/resolve`：解析成可直接喂 crawl 端点的参数包，**只读不发请求**，
  并按 `account` 返回 `tag_scope`（`scope_of(account,"capture")`）
- 挂载 `/api/crawl/policies`（`main.py`）

### 前端

- `RoomManagePage`：「绑定参数标签」下拉（照抄 `strategy_id` 范式）+ 列表展示
- 新建 `CrawlPolicySection.tsx` + 设置页 nav 项「采集策略」

## 4. 🔴 门禁抓出的真 bug（本案例最有价值的部分）

**现象**：G7 断言失败 —— `sort_type` 未提交时被拒，报「取值 `''` 非法」。

**根因**：`pick(field, clearable=False)` 的回落链是
`sent → cur → old → ""`。**新建**一条策略时 `old` 为空 ⇒ 回落到 `""` ⇒
撞上「非法枚举拒绝写入」的校验 ⇒ **新建策略必然失败**。

**修法**：`pick` 增 `default` 参数 + 新增 `_ENUM_DEFAULTS` 单源
（"不可清空字段的旧值也空 ⇒ 用默认"）。

**教训**：「清空性」与「必填校验」的交互是本项目**复发型**缺陷模式 ——
`live_rooms` 曾因同类问题出现「解绑后仍显示旧值」。**新建路径**是这类 bug 的
高发区（开发时通常只测「更新已有记录」）。

## 5. 门禁的第二个坑：探测方法错了会误报

**现象**：G8 断言「未挂载 `/api/crawl/policies`」。

**根因**：本项目 `main.py` 用**自定义 `_IncludedRouter`** 承载 `include_router`，
`app.routes` 里这些对象的 `.path` 取不到（实测为 `?`）⇒ 直接查 `app.routes`
对本项目**所有**路由都会误报「未挂载」。

**修法**：改用 `app.openapi()["paths"]`（实测 221 条，才是本项目可信路由真源）。

**教训**：门禁报红时，**先证「探测方法本身是否可信」**，再断言「被测行为坏了」。
否则会去修一个本来没坏的东西 —— 而且这种误报会让门禁整体失去信任。

## 5.5 🔴 第二个真缺陷：读取出口吞掉 tag_id（**实机验证才抓到**）

**现象**：单测 G1~G8 **全绿**，真实实例端到端验证 §⑧ 却报
`房间条目含 tag_id 字段` 失败 —— 列表回不到 `tag_id`。

**根因**：`api/live_rooms.py:_normalize_room`（**读取路径唯一出口**）有一行
历史残留清名单：

```python
for junk in ("force_rescan", "forceRescan", "tag_id"):   # ← tag_id 在这里
    c.pop(junk, None)
```

那个 `tag_id` 是**旧「配置标签 tab」时代**的废弃键（`live_config.py` 注释里的
「配置标签 tab 已删除」即指此事），属于当时该清的垃圾。ADR-018 F1-D1 把
`tag_id` **重新定义为正式字段**后，这行清理与正式字段契约**正面冲突**：
写入侧 `_FIELDS` 放行、落库成功，读取出口却主动抹掉。

**危害链**：用户绑了房间级标签 → 列表不显示（表现为「绑了没反应」）→
且 `scope_of` 拿不到 `room_tag` ⇒ **回落到账号级**，参数实际未按房间生效。

**为什么单测漏网（本案例最重要的教训）**：
G1~G8 全部**直调** `save_room` / 直读 kv，**不经过 `_normalize_room`**。
⇒ 单测存在**结构性盲区**：只覆盖写入侧与核心逻辑，覆盖不到「读取出口」。

**修法**：把 `tag_id` 移出残留名单 + `c.setdefault("tag_id", "")`
（旧记录补默认值，否则前端必填类型会拿到 `undefined`）；
同时新增 **G9/G9b** 断言（必须走 `_normalize_room` 而非直读 kv）与 **N4 负控**
（把 tag_id 塞回名单 ⇒ G9 必红）。

### ⚠️ 关于「验证脚本自身出错」

本轮真实实例验证共报 3 次失败，其中**只有 1 次是产品缺陷**，另 2 次是脚本 bug：

| 报错 | 归属 | 根因 |
|---|---|---|
| 房间条目含 tag_id 字段 | **产品缺陷** | `_normalize_room` 的残留名单 |
| （取 `rid` 为 None 导致找不到条目） | 脚本 | `save_room` 返回 `{"ok":true,"room":{...}}`，**顶层无 `id`** |
| `save_tag() missing 1 required positional argument` | 脚本 | `save_tag(tag_id, name)` 两参必填；返回的是标签对象本身，**无 `id` 字段**（id 是 kv 键） |
| 「拒绝是真拒绝」在末尾又报错 | 脚本 | 断写死 `total==1`，但④之后其它断言会新建 ⇒ **顺序相关假失败** |

**判据**：验证脚本报错时，**先分清「产品坏了」还是「探测方法错了」** ——
两者都要修，但修法完全不同；若把脚本 bug 当产品 bug 去改产品，会引入
**无谓的改动**（本项目已有先例：G8 的路由探测方法错，把「查 app.routes」
换成「查 app.openapi」才是正解）。



`test_negative_control_f1_d1_d3.py` —— 三项，每项「篡改 → 断言必红 → 还原」：

| 负控 | 篡改 | 目标断言 | 结果 |
|---|---|---|---|
| N1 | 删掉 `scope_of` 的房间级判定 | G1 | ✅ 如期变红 |
| N2 | 悬空引用改成直接返回 id（不校验） | G3 | ✅ 如期变红 |
| N3 | 非法枚举改成静默回落默认值 | G6 | ✅ 如期变红 |

**负控脚本自身的坑**：本仓混用行尾（`services/config_tag.py` = CRLF，
`api/*.py` = LF）。负控脚本写死 `\n` 锚点 ⇒ 在 CRLF 文件上「锚点命中 0 次」
而**静默失效**（首轮实测 N1/N2 假失败）。
**修法**：负控脚本按目标文件行尾自适应转换锚点。

## 8. 可迁移判据（下次同类改动可用）

1. **加字段给 kv 记录**：`_FIELDS` 白名单 + `pick(clearable)` + **引用完整性**
   三件套缺一不可；漏白名单 = 写成功读不到。
2. **可清空字段的校验顺序**：「清空性」与「必填/枚举校验」会互相咬；
   新建路径必须单独测（`old` 为空时的回落链）。
3. **孤儿模块检测**用 `app.openapi()["paths"]`，**不要**查 `app.routes[].path`
   （本项目路由由自定义 `_IncludedRouter` 承载）。
4. **门禁必配负控**；负控脚本要**行尾自适应**（本仓 CRLF/LF 混用）。
5. **加字段必须同时检查三个出口**：写入侧白名单（`_FIELDS`）、
   **读取出口装配函数**（`_normalize_room` 这类）、前端类型 —— 三者缺一即静默失效。
   本项目已有两次同类教训（`strategy_id` 解绑残留、本次 `tag_id` 被当垃圾清掉）。
6. **单测直调函数 = 结构性盲区**：凡有「读取出口装配层」的模块，
   断言必须**经过该层**；只直读 kv 会漏掉出口的全部加工逻辑。
7. **实机验证优先于单测全绿**：本轮单测 8/8 全绿仍藏一个真缺陷，
   是真实实例 HTTP 验证抓到的（Live-Instance 铁律的又一实证）。
8. **脚本报错先分类**：产品缺陷 vs 探测方法错 —— 后者只改脚本，
   切忌去改本来正确的产品代码。
9. **接口对账先于实现**：`scope_of` 扩展前先 grep 全部消费点（实测只有
   `dm_dispatch.py:126` 一处），确认加**带默认值的新参数**不会影响既有调用方。
