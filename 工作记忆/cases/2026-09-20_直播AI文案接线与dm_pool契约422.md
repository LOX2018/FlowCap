## 一、用户诉求与结论摘要

用户启动了一个**真实直播监听任务**，要求「分析 AI 回复是否正常」。

**结论：AI 回复不正常 —— 但不是质量问题，而是两层结构性缺陷：**

| # | 缺陷 | 性质 | 后果 |
|---|---|---|---|
| 1 | `POST /api/engine/start` 对所选直播间配置恒返 **422** | 契约声明与真实主形态不一致 | 直播任务**一次都没启动过**（用户实报即此） |
| 2 | 直播/采集私信的文案来源**只有词库**，无任何 AI 接线点 | 功能面缺口（设计已规划、从未接线） | 直播听众永远收到词库轮播，不是 AI 生成 |

第 2 条**不是**「AI 质量不好」，而是「AI 根本没参与」。这一区分很重要：
若按「回复质量」去调 prompt，是**在错误坐标轴上优化**（本项目性能优化一节同款教训）。

## 二、缺陷 1：dm_pool 契约 422（根因链 · 可复现）

### 事实链（文件:行）

| 跳 | 位置 | 事实 |
|---|---|---|
| ① 发送方 | `frontend/src/components/live/live-page.tsx:775-782` | `dm_pool: selCfg.dm_pool \|\| []` —— `selCfg` 来自 kv `live_room_configs`，元素为 `{text, enabled}` **对象** |
| ② 传输 | `frontend/src/api/client.ts:556-560` | `POST /api/engine/start`，body 含对象数组 |
| ③ 接收 | `backend/api/engine.py:19` | `config: TaskConfig` → Pydantic 形参校验，**早于** `config.resolved()` |
| ④ 声明 | `backend/models/task.py:35` | `dm_pool: list[str] = []` ← 唯一冲突点 |

**关键判据（决定修法方向）**：后端**消费侧本来就是对象形态**，只有声明是字符串 ——
`core/auto_dm.py:253 _normalize_dm_pool`、`api/live_config.py:255-260 _RuntimeCfg`
都按 `{text, enabled}` 归一。⇒ 放宽声明即与真实契约对齐，不改任何业务语义。

### 复现（离线，纯 pydantic，不启引擎/浏览器）

```
修复前：VALIDATION_FAILED
        loc: ["dm_pool",0/1/2]  msg: Input should be a valid string
        → 与用户实报逐条一致
修复后：对象形态通过，且 {"text":"A","enabled":false} 的 enabled 位保留
```

### 🔴 为什么这个缺陷能长期隐藏（最有价值的一条）

**两端类型错得一致 ⇒ 类型检查全绿**：

- 后端 `dm_pool: list[str]`；
- 前端 `live-shared.tsx` 的 `TaskConfig.dm_pool?: string[]` **也是错的**；
- ⇒ `npx tsc -b` 永远 0 错误，后端单测也从没用**对象形态**打过 `/engine/start`。

**通用判据**：凡「前端 TS 类型 × 后端 Pydantic 声明」这对契约，**必须各自独立核对真实数据形态**；
「类型检查通过」只证明两端**互相一致**，不证明**与真实存储/编辑器形态一致**。
本案例的破法：以「存储里的真实形态」（kv `live_room_configs`）为锚，而不是以另一端的类型为锚。

### 同族发现（顺带修）

`resolved()` 原写法 `t.get("text")` 会把对象**压成纯文本**，`enabled=False` 被静默丢弃
⇒ 与 `api/tasks.py:222-233` 已记录的同型缺陷（「写回时抹掉词条 enabled 标记」）完全同族。
本次一并修正为保留对象形态。

## 三、缺陷 2：直播私信文案的 AI 接线（落地形态）

### 改造前实测事实

| 环节 | 位置 | 事实 |
|---|---|---|
| 文案来源 | `core/auto_dm.py:295,486` → `core/dispatch.py:333` | 只有 `pick_dm_message = _make_pick_dm_message()`（词库随机） |
| AI 生成调用点 | 全仓 grep | **0 处** |
| AI 引擎 | `services/ai_reply.py:996 AutoReplyWorker` | 存在且在跑（日志 `[ai] 获客自动回复监听已启动`），但**只消费 `dm_messages` 的 `role='them'`** |
| 直播弹幕能否喂给它 | `core/live_hook.py` 的 `feed` | ❌ 只进内存 deque 给前端展示，**不落 `dm_messages`** |
| 水位 | kv `ai_reply_last_msg_id` | = `MAX(dm_messages.id)` ⇒ 启动即推平，只回启动后新消息 |
| 真实回复量 | 库实测 | 最新 `role='them'` = 09-19 22:28（当时距 20 小时）；`ai_leads` = 0 |

### 接线点设计（单一入口，禁止 live/crawl 各写一份）

```
core/dispatch.DispatchCenter._do_send（async）
  ├─ gen_dm_message(target)   ← 新增：AI 生成优先（sync/async 均支持，inspect.isawaitable）
  └─ pick_dm_message()        ← 保持：词库回落（改造前行为逐字不变）
        ↑
core/auto_dm.AutoDM._make_gen_dm_message()   ← 唯一接线点
  ├─ 判定：agent_of(account) → resolve_config → scopes 含 live + enabled 且非 kb_only
  └─ 生成：await asyncio.to_thread(ai_reply.generate_dm_for_live, ...)
        ↑
services/ai_reply.generate_dm_for_live()     ← 唯一生成入口
  ├─ ① reply_kb.find_match（命中即回，零 token，与私信侧同链）
  ├─ ② 专业库 RAG + build_system_prompt（与私信侧同一构建器）
  └─ 护栏 validate_reply / 思考泄漏检测（与私信侧同一套）
```

### 接线判定（全部满足才启用 AI）

1. `enabled=True`；
2. `scopes` 含 `live`；
3. `strict_level != "kb_only"`（kb_only = 用户显式选择「AI 完全不参与」，必须尊重）。

配置来源 = `ai_agent.resolve_config(account, base)`：**账号绑定了 Agent → 用该 Agent 的配置；
未绑定 → 原样返回全局 `ai_reply_config`**（这是该方法既有契约，文档原话「未绑定 → 零回归」）。
⇒ **「是否生效」由 `scopes` 决定，而不是由「有没有绑定」决定** —— 与 9.29 §AI 接入点收敛一致。

🔴 **踩坑（差点把功能做成永不生效）**：我第一版实现写成「必须先绑定 Agent 才接线」。
实测运行库状态：
```
kv ai_agents        → 不存在（未建任何 Agent）
kv ai_account_agent → 不存在（无任何绑定）
kv ai_reply_config  → {"enabled": true, "strict_level": "rag", "scopes": ["dm","live","crawl"]}
```
⇒ 库里**一个 Agent 都没有**，按第一版实现 AI 永远不会生效；但按既有语义，
全局配置带 `scopes: ["live"]` 本就应该生效。**根因是我把「绑定」误当成生效前提。**
**判据**：新增功能前先读**运行库的真实状态**（本例 `ai_agents` 不存在），
不要按「设计文档里写了 Agent 体系」就假定它已被配置；否则会做出「语法正确但永不触发」的功能。

### 回落语义（四态，全部实测）

| 情形 | 结果 |
|---|---|
| AI 生成非空 | 采用 AI 文案 |
| AI 返回空串 | 回落词库 |
| AI 抛异常 | 回落词库，**且发送继续**（不中断） |
| 未接线（None） | 词库（零回归） |

**为何直播侧「生成失败回词库」而私信侧「回兜底话术」**（刻意不同，勿强行合并）：
直播首触的场景里词库本来就存在；私信会话回复没有词库概念，只能回兜底话术。

## 五、踩坑记录

1. **探针自身缺陷会伪造「产品 bug」**（本轮实际踩到）：`DispatchCenter._do_send`
   在 `self.records` 里没有该 key 时**直接 return**（正常前置），
   我的验证脚本没先 `_ensure_record` → 5 项全红，看起来像「一条都发不出去」。
   **规则**：验证脚本红灯时，先自问「被测函数的**前置条件**我满足了吗」，
   再怀疑产品代码。
2. **Python 多行字符串拼代码块 = 转义地狱**：用 `'...\\n'` 逐行拼 Python 函数体时，
   引号转义错一层就 `SyntaxError`。**正解**：把片段用 `write_file` 落到临时文件，
   再读回插入 —— 一次成功，且片段可读可复查。
3. **改代码前先探行尾**：本仓文件**行尾混杂**（`task.py`/`dispatch.py` 纯 CRLF，
   `auto_dm.py`/`tasks.py` 纯 LF）。用 `patch` 工具会统一整文件行尾 → 上千行 diff 噪声。
   **正解**：Python `rb` 读 → 按该文件真实 `NL` 拼 → `wb` 写。
4. **`inspect` 未导入**：`dispatch.py` 原本没 import `inspect`，新增 `inspect.isawaitable`
   会 `NameError` —— 且只在**真正走到发送环节**时才炸（静态检查放过）。
5. **「探针 fixture 把被测开关写进全局桩」会把语义测反**（本轮第二次踩到探针缺陷）：
   L3 判定层原来把 `scopes: ["live"]` 直接预置在**全局 `get_config` 桩**里，
   于是「未绑定 Agent」场景的 `resolve_config` 也返回含 live 的配置 → 应当接线 →
   与旧断言「未绑定＝不接线」冲突。**这是 fixture 写错，不是产品错**。
   **规则**：fixture 只应提供**最小必要输入**；把「被测的开关」预置进去，
   等于把被测逻辑短路掉（同族：`_ensure_record` 前置未满足）。
6. **提交时漏文件**：`_build_version.py` 与 `Cargo.lock` 的版本行也是版本真源的一部分。
   本次第一版提交漏了这两个，用 `--amend` 补入（未污染历史语义）。
   **注意**：profile 记忆里写「`_build_version.py` 被 .gitignore 忽略」——
   **实测该文件是 git 跟踪的**（`git check-ignore` 退出码 1 = 未被忽略）。
   ⇒ 以实测为准，勿按记忆操作。
