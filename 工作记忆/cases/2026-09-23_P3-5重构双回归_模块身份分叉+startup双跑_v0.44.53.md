# 案例 · P3-5 重构引入的双回归：模块身份分叉 + startup 双跑

> **日期**：2026-09-23　**版本**：v0.44.53（提交 `2ce728a`）
> **分支**：`design/better-douyin`　**引擎**：Camoufox
> **级别**：🔴 阻断级（应用核心能力全失，BCC 容器完全起不来）
> **触发场景**：HC-07 P3 架构重构（大组件拆分）后的首次实机启动

## 1. 设计意图（Design-First Law）

### 1.1 模块本应怎样
- `browser_daemon.py` 是 **PyInstaller 入口脚本**（以 `__main__` 身份运行），
  同时又被同进程内的其它模块按**包名** `daemon.browser_daemon` 引用。
- 设计契约（隐含，从未显式声明 → 这正是缺陷根因）：
  **同一份源码在同一进程内只允许存在一份模块实例**；
  `_state` 是进程级单例状态，所有模块必须看到同一个 dict。
- FastAPI 契约：`on_startup` handler 在一次进程生命周期内**只执行一次**。

### 1.2 P3-5 重构做了什么（拆分的正确部分）
按 `docs/adr/P3-5-large-component-split-plan.md`：
- `browser_daemon.py` 3758 → 1541 行（−59%）
- 新增 5 个模块：`bcc_lease`(236) / `bcc_routes`(652) / `bcc_login`(660)
  / `bcc_capture`(239) / `bcc_audit`(313)

拆分本身**符合** Design-First Law（高内聚、单一职责）。
但拆分引入了两个**先前不存在的跨模块边界**，而这两个边界各带一个
「隐性前提」，前提未验证即上线 —— 事故就是这两个前提不成立。

## 4. 根因分析（Step 4）

### 4.1 根因一：模块身份分叉（`__main__` ≠ `daemon.browser_daemon`）

P3-5 Step2 新增 `bcc_routes.py`，其中用 `from daemon.browser_daemon import _state`。
由于入口以 `__main__` 加载，Python 的模块缓存键不同：
- `sys.modules["__main__"]` → main() 写入 `account/port` 的那份
- `sys.modules["daemon.browser_daemon"]` → bcc_routes 的 import 触发的新实例

⇒ startup 收到空 `_state` ⇒ `BrowserContainer(account="")`
⇒ `env_path` 为空 ⇒ `BCC-051` 熔断 ⇒ **容器永不启动**。
⇒ 附带：第二份模块重跑模块级 `logger.remove()` ⇒ 文件 sink 被删 ⇒ 日志 0 字节。

**为什么以前不出事**：重构前 handler 是 `@app.on_event(...)` + 全在 `browser_daemon.py` 内，
没有「另一个模块反向 import 入口」这条边。**拆分创造了这条边。**

#### 4.1.1 同类受害点（必须一并修）
`main.py`（backend 入口）同样缺归一，且 `api/accounts.py:62` 与
`api/notify.py:432/505` 在**请求期**执行 `from main import app`。
实证：
```
[1] __main__.app            id=1781024676832  state 有 adm? True
[2] api.accounts._get_adm() = None
    "main".app id=1781038617264  是同一个 app? False  state 有 adm? False
```
⇒ `_get_adm()` 返回 `None` → 「引擎实例不可用」。
（`api/notify.py` 的注释早已记录过该形态，故其自建 `bind_adm` 显式注入绕开；
但 `_get_adm()` 的**回退路径**仍会踩中，且每新增一处 `from main import ...` 都可能再犯。）

### 4.2 根因二：startup 双跑（上游 FastAPI 语义）

`bcc_routes.py` 用 `@router.on_event("startup")`，`browser_daemon.py` 用
`app.include_router(router)`。上游 `fastapi/routing.py`（0.141.1）中 `include_router`：

```python
for handler in router.on_startup:                 # ① 注册 handler
    self.add_event_handler("startup", handler)
...
self.lifespan_context = _merge_lifespan_context(  # ② 合并 router 的 lifespan
    self.lifespan_context, router.lifespan_context)
```

而 `APIRouter.__init__` 里 `lifespan_context = _DefaultLifespan(self)`，
其 `__aenter__` 正是 `await self._router._startup()`。

⇒ ① 注册的 handler 与 ② 合并进来的默认 lifespan **各跑一次** ⇒ `_startup()` ×2。

**为什么以前不出事**：重构前生命周期 handler 直接写 `@app.on_event(...)`，
不经 `include_router`，故只跑一次。**拆分把生命周期搬到了 router 上。**

⇒ 双容器抢 profile ⇒ 第二个 Camoufox `Failed to launch the browser process`（BCC-058）
⇒ `_state["container"]` 被后建的坏容器覆盖 ⇒ `/status` 恒 `alive:false`
⇒ keepalive×2 + 每轮 BCC-006 重建 ⇒ **用户所见的「反复激活」**。

## 5. 修复（Step 5，含 Live Verification）

### 5.1 定式一：入口模块身份归一
```python
# browser_daemon.py / main.py 顶部（任何反向 import 之前）
sys.modules.setdefault("daemon.browser_daemon", sys.modules[__name__])
sys.modules.setdefault("main", sys.modules[__name__])
```
`setdefault` 语义正确：以包名正常 import 时不动它；以 `__main__` 启动时补规范名。

### 5.2 定式二：路由可以 include，生命周期不行
```python
# bcc_routes.py：只导出普通函数
async def startup() -> None: ...
async def shutdown() -> None: ...

# browser_daemon.py：挂到最终 app 上
app.router.add_event_handler("startup", _bcc_startup)
app.router.add_event_handler("shutdown", _bcc_shutdown)
```

### 5.3 实机验证结果
- 部署产物 md5 四处 MATCH（主 exe + 3 sidecar）
- `/api/version` = `{"backend":"0.44.53"}` ✅
- `/status` = `{"alive":true,"account":"尚进工伤小助理","logged_in":true,"uid":316276709526638}` ✅
- 本次启动 startup 计数 = **1**（修复前 3）；16:39 后 BCC-058/BCC-006/profile 占用 = **0** ✅
- BCC 日志 0 字节 → 有内容 ✅
- 全量回归 **Ran 630 tests, OK** ✅
- 守卫含**负控**（注入事故形态必须变红，已证）✅

## 7. 可迁移判据（写进 skill 的部分）与项目事实（留在本案例）

**可迁移（用户级 skill）**：
1. 凡「以 `__main__` 运行、又被同进程按包名 import」的入口，必须做模块身份归一。
2. FastAPI：**路由可以 include，生命周期不行**（`@router.on_event` + `include_router` 会双跑）。
3. 判据性 grep 的模式串不得写进注释（否则判据失效）。
