# 2026-09-21 私信凭证校验「谎报可靠」根治 —— 判据从「字段/端口」升级为「真实写校验」

> 归属：DYAutoDM_v2 · design/better-douyin 分支 · v0.44.20
> 性质：**已定位 + 已修复 + 已实机双账号对照验证**
> 用户原始报告：「私信链路通了，但对私信凭证的校验依旧不合理，引擎校验依旧显示私信凭证可靠，需要重点优化」

---

## 一、现象

修复私信发送（aweType 信封）后用户立刻发现第二个问题：

**四川工伤张老师**（609 建会话被服务端拒、发送全废、wp 探活 uid 已漂移）
在账号管理页/自检弹窗里，**私信引擎仍显示 `ok / 私信守护正常`**。

## 二、三个独立缺陷（均代码级实证）

### 缺陷 1：dm 引擎「探端口」冒充「验凭证」（最严重）

`auto_dm/accounts.py` 的 `verify_account`，`dm_loopback=True` 分支原文：

```python
b_ok = _port_open(bport, timeout=0.5)   # browser_daemon 端口开着吗
r_ok = _port_open(rport, timeout=0.5)   # recv_daemon 端口开着吗
if r_ok and b_ok:
    result["dm"] = {"level": "ok", "label": "私信守护正常", ...}
```

**只探测端口是否 LISTEN，完全不碰 imapi。** 而同函数 docstring 写的契约是
「私信引擎：拉取会话列表成功则说明私信凭证有效」——**承诺与实现不符**。

讽刺的是第 638 行自己的注释就写着「**端口在 ≠ 凭证有效**（这是本项目的历史
假成功来源）」，而 dm 引擎正是这么判的。

### 缺陷 2：轮询场景用 wp 结果冒充 dm

```python
# dm_loopback=False（前端 30s 轮询）
if wp_level == "ok":
    result["dm"] = {"level": "ok", "label": "正常（沿用 wp）"}
```

wp = 「web_protect 四件套非空 + query/user 探活通」，与 imapi 私信凭证是
**两条独立通路**。wp 全绿完全不代表 imapi 可写（张老师实测即此形态）。
⇒ 用户点开页面看到的是绿灯，实际一条都发不出去。

### 缺陷 3：wp 的成功判据也太弱

```python
_has_sign = bool(auth.ticket and auth.ts_sign and auth.client_cert
                 and auth.private_key and (web_protect_str or ree_public_key))
if uid and _has_sign:  level = "ok"
```

只检查 `.env` 字段**非空**（`str(True)` 也是"真"）。本项目
`cases/2026-09-20_直播监听失败_cmd609…md §8.3` 早已写明：

> 「探活能过 ⇒ 凭证有效」在**写会话**这一层**不成立**……`_verify_credential`
> 的浅校验只做 `get_my_uid`（身份**读**）就判"凭证有效，跳过扫码"，
> **不校验写会话能力**。

**该缺陷当时已被识别并给出建议（加一次 `create_conversation`），但从未落地。**

## 三、修复（v0.44.20）

### 3.1 新增 IM 写能力探针 `auto_dm.accounts.probe_im_write`

```python
probe_im_write(name, auth=None, force=False, ttl=None) -> (ok: bool, detail: str)
```

- **选型**：`create_conversation(自身 uid)`（cmd 609）——只**建/取会话**、
  **不投递任何消息** ⇒ 零真人打扰、可安全高频调用。
- **目标 uid 取会话体系**（`conv_identity.my_uid`，conv_id 推断、零网络、权威），
  无历史会话才回退 web 探活 uid。
- **缓存 120s**（写能力变化慢；比读凭证的 300s 短，只读态自愈后较快放行）。
- **异常一律转 `(False, 原因)`**，绝不冒泡成「校验异常」而丢失「凭证不可用」。
- 错误分类识别 `session length` → 明确产出「只读态，请重新扫码」。

### 3.2 dm 引擎改为真实写校验

- `dm_loopback=True`（用户点「引擎校验」）：`probe_im_write(force=True)` 真打网；
  **守护进程状态降级为 detail 里的补充信息**（守护没起 ≠ 凭证无效）。
- `dm_loopback=False`（30s 轮询）：**不新增网络请求**，只读写探针缓存给出
  **诚实三态**（ok / fail / **unknown**）——三态之 unknown 如实报
  「私信凭证未校验」，**不伪造 ok**。
- 同时修正 docstring（承诺与实现对齐）。

### 3.3 wp 分支区分「身份漂移」与「网络抖动」

原实现把 AUTH-050（探活 uid 与历史 conv_id 不一致）一律写成
「网络抖动，可稍后重试」⇒ 把**凭证失效**误导成**临时故障**，
用户反复重试而问题永不消失。现拆分：
- 不一致 → `fail / 身份漂移（AUTH-050）`，文案明确「稍后重试无效，请重新扫码」；
- 真网络问题 → `warn / 捕获齐全但探活失败`。

### 3.4 凭证落盘门禁同步写探针缓存

`_probe`（accounts.py 凭证落盘校验）在 `create_conversation` 成功/失败时
同步写 `_im_write_cache` ⇒ 引擎校验/轮询**立刻**能反映最新写能力，
零额外网络请求。

### 3.5 `force_probe` 后门收敛为调用方白名单

`services/uid_probe.py` 的 `force=True` 能穿透 300s TTL，是本模块**唯一**能
造成探活频次失控的入口。原文只说「仅凭证落盘门禁可用」，但签名上任何调用方
都能传 —— 属「约束靠约定、不靠强制」。

现改为**显式登记制**（`_FORCE_CALLERS`），未登记调用方 `force=True` **降级**
为走 TTL 的普通探活并告警 `AUTH-052`（降级而非抛错，保证不中断任何路径）。

白名单**由实测函数名确定**（不可凭猜）：
| 调用点 | 实测函数名 |
|---|---|
| `daemon/browser_daemon.py:2343` | `_page_login_state_sync` |
| `camoufox_capture.py:203` | `verify_credentials` |
| `accounts.py:1207` 落盘 worker | `worker` |

（首版我凭印象写了 `credentials_complete` / `camoufox_capture`，**全错**；
实测后修正 —— 这正是「必须实测不能凭猜」的又一例证。）

## 五、uid 探活频次分析（用户提问）

**结论：设计合理，稳态风险已受控。**

| 项 | 值 |
|---|---|
| 唯一出口 | 全仓禁止直调 `get_my_uid`，一律走 `get_uid(name)` |
| 成功缓存 TTL | **300s**（每账号每 5 分钟至多 1 次） |
| 失败退避 TTL | **60s**（防失效时疯狂打网） |
| 并发去重 | 每账号一把锁（惊群只打一次网） |
| 一致性校验 | uid 必须出现在历史 conv_id，否则判陈旧不缓存 |
| 调度 | 后台单线程按账号**错峰**刷新，避免同秒并发 |

`query/user` 是抖音标准的「我是谁」接口，非批量查他人资料 ⇒ **不触风控红线**；
5 分钟 1 次远低于风控阈值。

**残余风险（本次已收敛其一）**：
1. ✅ `force=True` 穿透后门 → 已改白名单制（见 §3.5）。
2. ⚠️ **进程内缓存不跨进程**：`_cache` 是进程内字典，而 backend / BCC /
   recv_daemon 各持一份 ⇒ 实际频次 ≈ `300s × 活跃进程数`。三个进程都活跃时
   同账号实际约 100s 一次（仍是安全量级，但**不是**设计意图的 300s）。
   未改（改动面大：需跨进程共享缓存或集中到单一进程探活），列为遗留观察项。

## 六、新增可复用判据

1. **凭证「有效」的判据必须落到「能完成一次真实写操作」**，
   而不是「字段非空」「探活通」「端口开着」——后三者都是
   **必要条件而非充分条件**，会把「能读不能写」的账号判成健康。
2. **健康检查的每一条 must 落到真实业务通路**：探测资源存在性（端口/文件/
   字段）只能当**辅助信号**，不能当结论。
3. **`docstring 契约` 与 `实现` 必须逐条对齐**：本项目本次发现在同一函数里
   docstring 承诺「拉列表」而实现「探端口」，且两处相隔仅 200 行，
   长期无人发现 ⇒ 复查健康检查类函数时**先读 docstring 再读实现并比对**。
4. **三态铁律再次适用**：轮询路径拿不到证据时必须报 `unknown`，
   **既不许伪造 ok 也不许谎报 fail**。
5. **错误文案必须区分「可重试」与「不可重试」**：把身份漂移写成
   「网络抖动」会让用户陷入无效重试循环。
6. **收敛「靠约定」的后门用显式白名单**，且**白名单内容必须实测函数名**。
7. **静态断言必须限定在可执行代码段**（剥 docstring / 行注释），
   否则说明性文字会造成假阳性。
