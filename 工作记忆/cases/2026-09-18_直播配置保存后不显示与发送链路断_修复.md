# 2026-09-18 · 直播监听配置「保存后无法显示 / 无法运行」修复 · v0.43.91

> 分支 `design/better-douyin` · 环境 `C:\temp\dyautodm_design`
> 守卫测试 `backend/test_live_config_guards.py`（8/8 通过，且对旧代码 6/6 全红）
> 用户报告原话：「直播监听配置保存后无法正常显示，导致无法运行」

## 一、结论先行：这不是一个 bug，是**四个独立缺陷**叠加出的一个症状

| # | 缺陷 | 层级 | 严重度 |
|---|---|---|---|
| 1 | 打包产物缺 `services.dm_dispatch` | 构建（PyInstaller hidden-import） | fatal：私信一条都发不出 |
| 2 | 新建配置草稿用「页面当前直播间」预填 `live_url` | 前端（数据污染） | error：配置指向别的直播间 |
| 3 | 保存后不通知父页 → 直播页下拉不刷新 | 前端（回调缺失） | error：保存了但看不到 |
| 4 | 唯一可写入口没有「私信词库」编辑 UI | 前端（入口缺失） | fatal：`dm_pool` 恒空 → 发送被拒 |

**用户看到的「无法显示」= 缺陷 3；「无法运行」= 缺陷 1 + 缺陷 4 叠加。**

**⚠️ 根因修正记录（2026-09-18，第一版结论不完整，保留以便后人不再误判）**

**第一版（错误）结论**：以为是「函数体 import 静态分析扫不到，且它没有顶层引用点，
所以漏打 hidden-import」。据此加了 `--hidden-import services.dm_dispatch` 并重打 ——
**重打后归档里依然 MISS**（模块数不变、产物大小逐字节相同），即该结论**被实测推翻**。

**第二版（实测坐实的真根因）**：`scripts/build_sidecar.py` 的
`inject_test_whitelist()`（仅在 `--debug-whitelist` 时执行）在 **`DY_DM_TEST_WHITELIST`
未设置**时会生成**语法非法的 Python**：

```python
_TEST_WHITELIST = {
,                    ← 空映射也拼了逗号 ⇒ SyntaxError: invalid syntax
}
TEST_WHITELIST_ON = True
```

而注入发生在 **PyInstaller 分析之前** ⇒ ModuleGraph 解析 `services/dm_dispatch.py`
时 SyntaxError ⇒ **整个模块被静默丢弃**。三条实锤：

1. 构建日志里**没有** `Analyzing hidden import 'services.dm_dispatch'` 这一行
   （只对镜像名 `dm_dispatch` 报 `not found`）——模块从未进入分析队列。
2. `Analysis-00.toc` 里 `config_tag.py` 在、**`dm_dispatch.py` 不在**；
   `PYZ-00.toc` 同样没有它。
3. 用 `ModuleGraph` 直接分析（不注入）时它 `reachable: True`、有 3 个 caller
   —— 说明它**本来是能被正常收录的**，唯一变量就是注入污染。

**为什么长期掩盖**：构建末尾 `restore_whitelist()` 会把源码还原成
`_TEST_WHITELIST = {}`（合法）⇒ 源码态 import 永远正常、单测全绿，
**只有真跑打包产物才暴露**。这也解释了它为何在 v0.43.91 之前一直没人发现。

**修复**：注入体生成抽成纯函数 `build_whitelist_block(WL)`，空 WL 走
`_TEST_WHITELIST = {}\nTEST_WHITELIST_ON = False`；注入后立即 `compile()` 自证，
语法非法则 `SystemExit` 中止构建（不许再静默丢模块）。守卫测试
`test_whitelist_injection_is_valid_python` 对 `{}` / 单条 / 多条三种 WL 逐一断言。
修复后重打：三份 sidecar **全部 OK**，模块数 3272 → **3273**，产物体积随之增大
（25364516 → 25394047）。

**顺带修正**：`--hidden-import services.dm_dispatch` 这个声明**仍然保留**
（它是正向防御：`services/dm_dispatch.py` 确实只在函数体内被 import，
依赖「PyInstaller 恰好能扫函数体」并不可靠），但必须清楚
**它不是本次事故的真因**——真因是注入污染。

### 判据 4（缺陷 2）：新建配置的 `live_url` 是**别的直播间**

```
[前] 配置管理弹窗草稿：room_id 输入框初值 = '992931212705'（页面当前直播间）
     → 用户改填 777666555
[保存后] 服务端： {"room_id":"777666555","live_url":"992931212705","name":"污染探针"}
```

根因：`RoomConfigManager.save()` 传 `{...draft}`，而草稿的 `live_url` 是弹窗打开时的
`currentRoom` 预填值；后端 `save_room_config:118` 的 `if body.live_url:` 优先取它，
于是 `room_id` 与 `live_url` 不一致。

### 判据 5（缺陷 3）：保存后父页不刷新

```
弹窗内新建成功 → 关闭弹窗 → 直播页下拉：['lox · 992931212705']   ← 新配置不在
整页 reload 后       → 直播页下拉：['污染探针 · 777666555','lox · 992931212705']
```

`loadRoomCfgs` 只挂在 `useEffect(..., [loadRoomCfgs])`，而 `loadRoomCfgs` 依赖 `[ready, api]`
（稳定）→ 只在首次 ready 时执行一次；弹窗保存后用内部 `load()` 刷新**自己**的列表，
从不通知父页。`RoomConfigManager` 的 props 里只有 `onApply`，没有写操作完成回调。

### 判据 6（缺陷 4）：词库无处可填 → 发送恒被拒

- 弹窗全字段实测：直播间号/备注名/监听账号/发送上限/间隔/延迟抖动/连麦方式/自动申请连麦/强制重扫
  —— **无「私信词库」**；而直播页明确提示「该配置尚未设置词库 · 请到「配置管理」补充」。
- 服务端 `config.dm_pool = []`。
- 旧 `pages/live.tsx` 有词库编辑器（`私信词库`/`保存词库`），v0.43.34 重构「直播页零手填」时
  被删除，且**没有在唯一可写入口补回**。
- 后果链：`dm_pool=[]` → `_make_pick_dm_message()` 返回 `None` → `dispatch._do_send`
  得到 `content=""` → `dm_dispatch.submit_by_uid` 首行 `if not text: return 拒绝
  「账号/对端 uid/内容缺失」` → **一条也发不出**。

## 四、工具固化（本次真正的收获）

### 4.1 静态候选：`scripts/diag/scan_lazy_imports.py`

扫全仓「函数体内延迟 import 的本地模块」与 `build_sidecar.py` 的 hidden-import 清单做差集。
**静态差集有大量假阳性**（实测 22 个候选里只有 3 个真缺）——因为 PyInstaller 确实能扫到
大部分函数体 import。故它只作**候选**用途。

### 4.2 权威判据：`scripts/diag/list_archive_modules.py`

直接读产物 exe 的 CArchive → PYZ 两层归档，列出**真正打包的模块名**。
这是「某模块到底进没进产物」的唯一可信判据 —— **grep 二进制永远是假阴性**（代码在压缩 PYZ 里）。

```bash
python scripts/diag/list_archive_modules.py <exe> services.dm_dispatch
```

### 4.3 判型铁律（本次方法论要点）

> **「日志里出现 `No module named 'X'`」+「其余同类模块都在」⇒ 优先怀疑该模块的
> 唯一引用点在函数体内**。不要先怀疑打包缓存、也不要 clean 重打包（那是历史踩过的坑：
> 每次 14 分钟且不治本）。用 `list_archive_modules.py` 一条命令坐实。
