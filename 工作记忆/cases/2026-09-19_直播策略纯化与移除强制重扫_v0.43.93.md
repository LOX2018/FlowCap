# 2026-09-19 直播「策略纯化 / 去子 tab / 移除强制重扫」重构（v0.43.93）

> 本文是 v0.43.92 契约的**推翻与替代**。v0.43.92 的「三 tab 子视图 + 目标直播间独立页」
> 被用户否决；最终形态见下。查直播策略务必以本文为准。

## 一、设计意图（Design Intent）

**模块**：直播监听页 `frontend/src/components/live/live-page.tsx` +
策略弹窗 `RoomConfigPage.tsx` + 后端 `api/live_config.py`。

**用户最终原话（设计契约）**：

> 「把直播策略放到直播监听页面中『直播间』板块的配置标签中，该编辑页面中**只保留
> 直播策略**，策略以外的全部删除。直播间管理也是一样，不需要『监听 / 目标直播间 /
> 配置标签』tab 切换栏也不需要子 tab 页面。还有『强制重扫』策略早就废弃了，
> 给彻底移除。」

**契约分解**：

| 编号 | 契约 | 判据 |
|---|---|---|
| C1 | 策略编辑页 = 参数唯一可写入口，**只含策略** | JSX 无「备注名/直播间号/直播链接/强制重扫」 |
| C2 | 无子 tab 切换栏、无「目标直播间」页 | `subView` 不存在；`TargetRoomPage.tsx` 与 `api/target_rooms.py` 已删 |
| C3 | 策略以**弹窗**提供，入口在「直播间」板块策略下拉旁 | `data-od-id="live-strategy-modal"` + 「管理策略」按钮 |
| C4 | 「强制重扫」彻底移除 | 全仓业务代码无 `force_rescan` / `forceRescan` |
| C5 | 多策略并存取代「反复覆盖」 | kv `live_room_configs` 按 `id` 存多条 |

**概念边界（本次最重要的裁定）**：
- **策略（strategy）= 怎么发**：发送上限 / 间隔 / 延迟抖动 / 私信词库 / 自动申请连麦 /
  连麦方式 / 监听账号。这些是「跨直播间可复用」的参数。
- **身份（identity）= 发给哪个直播间**：直播间号 / URL / 备注名。
  归「直播间」板块的输入框 **与新建任务流程**，**不进策略**。
  理由：策略要能跨房间复用，绑定房间号就退化成「一房一策略」＝旧的反复覆盖形态。

## 二、观察到的偏差（修复前状态）

| 偏差 | 现象 |
|---|---|
| 策略页混入身份字段 | `RoomConfigPage.tsx` 含备注名 / 直播间号或 URL / 直播链接 / 强制重扫 |
| 出现三 tab 与子页 | `live-page.tsx` 有 `subView: monitor\|targets\|configs`；`TargetRoomPage.tsx` 444 行 |
| 废弃策略仍在链路 | `force_rescan` 贯穿 `models/task.py`、`app_config_schema.py`、`auto_dm.py`、`api/tasks.py`、前端 `client.ts` |

## 三、根因（RCA）

**根因**：上一版把「配置管理」当成「直播间管理」来处理，导致身份与策略耦合。
耦合的后果链：
身份字段进策略 → 策略无法跨房间复用 → 每条策略只能服务一个房间 →
用户只能「对现有配置反复覆盖」→ 退回旧形态。

即：**这不是 UI 布局问题，是数据契约的职责划分错误**。
所以修复必须落在契约层（字段白名单），而非仅调 UI。

**强制重扫**：属已废弃策略；其残留使 `apply_runtime_config` 的
`not_applied` 多出一项，且新旧配置迁移时产生语义歧义 → 一并清除。

## 六、踩坑（判据自身缺陷，非功能缺陷）

1. **静态判据误判自己的文档注释**：`A9b` 用整文件 grep 找「直播链接/强制重扫」，
   而文件头注释正引用用户原话「强制重扫」→ 假阳性。
   修法：把判据收紧到 `split("export default function RoomConfigPage")[-1]` 的 **JSX 段**。
   → **教训：文本判据必须限定在代码段，注释是合法的历史记录，不是缺陷。**
2. **数 import 行当「tab 数量」**：`SegmentedTabs` 在 import 行也出现。
   改判 `live_fe.count("<SegmentedTabs")`（JSX 使用处）。
3. **删除后剩 N 条的写法脆弱**：原断言 `len(list)==3`，被删项数一变就误报。
   改为「差集 == 被删的那一个」。
4. **行尾混合**：先前用 Python 追加导致 CRLF/LF 混排（`\r\r`），
   会让精确匹配失败。改前先归一化行尾再 patch。

## 九、实机验证中发现的第二个真缺口：存量记录未归一化

**现象**（部署产物 `GET /api/live/config-tags` 实测）：

```json
{"room_id":"992931212705","updated_at":1789806657,"name":"21","live_url":"992931212705",
 "max_target":100,"interval":60.0,"delay":"50,120","force_rescan":false,
 "dm_pool":[],"auto_link_mic":false,"link_mic_mode":"audio"}
```

旧的「一房一配置」记录（键=直播间号，体内带 `room_id` / `live_url` / `force_rescan`）
在读取时**原样返回** → 前端仍会看到「策略里带直播间号」，等于把用户刚要求删掉的东西
又露出来。写路径（`_FIELDS` 白名单）已干净，**漏的是读路径**。

**修法**：加 `_normalize_stored(cfg, key)` 作为读路径**统一出口**
（`list_strategies` / `get_strategy`），读时收敛：

- 剥除 `room_id` / `live_url` / `force_rescan` / `forceRescan` / `tag_id`；
- `id` 一律取**键名**（键才是真源，历史 `id` 字段不可信）；
- 补齐缺失策略键（`name` / `max_target` / … / `link_mic_mode`）。

**只在读时收敛、不写回**（避免「读操作产生写副作用」）；用户下次保存才落盘为新形态。

**教训（可复用）**：契约变更若涉及**存量数据**，写路径白名单 + **读路径归一化**必须成对做。
只做写侧 → 老数据照旧漏给前端，用户看到的是「你说删了但还在」。

**判据**：`verify_live_strategy.py` B7/B7b/B7c —— 塞一条旧形态记录进 kv，
断言读出来已无身份字段、id 取键名、参数保留。

## 十、用户实机反馈：策略弹窗缺「新增入口」

**用户原话**：「该页面没有新增入口」（附元素取址报告：
`button[data-od-id="live-room-configs"]`，前端版本 0.43.93）。

**核实**（未凭猜）：源码里弹窗只提供「清空表单 / 保存策略 / 更新策略」，
没有**显式"新建"按钮**；空态文案是"填写下方表单保存第一条"。
即：新建在功能上可行（`id: undefined` → 后端生成 `lc_*`），但**入口不可发现** ——
用户在编辑态下更无从回到"新建"心智模型。

**修法**：列表区加标题栏 `已保存策略（N）` + 右上 **`＋ 新建策略`**
（`data-od-id="strategy-new"`，`onClick` 清空表单并退出编辑态）。

**教训（可复用）**：**「功能可达」≠「入口可发现」**。
当把整页改成弹窗/内联时，必须显式检查"新增/创建"这类**主操作**是否有
一眼可见的入口 —— 仅靠「清空表单」按钮不能替代「新建」。

**判据**：`verify_live_strategy.py` A9d + `test_live_config_guards.py`
`test_explicit_new_strategy_entry`（断言 `data-od-id="strategy-new"` 存在）。
