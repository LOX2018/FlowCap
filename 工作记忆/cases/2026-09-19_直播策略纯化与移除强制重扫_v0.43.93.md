# 2026-09-19 直播「策略纯化 / 去子 tab / 移除强制重扫」重构（v0.43.93）

> 本文是 v0.43.92 契约的**推翻与替代**。v0.43.92 的「三 tab 子视图 + 目标直播间独立页」
> 被用户否决；最终形态见下。查直播策略务必以本文为准。

## 一、设计意图（Design Intent）

**模块**：直播监听页 `frontend/src/components/live/live-page.tsx` +
策略弹窗 `RoomConfigPage.tsx` + 后端 `api/live_config.py`。

**用户最终原话（设计契约）**：

> 「把直播策略放到直播监听页面中『直播间』板块的配置标签中，该编辑页面中**只保留
> 直播策略**，策略以外的全部删除。直播间管理也是一样，不需要『监听 / 目标直播间 /
> 配置标签』tab 切换栏也不需要子 tab 页面。还有『强制重扫』策略早就废弃了，
> 给彻底移除。」

**契约分解**：

| 编号 | 契约 | 判据 |
|---|---|---|
| C1 | 策略编辑页 = 参数唯一可写入口，**只含策略** | JSX 无「备注名/直播间号/直播链接/强制重扫」 |
| C2 | 无子 tab 切换栏、无「目标直播间」页 | `subView` 不存在；`TargetRoomPage.tsx` 与 `api/target_rooms.py` 已删 |
| C3 | 策略以**弹窗**提供，入口在「直播间」板块策略下拉旁 | `data-od-id="live-strategy-modal"` + 「管理策略」按钮 |
| C4 | 「强制重扫」彻底移除 | 全仓业务代码无 `force_rescan` / `forceRescan` |
| C5 | 多策略并存取代「反复覆盖」 | kv `live_room_configs` 按 `id` 存多条 |

**概念边界（本次最重要的裁定）**：
- **策略（strategy）= 怎么发**：发送上限 / 间隔 / 延迟抖动 / 私信词库 / 自动申请连麦 /
  连麦方式 / 监听账号。这些是「跨直播间可复用」的参数。
- **身份（identity）= 发给哪个直播间**：直播间号 / URL / 备注名。
  归「直播间」板块的输入框 **与新建任务流程**，**不进策略**。
  理由：策略要能跨房间复用，绑定房间号就退化成「一房一策略」＝旧的反复覆盖形态。

## 三、根因（RCA）

**根因**：上一版把「配置管理」当成「直播间管理」来处理，导致身份与策略耦合。
耦合的后果链：
身份字段进策略 → 策略无法跨房间复用 → 每条策略只能服务一个房间 →
用户只能「对现有配置反复覆盖」→ 退回旧形态。

即：**这不是 UI 布局问题，是数据契约的职责划分错误**。
所以修复必须落在契约层（字段白名单），而非仅调 UI。

**强制重扫**：属已废弃策略；其残留使 `apply_runtime_config` 的
`not_applied` 多出一项，且新旧配置迁移时产生语义歧义 → 一并清除。

## 九、实机验证中发现的第二个真缺口：存量记录未归一化

**现象**（部署产物 `GET /api/live/config-tags` 实测）：

```json
{"room_id":"992931212705","updated_at":1789806657,"name":"21","live_url":"992931212705",
 "max_target":100,"interval":60.0,"delay":"50,120","force_rescan":false,
 "dm_pool":[],"auto_link_mic":false,"link_mic_mode":"audio"}
```

旧的「一房一配置」记录（键=直播间号，体内带 `room_id` / `live_url` / `force_rescan`）
在读取时**原样返回** → 前端仍会看到「策略里带直播间号」，等于把用户刚要求删掉的东西
又露出来。写路径（`_FIELDS` 白名单）已干净，**漏的是读路径**。

**修法**：加 `_normalize_stored(cfg, key)` 作为读路径**统一出口**
（`list_strategies` / `get_strategy`），读时收敛：

- 剥除 `room_id` / `live_url` / `force_rescan` / `forceRescan` / `tag_id`；
- `id` 一律取**键名**（键才是真源，历史 `id` 字段不可信）；
- 补齐缺失策略键（`name` / `max_target` / … / `link_mic_mode`）。

**只在读时收敛、不写回**（避免「读操作产生写副作用」）；用户下次保存才落盘为新形态。

**教训（可复用）**：契约变更若涉及**存量数据**，写路径白名单 + **读路径归一化**必须成对做。
只做写侧 → 老数据照旧漏给前端，用户看到的是「你说删了但还在」。

**判据**：`verify_live_strategy.py` B7/B7b/B7c —— 塞一条旧形态记录进 kv，
断言读出来已无身份字段、id 取键名、参数保留。

## 十、用户实机反馈：策略弹窗缺「新增入口」

**用户原话**：「该页面没有新增入口」（附元素取址报告：
`button[data-od-id="live-room-configs"]`，前端版本 0.43.93）。

**核实**（未凭猜）：源码里弹窗只提供「清空表单 / 保存策略 / 更新策略」，
没有**显式"新建"按钮**；空态文案是"填写下方表单保存第一条"。
即：新建在功能上可行（`id: undefined` → 后端生成 `lc_*`），但**入口不可发现** ——
用户在编辑态下更无从回到"新建"心智模型。

**修法**：列表区加标题栏 `已保存策略（N）` + 右上 **`＋ 新建策略`**
（`data-od-id="strategy-new"`，`onClick` 清空表单并退出编辑态）。

**教训（可复用）**：**「功能可达」≠「入口可发现」**。
当把整页改成弹窗/内联时，必须显式检查"新增/创建"这类**主操作**是否有
一眼可见的入口 —— 仅靠「清空表单」按钮不能替代「新建」。

**判据**：`verify_live_strategy.py` A9d + `test_live_config_guards.py`
`test_explicit_new_strategy_entry`（断言 `data-od-id="strategy-new"` 存在）。

## 十一、用户第二轮反馈：「新建」点击无变化 + 位置错误（v0.43.94）

**用户原话**：
> 「首先你做的 `[data-od-id="strategy-new"]` 点击后没有任何变化，
>  第二这个按钮应该放到 `[data-od-id="live-strategy-modal"] > div.flex.justify-end.gap-2
>  > button:nth-of-type(3)` 左侧。」

### 根因（执行链追踪，非猜测）

弹窗 `useEffect([open])` 打开时**已经**执行 `setDraft(EMPTY_DRAFT)` + `setEditing(null)`；
而「新建策略」按钮做的**完全是同一件事** ⇒ 默认态下点击是**幂等空操作**，
React 状态无变化 ⇒ 零视觉反馈。用户看到的就是"点了没反应"。

**这不是 bug 而是设计缺陷**：把一个"复位"操作命名为"新建"，且没有任何
状态标记让用户看到"我现在处于新建态"。

### 修法（三件事一起做，缺一不可）

1. **位置**：从列表标题栏移到**页脚**，排在「保存/更新策略」**左侧**
   （`清空表单` 按钮直接改造成 `＋ 新建策略`，DOM 顺序天然满足 nth-of-type(3) 之前）。
2. **可见状态**：编辑中时，被编辑的那条列表项标题加 `●` 前缀
   —— 新建时 `●` 消失，用户能"看见"状态切换。
3. **显式反馈**：点击时 `push("已进入「新建策略」：填写策略名称后点「保存策略」")`。

### 教训（可复用，两条都很重要）

1. **「同名同义的操作」不会产生可见变化**。任何"新建/重置"入口必须同时改变
   **至少一处可见 UI 状态**（标题、标记、按钮文案、toast），否则用户判定为"坏了"。
   复位型操作尤其危险 —— 它在默认态下天然无副作用。
2. **版式要求用真实几何断言，不用 DOM 顺序猜**。用户给的是 CSS 选择器
   （`button:nth-of-type(3)` 左侧），验证必须量 `getBoundingClientRect().x`。

## 十二、我自己的两个误判（验证脚本缺陷，务必别重犯）

### 误判 1：广撒网拦截 `**/api/**` 导致页面空白，被误读为"视图不对"

首版 `verify_live_strategy_ui.py` 用 `page.route("**/api/**", ...)` 把所有 API 都
fulfill 成 `{"ok":true}` → **打爆了应用的启动门禁**（鉴权/版本/就绪校验全被伪响应
污染），页面渲染成空白，探针读到 `document.querySelectorAll('button')` 全空。

我却据此断言"直播页默认是多账户总览视图、需要先点进入监听" —— **完全错误**。
用户当场纠正："直播页默认明明是「单账户」视图"。
回源码核对：`const [viewMode, setViewMode] = useState<"single" | "grid">("single")`
（`live-page.tsx:52`）—— 初值就是 `single`，`live-room-configs` 一直都在。

**教训**：
1. **拦截要精准**（`**/api/live/config-tags**`），绝不要广撒网 —— 应用的启动门禁
   本身就是一串 API 调用，伪响应会把"页面能否渲染"这个前提毁掉。
2. **页面空白时先怀疑探针，不是先怀疑被测代码**。
3. **推翻自己结论前先回源码核对默认值**，别用"探针观察到 X"替代"源码写着 X"。

### 误判 2：拿"body 里出现 toast 文案"当 toast 渲染判据

预览 harness 的 `push` 实现是 `console.log("[push]", m)`（不渲染 toast），
所以 `document.body.innerText.includes(...)` 永远为假 → 假失败。

**教训**：断言前先确认**被测环境里该行为的真实实现**（harness vs 真实 app 不同），
不要假设"调了 push 就有 toast"。改法：harness 里捕获 push 调用；
真机 toast 另用 computer_use 目视确认（真实 app 的 push = `setToasts` → 渲染，`App.tsx:572`）。

## 十三、第三轮反馈：列表区（用户指明的元素）仍无变化（v0.43.95）

**用户原话**：
> 「点击新增后 `[data-od-id="live-strategy-modal"] > div.p-4 > div:nth-of-type(1)
>  > div.flex.flex-wrap.items-center` 并无任何变化。」

### 为什么 v0.43.94 没修好（重要：同一根因的第二次复发）

v0.43.94 我只改了**表单区 + 页脚**（清空表单、按钮文案、toast），
但用户指的元素是**列表区**（`.p-4 > div:nth-of-type(1)` 下那一行）。

**根本原因比 94 版理解的更深**：该弹窗**默认态 == 新建态**
（打开时 `useEffect` 就执行 `setDraft(EMPTY_DRAFT)` + `setEditing(null)`）。
所以"点新建"在**列表区**永远看不出差别 —— 因为列表本来就没有"新建态"这个视觉概念。

**教训（本轮最重要的一条，已两次踩）**：
> **修"操作无可见反馈"时，必须逐一定位"用户会盯着看的那个元素"，并在那个元素上造出变化。**
> 改别处（表单/页脚/toast）都不算 —— 用户判断依据是他指的那个 DOM 区域。

### 修法（让"新建态"在列表区**可见**）

| 改动 | 效果 |
|---|---|
| 新增 `newMode` 状态 | 显式区分"新建态"与"浏览态" |
| 列表区插入 **草稿行** `data-od-id="strategy-draft-row"` | 虚线高亮行「● 新策略（未保存）」→ **用户指的那个元素真的变了** |
| 编辑中的列表项加高亮（`border-l-2 accent` + `✎ 编辑中：`） | 编辑态在列表区也可见 |
| 按钮变 `✕ 取消新建` + toast | 连点两次 = 取消新建（**也**有可见变化，不做空操作） |
| 新建时聚焦名称输入框 | 用户可立即输入 |
| 表单上方加态标题（新建策略 / 新建策略（草稿）/ 编辑已有策略） | 第一眼可辨当前态 |

### 判据（必须打在用户指的元素上）

`verify_live_strategy_ui.py` 新增：
- `R2b` 点击后 **列表区出现草稿行**（`strategy-draft-row` 存在）
- `R2c` 列表区 **DOM 长度确实变化**（证明非空操作）
- `R2d` 再点一次 → 草稿行消失（连点也非空操作）
- `R3b2` 编辑态点新建 → 同时出现草稿行

### 附带修正
`guards` 的 `test_explicit_new_strategy_entry` 判据从"页脚有按钮"升级为
"**列表区有草稿行** + 存在 `newMode` + 存在 `startNew`" ——
防止再次出现"按钮在、但点了看不到变化"这种**功能可达而反馈不可见**的缺陷。

>  新建策略的按钮，改成策略名称，只要有变化或者有写入，则默认变成草稿模式，然后通过
>  点击保存策略就可以新建完成。把 `[data-od-id="strategy-new"]` 改回清空表单。
>  `[data-od-id="live-strategy-modal"] > div.p-4 > div.mb-1.font-semibold` 改成策略详情。」

### 设计裁定（比前三轮更根本）

用户否定的不是"按钮位置"，而是**"新建"作为一个独立动作本身**：

> 「新建策略按钮的本质也需要通过保存策略按钮才能固化写入」——
> 既然新建**只能**由「保存」完成，那"新建按钮"就是一个**多余且误导的动作**。

**新契约**：**没有"新建"动作，只有"草稿态"**。
- 表单任意字段一改（`touch()` 统一入口）→ `dirty = true` → 进入草稿模式
- 草稿模式在**列表区**可见（`strategy-draft-row` 显示「● 草稿（未保存）」）
- 点「保存策略」→ 落库（服务端生成 `lc_*`）→ 即"新建完成"
- `[data-od-id="strategy-new"]` **回归清空表单本义**（清空 + 退出编辑 + 退出草稿）
- 标题区固定为「策略详情」（用户指定；不再随状态改成"新建策略/编辑已有策略"）

### 编辑态与草稿态的互斥

`draftActive = dirty && !editing` —— **编辑已有策略时**不显示草稿行
（那一条已在列表里，用 `✎ 编辑中` 高亮标记即可），避免"编辑"被误当成"新建"。

### 四轮演进（同一处 UI，值得记住的收敛路径）

| 版本 | 形态 | 用户否决理由 |
|---|---|---|
| v0.43.94 | 页脚加「＋ 新建策略」按钮，点击复位表单 | 「点击后没有任何变化」（复位与默认态等价） |
| v0.43.95 | 点击在列表区插草稿行 + 按钮变「取消新建」 | （未否决，但见下一轮） |
| v0.43.96 | **取消新建按钮**，改动即草稿，保存即新建 | 本轮定调（更根本的设计简化） |

**最大教训**：
> 当用户反复要求"某个按钮要有反应"时，先问一句 —— **这个动作是不是本该不存在？**
> "新建 + 保存"两步其实可以收敛成"改动（草稿）+ 保存"一步。
> 反复给一个多余动作加反馈，不如直接删掉这个动作。
