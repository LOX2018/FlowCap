﻿# 13_会员管理体系（v0.37.0，2026-09-09 落地）

## 一、需求与用户决策（2026-09-09 三项澄清，均为用户选定）

- 整个项目引入会员管理体系，登录后使用，本地存储和管理，不接云端，目的是**隔离用户数据和加密保护**。
- 数据隔离粒度：**完全隔离**——每个会员独立数据空间（各自的抖音账号、会话数据、配置互相不可见）。
- 加密程度：**口令哈希 + 凭证加密**——会员口令 PBKDF2 加盐哈希存储；账号凭证（.env 里 cookie 等）用「主密钥」加密落盘，主密钥由会员口令派生包裹。口令不存明文，拖走文件也读不出凭证。
- 会员产生方式：**开放自助注册**（本地软件场景），任何人在登录页可注册，无管理员审批。

## 二、架构（实测证真）

```
<app_root>/members/registry.json          全局会员注册表（唯一跨会员共享文件）
  每会员: member_id / username / created_at
        / pwd {salt, iterations, hash}     PBKDF2-HMAC-SHA256 600_000 轮, 16B 盐
        / wrapped_key                      Fernet(sha256(口令)) 加密的主密钥
<app_root>/members/<member_id>/           每会员独立数据空间
  data/dyautodm.db                        独立 SQLite（全部业务表）
  auto_dm/accounts/<name>/.env.enc        独立账号凭证（整文件 Fernet 加密）
  auto_dm/accounts/<name>/profile/        独立浏览器 profile
  data/origin_images/                     独立图片缓存
```

- 主密钥：每会员 32B 随机（Fernet key），登录时用口令解包，**只在进程内存/子进程环境变量（DY_MEMBER_KEY），绝不写盘**。
- 运行时切空间：登录成功 → `member_ctx.set_current()` 注入 `DY_MEMBER` + `DY_MEMBER_KEY` 到 os.environ → DB 连接、账号目录、守护进程全部自动跟随。
- 会话 token：进程内随机 hex（X-Member-Token 头），重启即失效，12h TTL 滑动续期。

## 四、为什么前端守护启动必须改走 backend（关键设计决策）

Rust 侧 spawn 的 BCC/recv_daemon 继承的是 **Tauri 主进程环境变量**（不含 DY_MEMBER/DY_MEMBER_KEY），这些子进程读会员空间的加密凭证时主密钥不可用 → 失败。
backend 进程内 spawn（ensure_bcc / daemon_launcher）时 os.environ 已含会员变量 → 子进程正常解密。
因此 accounts.tsx 的 startBrowserDaemonReady/startRecvDaemon 全部替换为 fetch backend 的 ensure-bcc / ensure-recv 端点；sidecar.ts 的 Rust spawn 函数保留但不再被账号页调用。

## 五、登录时初始化链路（api/member.py login）

1. authenticate（口令验证 + 主密钥解包）
2. create_session + set_current（注入环境变量）
3. database.reset_connection() + get_db()（按会员路径重建 + 建表/迁移）
4. migrate_plain_envs（会员空间内明文 .env → 加密 .enc，幂等）
5. 逐账号 ensure_daemons_for（等效原 lifespan 的 _auto_start_daemons）

登出对称：clear_current + reset_connection（DB 回默认路径）。

## 七、铁律与注意（后续开发必读）

- **新增任何 .env 读点必须走 member_ctx.parse_env_dict**（或先 is_member_env 判断）；直接 open/dotenv_values 会读到密文或漏 .enc。
- **新增任何 .env 写点必须走 member_ctx.write_env_file**；直接 dotenv set_key 会在会员空间写出明文凭证（等于加密体系破洞）。
- **新增任何子进程 spawn 必须透传会员环境变量**（参考 daemon_launcher._spawn_sidecar 的 env 构造）。
- **新增任何 DB 访问必须走 database.get_db()**（自带会员一致性守卫）；禁止模块级缓存连接。
- **新增 API 路由默认被中间件拦截**，属预期；健康探测类端点若被前端启动探测依赖，需加入 main.py `_MEMBER_EXEMPT`。
- 未登录时 lifespan 跳过守护拉起/uid 预热/verify 预热——这些在登录时由 login 路由补做。
- 端口分配未按会员隔离：两个会员的同名账号会撞同端口（同名单账号场景）。当前单会员运行时无问题；若未来支持多会员同时在线需重设计端口段。
- backend 进程是**单会员运行时**（set_current 覆盖式）；多会员同时在线需引入会话级上下文（当前不做）。

## 八、遗留事项

- `/api/live/ws`（WebSocket）豁免了 token 校验（浏览器 WebSocket 无法自定义 header）；本地单机场景可接受，后续可改用首帧鉴权。
- 会员管理页（列出/删除其他会员）未做 UI——API 已有（/api/member/list、/delete），需要时在设置页加卡片。
- 存量数据迁移：现有默认路径下的 DB/账号属于「未登录回退空间」，首次使用会员体系需在会员空间内重新扫码添加账号（或手工把 accounts/ 目录拷入会员空间后在登录态触发 migrate_plain_envs 加密）。

## 九、登录链路治理与账号引导（2026-09-08 实测修复）

### 9.1 事件循环冻结（用户体感「登录时后端卡死」）

**根因是四段阻塞叠加**，不是单点：

1. `login` 同步直调 `member_store.authenticate`（PBKDF2 600k 轮 ×2，
   本机实测单轮 **341ms**，双轮 ~700ms）；
2. `register` / `change_password` / `delete_member` 同样含 600k 轮派生，同步直调；
3. 登录请求内同步跑 `ensure_daemons_for`：每账号 4 次 socket 探测（各 0.2~0.3s）
   + `subprocess.Popen` 拉起 onefile（解包瞬间打满 CPU/磁盘）；
4. `migrate_plain_envs` 同步文件 I/O。

**修复**：

- 四个会员端点全部 `await asyncio.to_thread(...)` 包裹；
- 登录后初始化（.env 加密迁移 + 账号引导 + 守护拉起）整体抽出为
  `api/member.py::_post_login_init` 后台任务，内部重活再丢 `to_thread`；
  登录请求路径只剩「认证 + DB 重建 + 返回 token」，**前端不再感知卡顿**。

### 9.2 账号引导（bootstrap）：登录后守护永不拉起的根因

**完整因果链（实锤）**：

```
账号索引存 SQLite kv_store.accounts_index（全局 DB）
  → 会员登录后 database.get_db() 切到 <space>/data/dyautodm.db（空索引）
  → list_accounts() 返回 0
  → 守护（BCC / recv_daemon）永不拉起
  → 前端一直显示「拉后端对齐」无限转
```

即使只复制索引也不够：`accounts/<name>/.env` 与 `profile` 仍不在会员空间
→ BCC 报 profile 不存在（BCC 的 profile 由 .env 同目录推导）→ 需重新扫码（风控成本）。

**修复 `_bootstrap_accounts_index()`（幂等，登录后后台执行）**：

1. 对全局 `<app_root>/auto_dm/accounts/<name>` 建 **Windows junction** 到会员空间同名路径
   （`cmd /c mklink /J`）—— `.env` 与 profile **物理同一份**：
   零复制（profile 达 172~410MB）、零重扫码、**不违反单 profile 铁律**（还是那一个目录）；
2. 全局 DB 的 `accounts_index` 复制进会员 DB 的 kv_store（仅会员侧为空时）；
3. 已有账号/已建 junction 的会员空间不受影响。

> ⚠️ `mklink` 输出是 GBK，Python `subprocess` 读取必须 `decode("gbk", errors="replace")`，
> UTF-8 解码直接抛异常（与 tasklist/taskkill 同坑）。

### 9.3 启动预对齐（用户体验需求，用户原话）

> 「我需要的是前后端先对齐后才出现登录框，别登录后还一直等，体验感极差」

**实现**：

- `backend/main.py` lifespan 未登录时后台线程跑 `_prealign_on_startup()`：
  读全局索引 → `ensure_daemons_for(..., skip_cooldown=True)` 拉起全部守护。
- `accounts.ensure_bcc` 新增 `skip_cooldown` 参数：豁免 30s 启动冷静期
  （预对齐是**有意**拉起，不是当初要防的「快闪误触发」）。
- 新增免鉴权端点 `GET /api/ready`（加入 `_MEMBER_EXEMPT`），返回
  `{"ok":true,"daemons_ready":bool,"accounts":n}`。
- 前端 `App.tsx`：启动轮询 `/api/ready`（1.5s），`daemons_ready=true` 才渲染
  `MemberGate`，否则保持 `BootSplash`。

**实测**（16:03）：启动后数秒内 `[prealign] 启动预对齐完成: 2/2 个账号守护就绪`，
`/api/ready` 返回 `{"ok":true,"daemons_ready":true,"accounts":2}`。
体验闭环：闪屏（秒级对齐）→ 登录框 → 登录后立即进主界面。

### 9.4 已知限制

- **member token 是进程内随机 hex，backend 重启即失效** → 每次重启都要重新登录。
  单机软件场景下偏苛刻，后续可把 token 存会员空间加密文件实现跨重启保持登录。
- 账号目录 junction 是 Windows 方案；跨平台需改用 symlink（逻辑同）。

## 十、会员数据空间隔离原则（2026-09-08 用户明确决策）

### 决策

**新会员的数据空间默认完全独立（空），不自动继承任何历史数据。**

历史数据（全局空间 `<root>/data/dyautodm.db` 里的会话/消息/任务/采集记录）
**只在用户明确要求时，由用户手动执行迁移脚本带入指定会员空间**。

> 用户原话：「这次是因为首次创建，之前的数据都是我的数据，但后续创建的数据不一定是我的。」

### 背景

会员体系（v0.37.0）登录后 `database.get_db()` 切到会员空间库
`<space>/data/dyautodm.db`。首次创建会员时该库是空的 ——
私信中心会话列表全空，容易被误判为「数据丢失」。

实测（2026-09-08）：全局库 356 会话/845 消息，会员库 0/0。

### ✅ 正确做法：手动一次性迁移

脚本：`backend/scripts/migrate_global_to_member.py`（幂等，可重复执行）

```bash
export DY_APP_ROOT="C:	emp\dyautodm_design"
python backend/scripts/migrate_global_to_member.py <member_id>
```

特性：
- 整表复制（`INSERT OR IGNORE`，重复执行安全）；
- **仅当会员库该表为空时才迁移**，已有数据绝不覆盖；
- 全局库原样保留作备份，不删除、不移动；
- 迁移前建议先备份会员库（脚本外手动 `cp`）。

已迁移表：`dm_conversations` / `dm_messages` / `tasks` /
`crawl_history` / `dm_uid_sink` / `kv_store`。

### ❌ 禁止做法

- **不要在登录流程里自动迁移历史数据**（曾规划 `_bootstrap_member_data()`
  挂到 `_post_login_init`，已被用户否决并撤销）。
  自动迁移会让每个新建会员都继承别人的历史数据，直接破坏隔离语义。
- 不要用「共享全局 DB」绕过隔离（同样是破坏设计）。

### 与账号引导（§9.2）的区别

| 项 | 是否自动 | 原因 |
|---|---|---|
| 账号引导（junction + 索引） | ✅ 登录后自动 | 账号是设备资产，会员空间需要「看见」它们才能工作 |
| 历史业务数据迁移 | ❌ 手动 | 数据归属用户，新会员应独立起步 |

## 十一、会员加密凭证读取失效事故（2026-09-10，commit `d0b55f3`）

### 现象
指纹浏览器登录态正常、**网页端私信能正常发送**，但**账号管理页校验持续异常**
（wp 引擎 `fail`「凭证未就绪」、uid=None），并不断触发无谓的「自动重捕获」。

### 根因 1：`is_member_env` 只靠路径前缀判定（凭证读取失效）

```
member_space_root() 依赖 current()（进程内内存会话）
   ↓ 独立进程 / 子进程 / 会话态未注入 → 返回 None
is_member_env(env_path) 恒 False
   ↓ parse_env_dict 走明文分支
磁盘上实际存在的 <env_path>.enc 被无视
   ↓ credentials_complete → "账号 .env 不存在"
wp 引擎 fail → 自动重捕获循环（弹浏览器 / 读 profile / 写回，全是无用功）
```

**凭证本身完全正常**（实测：解密后 7 键齐全，探活 uid 正确）。

### 修复：双判据 + 三层回退

`services/member_ctx.py`：

1. **`is_member_env` 改双判据**（任一成立即按加密凭证处理）
   - ① 路径位于会员数据空间内（原语义保留）
   - ② **文件事实**：存在 `<env_path>.enc` **且** 主密钥可用 → 以磁盘事实为准，
     不再依赖路径归属与进程会话态（**根治**：路径错配、会话丢失都不再致命）
2. **`master_key()` 加第三层回退**：内存会话 → 环境变量（`DY_MEMBER_KEY`）→
   **盘上 `members/.session.json`**（带 mtime 缓存）。独立进程也能解密。
3. **`member_space_root()` / `accounts_root()`**：member_id 同样加盘上会话回退，
   否则会拼出 `<members>/auto_dm/accounts`（**空 id 目录**，路径错假的另一表现）。

### 根因 2：`uid_probe` 配置常量裸名引用 → NameError（探活崩溃）

`services/uid_probe.py` 里 `LOCK_WAIT` / `UID_TTL_OK` / `UID_TTL_FAIL` 是
**PEP 562 `__getattr__` 惰性名**（`_LAZY_MAP` + `cfg()`）——
**只有 `module.attr` 访问才触发，函数内全局名查找不触发**。
函数内裸写 `lk.acquire(timeout=LOCK_WAIT)` → `NameError: name 'LOCK_WAIT' is not defined`
→ 探活直接崩 → `uid=None` → 校验 warn「**捕获齐全但探活失败**」（凭证其实已识别齐全）。

**修复**：6 处裸名改 `cfg("XXX")`（126 / 201 / 206 / 232 / 235 / 331 行）。

### 排查套路（下次直接照做）

```python
# 三步定位「校验异常但功能正常」
from services import member_ctx, member_store
print(member_ctx.member_space_root())          # None ⇒ 会话态没注入
print(member_ctx.is_member_env(env))           # False 但 .enc 存在 ⇒ 判据失效
member_ctx.parse_env_dict(env)                 # {} ⇒ 解密/路径有问题
# 注入会员态再对比（能区分「凭证真坏」还是「读不到」）
os.environ["DY_MEMBER"] = sess["member_id"]
os.environ["DY_MEMBER_KEY"] = sess["master_key"]
```

### 实测验证

| 项 | 修复前 | 修复后 |
|---|---|---|
| 无会员态 `credentials_complete` | `(False, '账号 .env 不存在')` | `(True, '凭证齐全')` |
| `uid_probe.get_uid` | `NameError` 崩溃 | `3887506227210423` |
| `verify_account` wp 引擎 | `fail` 凭证未就绪 | **`ok` 正常（捕获齐全）** |

### 铁律
- 判断加密凭证是否存在，**以「文件事实 + 密钥可用」为准，不以路径归属为准**。
- PEP 562 `__getattr__` 惰性常量**不能在函数内裸名引用**，必须走 `cfg("XXX")`。

### 🔴 启动时序坑（用户报「密钥正确连不上」的真实根因，2026-09-09 实修）

- **症状**：QQ bot 填了正确凭证但 WS 从不连接，日志只有 `NTY-003`（无内容）。
- **根因 1**：`main.py` 在**模块级**调用 `init_notifier()`，其中的
  `notifier.start_worker()` / `inbound.configure()` 都要
  `asyncio.create_task` —— import 时**没有 running loop**，抛
  `RuntimeError("no running event loop")`（str 为空 → 日志只见 NTY-003），
  **入站通道从未启动**。修复：`init_notifier()` 移入 **lifespan**（bind_adm 处），
  模块级只挂路由。
- **根因 2（掩盖问题）**：项目日志规范是 `logger.warning(f"[CODE] msg")`
  或 `errcode.ec_warn`，误写成 `logger.warning("CODE", f"msg")` 会让 loguru
  把第二参当 format args 丢弃 —— **16 处 IB/NTY 日志只剩代码号没有内容**，
  完全看不到失败原因。已批量改为 `f"[CODE] ..."`。
- **修复后**：假凭证实测立即打出真实错误
  `RuntimeError({'code': 10004, 'message': '机器人不存在'})` —— QQ 侧
  **10004 = appid 对应的机器人不存在**（未发布/沙箱未加列表）。链接失败
  自动 30s 重试（人工在 QQ 后台补发布后无需重启）。
- **排查指引**（QQ bot 连不上时依次核对）：
  ① appid/secret 是否复制完整；② 开放平台该机器人**是否已发布**

  是否开通**（未开通时 public_messages 收不到任何消息）；④ 保存配置后

### ⑦ v0.38.5 补丁2：同一 sender 出现两条不同「抬头」的待审（用户实测）

- **现象**：同一 QQ 号发消息，待审区出现 `qqofficial_mtttte34:D07B…` 和
  `qqofficial_mttzg4f4:D07B…` 两条。

  用户重复添加同一 QQ bot → 两个实例 id、两条 WS、同一条消息过两次网关，
  而 sender_key 用**实例 id** 作前缀 → 两个 key。日志还伴生
  「消息被去重，请检查请求msgseq」（两实例同时被动回复同一条消息）。
- **修复（双保险）**：
  ① 后端 `gateway` 按 **kind + sender_id** 归并：pending 条目与 grant 都记
  `kind` 字段，check 时同 kind 同 sender 只保留一条（alias_keys 记别名），
  授权/拉黑对所有实例生效；inbound._dispatch 传 `channel_kind`。

  必须由调用方显式传 kind。
  ② 前端 `addChannel` 同 kind 已存在时不再新增（toast 提示直接编辑现有卡片）。
- 实测：同 kind 双实例归并 1 条（msg_count=2）/ 审批后双实例放行 /
  跨 kind 独立 / 拉黑跨实例生效，全过（现场已还原）。

### ⑥ v0.38.5 补丁：「默认接收目标」自动推导（用户追问"为什么还要手填"）

- **根因**：default_target 是纯推送时代的历史字段（系统不知道推给谁）。
  有了网关后，**已授权来源本身就是合法推送目标**，无需手填。
- `notifier._targets_for(cid)`：手填目标（兼容保留，排在最前）→
  追加网关 grants 里**同渠道、非 blocked** 的 sender_id，去重多目标派发。
- 🔴 **坑：channel_id 双语义**——grants 里的 channel_id 是 **kind**
  （weixin_oc，来自 sender_key 前缀），派发循环的 cid 是**渠道实例 id**
  （如 ch_wx）。匹配必须同时比对两者（`kinds = {cid, cfg.kind}`），
  否则自定义渠道 id 的授权来源永远匹配不上（实测踩中，表现为推导空）。
- 🔴 **坑：gateway 单例未绑定**——`_get_cfg` 只在 `init_notifier` 绑定，
  任何绕过它的调用方（如 notifier 派发）拿到的是空配置。已加
  `ensure_bound()` 模块级自举（延迟 import api.notify，避免循环依赖）。
- 前端：字段改名「默认接收目标（可选）」，placeholder
  「留空 = 自动推送给已授权的会话」。
- 实测：无手填渠道自动推导 2 个授权来源（blocked 已排除）；
  手填+授权混合去重；id==kind 场景无重复。测试 grants 已清。
