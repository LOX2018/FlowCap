# 10. AI 获客自动回复（2026-09-06 嵌入，v0.35.1）

> 来源：嵌入开源项目 https://github.com/xyc667/douyin-auto-reply-assistant
> （基于 Douyin_Spider 二开的 AI 自动回复桌面助手）的核心能力
> （KnowledgeBase 知识库模糊匹配 + Anthropic 兼容 AIClient + 随机延迟），
> 按本仓库铁律重构。用户明确目标：**获客留资**（专业性靠知识库，留资是 agent 核心设定）。

## 一、架构与文件

| 文件 | 职责 |
|---|---|
| `backend/services/ai_reply.py` | 全部核心逻辑：KnowledgeBase / AIClient / 留资正则 / 护栏 / AutoReplyWorker 监听线程 / kv+ai_leads 存储 |
| `backend/api/ai.py` | REST 薄封装，挂载 `/api/ai`（main.py `include_router(ai_api.router, prefix="/api/ai")`） |
| `frontend/src/pages/ai.tsx` | 「AI」页（顶部导航第 5 项，TABS 注册在 components/ui.tsx） |
| `frontend/src/api/client.ts` | `api.aiXxx()` 18 个端点方法 |

- 存储：配置/知识库/黑名单/水位/防重 全在 `kv_store`（key 前缀 `ai_reply_`）；线索在独立表 `ai_leads`（UNIQUE(account,conv_id,contact_type,contact_value)，同联系方式只记一条）。
- `main.py` lifespan：`ensure_tables()` + 若 `enabled=true` 自启 WORKER。

## 二、回复决策链（顺序即优先级）

```
新消息(dm_messages.role='them', 水位之后)
 → 黑名单(uid/peer_name) → 忽略
 → 留资提取(正则) → 命中: 写 ai_leads + 回确认话术(不调AI) 【最高优先级】
 → 图片消息(msg_type='27') → 视觉模型描述 → 当文本继续; 视觉未配/失败 → 图片兜底话术, 绝不瞎猜
 → 档位分流:
    kb_only: 知识库未命中 → 兜底话术池(AI 完全不参与)
    rag(默认): 知识库未命中 → AI(知识库条目全文注入 prompt《资料》段) → 护栏 → 不过发兜底
    free: 纯 prompt 约束 → 护栏
```

## 三、实测证真（2026-09-06 实机 0.35.1 部署验证）

1. **图片消息 msg_type='27'**（非 '4'！）：实库 `dm_messages` 里 them 图片行全是
   `msg_type='27'`，text=`[图片] https://...douyinpic...`，extra 含
   `{"skey":..., "origin_url":...}`（08 §三十五 解密要素齐全）。代码判断图片用
   `text.startswith('[图片]') or msg_type=='27'` 双保险。
2. 留资端到端：向 dm_messages 插入含手机号的 them 行 → 开启监听 → 约 5s 内
   `ai_leads` 落库（log: `🎯 留资成功 ... → ai_leads`）→ 触发确认话术延迟发送。
3. 对不存在的测试会话（conv_id 无真实 peer）：WS 通道连接拒绝 + WP 通道失败 →
   **零外发**（该会话 role='me' 落库数=0）。发送失败不重试、不阻塞水位推进。
4. API 全链路：status/config GET+POST、start/stop、knowledge 增删查、
   blacklist 增删、leads/export CSV（UTF-8 BOM）全部 curl 实测通过。
5. 前端 bundle 验证（§九·甲 md5/产物名铁律）：exe 内 grep 到新产物名
   `index-DWYIkmy-.js`，部署 md5 与构建产物一致。

## 四、铁律对齐（本功能为什么这么设计）

- **发送 100% 复用既有链路**：`_send_via_chain` 直接 import
  `api.messages` 的 `_recv_url/_bcc_url/_http_post_json`，WS 主通道
  （recv_daemon /send，自带凭证刷新）→ 失败回退 BCC /wp_send。
  绝不复刻原项目的「读 .env 凭证直连 imapi」（红线 1）。
- **纯读库**：监听只 SELECT dm_messages/dm_conversations，零捕获、
  零主动昵称查询（昵称用 peer_name 落库值）。
- **水位防重**：kv `ai_reply_last_msg_id` 记最后处理的消息 id；关闭期间
  每 tick 推进水位 → 重新开启绝不回历史消息。会话维度 60s 同文本防重
  （WS+WP 双通道重复落库同一条消息只回一次）。
- **延迟期间不持锁**：随机延迟 8~20s 用 `self._stop.wait(delay)`，
  不持有 recent 防重锁（曾写过 release/acquire 包裹——对未持有的锁
  release 会 RuntimeError，已修）。

- **FreeLLM auto 路由评估与思考泄漏防护（2026-09-07）**：
  - 实测结论：**chat/vision/embeddings 三端点的 auto 路由均不可用于获客**——chat auto 每次路由到不同模型（含英文模型，中文请求被英文回复/乱码）；vision auto 只试 glm-4.6v-flash 一条路，限流即整体失败不避障；embeddings auto 固定路由到无 key 的 gemini-embedding 直接报错。**结论：三模型全部固定手选**，前端已移除 auto 选项（用户拍板"不保留auto选项"）。
  - ⚠️ **推理模型 max_tokens 不足会泄漏思考过程**：glm-5.2 在 max_tokens<~500 时 finish_reason=length 且 content 直接是「1. **分析请求：**…」思考文本。两层防护：① `_chat_openai` 出口 finish=length + `_looks_like_reasoning()`（编号列表+分析/思考/让我/Okay 等特征）→ 返回 None 走兜底；② `_generate_reply` 对 len>40 的疑似思考文本二次拦截。**max_tokens 建议 ≥1000**（AI 页默认值即 1000，勿调小）。
  - ⚠️ FreeLLM 限流波动大：glm-5.2 高频调用会进 80s~6m 冷却（502 rate_limit_error），期间 `/api/ai/test` 会失败——这是 provider 侧状态，非配置错误；可临时切 minimax-m3 验证链路，或等冷却。
- **语义检索（2026-09-07 增补，三级漏斗第 2 级）**：
  - 配置（kv `ai_reply_config`）：`sem_enabled/sem_base_url/sem_api_key/sem_model/sem_threshold`。默认指向本机 FreeLLM `http://127.0.0.1:31415/v1` + `nvidia/nemotron-3-embed-1b`（该部署实测唯一可用的 embedding 模型，其余 family 全部 no usable keys）。
  - ⚠️ FreeLLM 的 `/v1/models` 列表**不含** `nemotron-3-embed-1b`（隐藏 embedding 族，列表里 0 个含 embed 字样的 id），但直接调 `/v1/embeddings` 可用 —— 前端嵌入模型下拉列表为空时需手填，配置默认值已带该名。
- **视觉模型修正（2026-09-07）**：
  - `glm-4.6v-flash` 实测频繁限流（FreeLLM 单 key 冷却 80s~10m）→ 默认视觉模型改 **`nemotron-3-nano-omni-reasoning`**（omni 多模态推理系，实测 1x1 PNG 正确回答红色）。

  - **架构约定（用户明确）**：视觉模型是主 LLM 的**补充**——仅当主 LLM 不支持视觉时才需要独立配置；若主 LLM 本身多模态（如 gemini/qwen-vl 系），可直接把主 LLM 配成视觉模型省去独立配置。
  - `find_match` 三级漏斗：①精确/包含 →②语义余弦≥阈值 →③Jaccard 兜底；embedding 调用失败自动落 ③，不阻塞消息处理。
  - 向量缓存 kv `ai_reply_semv_<id>`，**只向量化 question**——实测混入 answer 会稀释语义（同义改写「你们这个什么价格呀」cos 从 0.582 掉到 0.358 漏召回）。缓存重建在 KB 增删改/导入 confirm 后自动后台触发 + 前端「重建向量缓存」按钮；模型变更使缓存 stale（cache_status.stale）。

## 六·甲、Agent 模版与账号绑定（v0.38.0，2026-09-09）

> **解决 v0.35.1 遗留问题**：AI 配置原本是**全局单份** `ai_reply_config`，
> 但消息处理按账号维度 —— 多账号共用必然紊乱（A 的商家名/知识库串到 B）。

### 设计（用户拍板）

- **Agent 是模版**：设置页定义命名 Agent（模型/档位/商家名/prompt/
  知识库/黑名单/兜底话术），账号绑定之 —— 改一次，所有绑定账号同步生效。
- **知识库 / 黑名单 / 兜底话术全部跟随 Agent**，账号不单独持有。
- **绑定关系在设置页维护**（子导航「AI 与 Agent」），**不在 AI 页** ——
  避免两处配置分裂。AI 页仍管全量参数（语义检索/视觉/知识库条目/护栏/延迟），
  Agent 页只放按账号差异化的核心项。

### 文件

| 文件 | 职责 |
|---|---|
| `backend/services/ai_agent.py` | Agent CRUD + 绑定；kv `ai_agents` / `ai_account_agent` |
| `backend/api/ai.py` | `/api/ai/agents`、`/api/ai/bind` |
| `frontend/src/components/AgentSection.tsx` | 列表 + 参数 + 绑定矩阵 |

### 核心函数

```python
ai_agent.resolve_config(account, base_cfg)
#  未绑定 Agent → 原样返回 base（零回归）
#  已绑定      → 逐键覆盖，未配置的键保留全局（不是整体替换）
ai_agent.resolve_knowledge(account, base_kb)
ai_agent.resolve_blacklist(account, base_bl)
```

### 接入点（ai_reply.py，全部 try/except 包裹）

- `_handle()`：按 `row["account"]` 解析 Agent 配置 → 覆盖 cfg
- `_handle()`：黑名单走 `resolve_blacklist(account, ...)`
- `KB.find_match(text, account=account)`：知识库按 Agent 隔离
- `find_match_semantic(..., items=)`：支持传入 Agent 级知识库

**Agent 模块异常绝不阻断回复主流程** —— 全部 try/except 后回落全局。

### 关键约束

- **删除 Agent 自动解绑所有引用账号**（防悬空绑定 → 账号指向不存在的 Agent）
- 保存 Agent 时按 `ai_reply._DEFAULT_CONFIG` 键**白名单过滤**（+ knowledge_base / blacklist），
  防止脏键污染配置
- 未绑定 = 使用全局配置，行为与改造前**逐字一致**
