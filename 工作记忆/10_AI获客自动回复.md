# 10. AI 获客自动回复（2026-09-06 嵌入，v0.35.1）

> 来源：嵌入开源项目 https://github.com/xyc667/douyin-auto-reply-assistant
> （基于 Douyin_Spider 二开的 AI 自动回复桌面助手）的核心能力
> （KnowledgeBase 知识库模糊匹配 + Anthropic 兼容 AIClient + 随机延迟），
> 按本仓库铁律重构。用户明确目标：**获客留资**（专业性靠知识库，留资是 agent 核心设定）。

## 一、架构与文件

| 文件 | 职责 |
|---|---|
| `backend/services/ai_reply.py` | 全部核心逻辑：KnowledgeBase / AIClient / 留资正则 / 护栏 / AutoReplyWorker 监听线程 / kv+ai_leads 存储 |
| `backend/api/ai.py` | REST 薄封装，挂载 `/api/ai`（main.py `include_router(ai_api.router, prefix="/api/ai")`） |

| `frontend/src/api/client.ts` | `api.aiXxx()` 18 个端点方法 |

- 存储：配置/知识库/黑名单/水位/防重 全在 `kv_store`（key 前缀 `ai_reply_`）；线索在独立表 `ai_leads`（UNIQUE(account,conv_id,contact_type,contact_value)，同联系方式只记一条）。
- `main.py` lifespan：`ensure_tables()` + 若 `enabled=true` 自启 WORKER。

## 二、回复决策链（顺序即优先级）

```
新消息(dm_messages.role='them', 水位之后)
 → 黑名单(uid/peer_name) → 忽略
 → 留资提取(正则) → 命中: 写 ai_leads + 回确认话术(不调AI) 【最高优先级】
 → 图片消息(msg_type='27') → 视觉模型描述 → 当文本继续; 视觉未配/失败 → 图片兜底话术, 绝不瞎猜
 → 档位分流:
    kb_only: 知识库未命中 → 兜底话术池(AI 完全不参与)
    rag(默认): 知识库未命中 → AI(知识库条目全文注入 prompt《资料》段) → 护栏 → 不过发兜底
    free: 纯 prompt 约束 → 护栏
```

## 三、实测证真（2026-09-06 实机 0.35.1 部署验证）

1. **图片消息 msg_type='27'**（非 '4'！）：实库 `dm_messages` 里 them 图片行全是
   `msg_type='27'`，text=`[图片] https://...douyinpic...`，extra 含
   `{"skey":..., "origin_url":...}`（08 §三十五 解密要素齐全）。代码判断图片用
   `text.startswith('[图片]') or msg_type=='27'` 双保险。
2. 留资端到端：向 dm_messages 插入含手机号的 them 行 → 开启监听 → 约 5s 内
   `ai_leads` 落库（log: `🎯 留资成功 ... → ai_leads`）→ 触发确认话术延迟发送。
3. 对不存在的测试会话（conv_id 无真实 peer）：WS 通道连接拒绝 + WP 通道失败 →
   **零外发**（该会话 role='me' 落库数=0）。发送失败不重试、不阻塞水位推进。
4. API 全链路：status/config GET+POST、start/stop、knowledge 增删查、
   blacklist 增删、leads/export CSV（UTF-8 BOM）全部 curl 实测通过。
5. 前端 bundle 验证（§九·甲 md5/产物名铁律）：exe 内 grep 到新产物名
   `index-DWYIkmy-.js`，部署 md5 与构建产物一致。

## 四、铁律对齐（本功能为什么这么设计）

- **发送 100% 复用既有链路**：`_send_via_chain` 直接 import
  `api.messages` 的 `_recv_url/_bcc_url/_http_post_json`，WS 主通道
  （recv_daemon /send，自带凭证刷新）→ 失败回退 BCC /wp_send。
  绝不复刻原项目的「读 .env 凭证直连 imapi」（红线 1）。
- **纯读库**：监听只 SELECT dm_messages/dm_conversations，零捕获、
  零主动昵称查询（昵称用 peer_name 落库值）。
- **水位防重**：kv `ai_reply_last_msg_id` 记最后处理的消息 id；关闭期间
  每 tick 推进水位 → 重新开启绝不回历史消息。会话维度 60s 同文本防重
  （WS+WP 双通道重复落库同一条消息只回一次）。
- **延迟期间不持锁**：随机延迟 8~20s 用 `self._stop.wait(delay)`，
  不持有 recent 防重锁（曾写过 release/acquire 包裹——对未持有的锁
  release 会 RuntimeError，已修）。

## 六·甲、Agent 模版与账号绑定（v0.38.0，2026-09-09）

> **解决 v0.35.1 遗留问题**：AI 配置原本是**全局单份** `ai_reply_config`，
> 但消息处理按账号维度 —— 多账号共用必然紊乱（A 的商家名/知识库串到 B）。

### 设计（用户拍板）

- **Agent 是模版**：设置页定义命名 Agent（模型/档位/商家名/prompt/
  知识库/黑名单/兜底话术），账号绑定之 —— 改一次，所有绑定账号同步生效。
- **知识库 / 黑名单 / 兜底话术全部跟随 Agent**，账号不单独持有。
- **绑定关系在设置页维护**（子导航「AI 与 Agent」），**不在 AI 页** ——
  避免两处配置分裂。AI 页仍管全量参数（语义检索/视觉/知识库条目/护栏/延迟），
  Agent 页只放按账号差异化的核心项。

### 文件

| 文件 | 职责 |
|---|---|
| `backend/services/ai_agent.py` | Agent CRUD + 绑定；kv `ai_agents` / `ai_account_agent` |
| `backend/api/ai.py` | `/api/ai/agents`、`/api/ai/bind` |
| `frontend/src/components/AgentSection.tsx` | 列表 + 参数 + 绑定矩阵 |

### 核心函数

```python
ai_agent.resolve_config(account, base_cfg)
#  未绑定 Agent → 原样返回 base（零回归）
#  已绑定      → 逐键覆盖，未配置的键保留全局（不是整体替换）
ai_agent.resolve_knowledge(account, base_kb)
ai_agent.resolve_blacklist(account, base_bl)
```

### 接入点（ai_reply.py，全部 try/except 包裹）

- `_handle()`：按 `row["account"]` 解析 Agent 配置 → 覆盖 cfg
- `_handle()`：黑名单走 `resolve_blacklist(account, ...)`
- `KB.find_match(text, account=account)`：知识库按 Agent 隔离
- `find_match_semantic(..., items=)`：支持传入 Agent 级知识库

**Agent 模块异常绝不阻断回复主流程** —— 全部 try/except 后回落全局。

### 关键约束

- **删除 Agent 自动解绑所有引用账号**（防悬空绑定 → 账号指向不存在的 Agent）
- 保存 Agent 时按 `ai_reply._DEFAULT_CONFIG` 键**白名单过滤**（+ knowledge_base / blacklist），
  防止脏键污染配置
- 未绑定 = 使用全局配置，行为与改造前**逐字一致**

## 七、模型中心 v2（v0.39.0 重构，2026-09-10）

用户拍板把 v0.38.4 的「链路 endpoint + 消费方直绑」重构为三层：

### 7.1 结构（services/model_hub.py，kv `model_hub` v=2）
- **提供商（providers）**：只管三件事 —— 密钥（base_url/协议/api_key）、
  `fetch_provider_models`（GET /models 拉取，anthropic 走 /v1/models）、
  `test_provider_key`（结果写 key_status 回显前端）。
- **模型（models）**：统一注册，caps ⊆ {llm, vision, sem}；
  拉取时 `guess_caps` 启发式预分类（embed/bge→sem；vl/vision/omni/-v\d/4v→llm+vision），
  UI 可点标签改。删提供商级联删模型；删模型自动清链路/兜底/固定绑定。
- **避障链路（routes）**：llm/vision/sem 三条，每链 ≤6 模型（MAX_CHAIN），
  消费时按序尝试（异常/HTTP错/空回复/思考泄漏→切下一个）。
- **兜底模型（fallback.model_id）**：**必须 llm+vision 双能力**（set_fallback 硬校验），
  附在 llm 链与 vision 链末尾（链内已含则不重复）；**sem 链不用兜底**
  （embedding 模型不通用，跨任务调语义模型必失败）。
- **消费方（consumers）**：ai_main/ai_vision/ai_sem/notify_cmd；
  `mode="route"`（选链路享避障+兜底）或 `mode="fixed"`（固定某提供商模型不避障）。
  fixed 模型被删→自动解绑回落默认 llm 链（服务连续性优先）。

### 7.2 消费侧接线（services/ai_reply.py）
- `resolve_chain_hub(cid)` → `AIClient.chat_failover`（ai_main）/
  `describe_image_failover`（ai_vision）/ `_embed_failover`（ai_sem）。
  链未配置/空 → 回落旧单配置（`apply_model_hub` 的 ai_reply_config 兜底），
  **零回归**。`hub.resolve(consumer_id)` 保持旧签名返回链首（notify.py 零改动）。
- **embedding 模型一致性**：`_embed_failover` 返回实际生效模型名；
  `find_match_semantic` 发现缓存（kv ai_reply_sem_model）与现用模型不同 →
  跳过语义级落 Jaccard（防跨 embedding 模型混算余弦出假命中）。
- 报错码：HUB-001~003、AI-030~034 已注册 errcode。

### 7.3 迁移与坑
- kv `model_hub.migrated` 标记一次性迁移：v1 结构（endpoints+consumers）→
  v2；更旧 ai_reply_config 字段 → 建默认提供商。
  **迁移结果必须 `_save(out)` 持久化**——曾漏写导致二次 `_load` 退回空结构（测试抓出）。

  `except: return data` 静默吞掉（trace 才抓到）。教训：**迁移函数的 except
  静默兜底必须配合测试用例真实触发一次迁移**，否则 NameError 级故障测不出来。
- 测试 `test_model_hub_v2.py` 5 用例（隔离 DB）：提供商 CRUD/分类、
  链路+兜底规则、消费方 route/fixed、级联删除、v1 迁移幂等。

### 8.1 一棵树：后端视图 = 树，前端只展示表格（用户 2026-09-11 追加定调）
- **树（数据视图）只留在后端**：后端 `GET /prokb` 返回的 `tree`（主题→子分类→条目）
  是唯一的结构化视图，供 AI 检索、主题清单注入、级联改名用。**前端不再渲染树**。
- **前端只有表格视图**（用户原话：「树视图作为后端视图就行前端不展示」）：
  每行=条目，列 `主题 | 子分类 | 总结 | 正文 | 状态 | 操作`（xlsx 式）。
- **前端不再有「手动编辑条目」表单**（用户原话：「表格视图还残留手动编辑条目区域」）：
  旧的新增/编辑表单（主题/子分类/总结/正文 4 输入框 + 添加按钮）**已删除**。
  条目的产生路径为：**文件导入 AI 提纯入库** 或 **单元格直接编辑**（改表格 = 改树）。
- **改表格 = 改树**：单元格 `onBlur` 即 `PATCH /api/ai/prokb/{id}` 单字段落库，
  刷新后后端树同步变化。没有任何第二套存储 —— 后端树与前端表格都读 kv `ai_pro_kb`。
- **xlsx 式行归类**：表格按 主题→子分类→条目 顺序展平，
  主题列/子分类列相邻同值只在首个显示，其余显示 `〃`（并给组首加 `2px` 主题色上边框）。
- **全局一棵树的 2 条保证**：①导入提纯提示词注入**现有主题清单**，让 AI 优先复用
  已存在主题名；②后端 `rename_topic` 级联改名（改一处全树同步）；
  ③导入预览的「主题」输入框挂 `<datalist>` 自动补全全库主题。
- **前端已删除的死代码**（本次清理）：`view/setView` 视图切换、`collapsed` 折叠、
  `renaming/renameTo` 改名态、`saveMut` 新增保存、`renameMut` 改名 mutation
  （改名仍在后端 API 保留 `/prokb/rename_topic`，前端入口待需要时再挂）。

### 8.2 数据层（services/pro_kb.py，kv `ai_pro_kb`）
新增条目字段（MalogBot 移植）：
`importance`（导入0.7/手工0.5）、`hits`、`occurrence`、`last_accessed_at`、
`is_stale`/`stale_reason`、`deleted_at`。

- **写入去重**：`add_item`/`bulk_add` 先算正文 embedding，
  与同主题已有条目余弦 **≥0.90 → 不新增，`occurrence+1`**（可 `dedup=False` 绕过）。
- **时间衰减**：`decay = e^(-0.02 × 距上次命中天数)`；
  50天→0.368、100天→0.135（实测值）。排序分 = 相关度 × decay。
- **质量门槛**：`importance<0.3 且 hits=0` → RAG 注入时过滤（低质条目不污染《资料》段）。
- **回收站**：`delete_item` → 进回收站（`deleted_at`），`restore_item` 可恢复，
  **30 天后 `purge_expired` 真删**。

### 8.3 知识维护（services/kb_maintain.py，新建）
三档扫描（阈值照搬 MalogBot，**只出报告、绝不自动改数据**）：
| 档 | 条件 | 动作 |
|---|---|---|
| 冷数据 | `hits=0` 且 >180天 | 标记 `is_stale` |
| 低价值 | `importance<0.3` 且 `hits=0` 且 >90天 | 报告默认勾选 |
| 重复 | 两两余弦 **≥0.95** | 保留 importance 高的，另一个建议合并 |

⚠️ 重复阈值实测校准：**0.95** 是分界线 —— 同义改写（"7个月本人工资"vs
"7个月工资"）实测 0.9909 会命中；措辞不同但实质不同的条目 0.9252/0.9146
**不误合**（曾用 MalogBot 原值 0.85 会误合工伤不同等级条文，已收紧）。

### 8.4 定时器（用户拍板：84小时一轮 + 全自动学习）
- `start_scheduler(interval_hours=84)`：`threading.Timer` 常驻循环，
  跟随主程序生命周期，**首次延迟 30 分钟**（避开启动初始化高峰）。
  在 `main.py` lifespan 末尾自动拉起。
- 每轮跑：①`run_learn_job`（自动学习，**全自动落库** —— 只增不删，安全）
  ②`run_scan_job`（陈旧扫描，**只出报告**）③`purge_expired`（回收站超期清理）。
- **删除边界（用户拍板 C）**：`全部先扫描出报告，我确认后才执行` ——
  维护绝不自动删，界面勾选 →「处理选中项」→ 进回收站。

## 【2026-09-12 实测修复】专业库 RAG 从「全库注入」改为「语义 TopK + 向量缓存」

### 问题（BUG2：AI_RAW empty 217 次）
`build_system_prompt` 旧实现对专业库 `pro_kb.list_items()[:40]` **全文注入**，
每条 content 上限 2800 字 → 实测 prompt **30,532 字符**，撑爆模型上下文，
上游返回空 → 全部降级兜底话术（探针 `AI_RAW empty`）。

**注意**：代码注释写「相关性由漏斗/向量负责」是**过时/错误**的——
三级漏斗只挂在**回复库**（`reply_kb.find_match`）上；专业库当时**没有任何检索**。
`pro_kb.py` 里虽有 `_embed`/`_cosine`（给去重用的），但未接到 RAG 注入路径。

### 修复
- 新增 `pro_kb.semantic_topk(text, items, k=5, threshold=0.0, max_chars=6000)`：
  客户问题向量化 → 与专业库条目余弦相似度排序 → 取 TopK 且总字数 ≤ max_chars。
- 新增**向量缓存**（kv_store，前缀 `pro_kb_semv_<item_id>`）：
  ① 缓存优先读取；② 未收录才实时调 embedding；③ 结果回写缓存。
  实测：冷缓存 11.4s → **热缓存 1.0s（11.2× 加速）**。
- 新增 `pro_kb.sem_cache_invalidate()`：挂在 `_kv_set` 写入 `ai_pro_kb` 时**自动**失效。
  （坑：逐个在 add/update/delete 里插调用会漏早返回分支——`update_item` 有 2 个 return。）
- `build_system_prompt` 降级链：语义命中 → `kb_mode=semantic`；embedding 不可用 →
  按 `time_decay_factor` 取前 5 → `kb_mode=fallback_decay`。**绝不阻塞**。
- 探针新增 `PROMPT` 环节记录 `prompt_len / kb_mode / pro_kb_chars / picked`
  （模块级 `_LAST_PROMPT_STATS`，因为它是 `build_system_prompt` 的局部变量）。

### 实测效果
| 查询 | 旧 prompt | 新 prompt | 模式 | 注入 |
|---|---|---|---|---|
| 工伤十级赔多少 | 30,532 | 7,752 | semantic | 6,421字/3条 |
| 没有劳动合同怎么办 | 30,532 | 5,803 | semantic | 4,472字/5条 |
| 私了能拿多少 | 30,532 | 5,841 | semantic | 4,514字/5条 |

**↓81%**，且命中高度相关（问"十级赔多少"→《工伤赔偿清单》《全国统筹地区赔偿标准》《骨折评级要点》）。

### 坑
- `pro_kb._embed` 内部 `texts[:20]` 会截断：**一次传 56 条 → 返回 20 条 ≠ 请求数 →
  被判定失败 → 返回 None（全部降级）**。必须**每批 20 条循环**。
- 常量名是 `_KV_PRO_KB`（值 `"ai_pro_kb"`），**没有** `PRO_KB` 这个名字；在 `_kv_set` 里
  引用未定义常量会 NameError——用字符串字面量避免定义顺序依赖。
