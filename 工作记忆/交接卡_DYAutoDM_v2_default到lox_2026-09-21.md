## 二、核心结论：项目当前状态诊断

### 2.1 体系性问题（**四条症状，同一前提错误**）

> **前提错误**：把「**爬虫**」当「**常规业务系统**」建。常规业务的前提是「契约稳定」；爬虫的前提恰是「对手在变、失败是常态」。

| 症状 | 实测数据 | 投影机制 |
|---|---|---|
| **臃肿** | 后端 **212 文件 / 65,999 行**（文档称 114/34,961）；历史 **净增 175,783 行**（只加不减）；`fix:refactor = 173:31 = 5.6:1` | 契约一变 → N 个调用点各打补丁 |
| **同一业务多处触发** | BCC 拉起 **6 个决策点 / 56 调用点**；凭证 **13 个决策点 / 74 调用点**；发送 6；昵称 5 | 无单一事实源（M4 缺失） |
| **并发未统一** | **60 threading 锁 + 5 asyncio 锁 + 38 模块级变量 + 34 线程池**；**153 处硬编码 timeout**、27 处 sleep | 无「资源生命周期」抽象（M6 缺失） |
| **debug 跑偏** | 42 事故归因：自家缺陷 31 / 环境已变 6 / 混合 5；但**静默吞异常 340 处**（AST 精确）；**概率/置信度模型 0 处**、不确定性建模 **0 处** | 无漂移检测（M2）+ 无三态（M3） |

### 2.2 最大正向发现

**统一调度体系真实落地**（未空壳）：
- `core/dispatch.py`（501 行）被 **15 个模块**使用
- `services/dm_dispatch.py`（1,193 行）被 **8 个模块**用 `get_dispatcher`，内含 `AccountQuota`/`UidSink`/`ConvPool`
- **所有发送方收敛到同一 per-account 串行队列** ← 重构时**不得破坏**

### 2.3 最优先缺口

**M1 能力探针 = 0 个**（`02_效果定义与探针.md` 已定义"应该有什么"，但**一个都没实现**）。

> **这是重构无法验收的根本原因**：2026-09-14「全解除」改动后**不敢回退**，因为没有探针能验证"业务效果是否还在"。
