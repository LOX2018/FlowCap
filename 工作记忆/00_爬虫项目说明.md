## 一、第一性认知：这是爬虫，不是业务系统

### 1.1 两者的根本差别

| 维度 | 常规业务系统（含搭积木式集成） | **本项目（对抗性爬虫）** |
|---|---|---|
| 外部契约 | **稳定**，接口/字段/调用方由双方约定 | **持续漂移**，对方单方面变更、无通知、无版本 |
| 失败性质 | 异常，应修复到零 | **常态**，应度量、分级、降级 |
| 正确性定义 | 代码符合契约 = 正确 | **在当前环境真实达成业务效果 = 正确** |
| 依赖性质 | 组件可锁定版本 | **组件随时失效或被封**，必须可替换 |
| 知识来源 | 官方文档 + 稳定参考 | **实时实测 + 爬虫基本原理**，参考信息天然稀缺 |
| 需求形式 | 功能清单 | **效果目标**（如「昵称覆盖率 ≥ 95%」） |

### 1.2 由此推出的五条根本纪律

**D1 · 效果优先于实现**
判定一件事是否成功，不看「代码是否按老定义执行」，只看「**当前能否真实达成业务效果**」。
→ 禁止用「接口返回 200」「弹窗提示成功」「日志无报错」作为成功判据。

**D2 · 假设必须显式且可证伪**
任何对外部世界的假设（字段含义、接口行为、页面结构、风控阈值）必须**写在文档里**，
标注「实测日期 + 判据 + 未验证部分」。假设被推翻时，**先改假设再改代码**。

**D3 · 失败必须可观测，禁止静默**
静默兜底会把「世界变了」伪装成「功能正常」。任何降级必须**分类、计数、可告警**。
（实测基线：本仓库曾有 340 处 `except: pass` 级静默吞异常，集中在与外部交互的模块。）

**D4 · 策略与组件必须可替换**
接口会失效、内核会被识别、签名会过期。因此**策略与组件绝不能硬编码进业务逻辑**，
必须通过配置/适配层注入，使「换策略」= 改配置而非改业务代码。

**D5 · 知识有保质期**
接口定性、选择器、签名算法、风控阈值的**有效期按天计**。
知识库必须能回答「这条信息是什么时候实测的、现在还成立吗」。


**D6 · 开源情报优先 —— 严禁闭门造车**（2026-09-21 用户明确，**本项目的根本禁忌**）

> **用户原话**：「爬虫类项目最忌讳的就是闭门造车，一定要学会利用网络上公开的信息和思路。」

**规则**：遇到任何能力问题，**第一动作是去外部公开信息里找答案**，不是读自家代码。

| 优先级 | 来源 |
|---|---|
| 1 | **开源社区的同题项目**（GitHub 同类爬虫，看别人怎么解的） |
| 2 | **实时实测**（抓包/探针，验证外部情报是否适用于本账号） |
| 3 | 自家代码与自家文档（**最低优先**，且属 D 级证据） |

**为什么这是第一性**：爬虫的对抗面是**外部世界**，而外部世界的变化与解法**总是先在公开社区出现**。
闭门造车 = 用自家旧定性去猜一个别人已经解过的问题 → 必然绕远路、必然滞后。

**本条的直接推论**：
- 写代码前先搜「别人怎么做的」；改接口前先搜「抖音现在有哪些接口」。
- 自家文档只能是「本项目实测到的现状」，**不能当权威**，更不能用它去否定外部情报。
- 遇到「以前定性正确」的假设，先去社区看是否已被推翻（见 §3.3 数据可信度分级 D 级）。

## 二、由纪律推出的必备机制（缺一不可）

> 这七条是**判定本项目健康度的标准**。缺失项即为体系级债务。

| # | 机制 | 回答的问题 | 缺失时的表现 |
|---|---|---|---|
| **M1** | **能力探针（Capability Probe）** | 「现在这个能力行不行？」 | 只能等用户发现失效；改完不知效果是否还在 |
| **M2** | **契约漂移检测（Contract Drift）** | 「是代码错了，还是世界变了？」 | 一律假设自家 bug → 反复在代码里找差异 |
| **M3** | **不确定性三态**：确认成功 / 部分成功（带覆盖率与置信度）/ 确认失败 | 「抓到了 37/44 算好还是坏？」 | 只有二态，部分成功被当成功或被当失败 |
| **M4** | **单一事实源（SSOT）** | 「这件事谁说了算？」 | N 个决策点各自为政 → 同一业务多处多次触发 |
| **M5** | **统一的节流/退避/超时策略中心** | 「为什么慢、为什么被封？」 | 硬编码散布，无法统一调优，风控判据不一致 |
| **M6** | **资源生命周期契约** | 「谁拥有、谁释放、如何互斥？」 | 自造锁/单例，跨进程组合时行为不可预测 |
| **M7** | **效果基线（Baseline）** | 「和上次比，是变好还是变坏？」 | 无法判断改动是否导致能力劣化 |

### 判定口径（可执行）

```
健康 = M1 探针全绿 且 M2 漂移有告警 且 M3 有覆盖率 且 M4 决策点唯一
       且 M5 无散落硬编码 且 M6 资源有主 且 M7 基线在跟踪
```

## 三、爬虫必须建的基础理论（不依赖任何具体平台）

### 3.1 采集链路的标准分层

```
采集目标定义 → 身份/会话语义 → 传输（HTTP/WS/浏览器） → 签名与凭证
   → 反爬对抗（指纹/代理/节流） → 解析（协议/结构） → 归一化 → 落库 → 效果度量
```

**每层都必须能独立回答「本层当前是否工作」**——这是 M1 探针的分层依据。
禁止让上层去猜下层状态（如用「昵称是否为空」去推断「浏览器是否可用」）。

### 3.2 对抗性采集的三条不变式

1. **被动优先于主动**：能复用对方已发出的请求/已渲染的页面，就不主动构造请求。
   主动请求次数与风控风险正相关。
2. **行为拟真优先于频率控制**：固定位置、固定频率的操作本身就是特征。
   节流不只是「慢一点」，还包括**不规律性**。
3. **多路径冗余但单一出口**：同一能力可有多个实现路径（降级用），
   但**决策必须收敛到一个出口**（否则就是 M4 缺失 → 多处多次触发）。

### 3.3 数据可信度分级（禁止把不同可信度混为一谈）

| 级别 | 来源 | 用途 |
|---|---|---|
| A · 实测确认 | 真实运行实例现场取证 | 可作为结论 |
| B · 协议解析 | 官方协议/结构化响应解析 | 可作为推断依据，需 A 验证 |
| C · 界面推断 | 页面结构、DOM、文案推断 | **仅作线索**，不可作结论 |
| D · 历史记载 | 旧文档、旧日志、旧定性 | **仅作对照**，必须重验 |

> **本库过去的头号错误**：把 D 级当 A 级用（「以前定性就是正确的」），
> 于是反复在代码里找「与以前的差异」，而不是重验那条定性本身。

### 3.4 变更响应流程（世界变了怎么办）

```
现象（效果劣化/静默失效）
  ↓ ① 先跑能力探针（M1）确认「效果是否真的没了」
  ↓ ② 比对契约（M2）判断「是自家代码问题还是外部契约漂移」
  ├─ 契约漂移 → 更新「外部世界假设」→ 更新策略/适配层 → 记录新定性(附日期)
  └─ 自家缺陷 → 常规链路溯源
  ↓ ③ 更新效果基线（M7），确认无劣化
  ↓ ④ 同步知识库：**作废旧定性**（不是追加新描述）
```

**第 ④ 步是关键**：知识库更新必须是**替换**，不是追加。
追加 = 新旧两套定性并存 = 下次 debug 遇到干扰信息。

## 五、本库的维护纪律（防止再次腐化）

### 5.1 写入纪律

1. **一页一事实**：一页只讲一个可复用的结论，不写「本轮做了 ABC」的流水账。
2. **必带三要素**：`实测日期` + `判据（怎么验的）` + `有效期/失效条件`。
3. **作废用替换**：方案被推翻时，**改写原页**（标注「已作废，替代方案见 X」），
   **不新增解释页**——否则新旧并存 = 下次的干扰源。
4. **禁写未验证推测**，或显式标 `【未决假设】`。
5. **禁止把「现场描述」当知识**：现场描述进 `cases/`（按日期归档，允许陈旧）；
   可复用结论才进 `工作记忆/`（必须保持现役）。

### 5.2 分层纪律（本库最容易违反的一条）

```
工作记忆/     ← 现役知识，必须全部当前有效。任一条失效立即改写或删除。
cases/        ← 历史现场，按日期归档，允许陈旧，检索时须看日期。
上游溯源/      ← 外部项目情报，标注"针对上游版本 vX"，上游变了要重验。
```

> **本次体检发现的畸形**：`cases/` 的内容被大量抽进 `工作记忆/` 与 wiki 各层，
> 导致「历史现场」与「现役知识」混杂。修复方向 = 按上述三分归位。

### 5.3 体检纪律（定期跑，不靠自觉）

| 检查项 | 健康判据 |
|---|---|
| 某主题页数 | 单一主题 ≤ 8 页（超过说明碎片化，需整合） |
| 重复页对 | 0（规范化标题后同名 = 必须合并） |
| 断链 | 0 |
| 陈旧定性残留 | 已被推翻的方案名在库内出现次数 = 0（仅案例页可保留，且须标注已作废） |
| 每页溯源 | `sources:` / `related:` 非空 |
| 版本混杂 | 现役版本号在「现役」语境下唯一 |

## 六、一页速查（TL;DR）

> **这是爬虫，不是业务系统。**
> 契约会漂移，失败是常态，参考信息天然稀缺——所以：
> **① 一切以真实效果为准（M1 探针）；② 先判断是"世界变了"还是"代码错了"（M2 漂移检测）；
> ③ 失败必须可见（M3 三态）；④ 决策只有一个出口（M4 SSOT）；
> ⑤ 策略与组件必须可换（D4）；⑥ 知识必须会过期，作废靠替换不靠追加。**
>
> 缺哪一条，哪一条就会变成下一次 debug 的干扰源。
