# V2 私信收发链路（2026-08-20 整理）

> 已验证成功的核心链路，符合当前 V2 架构。旧记忆中关于"KICK=接口路径错误/缺 msToken-a_bogus"的论断已被后续修复推翻，此处以最终正确版本为准。

## 一、凭证还原
- 发送/接收均用 `DYLoginApi._load_auth_from_env(env_path)` 读 `.env` → 还原完整 auth（cookie/ticket/ts_sign/client_cert/private_key + web_protect/keys 派生 ree_public_key）。

## 二、发送
- `core/sender.py` `send_by_uid` → `DouyinAPI.create_conversation`（`imapi.douyin.com/v2/conversation/create`，POST protobuf body，靠 body 内 ticket/ts_sign/sdk_cert 签名鉴权，不叠加 www.douyin.com 的 bd-ticket-guard-* 头）+ `DouyinAPI.send_msg`（`imapi.douyin.com/v1/message/send`）。
- msToken：优先 cookie 真实值，缺失则 `generate_msToken()` 动态生成（回归基座）。

## 三、接收
- `daemon/recv_daemon.py` 连 `frontier-im.douyin.com/ws/v2`（IM 私有长连接），消息按 `conversation_id` 隔离到 `AccountInbox.convs`；历史持久化 `dm_history.json`（重启不丢，unread 不持久化）；HTTP 9912 提供 `/conversations?account=`、`/conversation`、`/send`、`/quit`。
- 启动即加载已有会话：WS 连接初期抖音下发 `get_conversation_info_list_v2_response_body`（tag 610），`_sync_conversations` 建骨架（short_id 持久化），不等首条新私信。

## 四、调度（core/dispatch.py）
- `DispatchCenter`：入队延迟私信（捕获时刻 + SEND_DELAY_SEC 抖动到点才发）；去重跨来源（user_id / sec_uid / nickname 三件套）；`_loop` 锁外调 `_do_send`。
- 软停止 `stop_keep_queue()`：停监听但保留已入队延迟私信继续发完；硬停止 `stop()` 清空队列。
- `_on_dispatch_idle`：在 `state==STOPPING` 时直接 return（不提前收尾），交给 `_wait_dispatch_done` 等真发完，杜绝"日志显示发完但实质漏发"。
- `submit` 写 records 必须放在所有拒绝点**之前**（即使停止/暂停态拒发也保留 CAPTURED 记录），杜绝"连记录都没有"的漏发感知。

## 五、统计透传（api/tasks.py + overview.py）
- `get_tasks` 返回 `_records_from_adm(adm)`（从 `adm.dispatch.records` 取 `.values()`，转前端 Row dict）；`SendRecord` 是 Pydantic，迭代 `.values()` 而非直接 `for r in records`（后者迭代的是字符串 key）。
- status 用 `RecordStatus` 英文枚举（captured/sent/fail/skipped），前端 `toDmStatus` 映射：captured→wait / sent→sent / fail→fail。
- 字段映射：`captured_at` 同名、`sent_at`→`send_ts`、`user_id`/`sec_uid` 兜底 `uid`。

### 5.1 失败原因结构化分类与弹窗（2026-09-08 落地，commit `0155bc8`）

**需求**：私信发送失败时须弹窗说明**具体是调度堵塞 / 凭证失效 / 账号风控 / 频控限流还是其他**，不能再只给一行原始报错。

**七类划分**（`core/sender.py`：`classify_fail()` + `explain_fail()`，纯文本归类、零网络零副作用）：

| kind | 类名 | 判定关键字 | 用户建议 |
|---|---|---|---|
| `risk` | **账号风控** | KICK / 风控 / spam / 被限制 | 降频、暂停该账号 30 分钟、换账号 |
| `credential` | **凭证失效** | 签名三件套缺失 / 需重新扫码 / INVALID_REQUEST / 登录态失效 | 到「账号」页【重新扫码】重抓签名 |
| `ratelimit` | **频控限流** | rate_limited / 频繁 / 冷静期 / 冷却 / 上限 | 等冷却，勿连续重发（会加重限流） |
| `blocked` | **调度堵塞** | 堵塞 / 队列 / queue / 超时 / busy / 调度 | 暂停任务等队列消化，持续则重启后端 |
| `param` | 参数错误 | 为空 / 非数字 / uid 解析失败 / 会话整理失败 | 检查该目标会话数据完整性 |
| `network` | 网络异常 | 不可达 / connection / HTTP 5xx | 检查后端与 recv_daemon 是否在跑 |
| `other` | 其他原因 | —— | 看原始原因 + 后端日志 |

**⚠️ 判定顺序铁律：账号风控（KICK）必须最先判**。抖音返回的文案形如
`私信被风控(INVALID_REQUEST/KICK): ...`——**同时含 KICK 与 INVALID_REQUEST**，
若先判凭证会被误归为「凭证失效」（误导用户去扫码，实际是反 spam 风控）。
后端 sender.py 注释已明确：**KICK 多为账号级私信风控，不是签名失效**。
实测分类用例 12/12 覆盖此坑（修前 11/12）。

**数据链路**：
```
core/dispatch.py 发送失败 -> 填 rec.fail_kind/label/advice（explain_fail）
        ↓ models/task.py SendRecord 增三个字段
        ↓ api/tasks.py _records_from_adm 透传（**必须显式列出**，否则前端收不到）
        ↓ frontend/live.tsx Row.failKind/failLabel/failAdvice
        ↓ ReviewMode 失败行 -> 点击 -> FailReasonModal 弹窗
```

**易错点**：
1. `api/tasks.py` 的 dict 是**逐字段显式构造**，`SendRecord` 新增字段不会自动透传——必须手动加一行。
2. 失败列表渲染在 **`ReviewMode` 组件**（live.tsx 内第二个组件），不是 `LivePage`；弹窗 state 与 `<FailReasonModal>` 必须挂那里，`useState` 放错组件会报 "declared but never read" + "Cannot find name"。
3. 前端保留 `localClassifyFail()` 兜底：旧后端未下发时也能分类（规则与后端保持一致，**含同样的 KICK 优先顺序**）。

**实测验证**：分类用例 12/12 通过；端到端透传 3/3（credential/risk/ratelimit 各自正确）。

## 七、图片消息链路（2026-09-03 落地，详见 08 §四十）

完整链路（此前只有前两步，后两步缺失导致「前端看不到原图」）：

```
① 捕获落库  dm_messages.extra = {"skey":..., "origin_url":...}
              conversation_capture.parse_conversation_301 / recv_daemon._extract 写入
② 后端解密  auto_dm/origin_image_resolver.py::resolve()
              HTTP GET 密文(不带 cookie) → AESGCM(skey) 解密 → HEIC→JPEG 转码
③ 接口透出  api/messages.py::get_conversation 读 extra → messages[].image_url
④ 前端渲染  messages.tsx 情况 0：有 image_url 直接 <img>，优先于缩略图
```

要点：
- **`image_url` 优先级最高**（前端"情况 0"），先于 `[图片]`/`[原图]` 文本解析与 inline_pic 缩略图。
- 分流：**小图(≤32KB)本地静态** `<app_root>/data/origin_images/`；
  **大图默认也走本地**（tucdn 实测偶发 502、imgbb 频繁 SSL 超时），
  仅 `IMAGE_FORCE_HOSTED=1` 才上图床。
- HEIC 占 40%，服务端 `pillow_heif` 转 JPEG，前端零感知。
- 端点：`GET /origin_image/{filename}`（白名单防路径穿越）、
  `POST /origin_image/resolve`（手动补触发）、`GET /origin_image/stats`（缓存统计）。
  ⚠️ **stats 必须注册在 `{filename}` 之前**（FastAPI 按注册顺序匹配，否则被通配吃掉）。
- 缓存：sha1(skey|origin_url) 进程内 30 天，密文 HTTP 5 分钟。**二次访问 0 请求**。
- 风控：HTTP GET 不带账号 cookie，只靠 URL 自带签名；零主动批量。
- 依赖：`cryptography` + `pillow-heif` 已补进 `backend/requirements.txt`。
- **TTL 清理(2026-09-03)**：本地原图 30 天/2GB 上限双回收，mtime 判龄 +
  `touch_local()` 访问保活 + `sweep()` 三层触发(启动后台 60s / resolve 写图后 1h 节流 /
  手动 `POST /origin_image/sweep`)。配置 `ORIGIN_IMAGE_TTL_DAYS` / `ORIGIN_IMAGE_MAX_MB`。

**推翻的旧结论**（2026-08-31 记录）：
「resource_url 远程链浏览器加载失败（3/3 error，0×0）→ 只能去抖音网页看原图」
—— 该结论只在"前端裸拉远程链"场景成立；**密钥就在同消息 extra 里，后端代为解密即可**，
前端可直接显示高清原图（实测 50 条消息中 5 张图 100% 显示，411KB JPEG 证真）。

## 【2026-09-12 实测修复】PEP562 惰性常量「函数内裸名」系统性 NameError

### 问题（BUG1）
`services/dm_dispatch.py` 用 **PEP 562 模块级 `__getattr__`** 做配置中心惰性常量：
原名常量改名为 `_FALLBACK_<原名>`，`__getattr__` 命中 `_LAZY_MAP` 时返回 `cfg(name)`。

**缺陷**：`__getattr__` 只对**模块属性访问**（`dm_dispatch.QUEUE_MAX`）生效，
**对函数体内的裸名引用完全不生效** → 抛 `NameError`。

- 实证：`d.QUEUE_MAX` ✅ / `d.cfg("QUEUE_MAX")` ✅ / 函数内裸名 `QUEUE_MAX` → ❌ NameError
- 影响：`submit()` 的入队检查 L845 `if q.qsize() >= QUEUE_MAX:` 直接崩 →
  **409 次发送全失败**（与凭证无关，纯代码缺陷，必然复现）。

### 排查结论：不止 QUEUE_MAX —— 同类裸名共 25 处
| 常量 | 处数 | 影响路径 |
|---|---|---|
| `QUEUE_MAX` | 5 | 入队（L845/846/924/925/1058） |
| `POOL_STRICT` | 1 | 会话整理严格模式（L792） |
| `DEDUP_WINDOW` | 2 | 去重窗口（L708/711） |
| `STRANGER_PER_MINUTE` | 3 | 陌生人首发限流 |
| `STRANGER_PER_DAY` | 3 | 同上（每日） |
| `COOLDOWN_ON_FREQUENT` / `COOLDOWN_MAX` | 2 | 频控冷静期 |
| `WEIGHT_RECOVER_HALFLIFE` | 6 | 权重半衰期恢复 |
| `UID_SINK_COOLDOWN` / `UID_SINK_STRICT` | 3 | uid 汇冷却 |

### 修复
- 全部裸名 → **`cfg("常量名")`**（唯一正确写法）。
- 坑1：f-string 内**嵌套同种引号**在 Python < 3.12 语法错误 →
  `f"{cfg('WEIGHT_RECOVER_HALFLIFE') ...}"` 用单引号。
- 坑2：**别改 docstring**（`_decay_freq` 的注释里出现常量名是说明文字，不是引用）。
- 排查方法：全项目扫 `def __getattr__` + `_LAZY_MAP` 的文件，逐个常量找函数内裸名。
  （实测全项目只有 2 个文件有此机制：`dm_dispatch.py`、`uid_probe.py`，后者干净。）

### 验证
`disp.stats()` → `queue_max=200`、`stranger_limit={'per_minute':2,'per_day':30}`；
`submit()` 走到白名单/会话整理校验（不再 NameError）；
真实发送日志出现 `[dm-dispatch] 入池 task=8d5248330d1b ... 队列=1`。
