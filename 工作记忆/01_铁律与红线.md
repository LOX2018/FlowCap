## 一·甲、🔴 接口类 debug 必先遍历上游接口全集（2026-09-21 用户明确要求）

> **用户原话**：「涉及接口类的debug，在修改之前，先去 GitHub 等开源社区遍历最新的抖音接口，
> 将所有最新的抖音接口（**注意是所有接口，非 debug 业务用到的接口**）全部重新写入到上游情报当中。」

### 铁律

**触发条件**：任何涉及「接口」的 debug 或修改 —— 包括但不限于：
新接口接入 / 接口失效 / 字段变化 / 签名变化 / 请求方式变化 / 域名变化。

**强制前置动作（在改任何代码之前）**：

1. 去 **GitHub 等开源社区**遍历**最新的**抖音接口情报
   （抖音爬虫类项目：`cv-cat/DouYin_Spider`、`ihmily/DouyinLiveRecorder`、
   `saermart/DouyinLiveWebFetcher`、`TeamBreakerr/douyin-chat-export` 等，
   清单见 `docs/upstream_sources.json`）。
2. 把 **所有最新抖音接口**——**不是**只有当前 debug 业务用到的那个——
   重新写入 `10_上游情报_*`（上游情报分册）。
3. 写入时必须带：**来源项目 + 拉取日期 + 接口路径 + 用途**。

**判据（缺一不算执行）**：

- 上游情报里存在一份**全量接口清单**（覆盖内容侧 / IM 侧 / 直播侧 / 认证侧），
  而非只有本次业务相关的那几条；
- 每条带**来源与日期**；
- 能回答「抖音现在有哪些接口」，而不只是「我这个接口现在对不对」。

### 为什么是「所有接口」而不是「本次用到的接口」

| 做法 | 后果 |
|---|---|
| ❌ 只查本次 debug 用到的接口 | **每次 debug 都要重查一遍**；且不知道"还有哪些接口存在" → 无法判断某能力**是否本可以走更稳的接口** |
| ✅ 遍历并落全量清单 | 接口全集是**地图**：任何一处的失效都能在地图上定位；新需求可直接查表；上游变更时能整体比对（服务 M2 契约漂移检测） |

**这正是「不围现有代码打转」的落地形式**：围着本次 bug 查接口 = 围现有代码打转；
先建接口全集 = 先有世界模型。

### 与既有机制的关系

| 机制 | 分工 |
|---|---|
| **本铁律（R8）** | 提供「**最新的应该是什么**」——接口全集 |
| `M2 契约漂移检测` | 检测「**是否变了**」 |
| `D5 知识有保质期` | 要求每条接口带日期，过期须重验 |
| `10_上游情报_*` | 本铁律的**落点**（所有接口写进这里） |

> ⚠️ **反例（必须避免）**：本项目历史上多次「抖音改版 → 昵称失效 → 只在自家代码里
> 找与以前的差异」，全程未去上游看"现在抖音到底有什么接口"。
> 结果：反复在旧定性里打转，最终才发现正解是 IndexedDB（一条不在旧清单里的新路径）。
> **若当时先遍历上游接口全集，该结论可以更早得到。**

## 二、进程与浏览器启停（风控级）

1. **非必要不杀浏览器**：一次启动跑完整个流程，不为换探针而 kill 再拉起。
   **依据**：用户原话「非必要不要老是杀死浏览器后又重新激活，很容易风控」。
2. **绝不强杀 BCC / 主程序**（`Stop-Process` 会导致 session 降级重认证）。
   停止走 graceful close（`/quit`）。
3. `taskkill /IM chrome.exe /F` **只在确认死锁/孤儿进程时**用，非常规操作。
4. **单 profile**：每账号单一固定 profile，守护/查看/重扫复用。
   跨进程抢同一 profile → `SingletonLock` 冲突崩溃。
5. **联机探活后再操作**：任何拉起守护前先核对当前是否已在线（单例门禁）。

## 三、实测优先（用户核心要求）

1. **推断/假设必须实测验证后**才能据此改代码、下结论。严禁把推断当事实。
   - 反例：2026-09-08「双 uid 体系」误判、2026-09-09「`is_turn_on=0`=主播关闭连麦」误判。
2. 实测推翻推断后**必须撤回错误改动**并**改写知识库**（替换，非追加）。
3. **「验证后才汇报」**：任何「发送成功 / 风控触发 / 功能可用」结论必须有硬证据
   （如 DB 落库 `role=me` + skey 记录、接口返回体），
   严禁仅凭抓包到中间步骤或 UI 弹窗就宣称成功。
4. **定位「前端显示问题」先看前端收到的接口数据**，再谈代码。
5. 单一采样不足以定论：字段为 0/false 时先确认**前置状态**，避免采样偏差。
6. **「以前定性」不是证据**（见 `00_爬虫项目说明.md` §3.3 数据可信度分级）：
   旧文档/旧日志属 D 级，必须重验后才可作结论。**这是本项目最高的方法论红线。**

### D-02 · 版本递增分流：**产品行为** 升 patch，**验证/文档** 打 pre-release（2026-09-22 用户拍板）

> **背景（客观读数）**：本政策出台前，`v0.44.24 → v0.44.33` 在 **2 天内走了 9 个 patch 节点**，
> 而原策略规定「累积 patch 三个节点 → 强制全库审计 + 功能冻结」。
> ⇒ 两条规则**数学上互斥**：审计红线会被每两天触发一次，而全库审计本身又是全库级工作量
> （`H-6` 长期挂账即可为证）。这不是执行不力，是**策略冲突**。

| 项 | 值 |
|---|---|
| 决策 | **产品行为改动** → patch `+0.01`（不打积压审计）；**验证/判据/探针/门禁/文档/知识库类改动** → **不升 patch**，打 pre-release `-debug.N`（对齐既有 `v0.43.34-debug.1` 形态） |
| 判据（可机械执行） | 提交 `type` 为 `feat` / `fix`（**且改的是产品运行时行为**）→ 升 patch；为 `test` / `docs` / `chore`，或虽为 `fix` 但**只改验证器本身**（探针判据、守卫测试、门禁脚本、版本同步）→ 打 `-debug.N` |
| 审计红线触发口径 | 只计**产品行为 patch 节点**（如本次 9 个节点中，产品行为约占 5 个）；达 3 → 触发全库审计 + 功能冻结（H-6） |
| 权衡（显式接受） | 牺牲"每次提交都有唯一点版本号"；换来审计红线不被无意义触发。**升版号与打 tag 仍是每次提交的强制动作**，追溯性不受损 |
| 何时仍须全量重建 | 见 `dyautodm-dev-guards` §四·3：**一旦升了 patch，主 exe 必须一起重建**（前端 `__APP_VERSION__` 烘进 exe，前后端版本不等即全屏阻断启动） |

### D-04 · 并发边界：**离线可并行，真机永远串行**（2026-09-22 确认）

| 判据 | 正解 |
|---|---|
| 离线/只读验证（回放、纯逻辑、静态门禁） | **各自独立临时根，可并发**（`replay.sandbox` 即此原语的实现） |

### D-05 · 一条码只保留一条完整记录；六段契约**单一宿主** = `CODE_DESIGN`（2026-09-22 实测）

> **背景（线上缺陷，已复现）**：`errcode_data.py` 的 `ERRCODES` 字典内 `"ACC-017"` 被定义两次
> （行 185 单行 `{meaning,file,line}` / 行 333 六段契约）。Python 字面量重复键 **last-wins 且无告警**
> ⇒ 生效的那条缺 `meaning` ⇒ `lookup()` 的 `c["meaning"]` 抛 `KeyError` ⇒
> `all_codes()` 与 **`GET /api/errcodes`（会员门禁豁免端点）必然 500**。

| 项 | 值 |
|---|---|
| 决策 | ① 一条错误码在 `ERRCODES` 里**只允许出现一次**，且该条**必须含** `meaning/file/line`；② **六段契约（design/contract/deviation/chain/root/verify）只写在 `CODE_DESIGN`**，不得写进 `ERRCODES`；③ 追加契约时**按真实语义撰写**，不得把邻居编号的描述照抄过来；④ 业务代码从未发出的码**不追认契约**（先删/改名，再加） |
| 判据（机械） | `test_no_dup_dict_keys.py` 的 `test_whole_backend_has_no_duplicate_dict_keys` —— **全后端 .py 扫描**，任一字典重复键即 FAIL |
| 门禁盲区（已修） | 原门禁 `TARGET` **硬编码只扫 `services/app_config_schema.py`** ⇒ 该形态在别处无防护（实测因此放过了 ACC-017，门禁全程绿）。现扩为全后端扫描 |
| 有效性反证 | 用「改前备份」喂 `find_dup_keys()` 必报 `dict@163: 'ACC-017' 行 [185, 333]`；修复后 0 命中（未证明会拒绝的门禁 = 假门禁） |
| 顺带清出的幽灵码 | `ACC-018~021` 的六段契约原错放在 `ERRCODES` 内，但：① 它们在 `ERRCODES` 里**从无条目**（`lookup()` 曾返 None）；② 业务代码 **0 处**发出；③ 其描述的事件（未取得 profile 所有权锁）由 `ACC-022/023/024` 承担且各有契约。⇒ **不回填**（回填会造出 4 条永不触发、且劫持邻居编号语义的契约） |

### D-06 · 🔴 共享工作区**不得留半成品**；并发提交会夹带并在制品的状态（2026-09-22 实测事故）

**事实**：本会话改 `errcode_data.py` 至半成品态期间，**另一会话于 16:04 提交 `e43d153`（v0.44.34）**，
其 diff **含该文件我改到一半的状态**，随后于 16:08 构建、16:10 部署 ——
即：**别人一次 commit 把我未完成的代码带去构建并部署上线**。

| 项 | 值 |
|---|---|
| 判据 | 并行工作线提交时**快照整个工作区** ⇒ 会把他人未提交的中间态一并带走（与"逐文件 add 保护不了文件内他人 hunk"互为镜像） |
| 铁律 | ① 改文件前**先声明所有权**（写清"我负责哪些文件"）；② 做不到独占就**隔离副本**（`git worktree` 或每会话一份源码树）；③ 绝不在共享工作区"改一半放着"；④ **生产/部署产物必须来自干净提交**，不得来自半成品工作区 |
| 发现版本号/暂存区异常时的动作 | **先查并发**（`git log` 时间线 + 产物 `ls -l` 时间）→ 再决定重升版或等对方收工。**禁止**盲目再升一次（会撞号）；也**禁止**回退他人已提交成果（那是销毁他人工作） |
| 暂存失败的教训 | `git add a b c` 中**任一路径不存在** ⇒ **整条 add 失败且只报 bad path**，看起来像"没变化"、实际什么都没暂存 ⇒ add 后**必须回读** `git diff --cached --name-only` 逐条核对 |

### D-07 · 🔴 验收判据必须自证「失败态会变红」（2026-09-22 实测教训）

**事实（本轮）**：交接卡 HC-04 把「`GET /api/errcodes` 返回 **200**」当作 errcodes 500 修复的
**完成标准**。实测：**部署态旧版 0.44.34 也返回 200** ⇒ 该判据在新旧版本上都亮绿，
对本次修复**毫无区分度**。（500 只在同键冲突槽位恰好丢掉 `meaning` 时由 `lookup()` 抛
`KeyError` 才发生；覆盖后的条目仍是合法条目 ⇒ 该端点并非「必然 500」，卡里那句是**过强的断言**。）

| 项 | 值 |
|---|---|
| 判据 | 任何「修复完成」判据，必须能在**未修复态**下**变红**；否则是**恒绿判据**，与没有判据等价 |
| 机械做法 | 写完判据后**拿旧产物/回退修复跑一次**，确认变红；再还原跑绿。**只跑一次绿不能证明判据有效** |
| 可区分判据示例 | `/api/errcodes` 的 **`ENG-021/ENG-022` 存在性 + `has_contract=true`**（旧版 `total=361`、`/api/errcodes/ENG-021` 返「未知代码」⇒ 必红；新版 363 且六段非空） |
| 同族 | 与「没证明会拒绝的门禁 = 假门禁」（D-05 有效性反证）、守卫测试须回退变红，是同一条纪律的三处实例 |
| 附：断言接口行为前先读实现 | 断言某端点「必然 500」之前，先读 `lookup()` / `all_codes()` 的失败路径，确认它真的必然到达 |

### D-08 · 🔴 审计维度必须含**存量扫描**；纯 diff 审计看不见「没变化的危险」（2026-09-26 用户指出）

**事实**：用户原话 ——「这个项目我至少经历过 4 次全盘审计，都没有发现数据库治理的问题」。

实测复盘 3 份历史审计报告，维度**全部是「代码结构」视角**（入口分裂 / 分层依赖 /
大组件行数 / **逐条 diff**）。最后一类最致命：它是**增量审**，而 `schema` 从未改动
⇒ 天然不进入 diff 视野。**「没变化的危险」永远不会被增量审计发现。**

| 项 | 值 |
|---|---|
| 判据 | 审计维度清单必须**显式维护**，且至少含一个**存量扫描**维度（不看 diff，扫全量当前态）。只审「这个版本改了什么」= 结构性漏审 |
| 本项目落盘 | `scripts/audit_data_contract.py`（R8-1~R8-6），**委托**接入 `check_iron_rules.py` ⇒ 每次铁律检查都覆盖数据契约 |
| 🔑 直击根因的判据 | **R8-6「同一语义不得多名字」**：禁 `msg_type IN('a','b')` / `OR` 并列。多名字并列 = 「字段无规划」的**可测量形态**，是债务的早期指纹 |
| 上线即见效 | R8 上线当天抓出 2 个真问题：① `msg_type='image'` 未登记 ⇒ 发图被降级 `[未知类型]image`（v0.45.5 我引入的回归）；② `dm_search` 容忍不存在的别名 `'video'`（无任何写入点产生过） |
| 命名决策（用户拍板，方案 B） | 同一语义**只保留一个名字**：调用点统一为注册的 `"27"`/`"8"`，Registry **不收别名**；历史残留走迁移，不靠别名兼容 |
| ⚠️ 反面纪律 | **审计工具造假红比漏报更危险** —— 人一旦习惯了假红就会忽略它，那时的门禁比没有更坏。本批初版跑出 8 处假红（不区分表 / docstring 被当载荷 / 注释被当字面量），**逐条人工核实后**修正判据 |
| 与 D-07 的关系 | D-07 要求判据「失败态会变红」；D-08 进一步要求「**红必须是真的**」—— 故新增判据必须逐条核实命中行，并注入历史原状做负控 |
