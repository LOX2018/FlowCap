### 1.3 设备红线（长期有效）

1. **任何环节不得使用真实麦克风 / 真实摄像头**；键盘、鼠标、网卡不受限制。
2. 实现**缺一不可**：启动参数 `_FAKE_MEDIA_ARGS`
   （`--use-fake-device-for-media-stream` + `--use-fake-ui-for-media-stream`）
   **且** profile Preferences 放行音频、拒绝摄像头。
3. ⚠️ **事故教训**：曾为「验证不使用真实设备」调用 `getUserMedia({video:true})`，
   **真的打开了物理摄像头**。**任何验证脚本只允许测音频，禁止任何 video 调用。**

## 二、进程与浏览器启停（风控级）

1. **非必要不杀浏览器**：一次启动跑完整个流程，不为换探针而 kill 再拉起。
   **依据**：用户原话「非必要不要老是杀死浏览器后又重新激活，很容易风控」。
2. **绝不强杀 BCC / 主程序**（`Stop-Process` 会导致 session 降级重认证）。
   停止走 graceful close（`/quit`）。
3. `taskkill /IM chrome.exe /F` **只在确认死锁/孤儿进程时**用，非常规操作。
4. **单 profile**：每账号单一固定 profile，守护/查看/重扫复用。
   跨进程抢同一 profile → `SingletonLock` 冲突崩溃。
5. **联机探活后再操作**：任何拉起守护前先核对当前是否已在线（单例门禁）。

## 三、实测优先（用户核心要求）

1. **推断/假设必须实测验证后**才能据此改代码、下结论。严禁把推断当事实。
   - 反例：2026-09-08「双 uid 体系」误判、2026-09-09「`is_turn_on=0`=主播关闭连麦」误判。
2. 实测推翻推断后**必须撤回错误改动**并**改写知识库**（替换，非追加）。
3. **「验证后才汇报」**：任何「发送成功 / 风控触发 / 功能可用」结论必须有硬证据
   （如 DB 落库 `role=me` + skey 记录、接口返回体），
   严禁仅凭抓包到中间步骤或 UI 弹窗就宣称成功。
4. **定位「前端显示问题」先看前端收到的接口数据**，再谈代码。
5. 单一采样不足以定论：字段为 0/false 时先确认**前置状态**，避免采样偏差。
6. **「以前定性」不是证据**（见 `00_爬虫项目说明.md` §3.3 数据可信度分级）：
   旧文档/旧日志属 D 级，必须重验后才可作结论。**这是本项目最高的方法论红线。**

## 五、知识库纪律（**本条已重写**）

旧纪律是「追加式回写」（`cp` 到 raw/sources → rescan），它是知识库腐化的直接原因。

**新纪律**：

1. **现役知识必须全部当前有效**。任何一条被推翻 → **就地改写或删除**，
   不得「保留历史留痕」；历史留痕写进 `cases/`。
2. 每页必带四要素：`性质` / `实测日期` / `判据` / `有效期或失效条件`（见 `00_索引与导航.md` §四）。
3. **一页一事实**；不写修复流水账（流水账 → `cases/`）。
4. 未验证的推测必须显式标 `【未决假设】`。
5. **数字必须现场重算**（正则扫描有系统性偏差；本次体检初测 623 实为 AST 精确 340）。
6. 归档顺序：桌面权威源 → Obsidian 可靠层 → LLM Wiki（顺序绝不可反；绝不直写 `wiki/`）。
