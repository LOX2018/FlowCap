## 15.1 架构：schema 驱动

```
backend/services/app_config.py   ← 唯一真源：SECTIONS schema + kv 持久化
        │  get / save_section / reset_section / schema()
        ↓
backend/api/settings.py          ← 配置网关（4 端点）
        ↓  /api/settings
frontend/components/UnifiedConfigSection.tsx
        └── 按 schema **自动生成表单**，新增参数前端零改动
```

**关键设计**：参数在 `app_config.SECTIONS` 里声明一次（label/type/default/
min/max/apply/hint/risk），后端自动获得校验与持久化，前端自动获得表单。
此后新增一个全局参数，**只需在 SECTIONS 加一项**。

### dm_dispatch 的接线手法（值得复用）

风控参数是模块级常量（如 `QUEUE_MAX = int(os.environ.get(...))`），
直接改会漏调用点。做法是：

1. 常量**重命名**为 `_FALLBACK_<原名>`
2. 加 `_LAZY_MAP = {原名: (section, key)}`
3. 加模块级 `__getattr__`（PEP 562）返回 `cfg(原名)`

这样**所有既有调用点自动走配置中心**，零遗漏。
（注意：`__getattr__` 只对**不存在的**属性触发，所以必须改名，不能只加。）

## 15.4 三个开关的语义（用户决策，勿改）

**settings 实例优先，配置中心只作镜像同步，不反向覆盖。**

```python
def _flag(key: str, settings_obj) -> bool:
    return bool(getattr(settings_obj, key, True))   # 读：以 settings 为准
# 写：save_config 里 save_section("live", {...})   # 写：镜像进配置中心
```

**为什么不让配置中心优先**（曾踩坑）：
`app_config.get()` 在 reset 后会返回 schema 默认 `True`，若让配置中心优先，
settings 里的 `False` **永不可达**（回落路径是死代码），表现为
「用户在任务页关掉开关 → 切到设置页又被重置为开」。

## 15.4 配置标签（v0.38.2）：标签是指引，参数归原单位

> 用户原话纠正：**「标签是指引，具体的参数任由原单位隔离存储」**

### 职责边界（与 Agent 并列，不重叠）

| | 管什么 | 存储 |
|---|---|---|
| **Agent** | 「回什么」：回复内容（prompt / 知识库 / 话术 / 档位） | kv `ai_agents` |
| **标签** | 「怎么发」：发送风控频率 / 直播监听 / 历史捕获策略 | **不存参数** |

账号 = 1 个 Agent + 1 个标签。

### 核心设计：标签不持有参数副本

```
标签 = {id, name, created_at, updated_at}        ← services/config_tag.py
参数 = app_config.get(sec, key, scope="tg_xxx")  ← services/app_config.py（原单位）
```

- 标签 kv：`config_tags`（仅元数据）、`config_tag_bind`（账号绑定）
- 参数 kv：`app_config::<tag_id>`（按 scope 隔离）
- **删标签 → 解绑账号 + `drop_scope()` 清参数**（无孤儿数据）

`app_config` 为此新增：`scope_key(scope)`、`drop_scope(scope)`，
且 `get / get_section / save_section / reset_section` 均加 `scope` 参数
（默认 None = 全局，零回归）。

### 受管分区

`send` / `live` / `capture` —— `general` 是前端与系统行为，**不进标签**。

### 消费方接入

```python
dm_dispatch.cfg("STRANGER_PER_MINUTE", account="账号A")
#  → config_tag.scope_of(account) → app_config.get(sec, key, scope=...)
#  未绑定标签 → scope=None → 读全局（行为与改造前逐字一致）
```

所有标签调用 try/except 包裹，异常绝不阻断主流程。

### 踩过的两个坑（已修，勿重犯）

1. **id 碰撞**：`_new_id()` 曾用 `int(time.time()*1000) + id(object())`，
   同毫秒内建两个标签会生成**完全相同**的 id（CPython 复用刚释放的临时对象
   地址）→ 后者覆盖前者，表现为「第二个标签拿不到自己的参数」。
   `config_tag` 与 `ai_agent` 是同款写法，均已改 `uuid.uuid4().hex[:16]`。
2. **静默失败**：`app_config` 漏 `import database` → `drop_scope` 里的
   `database.get_db()` 抛 NameError 被 `except: pass` 吞掉 →
   表现为「删了标签但参数还在」。现改为记日志（CFG-010）+ 返回 bool。
   **教训：except 吞异常会让 bug 伪装成"功能没生效"。**

## 15.6 测试隔离（重要教训）

**坑**：`backend/database.py` 在**导入时**按 `DY_APP_ROOT` 固化 SQLite 路径。
`unittest discover` 会把所有 `test_*.py` 导进**同一个进程**，
于是**第一个**导入 database 的文件决定了 DB 路径 →
- 测试之间互相看到对方写入（单独跑全绿、整体跑失败）
- DB 落在源码目录 `backend/data/`，**污染真实配置库**

**解法**：`backend/test_config_isolation.py`
```python
_ROOT = <tempdir>/dyautodm_cfgtest_root
os.environ["DY_APP_ROOT"] = _ROOT
def fresh(section=None):   # 清掉 database / services.* 后重新导入
    ...
```
所有配置类测试文件顶部 `import test_config_isolation as iso; ac = iso.fresh()`。

## 15.7 边界保护（曾误导自己）

`save_section` 对越界值**直接丢弃**（`_coerce` 返回 None 则 continue），
回落 schema 默认值。例：`max_wait` 下限 5s，测试填 0.5s 会被丢弃回落 30s
—— 这是**正确行为**，但意味着设置页必须在 UI 上标出 min/max，
否则用户填小值会「改了没效果」。已在前端 `SchemaField` 显示范围并本地校验。

### ⑥ v0.38.5 补丁：「默认接收目标」自动推导（用户追问"为什么还要手填"）

- **根因**：default_target 是纯推送时代的历史字段（系统不知道推给谁）。
  有了网关后，**已授权来源本身就是合法推送目标**，无需手填。
- `notifier._targets_for(cid)`：手填目标（兼容保留，排在最前）→
  追加网关 grants 里**同渠道、非 blocked** 的 sender_id，去重多目标派发。
- 🔴 **坑：channel_id 双语义**——grants 里的 channel_id 是 **kind**
  （weixin_oc，来自 sender_key 前缀），派发循环的 cid 是**渠道实例 id**
  （如 ch_wx）。匹配必须同时比对两者（`kinds = {cid, cfg.kind}`），
  否则自定义渠道 id 的授权来源永远匹配不上（实测踩中，表现为推导空）。
- 🔴 **坑：gateway 单例未绑定**——`_get_cfg` 只在 `init_notifier` 绑定，
  任何绕过它的调用方（如 notifier 派发）拿到的是空配置。已加
  `ensure_bound()` 模块级自举（延迟 import api.notify，避免循环依赖）。
- 前端：字段改名「默认接收目标（可选）」，placeholder
  「留空 = 自动推送给已授权的会话」。
- 实测：无手填渠道自动推导 2 个授权来源（blocked 已排除）；
  手填+授权混合去重；id==kind 场景无重复。测试 grants 已清。
