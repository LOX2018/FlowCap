# V2 指纹浏览器与凭证链路（2026-08-20 整理）

> 筛选自已验证修复，符合当前 V2 架构（login_api.py / vbrowser.py / accounts.py 现状）。

## 一、指纹浏览器内核（vb_chromium）
- 项目强制只用指纹内核（ungoogled-chromium），**禁止回退原生 Playwright**（USE_VIRTUAL_BROWSER 必须 True，不可用时直接 raise RuntimeError，绝不静默降级）。
- `_CHROME_ARGS`（`vbrowser.py`）已去掉 `--no-sandbox` 与 `--disable-blink-features=AutomationControlled`（后者是我们自己写的冗余参数，ungoogled 编译期已移除 webdriver 痕迹，反而触发内核警告）。如仍见 `--no-sandbox` 警告，根因是 Playwright 在 Windows headed 模式强制注入 → 三处 `launch_persistent_context` 加 `ignore_default_args=["--no-sandbox"]` 剔除。
- CDP 模式（VB_MODE="cdp"）走 `connect_over_cdp`，根本不经过 Playwright 启动器，无任何这类警告；但需本地跑 VirtualBrowser/Ant-Browser 服务，当前 exe 模式无此服务。

## 二、扫码抓凭证（login_api.py）
- `get_login_auth(headless=False, env_path, force=True)` 弹 vb_chromium → `login_grab_ticket` 抓四件套(DY_COOKIES/DY_TICKET/DY_TS_SIGN/DY_CLIENT_CERT/DY_PRIVATE_KEY) + web_protect/keys（security-sdk 生成）→ `save_credential` 写各账号 `.env`。
- web_protect/keys 持久化：login_grab_ticket 把原始 web_protect_str/keys_str 挂 auth；save_credential 写 DY_WEB_PROTECT/DY_KEYS；`_load_auth_from_env` 优先用它们还原（含 ree_public_key），无则回退四件套+补 ree_public_key=base64(private_key)。
- `DY_PRIVATE_KEY` 在 .env 是字面量 `\n`（_encode_private_key 编码），任何直接读它去签名/建会话的路径都必须先 `_decode_private_key` 还原换行，否则 `SigningKey.from_pem` 报 `Empty string does not encode a sequence`。
- 风控/验证码处理铁律：
  - 检测到风控页（verify.zijieapi.com / captcha / 滑块 / 安全验证 / 人机验证 等关键字）：**绝不关闭浏览器、绝不立即 raise**，改为 warning 提示用户手动处理后继续轮询；超时仍处于风控页才 raise 并提示。
  - 抓取到的凭证被污染（s_v_web_id=verify_ 占位 / sid_ucp_v1=verify_ 前缀）：绝不写入 .env（RiskControlError 透传，前端提示"请在指纹浏览器中手动处理验证码"）。
  - ttwid/msToken 缺失单独不判污染（页面加载时序问题）；ttwid 缺失仍判强污染（登录态不完整）。

## 三、私信落地页（landing_url）
- 统一用 `https://www.douyin.com/chat?isPopup=1` 作为私信凭证落地页（新增账号重扫、auto_recapture 自动重捕均走此页）。
- 跳转时序：**先停在抖音首页等用户扫码登录，检测到真实登录态(sessionid/sid_tt)后才主动 goto chat?isPopup=1** 让 security-sdk 把 web_protect 从空壳升级为有效值。未登录前绝不开私信页（否则用户看不到登录窗口）。
- 查看模式（open_douyin_home）用持久化 profile 打开抖音首页，不扫码不跳私信页。

## 四、账号凭证校验（accounts.py）
- `credentials_complete(env_path)` → (bool, reason)：齐全 = .env 存在 + cookie(非 verify_ 占位) + 四件套 + wp(DY_WEB_PROTECT/DY_KEYS) 均齐全。守护启动前置校验，不全则 sys.exit(2)。
- `verify_account(name, timeout, dm_loopback)`：wp 引擎查凭证本身（不监测守护是否启动）；dm 引擎 dm_loopback=True 时拉取私信会话列表（get_conversation_list，无副作用）验证凭证有效，False 时沿用 wp 结果近似显示（不恒显"待校验"误导）。
- 自动重捕（auto_recapture）：仅当凭证失效（三件套缺失/INVALID_REQUEST/KICK 不触发）且 dm_loopback=True（用户点校验/启动自检）时，停该账号守护释放 profile 锁 → enrich_auth(force=True, landing_url=chat?isPopup=1) 重捕写回 .env；5 分钟节流（同账号只弹一次）。

## 五、单 profile 铁律（已固化）
- 每账号单一固定 profile，守护/查看/重扫复用，按优先级抢占（重扫 > 查看 > 守护保活）。
- `vbrowser.launch_async(force=True)` 用 `tempfile.mkdtemp(prefix="vb_force_rescan_")` 临时 profile，**绝不** `_wipe_user_data_dir` 清空持久化 profile（清空会与已打开的查看模式浏览器抢锁 + 丢登录态）。
- 双击指纹浏览器（查看模式）走 `open_douyin_home`（force=False 持久化 profile）；真正重扫/自动重捕走临时 profile。

## 六、孤儿 profile 锁 → 双击查看浏览器报错（2026-09-03 实机定位修复）

### 现象
双击账号卡片「打开指纹浏览器」立即报错：
`打开指纹浏览器失败: : Target page, context or browser has been closed`
日志里新 chrome `<launched> pid=xxx` 后 1 秒内 `exitCode=21`。
连点几次都一样（19:09~19:16 日志复现）。

### 根因（不是代码主链路 bug，是孤儿锁）
`api/accounts.py::_quit_browser_daemon` 旧逻辑**只探测端口**：
端口死（`_port_open` False）→ 直接返回 False 跳过清理 → 弹查看浏览器。
但存在一种致命情况：**browser_daemon 进程已死（端口释放），其 chromium 子进程族
仍持有 profile**（前一次 app 实例被杀 / daemon 异常退出，子进程没被回收）。
此时弹新 Chromium → SingletonLock 冲突 → exitCode=21。

实机证据（wmic/powershell 查命令行）：
- 孤儿 browser-daemon pid=16700（父进程 408 已死，19:06 启动）→ 子 chrome 族 7 个进程
  （428/1660/5544/7632/7940/16116/20836）全指向 `accounts/四川工伤张老师/profile`
- 端口 10074 无 LISTEN → `_quit_browser_daemon` 判定"未运行"跳过 → 锁一直在

### 修复（api/accounts.py，backend 0.33.2 已重打包部署）
`_quit_browser_daemon` 加固为**双段释放**：
1. 端口活着 → 照常发 `/quit` + sleep 1.5s（旧逻辑）
2. **端口已死 → 新增 `_kill_profile_holders(profile)`**：PowerShell 枚举所有 chrome.exe
   命令行，按 `--user-data-dir=<该账号profile>` 精确匹配，`taskkill /F /T` 按树清理
   → 释放孤儿锁，再让查看浏览器正常启动

关键实现细节：
- **编码坑**：PowerShell 输出是 GBK（中文系统默认 OEM 代码页），`subprocess text=True`
  按 UTF-8 解码会在中文 profile 路径处崩 `UnicodeDecodeError` → 必须 `raw.decode("gbk")`
  兜底 `utf-8`（实测先踩坑，修前 0 命中）
- 匹配只杀指向**该固定 profile** 的 chrome，绝不误伤其他账号/其他浏览实例
  （norm 化路径后 `--user-data-dir=` 精确包含匹配）

### 实机验证（隔离路径复现完整闭环）
1. 强杀 browser-daemon 两段进程（PyInstaller parent+child）→ 端口 10074 死
2. 手动 spawn 一个持 profile 的 chrome（模拟孤儿锁）
3. 调 `/open-browser` → 日志：
   `[open-browser] 账号 四川工伤张老师 发现并清理 6 个持有 profile 的孤儿浏览器进程（端口 10074 已死但锁未释放）`
4. 新查看浏览器正常打开（抖音页窗口出现）→ **修复前必崩，修复后秒开**

### 相关排查笔记
- PyInstaller onefile 是 **parent+child 双进程**（如 13064+10736），taskkill 主进程后
  child 仍持端口 → 强杀孤儿时两段都要杀
- 查看浏览器打开期间 BCC 是停的（`/quit`），关浏览器后需在前端重拉守护
  （`ensure_daemons_for` 幂等，校验/刷新时自动拉起）

## 七、账号级代理支持 DY_PROXY（2026-09-06 借鉴 OpenBrowser 落地，已实机验证）

借鉴 github.com/lyu0805/OpenBrowser 的 per-env proxy + egress check 设计，为 vb_chromium
链路补上每账号独立代理能力。**未配置 DY_PROXY 时行为与旧版完全一致（零变化回归已验证）**。

### 配置方式
在账号 `.env`（`auto_dm/accounts/<name>/.env`）加一行：
```
DY_PROXY=http://user:pass@host:port    # HTTP 代理+认证
DY_PROXY=socks5://host:port            # SOCKS5（Chromium 不支持 socks5 认证）
```
支持全局兜底：config 的 `DY_PROXY` 属性（account 未传时生效）。

### 实现要点（vbrowser.py）
- `parse_proxy_env(env_path)`：只读 .env 的 DY_PROXY 单行（绝不解析其他凭证字段），
  格式非法返回 err，调用方 warning 后**按无代理继续（不阻断启动）**。
- 注入走 **Playwright `launch_persistent_context(proxy=...)` 参数**（自动处理 407 认证弹窗），
  不用裸 `--proxy-server`；另加 WebRTC 防泄漏两参数：
  `--enforce-webrtc-ip-handling-policy` + `--force-webrtc-ip-handling-policy=default_public_interface_only`
  （防 STUN 经本机网卡暴露真实 IP）。
- 三个启动口全部透传 `account=` 参数：`launch_async` / `launch_sync` / `open_douyin_home`；
  调用方已接：BCC `_launch`（browser_daemon.py）、login_grab_ticket、read_auth_from_profile、
  refresh_cookie_from_profile（login_api.py）、api/accounts.py open-browser。
  **dyGenerateInitData 未接**（仅被已注释的 demo qrcodeMain/phoneMain 引用，死代码）。
  **bulk_user_info_via_browser 不接**（昵称红线死代码）。
- `check_egress_ip(context, proxy_url)`：在浏览器 context 开临时页访问 api.ipify.org /
  httpbin.org/ip 校验出口 IP；代理 hostname 是 IP 时精确比对，域名型只记录不比对。
  仅记日志**绝不阻断启动**。当前未自动挂进启动链路（避免每次启动多 1 次外网请求触发风控），
  供后续需要时调用。
- 日志脱敏：`_mask_proxy` 隐藏 user:pass。
- 新接口 `GET /api/accounts/{name}/proxy-status`：返回 {configured, masked, error}，
  纯读 .env 单行零网络请求，前端可随列表轮询。

### 实机验证（全部通过）
1. 单元级 14/14：各格式解析（http/socks5/带认证/非法格式报错/空值/无 .env）、
   pw_proxy 参数生成、WebRTC 参数、脱敏、stub 重导出、**无代理时 args 与旧版逐项相等**。
2. 实机（scratch 临时 profile，非账号 profile）：
   - 假代理 127.0.0.1:59999（无监听）→ `page.goto` 报 `net::ERR_PROXY_CONNECTION_FAILED`
     = 流量确实被强制路由进代理（若代理参数没生效会直连成功）；
   - PowerShell CIM 查 chrome.exe 真实命令行：`--proxy-server` / 两项 WebRTC 策略参数
     全部在列。
3. 重打包部署：backend + browser-daemon 两 sidecar，md5 双端一致
   （6df08fb2... / 4ee20e11...）。

### 注意事项
- **代理出口与登录环境一致性**：给账号加/换代理前，建议先停守护→配置→重扫码（force），
  避免"中国 IP 登录、海外 IP 使用"式环境跳变触发风控；同账号所有浏览器入口
  （守护/查看/重扫/扫码）现已统一走同一代理，不会出现同账号双出口。
- `check_egress_ip` 若要启用，建议挂在账号校验（verify_account）路径而非每次启动。

## 【2026-09-12 根治】凭证更新两套路径共存 + 签名必须随 cookie 一起刷新

### 用户需求原话
> 「你只优化了指纹浏览器和 BCC 的 profile 问题，没有优化**凭证校验**和**指纹浏览器（观测态）
> 更新凭证的写入方式**，我需要让二者兼容，**根据客户自己的用户习惯来选择**校验弹窗激活
> 更新还是观测态更新」

### 真正的核心缺陷（1）：观测态写回只更新 cookie，**签名始终是旧的**
`browser_daemon.refresh_cookie_to_env()` 旧实现：
```python
auth = DYLoginApi._load_auth_from_env(env_path)   # ← ticket/ts_sign/web_protect 来自 .env 旧值
cks  = await self.get_cookies()
auth.cookie = cks                                  # ← 只有 cookie 被覆盖
DYLoginApi().save_credential(auth, env_path)       # ← 写回「新 cookie + 旧签名」
```
抖音私信走 `imapi.douyin.com` 私有网关，靠 **protobuf 体内的 ticket/ts_sign/sdk_cert
（由 security-sdk 的 web_protect/keys 派生）** 鉴权，**与 cookie 是两套独立时效**。
→ 结果：cookie 有效但签名过期 → `cmd=609 INVALID_REQUEST`，
极易被误判成「账号被风控」或「凭证已失效」（本次实测张老师即此症）。

**实测铁证（同一时刻对比）**：
| 来源 | ticket | web_protect | keys |
|---|---|---|---|
| `.env`（旧） | `hash.FqCT3w8qCTXy...` | **无** | **无** |
| 页面 localStorage（新） | `hash.COFqk+VN4GKN2i56...` |417 字符 |495 字符 |

**修复**：`refresh_cookie_to_env` 写盘前新增 `_read_page_sign()` ——
从当前页面读 `localStorage["security-sdk/s_sdk_crypt_sdk"]` 与
`.../s_sdk_sign_data_key/web_protect`，成功则 `auth.perepare_auth("", wp, keys)`
**重新派生 ticket/ts_sign/ree_public_key**，再连同 cookie 一起写回；
读不到则沿用既有签名（不写残缺凭证、不阻塞）。

**验收**：注入页面新签名后 `create_conversation` 由 `INVALID_REQUEST` → **OK**
（剩余 `KICK` 是账号级风控限流，与签名无关，属另一个体系）。

### 真正的核心缺陷（2）：两条更新路径无法共存、用户不能选
原实现只有「弹窗激活（scan_login）」一条自动路径，观测态静默回写则是**无条件**
定时执行（`DY_BCC_COOKIE_SYNC_SEC`，默认 1800s），用户无法按自己习惯取舍。

**修复：新增统一配置项 `general.cred_refresh_mode`**（设置页可改，`apply=restart_daemon`）
| 取值 | 行为 | 适用 |
|---|---|---|
| `observe`（默认） | 保活心跳静默读实时 cookie+页面签名写回 .env；**页面需重激活时只告警、绝不弹窗/重启浏览器** | 无人值守 |
| `popup` | **跳过静默回写**；检测到需重激活时弹指纹浏览器请用户点一下 | 习惯人工确认 |
| `both` | 观测优先；确认页面登录态失效才弹窗（原行为） | 兼容旧习惯 |

- 实现：`browser_daemon._cred_refresh_mode()` 读 `app_config` → 环境变量
  `DY_CRED_REFRESH_MODE` → 默认 `observe`；`run_keepalive` 内按该值分支。
- 配置项 `options` 用**对象数组** `{value,label}`（前端 `UnifiedConfigSection.tsx`
  已同时兼容字符串数组与对象数组，对象数组能显示中文标签）。

### 坑
- 前端 schema 的 `options` 曾因「字符串数组 vs 对象数组」渲染出 `undefined`
  （见 04 §前端联调）；现已双向兼容，新字段直接用对象数组即可。
- `_read_page_sign()` 必须走 `self._exec()`（浏览器串行铁律），
  轻滚动 + 重试 4 次 ×1.5s（SDK 异步生成，首读可能为空）。


## 【2026-09-13 架构定义】环境门阀 —— 由「代理配置显式选择」单方面决定

### 用户原话（两次澄清，第二次为最终定义）
> 第一次：「正确环境就是根据代理配置当中的设定……环境的定义门阀是由代理配置来
> 决定的，而不是项目以外的本机环境」
> 第二次（纠正）：「代理配置当中选择独立节点，然后有填写独立节点的信息，就走独
> 立节点，代理配置当中有选择系统代理才走系统代理，以及代理配置选择不走代理，则
> 直接走本机 IP（豁免代理软件的端口），一切和本机环境没有任何关系」
> 「准确地来说，判断条件和本机环境没有关系」

### 语义（三态，模式由配置显式决定）
| 代理配置中的选择 | 行为 |
|---|---|
| 选「独立节点」且填了节点信息 | 走该独立节点（DY_PROXY） |
| 选「系统代理」 | 走系统代理（跟随本机系统代理设置） |
| 选「不走代理」 | 走本机 IP，**豁免代理软件端口**（--no-proxy-server） |

### 铁律
1. **模式只能来自配置，代码绝不自行探测/推断**（不许读注册表判断"系统代理是否
   开着"来选模式——那是把决定权交给本机环境）。
2. **项目与浏览器恒同一套环境**：同一账号在守护/扫码/查看/采集/解析各入口，
   出口 IP 必须一致，杜绝中途跳变。
3. 缺省（未配置任何模式）→ 按 `direct`（走本机 IP，最保守）。
4. 兼容旧数据：仅有 `DY_PROXY` 无 `DY_PROXY_MODE` → 按 `node`。
5. 选了 system 但本机未开系统代理 → 告警 BCC-038 并**如实走直连**（不静默改语义）。

### 存储
账号 .env 两字段：`DY_PROXY_MODE` ∈ {node,system,direct}、`DY_PROXY`=节点 URL。

### 实现
- `vbrowser.parse_proxy_config(env_path)` → (mode, node_url, err)
- `vbrowser._launch_args_with_proxy(cfg, account)` 严格按 mode 落地（三态实测通过）
- `api/accounts.py` save_proxy 三态写入（direct/system 清节点）、proxy-status 回传 mode
- 前端代理抽屉：SOCKS5/HTTP/HTTPS（独立节点）+ 系统代理 + 不走代理

### 为什么必须这样（本次事故根因）
| 谁打开浏览器 | 走哪条 | 出口 IP（实测） |
|---|---|---|
| 用户手动双击指纹浏览器 | 跟随系统代理 | 107.175.219.48（美国 Santa Clara） |
| BCC 守护（09-12 起被强制直连） | --no-proxy-server | 171.218.232.73（成都 CN） |

同账号同 profile，**出口在美/中之间跳** → 抖音判异地登录 → 弹「安全风险阻止
访问」+ **强制下线登录态** → UID 漂移（AUTH-050）→ 凭证失效 →
发送 INVALID_REQUEST(cmd609) + WS token 失效停推送 → 收不到消息/AI 不触发。

时间线：08-31~09-10 浏览器跟随系统代理（与手动打开同环境，账号正常）→
**09-12 提交"账号未配 DY_PROXY 强制直连"**（出发点是防误走国外节点，但当时账号

### 一、内核能力澄清（重要，避免误判"内核不行"）

   请求 + 反复 scan_login → 每次都被 passport 拦下 → 弹窗反复出现。

## 【2026-09-13 深挖】scan_login「假成功」—— 熔断永不触发的真正原因

### 发现的更深 bug
`browser_daemon.scan_login()` 的成败判据原来是：
```python
ok = bool(auth and getattr(auth, "cookie", None))
```
**只要 `.env` 里存在 cookie 就报「刷新成功」**，完全不验证凭证是否真的有效。

**致命后果**：
| 环节 | 表现 |
|---|---|
| ① | 凭证失效时仍返回 `ok=True` → 上游 `scan_fail_count` **永不累加** |
| ② | `SCAN_BREAKER_LIMIT` / `BCC-024` 熔断**永不触发**（v0.42.8 接上了"电线"，但此处假成功让"电流"永远为零） |
| ③ | 每轮探活都判"需要刷新" → 疯狂 `scan_login` → 抢占同一 profile |
| ④ | 容器 context 失活 → `BCC-006` 重启 → 又探活失败 → **无限循环**（155 次/日） |

### 修复（v0.43.0）
- `scan_login` 改用**真判据**：必须【探活通过 + 与历史会话一致】
  （`uid_probe.get_uid(force=True)` + `_uid_consistent_with_history`）才 `ok=True`；
  否则记 `BCC-036`「刷新后凭证仍未通过校验」，判定仍需人工扫码。
- 三个自动调用点（uid漂移 / 页面重激活 / 探活失败）统一改为
  **读 `scan_login` 返回的 `ok` 字段**决定 `scan_fail_count` 增减，
  不再是"调用没抛异常就算成功"。
- 调用点1（uid漂移）原先**完全没有熔断**，一并补上 `BCC-024`。

### 铁律（重要，通用）
1. **"没抛异常" ≠ "成功"**。失败计数/熔断/重试这类保护逻辑，
   必须由**业务判据**驱动（此处=凭证真的有效），不能由"函数返回了"驱动。
   否则保护逻辑会被"假成功"架空，形同虚设。
2. **审计保护逻辑时，要同时检查三处**：
   ① 是否真的接上触发点（v0.42.8 修的）
   ② 成败判据是否真的能判出失败（v0.43.0 修的）
   ③ 计数/阈值/退避是否真的会被消费
   缺任何一处，整套熔断都等于不存在。
3. **同一个 bug 会有多个层次**：先发现"熔断没接线"，再发现"接线了但电流恒为零"。
   修完一层要**再验一层**，不要看到"代码看起来对了"就收工。

## 【2026-09-13 v0.43.2】浏览器统一入口（单例门禁）+ 部署防假版本

### 用户的两次灵魂拷问（都指中了真问题）
> 「浏览器守护不能通过调度器统一管理吗，必须手动处理？」
> 「所有启动路径统一走同一入口（杜绝环境分叉）」
> 「你在构建的版本号和部署的版本号是同一个版本吗？会不会出现调用版本号不一致的问题？
>   还是说你版本号这个地方没有进行配置化处理？」

### ① 更新会话会「另起浏览器」—— 实锤 + 根治
**证据（19:44-19:46 日志）**：
```
19:44:50 [auth] 账号专属指纹 profile: ...members\...\尚进工伤小助理\profile
19:44:50 [vbrowser] 强制重扫模式：复用固定 profile（不新建临时目录、不清空）
19:46:41 [bcc] 尚进工伤小助理 profile 锁 10s 未释放   ← 两个所有者抢同一 profile
```
**根因**：`conversation_capture.capture_all` 里有后门
```python
if with_browser:
    DYLoginApi.refresh_cookie_from_profile(auth, env_path, allow_launch=True)
    # allow_launch=True = 「BCC 不在线时允许兜底直开浏览器」→ 绕过调度器
```
项目**本就有调度器**（`daemon_launcher.ensure_daemons_for` → `accounts.ensure_bcc`），
是这条后门绕过了它。

**根治：新增 `backend/services/browser_gate.py` 作为唯一决策点**
- `ensure_browser(account, purpose)`：
  - `AUTO`（更新会话/凭证刷新/采集）：复用 BCC；离线则**先拉起 BCC 再复用**；
    拿不到就**显式失败 + 可操作提示**，**绝不新开独立实例**。
  - `EXCLUSIVE`（扫码/重扫/读 profile 凭证）：要求 BCC 让出 profile，
    但仍是**同一个 BCC 进程**持有目录，不新开。
- `refresh_cookie_via_owner()`：自动路径**只走 BCC /cookie**，`allow_launch` 恒 False。
- `audit_standalone_launch()`：直开审计。判定「环境分叉」需同时满足
  ① 该账号 BCC 在跑 ② BCC 未独占让出 ③ 非 BCC 自身 ④ 未显式豁免 → 打 `BCC-042`。
- `_is_bcc_owner()`：`DY_BROWSER_DAEMON=1`（BCC 入口设置）或 argv 含 browser_daemon
  时豁免，防止 BCC 启动自己的容器时「自己告警自己」。
- 审计插在 **`vbrowser.launch_async` / `launch_sync` 最底层**——一处覆盖全部
  **12 个**调用点（login_api 8 / link_resolve / web_probe / api.accounts / browser_daemon），
  比逐处补更彻底（这也印证：收敛点要选在**最底层出口**，不是每个调用方）。

### ② 假版本 —— 确实存在，已机械根治
**事实核查**：
```
主程序 exe 的 Windows 资源版本 = 0.43.0（19:34 构建）
部署文件名 = DYAutoDM_v2_0.43.1.exe（版本号 19:51 才改成 0.43.1）
→ exe 内嵌前端 bundle 与版本号都在【构建期固化】，改版本号不重建 ⇒ 名字与内容不符
```
**根治：新增 `scripts/deploy.py`，把「版本一致」变成部署关口的机械校验**
1. 期望版本 = `src-tauri/tauri.conf.json`（唯一真源）。
2. **主程序 exe 的 Windows 资源版本**（`(Get-Item).VersionInfo.FileVersion`）
   必须 == 期望版本，否则**拒绝部署**并提示执行完整重建。
   （实测成功拦下 `0.43.0 vs 0.43.1` 那次假版本 —— 这就是它的价值证明。）
3. 部署文件名**一律取产物真实版本**，不用人工口述版本。
4. sidecar 的编译期版本常量 `_build_version.py` 必须 == 期望版本。
5. 三份 sidecar 构建产物与部署产物 **md5 逐一致**，否则告警。
6. 部署后打印 `curl /api/version` 验收命令。

**关键洞察**：主程序 exe 的 **Windows 资源版本是真实可读的**（Tauri 会写
FileVersion/ProductVersion），而 **PyInstaller sidecar 没有资源版本**——所以
sidecar 的版本必须靠**编译期常量**（`_build_version.py`）自述。两者结合才能
全链路验版本。

### 铁律（新增，通用）
1. **部署文件名必须来自产物自述版本，不能来自人的记忆或期望**——
   「我以为构建的是 X」是假版本的唯一来源。能用机器读的版本，绝不用人填。
2. **收敛绕行路径，要选在最底层出口加审计**，而不是在 N 个调用方逐个补——

4. **审计先行、阻断后置**：新增门禁先以 ERROR 日志观测（`BCC-042`），

进一步实测后确认：真正的风险不是「没用满参数」，而是
**两层指纹来自两个互不同源的随机源**。

### 实测证据（生产形态 headless=False + 项目实际 _CHROME_ARGS，一次性临时 profile）

| 维度 | HTTP 层 `utils/fingerprint.py` | 浏览器层（内核实测） | 判定 |
|---|---|---|---|
| 浏览器版本 | **Chrome/150.0.0.0** | **Chrome/148.0.0.0** | 🔴 矛盾 |
| `sec-ch-ua` | `"Google Chrome";v="150"` | 内核 UA 无品牌标记 | 🔴 与 UA 不自洽 |
| CPU 核心数 | `12`（写死） | **24**（本机真值） | 🔴 矛盾 |
| 设备内存 | `8`（写死） | `undefined`（未伪装） | 🟡 缺失 |
| 屏幕尺寸 | 5 个预设随机选 | **1280x720**（恒定） | 🔴 两套独立随机 |
| WebGL GPU | 4 个预设随机选 | 随种子变化（**不是**那 4 个） | 🔴 两套独立随机 |
| 时区 | 未设置 | `Asia/Shanghai`（恒定） | 🟡 海外节点时与 IP 地区矛盾 |

运行期 `navigator.userAgent` = `Chrome/148.0.0.0`；
而 `fingerprint.py:36,37,40,42` **硬编码 150**。

### 影响面（确认真的发出去）

- `builder/params.py:20-32` 把 `screen_width/screen_height/cpu_core_num/
  device_memory/browser_version/engine_version` 作为**查询参数**发给抖音；
- `builder/header.py:50-53` 把 `ua / sec_ch_ua / sec_ch_ua_platform` 作为**请求头**发出。

即：**同一账号对抖音呈现「HTTP 说 Chrome150 + 12 核，浏览器说 Chrome148 + 24 核」。**
同源对照是现成的风控特征。

### 由实测得出的判定边界（避免再次误判）

1. **内核对抖音的伪装是有效的，未暴露真实硬件**。换种子实测：
   `seed=111 → cores=22`、`seed=999999 → cores=8`、`seed=42424242 → cores=14`
   —— **cores 随种子变化 = 伪装生效**。
   （对照：**不加** `--fingerprint` 时 renderer 显示 `AMD Radeon(TM) Graphics`、
   cores=12，**那才是真机值**。）
   ⚠️ 我中途曾误判为「暴露真实显卡」，靠换种子对照实验纠正 ——
   **判定伪装是否生效，必须做「有无种子」的对照实验，不能只看单次值。**

2. **`--fingerprint-gpu-vendor` / `--fingerprint-gpu-renderer` 在本内核(148)已不可用**
   —— 官方文档明确：Chrome **144 已移除**，替代品是 `--disable-spoofing=gpu`。
   加这两个参数**会静默忽略**（不报错），不要以为设了就在起效。

3. **本内核(148)可用且未接线的参数**（官方 README-ZH 核实）：
   `--fingerprint-platform` / `--fingerprint-platform-version` /
   `--fingerprint-brand` / `--fingerprint-brand-version` /
   `--fingerprint-hardware-concurrency` / `--timezone` / `--lang` / `--accept-lang`

4. **`navigator.userAgentData` 实测为 `null`** —— 该内核未伪装 Client Hints，
   与 `fingerprint.py` 声明的 `sec_ch_ua` 又构成一处不自洽。

### 待办（未修，先记录）

方向应为**单源化**：让浏览器层与 HTTP 层读**同一份账号级档案**，
而不是各自随机。落点候选：`utils/fingerprint.py` 的 `get_profile()` 改为
按账号派生（种子可用现有 `vbrowser.fingerprint_seed_of(account)`），

**修前须先评估**：改 `fingerprint.py` 会影响 `builder/header.py`、`builder/params.py`、
`builder/proto.py`、`mstoken.py` 等全部出站请求 —— 属架构级改动，须整体设计。

### 屏幕尺寸的正确控制点

**`screen` 由 Playwright 的 `viewport` 决定，内核的 `--window-size` 会被它覆盖**：

| 实验 | screen 结果 |
|---|---|
| 默认（不设 viewport） | `1280x720`（Playwright 默认） |
| `--window-size=1920,1080` | `1280x720` ← **被覆盖，无效** |
| `viewport={1440,900}` | `1440x900` ✅ |
| `viewport=None` + `--window-size` | `1280x720` ← 仍无效 |

⚠️ 未设 viewport 时 `screen == availWidth == innerWidth` 全等于 1280x720 ——
真实屏幕不可能三者相等，属明显自动化特征。**故必须显式设 viewport。**


- `_launch_args_with_proxy`：并入 `launch_args(account)`（失败降级为仅种子指纹 + 告警）

## 【2026-09-20 v0.43.99】弹窗真因定位：出口 IP 分叉的代码落点

早期 §363-384 已记载「弹窗真因 = 出口 IP 分叉」，本次找到了**代码落点**：

`vbrowser._env_path_of_account()` 为避免循环导入自行硬拼
`<root>/auto_dm/accounts/<name>/.env`，而会员体系真实路径是
`<root>/members/<member_id>/auto_dm/accounts/<name>/.env` ⇒ **恒返回 None**。

后果链：
  env_path=None → parse_proxy_config 读不到 DY_PROXY_MODE → mode 落缺省 direct
  → 浏览器强制 `--no-proxy-server`（国内直连 IP）
  → 用户用 Edge 时跟随系统代理（实测出口 23.191.200.205 境外）
  → 同账号境外↔境内跳变 = 异地登录 → 弹「安全风险…已阻止此次访问」。

修复：改为优先委托 `accounts.env_path_of`（唯一真源），延后导入避免循环。
验证：浏览器页面内 fetch https://api.ipify.org 实测出口 = 23.191.200.205，
      与代理出口、Edge 出口三者一致，分叉消除。

**排查规则（重要，本次教训）**：出现「某浏览器被拦而本机常规浏览器正常」时，
**第一步应比对两者出口 IP**，不要先查注入/指纹/profile。本次曾误判四轮，
而 `risk_level=no_risk` 与「Edge 没事」两个信号早已指向浏览器之外。


## 【2026-09-20 v0.44.0】指纹浏览器内核可切换：Chromium / Camoufox

**触发**：抖音在**交互时刻**（扫码授权、输手机号）弹「安全风险…已阻止此次访问」，

|---|---|---|---|

1. 此前所有对照都用 `tempfile.mkdtemp()` = **全新环境**，而全新环境本身就是

   样本=1 的观察不得作为定论依据。

WP 私信的 JS 劫持 WebSocket 失效（须改 Playwright 原生事件）；昵称 IndexedDB
结构在 Firefox 下未验证；出口 IP 的机房属性仍是隐患。
