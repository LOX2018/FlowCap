# DYAutoDM_v2 开发与构建流程（2026-09-20 建立 · 最高优先级）

> **本文解决一个持续两个月的问题**：项目一直把"全量打包 ~12 分钟"当作唯一开发方式，
> 导致每次改一行代码都要等 5~15 分钟，**严重损失 debug 时效**（用户原话：
> 「这个项目我已经持续跟进2个月了，这两个月的时间居然一直没有提示我正确的debug方式」）。
>
> 根因：知识库只记录了「打包与部署」，**缺失「日常开发调试」这一环**。

---

## 一、三种工作模式（按场景选，别默认全量打包）

| 场景 | 命令 | 耗时 | 说明 |
|---|---|---|---|
| **① 改前端 / 联调 UI** | `cd DYAutoDM_v2 && npx tauri dev` | **秒级 HMR** | Rust 只编一次；改 `.tsx/.ts/css` 存盘即生效 |
| **② 只改 Python 后端** | `npm run backend:dev`（= `uvicorn main:app --reload --port 8000`） | **存盘即重载** | 不启动桌面壳；配 `npm run dev` 用浏览器调前端 |
| **③ 打包验证 / 交付** | `python scripts/build_all.py` | ~5 分钟 | **默认 debug 版**；并行 sidecar + Rust dev profile |

### 判据：什么时候**必须**走 ③

以下三类问题**只在打包态暴露**，`tauri dev` 测不出，发版前必须走 ③：

- 新增第三方依赖的**原生扩展**（`.pyd`）、**数据文件**（`.zip/.json`）、**node driver**
- `hidden-import` / `--collect-all` 相关的 `ModuleNotFoundError`
- sidecar 与主程序的**版本齐平**、`_internal` 布局

> 实测教训（2026-09-20）：Camoufox 接入时连续踩 6 个「源码态全绿、打包态必挂」的缺陷
> （orjson.pyd / apify data / language_tags / camoufox 预设 / playwright driver / `_internal` 陈旧），
> **全部靠 ③ 才发现**。所以 ③ 不能省，但**只在关键节点做**。

## 二、`tauri dev` 的唯一坑：sidecar 找不到 `_internal`（必须建 junction）

### 症状
```
[backend] [PYI-13188:ERROR] Failed to load Python DLL
  '...\src-tauri\target\debug\_internal\python314.dll'
后端 sidecar 已退出
```
前端正常（vite 200）、窗口也起来，但**后端挂掉** → 整个应用无数据。

### 根因
`tauri dev` 的 `current_exe()` 是 `src-tauri/target/debug/dyautodm-v2.exe`，
Tauri 的 externalBin 只把 **sidecar exe** 复制到 `target/debug/`，
**不带 `_internal/`**（onedir 形态的依赖目录）→ Python DLL 加载失败。

### 修复（一次性，之后长期有效）
```bash
# 在 shell 里执行（PowerShell）
$t = 'C:\Users\LOX\Desktop\DYchajian\DYAutoDM_v2\src-tauri\target\debug'
$l = Join-Path $t 'binaries'
$s = 'C:\Users\LOX\Desktop\DYchajian\DYAutoDM_v2\src-tauri\binaries'
if (-not (Test-Path $t)) { New-Item -ItemType Directory -Path $t -Force | Out-Null }
if (Test-Path $l) { Remove-Item $l -Force -Recurse -ErrorAction SilentlyContinue }
New-Item -ItemType Junction -Path $l -Target $s | Out-Null
```
即：让 `target/debug/binaries` 成为 `src-tauri/binaries` 的 **junction**，
这样 `resolve_sidecar` 的候选 3/4（`binaries/<full>/`、`binaries/<full>.exe`）命中，
且 `_internal` 随 junction 可达。

> 注：MSYS 的 `ls` 读不到 junction 内容，验证要用
> `powershell -Command "Test-Path <路径>"` 或 `cmd /c dir /AL`。

### 验证就绪
```bash
curl -s http://127.0.0.1:8000/api/version     # 期望 {"backend":"0.44.x",...}
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:1420/   # 期望 200
```

## 三、构建类型铁律：**默认 debug，除非显式 --release**

（2026-09-20 用户明确，选 A 方案）

| 项 | 规则 |
|---|---|
| **默认** | `build_sidecar.py` 不带参数 = **debug 版**；`build_all.py` 默认 `--debug` |
| **正式版** | 必须显式 `--release`（sidecar）/ 不给 `--debug`（tauri） |
| **醒目横幅** | 构建开始打印 `构建类型：DEBUG 测试版（非正式发布）`，无法忽略 |
| **产物名** | debug → `DYAutoDM_v2_<ver>-debug.exe`；release → `DYAutoDM_v2_<ver>.exe` |
| **清理** | 只清理**同类型**旧版（debug 不删 release，反之亦然） |
| **`_build_version.py`** | 同时写 `BUILD_KIND = "debug"/"release"`，供 deploy 识别 |

**测试阶段永远不需要正式版** —— 把默认值本身变成铁律，而不是靠人记得加参数。

## 四、为什么 tauri（体积最小）反而最慢 —— 及对策

实测：sidecar 385MB 约 4.6 分钟（并行），tauri 产物仅 5MB 却要 **7 分钟**。

根因在 `src-tauri/Cargo.toml` 的 release profile（为**产物体积**服务）：

| 配置 | 影响 |
|---|---|
| `codegen-units = 1` | 代码生成**无法并行**（实测 12 核只跑 1 个 rustc） |
| `lto = true` | 链接时把**全部依赖 crate** 拉平重优化（实测卡在这一步 10+ 分钟） |
| `opt-level = "s"` | 面向体积的完整优化流程 |

**即：「产物最小」正是「编译最慢」的原因，同一枚硬币的两面。**

### 对策
- 测试期用 **`tauri build --debug`**（dev profile：`unoptimized + debuginfo`）：
  首次全量 4m36s，改代码后**增量编译 ~1m22s**（对比 release 每次 ~7 分钟）。
- **正式发布仍走 release**（`[profile.release]` 保持原样不降级）。
- `deploy.py` 自动探测 `target/debug|release/dyautodm-v2.exe`，取**较新**者，避免拿错。

## 七、免打包启动的两个入口 + 环境注入铁律（2026-09-20 补，实测）

> 背景：`start_dev.ps1` 早在 2026-09-17 就存在，但**全文没有提到 `DY_APP_ROOT`**，
> 且它把后端的 WorkingDirectory 设为**源码根** → 运行时数据（data/ accounts/ logs/）
> 全部落进源码仓库，违反「分支隔离 / 源码目录不得有 profile 与 db」铁律。
> 本节把入口、环境注入、日志落点与「免打包到底免了什么」一次写清。

### 7.1 两个入口（互补，按需选）

| 入口 | 命令 | 含桌面壳？ | Rust 编译 | 适用 |
|---|---|---|---|---|
| **全栈** | `.\dev.ps1`（= `npx tauri dev` + 环境注入） | 是 | 首次/改 Rust 后 **~84s**（增量） | 需要桌面壳能力（原生对话框 / invoke / write_boot_log）、改了 `src-tauri` |
| **轻量** | `.\start_dev.ps1`（backend sidecar + vite + 浏览器） | 否 | **零** | 改 `frontend/` 或 `backend/` 后联调最快 |

辅助开关：`dev.ps1 -EnvOnly`（只自检不启动）· `dev.ps1 -Stop` / `start_dev.ps1 -Stop`（停止）·
`start_dev.ps1 -DevBackend`（后端走 Python 源码而非 sidecar exe）。

### 7.2 「免打包」免的是什么、不免什么（术语边界，别误解）

- **免掉**：Python sidecar 的 PyInstaller 打包 + 部署（省 4.6~9 min）。
- **免不掉**：**Rust 桌面壳的编译** —— Tauri 的壳是原生 exe，`tauri dev` 的语义是
  「用 dev profile 编译并运行它」，不是「不编译」。
- 但它便宜：dev profile（opt-level=0、多 codegen-units）实测 **首次 84s**；
  对比 release 每次 ~7min（根因见 §四：codegen-units=1 + lto=true）。
- **改前端 .tsx / 后端 .py 不触发 Rust 重编**：起一次 `dev.ps1` 后前端存盘即 HMR；
  后端换 `start_dev.ps1 -DevBackend` / uvicorn --reload。
- 要「彻底零编译」→ 不起桌面壳，用 `start_dev.ps1`（纯浏览器 + sidecar）。

### 7.3 🔴 环境注入铁律：任何免打包启动都必须注入 DY_APP_ROOT + 会员态

**为什么必须**：`vbrowser.app_root()` 在源码态**不设** `DY_APP_ROOT` 时回落到项目根
（DYAutoDM_v2/）⇒ data/dyautodm.db、accounts/（含 profile）、logs/ 全部落进源码树。
实测对照（同一份代码，只差这一个变量）：

| 环境变量 | `vbrowser.app_root()` | DB 落点 |
|---|---|---|
| **不设**（旧 `start_dev.ps1` 的行为） | C:\Users\LOX\Desktop\DYchajian\DYAutoDM_v2 | 源码树 data\dyautodm.db（实测该文件已存在，09-20 14:40 仍在被写） |
| DY_APP_ROOT=C:\temp\dyautodm_design | C:\temp\dyautodm_design | ...\members\m17db0f8209156f26\data\dyautodm.db（会员空间） |

会员态同理：.env.enc 需 DY_MEMBER + DY_MEMBER_KEY（从 <AppRoot>/members/.session.json 读）
才能解密；缺了会报「无 .env（索引未登记？）」并可能引发重启循环。
两个脚本都已在启动前自行读取注入，**不依赖调用方记得 export**。

### 7.4 ⚠️ 日志落点取决于**启动方 CWD**（易静默落进源码树）

`backend/main.py` 的 loguru 用**相对路径** logs/run_{time}.log
（不是 app_root()/logs）⇒ 日志落在**拉起它的进程的 CWD** 下。实测三处：

| 谁拉起 | CWD | 日志落点 |
|---|---|---|
| `tauri dev` | src-tauri/ | src-tauri/logs/（在源码树内） |
| `start_dev.ps1`（**修前**） | DYAutoDM_v2/ | DYAutoDM_v2/logs/（在源码树内） |
| `start_dev.ps1`（**修后**） | C:\temp\dyautodm_design | 设计环境 logs/ ✓ |

两类日志都在 .gitignore 的 logs/ 下（不污染 git），但会造成**日志分裂**：
排查时去看设计环境 logs/ 却发现后端那条链的日志不在这里。修法是**由启动方设 CWD**
（本分支已如此修）——不要把 DY_APP_ROOT 误当成它能管住相对路径日志。

### 7.5 ⚠️ 就绪等待必须 ≥60s（sidecar 冷启动实测 ~18s）

sidecar 启动时 main.py lifespan 会**并行拉起守护**（BCC + 各账号 recv_daemon），
uvicorn 的 create_server（绑定 8000）**在 lifespan 之后** ⇒ 实测
15:58:19 启动 → 15:58:37 startup complete，**约 18s**。
`start_dev.ps1` 原先用 Wait-For-Url ... 15 → 必然假报 [FAIL] 后端启动超时
（而后端其实活着、稍后就会绑上）。已改 60s。

### 7.6 实测验收（本机，2026-09-20）

| 项 | 证据 |
|---|---|
| `dev.ps1 -EnvOnly` 自检 | 6/6 全 OK（junction / cargo / sidecar / 版本一致 0.44.11==0.44.11） |
| `dev.ps1` 全栈启动 | [db] SQLite 已初始化: C:\temp\dyautodm_design\...\dyautodm.db；vite 1420 LISTENING；backend 8000；BCC(11231)+recv×2 |
| 版本门禁 | curl /api/version → {"backend":"0.44.11",...}（与前端一致，未被阻断式遮罩拦） |

| 日志落点 | 源码树 logs/ **零新增**；新日志在设计环境 logs/run_*.log |
| 优雅停止 | -Stop → BCC 走 POST /quit，端口 8000/1420 释放，残留进程 0 |

> ⚠️ 环境陷阱（本机实测）：`.ps1` 用 UTF-8 **无 BOM** 保存时，PowerShell 5.1 会按
> **GBK 解码** → 中文多字节序列吞掉引号/括号 → ParserError: UnexpectedToken。
> **PowerShell 脚本必须存成 UTF-8 with BOM + CRLF**（仓库内 git-commit.ps1 即此口径）。
