> 本文档基于 2026-08-25~27 真机验证（V6~V23 探针脚本 + uid 桥接探针，均跑在隔离测试路径
> `C:\temp\dyautodm_test`，使用「工伤小助理」自有指纹浏览器 profile，可视化/无头均实测）。
> 所有结论均为实机抓包结果，非代码猜测。
>
> **文档主线（2026-08-27 定稿）：昵称/头像的关联靠「数字 UID 精确比对」实现，不靠 sec_uid 串匹配。**
> 首包 protobuf 解出对端数字 `peer_uid`，`im/user/info` 响应返回同一用户数字 `uid`，

## 二、数据分发真实机制（回答"数据在哪"）

```
登录态建立
  → 后端/前端 调 get_message_by_init (cmd 2043)  [首包, protobuf]
      返回 250KB，含：
        - 全部会话 (conv_id + peer_uid)             ← conv_id 形如 0:1:uid:uid，排除自身=peer_uid，100% 可靠
        - 有聊天历史的会话的消息体 (text 明文 JSON)  ← 仅"实际聊过天"的会话
        - 头像 URL（部分）
  → 前端渲染列表（DOM 显示昵称+头像）
  → 前端对可见/滚动到的会话 调 im/user/info (POST)
        响应 {uid(数字), sec_uid, nickname, avatar}  ← 自带数字 uid，与首包 peer_uid 同值
  → 聊天内容：切换会话时【不】现拉，直接从已加载内存 store 取（首包已全量下发）
```

**关键认知：**
- 聊天内容**源头在首包 protobuf**（连接时一次性全量），不是切换会话时拉
- 昵称/头像**源头在 `im/user/info` 响应**（前端自发，自带数字 `uid`）
- conv_id **只在首包 protobuf**（DOM/network/WS 明文均不暴露）
- **关联键 = 数字 UID**：首包 `peer_uid` ↔ `im/user/info.uid`，两端都是精确数字，直接相等比对
- 一切数据抖音前端都自己拿到了，我们**截前端已拿到的响应**即可，不需后端另发请求

## 三、目标架构（对齐用户原话）

> "获取私信列表的机制提前：新增账号且凭证有效时，用无窗口指纹浏览器捕获 → 写库。
> 私信页面直接从数据库读取。后端只针对直播监听产生的发送会话、守护进程收到新消息时
> 解密并新增到数据库。"

### 三层职责
1. **获取列表前移（账号新增+凭证有效 / 校验 / 守护启动）**
   - 无头指纹浏览器打开 `douyin.com/chat?isPopup=1`
   - 截 `im/user/info` 响应（`uid`+昵称+头像）+ 解析首包 protobuf（`conv_id`+`peer_uid`+消息）
   - 按 **数字 `peer_uid ↔ im/user/info.uid`** 关联 → 写 `dm_conversations` + `dm_messages`
   - 一次性、账号级，不在私信页运行时批量查
2. **私信页纯读库**
   - `/conversations` 只从 SQLite 读，不再触发拉取/解密
3. **运行时增量解密（只管两类）**
   - 直播监听产生的发送会话 → 写库（已知对端，可即时取昵称）
   - 守护进程 WS `new_message_notify` → 写库（已带 `sender_nickname`）

## 四、捕获方案（产品化实现）

### 4.1 无头指纹浏览器 + hook 截接口（推荐，零后端请求）
- 复用 `auto_dm.vbrowser.launch_sync(mode, cfg, headless=True, user_data_dir=profile)`
- `page.add_init_script` 注入 hook（必须在 `goto` **之前**注入，否则已加载页面不回放；V16 踩坑）
  - hook `window.fetch` / `XMLHttpRequest`：截 `im/user/info` 响应 → 收集 `{uid, sec_uid, nickname, avatar_small.url_list[0]}`
  - hook `window.WebSocket`：可选，截 WS 帧备用
- 打开 chat 页 → 等列表渲染 + 平滑滚动点完会话 → 收集 `im/user/info` 响应（自带数字 `uid`）
- 同时调 `get_message_by_init` 拿首包字节 → protobuf 解析 → `(conv_id, peer_uid)` + 消息 `text`
- **关联（数字 UID 桥接）**：首包 `(conv_id, peer_uid)` 与 `im/user/info` `(uid ↔ {nickname, avatar})`
  用 `str(peer_uid) == str(uid)` 精确比对，命中即写昵称/头像；首包脆弱 sec_uid 仅作兜底
- 写库 `dm_conversations(conv_id, peer_id, peer_name, avatar)` + `dm_messages(conv_id, role, text, ts)`

### 4.2 风控评估
- **零额外 API 请求**：截的是抖音前端自己发的 `im/user/info`，不是我们后端发
- 无头、单 profile（铁律）、账号级一次性（非运行时高频）
- 等同抖音官方前端自然行为，风控最低
- 对比之前否掉的"后端 BCC 批量按 sec_uid 查"：那是后端主动枚举，触发机器人特征；本方案是截前端已有响应，不新增任何请求

## 七、首包 protobuf 精确结构（V23 已解）

### 7.1 顶层字段
`1,2,3,4,5,6,7,10,11,13`（varint/len 混合），其中：
- **field 6 = conversation 数组**（567 个子对象全部含 `0:1:uid:uid` conv_id，集中在 field 6）
- 每个 conversation 子对象内嵌 conv_id + 子消息列表

### 7.2 消息链接键
- 每条 message 对象**自身内嵌 conv_id**（`0:1:uid:uid` 形态），作为精确链接键
- **不靠邻近匹配**：按 message 内嵌 conv_id 分组即可 100% 精确配对
- V21 用"conv_id 附近 5000 字节找文本"只成功 2 个；V23 用结构化内嵌键 → 13 个全配对

### 7.3 消息体形态
- 消息内容是 **JSON 字符串**，嵌套在 protobuf length-delimited 字段里
- 形如：`GBE{"mention_users":[],"aweType":700,"richTextInfos":[],"text":"你好"}J`
  （前缀 `GBE`/`BF` 是 protobuf tag 残影，JSON 部分可直接 `json.loads` 提取 `text`）
- **无密码学加密**，protobuf 解析 + JSON 提取即可
- 部分会话含 `"stranger_index"` 字段（陌生人/未互关会话，结构略不同，需兼容）

### 7.4 配对覆盖率
- 13/45 会话有消息（其余为空会话，数据本身如此）
- 配对消息总数 120 条（V22 regex 仅 33 条，因嵌套 JSON 深度）

### 7.5 产品化解析要点
1. `parse(init_bytes)` → 顶层 field 6 取 conversation 数组
2. 遍历每个 conversation：提 conv_id（正则 `0:1:\d+:\d+`）+ peer_uid（排除自身 uid）+ 子消息
3. 每条消息：从 protobuf len 字段提 JSON 串 → 剥 protobuf tag 残影 → `json.loads` → 取 `text`/`aweType`/`createdAt`
4. 按 conv_id 写入 `dm_messages(conv_id, role, text, ts)`
5. 关联 `dm_conversations`：用 `peer_uid ↔ im/user/info.uid` 数字比对取昵称/头像

## 八、为何弃用首包 sec_uid 作为关联键（实测论据）

### 8.1 对比方法
- 首包：`parse_init_protobuf` 解析 `init_1.bin`，提取 44 个会话的对端 sec_uid
- im/user/info：BCC 常驻浏览器 early hook 截 `im/user/info` 响应，滚动点完会话后收集
- 对比：两者 sec_uid 集合求交集

### 8.2 对比结果
| 指标 | 数值 |
|------|------|
| 首包有 sec_uid | 12/44 (27%) |
| im/user/info 有 sec_uid | 37/44 (82%) |
| 两者重叠 | 2/44 (5%) |
| 首包 sec_uid 长度分布 | 全部 55 字符（正则匹配"MS4wLjABAAAA" + 47~52 后续） |
| im/user/info sec_uid 长度 | 48~56 字符（完整值） |

### 8.3 根因分析
**首包 sec_uid 覆盖率低的根因：**
1. `_extract_str` 按"ASCII 可打印字节连续"切分 protobuf 字节，sec_uid 经常和后续字段（头像 URL、uid、时间戳）粘连成一个超长串
2. 正则 `MS4wLjABAAAA[\w_\-]{36,44}` 要求"MS4wLjABAAAA"后跟 36~44 个 `[\w_\-]`，但粘连后：
   - 情况 A：后续字节含非 `\w_\-` 字符（如 `+`/`/`/`=`）→ 正则提前中断，匹配不到
   - 情况 B：后续字节恰好都是 `\w_\-` → 匹配成功，但取到的是"sec_uid + 垃圾"的变形串
3. 这就是为什么首包提取的 sec_uid 和 im/user/info 对不上——**首包取到的经常是变形串**

**im/user/info 覆盖率高的根因：**
1. 浏览器观测截的是前端自己解析好的 JSON 响应，`data[i].sec_uid` 是完整值
2. 前端对每个需要渲染的会话都会调 `im/user/info`，覆盖率由"前端是否发请求"决定

### 8.4 结论
- 首包 sec_uid（27% 覆盖、与 im/user/info 重叠仅 5%）**不可作关联键**，实测端到端 0 命中
- `im/user/info` 是昵称/头像主数据源，但其 sec_uid 同样不可靠作为桥接键
- **正确解 = 数字 UID 桥接**：首包 `peer_uid`（100% 可靠）↔ `im/user/info.uid`（100% 在），绕过脆弱 sec_uid 串

## 九、昵称关联演进与最终定稿（数字 UID 桥接）

### 9.1 问题演进（为何走到数字 UID）
1. **初版 bug：首包 `sec_uid` 全取自身** —— `parse_init_protobuf` 原取 `_extract_str` 中第一个 `MS4wLjAB...` 串，而首包每个会话字节里自己的 sec_uid 排在最前 → 全部会话 sec_uid=自己 → 对端全丢。
2. **修复 A：排除自身取对端 sec_uid** —— 全局统计 sec_uid 频率，自己账号的 sec_uid 频率最高；取非最高频的作为对端 sec_uid。实测首包 44 会话 0 个 sec_uid=None。
   - **但 A 仍不可靠**：首包 sec_uid 与 im/user/info 重叠仅 5%（§八），用首包 sec_uid 去查 im/user/info 的 sec_uid 映射，基本全漏。
3. **初版 B 漏洞：WS 新消息不回写昵称** —— `recv_daemon.add_message` 原只 `UPDATE last_ts/unread`，不碰 `peer_name`；对端发消息带 `sender_nickname` 时昵称不写库 → B 形同虚设。
4. **修复 B：运行时回写昵称** —— `add_message` 收到带 `peer_name`(sender_nickname) 的消息时，补 `UPDATE dm_conversations SET peer_name=? WHERE ... (peer_name IS NULL OR =peer_id OR =自身昵称)`，不破坏已有正确昵称。
5. **定稿（2026-08-27）：数字 UID 桥接** —— 发现 `im/user/info` 响应**自带数字 `uid`**，与首包 `peer_uid`（conv_id `0:1:uid:uid` 排除自身）是同一用户的精确数字，直接相等比对即可 100% 关联，彻底绕开 sec_uid 串。

### 9.2 数字 UID 桥接机制
```
首包 protobuf → conv_id + peer_uid（conv_id 0:1:uid:uid 排除自身即得，100% 可靠）+ 消息内容 + 时间戳
im/user/info  → uid(数字) + sec_uid + nickname + avatar（主数据源，hook 补取 uid）

关联：for 每个会话:
        info = userinfo_by_uid.get(str(peer_uid))   # 数字精确比对
        if info: 写昵称/头像
        else:    fallback userinfo.get(sec_uid)      # 首包 sec_uid 兜底，实测 0 命中
```

- **覆盖率 = 100%**（实测，见 §九.3）：只要 BCC 在 chat 页按平滑滚动点完全部会话、触发全部 `im/user/info`，一次性前移捕获即 44/44 全覆盖。
- **0 错配**：数字精确相等，不存在模糊匹配错位。
- **首包 sec_uid 彻底退为无效兜底**（实测兜底命中 0），不再影响关联质量。

## 十二、聊天记录完整抓取与解码（2026-08-29 实机验证）

### 12.1 核心结论：聊天记录走 HTTP 双路，必须合并才完整

实测（账号「四川工伤张老师」，会话 `0:1:103242153689:3887506227210423`）：

| 端点 | cmd | 内容范围 | 实测条数 |
|---|---|---|---|
| `get_message_by_init` | 2043 | **首包初始化数据**，含每个会话的**最新**消息 | 24 条（最新段） |
| `get_by_conversation` | 301 | **点进会话**时拉该会话**历史**消息 | 30 条（历史段） |
| **合并去重** | — | 完整对话 | **50 条有效** |

**单靠任一路都不完整**：
- 只调 `get_by_conversation` → 只能拿历史段（实测漏最新 20 条，含末条「好的 谢谢」）
- 只调 `get_message_by_init` → 只能拿最新段（首包只含每会话最后几条预览）

**铁律：拿全聊天记录 = 首包(2043) + 历史(301) 两路 HTTP 合并去重。**

### 12.2 之前踩的坑（避免重复）

1. **`mcs.zijieapi.com/list` 不是会话详情** —— 它是抖音 Web SDK 配置/心跳 ping，
   响应体为空（`len=0`），与聊天记录零关系。实测点进会话前后它一直刷屏，纯干扰项。
2. **`get_info_list`(610) / `participants_readindex` 不是聊天内容** ——
   前者是会话元数据列表，后者是已读游标。
3. **`get_by_conversation` 的 `field 5.2` 是本页条数，不是总数** ——
   实测首屏返回 `32`，误读为"会话只有 32 条"导致漏抓最新 19 条。
4. **滚动翻页拿不到最新消息** —— 前端 cursor 卡在 `1672502400010000`（与首屏相同），

5. **WS 帧不含消息体** —— `wss://frontier-im.douyin.com/ws/v2` 只推
   `command_type:14/1` 会话同步（已读、未读数），**不推历史聊天消息**。
6. **拒绝 DOM 方案** —— DOM 直读虽能拿到全量，但会持续唤醒指纹浏览器，

### 12.3 protobuf 解码方法

响应是 protobuf 二进制（非 JSON），项目 `Response.proto` 的 body oneof
只定义了 500/609/610，**未定义 301 和 2043**，业务数据落在 unknown field。

解码方式：`blackboxprotobuf.decode_message(raw)` 黑盒还原（不依赖 .proto）。

**消息结构路径**：
```
get_by_conversation(301):
  parsed["6"]["301"]["1"]        -> 消息数组
    每条: "1"=conversation_id  "7"=sender_uid  "8"=content  "10"=create_time

get_message_by_init(2043):
  parsed["6"]["2043"]            -> 递归遍历，找含 conversation_id 且有 "8" 的节点
```

**content（field 8）是 JSON 字符串**，UTF-8 转义，需反转义后 `json.loads`：
- `text` 字段 → 文本消息（如 "老师 左桡骨小头骨折 上海能评上吗"）
- `tips` 字段 → 系统消息（如 "你已确认聊天，对方可继续向你发送消息"）
- `aweType:2702` → 图片消息（含 `resource_url.large_url_list` 可下载图床 URL）
- `activity_desc` → 卡片/分享消息
- 空 `{}` → 无内容消息（撤回/红包等），应剔除

**反转义写法**：
```python
s = str(content)
if s.startswith("b'"): s = s[2:-1]
s = s.encode("utf-8").decode("unicode_escape").encode("latin1").decode("utf-8")
obj = json.loads(s)
```

### 12.4 时间戳字段（可转可读时间）

**消息级时间戳在 `field 10`**（毫秒），另 `field 9` 的 ext 里有
`s:server_message_create_time`（字符串形式，同值）。

```python
from datetime import datetime, timezone, timedelta
CST = timezone(timedelta(hours=8))
def ts_to_str(ts):
    ts = int(ts)
    if ts <= 0: return None        # 脏数据：时间戳为 0 → 1970-01-01，应剔除
    if ts < 1e12: ts *= 1000       # 秒级转毫秒
    return datetime.fromtimestamp(ts/1000, CST).strftime("%Y-%m-%d %H:%M:%S")
```

**注意**：会话级 `read_index`（如 `1672502400520000`）是**消息序号游标**
（步长 10000），**不是时间戳**，不可当时间用。

### 12.5 清洗规则（实测 56 条原始数据 → 50 条有效）

剔除：
1. 时间戳为 0 / 1970-01-01 的无效记录（3 条）
2. content 为空 `{}` 的消息（2 条）
3. 非 JSON 的纯数字脏数据（1 条）

保留：文本、系统、图片、卡片消息（均有真实内容）。

### 12.6 实测结果（会话 `0:1:103242153689:3887506227210423`）

- 时间范围：`2026-08-28 13:53:41` → `14:32:08`

> 回归脚本：`backend/daemon/verify_handledispatch.py`（真实 protobuf 帧注入，11/11）。
>
> **教训**：`getattr` 的默认值会**静默掩盖字段名错误** —— 不报异常、不写日志，
> 只是条件恒真。涉及 protobuf 字段必须对照 `.proto` 核字段名，
> 绝不能把 `getattr(..., None)` 当「字段不存在」的正常兜底路径。

### 13.6 Bug 修复二：重复落库

**现象**：「转角遇到」会话真实 ~19 条，数据库存了 **104 条**（重复 5~6 遍）。

**修复**：改为开关控制，**默认关闭**。私信页纯读库，需要更新时点「更新会话」。

- 开启方式：环境变量 `DY_AUTO_CAPTURE_ON_START=1`

### 16.2 会话列表乱跳 + 点开后聊天记录变空

**现象**：列表每 5s 自动重排（前 20 名全换一批），点开的会话聊天框变空。

**两条根因叠加**：

| # | 位置 | 问题 |
|---|---|---|
| 1 | `api/messages.py::list_conversations` | 仅 `ORDER BY last_ts DESC`，大量会话 last_ts 相同/相近时**顺序不稳定**（依赖 SQLite 内部扫描顺序，而表持续被 WS 写入） |
| 2 | `messages.tsx` 列表项 id | `id: "rc" + i` 用**数组下标**当 id，排序一变下标就变 → `active` 失配 |

**实测**：连续 4 次列表轮询（间隔 5s），前 20 名**每次都完全不同**。

**修复**：

```sql
-- 加二级排序键，保证顺序确定
ORDER BY last_ts DESC, conv_id ASC
```

```tsx
// id 用会话唯一标识，不随排序变化
id: c.conv_id || "rc" + i,
```

同时 `send()` 的会话有效性校验从 `conv.id.indexOf("rc") !== 0`
改为 `!conv.conv_id`（id 语义已变）。

**铁律**：列表项 React key / 选中态标识**必须用业务唯一键（conv_id）**，
禁用数组下标 —— 任何会重排序的列表用下标都会导致选中态错位。

### 16.3 「对方已读」回执刷屏挤掉真实聊天记录

**现象**：聊天框里大量重复无意义内容，真实对话被挤掉。

**根因**：`msg_type=50001`（「对方已读 标号 X」回执）经 WS 反复写入：

- 无 msg_id → `uniq_dmmsg` 唯一索引（要求 msg_id NOT NULL）**管不到**
- 每次 WS 同步重复写入 → 实测全库堆积 **2368 条**（占当时总量 80%）
- 且不断刷新会话 `last_ts` → 加剧 16.2 的排序抖动

1. `recv_daemon.add_message` 对 `msg_type == "50001"` **直接不落库**
   （仅 `get_or_create` 维持会话存在，不写 dm_messages、不刷 last_ts）
2. 详情接口查询加过滤 `AND msg_type <> '50001'`
3. 已清理历史脏数据 2368 条（真实消息 586 条保留）

### 16.4 「分享视频」卡片的来源（非脏数据）

`recv_daemon.py` 对 `msg_type == 8` 解析为 `[分享视频] 视频ID xxx`。

> 后续 `_NOISE_PATTERNS` 仍加了裸 `"[分享视频]"` 子串 ⇒ **带 ID 的真实分享

> 两条同文本并存）。**教训：所有写 dm_messages 的路径必须带 msg_id。**

## 十七、聊天记录被列表轮询清空（2026-08-29 实测，v0.31.2）

### 17.1 现象

用户反馈：**「确实没乱跳了，但聊天记录也没了」**。

（上一版修好乱跳后立刻暴露 —— 原先「乱跳」掩盖了这个问题。）

### 17.2 根因

上一版把会话详情消息用 `qc.setQueryData(["msg-convs", acct], ...)` 写回
**列表缓存**，但列表 query 带 `refetchInterval: 5000`：

- 每 5s 用后端新数据**整体覆盖** `["msg-convs"]` 缓存
- 而列表接口 `/conversations` 的 `messages` **恒为 `[]`**
- → 点开会话时消息能显示，**5 秒内就被下一次列表轮询清空**

### 17.3 修复

聊天记录改用**独立 query**，与列表缓存解耦：

```tsx
const detailQ = useQuery({
  queryKey: ["msg-detail", activeAcct, conv.conv_id],
  queryFn: async () => { /* GET /api/messages/conversation */ },
  enabled: !!ready && !!activeAcct && !!conv.conv_id,
  staleTime: 3000,
});

const convMsgs: Msg[] = detailQ.data || conv.msgs || [];
```

配套改动：

- `openConv` 只做 `setActive(id)`，**不再手动拉取与回填**
- 渲染数据源从 `conv.msgs` 改为 `convMsgs`
- 移除已不再使用的 `qc`（useQueryClient）及 import

### 17.4 铁律（本次核心教训）

> **凡是被轮询（`refetchInterval`）覆盖的缓存，绝不能往里塞需要长期保留的数据。**
> 派生数据 / 详情数据必须用**独立 queryKey**。

典型错误模式（勿重犯）：

```tsx
// ❌ 错：写进轮询缓存，5 秒后被清空
qc.setQueryData(["msg-convs", acct], (old) => /* 塞 msgs */);

// ✅ 对：独立 queryKey，不受列表轮询影响
useQuery({ queryKey: ["msg-detail", acct, convId], ... });
```

### 17.5 三个相关问题的因果链

```
列表 id 用数组下标
  └─> 排序变化导致 id 错位 ──> 会话「乱跳」+ 聊天框变空
        └─> 改用 conv_id 修好乱跳
              └─> 暴露「回填消息被 5s 轮询覆盖」──> 记录消失
                    └─> 改用独立详情 query 修好
```

## 十九、富媒体消息解析与气泡渲染规范（2026-08-29，v0.31.4）

### 19.1 四类消息必须区分渲染

| 类别 | 判定 | 渲染 |
|---|---|---|
| 普通对话 | 有真实文本 | 左(对方) / 右(我) 气泡 |
| **系统提示** | `你已确认聊天` / `Recall Content Hided` / `消息已撤回` 等 | **居中**虚线小气泡（`.msg.sys`） |
| 图片 / 表情包 | 文本含媒体 URL | `<img>` 缩略图预览 |
| 撤回 | `Recall Content Hided` | 归入系统提示 |

**关键**：系统提示**不是对话内容**，不能按 dir 左右分列，
否则「你已确认聊天，对方可继续向你发送消息」会被当成"我发的消息"。

### 19.2 富媒体 URL 丢失的根因（重要）

后端首包解析（`conversation_capture.parse_init_protobuf`）原逻辑：

```python
text = obj.get("text") or obj.get("tips")
if not text:
    continue          # <- 图片/表情/语音没有 text 字段，整条被丢弃
```

抖音的**图片/表情/语音/视频卡片消息没有 `text` 字段**，
只有 `resource_url` / `url` / `itemId`。
结果：这类消息被整条 `continue` 丢弃，或只剩「图片」二字（无 URL）。

**修复**：新增 `_extract_media_text(obj)`，按类型提取媒体 URL：

```python
resource_url.origin_url_list[0]  ->  "[图片] <url>"
url.url_list[0]                  ->  "[表情包] <url>"
itemId                           ->  "[分享视频] 视频ID <id>"
兜底                              ->  "[未知媒体] <json前200字符>"
```

实测：

```
图片           -> [图片] https://p.img/abc.jpeg
图片仅url_list -> [图片] https://p.img/only.jpeg
表情包         -> [表情包] https://p.img/sticker.webp
分享视频        -> [分享视频] 视频ID 7300000001
纯文本         -> 你好
```

### 19.3 WS 侧同样要修（recv_daemon._extract）

`t == 5`（表情）/ `t == 27`（图片）的原兜底分支也会丢 URL。
改为按优先级取：`origin_url_list` → `url_list` → 才退化占位。

**不能只修首包解析** —— 两条链路（HTTP 首包 + WS 实时）都要覆盖。

### 19.4 前端渲染

```tsx
function extractImageUrl(text: string): string {
  const m = (text || "").trim().match(/https?:\/\/\S+/);
  return m ? m[0] : "";
}
```

- 有 URL → `<a class="imgbubble"><img src={url}></a>`（最大 220×240，点击看原图）
- 无 URL 的历史数据 → `[图片]（无图链，需重新捕获）`

### 19.5 时间对齐

`.msg .mtm` 原为 `align-self: flex-end`（贴气泡底部），改为 `center` 垂直居中。

### 19.6 消息类型速查（更新版）

| msg_type | 含义 | text 字段 | 处理 |
|---|---|---|---|
| 7 | 文本 | 有 | 正常气泡 |
| 5 | 表情包 | **无** | `[表情包] <url>` → 图片预览 |
| 8 | 分享视频 | **无** | `[分享视频] 视频ID x` |
| 17 | 语音 | **无** | `[语音] <url>` |
| 27 | 图片 | **无** | `[图片] <url>` → 图片预览 |
| 50001 | 已读回执 | — | 不落库（§十六） |

## 二十、抖音 IM 图链是私有加密格式，不能内嵌预览（2026-08-29 实测）

### 20.1 现象

把图链直接塞进 `<img src=...>` 后，界面显示**报错/破损图片图标**。

### 20.2 实测根因

取一条真实图链（如 `https://p11-sign.douyinpic.com/tos-cn-o-00061/...`
`~tplv-x-get:.image?lk3s=...&x-expires=...&x-signature=...`）直接请求：

```
HTTP: 200
Content-Type: application/octet-stream
总字节: 369293
前 64 字节: e2fdd402 3e2c47f3 1c1f2837 930a45be 9e8580d4 878c6d0c ...
```

**关键**：在**全部 369293 字节**里搜索标准图片魔数，**一个都没有**：

| 格式 | 魔数 | 出现位置 |
|---|---|---|
| JPEG | `ffd8ff` | -1（不存在） |
| PNG | `89504e47` | -1 |
| WebP | `RIFF` | -1 |
| GIF | `GIF8` | -1 |
| HEIC | `ftyp` | -1 |

抽 3 条不同图链，首 8 字节各不相同且都不是标准格式：

```
e2fdd4023e2c47f3
d3aa3b25f7e135ec
6ef25b2a9fa4f29c
```

**结论**：抖音 IM 的图片是**私有加密/封装格式**（不是加了私有头的 JPEG，
而是整段数据流都非标准），浏览器 `<img>` 无法解码。

### 20.3 结论与处理

**图链预览这条路技术上不可行** ——
除非逆向抖音的解密算法（成本高、且主动解密属高风险操作，违反风控红线）。

**正确做法：降级为可点击链接 + 明确说明**

```tsx
// 不能用 <img src={url}>，会显示破损图标
<div className="bubble medialink">
  <span className="mlabel">[图片]</span>
  <a href={url} target="_blank" rel="noreferrer">点击查看原图</a>
  <span className="mhint">（抖音加密格式，不支持内嵌预览）</span>
</div>
```

用户点击后在浏览器打开：抖音服务器会返回该 URL，
至于能否在浏览器里正常显示取决于抖音自己的解码能力，
但**在本应用内嵌渲染是不可行的**。

### 20.4 排查方法（可复用）

拿到媒体 URL 后，**先验证是否真的可渲染**，不要想当然：

```python
d = urllib.request.urlopen(req, timeout=15).read()
for name, sig in [("JPEG", bytes.fromhex("ffd8ff")),
                  ("PNG", bytes.fromhex("89504e47")),
                  ("WEBP", b"RIFF"), ("GIF", b"GIF8"),
                  ("HEIC", b"ftyp")]:
    print(name, d.find(sig))     # 全为 -1 => 非标准格式
```

若 `Content-Type: application/octet-stream` 且无任何图片魔数，
即可判定为私有格式，**不要**尝试 `<img>` 渲染。

### 20.5 顺带：过滤「[未知媒体] {}」噪音

空媒体对象（解析出 `{}`）会被兜底逻辑存成 `[未知媒体] {}`，
污染聊天记录。三层防护：

1. `_extract_media_text()` 遇空 dict 返回 `None`（调用方丢弃）
2. 后端详情接口 SQL 加 `AND text NOT LIKE '[未知媒体]%'`
3. 前端 `detailQ` 加 `.filter(m => !/^\[未知媒体\]/.test(m.text))`

版本：`0.31.5` → **`0.31.6`**。提交：`1e1be3d`。

## 二十一、图片消息解析根因与图床方案（2026-08-30 实测，`0.31.7`）

> 本节全部结论来自实机探针 + 首包原始字节离线分析（首包 1,304,194 字节，

### 21.1 图片数据到底存在哪（决定性结论）

**图片既不是 DOM 捕获，也不是 HTTP 拉取——是内嵌在 protobuf 消息体里。**

解析出的图片消息 JSON（实测 8418 字节，35 个字段）关键结构：

```json

  "inline_sign": "db1b414e42a987d841bf0df371826be739bd2d43...",
  "md5":         "b068dc0f90e57fea539a185479bafe73",
  "cover_width":  1206,
  "cover_height": 2622,
  "resource_url": {
    "data_size":       292635,
    "thumb_url_list":  ["https://p3-sign.douyinpic.com/...~tplv-x-get:thumb.image?..."],
    "medium_url_list": [...],
    "large_url_list":  [...],
    "origin_url_list": ["https://p5-ex-gddgtc-sign.douyinpic.com/...~tplv-x-get:.image?..."],

  }

```

| 来源 | 实测结论 |
|---|---|
| **`inline_pic`** | **图片本体**。base64 编码的**标准 WebP**（`RIFF....WEBP`）。实测 27/35 条可用，平均 3.5KB，典型 160×213。零请求、零风控 |
| `resource_url.*_url_list`（thumb/medium/large/origin 四组） | **全部为抖音私有加密格式**。实测 HTTP 200 但 `Content-Type: application/octet-stream`，**熵 7.955~7.999 / 8.0**，256 种字节值均匀分布，**无任何标准图片魔数**。浏览器 `<img>` 必报破损图标 |
| `skey` | 远程图的解密密钥。**未逆向**（高风险，且违反风控边界） |

**与用户 `图链地址.md` 的相互印证**：用户从抖音网页复制图片得到的
`data:image/png;base64,UklGR...`，其 `UklGR` 前缀 = base64 的 `RIFF`，
与 `inline_pic` 前缀**逐字符一致**——证明网页显示的就是 `inline_pic` 解码产物。

**解释了此前全部疑点**：
- 前端为何从不发图片 HTTP 请求（探针实测 `fetch.img=0` / `xhr.img=0`）→ 字节已在消息里
- 远程图链为何解不开 → 那是备用引用且加密
- 前端网络面板出现 `blob:https://www.douyin.com/...` → 解密后包成 Blob 给 `<img>`

### 21.2 两个解析 bug（图片消息解析后为 0 条的真因）

首包原始字节里 `inline_pic` 出现 **40 次**、`resource_url` 出现 **44 次**，
但 `parse_init_protobuf` 解析后**图片消息 0 条**。两个独立 bug：

| # | 位置 | 问题 | 证据 |
|---|---|---|---|
| 1 | `_parse_message_text` | 只接受含 `"text"` 的字符串，且 `obj["text"]` 非空才返回。图片消息**没有 text 字段** → 第一关 `continue` 丢弃 | spy 挂载确认 `_extract_media_text` 被调用 **0 次** |
| 2 | `_extract_str` | 有 `if 1 <= len(s) <= 800` 硬上限（原为过滤短噪音设计）。图片消息 content JSON 实测 **8KB+**（含 inline_pic base64）→ 整条被过滤 | 构造 8418 字节消息测试，只提取到 **1 个长度=1 的字符串** |

**修复**（`backend/auto_dm/conversation_capture.py`）：
1. 新增 `_extract_long_str(b, min_len=200, max_len=200000)` —— 只放宽长度上限，
   其余提取规则与 `_extract_str` 一致。**单独提供，不动 `_extract_str` 的短串语义**
   （避免影响依赖它的其他逻辑）。
2. `_parse_message_text` 改**双路径**：先走原短串路径（文本消息行为完全不变），
   失败后用 `_extract_long_str` 重试富媒体（匹配 `resource_url` / `inline_pic`）。

**修复后实测**：图片/表情类消息从 **0 条 → 23 条**。

## 二十三、图片存储策略：图床 → 内联 base64 的方向纠正（2026-08-31，`0.31.8`）

### 23.1 用户的关键质疑

> 「使用图床还是要下载的话那不是和本地没区别吗，我记得图链是可以直接查看图片的呀」

**这一问戳中了要害**。此前我默认"图床一定更优"，从未实测过**图片到底多大**。
实测后证明方向是错的。

### 23.2 决定性数据（60 张真实私信图片）

| 指标 | 实测值 |
|---|---|
| 图片平均大小 | **2.9 KB**（中位 4KB，最大 4.9KB，最小 362B） |
| 60 张合计 | **121 KB** |
| 全部内联进 SQLite | +161 KB（base64 膨胀 33%） |
| 数据库变化 | 1.21 MB → 1.37 MB，**仅增 13%** |
| 单条消息 | 约 4KB 字符串 |

**结论**：图片本来就只有 3KB。为省这 3KB 让每张图多花几百毫秒跨网络下载，
是**本末倒置**。

### 23.3 两个图床实测对比（真实 4066B WebP）

| 指标 | imgbb（境外） | tucdn.wpon.cn（国内） |
|---|---|---|
| 上传 | 1.13s，频繁 SSL 超时 | **0.83s** |
| 下载（5 次均值） | **2.278s** | **0.353s** |
| 最快单项 | thumb 2.078s / display 2.479s | 原图 0.353s |
| 超时 | 实测出现 31s 超时 | 无 |
| 字节一致 | ✅ | ✅ |
| 提速 | — | **6.4×** |

**imgbb 的 HTML/BBCode 嵌入能力无效**：返回的 `html`/`bbcode` 只是把同一个
境外 URL 包一层 `<a><img src="...">`，`src` 仍指向 `i.ibb.co`，
浏览器照样跨洋下载 —— **嵌入代码不改变任何加载耗时**。

imgbb 响应字段全貌：`url` / `display_url`（同值）、`image{}`、`thumb{160}`、
`delete_url`、`expiration: 0`（永久）。**注意：无 `medium` 字段**（返回 None）。

### 23.4 最终策略（v0.31.8 落地）

**小图内联 base64（默认），大图才上图床**：

```
inline_pic 存在？
  ├─ 是 → 估算大小 ≤ image_inline_max_kb（默认 32KB）？
  │        ├─ 是 → 直接内联 data:image/webp;base64,...  ← 绝大多数走这里
  │        └─ 否 → 上传图床（tucdn 优先，imgbb 备选），失败仍内联
  └─ 否 → 用远程 thumb URL 兜底（前端降级为可点击链接）
```

**收益**：
- 渲染**零网络请求、瞬时显示**（数据随消息一起返回）
- 无超时风险、无第三方依赖、无隐私外泄（图床链接是公开可访问的）
- 数据库代价可忽略（+13%）

**配置项**（`backend/config.py`）：

```python
image_inline_max_kb: int = 32   # ≤ 此值内联；超过才上图床；0 = 永远内联
image_host_backend: str = "tucdn"  # tucdn / imgbb
tucdn_token: str = ""
imgbb_api_key: str = ""
```

对应环境变量：`IMAGE_INLINE_MAX_KB`、`IMAGE_HOST_BACKEND`、
`TUCDN_TOKEN`、`IMGBB_API_KEY`。

**实现位置**：
- `backend/auto_dm/conversation_capture.py` — `_inline_max_kb()` +
  `_extract_media_text()` 的分支判断
- `backend/auto_dm/image_host.py` — 双后端上传（`_upload_tucdn` /
  `_upload_imgbb`），保留为**大图兜底**

### 23.5 tucdn.wpon.cn API 备忘

- 上传：`POST https://tucdn.wpon.cn/api/upload`
- 格式：`multipart/form-data`，字段名 **`image`**
- 认证：token 放 **HTTP header `token`**（不是表单字段）
- 响应：`{"code":200,"msg":"success","data":{"url":"https://tucdn.wpon.cn/2026/08/31/xxx.webp",
  "size":4066,"mime":"image/webp","sha1":"...","md5":"...","quota":107374182,"use_quota":8132}}`
- 配额：约 100MB（`quota` 字段），60 张图用掉 8KB
- 官方文档里写的域名是 `ddnsapi.aa1.cn`，**实际 `tucdn.wpon.cn` 可用**

### 23.6 教训（重要）

> **任何"优化"前先量尺寸。**
>
> 本次错误：想当然认为"图片很大 → 应该上图床省空间"，
> 却从未测过图片实际大小。结果图片平均只有 3KB，
> 图床带来的网络延迟（0.35~2.5s/张）远大于它省下的空间收益。
>
> 通用判据（本项目场景）：
> - 平均 < 10KB 且总量 < 5MB → **内联 base64 更优**（零请求、瞬时渲染）
> - 平均 > 100KB 或总量 > 50MB → 图床更优（避免库膨胀）
>
> 另：用户质疑"图链不是可以直接查看吗"时，正确做法是**立刻质疑自己的前提**，
> 而不是继续在错误方向上优化（当时我还在对比该换哪个图床）。

## 二十四、前端缓存位置与 301 补全并发优化（2026-08-31，`0.31.8`）

### 24.1 前端缓存到底在哪（三处，之前一直没清干净）

用户问「前端缓存你没清除呀」——确实有三层，只清数据库不够：

| 层级 | 位置 | 清理方式 |
|---|---|---|
| React Query 内存缓存 | 进程内，`staleTime` 10~20s | 代码层 `invalidateQueries()` |
| WebView2 磁盘缓存 | `C:\Users\LOX\AppData\Local\com.dyautodm.console\EBWebView` | **删目录**（实测 82MB → 4KB） |
| BCC 浏览器缓存 | `C:\temp\dyautodm_test\guest_profile_tmp\Default\Cache` | 删目录内容 |

**代码修复**（`frontend/src/pages/messages.tsx`）：更新会话完成后原本只
`convsQ.refetch()`，**不够**——React Query 未失效的旧数据仍会显示。
改为：

```ts
const qc = useQueryClient();
...
.finally(() => {
  setRefreshing(false);
  qc.invalidateQueries().catch(() => {});  // 强制失效全部缓存
  convsQ.refetch().catch(() => {});
});
```

同时需导入 `useQueryClient`（原文件只 import 了 `useQuery`）。

**排障要点**：清空数据库后若前端仍显示旧数据（旧昵称、已删除的污染数据），
先怀疑这三层缓存，而不是后端。

### 24.2 逐个会话串行请求 —— 不是浏览器点击

用户问「逐个会话串行请求是如何处理的，是因为浏览器逐个点击会话造成的吗」

**答：不是。** 是**后端 HTTP 串行**，与浏览器无关。

位置：`backend/auto_dm/conversation_capture.py` 长会话补全段（约 916 行）：

```python
for i, c in enumerate(need):
    if i:
        _time.sleep(sleep_s)                 # 间隔 1.5s
    hist = fetch_conversation_history(...)   # 直接 HTTP，不开浏览器
```

**365 秒的构成**（实测对得上）：

```
首包拉取 + BCC 浏览器启动        ≈ 135s
长会话补全 20 个 × (请求~10s + 间隔1.5s) ≈ 230s
────────────────────────────────────
总计                              ≈ 365s
```

`need` 的选取规则：只补 `(total_msgs - 已有消息数) > 0` 的会话，
按缺口**降序**排序，取前 `DY_HISTORY_MAX`（默认 20）个。

### 24.3 并发优化（保守，默认 4）

改为**按批次错峰并发**：

```python
workers = max(1, min(8, int(os.environ.get("DY_HISTORY_WORKERS", "4"))))
with ThreadPoolExecutor(max_workers=workers) as ex:
    for b in range(0, len(need), workers):
        if b:
            _time.sleep(sleep_s)          # 批间错峰，不是逐个 sleep
        batch = need[b:b + workers]
        for peer_uid, n, err in ex.map(_fill, batch):
            ...
```

**两个实现坑**（都已规避）：

1. `sleep` 位置：若把 `_time.sleep(sleep_s)` 放在 `_fill()` 内部并配
   `ex.map(_fill, enumerate(need))`，并发会**退化成串行**（每个任务各自
   sleep，第一批 workers 个全在睡）。必须把 sleep 提到**批间**，
   `ex.map(_fill, batch)` 只传会话不传索引。
2. `need` 里的元素是 dict（引用），`_fill` 内改 `_c["messages"]`
   能正确写回外层列表，不需要回传整个对象。

**为什么默认只有 4**：本项目曾因短时高频调用抖音接口触发风控
（首包返回 50 字节空响应 `{"BaseResp":{},"Header":{},"Method":0,"Service":0}`、
cookie 失效需重新扫码）。故不做激进并发，上限硬编码 8。
想更快调 `DY_HISTORY_WORKERS=6`，但需自担风控风险。

**预期**：20 个会话从 ~230s 降到 ~60~80s，总时长 365s → ~200s。

清空数据库后重新捕获，干净数据下的结果：

| 指标 | 值 |
|---|---|
| 会话 / 消息 | 45 / 648 |
| 图片消息 | 60 条 |
| **内联 base64** | **43 条（71%）** ✅ |
| 图床链 `i.ibb.co` | **0 条** ✅（策略生效，不再走图床） |

## 二十五、昵称 100% 命中：`wait=90` 才是超时根因（2026-08-31，`0.31.9`）

### 25.1 现象与误判

用户反馈「更新完毕昵称还是 UID，未显示解密」。

**我此前的误判**：查库看到 `peer_name IS NOT NULL` 有 222/222，
就报告「昵称全有，是前端缓存」。**这是错的** —— 没检查
`peer_name` 是否等于 `peer_id`。真实情况：

```
peer_name = peer_id（降级数据）: 222/222
真昵称（peer_name != peer_id） :   0/222   ← 一个真昵称都没有
```

**教训：`peer_name IS NOT NULL` 不能作为"有昵称"的判据**，
因为降级逻辑会把 UID 写进 `peer_name`。正确判据是
`peer_name != peer_id`。

### 25.2 根因：不是 BCC 慢，是 `wait` 配置错误

`conversation_capture.capture_userinfo_via_browser()` 原配置：

```python
r = requests.post(url, json={"wait": 90}, timeout=180)
```

`wait=90` 意味着 BCC 先等 90 秒，再跑 40 轮滚动点击
（每轮点遍所有可见会话 + 1.2s），**总耗时必然超过 180s 超时**。
超时后 `capture_userinfo_via_browser` 返回 `{}`，
写库走降级分支把 UID 填进 `peer_name`。

### 25.3 实测（`scripts/probe_bcc_speed.py`，222 会话真机账号）

| wait | 耗时 | 截获昵称数 |
|---|---|---|
| 5s（首次，含浏览器预热） | 152.7s | **278** |
| **15s** | **23.4s** | **278** |
| 30s | 38.4s | 278 |

**结论**：15s 与 30s 截获量完全相同（278 个），多等无收益。
抖音前端**首屏就会自发 `im/user/info`**，不需要等 90 秒，也不需要狂点会话。

### 25.4 关联验证：100% 命中

BCC 返回 `{sec_uid: {nickname, avatar, uid}}`，其中 **`uid` 是数字**，
**278/278 全部带**。与首包 `peer_uid` 做数字比对：

```
BCC 数字 uid 映射 : 278
库里 peer_uid     : 46
命中             : 46/46 = 100%
```

样例：`103242153689 -> 蛋蛋后`、`3871824015002071 -> 益览五金`、
`87776691233 -> 承 诺`、`3570809030839767 -> 香飘飘~`。

**这印证了 08 文档主线**：昵称关联靠**数字 UID 精确比对**，
不靠 sec_uid 串匹配（首包 sec_uid 覆盖率仅 27%）。

```python
# backend/auto_dm/conversation_capture.py

+ r = requests.post(url, json={"wait": 15}, timeout=240)
```

`timeout` 提到 240s 的原因：BCC **冷启动**首次调用实测 152.7s

**预期效果**：昵称捕获从「超时失败、0% 命中」变为
「约 23s 完成、100% 命中」；更新会话总时长不受影响

| 调用次序 | wait | 耗时 | 截获 |
|---|---|---|---|
| 第 1 次（冷启动） | 5s | **152.7s** | 278 |

### 26.4 两项优化（v0.32.0）

**① BCC 启动后后台预热**（`daemon/browser_daemon.py::_startup`）

启动 20 秒后**后台**（不阻塞 BCC 启动、不影响接口）跑一次
`capture_userinfo_map(wait=15)`，把昵称缓存填满。
之后用户点「更新会话」时缓存已热，昵称捕获降到 20~30 秒。

```python
def _prewarm():
    threading.Event().wait(20)
    loop = getattr(container, "_loop", None)
    if not loop:
        return
    fut = asyncio.run_coroutine_threadsafe(
        container.capture_userinfo_map(wait=15), loop)
    data = fut.result(timeout=300)
    logger.info(f"[bcc] 昵称缓存预热完成：{len(data)} 个")
threading.Thread(target=_prewarm, daemon=True).start()
```

**坑**：`_state` 里**没有** `loop` 键，要用 `container._loop`
（BrowserContainer 在 `start()` 里存的 `self._loop`）。

**② 滚动提前退出**（`capture_userinfo_map`）

昵称往往前几屏就截全（222 会话实测截到 278 个），后面 30 多轮是空转。
加「连续 3 轮无新增就停」：

```python
_stall = 0
_prev = -1
for _round in range(40):
    await _click_all()
    _cur = await self._page.evaluate(
        "() => window.__CAP_USERINFO__ "
        "? Object.keys(window.__CAP_USERINFO__.map || {}).length : 0")
    if _cur >= 0 and _prev >= 0 and _cur <= _prev:
        _stall += 1
        if _stall >= 3:
            break          # 提前结束，省下大量空转
    else:
        _stall = 0
    _prev = _cur
    ...
```

**预期**：179s → 约 40~60s（预热命中时更低）。

## 三十、【根因】WebView 里 `<a target="_blank">` 静默失败（2026-09-01，`0.33.1`）

### 30.1 用户反馈

> 「两处查看原图皆无效」

改了三处死链、加了缩放之后，点击**依然**没有任何反应。

### 30.2 真正的根因：不是链接问题，是 WebView 根本不会开新窗口

**Tauri 应用的界面跑在 WebView 里，WebView 没有标签页 UI**
（不像 Chrome 有地址栏/标签栏）。因此在 WebView 中点击
`<a href target="_blank">` 会**静默失败** —— 不弹错误、不报异常，
就是什么都不发生。

所以我之前反复改 `href` 的目标（加密链 → `douyin.com/chat`）**都是白改**：
链接本身早就对了，但 WebView 不知道该拿它怎么办。

**两个问题叠加**：
1. `href` 指向加密死链（§二十八 已修）
2. `<a target="_blank">` 在 WebView 里根本不工作（本轮才发现）

### 30.3 修复：用 `shell.open()` + 开 `shell:allow-open` 权限

**① capabilities 加权限**（`src-tauri/capabilities/default.json`）：

原配置只有 `shell:allow-execute` / `allow-spawn` / `allow-stdin-write` /
`allow-kill`，**没有 `allow-open`** —— 即使调用了 `open()` 也会被拒。

```json
{
  "permissions": [
    "core:default",
    "shell:allow-execute",
    "shell:allow-spawn",
    "shell:allow-stdin-write",
    "shell:allow-kill",
    "shell:allow-open",     ← 新增
    "dialog:default",
    ...
  ]
}
```

注：`tauri_plugin_shell::init()` 已在 `lib.rs:146` 注册，只需补权限。

**② 新增 `frontend/src/utils/openExternal.ts`**

```ts
export async function openExternal(url: string): Promise<boolean> {
  if (!url) return false;
  try {
    const mod: any = await import("@tauri-apps/plugin-shell");
    const open = mod?.open;
    if (typeof open !== "function") {
      window.open(url, "_blank", "noopener,noreferrer");  // Web 端兜底
      return true;
    }
    await open(url);
    return true;
  } catch (e) {
    console.warn("[openExternal] shell.open 失败，回退 window.open:", e);
    try { window.open(url, "_blank", "noopener,noreferrer"); return true; }
    catch { return false; }
  }
}
```

要点：
- **动态 `import()`**：Web 端（vite dev）没有 tauri 模块，静态引入会崩
- 双重兜底：非 Tauri 环境 / `open()` 失败 → `window.open`

**③ 四处调用点改为 `onClick` + `preventDefault`**

| 文件 | 位置 | 文案 |
|---|---|---|
| `messages.tsx` | ImageViewer 弹窗底部 | 去抖音网页查看原图 ↗ |
| `messages.tsx` | 气泡下方 thumbbar | 去抖音看原图 ↗ |
| `messages.tsx` | 无缩略图分支 | [{label}] 去抖音查看 ↗ |
| `accounts.tsx:844` | 前往直播间按钮 | 前往直播间 |

```tsx
<a
  href="https://www.douyin.com/chat"
  onClick={(e) => {
    e.preventDefault();
    void openExternal("https://www.douyin.com/chat");
  }}
>
```

**顺带修了 `accounts.tsx` 的「前往直播间」** —— 同一个 bug，
用户还没反馈到那里。

### 30.4 教训

| 教训 | 说明 |
|---|---|
| **桌面端外链必须用原生 API** | Tauri/WebView 里 `<a target="_blank">` 静默失败，`shell.open()` 才是正解。这是 Web 开发与桌面开发的**思维差异** |
| **"改了没生效" 要怀疑假设本身** | 我连续两轮只改 `href` 目标，却没怀疑过 `<a>` 这个标签在 WebView 里就不работает。**当同一处改两次都无效时，要回头质疑技术前提，而不是继续修参数** |

## 三十一、【根因】dist 残留旧 JS ——「改了没生效」的真正元凶（2026-09-01）

### 31.1 现象

连续多轮出现「代码改了、编译通过、打包成功，但界面行为没变」。
逐轮排查都指向"代码是对的"，但用户实测就是不生效。

### 31.2 根因：`emptyOutDir: false` + 每次构建生成新 hash 文件名

`frontend/vite.config.ts` 里有：

```ts
build: {
  emptyOutDir: false,   // ← 元凶
}
```

**当初加这个是为了规避 IDE safe-delete 拦截**（见注释），但副作用是：
Vite 每次构建生成**新的 hash 文件名**（如 `index-lFSom_Dd.js`），
旧文件**永远不会被清理**，于是 `dist/assets/` 越堆越多。

实测堆到 **43 个 index-*.js（17MB+）**。

### 31.3 为什么这会导致「改了没生效」

关键在于：**验证时必须看 exe 里真正打包的是哪份 JS，而不是 dist 里最新的那份**。

本轮实测发现：

```
dist/assets/
  index-CwjaXBRV.js  01:40  433,704  ← 旧代码，含 4 处 target:"_blank"
  index-lFSom_Dd.js  02:31  434,327  ← 新代码，已改 openExternal
index.html 引用 → index-lFSom_Dd.js   ✅ 正确
```

`index.html` 引用是对的，但 **exe 是在旧 dist 状态下打的**，
里面塞的可能是 `index-CwjaXBRV.js`（旧代码）。

所以：
- 源码 ✅ 改对了
- `tsc --noEmit` ✅ 编译通过
- dist 里有新 JS ✅
- **但 exe 里是旧 JS** ❌

### 31.4 排查方法：`scripts/verify_build.py` + `scripts/find_blank.py`

**`find_blank.py` 是定位关键** —— 它打印命中处的**前后文**，
能直接看出残留来自哪个文件：

```
============================================================
index-CwjaXBRV.js  (433,704 字节)  命中 4 处     ← 旧文件！
============================================================
--- 命中 1 @ offset 350249 ---
...i.jsx("a",{href:"https://www.douyin.com/chat",target:"_blank",...
```

**方法沉淀**：验证打包产物时，不能只统计"某字符串出现了几次"，
必须**打印前后文定位到具体文件**，否则会把旧文件的命中
误当成新代码生效。

### 31.5 修复与规范

1. **每次打包前清理 dist 旧 JS**（保留 index.html 引用的那个）：

```bash
cd frontend/dist/assets
keep=$(grep -oE 'index-[A-Za-z0-9_-]+\.js' ../index.html | head -1)
ls index-*.js | grep -v "^$keep$" | xargs rm -f
```

2. **`emptyOutDir: false` 不能动** —— 它是为规避 IDE safe-delete 拦截，
   改成 true 会导致打包失败。只能在打包后手动清理。

3. **验证脚本 `scripts/verify_build.py`** —— 每次打包后必跑，检查：
   - capabilities 权限（源文件 + schema 注册）
   - exe 大小是否异常（< 3MB 可疑）
   - 前端新代码字符串是否在 **dist 里被引用的那份 JS** 中
   - `target:"_blank"` **JSX 属性**残留（注意：注释里的
     `target="_blank"` 是误报，两者形式不同）

### 31.6 教训

| 教训 | 说明 |
|---|---|
| **dist 不清空 = 打包结果不可信** | Vite 的 hash 文件名机制 + `emptyOutDir:false`，导致旧产物永久残留 |
| **验证要定位到文件，不是统计次数** | "字符串出现了 2 次" 可能是旧文件的 2 次，必须看前后文 |
| **exe 与 dist 是两回事** | 改完 dist 后必须**重新打包 exe**，否则前端改动不生效 |
| **JSX 属性 vs 注释要区分** | `target:"_blank"`（JSX 编译后）是真代码；<br>`target=\"_blank\"`（注释原文）是误报 |

### 31.7 脚本

- `scripts/verify_build.py`（新建）：打包后验证产物
- `scripts/find_blank.py`（新建）：定位 `target:"_blank"` 残留的具体文件与上下文

## 三十三、图片原图 AES-256-GCM 解密：机制证真 + 落地证伪（2026-09-01 实测）

> 起因：用户发现开源项目 `TeamBreakerr/douyin-chat-export`（97 stars）能导出抖音私信的
> 图片/视频/语音/表情包。其 README 写明「AES-GCM 解密 + HEIC 自动转 JPEG」。
> 本节记录**逆向分析 + 本机隔离路径实测**的完整结论。

### 33.1 逆向结论：原图是 AES-256-GCM 加密，密钥在消息体里

`extractor/web_scraper.py::_save_image` 的核心（已抓源码核实）：

```python
cipher = _fetch(origin_url)        # p*-sign.douyinpic.com 那个"解不开"的图
key    = bytes.fromhex(skey_hex)   # ← 32 字节 hex，来自 content_json.resource_url.skey
iv     = cipher[:12]               # 密文前 12 字节
body   = cipher[12:]
plain  = AESGCM(key).decrypt(iv, body, None)   # ← 解密即原图
```

**skey 出处**：`content_json.resource_url.skey` —— 每条图片消息**自带**，
不需额外请求、不需计算。**这是全部关键。**

#### 对照：我们为什么判了「原图不可得」

§二十七 看到 `createImageBitmap` 解不开、去签名 403，就下了「不可得」结论。
**错在只看到 `origin_url`，没注意同一层还有 `skey`**。图链本身没错，
是我们没拿钥匙就去开门。

`backend/auto_dm/image_host.py:10` 其实已记录「私有加密（熵 7.999/8.0，
无图片魔数）」—— 现象测到了，但没人知道是 AES-GCM，所以止步。

#### 该项目的接口（只有 2 个）

| 接口 | 用途 |
|---|---|
| `POST imapi.douyin.com/v1/message/get_by_conversation` | 逐会话拉完整历史（protobuf，cmd 301） |
| `GET /v1/web/im/user/info/` | 用户信息 |

cmd 301 请求构造：`inner = f1=conv_id f2=1 f3=cursor f4=1 f5=timestamp f6=50`，
外层 `f1=301 f2=10027 f3="0.1.6" f5=3 f6=0 f7="fef1a80:p/lzg/store"
f8=encodeBytes(301,inner) f11="douyin_pc" f14="360000" f18=1 f21="douyin_pc"`，
响应 `f6→f301→{f1=消息数组,f2=nextTs,f3=hasMore}` 翻页到底。
**这就是「突破虚拟列表滚动上限」的原理**，比我们靠滚动触发懒加载彻底。

消息字段：`f3=server_id`（高 32 位 = Unix 秒）、`f4=created_at_us`（**正确排序键**）、
`f7=uid` / `f14=sec_uid`、`f8=content_json`（明文 JSON）、`f18=引用消息`。

消息类型（aweType）：700/0/701/703 文本；**2702/2703/2704 图片**（skey 解密）；
500/501/507/508/510/514/516 表情包（无加密）；带 resource_url+duration 且非 2702/3/4 = 语音；
11054/11055/11063/11066/11067/11069/11070 分享；≥100000 系统消息。

### 33.2 本机实测（隔离路径 C:\temp\dyautodm_test，账号「工伤小助理」）

#### ✅ 证真一：库里存的图链确实是密文（probe_skey.py）

抽样 5 条 `p*-sign.douyinpic.com` 图链，全部：

| 指标 | 结果 |
|---|---|
| Content-Type | `application/octet-stream`（**不是图片类型**） |
| 前 16 字节 | 全随机 hex，**0/5 命中**任何图片/视频 magic |
| lk3s 参数 | 全部 `lk3s=9698d6d2` |
| 体积 | 499KB / 435KB / 369KB（**原图量级**，非缩略图） |

→ 这些 URL 指向**加密的原图**，不是坏链。

#### ✅ 证真二：当前落库确实丢了 skey

- `dm_messages` 共 665 条，**msg_type 全为 `text`**，无一条 image
- `extra` 列**全为空**（43 条 base64 内联缩略图 + 80 条图链，均无 skey）

根因在 `daemon/recv_daemon.py::_extract`（第 553-606 行）：
每个分支都 `return f"[图片] {u}", {}` —— **extra 硬编码空 dict，skey 在此丢弃**。
`auto_dm/conversation_capture.py` 的图片分支同样只取 URL，不取 skey。

#### ❌ 证伪一：首包里**没有** skey

`probe_skey2.py` 离线解析 `probe_raw/init_*.bin`（250KB）：

```
skey: 0 次    resource_url: 0 次    origin_url_list: 0 次
aweType: 76 次   douyinpic: 493 次
```

**首包只给会话骨架 + 部分字段，不带 skey。**

#### ❌ 证伪二：浏览器被动 hook 也截不到 skey

`probe_skey4.py`（遵循 BCC hook 时序铁律：`add_init_script` 在 `goto` 前）：

| 滚动+点击全部会话 | ✅ 执行（12 项 × 2 轮，高度稳定到底） |

`probe_skey5.py` dump 原始响应字节（71 个响应 / 543KB）离线分析，同样 0。

#### ❌ 证伪三：首包的 douyinpic URL 是**表情包贴图**，不是聊天图片

> **判据（可复用）**：`lk3s=69c9632d` = 贴图，明文；`lk3s=9698d6d2` = 加密原图，需 skey。

### 33.3 结论：机制成立，但**落地必须先解决 skey 来源**

| 问题 | 结论 |
|---|---|
| 原图能拿到吗？ | **能**。密文可下载，AES-256-GCM 解密即可得到真原图 |
| skey 在哪？ | 在**消息体** `content_json.resource_url.skey`，随消息下发 |
| 我们为什么拿不到？ | **落库时主动丢弃**（`_extract` 的 `return ..., {}`） |

4. **前端**：解密后的图走现有内联/本地路径渲染。

### 33.5 风控评估

**不触碰红线**。红线是「不主动用后端批量**查昵称**」；

## 三十四、历史消息如何获取：三条路径 + 当前阻塞点（2026-09-01 实测）

> 承接 §三十三（图片 skey）。本节回答「历史消息怎么拿」，
> 全部结论经本机隔离路径实测，非代码推断。

### 34.1 三条路径总览

| # | 路径 | 接口 | 能力 | 现状 |
|---|---|---|---|---|
| A | 首包 `get_message_by_init` | cmd 2043 | 每会话**最后约 20 条** | ✅ 已在用（§十三） |
| B | 长会话补全 `get_by_conversation` | **cmd 301** | 单会话**完整历史**，翻页到底 | ⚠️ 代码已落地，但**存量会话缺 short_id 跑不通**（§34.3） |
| C | 浏览器滚动 | — | 受虚拟列表限制，拿不全 | ❌ 已弃用 |

**路径 B 是关键**：首包语义是「初始化预览」（实测每会话固定 ~20 条），
长会话历史必须靠 cmd 301。开源项目 `douyin-chat-export` 也正是用它实现
「突破虚拟列表滚动上限」。

### 34.2 cmd 301 已落地（代码位置）

| 函数 | 位置 |
|---|---|
| `_build_301_body(cid, short_id, cursor, count, direction)` | `backend/auto_dm/conversation_capture.py:608` |
| `fetch_conversation_history(auth, cid, short_id, ...)` | 同上 `:621` |
| `parse_conversation_301(raw, cid, my_uid)` | 同上 `:658` |
| 补全调度（含并发/节流） | 同上 `:922` 起 |

请求：`POST https://imapi.douyin.com/v1/message/get_by_conversation`，
复用 `ProtoBuilder.build_normal_request(auth, 301)` + 手工追加 field 301 body
（项目 .proto 未定义 cmd 301 的 oneof）。

**inner body 字段**（实测验证，与 §13.3 一致）：
```
1: conversation_id   2: type=1   3: conversation_short_id
4: direction=1       5: cursor=0 6: count
```

**响应结构**（用真实响应 `cap_conv_15.bin` 16,776B 验证）：
```
6 → 301 → { 1: 消息数组(n=9), 2: nextTs, 3: hasMore, 5: {...} }
每条消息: 1=conv_id  3=msg_id  7=sender  8=content(JSON明文)  10=create_time
```
与 §13.3 记载的 `parsed['6']['301']['1']` 完全吻合，**解析器无需改动**。

**风控保护**（已内置，§13.4）：`DY_HISTORY_FULL`(默认1) /
`DY_HISTORY_MAX`(默认20，单次最多会话数) / `DY_HISTORY_SLEEP`(默认1.5s 间隔) /
`DY_HISTORY_WORKERS`(默认4，并发上限8)。补全按「缺口降序」优先长会话。

### 34.3 ⚠️ 当前阻塞点：存量会话 short_id 全为 NULL

**实测数据（隔离路径 `data/dyautodm.db`）**：

```
dm_conversations 总数: 236
有 short_id 的:        0        ← 全部为 NULL
含图链的会话数:        27
```

**为什么致命**：cmd 301 的 field 3 `conversation_short_id` 是**必需参数**，
`_build_301_body` 里 `int(short_id)` 对 None 会直接抛 TypeError，
`capture_all` 补全调度也有 `if c.get("short_id")` 守卫 → **所有会话被静默跳过**。

**short_id 其实一直都在首包里**（实测 `cap_init_0.bin`）：
```
6 → 2043 → 1[i] → 4 → { 1, 2: 总消息数, 5: short_id, 6: conv_id }
```
45 个会话 **45/45 都有 short_id**（如 `7679817714411586091`）。

**根因**：存量会话是由 `recv_daemon` 的 WS 同步帧建的骨架
（`recv_daemon.py:195` 建会话时 `short_id` 传 None），
而 `capture_all` 的 short_id 补齐只走首包解析路径，**没有回写存量行**。

### 34.4 修复方向（若要打通路径 B）

1. **回写 short_id**：`capture_all` 产出 short_id 后，
   对已存在的 `dm_conversations` 行做 UPDATE（当前只在 INSERT 时写入）。
   —— 这是打通 B 的**唯一前置**，改动小。
2. **补 total_msgs**：同理，用于计算缺口、决定是否需要补全。
3. 之后即可按 §13.4 的风控参数分批补全。

### 34.5 关于图片 skey（与 §三十三 衔接）

- **新消息**：改 `recv_daemon._extract` 返回 skey 即可解密原图。
- **历史图片**：skey 只随**消息体**下发。首包不带（§33.2 证伪一，
  首包 493 个 douyinpic URL 全是表情包贴图 `lk3s=69c9632d`，
  与加密聊天图 `lk3s=9698d6d2` 不相交）。
  → **必须先走 cmd 301 拉完整消息体**，才有历史图的 skey。
  → 即：**先修 short_id（§34.4），历史图片才可能解密**。这是一个依赖链。

### 34.6 实测数据存档

| 指标 | 数值 |
|---|---|
| 首包会话数 | 45（45/45 有 short_id） |
| 首包总消息 | 各会话 1~21 条，总缺口仅 2 条（该账号历史已基本补齐） |
| 库中会话 | 236（short_id 全 NULL） |
| 库中消息 | 665 条，msg_type 全 text，extra 全空 |
| 含图链会话 | 27 个，共 87 条图链（全为 `lk3s=9698d6d2` 加密原图） |

### 34.7 教训

- **「代码已落地」不等于「链路能跑通」** —— cmd 301 代码齐全，
  但因上游 short_id 为 NULL 而**静默失效**（守卫直接跳过，无报错）。
  凡带 `if x:` 守卫的链路，必须验证守卫条件是否真能满足。
- **存量数据 ≠ 新数据**：新会话走 `capture_all` 有 short_id，
  存量走 recv_daemon 骨架没有 —— 补字段时要考虑存量回写。
- **依赖链要先理顺再动手**：历史图解密 → 需要 301 → 需要 short_id。
  直接改图片解密而跳过 short_id，会白做。

## 三十五、【推翻 §二十七】实机端到端证真：历史原图可解密（2026-09-01）

> **本节是 §二十七、§三十三、§三十四 的更正。凡冲突处以本节为准。**
> 本节全部结论来自隔离路径实机跑通 + 真图解码验证，非推断。

### 35.1 结论一句话

**抖音私信图片的原图一直都能拿到。** 走 cmd 301 拿 `resource_url.skey`，
AES-256-GCM 解密即得真原图。**实测 5/5 全部解密成功。**
§二十七「原图确认不可得」是**误判**，予以推翻。

### 35.2 端到端实测结果（账号「四川工伤张老师」，隔离路径）

```
1. DouyinAPI.get_message_by_init(auth)   -> 首包 1,301,157 字节
2. parse_init_protobuf(raw, my_uid)      -> 45 个会话，44 个有 short_id
3. 与库中有图会话求交集                  -> 27/27 全部命中
4. 每会话 _build_301_body + POST         -> 301 响应（含 skey）
5. 解析 field 8 -> resource_url.skey     -> 提取到 5 组配对
6. AESGCM(key).decrypt(...)              -> 原图
```

| # | 密文 | 解密后 | 格式 | 验证方式 |
|---|---|---|---|---|
| 1 | 254,694B | 254,666B | HEIC | `ftyp`+`heic` brand 合法 |
| 2 | 331,415B | 331,387B | **JPEG** | **PIL 解码通过 1206×2622** |
| 3 | 124,930B | 124,902B | HEIC | `ftyp`+`heic` brand 合法 |
| 4 | 169,099B | 169,071B | **JPEG** | **PIL 解码通过 1080×1920** |
| 5 | 292,663B | 292,635B | **JPEG** | **PIL 解码通过 1206×2622** |

产物存于 `C:\temp\dyautodm_test\probe_raw\DECRYPTED_*.jpg/.heic`。

**注意 HEIC 占比 40%（2/5）**：抖音私信图片相当比例是 HEIC，
浏览器不原生支持，**必须装 `pillow_heif` 转 JPEG 才能显示**（开源项目同做法）。

### 35.3 skey 的准确位置（按开源项目标注，实测确认）

```
301 响应 protobuf
  └─ 6 → 301 → 1[] (消息数组)
        └─ 8 = content_json  ← 明文 JSON 字符串
              └─ resource_url
                    ├─ skey                    ← 64 hex = 32 字节 = AES-256 密钥
                    ├─ origin_url_list[0]      ← 加密原图（优先）
                    ├─ large_url_list[0]
                    ├─ medium_url_list[0]
                    └─ thumb_url_list[0]
```

解密：
```python
cipher = fetch(origin_url)
key    = bytes.fromhex(skey)          # 32 字节
plain  = AESGCM(key).decrypt(cipher[:12], cipher[12:], None)   # IV = 前 12 字节
# 再按 magic bytes 判格式；HEIC 用 pillow_heif 转 JPEG
```

**不要用正则扫原始字节提取**（我第一版就这么干，失败）。
正确做法：`blackboxprotobuf` 解析 → 取 field 8 → `json.loads` → 按 key 取值。

### 35.4 【重要更正】之前几处判断错在哪

| 旧结论 | 错因 | 真相 |
|---|---|---|
| §33.2 证伪二「hook 截不到 skey」 | 用**错误账号**测 | 见 §35.5，与账号无关；skey 在 301 响应，不走 hook |
| §33.2 证伪三「首包 douyinpic 全是贴图」 | —— | **这条本身没错**，首包确实不带 skey。但不代表拿不到 —— 301 才带 |
| §33.3「历史图拿不到」 | 推论过度 | **推翻**。301 响应里 skey 6/6 会话全命中 |
| §34.3「short_id 全 NULL 阻塞」 | 误把数据库当唯一来源 | short_id 可从**首包现取**（44/45 有），不必依赖库 |
| §34.4「首包与有图会话交集 0」 | **账号搞错** | 见 §35.5 |

**核心教训**：§33.3 那句「历史消息怎么办？—— 拿不到」是从
「首包不带 skey」错误外推到「服务端不下发 skey」。
**正确做法是直接测 301 响应，而不是从首包推断。**

> **铁律**：看到「响应异常小/空」时，先排查**参数正确性**（账号、conv_id、

## 三十六、隔离路径 `DY_APP_ROOT` + skey 落库 UPSERT 陷阱（2026-09-01 实测）

> 本节记录两项基础改动：① 让源码态能干净地指向隔离测试路径；
> ② skey 落库时踩到的 SQLite 陷阱。二者都是后续所有隔离验证的前提。

### 36.1 问题：源码态无法使用隔离路径资源

`backend/vbrowser.py::app_root()` 源码态用 `__file__` 硬算根目录：

```python
# 本文件: <root>/backend/vbrowser.py -> 向上两级 = <root>
return os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
```

**9 个模块依赖它**（`accounts.py` / `database.py` / `recv_daemon.py` /
`browser_daemon.py` / `login_capture.py` / `auth_helper.py` / `core/auto_dm.py` /
`vbrowser.py` 自身）。后果：

- 源码态跑测试，**账号 .env / data / vb_chromium 全部指向源码仓库**
- 隔离路径 `C:\temp\dyautodm_test` 的资源**用不上**
- 导致 08 §35.5 的「账号混淆」错误，以及为了跑通而**把隔离库复制回源码仓库**
  的危险操作（违反隔离铁律，曾污染过开发库）

### 36.2 解决方案：`DY_APP_ROOT` 环境变量 override

在 `app_root()` 最前面加**最高优先级**分支：

```python

        return os.path.abspath(_ov)

```

**不设时行为与之前完全一致**（已用 19 个回归测试验证）。

用法：

```bash

set PYTHONPATH=backend;.

```

实测生效（`DY_APP_ROOT=C:\temp\dyautodm_test`）：

| 检查项 | 值 |
|---|---|
| `app_root()` | `C:\temp\dyautodm_test` |
| `accounts._ACCOUNTS_DIR` | `C:\temp\dyautodm_test\auto_dm\accounts` |
| 账号 .env | ✅ 找到（四川工伤张老师） |
| `database._db_path()` | `C:\temp\dyautodm_test\data\dyautodm.db` |
| vb_chromium | ✅ 存在 |

> **铁律（新增）**：源码态做任何涉及账号/数据库/浏览器的验证，
> **必须先设 `DY_APP_ROOT` 指向隔离路径**，禁止把隔离库复制回源码仓库。

### 36.3 陷阱一：`INSERT OR IGNORE` 导致 skey 写不进历史行

现象：`capture_all` 明明解析到 skey（写库 45 会话 / 647 消息），
但 `SELECT ... WHERE extra LIKE '%skey%'` 返回 **0**。

**根因**：`dm_messages` 有两个唯一索引：

```sql
uniq_dmmsg          ON dm_messages(account, conv_id, msg_id) WHERE msg_id IS NOT NULL
uniq_dmmsg_fallback ON dm_messages(account, conv_id, role, text, CAST(ts AS ...))
```

历史图片消息**早已入库**（extra 是旧的 `{}`），
`INSERT OR IGNORE` 遇唯一索引冲突 → **静默跳过**，旧行永远拿不到 skey。
（实测：665 条 → 666 条，只新增 1 条，其余 60 条图片全被跳过。）

### 36.4 陷阱二：`ON CONFLICT` 匹配不上部分索引

第一反应改用 UPSERT：

```sql
INSERT INTO dm_messages(...) VALUES(...)
ON CONFLICT(account,conv_id,msg_id) DO UPDATE SET extra=excluded.extra
```

**报错**：
```
OperationalError: ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint
```

**根因**：`uniq_dmmsg` 是**部分索引**（带 `WHERE msg_id IS NOT NULL`），
SQLite 的 `ON CONFLICT(...)` 无法匹配部分索引的冲突目标。

### 36.5 正解：UPDATE 优先 + 幂等，无影响行再 INSERT

```python
_cur = conn.execute(
    "UPDATE dm_messages SET extra=? "
    "WHERE account=? AND conv_id=? AND msg_id=? "
    "  AND (extra IS NULL OR extra='' OR extra NOT LIKE '%skey%')",
    (_extra, name, cid, m.get("msg_id")),
)
if (_cur.rowcount or 0) == 0:
    conn.execute("INSERT OR IGNORE INTO dm_messages(...) VALUES(...)", (...))
```

要点：
- 只补写**尚未有 skey** 的行（`extra NOT LIKE '%skey%'`）→ 重复跑幂等，不覆盖正确值
- 只改 `extra`，不动 `text`/`role`/`ts` → 不影响既有展示
- `UPDATE` 优先 + `INSERT` 兜底，绕开部分索引限制

### 36.6 端到端验证结果（隔离路径，干净无复制）

```

跑 capture_all('四川工伤张老师', with_browser=False)
  -> 首包 1,301,157B，45 会话（含消息 42）
```

## 三十七、「更新会话」220s → 17s 性能优化（2026-09-01 实测）

> 用户反馈「怎么现在更新会话又要 220 秒了！」。
> 按 performance-tradeoff-analysis 铁律**先测量再优化**，实测定位并修复。

### 37.1 测量：真实时间线（日志 run_20260901_210924.log）

```
21:17:12  更新会话开始
21:17:28  BCC /cookie 刷新成功              16s
21:17:30  首包 1301157 bytes                2s
21:17:33  首包解析 45 会话                  3s
21:17:33  301 补全开始（并发 4）
21:17:55  301 补全 20 个会话完毕            22s
21:17:55  ↓ 空白 176 秒 ↓
21:20:51  经 BCC 截到昵称 277 个           176s  ← 瓶颈（80%）
21:20:52  写库完成
21:20:52  更新会话完成 耗时 219.1s
```

| 阶段 | 耗时 | 占比 |
|---|---|---|
| cookie + 首包 + 解析 | 21s | 10% |
| 301 长会话补全（20 个） | 22s | 10% |
| **BCC 昵称捕获** | **176s** | **80%** |

与 §二十六（179s，BCC 占 90%）结论一致 —— **BCC 昵称捕获始终是瓶颈**。

### 37.2 根因：预热白做了（缓存缺失）

BCC 启动后 `_prewarm` 线程会后台跑一次完整捕获
（日志「昵称缓存预热完成：277 个」，耗时 163s，滚动 30 轮）。

**但 `capture_all` 每次都重新调 BCC `/capture_userinfo` 再跑一遍滚动** ——
两处都没有任何结果缓存。预热的 163s 白花，用户点「更新会话」时又付一遍。

> 这是典型的「优化做了一半」：§二十六 加了预热线程，
> 却没让消费方复用预热结果，所以用户侧耗时几乎没变。

### 37.3 修复（三层）

**① BCC 侧进程内缓存**（`browser_daemon.py::capture_userinfo_map`）

```python
# 在 _lock 外先查缓存，避免不必要的串行等待
if _ttl > 0 and self._userinfo_cache:
    _ts, _data = self._userinfo_cache
    if _data and (time.time() - _ts) < _ttl:
        return _data          # 命中直接返回，跳过 163s 滚动
```
成功捕获后写入 `self._userinfo_cache = (time.time(), cap)`。
TTL 由 `DY_USERINFO_CACHE_SEC` 控制（**默认 600s**，设 0 = 关闭）。

**② backend 侧缓存**（`conversation_capture.py::capture_userinfo_via_browser`）
同样加 TTL 缓存，双重保险（backend 重启后 BCC 缓存仍在）。

**③ 滚动点击去重**（`browser_daemon.py`）

原实现每轮把可见的 12 项**全部重点一遍**（含前几轮已点过的），
但重复点击不会触发新的 `im/user/info`（前端已缓存），纯浪费。
改为用会话文本做 key 去重，只点新会话，且**只在真点了才付 400ms 等待**。

**④ 可观测性**（性能 skill Rule 5）
每轮打印 `[bcc] 滚动轮次 N: 新点击=X 累计昵称=Y 用时=Zs`，
让 176s 黑盒变成可定位的明细 —— 本次优化正是靠它发现「每轮 4.9s」的构成。

### 37.4 优化效果（实测 4 次连续调用）

| 次序 | 场景 | 耗时 |
|---|---|---|
| 第 1 次 | 冷启动（BCC 正在刷新 cookie / profile 占用） | 144.8s |
| 第 2 次 | 缓存已热 | **17.4s** |
| 第 3 次 | 缓存已热 | **16.8s** |
| 第 4 次 | 缓存已热 | **17.8s** |

数据一致性：4 次均为 45 会话 / 647 消息，**无数据损失**。

**220s → 17s（提升 12.7 倍）**

### 37.5 第 1 次仍要 144.8s 的原因（已知，非本次引入）

时间线：
```
21:46:22  301 补全第 1 个会话完成（50 条）
21:48:29  第 2 批完成          ← 中间卡 127s
21:48:29~41  其余 18 个完成（12s）
```

首个 301 请求卡了 127s，之后 18 个只用 12s。
原因：**冷启动时 BCC 正在做 `/cookie` 刷新（21:46:16）且 profile 被占用**，
301 请求与其串行等待。属一次性冷启动成本，不影响后续调用。

（若要继续优化，方向是在 backend 侧检测 BCC 忙碌时延迟发起 301，
但收益仅限首次，优先级低。）

### 37.6 滚动耗时构成（靠新加的计时日志测得）

| 项 | 每轮耗时 | 占比 |
|---|---|---|
| 点击等待（7 项 × 400ms） | 2.8s | 57% |
| 滚动后等待渲染 | 1.2s | 25% |
| evaluate + 点击开销 | 0.9s | 18% |
| **合计** | **~4.9s** | |

30 轮 ≈ 150s。每轮稳定新增 7 个昵称（去重生效后，此前是重复点 12 个）。

> 若还想压缩冷启动：把点击间隔 400ms → 150ms 可省约 52s（30 轮）。
> 但因有缓存，用户侧几乎不再付这个成本，暂不改动（保守优先）。

```python
        if c.get("short_id")
        and _db_counts.get(str(c.get("conversation_id")), 0)
            < max(len(c.get("messages", [])), 1)]
```

| 场景 | 库内 | 首包 | 判断 | 结果 |
|---|---|---|---|---|
| 长会话未补 | 0 | 20 | 0 < 20 | 补 ✅ |
| 长会话已补 1 页 | 50 | 20 | 50 < 20 = False | 跳 ✅ |
| 短会话未补 | 0 | 5 | 0 < 5 | 补 ✅ |
| 短会话已补 | 5 | 5 | 5 < 5 = False | 跳 ✅ |
| 边界（30 条/1 页中途） | 30 | 20 | 30 < 20 = False | 跳 ⚠ |

第 5 种边界理论上**有 20 条没补全**，但 301 一次 50 条意味着
库内 30 条说明此会话**就 30 条**（短会话），不是中途状态。
若真>50 中途（罕见），下一次仍会触发补全到 ≥50。

```python
    need = [c for c in convs
            if c.get("short_id")
            and _db_counts.get(str(c.get("conversation_id")), 0)
                < max(len(c.get("messages", [])), 1)]
```

## 三十九、冷启动实测真相 + 误报纠正（2026-09-02）

> 用户质疑「你确定这是清库后的冷启动吗，我怎么看到前端一直运作在页面上」。
> 核实后确认：**我的 37.5s「冷启动」是误报**。本节记录真相与教训。

### 39.1 误报经过

我声称的「清库后冷启动」时间线：
```
15:33  清空库（输出「清空 dm_conversations: 236 行」）
16:12  第 1 次刷新 37.5s  ← 我称之为「冷启动」
16:13  第 2 次 14.9s / 第 3 次 14.5s
```

**核查发现的三处错误**：

| 核查项 | 我以为 | 实际 |
|---|---|---|
| 清空后剩余行数 | 0（看到「清空 226 行」以为是剩余） | **226 行仍在** |
| DELETE 输出含义 | 「剩余行数」 | **「DELETE 影响的行数」**，不是剩余 |
| db mtime | 我清空的时间（16:13） | **15:57**（BCC 预热写的） |

（`dm_messages` 表无 `created_at` 列，直接查会报
`no such column: created_at`，需用别的字段核对，见 §39.5）

### 39.2 真相：BCC 预热会自己写库

```
17:19  我清空库 → conv=0, msg=0（这次核验了剩余行数，真清空）
17:24  启动 DYAutoDM_v2_0.33.1.exe
17:27  BCC 预热完成：274 个
17:27  db mtime = 17:27:23 → conv=221, msg=637   ← 预热写回的！
17:30  触发刷新 → 14.6s
```

**关键结论：清空库后不等 BCC 预热完就测「冷启动」是不可能的。**
BCC 预热期间（30 轮滚动 + 274 个会话列表）就会通过
recv_daemon WS 骨架 + backend 首包把库写回 600+ 条。

> 所以「清库 → 测冷启动刷新」这个测试设计本身就有缺陷：
> 预热阶段已经把骨架灌满，触发刷新时走的是 UPDATE 而非 INSERT。

### 39.3 真实数据（run_20260902_170916.log）

```
17:30:50  首包 拉取=1.0s 解析=2.5s（1,302,796B -> 45 会话）  3.5s
17:30:50  长会话补全：20 个会话（并发 4，间隔 1.5s）
17:31:01  更新会话完成：会话 45（消息 549），耗时 14.6s
17:31:08  第 2 次 14.3s
17:31:25  第 3 次 16.1s
```

| 场景 | 实测耗时 | 说明 |
|---|---|---|
| BCC 已预热完 → 刷新 | **14.6s** | 库已有 637 条，走 UPDATE |
| 稳态第 2 次 | 14.3s | |
| 稳态第 3 次 | 16.1s | |

**数据一致性**：3 次均为 45 会话 / 549 消息，无损失。

### 39.4 那 37.5s 到底是什么

不是冷启动，是**双写**：
- BCC 预热把 637 条写回 `dm_messages`
- 触发刷新又写 549 条（UPDATE 已有行 + INSERT 新增）
- 且 `dm_conversations` 里 226 个**骨架空行**未级联删除，
  写库时要先 UPDATE 这些行 —— 这才是 25s「写库」的来源

**修正后的认识**：库空不空对刷新耗时影响很小，
因为 BCC 预热已经把骨架写满；真实瓶颈是 **301 补全 20 个会话 ~11s**。

### 39.5 可复用的核验方法

测「是否真清空」必须查**剩余行数**，不能看 DELETE 输出：

```python
c = sqlite3.connect(src)
for t in ['dm_messages', 'dm_conversations']:
    before = c.execute(f'SELECT COUNT(*) FROM {t}').fetchone()[0]
    c.execute(f'DELETE FROM {t}')
    after = c.execute(f'SELECT COUNT(*) FROM {t}').fetchone()[0]
    print(f'{t}: 删除前={before} 删除后立即查={after}')  # after 必须是 0
c.commit()
c.execute('VACUUM')
```

同时用 **db mtime** 交叉验证 —— 如果 mtime 早于你的清空时间，
说明清空后又有进程写库了（本项目即 BCC 预热）。

注意 `dm_messages` **无 `created_at` 列**（本轮踩坑），
核对时间要用 db 文件 mtime，或表内其他时间字段。

### 39.6 BCC 预热为什么 164s（用户原问）

实测（browser_daemon 日志，靠 §37.3④ 加的每轮计时日志）：

```
滚动轮次 24: 新点击=7 累计昵称=219 用时=119.5s
滚动轮次 29: 新点击=7 累计昵称=264 用时=144.0s
昵称捕获完成：277 个，总耗时 164.0s
```

| 指标 | 数值 |
|---|---|
| 滚动轮次 | **30 轮** |
| 每轮耗时 | **4.9s** |
| 每轮新增昵称 | 7 个 |
| 总计 | 277 个 / 164s |

**为什么必须 30 轮**：277 个会话 ÷ 每屏 7 个 ≈ 30 屏。
抖音**只为真正滚进可视区**的会话发 `im/user/info`，
不滚到底就截不全（08 §三·乙 铁律：必须滚到底 + 点全部）。

**每轮 4.9s 构成**：

| 动作 | 耗时 | 占比 |
|---|---|---|
| 点击等待（7 项 × 400ms） | 2.8s | 57% |
| 滚动后等渲染 | 1.2s | 25% |
| evaluate + 点击开销 | 0.9s | 18% |

**可优化空间**（收益有限，且预热是后台的，不阻塞用户点「更新会话」）：
- 点击间隔 400ms → 150ms：省约 52s（低风险）
- 滚动等待 1200ms → 800ms：省约 12s（中风险，可能漏截）
- 多线程并发点击：**禁止**（违反单 profile 铁律，触发风控）

### 39.7 教训

- **「清空了」必须核验剩余行数 + 文件 mtime，不能信命令回显。**
  「DELETE 影响 226 行」≠「剩余 0 行」，我被这个字面意思骗了一整轮。
- **测试设计要考虑副作用。** 「清库测冷启动」在本项目不可行 ——
  BCC 预热会写库。设计测试前先问「这个动作本身会不会改变被测状态」。
- **用户质疑时先核查，不要辩解。** 用户一句
  「我怎么看到前端一直运作在页面上」直接戳穿了我的误报 ——
  用户对运行时状态的直觉往往比我的日志推断准。
- **进程存活状态要确认。** 本次误报的另一个原因是
  我以为「重启了程序」，实际老进程（15:09 启动）一直活着，
  新启动的 Popen 无效，所有测试都打在老进程上。
  启动前应先 `tasklist` 确认无残留。
- **性能数字必须标注场景。** 「37.5s」和「14.6s」都是真的，
  但场景不同（双写 UPDATE vs 稳态）。报性能数字必须带上「什么状态」。

## 四十、加密原图解密与前端真实渲染（2026-09-03 实机落地）

> 用户原话诉求：「小图片本地大图片图床」「解决前端目前没有真实显示私信内容的原图」。

### 40.1 问题定性：三层断裂（不是"抖音加密拿不到"，是链路没接通）

2026-09-01 已证真「图片 AES-256-GCM 可解密」（§三十五），但**前端依然看不到原图**。
实测逐层拆解，断裂在三处：

| 层 | 状态 | 证据 |
|---|---|---|
| ① 密钥入库 | ✅ 已落地(2026-09-01) | `dm_messages.extra` = `{"skey":..., "origin_url":...}`，`conversation_capture.parse_conversation_301` L744-757 提取、L1169-1195 UPDATE 优先落库；`recv_daemon._extract` L601-607 同样写 extra |
| ② **后端解密** | ❌ **无人调用** | `_extract_image_secret` 只**取** skey/origin_url，**不解密**；`requirements.txt` 甚至没写 `cryptography`（代码里 `AESGCM` 是悬空引用） |
| ③ **接口透出** | ❌ **没读 extra** | `api/messages.py::get_conversation` 原 SQL `SELECT role,text,msg_type,ts`，**完全没 SELECT extra** |
| ④ **前端消费** | ❌ 0 行 | `messages.tsx::parseMedia` 只解析 `[图片]/[原图]` 双行文本，弹层写死「该图为抖音私有加密格式」+ 跳 `douyin.com/chat` |

**结论（纠正 2026-08-31 旧结论）**：
旧注释「resource_url 远程链是私有加密，浏览器加载失败（3/3 error，0×0）」
**在"前端裸拉远程链"场景是对的，但不是死路** ——
远程链确实加密，但**密钥就在同一条消息的 extra 里**，后端代为解密即可。
原注释导出的「只能去抖音网页看原图」是**错误结论**，已推翻。

### 40.3 落地实现（用户定调：小图本地 / 大图图床）

新增 `backend/auto_dm/origin_image_resolver.py`（核心职责）：


### 40.8 本地原图 TTL 清理（2026-09-03，用户追加需求）

本地原图目录（`data/origin_images/`）随会话增长膨胀（实测单张 170~410KB），
用户要求加 **TTL 清理**。落地两条回收规则：

| 规则 | 触发 | 默认值 | 说明 |
|---|---|---|---|
| ① 过期 | 文件 mtime 距今 > TTL | **30 天**（`ORIGIN_IMAGE_TTL_DAYS` / `settings.origin_image_ttl_days`；0=永不过期） | mtime 由 `touch_local()` 在**每次被访问时刷新** → "最近看过"的图不删 |
| ② 超容 | 目录总字节 > 上限 | **2 GB**（`ORIGIN_IMAGE_MAX_MB` / `settings.origin_image_max_mb`；0=不限） | 按 mtime 升序（最旧的优先）删到限额内 |

**判龄用 mtime 而非内存状态**：`_origin_cache_dir()` 随 app_root 变化，
进程重启后内存缓存已空，只有 mtime 是跨进程可靠的年龄依据。

**清理触发点（三层）**：
1. backend 启动 60s 后 `sweep_background()`（延迟避开启动高峰，不阻塞）
2. `resolve()` 每次写新图后顺手 `sweep(force=False)` —— **1 小时节流**（`_SWEEP_MIN_INTERVAL`），
   实际不常扫盘，但能保证 backend 长跑不重启也持续回收
3. 手动 `POST /api/messages/origin_image/sweep`（调试用）

**关键实现点**：
- `touch_local(filename)`：`serve_origin_image` 每次命中调用 `os.utime` 刷新 mtime，
  使"最近看过"的图永不过期（前端每 5s 轮询若重复看图会持续保活）
- `resolve()` 的 `max_age_sec` 默认取 `_ttl_seconds()`，与磁盘 TTL **一致** ——
  否则会出现「内存缓存说命中、但磁盘文件已被 sweep 删」→ 前端 404
- 删除用 `Path.unlink()` + try/except 吞权限错误（Windows 上文件被 FileResponse
  占有时删除失败，下轮 sweep 会再试）

**实机验证**（`C:\temp\dyautodm_test` 部署态）：
- 5 张真图（30 天内）sweep 后 `removed:0` 保留 ✓
- 造 40 天前的假文件 → sweep `removed:1` ✓
- 图片访问 HTTP 200 + touch 生效 ✓
- `ttl=0` 单测 = 永不过期 ✓、超容单测触发删除 ✓

**⚠️ 路径坑（实机踩到）**：backend 部署态的缓存目录是 `<app_root>/data/origin_images/`
= `C:\temp\dyautodm_test\data\origin_images\`；源码仓库 `DYAutoDM_v2/data/origin_images/`
是**源码态**残留。测 TTL 时要往**正在运行的 backend 实际目录**造文件，
否则 sweep 删的是空目录（假文件放错目录时 remaining=5 不变即此因）。

### 22.2 base64 图片渲染失败（灰圈占位）根因：URL 编码污染

**现象**：私信图片消息显示为**灰色圆圈占位**，图片完全无法渲染。

**根因**：数据库 text 列里 `[图片] data:image/webp;base64,...` 的 base64 段**混入 URL 编码**
（实测尾部粘着 `%2F`→`/`、`%2B`→`+`、`%3D`→`=` 等编码字符）。前端 `sanitizeDataUri()`
原来直接 `replace(/[^A-Za-z0-9+/=_-]/g, "")` 剔除非法字符 → **`%` 被删掉，残留 `2F`/`2B`**
不是合法 base64 → 图片解码失败 → 灰圈。

**修复**（`frontend/src/pages/messages.tsx` `sanitizeDataUri`）：
```ts
let rest = u.slice(comma + 1);
try { rest = decodeURIComponent(rest); } catch { /* 保持原样 */ }
rest = rest.replace(/[^A-Za-z0-9+/=_-]/g, "");
return head + rest;
```
**铁律**：base64 清洗前必须先 `decodeURIComponent`，否则删 `%` 留下十六进制残渣。

### 24.10 BCC 风控对齐：「无头」改真有头+窗口移屏外（2026-09-06 实测闭环）

**根因实证**：Chromium headless 模式被抖音风控识别。同一 profile 下，
有头（双击打开的指纹浏览器）登录态正常，BCC headless 容器却触发
step-up 重验证降级为半登录态（页面显示「一键登录」）——环境跳变是诱因。

**对照实验**（小助理 profile）：伪装模式与纯有头均半登录 → 确认 session
服务端失效与伪装无关；用户重新扫码后，伪装模式复测 **完全正常**
（conv=12，rel=False，14:31）。

**实现**（vbrowser.py，launch_async/launch_sync 双路径统一）：
```
headless=True 请求 → headless=False（恒有头）
  + --window-position=-32000,-32000   ← 窗口移出屏幕
  + --window-size=1440,900            ← 常规桌面尺寸
```
对抖音 100% 有头特征（与用户双击打开完全一致），对用户等效无头。
**BCC = 双击打开的指纹浏览器（无头状）**：同内核/同 profile/同链路，
仅窗口不可见。日志标记「无头请求已转为 真有头+窗口移屏外」。

⚠️ 注意：`--window-position` 在 Windows 下部分环境可能被显示器布局
覆盖；若窗口意外可见，可在 BCC 启动后用 CDP `Browser.setWindowBounds`
二次纠偏。

**副作用修复（2026-09-06 用户报告：扫码窗口跳到桌面外，无法重新扫码）**：
持久化 profile 会把窗口位置写进 Preferences——伪装模式跑过一次后，
下一次【可见启动】（扫码登录 / 查看模式）窗口从 -32000 屏外位置恢复，
二维码落在桌面外根本扫不了。修复（vbrowser.py）：
- 新增 `_ensure_window_visible()` / `_ensure_window_visible_sync()`：
  CDP `Browser.getWindowForTarget` 检测窗口坐标，|coord| > 30000（只命中
  ±32000 伪装量级，不误伤多显示器负坐标如 -1920）即 setWindowBounds
  归位到 (80,80)，失败仅告警不阻塞。
- 接入点：`launch_async`（headless=False 且非伪装）、`launch_sync`
  （非伪装）、`open_douyin_home`（恒调用）。
- **关键区分**：用 `_disguise` 标志位区分「伪装启动」与「真可见启动」
  ——伪装分支里 headless 被置 False，若只判 `if not headless` 会把
  伪装窗口也归位，伪装彻底失效（第一版补丁就犯过，已修）。
- 伪装模式行为不变：窗口仍留在屏外，风控对齐不受影响。

### 24.13 keepalive 熔断：防「每 5 分钟重启浏览器」风控恶性循环（2026-09-06 P0）

**实测事故**（16:03-16:13 日志）：页面半登录 → keepalive 触发 scan_login
→ **整个浏览器重启** → 仍半登录（session 服务端已死，自动登录救不回）
→ 5 分钟后又来，连续 3 轮。每 5 分钟一次完整浏览器重启 = 极强风控信号。
**修复**：scan_login 连续失败 **2 次即熔断 30 分钟**——期间页面级检查
失败只记 warning 告警（提示"请在指纹浏览器重新扫码"），**绝不自动重启
浏览器**；页面恢复（conv>0）自动清零。三处触发点（uid 漂移/页面失效/
uid 失效）统一受熔断保护。

### 24.14 BCC 懒加载架构（2026-09-06 用户架构决策落地）

**决策**：启动**不再拉起 BCC**。历史理由（昵称自动捕获）08-29 已废，
BCC 消费者（WP 发送/昵称捕获/回声轮询）全部按需或可延后——启动时不该
为「可能不用」的功能预付 15s 成本与风控暴露。

**实现**：
- `main.py`：BCC 默认不随启动拉起（`DY_BCC_ON_START=1` 可恢复）；

- `accounts.ensure_bcc(name)`：懒加载辅助（端口双检锁/防重复拉起/等就绪）
- `api/messages.py _bcc_url`：调 BCC 前自动 ensure_bcc（WP 发送即触发）；
  更新会话路径本就走 `ensure_daemons_for`（自带拉起），无需改

**headless 模式配置**（复盘修正归因）：半登录态根因是 **session 生命周期**
（强杀进程/握手时序）而非 headless 模式本身——00:42-00:54 headless 一直
正常即为反例。`DY_BCC_HEADLESS_MODE=disguise(默认)|native`：
- `disguise` = 真有头+窗口移屏外（特征与双击打开一致，保险策略）
- `native` = 纯 Playwright headless（省资源；保留供回退）

### 24.15 启动冷静期 + 系统占位提示过滤（2026-09-06）

**BCC 启动冷静期**（`accounts.ensure_bcc`）：进程启动后 **30s 内禁止懒加载
BCC**（`DY_BCC_LAZY_DELAY` 可调秒数）。防御「启动时 BCC 快闪唤醒」——启动

路径）若走到 ensure_bcc，冷静期内只读不拉进程，30s 后才接受懒加载。设计
依据：启动期不该让任何自动重捕打断启动节奏，重捕始终应该由用户显式触发。

发送一条文字消息。请礼貌发言，自觉遵守{{0}}」。sender 来自陌生人，role=them
被当真实消息入库污染聊天记录。识别：文本含"对方回复你或互关之前"/"可发送
一条文字消息"/"请礼貌发言"/"自觉遵守"四选一即中，直接返回 None 不入库。

**问题 A — 多进程写竞争**：`database.get_db` 只有 WAL（解决读写不互斥），
**没有 `busy_timeout`**。而 backend + N×recv_daemon + BCC 会并发写同一个
db 文件 → 并发写直接抛 `database is locked`（默认 5s 且不重试）。
**修复**：`connect(timeout=30)` + `PRAGMA busy_timeout=30000`。

**问题 B — 双通道重复落库（唯一索引建了却没生效）**：`dm_messages` 早有
`uniq_dmmsg(account,conv_id,msg_id)` 与 `uniq_dmmsg_fallback(...)` 两个
唯一索引，但：
- `recv_daemon.add_message` / `wp_recv` / database JSON 迁移 用的是**裸
  INSERT**（绕过去重，冲突时抛 IntegrityError 而非静默去重）
- WP 通道只把 `client_msg_id` 塞进 extra JSON，**不写 msg_id 列**
  → `uniq_dmmsg` 完全管不到它；而 WS 回声与 WP 轮询的 ts 有毫秒级
  差异 → fallback 索引也失效 → **同一条消息必然重复入库**

**修复**：三处裸 INSERT 全改 `INSERT OR IGNORE` 且写入 msg_id 列
（WS 侧 `add_message` 新增 msg_id 参数，取 `msg.msg_id`；WP 侧取
`client_msg_id`）。现在 WS / WP 双通道同一条消息命中同一唯一索引真正去重。

## 三十八、v0.43.11：跨调用窗口租约接线 —— 昵称「抓到但没入库」的两次进程分裂（2026-09-14）

> 本节承接 §三十一（DOM 方案）与 §三十七（预热缓存）。**症状相同（前端只显示数字），
> 但根因完全不在捕获侧**，而在 **backend ↔ BCC 两个进程之间的租约协商**。
> 逐节对照的价值：§三十一 修的是「抓到没有」，本节修的是「抓到了为什么传不回来」。

### 一、症状与关键矛盾

- 用户：「更新会话 hook 失败、捕获入库失败、前端只显示数字」
- 实测：**BCC 进程内抓到 37 个昵称，backend 收到 0 个**，事件相隔 7 秒。

这一矛盾点是本节全部定位工作的锚点 —— 一旦成立，
`DOM 选择器 / hook 注入 / 滚动轮次 / 无头有头` 全部被排除，
唯一嫌疑落在「BCC → backend 的返回通道」。

### 二、链路（源头 → 传播 → 终端）

```
源头① conversation_capture.capture_all
        ensure_browser(purpose=AUTO) → 取得租约 lease_id=83a780e866e2（gate:auto / prio=1）
        ✗ 该 lease_id 只存局部变量 _g，**从未向下传**
源头② capture_userinfo_via_browser(name)          ← 签名无 account、无 lease
源头③ POST /capture_userinfo  {"wait": 15}        ← 请求体无 lease_id
源头④ BCC _exec: _is_reentry = bool(lease_id and …) ← lease_id="" ⇒ 判为并发冲突
传播   _lease_acquire(bcc-internal, prio=2) 被拒 → ContainerBusy
终端   BCC-047 → BCC-030 → 昵称 0 个 → peer_name=peer_id → 前端显示数字
```

**性质：自我死锁。** 同一进程 5 秒前给自己拿的租约，把自己 5 秒后的请求挡在门外。

### 三、为什么之前一直没发现（三层都「看着对」）

## 三十九、v0.43.11 方案 A+B：DOM 昵称 ↔ peer_uid 的精确关联（2026-09-14 实机确证）

### 二、方案 A（文本桥）—— 把 DOM 昵称精确接到 peer_uid

**核心洞察**：两端虽无共同 id，却有**共同的自然键 = 最后一条消息的正文**：
- 首包每个会话自带 `messages`（权威、天然带 uid 归属）
- DOM 每项的 `desc`（`[class*=ConversationItemDescleft]`）**就是该会话最后一条消息**的预览

实现（`conversation_capture.capture_all`）：
1. `CAP_DOM_SWEEP_JS` 新增抓 `desc`（昵称/头像/desc 三项）
2. 用首包消息文本建 `_text_to_uids` 索引（`text[:80] → {uid}`）
3. DOM 项的 desc 与之匹配（先精确 `desc[:80]`，再双向包含前 24 字兜底截断）
4. **仅当候选 uid 唯一**时写入 `_userinfo_by_uid[uid] = {nickname, avatar}`；
   歧义（≥2 候选）**显式计数并放弃**

**为什么必须"宁可不显示"**：群发欢迎语场景下同一条文本属于 N 个会话，
任何按顺序/位置的猜测都会张冠李戴 —— 这正是本轮 80 条「傲雪」事故的成因。
日志：`文本桥（方案A）：唯一关联昵称 N 个，歧义放弃 M 个，未匹配 K 个`。

**实测覆盖**（本轮探针，11 项 DOM）：唯一命中 1 项、被系统提示覆盖 9 项、过滤 1 项。
⇒ 桥的**上限受限于「DOM desc 是否为真实消息」**：未互关会话被
「对方回复你或互关之前…」占位覆盖 → 分不清对端 → 按设计放弃。

### 三、方案 B（WS 增强）—— 实际落地形态与原设想不同

| | 原设想 | 实际落地 |
|---|---|---|
| 昵称来源 | WS `sender_nickname` | **实测恒 None**，不能用 |
| peer_uid | `sender` | **只认 `conv_id`**（`0:1:uid_a:uid_b` 排除本号，100% 可靠） |
| 效果 | 回填昵称 | 昵称取不到就**留空**（绝不写裸数字 UID） |

改动（`recv_daemon._handle`）：
1. `_real_peer` 从 conv_id 推导（排除本号），不再 `peer_id=sender`
2. `peer_name = sender_nickname`（拿不到就 `None`），删除 `or sender` 兜底
3. 该行日志 `INFO → debug`（实测单日 564 行、15 天数万行刷屏）

### 四、新增铁律

1. **两端无共同 id 时，禁止任何「按顺序/位置」的对齐**——懒加载 + 新消息置顶
   必然错位。要么找自然键（文本/时间戳指纹），要么放弃。
2. **关联不到就留空，绝不猜**。展示层看到数字 UID 是可接受的降级；
   看到**别人的昵称**是数据污染，代价高得多（用户会据此发错消息）。
3. **`peer_id` 只从 `conv_id` 推导**（`0:1:uid_a:uid_b`），绝不用 `sender`
   —— `sender` 在 role=me 时就是本号。
4. **循环变量绝不在循环外使用**：`for _c in convs:` 之后的 `_c` 恒为最后一个元素。
   本轮 80 条「傲雪」即此（`convs.index(_c)` → 恒等于 len-1）。
   教训：`_` 前缀的临时变量同样会泄漏，静态检查（grep 循环外引用）比直觉可靠。
