## 一、核心结论

**架构未崩塌，但出现 5 类「设计与代码偏离」，其中 3 类属用户铁律直接违规。**

| 类别 | 数量 | 最高级别 |
|---|---|---|
| 统一入口分裂（铁律：杜绝环境分叉） | 3 项 | **P0** |
| 分层依赖逆行（铁律：解耦） | 3 项 | P1 |
| 大组件/大文件（铁律：禁止大组件） | 12 项 | P1 |
| 文档与实际漂移 | 6 项 | P2 |
| 环境隔离破坏（铁律：四目录物理隔离） | 3 项 | P1 |

**一句话**：中期（09-13 后）为「全解除」分支快速推进，引入了**架构性妥协**——浏览器内核双栈、sidecar 双入口、风控铁律双标准；这些是**主动决策而非事故**，但**没有任何一处形成 ADR 或契约文档**，后人无从判断哪条是现行有效设计。

## 二、P0 级：统一入口分裂（违反「统一调度，杜绝环境分叉」铁律）

### P0-1　存在**两个** `_spawn_sidecar`，行为不一致

| 位置 | 进程组标志 | 注册 pid | 行号 |
|---|---|---|---|
| `backend/main.py:144` | `CREATE_NEW_PROCESS_GROUP` | `_dreg.register()` | 144–174 |
| `backend/auto_dm/daemon_launcher.py:81` | `CREATE_NO_WINDOW` | `_dreg.register()`（**带 None 兜底判断**） | 81–105 |

**偏离**：同一语义（spawn sidecar）两处实现，**进程组语义相反**：
- `CREATE_NEW_PROCESS_GROUP` → 子进程不受父 Ctrl 事件影响，但**不能**用 `CREATE_NO_WINDOW`
- `CREATE_NO_WINDOW` → 隐藏窗口，但**共享**父进程组

引伸后果：`main.py` 路径拉起的 sidecar 与 `daemon_launcher` 路径拉起的 sidecar，**Ctrl+C / 控制台关闭时的存活行为不同**。这正是用户 2026-09-12 亲历的「残留 9 小时、占着 12687/12726 端口」事故的**同一类根因**（`daemon_registry.py` 文件头明文记录了该事故）。

**设计契约应为**：spawn 是**单点能力**，必须收敛为一个函数（唯一入口），所有调用方透传参数而非各自实现。

### P0-2　sidecar 生命周期由**双主体**管理，边界未定义

| 主体 | 实现 | 职责 |
|---|---|---|
| Rust `SidecarManager` | `src-tauri/src/sidecar.rs`（458 行，7 个 fn） | `start_backend` / `start_browser_daemon` / `start_recv_daemon` / `kill_tree` |
| Python `daemon_registry` | `backend/daemon_registry.py`（115 行） | `register` / `unregister` / `kill_all` |

`lib.rs` 注册 **9 个 Tauri 命令**（`backend_status`/`start_backend`/`stop_backend`/`start_browser_daemon`/`stop_browser_daemon`/`start_recv_daemon`/`stop_recv_daemon`/`list_daemons`/`write_boot_log`），而 Python 侧同时用 `subprocess.Popen` 自行拉起同名进程。

**实测证据**：前端 `invoke()` **只调过 `write_boot_log`**，从未调用 `start_backend` / `start_recv_daemon`（`daemon_registry.py` 文件头记录）→ `AppState.backend=None`、`daemons=[]` → **关窗时「杀空气」**。

即：**Tauri 那套 9 命令的 sidecar 管理面，实际是死面（dead surface）**，真正生效的是 Python 侧。两套并存且无契约说明谁是权威。

### P0-3　BCC 拉起路径 ≥4 条

```
backend/main.py:250                _auto_start_daemons()      → 启动预对齐
backend/main.py:144                _spawn_sidecar()           → 直接 spawn
backend/auto_dm/daemon_launcher.py:124  ensure_daemons_for()  → 按需
backend/services/browser_gate.py:240    ensure_browser()      → 租约准入
backend/auto_dm/accounts.py:299         ensure_bcc()          → 底层
```

用户 2026-09-13 明确要求「**所有启动路径统一走同一入口（杜绝环境分叉）**」。实际是**5 个函数形成 3 层调用链**，其中 `main.py` 与 `daemon_launcher.py` **各自持有 spawn 实现**（P0-1）。

**这也是「BCC 关不掉」事故的结构性土壤**——v0.43.8 只能在 `ensure_daemons_for`/`ensure_browser` 两处插入停止态检查，`main.py` 路径**未覆盖**。

## 三、P1 级：分层依赖逆行（违反「解耦」铁律）

### P1-1　`services/ai_reply.py` → `api/`（下层依赖上层）

**取证（已逐行核实，非推断）**：

```python
# backend/services/ai_reply.py:1379
    from api.messages import _recv_url, _bcc_url, _http_post_json
```

性质：**函数内延迟 import**（非模块顶层），因此不会启动即循环导入——但**架构违规成立**：服务层反向依赖路由层，导致：

1. 服务层**无法被非 HTTP 场景复用**（守护进程内首次调用即触发循环依赖风险）
2. `api/messages.py` 的**私有函数**（`_` 前缀）被跨层引用 → 签名变更会**静默击穿服务层**
3. `api/messages.py` 已 1,645 行（P1 大组件），下游反而依赖其内部实现

### P1-2　`utils/` 携带业务依赖（工具层不纯）

| 文件 | 违规依赖（已逐行核实） | 应有形态 |
|---|---|---|
| `utils/common_util.py:53` | `from services import member_ctx` | 纯函数，零项目业务 |
| `utils/fingerprint.py:72,82` | `from auto_dm import config as _c` | 指纹生成不应知道账号业务 |

`utils/` 是**最底层**，被 14 个模块依赖；它一旦反向依赖业务层，**任何业务重构都会击穿全仓**。

### P1-3　`models/` 纯度 ✅（对照组）

`models/` 6 个文件（account/enums/live/overview/task）**内部依赖为零**，是**全仓唯一完全符合「下层零依赖」规范**的层。可作为整改模板。

## 八、⚠️ 重大架构警示：风控铁律「双标准」

**当前分支 `design/better-douyin` 明确声明「全解除风控铁律」。**

```python
# backend/api/platform.py:32-35（docstring）
### 历史留痕：主分支铁律原文（本分支不生效）
1. ~~复用账号既有凭证被动签名~~；
2. ~~绝不批量补查用户信息；get_im_user_info / bulk_user_info 类方法绝不调用~~；
3. ~~主动请求须可节流、不做后台轮询~~；
```

而 `api/platform.py:342` 新增端点 `POST /user/info/batch`，docstring 明写：

> ★ 本分支新增（全解除）：**主动批量查询**用户昵称/头像。
> 主分支铁律原为「`get_im_user_info`/`bulk_user_info` 绝不调用」（昵称风控红线），
> 本分支按用户 2026-09-14 授权「全解除」已解禁。

**同时**，`dy_apis/login_api.py:770` 的 `bulk_user_info_via_browser` 标注 **DEPRECATED · 属风控红线面**，调用即打 `AUTH-043` 告警。

**问题**：同一代码库内，**同一能力**存在「禁止（AUTH-043 告警）」与「已解禁（本分支新增）」**两套判定**，且**都缺 ADR**。风险：

1. 分支合并/回退时，**哪条有效无法判断**
2. `bulk_user_info` 全局 9 处引用分散在 `api/platform.py`、`daemon/browser_daemon.py`、`dy_apis/login_api.py` 三层
3. BCC 侧 `/user_info`、`/user_info_by_uids` **无鉴权**（20 个端点均无鉴权中间件）→ 任何本机进程可脱手触发主动批量查

**用户画像铁律**：「只要没用到后端去批量查询昵称就行，我就怕风控」。当前分支**已按 09-14 授权解禁**，但**主分支红线仍在文档与代码注释中并存**，必须由用户裁决**正式书**。
