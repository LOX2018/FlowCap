# DYAutoDM_v2 体系体检报告：为什么「臃肿 + 状况百出」

> 2026-09-21　基线：`design/better-douyin` @ `59f9a28`（HEAD=v0.44.24）+ 56 项未提交改动
> 方法：定量测量（非感受描述）。每条结论附测量口径，**全部可复跑**
> 触发：用户判断「项目臃肿 / 同一业务多处多次触发 / 并发逻辑未统一 / debug 未聚焦真实爬虫业务环境」

## 〇、结论先行

**用户的四条判断全部成立，且已从定性升级为定量。**

| # | 用户判断 | 实测数据 | 判定 |
|---|---|---|---|

| 2 | 同一业务多处多次触发 | 「更新会话」**4 个决策点 / 51 处调用**；「BCC 拉起」**6 个决策点 / 56 处调用**；「凭证刷新/重捕获」**13 个决策点 / 74 处调用**；「昵称关联」**5 个决策点** | ✅ 成立 |
| 3 | 底层并发逻辑未规则统一 | **60 个 threading 锁 + 5 个 asyncio 锁 + 38 个模块级锁变量 + 34 处线程池**，无公共并发设施；153 处硬编码 timeout、27 处硬编码 sleep，各自为政 | ✅ 成立 |
| 4 | debug 未聚焦真实爬虫业务环境 | 42 个事故案例归因：**自家代码缺陷 31 / 环境已变 6 / 混合 5**；不确定性建模 **0 处**、概率置信度 **0 处** | ✅ 成立（且是最深层问题） |

**一句话根因**：
> 项目把「**爬虫**」当「**常规业务系统**」建。
> 常规业务系统的前提是「**契约稳定**」——接口不变、字段不变、调用方不变。
> 爬虫的前提恰恰相反：「**对手在变、环境在变、失败是常态**」。
> 于是所有为「稳定契约」设计的结构（确定性的分层、单点入口、一次性验收），在爬虫场景下都会**反向变成债务**：接口一变就要在 N 个调用点各打一个补丁，补丁层叠成臃肿，静默兜底掩盖真实失败。

## 一、臃肿的定量证据

### 1.1 规模

```
后端：212 个 .py / 65,999 行     （文档声称 114 个 / 34,961 行 → 漂移 +89%）
前端： 96 个文件 / 24,895 行     （文档声称 11 页面 / 8,490 行）
Git ：+295,311 / −119,528 = 净增 175,783 行
```

**「只加不减」**：净增是删除量的 1.47 倍。脏代码没有出口——每轮修复都是「在旧逻辑旁边再加一层」，而不是「替换旧逻辑」。

### 1.2 提交构成（补丁层叠的指纹）

| 类型 | 数量 | 占比 |
|---|---|---|
| **fix** | **173** | **33%** |
| feat | 102 | 20% |
| docs | 71 | 14% |
| refactor | 31 | **6%** |
| perf | 7 | 1% |

**判读**：`fix : refactor = 173 : 31 = 5.6 : 1`。健康项目的比值应接近 **1:1**（每修 1 个 bug，有 1 次结构性整理）。
**当前每 5.6 次灭火才有 1 次疏导** —— 这就是「状况百出」的数学表达：**灭火速度追不上起火速度，且结构性熵持续累积**。

### 1.3 反复修的模块（补丁热点）

```
工作记忆 24 次 · frontend 19 次 · live 9 · browser 9 · platform 9 · 私信 9 · im 7 · recv 7 · messages 6 · capture 5 · bcc 5
```

`live` / `browser` / `私信` / `bcc` / `capture` —— **正好是 5 个「与外部世界直接交互」的域**。这印证了根因：**越靠近不确定边界的地方，补丁层叠越严重**（因为契约在变）。

### 1.4 版本迭代速率

```
09-17  59 个版本   09-14  23 个版本   09-16  19 个版本   09-13  16 个版本
```

**单日 59 个 debug 版本**。用户铁律「每次修复 +0.01」被严格执行——但速率本身是症状：**一天内 59 次「发现问题→打补丁」，说明书级别的试错**，而非设计驱动。

**这就是「同一业务多处多次触发」的实证**：

- 「**BCC 该不该拉起**」这一件事，**6 个函数各自拥有决策权**（更严重的是其中 `_spawn_sidecar` 有 **2 份不同实现**），**56 个调用点**分散在 7 个模块
- 「**凭证是否有效/该不该重捕获**」更是 **13 个实现入口**：`verify_account`、`scan_login`（3 份：api 层、browser_daemon 2 处）、`auto_recapture`（2 份）、`recapture_from_profile`、`refresh_cookie_to_env`、`run_keepalive`、`refresh`…… **每一条都有自己的判据** —— 这正是 2026-09-13「UID 漂移=凭证失效」铁律**无法一处落地**的结构原因（判据分散在 13 处，改一处漏十二处）
- 「**昵称怎么拿**」有 **5 条路径**（主动批量 2 + IDB 1 + 端点 1 + 废弃 1），其中 2 条属风控红线面 → **同一能力两套价值观并存**

### 2.2 后果链（已实际发生的事故）

```
「BCC 关不掉」事故（v0.43.8）
  ← 6 个决策点中，v0.43.6 只改了「启动就拉」
  ← v0.43.8 只能在 2 个点（ensure_daemons_for / ensure_browser）插停止态检查
  ← main.py 路径未覆盖 → 仍有路径能拉起
  ← 根因：**决策权分散在 6 处，任何单点修复必然漏**

「昵称捕获 14 个而非 44 个」事故（v0.43.10）
  ← 捕获定义 4 处（api/messages 1589 / conversation_capture 1369 / browser_daemon 1530 / browser_daemon 3185）
  ← 修了 1 处循环位置 → 另 3 条路径行为不同
  ← 根因：**同一能力 4 个实现，修一处不知另三处**

「同一机制下账号差异」（ENG-020, v0.44.25）
  ← wp_recv 单例假设 → 多账号下行为不一致
```

### 2.3 层叠兜底（兜底掩盖了真实失败）

`auto_dm/conversation_capture.py`（2,023 行）内部：

```
「兜底」16 处 · 「回退」5 处 · try/except 链 23 处 · except: pass 9 处
```

**全后端**：`except: pass` / `except: continue` 静默吞异常 —— **AST 精确口径 340 处**（宽泛捕获 `except:` / `except Exception` 达 **1,085 处**）

```
（AST 口径，逐语法树节点统计）
browser_daemon 31 · recv_daemon 24 · im_protobuf 14 · vbrowser 13 · origin_image_resolver 13
accounts 11 · ai_reply 11 · live_hook 10 · im_video 10 · database 9 · conversation_capture 9 · auto_dm 9
```

> **口径修正说明**：初测用正则得 623 处，含多行误匹配与 `# except: pass` 注释命中。
> 复核改用 Python `ast` 逐 `ExceptHandler` 节点统计，**精确值 340 处**（报告以 340 为准）。
> 无论哪个口径，结论不变：**每 2,000 行代码就有 1 处静默吞异常**，且集中在「与外部世界交互」的模块。

**这是「状况百出但查不到」的机理核心**：
每一次上游变更都会打到一个静默兜底 → 代码「不崩、不报错、返回空」→ 表现为「功能静默失效」（昵称 0 个、会话 44 个但昵称空、假成功）→ 排查时无任何线索 → 只能靠人肉逐层猜 → 猜错方向 → 再打补丁 → 熵增。

**「兜底」本意是健壮性，实际变成了「故障隐藏层」。**

## 三、「底层并发逻辑未规则统一」的定量证据

### 3.1 并发原语：各路自造，无公共设施

| 原语 | 数量 | 分布 |
|---|---|---|
| `threading.Lock/RLock/Semaphore/Event` | **60** | dm_dispatch 6 · recv_daemon 4 · ai_reply 4 · accounts 3 · browser_daemon 3 · ws_link 3 · uid_probe 3 |
| `asyncio.Lock/Event` | 5 | api/engine:52 · core/auto_dm:143 · core/dispatch:103 · browser_daemon:479 · notify/channels:76 |
| 模块级锁变量 `_lock = ...` | **38** | dm_dispatch 4 · accounts 3 · platform 2 · browser_daemon 2 · recv_daemon 2 |
| 线程池/进程池 | **34** | main 5 · api/accounts 3 · auto_dm/accounts 3 |

**关键缺陷**：**同一进程内同时存在 asyncio 事件循环 + threading + 线程池 + 多进程守护 + 浏览器容器**，五套并发模型叠加，但**没有任何一处定义「哪层用哪种原语、如何跨层同步」的规则**。

具体危险（已在事故中体现）：

- `threading.Lock` 在 async 函数内使用 → **阻塞事件循环**（09-06 台账「事件循环阻塞」就是这么来的）
- `asyncio.Lock` 跨进程无效 → BCC（独立进程）与 backend 之间的互斥**只能靠 HTTP 租约**，但租约与 threading 锁**两套互斥体系并存**（`gate:auto` 独占 vs `_lock`）
- `daemon_registry._lock` 保护 pid 表，但 `_pid_running()` 是**跨进程 IPC**，被迫设计两段式锁（`kill_all` 的注释就是被这个问题逼出来的补丁）

### 3.2 超时/重试/退避：全部硬编码、各自为政

| 项 | 文件数 | 总数 | 最集中 |
|---|---|---|---|
| `timeout=` 硬编码 | 41 | **153** | browser_daemon 28 · api/accounts 20 · login_api 12 · accounts 9 |
| `sleep` 硬编码 | 13 | **27** | verify_ws_ab 6 · sender 3 · main 2 |
| `retry` 硬编码 | 3 | 4 | env_baseline 2 · vbrowser 1 |

**没有统一的重试/退避/超时策略中心**。后果：
- 每个调用点自己拍一个 timeout（28 个数量的 browser_daemon 意味着 28 个不同的时间假设）
- 无法统一调优：改一个风控退避策略要动 41 个文件
- 无法统一定位「为什么慢」：没有共同的时间语义

### 3.3 单例/生命周期：三种模式混用

| 模式 | 现实 |
|---|---|
| 模块级单例（`get_dispatcher()` / `get_xxx()`） | dm_dispatch / uid_probe / conv_identity … |
| 进程级单例（BCC 容器 `_state["container"]`） | browser_daemon |
| 跨进程单例（HTTP 租约 `gate:auto`） | browser_gate |
| **「单例假设」** | wp_recv 单例假设被证伪（ENG-020） |

**根因**：没有「**资源生命周期契约**」——每个资源（BCC/browser context/DB 连接/锁/租约）各自实现自己的「谁拥有、谁释放、如何互斥」，导致跨层组合时行为不可预测。

## 四、最深层问题：debug 没聚焦真实爬虫业务环境

### 4.1 事故归因统计（42 个案例）

| 归因 | 数量 | 占比 |
|---|---|---|
| **自家代码缺陷** | **31** | **74%** |
| 环境/上游已变 | 6 | 14% |
| 混合 | 5 | 12% |

**表面看**：74% 是自家代码问题 → 好像只要「把代码写对」就行。
**实际看**：这 31 个「自家代码缺陷」中，**大部分是「用稳定契约假设去写爬虫」的必然结果**：

```
直播配置标签与目标直播间分离（20 处自家关键词）      ← 假设前端契约稳定
直播策略纯化与移除强制重扫（11 处）                ← 假设「重扫」是可靠的补偿手段
a-bogus 子域签名（9 上游 / 26 自家）              ← 上游签名机制已变，但代码假设旧机制
内容页播放失败 secsdk 签名（4 上游 / 19 自家）      ← 同上
BCC-053 误判（1 上游 / 11 自家）                 ← 探活判据用旧假设
弹窗真因_出口IP分叉（2 上游 / 6 自家）             ← 假设「网络出口唯一」
浏览器可见性假成功（3 上游 / 1 自家）              ← 假设「可见=可用」
```

**结论**：**这些不是「代码写错了」，而是「世界变了但代码的假设没变」**。
把它们归为「自家代码缺陷」会**误导修复方向**——去改代码，而不是去**升级对世界的建模**。

### 4.2 爬虫项目特性：核心能力**零建模**

| 爬虫必备能力 | 命中 | 判定 |
|---|---|---|
| **概率/置信度模型** | **0** | ❌ 零 |
| **不确定性显式建模**（degraded/best_effort） | **0** | ❌ 零 |
| 采样/节流/退避（jitter/backoff/throttle） | 7 | ⚠️ 极少（仅 ws_link 6 + events 1） |
| 上游变更检测 | 6 | ⚠️ 极少（仅 env_baseline 4 + 2） |
| 多路径冗余（fallback） | 59 | ✅ 有（但集中在 model_hub 20，是 AI 模型路由，非爬虫链路） |
| 观测/遥测（metrics/probe/health） | 26 | ✅ 弱有（uid_probe 7 + im_video 5） |

**这是最致命的缺口**：
> 一个**对抗性、概率性、契约漂移**的爬虫系统，**没有一处代码表达「置信度」「降级」「不确定性」**。
> 所有代码都在表达「**确定性成功或确定性失败**」。

于是：
- 抓不到 = 报错 or 静默返回空（没有「可能抓到了但质量存疑」这一态）
- 抓到了 37/44 个 = 不知道这是「好」还是「坏」（没有覆盖率/置信度指标）
- 上游变了 = 只会在某个静默兜底处表现为「空」，不会表现为「契约漂移告警」

### 4.3 「总觉得以前定性的接口环境就是正确的」——这条批评最准

用户原话：
> 「总觉得以前定性的接口环境就是正确的，反复去排查现有环境、现有定义与以前的差异，没有真实判断，是否符合真实业务需求的爬虫效果。」

**这精确描述了本项目过去多轮排查的真实模式**：

```
已知：08-31 / 09-12 某接口返回 X（当时的定性）
现象：现在得到 Y
默认动作：沿代码链路找「哪里把 X 变成了 Y」
            → 假设是自家 bug
            → 逐层加日志、加兜底
遗漏判断：X 这个「定性」本身是否还有效？
          **X 当时可能是因为某种前置条件才成立的**
```

**项目里已有血证**：
- `vbrowser.py` 注释写「纯 headless → 昵称 0」，但日志显示 03:00 前纯 headless 捕获 83 个 → **注释里的「定性」本身是错的**，它带偏了整轮排查（已写入技能警示）
- `architecture.md` 写「昵称唯一来源是 BCC 被动 hook」，实测已被推翻 → 文档写的是「校准横幅」但正文仍是旧定性
- 「连麦申请失败」曾误判为登录态，真因是 `is_turn_on=0` 硬门槛

**根本缺失**：没有「**能力探针**」（capability probe）——即
> **不问「代码是否按老定义工作」，而问「现在能否真实达成业务效果」。**

## 五、根因收敛：一个判断

**这个项目的所有四条症状，出自同一个设计前提错误：**

```
设计前提（隐含）：「外部契约是稳定的，代码正确 = 业务正确」
爬虫现实（必然）： 「外部契约是漂移的，代码正确 ≠ 业务正确」
```

四条症状都是这个前提的必然投影：

| 症状 | 投影机制 |
|---|---|
| 臃肿 | 契约一变 → 在 N 个调用点各打补丁（因为契约信息散落在 N 处） → 只加不减 → 净增 17.5 万行 |
| 多处多次触发 | 同一业务没有「单一事实源」，6 个决策点各自维护「何时该做」→ 任何变更要 N 处同步 |
| 并发未统一 | 每遇到一个并发问题就自造一个锁/池/单例，因为**没有「资源生命周期」这个抽象** → 60 锁 + 5 asyncio + 38 模块级变量 |
| debug 跑偏 | 契约漂移时，**没有机制告诉人「是契约变了」**（0 概率模型 / 0 不确定性建模 / **340 处静默兜底**）→ 人只能假设自家 bug → 反复在代码里找差异 |

## 六、体系性矫正方向（不是打补丁，是换前提）

### 6.1 核心换前提：从「契约正确」到「**效果可验**」

**当前**：`代码符合旧定义 → 认为成功`
**应为**：`能力探针在当前真实环境达成业务效果 → 才算成功`

具体落地（三条，按优先级）：

**① 能力探针层（Capability Probe）** —— 对应第 4 条病症
> 每个关键能力定义一个**可执行探针**，随时回答「现在行不行」：
> `更新会话` → 探针：捕获数 / 会话总数 ≥ 阈值，且昵称覆盖率 ≥ 阈值，且与上次基线比对无漂移
> `发私信` → 探针：真实写校验（已有 v0.44.20 的雏形）+ 回执
> 探针结果**不是日志，是状态**（健康/降级/失效三态，而非二态）
>
> **判据**：任何「功能失效」都必须在探针层先暴露，而不是等用户发现

**② 契约漂移检测（Contract Drift）** —— 对应第 4 条病症

> **判据**：340 处减少到「有明确降级语义」的少数几类；每次降级都进指标

### 6.2 对应第 1、2、3 条病症的结构矫正
