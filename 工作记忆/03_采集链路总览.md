## 三、C1 会话与消息捕获（最核心链条）

### 3.1 数据源与可靠性矩阵

| 数据 | 来源 | 关联键 | 实测覆盖 | 成本 |
|---|---|---|---|---|
| `conv_id` / `peer_uid` | 首包 `get_message_by_init`（cmd 2043） | — | **44/44** | 1 请求 |
| `short_id` | 首包元数据 `field4.5` | conv_id | 44/44 | 0 |
| 消息（近 ~20/会话） | 首包 `field2` 内嵌 JSON | conv_id 内嵌 | 25 条/11 会话 | 0 |
| 消息（完整历史） | **cmd301** `get_by_conversation` | conv_id + short_id | 43 条（目标会话） | 1 请求/会话 |
| 图片解密要素 | **cmd301** `field8.resource_url` | msg_id | 5/5 | 随 301 |
| **昵称 / 头像** | **IndexedDB** `<自身uid>_user` | **数字 uid** | **44/44** | **0 请求** |

> 数据来源、字段口径详见 `05_端点与协议台账.md`（**索引**，分册 `05a`~`05g`）；昵称三通道的演化见 `01_铁律与红线.md` §1.2。

### 3.2 四条设计不变式（破了即 bug）

| # | 不变式 | 曾发生的反例 |
|---|---|---|
| **I1** | **幂等**：重复触发结果一致，不重复写 | 有唯一索引 `uniq_dmmsg` 兜底 |
| **I2** | **不降级**：新结果不得劣于已有 | ❌ **15 个覆盖了 83 个**（登录态失效后） |
| **I3** | **解耦**：昵称与消息互不阻塞 | ❌ 昵称失败连带消息不落库 |
| **I4** | **可离线重放**：首包落盘后可无限重放 | ❌ 代码从不落盘 |

### 3.3 已知失效模式（探针必须捕获）

- 昵称全为数字 uid（关联失败）
- `peer_name` 存的是数字 `peer_id`（**DB 实测：`peer_name` = 假昵称**）
- `short_id` 78/78 为 None（消费方依赖时不成立）
- 会话数骤降（覆盖/降级）

## 四、C2 私信收发

### 4.1 双通道

| 通道 | 载体 | 方向判定铁律 |
|---|---|---|
| **WS** | `recv_daemon.py` 长连接 | **空 sender → me** |
| **WP** | BCC 页面内 | **空 sender → me** |
| 捕获 | `conversation_capture.py` | **空 sender → me** |

> **铁律**：三通道方向判定必须一致（曾出现 WS 判 `them`、另两通道判 `me` 的 P0 级不一致）。
> 原理：`sender` 为空 = 本系统自己产生的（自动欢迎语/自动回复）。

### 4.2 发送统一出口

所有发送方（手动 / AI / WS 回复 / 调度器）**收敛到同一 per-account 串行队列**
（`services/dm_dispatch.py`，被 8 个模块使用，含 `AccountQuota`/`UidSink`/`ConvPool`）。
**这是本项目做得最好的架构项，P3 重构不得破坏它。**

## 九、链路重定义（爬虫能力视角 · P4，v0.44.28）

> **为什么重定义**（用户原话）：
> 「总觉得以前定性的接口环境就是正确的，反复去排查现有环境、现有定义与以前的差异，
> 没有真实判断，是否符合真实业务需求的爬虫效果。」
> 上文 §一~§八 是**特征视角**（这条链做什么）；本节是**能力视角**（爬虫在什么条件下会失败）。
> 两个视角**互补而非替代** —— 特征视角回答「有哪些链路」，能力视角回答「链路何时不可信」。

### 9.1 统一爬虫分层（带**可失败点**声明）

对抗性爬虫的每层都有独立的失败模式；重定义要求**每层显式声明失败点**：

| 层 | 责任 | 本层**可失败点**（必须显式建模） | 本项目现状 |
|---|---|---|---|
| ① 目标定义 | 明确采什么 | 目标定义漂移（用户需求变了而代码未变） | ⚠️ 无显式声明 |
| ② 取数-传输 | HTTP / WS / 浏览器 | 网络失败、**403（签名/策略）**、限流 | ❌ 静默（无分类） |
| ③ 解析-协议 | protobuf / JSON 解包 | **结构漂移**、字段缺失、脏数据（`msg_type=7`） | ❌ 静默 |
| ④ 归一化 | 字段口径统一 | 命名漂移、单位/类型不一致 | ⚠️ 部分 |
| ⑤ 落库 | 持久化 | 唯一索引冲突、覆盖降级（**15 覆盖 83 事故**） | ⚠️ 部分 |
| ⑥ 效果度量 | 判断「行不行」 | —— | ✅ 探针层（P2/P1 已建） |

**判据（P4 验收）**：②③④⑤ 每层失败必须**可分类**（不是 `except: pass`），
且分类结果**进探针指标**。

### 9.2 三态模型（替换二态，对应体检报告 §6.1③）

**旧**：`成功 / 失败`（二态） → 抓不到就报错或静默返空。
**新**：`confirmed` / `degraded` / `failed`，**degraded 必须带覆盖率与置信度**。

| 链 | confirmed（确认成功） | degraded（部分成功，带覆盖率） | failed |
|---|---|---|---|
| **C1 捕获** | 会话数 ≥ 基线 × 0.95 **且** 昵称覆盖率 ≥ 0.9 **且** 无降级 | 会话数达标但昵称覆盖率 0.5~0.9，或较基线下降 5%~30% | 会话数 < 基线 × 0.7，或昵称全为数字 uid |
| **C2 私信** | DB 落库 `role=me` + 本次 `skey`/msg_id 命中 | 已投递但回执侧无独立证据 | 写被拒（`unexepcted session length`）/ 频控冷静期 |
| **C3 直播** | 弹幕持续到达 + 在线观众数 ≥ 1 | 连上但长时间无弹幕（可能低活跃，非故障） | 解析失败 / WS 断连不恢复 |
| **C4 凭证** | 探活 uid == 历史 conv_id **且** 写探针 ok | 探活 ok 但未做强写探针（`unknown`） | uid 漂移 / 写被拒（只读态） |
| **C5 内容** | `status_code=0` 且有数据 | 有响应但 `aweme_list` 为空（可能真无内容） | HTTP 403 / 非 JSON |

> **铁律**：`unknown` **绝不等同于** `confirmed`。历史所有「假健康」都源于把「未知」当「好」。

### 9.3 覆盖率与置信度（爬虫的核心量纲）

| 指标 | 定义 | 归属链 |
|---|---|---|
| **覆盖率** | 实际采到 / 应有（分母取**基线快照**，非硬编码期望值） | C1、C5 |
| **关联率** | 昵称非数字 uid 的记录 / 总记录 | C1 |
| **回执一致率** | 有回执确认的发送 / 总发送 | C2 |
| **漂移信号** | 字段集与契约不符的次数（见 `docs/design-contracts/`） | 全部 |

### 9.4 与探针的映射（能力视角必须可测）

| 探针 | 覆盖链 | 三态来源 |
|---|---|---|
| `conversation_capture` | C1 | 会话数 vs 基线 + 昵称关联率 |
| `message_integrity` | C1 | 脏数据过滤 + 字段完整度 |
| `send_delivery` | C2 | 落库硬验证（缺验证标记 → degraded） |
| `live_pipeline` | C3 | 弹幕到达 + 房间状态 |
| `credential_effective` | C4 | 探活 uid + 强写探针（→ `auto_dm/accounts`） |
| `content_fetch` | C5 | `status_code` + 数据非空 |

> 详见 `02_效果定义与探针.md` §六（6 个探针已落地）。探针**只读本地事实**（DB + 本项目日志），
> 零网络零浏览器 —— 这是 C1/C4 能高频巡检而不触发风控的前提。
