# V2 私信守护与会话列表拉取（2026-08-25 整理，结合代码核实）

> 筛选自对 recv_daemon / api.messages / auto_dm.accounts.verify_account / messages.tsx 的逐行核实，符合当前 V2 架构（0.29.0）。

## 一、概念澄清：私信列表有两层

- **会话列表的数据产生**：由 `recv_daemon`（私信守护，每账号一个 sidecar）维护，来源是抖音 IM 长连接 WS 主动下发 + 守护生命周期内首次被请求时的一次全量 API 拉取。**前端轮询只读，不主动拉列表**。
- **"真拉私信列表 API"**：仅 `auto_dm/accounts.py` 的 `verify_account(dm_loopback=True)` 调用 `DouyinAPI.get_conversation_list` 时直连抖音。它**不经过 recv_daemon 的 `/conversations` 端点**，不会翻转守护的 `_api_pulled` 标志——是独立于下述链路的第二条拉列表路径。

## 二、守护启动时拉列表吗？（结论：启动时不主动拉）

- `recv_daemon.py` 的 `@app.on_event("startup")`（第 538-561 行）：
  1. 为每个账号建 `AccountInbox`（`_load_from_db` 从 SQLite 加载**已持久化**的历史会话骨架）；
  2. 建 `RecvChannel` 并 `channel.start()` → `_restart_ws()` 连 `frontier-im.douyin.com/ws/v2`。
- **启动那一刻不调任何拉列表 API**。列表来源：
  - WS 同步帧：`_handle` 解析 `get_conversation_info_list_v2_response_body`（tag 610）→ `_sync_conversations` 建骨架（第 424-427、459 行）。仅骨架，peer 信息待补全。
  - **首次 HTTP 请求触发全量 API**（见第三节）。

### 2.1 守护进程的启动方式（2026-08-27 修复）

**问题**：旧机制假设 recv_daemon 已运行，但 Tauri sidecar 架构下 recv_daemon 是独立进程，需由外部拉起。Backend 启动时未主动拉起，导致前端首次轮询连续失败（`recvDaemonDown`），需等待 daemon 启动后才能正常拉取。

**修复**：`main.py` 的 `lifespan` 中新增 `_auto_start_recv_daemons()`，backend 启动后为所有账号 spawn recv_daemon sidecar：
- 路径解析：`_resolve_recv_daemon_binary()` 对齐 `sidecar.rs` 的 `resolve_sidecar` 逻辑（优先 `binaries/<name>-<triple>.exe`，回退 `dyautodm-recv-daemon.exe`）
- 端口探测：`_port_open(port, timeout=0.2)` 跳过已在运行的 daemon（避免重复拉起）
- 进程隔离：Windows 用 `CREATE_NEW_PROCESS_GROUP`，Unix 用 `start_new_session`
- 失败兜底：try/except 包裹，单账号失败不影响其他账号，整体失败不影响 backend 启动

**效果**：backend 启动完成时，所有账号的 recv_daemon 已在运行，前端首次轮询即命中就绪的 daemon，消除 `recvDaemonDown` 窗口。

## 三、"首次 HTTP 请求"的精确定义（核心）

### 3.1 判定标准（代码层）

`_api_pulled` 是 `AccountInbox` 实例属性，**每账号、每 recv_daemon 进程**一份，初始 `False`（第 129 行）。翻转条件：打到该守护的两个端点**任意一个**先到达：

- `GET /conversations?account=X`（`recv_daemon.py` 第 583-595 行）
- `GET /conversation?account=X&conv_id=Y`（`recv_daemon.py` 第 727-738 行，同样守卫）

到达后执行 `_pull_conversations_api(ib)`（全量 `get_message_by_init`），置 `_api_pulled=True`；之后该进程内所有请求只读内存/SQLite，不再拉 API。

### 3.2 全量拉取做什么（`_pull_conversations_api`，第 602-724 行）

1. `DouyinAPI.get_message_by_init(auth)`：抖音私信页用的 cmd 2043，拉**全量真实会话**（实测 250KB / 259 个 conversation_id；返回 <2000 字节疑为凭证失效/限频）；
2. 写会话骨架到 SQLite + 内存（INSERT OR IGNORE）；
3. 后台线程 `bulk_user_info_via_browser`（走 BCC 浏览器容器）批量解析昵称/头像（不阻塞 HTTP 响应）。

### 3.3 演进佐证（为何改 API 全量拉）

`_pull_conversations_api` docstring（第 605-607 行）：旧实现依赖 WS 同步帧 `get_info_list`（cmd 610），但那是**按 user_id 查单个会话，不是"列全部"**，列不全。现改为守护启动后第一次被请求时强制 `get_message_by_init` 补齐全量，`_api_pulled` 守卫保证只拉一次，避免"WS 同步帧给 1 个骨架导致 list_convs 非空、跳过 API 拉取"（第 589-591 行注释）。

### 3.4 实际发生时机（前端主路径）

`messages.tsx` 的 `convsQ`（`enabled: !!ready && !!activeAcct`，`refetchInterval: 5000`，第 166-219 行）：
1. `ready`（后端存活）+ `accountsQ` 加载出账号；
2. `activeAcct` 设为第一个账号（第 161-163 行）；
3. 此后每 5 秒 `a.getConversations(activeAcct)` → 后端 `GET /api/messages/conversations` → `api/messages.py` 转发到 `recv_daemon /conversations`（端口稳定哈希 `recv_daemon_port`）；
4. **这串转发里的第一次**即翻转 `_api_pulled`、真拉全量。

其它触发：
- 用户点开单个会话 → `GET /conversation`（第 735 行守卫）也会触发首次全量拉，即便列表轮询尚未发生。
- 守护未启动时：后端 `api/messages.py` 先 `_port_open` 探测，未开直接返回 `{ok:True, conversations:[], recvDaemonDown:True}`（第 109-111 行），**不转发**，前端据此自动拉起一次（`convTried` ref 守卫只试一次，第 177-184 行）→ 下一轮询（≤5s 内）触发全量拉。

### 3.5 复位点

`_api_pulled` 是**进程内存态**。recv_daemon 进程**重启**（崩溃被 Rust 监督重启 / 手动 stop+start）后新进程重建 `AccountInbox`，`False` 复位 → **下一个到达的请求又拉一次全量**。"首次"是**每次守护进程生命周期内**的首次，非全局只一次。

## 四、两条拉列表路径对照表

| 行为 | 触发方 | 触发条件 | 走 recv_daemon? | 是否真拉 API |
|---|---|---|---|---|
| 列表产生（骨架） | recv_daemon WS 同步帧 | WS 连上 + 抖音下发同步帧 | 是（内部） | 否（抖音推） |
| 列表补全（全量） | recv_daemon `/conversations` `/conversation` | 该账号**首次**被请求（`_api_pulled` 守卫） | 是 | 是（`get_message_by_init`） |
| 前端展示列表 | messages.tsx 轮询 | 有 activeAcct + 守护在跑 + 每 5s | 是（转发） | 否（只读守护） |
| 校验真实拉列表 | verify_account | `dm_loopback=True`（点校验/启动自检/自动重捕） | **否**（直连抖音） | 是（`get_conversation_list`） |
| 校验近似显示 | verify_account | `dm_loopback=False`（账号列表轮询） | 否 | 否（沿用 wp 引擎结果） |

## 五、关键不变量 / 铁律（踩坑固化）

1. **守护启动 ≠ 拉列表**：启动只建收件箱（读 SQLite 历史）+ 连 WS，不调拉列表 API；全量列表靠"首次请求"兜底。
2. **`verify_account` 的 `dm_loopback` 是唯一"直连抖音真拉列表"开关**：常规账号列表轮询 `dm_loopback=False` 不真拉，只用 wp 引擎结果近似 dm 状态，避免"恒显待校验"误导。
3. **WS 同步帧列不全**：旧 cmd 610 是按 user_id 查单会话，必须用 cmd 2043 `get_message_by_init` 才列全；`_api_pulled` 守卫防重复拉。
4. **守护重启即复位首次拉取**：`_api_pulled` 为内存态，进程重启后下一请求重新全量拉——属预期行为，非 bug。
5. **前端自动拉起守护只试一次**：`convTried` ref 守卫，避免每 5s 轮询狂拉起守护进程。**注意**：backend 启动时已自动拉起 recv_daemon，前端的 `recvDaemonDown` 分支现在是**兜底路径**（daemon 崩溃重启期间触发），非常规路径。

6. **messages.py 已改纯读 SQLite（08 §十一）**：`/conversations` 直接 `get_db()` 读
   `dm_conversations`，不再转发 recv_daemon 内存（内存 peer_name 多为裸 UID）。recv_daemon
   仅负责 WS 实时增量（新消息/未读数）写库；昵称/头像由 backend 启动期 `capture_all`
   （with_browser=True）经 BCC 截获后**权威写入**，recv_daemon 的 `get_or_create` UPDATE
   受 COALESCE 保护，绝不回退已关联昵称。
