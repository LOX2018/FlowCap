# DYAutoDM_v2 铁律（最高优先级 · 违反即停手）

> **本文件是 DYAutoDM_v2 项目的「最高优先级铁律」集中清单。**
> 在任何开发、调试、逆向、测试动作之前**必须先读本文件**，再读对应业务知识库。
> 铁律优先级高于一切便利性考虑：与铁律冲突的"更高效做法"一律不得采用。
>
> 整理：2026-09-09　来源：用户历次明确要求 / 重大事故复盘

---

## 一、账号与凭证红线（风控级）

1. **绝对禁止复用凭证**。不可用 cookie / DY_TICKET / DY_TS_SIGN / DY_CLIENT_CERT /
   DY_PRIVATE_KEY 等到后端、脚本、requests 里批量查昵称 / 发消息 / 调业务接口。
   用户原话：「复用凭证是绝对不可取的！复用会直接导致风控！」
2. **只能复用「带凭证的浏览器」本身去观测页面**（BCC 每账号常驻 sidecar，
   持有唯一 Playwright context）。用账号**自己的**浏览器环境观测是被允许的边界。
3. **单 profile 铁律**：每账号单一固定 profile（`auto_dm/accounts/<name>/profile`）。
   绝不 `launch_persistent_context` 新建目录、绝不复制 profile 另开、绝不 `_wipe_user_data_dir`。
   多进程抢同一 profile 会 SingletonLock 冲突 → 崩溃。
4. 一切必须与抖音网页交互的动作都走 BCC（HTTP 调 `browser_daemon`），
   降级只能走 `vbrowser.launch_async(force=True)` 临时 profile，**不是复制持久化 profile**。

## 二、昵称关联风控红线（用户最在意）

- 用户原话：「只要没用到后端去批量查询昵称就行，我就怕风控」。
- 昵称**唯一来源 = BCC 被动 hook**（复用账号常驻浏览器截前端自发 `im/user/info`，零主动请求）。
- 以下都是**死代码**，昵称链路绝不调用，也不要"优化"成主动批量查：
  - `dy_apis.douyin_api.get_im_user_info`
  - `browser_daemon.bulk_user_info(/user_info)`
  - `bulk_user_info_by_uid(/user_info_by_uids)`
  - `login_api.bulk_user_info_via_browser`
- WS 长连接只落库骨架 + 用消息自带 `sender_nickname`，**绝不补全昵称**。

### 2.1 修订（2026-09-17，用户明确授权）：低频「昵称兜底」白名单

用户原话：「**im/user/info 主动批量查昵称可作为兜底方案，低频查询风控系数较低**。」

该授权**修订**上文的绝对禁令，但**不取消风控边界**——兜底只能走
`services/nickname_fallback.py` 这一条路，且必须同时满足：

| 约束 | 值 | 说明 |
|---|---|---|
| 默认开关 | **关闭** | `dm.nickname_fallback_enabled=False`，须显式开启 |
| 最小间隔 | ≥600s（下限 60s） | 进程内硬限速，非配置可绕过 |
| 单次上限 | ≤20（默认 10） | 与接口批次一致 |
| 每日上限 | 默认 50 | 当日累计，超限拒绝 |
| 候选筛选 | **只补缺失** | 已有真实昵称的会话绝不进入候选，也绝不覆盖 |
| 传输 | **必须经 BCC 页面上下文** | 复用登录态；后端**不得**直发 cookie |

**仍然禁止**（上文死代码清单继续有效）：
`api/platform._im_user_info_by_sec`（后端直发版）等旧路径**不得**被昵称链路调用。
常规昵称来源**仍是 BCC 被动 hook**；兜底正常情况下永远不该被触发。

## 三、设备红线（2026-09-09 用户明确要求）

1. **采集类设备一律虚拟，绝不碰真实硬件**
   本项目**任何环节、任何模块**都不得使用真实麦克风 / 真实摄像头。
   **键盘、鼠标、网卡等输入/网络设备不受限制。**
2. 实现（**缺一不可**）：
   - 启动参数 `vbrowser._CHROME_ARGS` 内置 `_FAKE_MEDIA_ARGS`：
     `--use-fake-device-for-media-stream`（虚拟设备源）
     `--use-fake-ui-for-media-stream`（自动授权，不弹系统框）
     `--mute-audio` / `--deny-permission-prompts` / `--allow-file-access-from-files`
   - profile Preferences **只管权限放行**，**不能替代**虚拟设备源参数：
     - `permissions.audio_capture["https://live.douyin.com:443"].setting = 1`
     - `permissions.video_capture[...] = 0`（摄像头**一律拒绝**）
     - `media.auto_select_audio = true`
   - 脚本 `scripts/fix_virtual_mic.py`（浏览器**关闭**时跑，自动备份）。
3. ⚠️ **事故教训**：曾为「验证不使用真实设备」而调用 `getUserMedia({video:true})`，
   结果**真的打开了物理摄像头**（label=`Integrated Camera (174f:244c)`）。
   **任何验证脚本只允许测音频，禁止任何 video 调用。**

## 四、浏览器启停纪律（风控级，2026-09-09）

- 用户原话：「非必要不要老是杀死浏览器后又重新激活，很容易风控」。
- 一次启动跑完整个流程，**脚本自己开、自己关**；不要为了换探针就 kill 再拉起。
- 禁止把 `taskkill /IM chrome.exe /F` 当常规操作——**只在确认死锁/孤儿进程时才用**。
- 连续多次探测应复用同一个已开的浏览器实例（CDP 连接或保持 page 引用）。
- **绝不强杀 BCC / 主程序**（`Stop-Process` 会导致 session 降级重认证）。
  部署前走 graceful close（`/quit`）。

## 五、实测优先纪律（以事实为主，用户核心要求）

1. **推断/假设必须实测验证后才能据此改代码、下结论**，
   严禁把推断当事实（2026-09-08「双 uid 体系」误判事故、2026-09-09「is_turn_on=0=主播关闭连麦」误判）。
2. 实测推翻推断后**必须撤回错误改动**并更新知识库。
3. **「验证后才汇报结果」**：任何"发送成功/风控触发/功能可用"结论必须硬验证
   （如 DB 落库 role=me+skey 记录、接口返回体），
   严禁仅凭抓包到中间步骤或 UI 弹窗就宣称成功。
4. **定位「前端显示问题」先看前端实际收到的接口数据**，再谈代码。
   用户原话：「你不是应该查前端收到了什么吗，为什么去查后端」。
5. 单一采样不足以定论：某字段为 0/false 时，先确认前置状态（如主播是否在线）
   再下结论，避免**采样偏差**。

  源码在 `C:\Users\LOX\Desktop\DYchajian\DYAutoDM_v2\backend`，

  不要为单文件改动重打全部。
- 部署名带版本号 `DYAutoDM_v2_<版本>.exe`，前后端都改或纯前端改动需升版本号。

## 七、隔离环境前置（会员空间）

- 会员空间账号真实目录：
  `C:\temp\dyautodm_test\members\<member_id>\auto_dm\accounts\<账号>\`
- `.env` 是 Fernet 加密的 `.env.enc`。进程必须带 `DY_MEMBER` + `DY_MEMBER_KEY`
  （从 `members/.session.json` 读）+ `DY_APP_ROOT`，
  否则报「无 .env（索引未登记？）」——**那是没解密，不是索引坏**。
- BCC 端口是账号名哈希，**不能自选**（加 `--allow-any-port` 属调试例外）。

- 代码修复后**同步更新知识库**（用户多次主动追问「知识库更新没」）。
  架构/方案变更、接口逆向成果、踩坑教训都要主动补写 `工作记忆/*.md`。
- 回写三步：① 追加到 `工作记忆/<文档>.md` →
  ② `cp` 到 `D:\文档\Biancheng   CK\DY v2\DY v2\raw\sources\工作记忆\`
  （`Biancheng` 与 `CK` 之间是**多空格**）→ ③ 触发 rescan。
  **绝不直接 cp 到 `wiki/`**（会被 rescan 覆盖）。
- 内容规范：区分「实测证真」与「证伪」，写清判据和实测数字，
  记录导致误判的前置条件。
