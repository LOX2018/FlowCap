### 5.4 ★ TicketGuard 机制（对抗 403 风控的核心）

这是它 v1.1.18 宣称"修复 403 风控"的真实实现。实测提取的**完整参数面**：

```
Cookie 侧：
  uid_tt / uid_tt_ss
  bd_ticket_guard_client_data / bd_ticket_guard_client_data_v2

  bd-ticket-guard-ree-public-key        ← ★ REE 公钥（服务端下发）
  bd-ticket-guard-web-sign-type
```

**机制判读**：
1. 服务端通过 Cookie 下发 **REE 公钥**（`bd-ticket-guard-ree-public-key`）

| **`x-tt-passport-aid-sign` / `sign` / `qs` / `enc`** | web | **纯 Python** | ✅ current | Passport 网关（`login.douyin.com/passport/web/*`）专用。`enc = hex(utf8(s) XOR 0x05)`；`sign = sha256(params排序前10 + '&' + body全部 + '&app_key=' + APP_KEY)`，**`APP_KEY=163e7ce78d58971a41f5b969996d85c2`**（aid=6383）；`qs = enc(前10键名)`；`x-tt-passport-aid-sign = HMAC(HKDF-Expand(HMAC(ts,appKey)), 'aid=…&path=…&ts=…')`，**ts = 当天 12:00 UTC**（整天不变）。均已逐位对齐抓包 |
| **`bd-ticket-guard-client-data`** | web | ECDH+RSA/ECDSA | ⚠️ current（**无纯 Python 实现**） | **TicketGuard / 风控层**，用于创作者**写接口**（`/web/api/media/aweme/create/`、`commit/item/digg/` 等）。从浏览器 localStorage 取 `security-sdk/s_sdk_crypt_sdk` 的 `ec_privateKey` 与 `security-sdk/s_sdk_sign_data_key/web_protect` 的 `ts_sign` 算出。配套头：`Bd-Ticket-Guard-Client-Data` / `-Iteration-Version` / `-Ree-Public-Key` / `-Version` / `-Web-Sign-Type` / `-Web-Version`。**uncertainty：公开明文结构与算法（ECDSA vs RSA-OAEP）互相矛盾，须现场抓包** |
| **`X-Bogus`** | web | 纯 Python / JS | ❌ **deprecated** | **抖音 Web 已被 a_bogus 取代**（MediaCrawler #297「抖音 x-bogus 已彻底失效，更换了 a-bogus」；B1gM8c/X-Bogus #12「xb 不可用了」）。**仅 TikTok Web 与部分抖音端点/直播仍接受**（webmssdk 1.0.0.20 的 `byted_acrawler.frontierSign` 仍产 16 字符，用于直播等） |

## 二、IM 侧签名（`imapi.douyin.com`）—— **与 Web 完全不同**

### 2.1 机制

```
imapi.douyin.com 使用 protobuf（application/x-protobuf）+ cookie(sessionid, HttpOnly) 鉴权
与 Web 的 a_bogus / msToken / x-secsdk 体系无关
```

| 路径 | 是否需要签名 | 证据 |
|---|---|---|
| **读**（`get_by_conversation` cmd301 / `get_message_by_init`） | ❌ **不需要** | 实测 URL 无 `a_bogus`/`msToken`，请求体内无 `ts_sign`/`sdk_cert`/`req_sign`，**纯 cookie 即可 POST，且可无头**。creatorhub 与 my-jxy/douyin-im-export **两处独立实现互相印证** |
| **写**（`send` cmd100 / `create` cmd609） | ⚠️ **以会话级 ticket 为主** | `ticket` 来自会话信息 protobuf `field 1..4` 的 `id`/`short_id`/`type`/`ticket`。creatorhub 2026 抓包**未见** `req_sign` 与额外安全头，仅 cookie + ticket |
| **写（企业号侧）** | ⚠️ 可能携带完整签名套件 | CSDN 企业号 IM 逆向（2026）显示发送体含 `token`/`sdk_cert`/`ts_sign`/`req_sign`，其中 `req_sign` 为基于 EC 私钥的 **ECDSA(SHA256, DER)** 签名，对 `conversation_id`/`short_id`/`content`/`timestamp` 明文签名；`ts_sign` 形如 `ts.1.`/`ts.2.`+hex；`sdk_cert` 为证书 |

### 2.2 参数清单

`ticket` · `ts_sign` · `sdk_cert` · `reuqest_sign`(ECDSA/SHA256-DER) · `token` · `sequence_id` · `conversation_short_id` · `client_message_id` · `device_platform` · `channel` · `auth_type`

### 2.3 对本项目的意义

- ✅ **印证**：本项目 IM 读路径纯 cookie + protobuf 是**正确且已被两个独立开源项目验证**的
- ⚠️ **待验**：写路径是否需 `req_sign` **依账号类型而定**（普通号 vs 企业号）→ 须按本项目账号类型现场抓包
- ⚠️ 本项目已知的 `ticket`/`ts_sign`/`sdk_cert` + `bd-ticket-guard-*` 头，与 **TicketGuard / Passport 网关同源**

1. **`a_bogus` 盐值**：`'dhzx'`（evil0ctal/hanzheng，对 bdms 1.0.1.19-fix.01 实证）vs `'cus'`（creatorhub 自述同版本）→ 疑为**不同版本或不同索引字段**

## 四、关键架构事实（已验证，避免重复踩坑）
1. `backend/vbrowser.py` 才是指纹浏览器真实实现；`backend/auto_dm/vbrowser.py` 仅是 `from vbrowser import ...` 重导出 stub。任何新加的 vbrowser 符号必须在 stub 中也重导出，否则 `auto_dm.*` 引用会 `ImportError`。
2. 端口分配用 `zlib.crc32` 稳定哈希（非 `hash()`，后者因 PYTHONHASHSEED 随机导致跨进程端口不一致、连不上守护）。`browser_daemon_port(name)` / `recv_daemon_port(name)` 在 `auto_dm/accounts.py`，段位 browser=[10000,10499]、recv=[10500,10999]。
3. `app_root()`：frozen 态（PyInstaller onefile）返回 `dirname(sys.executable)`；若 exe 父目录是 `binaries`/`bin`，上溯一级取真正根（否则 `vb_chromium` 路径会被拼成 `binaries/vb_chromium` 找不到）。源码态返回项目根。
4. 抖音 cookie 新格式：s_v_web_id 正常就是 `verify_` 开头（非旧版 19 位纯数字）；uid_tt 是 32 位 hex（转十进制 39 位超 int64）。任何基于"cookie 格式"的污染/伪造判断都可能误伤新版正常登录态——污染判定应靠页面 URL/内容实时监测，而非 cookie 格式猜测。
5. `get_my_uid` 拿真实 uid 的唯一可靠方式是网络接口 `query/user`（即使 s_v_web_id=verify_ 开头也返回真实十进制 uid）；cookie 的 uid_tt/uid_tt_ss 仅是 hex 标识，**绝不能 `int(hex,16)` 转十进制当 uid**（会得超 int64 假值，私信 protobuf 溢出 Value out of range）。
6. 私信 IM 私有网关（`imapi.douyin.com` v2/conversation/create、v1/message/send）靠 protobuf body 内 ticket/ts_sign/sdk_cert 签名鉴权，**不叠加** www.douyin.com 的 bd-ticket-guard-* 头。
7. 发送失败 `KICK` 是账号级私信风控（陌生目标反 spam / 私信频控），与凭证有效性无关（建会话成功已证明签名有效）；需降频或换号。
8. 单 profile 铁律：每账号单一固定 profile（`accounts/profile_dir_of` 算出的 `accounts/<name>/profile`），守护/查看/重扫都复用它，谁要用谁按优先级抢占（重扫 > 查看 > 守护保活）；绝不临时新建临时 profile（临时目录会触发新设备风控 + profile 错乱）。守护只在凭证全齐（`credentials_complete`）时才启动，否则 sys.exit(2)。

- **写入去重**：`add_item`/`bulk_add` 先算正文 embedding，与同主题已有条目余弦 **≥0.90 → 不新增，`occurrence+1`**（重复即证据，不是垃圾）；0.80~0.90 标记 `suspected_dup` 等人工确认。
- **时间衰减**：`decay = e^(-0.02 × 距上次命中天数)`（λ=0.02，约 50 天衰减到 0.37）；排序分 = 相关度 × decay；实测 50天→0.368、100天→0.135。
- **质量门槛**：`importance<0.3 且 hits=0` → RAG 注入时过滤（低质条目不污染《资料》段）。
- **陈旧扫描只出报告不删**（用户拍板 C「全部先扫描出报告，我确认后才执行」）：冷数据（hits=0 且 >180天）/ 低价值（importance<0.3 且 hits=0 且 >90天）/ 重复（两两余弦 ≥0.95）。删除流程：人工确认 → 回收站 30 天 → 真删（`purge_expired`）。
- **重复阈值校准**：0.95 是分界线（同义改写实测 0.9909 命中；措辞不同但实质不同 0.9252/0.9146 不误合；曾用 MalogBot 原值 0.85 会误合工伤不同等级条文，已收紧）。
- **定时器**：`start_scheduler(interval_hours=84)`，`threading.Timer` 常驻循环，首次延迟 30 分钟；每轮跑 run_learn_job（全自动落库，只增不删）/ run_scan_job（只出报告）/ purge_expired。

上述「09-14 成功拉取 10 个项目」是**假成功** —— 那轮修的是清单里的 3 个地址错误，
而脚本对**所有**项目其实恒定 HTTP 400（详见 `cases/2026-09-17_上游追踪机制整体失效_代理写法致400.md`）：

- 根因：`_get()` 同时用 `req.set_proxy()` 与 `ProxyHandler`，前者把 URL 改写成绝对形式
  → GitHub 前置 CDN 判为畸形请求回 **400**；脚本又把 400 误报成「仓库不存在/改名」。
- 放大：`_pick_proxy()` 自动探测端口，而 **10808 在本机常开** ⇒ 无需任何环境变量即命中
  ⇒ **11/11 项目恒定失败**。
- 后果：`upstream_baseline.json` **从未写入过任何 sha**（恒为 `{"projects": {}}`）
  ⇒ `prev` 永远为空 ⇒ **永远判不出「有更新」**，机制等于空转。
- 修法：删除 `req.set_proxy(...)` 单行；非 404 不再报「仓库不存在」（改带响应体摘要）。
- 验证：`--update` → 11 项中 10 项成功落 `pushed_at`+`head_sha`（第 11 项撞匿名限流 60/h，属预期）；
  复跑得 `✅ 无变化`（证明「有更新」判定真正接通）。

**教训**：验收标准要落在**可核验产物**（基线里出现 sha）上，而不是「脚本跑完没报错」；
带代理分支的脚本**必须代理/直连各跑一次**。当前清单 11 项，`--update` 后基线非空。
