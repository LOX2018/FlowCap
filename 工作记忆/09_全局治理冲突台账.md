## 一、已修复（本轮落地）

### 1.1 DB 多进程写竞争（高危）
- **证据**：`backend/database.py:45-65` `get_db()`
- **问题**：只有 WAL（解决读写不互斥），**没有 `busy_timeout`**。
  backend + N×recv_daemon + BCC 并发写同一 db → 直接抛
  `database is locked`（默认 5s 且不重试）
- **修复**：`connect(timeout=30)` + `PRAGMA busy_timeout=30000`

### 1.2 双通道重复落库：唯一索引建了却没生效（高危）
- **证据**：`database.py:141-160` 建了 `uniq_dmmsg(account,conv_id,msg_id)`
  与 `uniq_dmmsg_fallback(account,conv_id,role,text,ts_ms)`
- **问题**：
  - `recv_daemon.add_message` / `wp_recv` / database JSON 迁移用**裸 INSERT**
    → 冲突时抛 IntegrityError 而非静默去重
  - WP 只把 `client_msg_id` 塞进 extra JSON，**不写 msg_id 列**
    → `uniq_dmmsg` 完全管不到它
  - WS 用本地 `time.time()`、WP 用 `create_time`，ts 有差异
    → fallback 索引也失效 ⇒ **同一条消息必然重复入库**
- **修复**：三处裸 INSERT 全改 `INSERT OR IGNORE` 且写入 msg_id；
  WP 侧 ID 归一化（优先服务端 `msg_id`/`server_msg_id`，
  `client_msg_id` 仅兜底并保留在 extra 溯源）
- **实测**：WS + WP 写入同一 msg_id → 1 条；不同 msg_id → 正常 2 条 ✓

### 1.3 跨通道方向判定不一致（违反 08 §13.5 铁律）
- **证据**：`wp_recv.py:152`（旧）vs `conversation_capture.py:602`
- **问题**：`role = "me" if sender and my_uid and sender==my_uid else "them"`
  在 **sender 为空 → them**；而 capture 是 **空 sender → me**
  （自动欢迎语/自动回复本系统产生）。同一条消息走 WS/WP 得到相反 role
- **修复**：统一为 `not sender → me`，与 capture 一致

### 1.4 事件循环阻塞（前端整体卡死的根因之一）
- **证据**：`api/accounts.py`（list_accounts/check_account/self_check）、
  `api/messages.py`（refresh_conversations）
- **问题**：async 路由内**同步调**重型函数：
  - `verify_account`（含 `get_my_uid` 外网探活，1~8s）
  - `capture_all`（含浏览器操作，数秒~数十秒）
  - `ensure_daemons_for`（含 `time.sleep(0.5)` 轮询最多 30s）
  - `ThreadPoolExecutor.pool.map` **本身是同步阻塞**（虽让出 GIL，
    事件循环仍卡到最慢账号返回）
  ⇒ 期间 `/api/overview`、`/api/live/stream` 等 3s/5s 轮询全部排队
- **修复**：全部改 `run_in_executor`；self_check 由串行 N×8s 改线程池并发

### 1.5 缓存错配：TTL 3s vs 轮询 30s（每轮都真实外网探活）
- **证据**：`api/accounts.py:34` `_VERIFY_TTL=3.0`；
  `App.tsx:164` `refetchInterval=30000`；`main.tsx:14` `staleTime=20000`
- **问题**：3s TTL 意味着 **30s 轮询永远命中不了缓存**，
  每次都真实跑 `verify_account`（含外网探活），N 账号 = 每 30s 一轮 N 次外网请求
- **修复**：`_VERIFY_TTL` 3s → **25s**（略小于 30s 轮询间隔，既保鲜又命中缓存）

### 5.2 结论：profile 锁冲突已基本根治，残余风险转移为两类

**A. BCC 内部占线（锁维度）**：
1. 单 asyncio.Lock + 单 page：capture_userinfo（最长 180s）、wp_send DOM 流程（数十秒）、
   scan_login（关 context 独占）互相排队，后到者只能干等。
2. `/resolve_url` 用主 page `goto` 直播间 → **把常驻 chat 页导航走**，期间被动昵称 hook、
   WP 发送、页面级登录态探测全部失效，直到下个操作把页面导回 chat。
3. keepalive 的 page_state 探测、capture、wp_send 共用同一 page 的 DOM 状态
   （如 wp_send 会切换选中会话），虽然锁保证不崩，但状态互相踩。

**B. 凭证侧风控面分散（行为维度）**：
1. `get_my_uid` 外网探活 4 处独立发起：verify_account（25s TTL）、BCC keepalive
   （`_load_uid_from_env` 每 300s 真探）、recv_daemon 重连刷新、capture_all 链路。
2. 发送三源无统一配额：dispatch（imapi 直发）、AI 回复（/send → WS→WP）、手动发送
   （/send）。同账号三源同时活跃时频率叠加，是最现实的频率风控面。
3. `load_dotenv(env_path, override=True)` 写进程级 os.environ：backend 进程内
   多账号（监测+发送不同账号、capture_all 多账号循环）后加载者覆盖先加载者的
   环境变量，靠「加载后立即构造 auth」的时序纪律兜底，脆弱。

  或至少与 /send 共用同一 per-account token bucket）。三源一配额，AI 回复的随机延迟

- **P2 BCC 多 tab 化**：一个 context 内开常驻 tab——① chat 常驻 tab（昵称捕获 + WP 发送 +

### 实施中的关键决策（防后人误改）

1. **不做探活失败负缓存**：query/user 失败多为网络抖动，负缓存 60s 会屏蔽 keepalive 探活
   → 半登录态发现延迟 → 误触发重扫链。成功缓存已足够消除叠加探测。
2. **P3 不动 auth_helper.py:49 的 load_dotenv**（enrich_auth 内）：它服务于扫码链路
   （DYLoginApi 内部读 DY_COOKIES），单账号单次调用无串号场景；高频读路径
   （_load_auth_from_env）已全部文件化。
3. **闸门在 recv_daemon 而非 backend**：backend 是多线程 asyncio，闸门放发送最终汇聚点
   （recv_daemon 进程内串行），且 WP 兜底（BCC wp_send）也建议后续纳入——当前 WP 仅
   作为 WS 失败的降级通道，触发频率低，暂不加闸（避免降级路径被限流卡死）。
4. **dispatch 兜底直发保留**：recv_daemon 未启动时直播功能不能死。兜底路径会打
   warning（`发送闸门失效`），便于日志审计风控暴露窗口。

## 第六轮：本账号卡片污染（2026-09-07，D 方案根因修复）

### 现象
尚进工伤小助理私信列表 77 个会话中 **32 个显示为本账号昵称「尚进工伤小助理」**，
peer_id 字段全部 = my_uid(316276709526638)。另 45 个昵称正常（Allen历史、一路向前…）。

### 根因（实测确认）
`parse_init_protobuf(raw, my_uid)` 里取对端逻辑：
```python
peer_uid = uid_b if uid_a == my_uid else uid_a   # 第 594 行
```
**my_uid 失效**（auth.get_uid() 偶发返回空/None，str() 后成 "" 或 "None"，
不抛异常所以外层 except 不触发）→ `uid_a == my_uid` 恒 False → **恒取 uid_a**
→ 而抖音 conv_id 里 uid_a 常是本账号 → peer_uid=自己 → peer_name 回填本账号昵称。
另 45 条正确的，是恰好 conv_id 里 uid_a 是对端（顺序不同）。

### 修复（4 处，conversation_capture.py）
1. **my_uid 自愈**（parse_init_protobuf 开头）：my_uid 无效时，从首包全部
   conv_id 统计 uid 频次，**出现次数 ≥ 会话数×0.9 的即本账号**（自己与所有人
   聊天，必然出现在每个 conv_id）。自测 77 会话 → 命中 77 次，100% 正确。
2. **第二道防线**（主解析 594 行 + fallback 910 行）：若算出的 peer_uid == my_uid
   → 置 None，降级裸 UID，**绝不用"自己"冒充对端**。
3. **写库订正**（写 dm_conversations 前）：用 conv_id 重解析真实对端覆盖
   错误 peer_uid；peer_uid 为空时昵称置空（不写"自己"）。
4. **存量一次性订正**（conn.commit() 后）：扫全表 peer_id==my_uid 的记录，
   用 conv_id 改回真实对端 UID，昵称降级为 UID 占位（下次 BCC 截获回填）。

### 铁律合规
全程**零主动请求**：只复用首包 bytes 与已截获的 BCC 昵称字典，未调用任何
bulk_user_info / get_im_user_info 等死代码接口。符合"昵称唯一来源=BCC 被动 hook"。

### 验证基准
- 修复前：`SELECT COUNT(*) ... WHERE peer_id=my_uid` = 32
- 修复后（点「更新会话」触发 capture_all 后）：应降为 0，且 32 条显示为裸 UID，
  待下次 BCC 截获真实昵称后自动回填。
