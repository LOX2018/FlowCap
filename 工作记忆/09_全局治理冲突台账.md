## 一、已修复（本轮落地）

### 1.1 DB 多进程写竞争（高危）
- **证据**：`backend/database.py:45-65` `get_db()`
- **问题**：只有 WAL（解决读写不互斥），**没有 `busy_timeout`**。
  backend + N×recv_daemon + BCC 并发写同一 db → 直接抛
  `database is locked`（默认 5s 且不重试）
- **修复**：`connect(timeout=30)` + `PRAGMA busy_timeout=30000`

### 1.2 双通道重复落库：唯一索引建了却没生效（高危）
- **证据**：`database.py:141-160` 建了 `uniq_dmmsg(account,conv_id,msg_id)`
  与 `uniq_dmmsg_fallback(account,conv_id,role,text,ts_ms)`
- **问题**：
  - `recv_daemon.add_message` / `wp_recv` / database JSON 迁移用**裸 INSERT**
    → 冲突时抛 IntegrityError 而非静默去重
  - WP 只把 `client_msg_id` 塞进 extra JSON，**不写 msg_id 列**
    → `uniq_dmmsg` 完全管不到它
  - WS 用本地 `time.time()`、WP 用 `create_time`，ts 有差异
    → fallback 索引也失效 ⇒ **同一条消息必然重复入库**
- **修复**：三处裸 INSERT 全改 `INSERT OR IGNORE` 且写入 msg_id；
  WP 侧 ID 归一化（优先服务端 `msg_id`/`server_msg_id`，
  `client_msg_id` 仅兜底并保留在 extra 溯源）
- **实测**：WS + WP 写入同一 msg_id → 1 条；不同 msg_id → 正常 2 条 ✓

### 1.3 跨通道方向判定不一致（违反 08 §13.5 铁律）
- **证据**：`wp_recv.py:152`（旧）vs `conversation_capture.py:602`
- **问题**：`role = "me" if sender and my_uid and sender==my_uid else "them"`
  在 **sender 为空 → them**；而 capture 是 **空 sender → me**
  （自动欢迎语/自动回复本系统产生）。同一条消息走 WS/WP 得到相反 role
- **修复**：统一为 `not sender → me`，与 capture 一致

### 1.4 事件循环阻塞（前端整体卡死的根因之一）
- **证据**：`api/accounts.py`（list_accounts/check_account/self_check）、
  `api/messages.py`（refresh_conversations）
- **问题**：async 路由内**同步调**重型函数：
  - `verify_account`（含 `get_my_uid` 外网探活，1~8s）
  - `capture_all`（含浏览器操作，数秒~数十秒）
  - `ensure_daemons_for`（含 `time.sleep(0.5)` 轮询最多 30s）
  - `ThreadPoolExecutor.pool.map` **本身是同步阻塞**（虽让出 GIL，
    事件循环仍卡到最慢账号返回）
  ⇒ 期间 `/api/overview`、`/api/live/stream` 等 3s/5s 轮询全部排队
- **修复**：全部改 `run_in_executor`；self_check 由串行 N×8s 改线程池并发

### 1.5 缓存错配：TTL 3s vs 轮询 30s（每轮都真实外网探活）
- **证据**：`api/accounts.py:34` `_VERIFY_TTL=3.0`；
  `App.tsx:164` `refetchInterval=30000`；`main.tsx:14` `staleTime=20000`
- **问题**：3s TTL 意味着 **30s 轮询永远命中不了缓存**，
  每次都真实跑 `verify_account`（含外网探活），N 账号 = 每 30s 一轮 N 次外网请求
- **修复**：`_VERIFY_TTL` 3s → **25s**（略小于 30s 轮询间隔，既保鲜又命中缓存）

## 二、已定位、待修（按优先级）

### 2.1 凭证无唯一真相源 —— ✅ 已修（2026-09-06，用户决策根治）
- **证据**：4 份副本并存
  1. 账号 `.env`（唯一被 `save_credential` 写的正式落盘点）
  2. **项目根 `.env`**——实测含全部 7 个 `DY_` 凭证键（2026-08-15 陈旧），被
     `common_util.load_env()` 的**裸 `load_dotenv()`**（无参数=从工作目录
     向上找任意 .env）读进来 ⇒ **陈旧平行副本，会覆盖账号真实凭证**
  3. 浏览器 profile 里的实时 cookie（BCC 独占）
  4. 各进程内存里的 `DouyinAuth` 副本
- **同步链断裂**：BCC `run_keepalive` 只做探活+scan_login，
  **从不调 `refresh_cookie_to_env`**（保活心跳根本不刷新 .env，
  只在有人 POST `/cookie` 时才写）；`recv_daemon.my_uid` 在
  `AccountInbox.__init__` 算一次后**永不刷新**
- **已修（用户选根治方案）**：
  1. 根 `.env` 的 7 个 DY_ 键全部清空，备份 `.env.stale_backup_20260906`
  2. `common_util.load_env(env_path=None)` 加护栏：
     - 传 `env_path` → 只加载该账号 .env（`override=True`，账号内自洽）
     - 不传 → `override=False`，**只补充缺失键，绝不覆盖账号凭证**
  3. 铁律：凭证唯一真相源 = 各账号 `auto_dm/accounts/<name>/.env`；
     **禁止**在根 .env 存放任何 DY_ 凭证键
- **实测**：测试目录 3 个账号 .env 各含 7 个 DY_ 键完整；
  测试目录根 .env 本身干净（0 个 DY_ 键），清理无风险
- **仍待修**：keepalive 不回写 .env（2.1a）、`recv_daemon.my_uid` 不刷新（2.1b）

### 2.2 端口碰撞 —— ✅ 部分已修（2026-09-06）
- **证据**：`auto_dm/accounts.py:148-151`（browser 10000-10499 / recv 10500-10999）
- **问题 A（已修）**：browser / recv 用**同一个 `crc32(name)` 值**，仅 base
  不同 ⇒ 两守护端口偏移**完全同步**，某账号在 browser 段撞车则 recv 段
  必然也撞车，且是「同一对账号互撞」，表现为守护互相串号
  - **修复**：`_stable_port` 新增 `salt` 参数 —— browser 用 `"|bcc"`、
    recv 用 `"|recv"`，错开哈希输入
  - **踩坑**：`accounts.py` 里存在**两处 `recv_daemon_port` 定义**，
    后面无 salt 的旧版本会覆盖前面的新版导致修复失效；已删除重复定义
  - **⚠️ 部署影响**：recv 端口值变化（工伤小助理 10632→10883），
    **必须先停全部守护再覆盖二进制**，否则新旧端口对不上
- **问题 B（未修）**：500 槽位固有的碰撞率（20 账号≈32%，生日悖论），
  受 span 限制。彻底解决需扩大 span 或引入碰撞检测，待评估
  （扩大 span 同样会改变所有端口，需与 A 的部署一起做）

### 2.3 BCC spawn 路径 —— ✅ 已收敛为 1 条（2026-09-06）
- **证据（原 4 条）**：`src-tauri/src/sidecar.rs`（Rust）、`main.py:146`、
  `daemon_launcher.py:88`、`accounts.py:233`（懒加载）
- **问题**：谁都能拉、彼此不知道对方拉过；Tauri 侧与 Python 侧职责重叠。
  其中 `daemon_launcher` 那条**绕过 `ensure_bcc` 的启动冷静期与防重复拉起
  保护** —— 更新会话/凭证校验走到这里就直接拉起浏览器，
  这是「启动时 BCC 快闪唤醒」的**结构根因**
- **已修**：
  1. `daemon_launcher.ensure_daemons_for` 改为统一委托
     `acct_core.ensure_bcc(account, wait_ready=wait)`，不再自己 spawn
  2. `ensure_bcc` 内置：启动冷静期（`DY_BCC_LAZY_DELAY`，默认 30s）、
     端口双检锁、防重复拉起、等就绪
  3. `main.py` 启动路径：`DY_BCC_ON_START=1` 才拉（默认关闭）
  4. 保留 Rust sidecar 路径（前端「启动/停止守护」按钮，用户显式操作）
- **现状**：Python 侧只剩 `accounts.ensure_bcc` 一个拉起入口

### 2.4 通道路由无健康检查 / 自动降级
- **证据**：前端单选 `messages.tsx:613` + 后端硬分支 `api/messages.py:556`

### 2.5 过滤只在读侧，脏数据仍入库并计入未读 —— ✅ 已修（2026-09-06）
- **证据**：`api/messages.py:334-344` 的 `NOT LIKE` 只在查询时过滤
- **问题**：脏数据已入库、`unread+1` 已累加 ⇒ **会话列表显示未读，点开空白**
- **已修**：过滤前移到写侧
  - 新增 `recv_daemon._NOISE_PATTERNS` + `_is_noise_text()` 作为
    **写侧与读侧共用的唯一规则源**（避免两侧规则漂移）

    `[分享视频]` / iesdouyin 分享链接 → 不写 dm_messages、不累加 unread
- **实测**：6/6 用例通过（脏数据全命中，正常消息不误杀）
