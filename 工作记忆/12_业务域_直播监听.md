# V2 直播解析与监听（2026-08-20 整理）

> 符合当前 V2 架构的直播相关链路。

## 一、解析房间号（api/live.py + backend/link_resolve.py）
- 后端 `POST /api/live/resolve` 调 `link_resolve.resolve_live_id(raw)`，返回 `(live_id, src)` 元组需解包。
- 成功写运行时 `settings.live_url`（供 engine.start 读取）+ 落盘 `data/config.json`；返回 `{ok, liveId, liveUrl}`。
- 路由装饰器必须用 `@router.post`（文件内无 `app` 对象，误用 `@app.post` 会 `NameError`）。
- 情形：纯数字短 ID / 抖音 URL / 分享文案提取 web_rid（情形 23 需指纹浏览器 vbrowser）。

## 二、直播流采集（core/live_hook.py）
- `LiveChatHook`（继承 DouyinLive 基类）处理 protobuf 消息：Gift→"gift"、Chat→"danmaku"、Member→"enter"、Like→"like"、Social→"follow"、RoomStats→`_on_room_stats`。
- `feed`（deque maxlen=500）、`room_stats`、`heat_series`（deque maxlen=180）。
- 弹幕提交门控仅要求 `nickname`（与 web_probe 对齐），缺失 user_id/sec_uid 的弹幕用 nickname 作 key 去重，不再被丢弃。
- `_on_room_stats` 在线/点赞解析：支持数字+单位、单位+数字两种顺序，万/k 换算，互不污染；兜底 displayLong→displayMiddle→displayShort。

## 三、引擎状态与统计
- 直播引擎（listening/running）与私信引擎（dmRunning/dmPaused/dmQueue/dmSent）两枚独立徽章。
- 实时评论统计列表来自 `adm.dispatch.records`（api/tasks.py `_records_from_adm`），status 英文枚举 captured/sent/fail/skipped。
- 历史任务（tasks_history.py）：start_task 记运行中任务到 `data/task_history.json`，finish_task 更新结果条数/records 快照；前端任务中心历史任务可跳转查阅模式。

## 四、中控台（web_probe）
- 只用指纹浏览器（禁止回退原生 Playwright），不可用时 `logger.error` 跳过、return。
- 弹幕来源 target 可能只带 nickname（user_id/sec_uid 为 None），调度层用 nickname 兜底去重。

#### ⚠️ 重要修正（2026-09-09 晚，用户指正 + v16 实测）

**`is_turn_on=0` 不等于"主播关闭了连麦"！**
v16 实测抓到：页面显示「暂时离开 / 休息片刻，更多精彩马上到来」，`/webcast/room/web/enter/`
返回 `status=3`。

**status 语义（实测）**：
- `status=2` = 主播正常直播
- `status=3` = **主播暂时离开**（切出直播间）→ 此时 `is_turn_on` 临时变 0，连麦暂停

**正确判定连麦是否可用**：必须**同时**满足
1. `enter.status == 2`（主播在线直播，不是"暂时离开"）
2. `get_settings.is_turn_on == 1`
3. 页面文本不含「暂时离开 / 主播不在 / 已下播 / 直播已结束」

任一不满足 → 点击「申请连线」都会走 onClick 的 `if(!I){...return}` 静默返回。

**教训**：单次抓到 `is_turn_on=0` 就下"主播关闭连麦"的结论是**采样偏差**——
必须先确认主播在线状态，否则会把临时状态当成永久配置。

### 5.5 关键坑（踩过的，禁止重犯）

- ❌ **按钮文本是「申请连线」不是「申请连麦」**：不同直播间文案不同，v1/v2 探针只匹配「连麦」导致 0 命中。
- ❌ **按钮 24 秒才出现**（用户实测：进房 18s、按钮 24s）。只等 8~9 秒必然抓不到或抓到错误元素。
- ❌ **用户 XPath `//*[@id="BottomLayout"]/div[@class="mJFWV6sM CSAsqRrd YuhFoReA"]/button` 未命中**：class 是动态哈希（实测为 `gwq9bZom zpfnyHM7 Rewt1hLn`）。**必须用 `//*[@id="BottomLayout"]//button[@type="button"]` + 文本匹配**，不要用固定 class。
- ✅ **必须开虚拟麦克风**：`--use-fake-device-for-media-stream` + `--use-fake-ui-for-media-stream` + `permissions=["microphone","camera"]`。
  实测：`navigator.permissions.query({name:'microphone'}).state === "granted"`，`getUserMedia` 返回 `Fake Default Audio Input`（state=live）。
  **指纹浏览器不能开真实麦克风**（用户铁律），虚拟设备是唯一可行方案。
- ✅ **点击后会弹「请选择麦克风输入」对话框**（Fake Audio Input 1/2 + 确定按钮），必须选设备并点「确定」才能继续。
- ✅ BCC 的 `/exec_js` 端点**硬限制在 /chat 页**（源码 `_do` 里检测到非 /chat 就 `goto` 回 chat），**无法用它驻留直播间页面**。需要在直播间做交互必须另起浏览器（V6 范式）。

3. `list/v2` 响应含自己 uid（注意：实测 join_channel 后 list 里**只有主播**，

**虚拟麦克风状态（实测）**：
- 连麦中 `getUserMedia` 返回 `Fake Default Audio Input`，`muted=false, readyState=live`

### 5.8.2 silence 闭麦接口实测（2026-09-10，v29）

连线保持期间（join_channel 已发、check_audience_linkers 正常轮询）调用闭麦：

| 尝试 body | 结果 |
|---|---|
| `mute=1` | `status_code=10011`「Request params error」 |
| `status=1` / `mute_status=1` / 空 body | 同样 10011 |

**结论**：`silence/` 接口存在但**纯 fetch 拼 body 过不去**——和 `apply/` 一样，

确认 fake device 输出的是持续正弦波，**连麦期间电平检测无法用作"静音"判据**。
「无音频输入」的正确判据：`silence_status=1`（平台侧状态）或页面闭麦图标状态。

### 5.8.4 ★ 闭麦实测：音轨强制 0 输入（2026-09-10，v30，用户方案采纳）

**「虚拟麦克风 0 输入」实测成功**：

```

track.enabled = false 之后：    peak = 0        ← 0 输入达成
轨状态：{muted: false, enabled: false, readyState: "live"}
设备详情：Fake Default Audio Input, 48kHz/16bit/mono,
         echoCancellation=true, noiseSuppression=true, autoGainControl=true
```

**结论**：`track.enabled = false` 是可靠的编程式闭麦——上行变成静默帧，
等效「麦克风 0 输入」。全程零真实设备（label 一直是 Fake）。

**工具条 dump 结果**：连线后底部区域只找到 5 个候选元素，**无麦克风图标**
（闭麦入口可能：悬停显示 / 在主播端控制 / 需展开更多面板）。
本次点击路径未触发 silence/mute 接口（v29 直调 10011 的前提下，
页面自己也没发 mute 类请求）。

**对产品实现的结论（接口优先 + 0 输入兜底）**：
1. 首选：连麦 SDK 层闭麦（WebRTC sender 替换为静音轨 / track.enabled=false）
   —— 不需要抖音接口，纯浏览器端即可实现 0 输入
2. 平台侧状态同步（silence_status）暂无法直调接口（10011 签名问题），
   DOM 图标状态可作为辅助显示
3. 后续如需真接口：抓页面「静音」按钮的原生调用（本服务端签名机制待逆向）

## 七、2026-09-21 补充：引擎状态被误收尾导致前端控件全失效（ENG-015）

> 完整案例：`工作记忆/cases/2026-09-21_直播监听前端进程控件全失效_握手窗口误收尾_v0.44.17.md`

### 现象判据（强判据，可直接定位）

**弹幕流正常 + AI 生成正常 + 私信照发，但前端引擎徽章与「暂停/继续/停止」全灰**
= 状态机被写坏，**不是采集链路坏了**（两条路径互相独立）。

### 根因（两处连坐）

1. `DispatchCenter._loop` 触发 `on_idle` 后**自行** `self.on_idle = None`
   —— 把「只触发一次」这个**上层状态机语义**硬编码进通知方；而队列空在
   **WS 握手窗口内是必然的正常中间态**，唯一的触发机会被它吃掉。
2. `AutoDM._on_dispatch_idle` 的存活判据 `self.live.ws is not None`
   —— `ws` 由 `run_forever()` 内部赋值，**握手窗口内恒 None**
   → 正在启动的监听被判成「已死」→ 落 `STOPPED`。

实机：收尾发生在 `[live-ws] 连接已建立` **前 1 秒**。

### 修复要点

- `dy_live/server.py` 新增 `_ws_alive`：**置活在 `start_ws()` 入口**（覆盖握手窗口），
  置死仅在「主动停止」与「取不到房间信息」两处；**重连空隙保持 True**。
- 抽 `_listen_line_active()` 作唯一真源：`_on_dispatch_idle` / `snapshot()` /
  `/api/live/stream` 三处共用（此前三处各写一份，改一处漏两处）。
- 调度器不再自行解绑，新增 `detach_on_idle()` 把解绑权交回上层。

### 三条通用判据（写同类代码前必过）

1. **判据必须覆盖「已发起 → 已确认」的完整区间**：问一句「意图已发起但尚未确认时，
   这个判据返回什么」。返回 False = 把「正在启动」判成「已死」。
   （同族：`ws is not None`、`_port_open`、`pid_exists`。）
2. **「只触发一次」的语义属于上层，不属于通知方**：通知方只报告事实。
3. **新回归测试必须做「回退验证」**：临时回退修复 → 必须变红 → 还原变绿。
   全绿只证明断言没报错，不证明它在守不变式（本例回退后红 3 项，是真守住了）。


## 八、2026-09-21 补充：软停止卡死（ENG-016）与直播流凭证解耦（ENG-017）

> 完整案例：`工作记忆/cases/2026-09-21_软停止卡死与直播流凭证解耦_v0.44.18.md`

### 8.1 「点击停止监听后控件无变化」= 软停止卡死

**判据**：`stop(hard=False)` 后状态卡在 `stopping`，耗时 = 那条待发记录的
**随机延迟窗口**（实测 50s，`delay_range` 上限可达 ~120s）才转 `stopped`。

**根因（两点叠加）**：
1. `DispatchCenter._loop` 无条件 `await asyncio.sleep(item.send_at - now)`，
   软停止（`_accept_new=False` 但 `_stopped` 未置）**不打断它**；
2. 软停止后该记录必然走不到发送（闸门拒收），却仍要睡满才在 `_do_send` 里
   `pending.pop` —— 而 `wait_done()` 与 `on_idle` 的收尾条件**都要求 pending 为空**
   ⇒ 两条收尾路径被同一条记录同时堵死。

**修复**：新增 `_stop_signal`（`asyncio.Event`），等待改为
`wait_for(_stop_signal.wait(), timeout=...)`；被唤醒即丢弃该目标并清 `pending`。
`stop_hard`/`stop_soft` 置位，`start()` 清除。**实测 50s → 2.5s。**

### 8.2 直播流连接与凭证解耦（用户架构判断，实测成立）

**用户原话**：「抖音的直播本身是支持匿名连接查看的，凭证是为了部分直播间昵称
加密需要写入有解密权的凭证使用。不能因为凭证失效就连直播流都无法连接。」

**实测证实**（零账号凭证）：匿名进房拿到 `room_id` + `status=2` + `ttwid(127)`
→ 匿名 WS 握手成功 → 收到 6 帧。

**修复前的耦合点**：`AutoDM._run` 在 AUTH-018/019/020/021 四处**直接 return 并置 IDLE**
⇒ 凭证失效 → 引擎回 IDLE → `LiveChatHook` 从未创建 → 连流都建不起来。

**解耦后的两条线**：

| 线 | 凭证 | 缺失时 |
|---|---|---|
| 监听线（进房 + WS 收弹幕） | 不需要 | 匿名（ttwid）继续 |
| 增强线（昵称解密 + 私信发送） | 需要 | 降级「只听不发」，捕获记录仍入库 |

**⚠️ 实现坑**：`DouyinAPI.get_live_info(auth_=None)` **会 AttributeError**
（内部 `cookies=auth_.cookie`）。匿名路径必须自建请求
（`LiveChatHook._anon_live_info()`），不要复用该函数。

### 8.3 三条通用判据

1. **「等资源就绪」的 sleep 必须可被停止打断** —— 否则停止操作要等满整个等待窗口，
   表现为「点了没反应」。
2. **收尾判据不能依赖「只有正常路径才会清」的状态**：任何「等 X 为空」的收尾，
   都要检查 Y 路径异常/被拒时 X 是否也会被清（本例 pending）。
3. **能力解耦要落到判据层，不能只改文案**：`_run` 里 4 个 `return` 是耦合的实体，
   不是只把 error 改成 warning 而保留 return —— 要去掉的是 return 这个"耦合实体"。

### 🔴 两条必读判据（本轮实测得出）

1. **「schema 驱动 = 前端零改动」只在「新增字段」维度成立。**
   `UnifiedConfigSection` 确实是 schema 驱动，**但其调用方 `settings-page.tsx`
   对每个 tab 用显式白名单** `onlySections={["live"]}` —— 新增**字段**无需动前端，
   新增**分区**必须把分区名登记进目标 tab 的白名单（一行）。
   ADR-002 §3.5 原文「前端零改动」已就地修正（见 ADR §7）。
2. **配置写操作必须独立回读验值，`ok:true` 不算数。**
   实测：把 body 形状写错（`{sec:{...}}` 而非 `{"sections":{sec:{...}}}`）时，
   pydantic 把非法 body 静默变空，接口仍 `200 ok:true`、值**未变**。

### 13.1 跨账号沉淀池（CrossAccountSink）

DB 新表 `dm_cross_sink`（`database.py:231`），主键 `peer_uid`，字段含 `account_sent`、`cool_until`、`send_count`。与 `dm_uid_sink`（主键 `(account, peer_uid)`）**并存**，由 `sink_global_scope` 开关选择路径。

`services/dm_dispatch.py:548` 的 `CrossAccountSink`：

| 方法 | 职责 |
|---|---|
| `should_send(peer_uid)` | 全局唯一裁决：查内存 + DB 缓存，冷却期内返回 False（含永久冷却） |
| `mark_sent(peer_uid, account, ...)` | 标记已发送：写 `dm_cross_sink`（INSERT ON CONFLICT）+ 内存一级缓存 |

冷却值取自 §5.4 `live_orchestration.sink_cooldown_days`（默认 90 天）/ `sink_permanent`，通过 `_live_orch_cool()` 读取。**permanent 时 `cool_until=-1`**。

### 13.2 轮转分配器（RotationAllocator）

`services/dm_dispatch.py:624`，三种策略（同 §5.4 枚举）：

| 策略 | 规则 | 持久化 |
|---|---|---|
| `per_target`（默认） | 同一 uid 轮询交替账号 | 内存 `_last_sender` |
| `per_time_window` | 30 分窗内同一账号，窗满递补 | 内存 `_window_sender` |
| `per_room` | 固定由首个启动账号发送 | 内存 `_room_owner` |

> ⚠️ 全部仅存内存，进程重启后重置。

### 13.3 接线全景（submit_by_uid → _send_one）

```
submit_by_uid(account, peer_uid, text)
  ↓ sink_global_scope=true?
  ├─ rotation.pick_account(peer_uid, active_accounts, strategy)   ← 选发送者
  │  └─ 若选了 ≠ account → 当前请求静默丢弃（该 uid 已交其他账号）
  ├─ cross_sink.should_send(peer_uid)                              ← 跨账号去重

_send_one() 成功发送后：
  └─ cross_sink.mark_sent(peer_uid, account, source)              ← 写跨账号冷却
```
