## 三十八、v0.43.11：跨调用窗口租约接线 —— 昵称「抓到但没入库」的两次进程分裂（2026-09-14）

> 本节承接 §三十一（DOM 方案）与 §三十七（预热缓存）。**症状相同（前端只显示数字），
> 但根因完全不在捕获侧**，而在 **backend ↔ BCC 两个进程之间的租约协商**。
> 逐节对照的价值：§三十一 修的是「抓到没有」，本节修的是「抓到了为什么传不回来」。

### 一、症状与关键矛盾

- 用户：「更新会话 hook 失败、捕获入库失败、前端只显示数字」
- 实测：**BCC 进程内抓到 37 个昵称，backend 收到 0 个**，事件相隔 7 秒。

这一矛盾点是本节全部定位工作的锚点 —— 一旦成立，
`DOM 选择器 / hook 注入 / 滚动轮次 / 无头有头` 全部被排除，
唯一嫌疑落在「BCC → backend 的返回通道」。

### 二、链路（源头 → 传播 → 终端）

```
源头① conversation_capture.capture_all
        ensure_browser(purpose=AUTO) → 取得租约 lease_id=83a780e866e2（gate:auto / prio=1）
        ✗ 该 lease_id 只存局部变量 _g，**从未向下传**
源头② capture_userinfo_via_browser(name)          ← 签名无 account、无 lease
源头③ POST /capture_userinfo  {"wait": 15}        ← 请求体无 lease_id
源头④ BCC _exec: _is_reentry = bool(lease_id and …) ← lease_id="" ⇒ 判为并发冲突
传播   _lease_acquire(bcc-internal, prio=2) 被拒 → ContainerBusy
终端   BCC-047 → BCC-030 → 昵称 0 个 → peer_name=peer_id → 前端显示数字
```

**性质：自我死锁。** 同一进程 5 秒前给自己拿的租约，把自己 5 秒后的请求挡在门外。

### 三、为什么之前一直没发现（三层都「看着对」）

| 层 | 看起来的样子 | 实际 |
|---|---|---|
| 设计文档 | §3.6 写明「更新会话全程 = 跨调用窗口，显式 lease + release，_exec 复用同 lease_id」 | 只是规划，**从未实现** |
| `_exec` 重入判据 | 「只认显式 lease_id」注释严谨、逻辑自洽 | 自洽的前提（调用方传 lease_id）不成立 |
| 错误码 | BCC-047「租约冲突被拒」有码有日志 | 冲突的双方其实**是同一个调用链**，码本身不揭示这一点 |

`grep -rn "release_lease" backend --include=*.py` → **全仓零调用点**，
是「这一类改动只写在文档里」最直接的取证。

### 四、并发修复的其余四项（同轮一并，见 07 §三十六）

1. **两套缓存不共享 + 时序错配**：BCC `_prewarm` 161.5s 写 BCC 侧缓存；
   backend 侧缓存是另一份，且请求早于预热完成 7s。
2. **早退判据读废弃计数器**：hook 的 `__CAP_USERINFO__.map` 恒 0（v0.43.9 已证）
   → `_cur <= _prev` 恒真 → 第 3 轮必 break，44 会话只滚 4 屏。
   判据改用 `_dom_total`。
3. **用途分类错**：滚动实测 161.5s vs `PURPOSE_AUTO` 的 ttl 上限 180s，同量级 →
   `BCC-046 租约超时强制回收` 连爆 4 次。改 `PURPOSE_USER`（ttl≤300s）。
4. **假成功结构**：拿不到 BCC 只 `warning` 不 return → 前端看到「1.6s 完成」实则昵称 0 个。

## 三十九、v0.43.11 方案 A+B：DOM 昵称 ↔ peer_uid 的精确关联（2026-09-14 实机确证）

> 承接 §三十八（租约修复）。租约打通后昵称**已能传回**（0 → 83），
> 但落库仍 44/44 未命中 —— 本节解决「**传回来了却对不上人**」。
> 这同时是「前端只显示数字」的最后一块。

### 一、实机证据（全部为本轮实测，非推断）

**证据1 · DOM 项没有任何 uid 属性**
```javascript
// /exec_js 抓 consoleConversationItemwrapper 的全部属性
{ cls: "conversationConversationItemwrapper",
  attrs: { "data-e2e": "conversation-item", "class": "..." },   // ← 仅此
  fiberKeys: [], propsKeys: [], dataset: {"e2e":"conversation-item"},
  allAttrsDeep: [ rowArea1, commonIMAvataravatarContainer, semi-avatar,
                  IMG[src=aweme-avatar/...], rowArea2, titleWrapper,
                  conversationConversationItemtitle, ...TitletimeStr,
                  ConversationItemDescleft, ConversationItemHinttextBox ] }
```
过滤全页 `*[uid|conversation|conv_id|cid]` → **0 命中**。

**证据2 · 点击会话不改变 URL**
```
click 前: https://www.douyin.com/chat?isPopup=1
click 后: https://www.douyin.com/chat?isPopup=1    ← 无 uid/conv_id 追加
```
⇒ **DOM 侧拿不到 uid**，`/chat` 是纯前端路由。

**证据3 · WS 的 `sender_nickname` 实测恒为 None**
```bash
grep -aho "sender_nickname=[^,]*" recv_daemon_*.log | sort | uniq -c
# 结果：27947 条全部 "sender_nickname=None"，非空 0 条（覆盖 8-31 ~ 9-14 共 15 天）
```
⇒ 原「B 方案」按字面理解（用 WS 的 sender_nickname 回填昵称）**不可行**。

**证据4 · WS 的 `sender` 是真 uid，但只在 role=them 时等于对端**
```
conv=0:1:3162… sender=316276709526638 role=me    (390 条)  ← sender=本号
conv=0:1:3162… sender=3887506227210423 role=them  (9-13)   ← sender=对端 ✅
```
⚠️ 这证明原代码 `peer_id=sender` 是**污染源**：role=me 时把 peer_id 写成了本号，
正是 `capture_all` 要花大力气做「存量订正」的原因。

**证据5 · protobuf 字段（static/Response.proto 反序列化自证）**
| 消息 | 字段 | 含昵称? |
|---|---|---|
| `GetConversationInfoV2Response`（连接初始化同步帧） | conversation_id / short_id / type / ticket | ❌ |
| `MessageBody`（new_message_notify） | … sender(field 7, int64) / content(field 8, JSON) | 仅 content 里可能有 |

⇒ 同步帧**不含昵称**，新消息帧才可能带。

### 二、方案 A（文本桥）—— 把 DOM 昵称精确接到 peer_uid

**核心洞察**：两端虽无共同 id，却有**共同的自然键 = 最后一条消息的正文**：
- 首包每个会话自带 `messages`（权威、天然带 uid 归属）
- DOM 每项的 `desc`（`[class*=ConversationItemDescleft]`）**就是该会话最后一条消息**的预览

实现（`conversation_capture.capture_all`）：
1. `CAP_DOM_SWEEP_JS` 新增抓 `desc`（昵称/头像/desc 三项）
2. 用首包消息文本建 `_text_to_uids` 索引（`text[:80] → {uid}`）
3. DOM 项的 desc 与之匹配（先精确 `desc[:80]`，再双向包含前 24 字兜底截断）
4. **仅当候选 uid 唯一**时写入 `_userinfo_by_uid[uid] = {nickname, avatar}`；
   歧义（≥2 候选）**显式计数并放弃**

**为什么必须"宁可不显示"**：群发欢迎语场景下同一条文本属于 N 个会话，
任何按顺序/位置的猜测都会张冠李戴 —— 这正是本轮 80 条「傲雪」事故的成因。
日志：`文本桥（方案A）：唯一关联昵称 N 个，歧义放弃 M 个，未匹配 K 个`。

**实测覆盖**（本轮探针，11 项 DOM）：唯一命中 1 项、被系统提示覆盖 9 项、过滤 1 项。
⇒ 桥的**上限受限于「DOM desc 是否为真实消息」**：未互关会话被
「对方回复你或互关之前…」占位覆盖 → 分不清对端 → 按设计放弃。

### 三、方案 B（WS 增强）—— 实际落地形态与原设想不同

| | 原设想 | 实际落地 |
|---|---|---|
| 昵称来源 | WS `sender_nickname` | **实测恒 None**，不能用 |
| peer_uid | `sender` | **只认 `conv_id`**（`0:1:uid_a:uid_b` 排除本号，100% 可靠） |
| 效果 | 回填昵称 | 昵称取不到就**留空**（绝不写裸数字 UID） |

改动（`recv_daemon._handle`）：
1. `_real_peer` 从 conv_id 推导（排除本号），不再 `peer_id=sender`
2. `peer_name = sender_nickname`（拿不到就 `None`），删除 `or sender` 兜底
3. 该行日志 `INFO → debug`（实测单日 564 行、15 天数万行刷屏）

### 四、新增铁律

1. **两端无共同 id 时，禁止任何「按顺序/位置」的对齐**——懒加载 + 新消息置顶
   必然错位。要么找自然键（文本/时间戳指纹），要么放弃。
2. **关联不到就留空，绝不猜**。展示层看到数字 UID 是可接受的降级；
   看到**别人的昵称**是数据污染，代价高得多（用户会据此发错消息）。
3. **`peer_id` 只从 `conv_id` 推导**（`0:1:uid_a:uid_b`），绝不用 `sender`
   —— `sender` 在 role=me 时就是本号。
4. **循环变量绝不在循环外使用**：`for _c in convs:` 之后的 `_c` 恒为最后一个元素。
   本轮 80 条「傲雪」即此（`convs.index(_c)` → 恒等于 len-1）。
   教训：`_` 前缀的临时变量同样会泄漏，静态检查（grep 循环外引用）比直觉可靠。

### 五、验证

```bash
python scripts/verify_nickname_link.py    # 16 项：静态 3 + 桥不变式 6 + B方案 5 + 回归 2
```
关键不变式用例：**群发同文本 → 一条都不写**、**任何情况下昵称不重复**。

实机判据（部署后）：
- `grep "文本桥（方案A）" logs/run_*.log` → 有「唯一关联 N>0」
- `select count(distinct peer_name) from dm_conversations where peer_name not glob '[0-9]*'`
  → 应 **> 1**（不再是单一值）
- `select count(*) ... where peer_name=peer_id` → 剩余的都是**合理降级**（未匹配）
- recv 日志不再出现「每消息一条 INFO」
