# DYAutoDM_v2 · 抖音直播间自动私信控制台

> 抖音直播间评论监听 → 自动定向私信的桌面工具。Tauri2 + React + FastAPI（唯一活跃代码库）。
>
> **当前版本：0.41.1** ｜ 最后校准：2026-09-11（数字均为实测）

---

## 一、项目定位

在抖音直播间监听用户弹幕/评论，按配置对指定主播的发言观众自动发送私信（话术词库随机抽取、延迟抖动拟真、去重防骚扰）。面向「主播运营 / 私域引流」场景。

核心能力：

- **直播监听**：拉起指纹浏览器进入直播间，捕获实时弹幕/评论（弹幕 WebSocket + 中控台采集双路聚合）。
- **自动私信**：捕获发言人后延迟发送（延迟区间可配，默认 40~120s 随机抖动）；话术支持词库随机抽取 + 每条独立开关；按 user_id / sec_uid / nickname 三套去重，杜绝同人重复骚扰。
- **私信收发闭环**：独立私信接收守护进程，按会话隔离拉取历史私信、可手动回复、支持图片。
- **多账号管理**：凭证守护 + 私信守护每账号独立；指纹浏览器扫码登录、双引擎校验（wp 凭证 / 私信凭证）；账号 = 1 个 Agent 模版 + 1 个配置标签。
- **AI 获客回复**：双知识库（reply_kb 命中即回零 token / pro_kb 思维导图 RAG）+ Agent 模版 + 54 个 AI 端点。
- **IM 通知网关**：QQ 官方机器人 / iLink 等入站通道，指令解析 + 授权审批 + 权限组（v0.38.5 起）。
- **会员体系 + 统一配置中心**：多会员数据隔离分库；配置收敛为「5 分区 / 45 字段」，带 apply 三分类（hot / restart_daemon / restart_backend）。
- **历史任务**：每次运行记录进 SQLite，可回溯、可跳转查看结果。

## 二、技术栈与架构

| 层 | 技术 | 说明 |
|---|---|---|
| 桌面壳 | **Tauri 2** (Rust) | 窗口 1280×720（最小 1024×680）+ 子进程管理 + 关闭时联动清理后端进程树 |
| 前端 | **React 18 + TypeScript** (Vite) | 9 个主 tab + 子页；28 个 `.tsx`（11 页面 / 14 组件） |
| 后端 | **FastAPI + Uvicorn** | 业务逻辑、抖音接口封装、守护进程编排；**16 路由模块 / 157 端点** |
| 样式 | 双主题玻璃体系 | `global.css` 884 行 + `theme-glass.css` 1,110 行；day / aerospace 双主题 + 可换主色 |
| 浏览器 | **指纹浏览器内核** (ungoogled-chromium + vb_chromium) | 扫码登录、直播间监听、中控台采集；**禁用原生 Playwright 回退** |
| 数据存储 | **SQLite**（WAL） | `database.py` 统一封装；会员维度分库（见 §五） |
| 打包 | **PyInstaller + Tauri build** | 3 个 Python sidecar + NSIS/MSI 安装包（仅正式发布） |

### 进程模型

```
┌─────────────────────────────────────────────┐
│  DYAutoDM_v2_<版本>.exe  (Tauri 壳 / Rust)   │
│   ├─ 启动→拉起 backend sidecar                │
│   └─ 关闭→ kill_tree 递归杀后端 + 守护        │
└─────────────────────────────────────────────┘
        │  HTTP 127.0.0.1:8000
        ▼
┌─────────────────────────────────────────────┐
│  dyautodm-backend-*.exe  (FastAPI 主后端)    │
│   /api/* 全部业务路由（16 模块）              │
└─────────────────────────────────────────────┘
        │ 每账号独立守护（懒加载 + 稳定端口）
        ▼
┌──────────────────────────┐  ┌──────────────────────────┐
│ browser-daemon (BCC 容器) │  │ recv-daemon (私信接收)     │
│ 端口 [10000, 11999]       │  │ 端口 [12000, 13999]       │
│ 常驻唯一浏览器 context     │  │ 私信 WS 长连接 / 会话隔离  │
└──────────────────────────┘  └──────────────────────────┘
```

- **端口分配**：`zlib.crc32(账号名) + salt` 稳定哈希（非 `hash()`，避免 `PYTHONHASHSEED` 跨进程不一致导致连不上）。加 salt 是为打破 browser / recv 两段的**同步撞车**（2026-09-06 治理）。常量见 `backend/auto_dm/accounts.py`：`_BPORT_BASE=10000 / _BPORT_SPAN=2000`、`_RPORT_BASE=12000 / _RPORT_SPAN=2000`。
- **守护懒加载**：账号守护按需拉起（并发去重锁 + 冷静期），不再启动即全量拉起。
- **代理隔离**：后端进程设 `NO_PROXY=*`，`DY_PROXY` 只注入浏览器进程。

## 五、数据存储（会员分库）

数据按会员维度物理隔离，`backend/services/member_store.py` 定义：

```
members/
├── registry.json          全局会员注册表（唯一跨会员共享文件）
└── <member_id>/           每会员独立数据空间（完全隔离）
    ├── data/dyautodm.db   SQLite 主库（WAL）
    ├── accounts/          账号凭证（AES 加密存储）
    └── logs/              运行日志
```

- 账号凭证 **AES 加密存储在本地**，不上传任何第三方服务器。
- 启动时 `database.get_db()` 初始化 SQLite，并自动 `_migrate_json` 把旧 JSON 数据并入。
- 主要表：历史任务 `tasks`、私信会话 `dm_conversations` + 消息 `dm_messages`、配置 `kv_store`（`config` 任务配置 / `app_config` 统一配置中心）。

## 六、关键业务链路

### 0. 后端启动流程（lifespan）
`main.py` 的 `lifespan` 在 FastAPI 启动期依次：
① 初始化 SQLite（WAL + 自动 `_migrate_json`）；
② 收尾上次进程遗留的悬空「运行中」历史任务（`fix_stuck_tasks` 按 pid 比对）；
③ 创建引擎主控单例 `AutoDM()` 挂到 `app.state.adm`，并显式注入通知模块（`api.notify.bind_adm`，避免 PyInstaller onefile 下 `from main import app` 反查失败）；
④ 后台线程预热账号校验缓存进 TTL 缓存，使账号管理页首屏秒出。关闭期释放引擎资源。

### 1. 凭证获取（扫码）
`api/accounts → auto_dm.accounts → dy_apis.login_api.get_login_auth`
→ 弹指纹浏览器（`vbrowser.launch_async`）→ 抓取四件套
（DY_COOKIES / DY_TICKET / DY_TS_SIGN / DY_CLIENT_CERT / DY_PRIVATE_KEY）
+ web_protect / keys（security-sdk 在登录态生成）→ 写回各账号 `.env`。
**单 profile 铁律**：每账号固定 profile，重扫前先停守护释放锁，绝不临时清目录。

### 2. 直播监听
`core/auto_dm._run` → `live_hook` 连直播间 WebSocket / 中控台采集 →
`on_message` 抽取 (nickname, comment, user_id, sec_uid) → `dispatch.submit`。

### 3. 延迟私信（双通道 + 自动降级）
`dispatch.submit`：去重（三套集合）→ 写 records（status=已捕获）→ 按
`capture_ts + random(延迟区间)` 入优先级队列 → 会话整理池 + **per-account 串行调度器**。
到点调用 `services/dm_dispatch` → **双通道发送**（ws ⇄ wp 互备，一条失败自动降级走另一条，两条都失败才算失败）
→ 成功更新 records（status=已发送）。
**验收语义**：发送端**同步等至最多 90s 到 `done` 才算成功**（受理即返回不算成功）。
发送上限达则停止；暂停只停监听与发送、存量私信发完才整体停止。

### 4. 私信收发
`daemon/recv_daemon` 连 `frontier-im.douyin.com` 长连接 →
消息按 `conversation_id` 隔离进 `AccountInbox`，持久化到 SQLite
（`dm_conversations` 会话骨架 + `dm_messages` 消息明细）；
`api/messages` 转发给前端（会话列表 / 回复发送）。

> **昵称铁律（风控级）**：昵称唯一来源是 BCC 被动 hook（复用账号常驻浏览器截前端自发 `im/user/info`，零主动请求）。**绝不**做后端批量查昵称。

### 5. 图片收发
发送链路见 [`docs/upload_flow.md`](docs/upload_flow.md)（STS → ApplyUploadInner → TOS 直传 → CommitUploadInner → batch_build_image → message/send，`aweType=2702`）。
接收侧 `auto_dm/origin_image_resolver.py` 用 `resource_url.skey`（AES-256-GCM）解密原图，HEIC 经 pillow-heif 转码。

### 6. 历史任务
`core/auto_dm` 启动时 `tasks_history.start_task` 记一条（写入当前进程 pid，用于区分「本进程运行中」与「上次进程退出未收尾的悬空 running」，后者由 `fix_stuck_tasks` 兜底）；停止/收尾 `finish_task` 更新状态与记录快照 → 落 SQLite `tasks` 表 → `api/tasks/history` 列表。重启后仍保留。

## 九、已知约束 / 设计铁律

1. **单 profile 铁律**：每账号唯一固定 profile，重扫 > 查看 > 守护保活（优先级抢占），绝不临时新建目录（避免新设备风控 + profile 错乱）。
2. **指纹浏览器禁用原生 Playwright 回退**：内核不可用时直接报错，绝不静默回退。
3. **凭证有效期因果**：凭证有效 → 守护才能启动；守护启动与否与 wp 引擎校验无关（校验只看凭证本身）。
4. **风控区分**：私信 `KICK` = 账号级私信风控（陌生目标反 spam / 频控），需降频或换号，与凭证有效性无关；凭证失效（三件套缺失 / INVALID_REQUEST）才触发自动重捕。
5. **抖音 cookie 格式已升级**：`s_v_web_id` 现正常为 `verify_` 开头、`uid_tt` 为 32 位 hex（转十进制超 int64），任何基于旧 cookie 格式的「污染/伪造」判断都会误伤新版正常登录态。
6. **前端 / Rust 改动必须完整 `tauri build` 重嵌**：仅重打包 backend sidecar 不会更新前端 UI。
7. **绝不强杀 BCC / 浏览器进程**：`Stop-Process` 会导致 session 降级重认证；停进程一律走 `/quit` 优雅关闭。
8. **测试阶段只打前后端并部署，不打 NSIS/MSI**（`tauri build --no-bundle`）；仅正式发布才需安装包。
9. **禁止商业/付费指纹浏览器**（2026-09-28 用户裁定）：不得引入任何按用户收费的指纹浏览器或 profile 托管服务（AdsPower / 比特浏览器 / Multilogin / GoLogin / VMLogin / 紫鸟 等），也不得把 BCC 的容器治理外包给此类厂商云。理由：本产品自身就是要卖的，**再为每个终端用户引入一份第三方月卡 = 自断产品价值**；且多客户共用同一厂商内核模板会带来「指纹碰撞」的连带封禁风险。指纹内核与容器治理均自持。

## 十、开放说明（前端不展示，统一在此说明）

前端界面按用户要求保持极简，以下功能性说明不在界面内显示：

- **会员登录后使用**：控制台需会员账号登录后使用。
- **数据本地加密隔离存储**：每个会员拥有独立数据空间，账号、会话、配置互相隔离；账号凭证 AES 加密存储在本地，不上传任何第三方服务器。
