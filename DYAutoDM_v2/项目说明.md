# DYAutoDM_v2 · 抖音直播间自动私信控制台

> 抖音直播间评论监听 → 自动定向私信的工具。Tauri2 + React + FastAPI 重构版（唯一活跃代码库）。

---

## 一、项目定位

在抖音直播间监听用户弹幕/评论，按配置对指定主播的发言观众自动发送私信（话术词库随机抽取、延迟抖动拟真、去重防骚扰）。面向「主播运营 / 私域引流」场景。

核心能力：

- **直播监听**：拉起指纹浏览器进入直播间，捕获实时弹幕/评论（弹幕 WebSocket + 中控台采集双路聚合）。
- **自动私信**：捕获发言人后，延迟 40~120s 随机抖动再发送；私信话术支持词库随机抽取 + 每条独立开关；按 user_id / sec_uid / nickname 三套去重，杜绝同人重复骚扰。
- **私信收发闭环**：独立私信接收守护进程，按会话隔离拉取历史私信、可手动回复。
- **多账号管理**：账号凭证守护 + 私信守护每账号独立、稳定端口互不冲突；指纹浏览器扫码登录、双引擎校验（wp 凭证 / 私信凭证）。
- **历史任务**：每次运行记录进 SQLite，可回溯、可跳转查看结果。

## 二、技术栈与架构

| 层 | 技术 | 说明 |
|---|---|---|
| 桌面壳 | **Tauri 2** (Rust) | 窗口 + 子进程管理 + 关闭时联动清理后端进程树 |
| 前端 | **React + TypeScript** (Vite) | 8 个功能页面，Webview 渲染 |
| 后端 | **FastAPI + Uvicorn** | 业务逻辑、抖音接口封装、守护进程 |
| 浏览器 | **指纹浏览器内核** (ungoogled-chromium + vb_chromium) | 扫码登录、直播间监听、中控台采集；禁用原生 Playwright 回退 |
| 数据存储 | **SQLite** (data/dyautodm.db) | 统一存储层（`database.py`）：历史任务 `tasks`、私信会话 `dm_conversations` + 消息 `dm_messages`；由旧 JSON 文件迁移而来，启动自动 `_migrate_json` |
| 打包 | **PyInstaller + Tauri build** | 3 个 Python sidecar 内嵌 / 旁附 + NSIS/MSI 安装包 |

### 进程模型（3 + 1）

```
┌─────────────────────────────────────────────┐
│  dyautodm-v2.exe  (Tauri 壳 / Rust)          │
│   ├─ 启动→拉起 backend sidecar                │
│   └─ 关闭→ kill_tree 递归杀后端 + 守护        │
└─────────────────────────────────────────────┘
        │  HTTP 127.0.0.1:8000
        ▼
┌─────────────────────────────────────────────┐
│  dyautodm-backend-*.exe  (FastAPI 主后端)    │
│   /api/* 全部业务路由                          │
└─────────────────────────────────────────────┘
        │ 每账号独立守护（稳定端口）
        ▼
┌──────────────────────────┐  ┌──────────────────────────┐
│ browser-daemon (凭证守护)  │  │ recv-daemon  (私信接收守护) │
│ 端口 10000~10499           │  │ 端口 10500~10999           │
│ 常驻保活凭证 / 探活        │  │ 私信 WS 长连接 / 会话隔离   │
└──────────────────────────┘  └──────────────────────────┘
```

- **端口分配**：用 `zlib.crc32(账号名)` 稳定哈希（非 `hash()`，避免 PYTHONHASHSEED 跨进程不一致导致连不上）。浏览器守护段 `[10000,10499]`，私信守护段 `[10500,10999]`。

## 四、前端页面（8 个）

| 页面 | 功能 |
|---|---|
| **Overview（概览）** | 引擎/守护状态卡片、最近活动、快捷操作 |
| **Crawl（采集）** | 用户/作品/直播搜索、点赞收藏（基座功能） |

## 五、关键业务链路

### 0. 后端启动流程（lifespan）
`main.py` 的 `lifespan` 在 FastAPI 启动期依次：① 初始化 SQLite（`database.get_db()`，WAL 模式 + 自动 `_migrate_json` 把旧 JSON 数据并入）；② 收尾上次进程遗留的悬空「运行中」历史任务（`fix_stuck_tasks` 按 pid 比对）；③ 后台线程 `_warm_verify_cache` 并行预热全部账号的双引擎校验结果进 TTL 缓存（默认 3s），使账号管理页首屏秒出、消灭 4s 网络探活等待。关闭期释放引擎资源。

### 1. 凭证获取（扫码）
`api/accounts → auto_dm.accounts → dy_apis.login_api.get_login_auth`
→ 弹指纹浏览器 (`vbrowser.launch_async`) → `login_grab_ticket` 抓取四件套
（DY_COOKIES / DY_TICKET / DY_TS_SIGN / DY_CLIENT_CERT / DY_PRIVATE_KEY）
+ web_protect / keys（security-sdk 在登录态生成）→ 写回各账号 `.env`。
单 profile 铁律：每账号固定 profile，重扫前先停守护释放锁，绝不临时清目录。

### 2. 直播监听
`core/auto_dm._run` → `live_hook` 连直播间 WebSocket / 中控台采集 →
`on_message` 抽取 (nickname, comment, user_id, sec_uid) → `dispatch.submit`。

### 3. 延迟私信
`dispatch.submit`：去重（三套集合）→ 写 records（status=已捕获）→ 按
`capture_ts + random(SEND_DELAY_SEC)` 入优先级队列。
后台任务到点调用 `core/sender.send_target_async` → `dy_apis.douyin_api`
（`create_conversation` + `send_msg`，imapi 私有网关 protobuf 签名鉴权）→
成功更新 records（status=已发送）。发送上限达则停止；暂停只停监听与发送、存量私信发完才整体停止。

### 4. 私信收发
`daemon/recv_daemon` 连 `frontier-im.douyin.com/ws/v2` 长连接 →
消息按 `conversation_id` 隔离进 `AccountInbox`，持久化到 SQLite
（`dm_conversations` 会话骨架 + `dm_messages` 消息明细，替代旧 `dm_history.json`）；
`api/messages` 转发给前端（会话列表 / 回复发送）。

### 5. 历史任务
`core/auto_dm` 启动时 `tasks_history.start_task` 记一条（写入当前进程 pid，
用于区分「本进程运行中」与「上次进程退出未收尾的悬空 running」，后者由
`fix_stuck_tasks` 按 pid 比对兜底修正）；停止/收尾 `finish_task` 更新状态与
记录快照（records 经 `_rec_to_dict` 转 dict 再 JSON 序列化，避免 protobuf/
Pydantic 对象不可序列化）→ 落 SQLite `tasks` 表 → `api/tasks/history` 列表，
可清空。重启后仍保留，可回溯、可跳转查看结果。

## 八、已知约束 / 设计铁律

1. **单 profile 铁律**：每账号唯一固定 profile，重扫 > 查看 > 守护保活（优先级抢占），绝不临时新建目录（避免新设备风控 + profile 错乱）。
2. **指纹浏览器禁用原生 Playwright 回退**：内核不可用时直接报错，绝不静默回退。
3. **凭证有效期因果**：凭证有效 → 守护才能启动；守护启动与否与 wp 引擎校验无关（校验只看凭证本身）。
4. **风控区分**：私信 `KICK` = 账号级私信风控（陌生目标反 spam / 频控），需降频或换号，与凭证有效性无关；凭证失效（三件套缺失 / INVALID_REQUEST）才触发自动重捕。
5. **抖音 cookie 格式已升级**：`s_v_web_id` 现正常为 `verify_` 开头、uid_tt 为 32 位 hex（转十进制超 int64），任何基于旧 cookie 格式的"污染/伪造"判断都会误伤新版正常登录态。
6. **前端改动必须完整 tauri build 重嵌**：仅重打包 backend sidecar 不会更新前端 UI。
