# 更新会话（refresh conversations）整合方案

> 分支：`design/better-douyin` · 版本：v0.43.27 · 日期：2026-09-15
> 依据：08 §35.2 复现实测 + 静态资料（IndexedDB/DOM）解昵称实测 + 主分支 `v2-refactor` 对照
> 性质：**设计契约文档**（改动前必读；与 08 冲突时以实测为准）

---

## 〇、回归设计理念：这个模块「应该做什么」

**设计契约**：一次「更新会话」= 把该账号的**会话骨架 + 消息正文 + 昵称头像**三样，
从抖音侧**一次性前移**到本地 SQLite；此后私信页**纯读库**、零网络。

**四条不变式**（破了就是 bug）：

| # | 不变式 | 今天的实测反例 |
|---|---|---|
| **I1** | **幂等**：重复触发结果一致，不重复写 | ✅ 297(A) 有唯一索引 `uniq_dmmsg` |
| **I2** | **不降级**：新结果不得劣于已有结果 | ❌ **15 个覆盖了 83 个**（登录态失效后）|
| **I3** | **解耦**：昵称与消息互不阻塞 | ❌ 昵称链路（BCC）失败时，消息也未落库 |
| **I4** | **可离线重放**：首包落盘后可无限重放 | ❌ 代码**从不落盘**（08 §22.1 早已定为铁律）|

**风控边界**：
- 本分支 R1/R2/R3 已解除（用户授权）→ 允许凭证 HTTP、允许主动查；
- 但**请求数仍须最小化**（首包 1 次 + 301 按需），用户显式动作豁免守卫。

## 一、数据源与可靠性矩阵（全部为实测结论）

| 数据 | 来源 | 关联键 | 覆盖率（实测） | 风控成本 |
|---|---|---|---|---|
| `conv_id` / `peer_uid` | 首包 `get_message_by_init` (cmd 2043) | — | **44/44** | 1 次请求 |
| `short_id` | 首包 元数据对象 `field4.5` | conv_id | **44/44**（修复后）| 0 |
| 消息正文（近 ~20 条/会话）| 首包 `field2` 内嵌 JSON | conv_id 内嵌 | 25 条 / 11 会话 | 0 |
| 消息正文（完整历史）| **cmd301** `get_by_conversation` | conv_id + short_id | 43 条（目标会话）| 1 次/会话 |
| 图片解密要素 `skey`/`origin_url` | **cmd301** `field8.resource_url` | msg_id | **5/5** | 0（随 301）|
| **昵称 / 头像** | ① DOM 会话列表 ② IndexedDB ③ `im/user/info` | ① 无 uid ② `sec_uid` ③ `uid`(数字) | ①83 个 ②232 处 ③**已废** | ①0 ②0 ③高 |

### ★ 昵称三条通道（今天的核心整合点）

| 通道 | 实现 | 优点 | 局限 |
|---|---|---|---|
| **① DOM 直读**（**首选**）| `.conversationConversationItemtitle` + 首个 `img` + `.ConversationItemDescleft` | 零请求、零风控；实测一次拿 **83 个**（含滚动覆盖）| 条目**无 uid/sec_uid** → 需桥接；须浏览器在 |
| **② IndexedDB 离线**（**兜底/补全**）| 解 `profile/Default/IndexedDB/https_www.douyin.com_*/**.ldb` | **零请求**；**离线**（连浏览器都不用开）；一次 232 处 | 缓存可能过期/被逐出；索引需与首包 `sec_uid` 交集 |
| **③ 主动查** `im/user/info`| `POST sec_user_ids=[...]` | 精确覆盖 | **风控面最大**；本分支已授权，主分支禁止 |

**关键实测事实（务必记住）**：
1. **`im/user/info` 被动 hook 已失效** —— 抖音改版后前端不再发该请求（`hook=0` 全程），
   靠它截昵称是**死路**。DOM / IndexedDB 是现行有效来源。
2. **IndexedDB 的字符串是 V8 序列化（UTF-16LE）** —— 按 UTF-8 grep 中文**必然 0 命中**；
   正确解：定位 `\x22\x08nickname` 后按 UTF-16LE 解码。
3. **DOM 与首包无共同 id** → 禁止按位置对齐（08 §三十九铁律）；
   桥接只有两个可靠键：**文本桥**（DOM `desc` ↔ 首包消息正文，仅唯一命中才写）
   或 **点击会话拿 sec_uid**。
4. **昵称与消息是两条独立链路** —— 必须解耦（今天 15 覆盖 83 就是耦合的反例）。

## 二、执行链路（三阶段，可独立失败）

```
阶段 A · 采集（HTTP，需网络）
  A1  首包 get_message_by_init(auth)
        └→ 会话骨架 {conv_id, peer_uid, short_id, total_msgs}
        └→ 内嵌消息（~20/会话）+ 图片要素
  A2  cmd301 逐会话补全（仅对 short_id 存在者）
        └→ 完整历史 + skey/origin_url（图片解密要素）
  A3  ★ 首包落盘 snapshot/init_<ts>.bin（08 §22.1 铁律，当前缺失）

阶段 B · 昵称（三通道，按优先级降级；失败不阻断 A/C）
  B1  DOM 会话列表直读        ← 零请求，首选
  B2  IndexedDB 离线解        ← 零请求，兜底（V8/UTF-16LE 解码）
  B3  主动查 im/user/info     ← 仅本分支授权时启用
  B*  桥接：见 §一★（文本桥 / sec_uid 交集）；**关联不到就留空，绝不猜**

阶段 C · 落库（解耦写入 + 有效性守卫）
  C1  dm_conversations  UPSERT（昵称非空才覆盖；不覆盖更优值）
  C2  dm_messages       INSERT OR IGNORE（唯一索引 uniq_dmmsg）
  C3  图片 extra        {skey, origin_url}（供 AES-GCM 解密）
  C4  ★ 有效性守卫：新结果条数 < 既有值的 50% → 拒绝覆盖 + 告警（I2）
```

**顺序铁律**：A 与 B 可并行/可单独失败；**C 必须等 A 完成**，且 **C4 守卫必须先于任何覆盖写**。

## 六、经验固化（防重蹈）

1. **「纯搬移」重构必须搬全依赖**：跨模块引用（`json` 等隐式依赖、`_extract_media_text`
   等函数引用）不会因 `py_compile` 报错，只在**运行期**炸，且**被 `except: continue` 吞掉**。
   → 搬移后必须跑**功能级**验收（不能只 `py_compile` + import 成功）。
2. **搬移后跨层依赖用依赖倒置**：工具层不得反向 import 业务层。
3. **`except: continue` 必须配一次性告警**：静默吞异常 = 5 秒的 bug 查 5 小时。
4. **数据不对先怀疑环境**（账号/路径），再怀疑业务（08 §35.5 教训）。
5. **不信推断链**：「首包无 skey」→「服务端不下发」是三级外推，**直接测终点**。
6. **同一 conv_id 可能在 protobuf 里出现多个层级**，收对象时必须按「是否带必要字段」择优，
   不能按出现顺序先到先得。
