## 二、复现中发现的两个真实缺陷

### 缺陷 1（error）：解析器把「消息容器」当成会话 → 该会话 short_id 永久丢失

**证据**（本次首包离线拆解）：

```
所有含目标 conv_id 的对象：
  objs[0]   125,868 B   field4.5 short_id = None      ← 消息容器包装对象
  objs[1]    21,838 B   field4.5 short_id = 7669698910541316648  ← 真正的会话元数据

46 个对象中 45 个能取到 short_id，1 个取不到 —— 正是这个容器对象
```

**根因**：`parse_init_protobuf` 的 `conv_objs` 收集逻辑
（`auto_dm/conversation_capture.py` 首包解析段）会把**同时含 conv_id 的父容器**
与**会话元数据子对象****双双收进 `conv_objs`**。父容器没有 `field4.5`，
于是它落库时 `short_id=None`。

**影响面**（真实业务后果）：
- `capture_all` 的长会话补全判据是 `need=[c for c in convs if c.get("short_id")]`
  （`:1001`/`:1012`/`:1016`）→ **该会话被永久跳过**，历史消息永远补不全。
- 本次正是这个会话承载着**全部 5 条图片消息**（其余会话一张图都没有）。
  ⇒ 「图片取不到」的表象，根因是 **short_id 解析盲区**。

**修复方向**：收 `conv_objs` 时**只保留能取到 `field4.5`（short_id）的元数据对象**，
或在取 short_id 时**向上/向下兼容**（先 field4.5，取不到再退回该子树的 field5）。
⚠️ 修复前必须先跑 `verify_*.py` 确认不破坏 43/44 的既有覆盖率。

### 缺陷 2（warn）：首包自带消息，但解析结果为 0 条

本次首包目标会话**自带消息体**（实测可见）：
```
{"mention_users":[],"aweType":700,"richTextInfos":[],"text":"【端到端测试】链路验证"}
{"mention_users":[],"aweType":700,"richTextInfos":[],"text":"【对照测试】尚进通道"}
{"mention_users":[],"aweType":700,"richTextInfos":[],"text":"【验证】张老师通道复测"}
```
但 `parse_init_protobuf` 日志恒为 `首包解析出 44 个会话，含消息的 0 个`。
⇒ 首包路径的消息解析**未工作**（`aweType=700` 文本消息也未被计入）。
不影响 301 补全（301 路径正常），但**首包本应提供的 20 条/会话被浪费**，
且冷启动时可见消息更少。

## 六、结论

**§35.2 的算法链路完全成立且可复现**：首包 → `short_id` → cmd301 → `field8.content_json.resource_url.skey`
→ AES-256-GCM（IV=前 12 字节）→ 原图。5/5 解密成功。

**真正的瓶颈不在算法，在两处解析缺陷**：
① 会话元数据对象与消息容器对象混收 → 承载全部图片的那个会话 `short_id=None` → 被补全逻辑跳过；
② 首包消息解析未工作（含消息恒 0）。

修好 ①，图片历史就能自动补全（不必逐会话手工 301）。
