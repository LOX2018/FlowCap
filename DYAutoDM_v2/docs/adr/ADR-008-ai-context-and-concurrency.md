## 1. 背景（实测，非推断）

2026-09-25 对 AI 回复链路做只读实测（数据库副本沙箱 + 插桩 `requests.post`），
结论**推翻三处既有认知**，并暴露 11 项缺陷（编号 AI-050~AI-060）。

### 1.1 关键实测事实

| # | 事实 | 证据 |
|---|---|---|
| F1 | **单会话全文注入容量没问题** | 30 条 / 29,304 字整段送达：`HTTP 200`，`messages=32`，`content=29,337 字`，实际服务 glm-5.2，18.7s。全库 252 会话中 **97% ≤4000 字** |
| F2 | **真实瓶颈是 `max_tokens`** | 同请求 `max_tokens=1000` → 返回 `None`（思考泄漏）；`max_tokens=4000` → 成功（12.9s） |
| F3 | **图片描述全链断裂** | 真实会话：客户发病例（`id=10428`, `msg_type='27'`）→ 之后 3 个轮次 `历史含图片信息 = False` |
| F4 | **排序基准错** | 同会话存在 **2 次 ts 倒挂**；按 `id` 会把 9 天前消息当"刚发生" |
| F5 | **端点支持并发** | chat 同发 10 → **10/10 全 200，墙钟 2.3s**；embed 同发 5 → 5/5 全 200 |
| F6 | **`auto` 路由并发漂移** | 同一次 10 并发被 **4 个模型**服务：GLM-5.2×3（思考泄漏）/ agnes-2.5-flash×6（正常）/ glm-5.2×1（垃圾）/ deepseek-v4-flash×1（英文）⇒ **约 40% 不可用** |
| F7 | **视觉能力可用，消费点被门拦** | 直连 vision 链实测返回正确描述（6720ms）；但 `vision_enabled=False` ⇒ 业务入口出网 0 次 |
| F8 | **嵌入模型真被调用** | 3 次真实 `/v1/embeddings` 出网，`model=llama-nemotron-embed-vl-1b-v2`，`kb_mode=semantic` |

### 1.2 当前实现的三处结构性缺口

1. **上下文装配散落** —— 内容在 `build_system_prompt`、历史在 `_build_history`、消息编排在 `AIClient.chat`。
2. **双通道表达同一件事** —— `AIClient.session_history`（内存态，**每次回复新建实例 ⇒ 恒空**）
   与 `_build_history`（DB）。半成品会被误读为"已有记忆"，掩盖 DB 通道故障。
3. **并发模型 = 单线程全局串行** —— 1 个 daemon 线程逐条 `_handle`，
   N 会话 = N × 13~25s；10 人时最后一名等 **2.5~4.5 分钟**。

### 1.3 上游情报（已嵌入上游自带方案）

`AstrBotDevs/AstrBot`（40,981★，当日活跃）提供：

| 上游 | 语义 |
|---|---|
| `core/utils/session_lock.py` | **per-session 锁**（跨会话并行 / 同会话串行，含引用计数清理） |
| `core/utils/active_event_registry.py` | `UMO → 活跃事件集合`，按会话终止在途事件 |
| `core/platform/message_session.py` | 会话唯一标识 `platform_id:message_type:session_id` |
| `core/agent/context/config.py` | `max_context_tokens` / `enforce_max_turns` / `truncate_turns` |
| `core/agent/context/{manager,compressor}.py` | 超限二策略：**按轮截断** 或 **LLM 摘要压缩** |

⚠️ **可移植性**：上游是 `asyncio` 体系，我方是 `threading` ⇒ **借语义，不抄代码**。

## 2. 决策

### 决策 1：上下文 = **单会话全文注入** + 平台时间排序 + 超预算兜底

- **默认全文注入**：注入该会话（`account` + `conv_id`）全部消息，**不做条数截断**。
  理由：F1 证明 97% 会话 ≤4000 字，容量不是问题；"AI 只看最后 10 条"是缺陷①的历史包袱。
- **排序基准改平台时间**：`ORDER BY COALESCE(ts,0) ASC, id ASC`。
  理由：F4 实测 `id` 存在时间倒挂 ⇒ 排序错序会直接喂错上下文。
- **超预算兜底**：仅当超 token 预算时，从**最新往旧**累加，**保证单条消息完整**（不切断）。
  预算取值见 §3 待定项。
- **`max_tokens` ≥ 4000**。理由：F2 —— 1000 时返回 None。

**否决的方案**：
- ❌ 保持 `ORDER BY id`（错序）；
- ❌ 保持"最近 N 条截断"（信息有损且无必要）；
- ❌ 摘要压缩作为默认（增一次 LLM 调用 + 延迟，违反实时性；仅在超预算且累加仍超时才启用）。

### 决策 2：图片信息 **持久化为会话消息**（不只在当轮内存）

- **新增独立 KV 缓存**：`ai_img_desc_<msg_id> = {desc, model, at}`。
  理由：不写回 `dm_messages`（**不改原始取证数据**，符合铁律），不改表结构，
  与既有 `pro_kb_semv_<id>` 缓存同款模式。
- **白名单纳入 `'27'`**（图片）：组装历史时按 `msg_id` 查缓存 → 还原为一条正常会话消息：
  `{"role":"user","content":"[客户发来图片] <描述>"}`。
- **补描述**：组装时若图片无缓存且 URL 未过期 → 补解密 + 补描述 → 落缓存。
- **当轮复用**：`_describe_image` 先查缓存，命中不重复调模型（顺带消除重复烧视觉调用）。

**前置条件（实测已确认可行）**：图片 URL 有效期至 **2027-09-23**（剩 363 天）；
`skey`/`origin_url` 已持久化在 `extra`；解密产物已落盘 `data/origin_images/`。

### 决策 3：并发 = **per-session 串行 + 跨会话并行**

- **同会话严格串行**（保证客户看到顺序与发言顺序一致、上下文不串），
  **不同会话并行**（借 AstrBot `session_lock_manager` 语义）。
- 实现选型（我方 `threading` 体系，**不照搬 asyncio 代码**）：
  - 首选：`ThreadPoolExecutor(max_workers=N)` + `per-(account,conv_id)` `threading.Lock`；
  - 会话键统一为 `account` + `conv_id`（与 `_build_history` 一致，消除双通道）。
- **并发上限保护**：`max_workers` 设上限（建议 8~10）。依据 F5：端点 10 并发 OK，但不设上限时
  30 人涌入会打爆 FreeLLM 上游。
- **发送侧无需改动**：`dm_dispatch` 已是 per-account 串行队列，与生成侧正交。

### 决策 4：🔴 **摘除 `auto` 首候选**（并发前提）

- 将 llm 与 vision 链的 `auto` 从**首候选**移出（换为确定模型，或降至链尾/移除）。
- 理由：F6 实测 10 并发下 4 模型混用、约 40% 输出不可用；且知识库 `13_业务域_AI与通知.md:87`
  早有结论「auto 三端点均不可用于获客」。**开并发会放大该缺陷**（并行会话各自随机命中）。
- **这是决策 3 的前置条件** —— 不先修 `auto`，开并发等于把 40% 故障率并行放大。

### 决策 5：契约收口（伴生项）

| 项 | 处置 |
|---|---|
| `sem_enabled` 对 `pro_kb` 形同虚设 | 二选一：① 让 `pro_kb` 也读 `sem_enabled`；② 明确"该开关只管回复库"，并在 UI/文档改名。**须选一个，禁止含糊** |
| `_history_limit`（clamp 1~50）与 `chat()`（无 clamp）双处上限 | 收口为单点（决策 1 全文注入后，两处一并移除或统一） |
| RAG `threshold=0.0` | 设为实测阈值（参考 `sem_threshold` 0.40）或明确"不过滤、全注入"的设计意图 |
| `current_sem_model()` 探针 | 改为**只读缓存**模型名，不在每次 RAG 组装时真发一次 embedding |
| `_RAG_SUFFIX` 重复写客户消息 | 从 system 段移除（user 消息已是权威位置） |
| `kb_items` 死参数 / text-URL 兜底正则 | 清理死代码 |

### D4 实施记录（实测取证）

实测探活（固定 prompt 直连网关）：`agnes-2.5-flash` **0.8s / 正常中文**；

## 5. 验收判据（可判定）

| 决策 | 判据 |
|---|---|
| 1 | 真实会话注入条数 = 该会话白名单条数（非 10）；`ts` 排序下序列尾部 = 真实最新消息；`max_tokens≥4000` 下长会话不再返回 None |
| 2 | 图片会话：图片到达后**下一轮**历史中出现 `[客户发来图片] <描述>`；重复轮次**不重复调**视觉模型（出网计数 = 1） |
| 3 | 5 个不同会话并发发起 → 墙钟 ≈ 单次延迟（非 5×）；**同会话**连发 2 条 → 严格按序、上下文不串 |
| 4 | 并发 10 次请求，返回模型集合**只有 1 个**；思考泄漏率 = 0 |
| 5 | 各项门禁脚本全绿；`sem_enabled` 行为与文档一致 |
| 全局 | 实机（`C:\temp\dyautodm_design`）验证；**零回归**；版本 6 处齐平；案例归档 |

## 6. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 全文注入使个别超长会话变慢/失败 | 决策 1 的兜底 + `max_tokens≥4000`；D1 预算按比例 |
| 并发提高触发风控（发送频率） | 发送侧 `dm_dispatch` 闸门不变（per-account 串行 + 频率上限）；生成并行**不等于**发送并行 |
| 图片补描述引入解密开销 | 仅对**无缓存**图片触发，且落缓存后只做一次；URL 过期则跳过 |
| `auto` 摘除后无可用模型 | D4 保留链尾兜底选项；实测 agnes-2.5-flash 正常 |

**回滚**：全部改动集中在 `ai_reply.py` + 链路配置；链路配置改动可通过 UI 一键回填。
