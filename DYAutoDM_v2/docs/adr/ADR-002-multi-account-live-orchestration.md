## 1. 背景（实测证据，非推断）

**用户设计意图**：直播监听**支持多账号并发**（「小助理和张老师同时进行直播间的任务」）。

**当前实现的实测事实**（全部可复跑）：

| # | 证据 | 位置 |
|---|---|---|
| 1 | 引擎是**单例**：`app.state.adm = AutoDM()`，注释原文「引擎主控单例」 | `main.py:417` |
| 2 | 五个引擎端点（start/pause/resume/stop/stop-soft）**全部**读同一个 `request.app.state.adm` | `api/engine.py:29,92,100,109,118` |
| 3 | 全仓**无** `account → AutoDM` 映射，也无 `get_adm/adm_for` 之类按账号取实例的入口 | grep 0 命中 |
| 4 | `EngineState` 是**实例级单一状态机**（IDLE/STARTING/RUNNING/PAUSED/STOPPING/STOPPED） | `models/enums.py:17` |
| 5 | 实机复现：张老师 `RUNNING` 时对小助理 `POST /start` → `{"ok":true,"state":"running","already":true}` | 2026-09-22 16:47 |
| 6 | 文档侧：`工作记忆/12_业务域_直播监听.md` 与 `docs/adr/` 对「多账号并发」**0 记载** | grep 0 命中 |

⇒ **结论**：设计意图存在，但**既未落文档、也未落实现**。这不是「本该如此」，是**架构缺口**。

### 1.1 附带发现：静默假成功

`/start` 在已 `RUNNING` 时**静默**返回 `ok:true` —— 用户点「启动」却无任何事发生，界面仍显示 running。
这违反项目既有规则（`〇·丁` 规则 2：**拿不到资源必须显式失败并向上报，绝不静默往下跑**），
与本项目多起「假成功」事故同族。

### 1.2 前置缺陷：日志归因不含账号

`[弹幕]` 日志行**不含账号字段**（`12_业务域` §十已记）。多账号共写同一 `logs/` 时，
**同一批弹幕会被每个账号都计入** ⇒ 多实例跑起来后，能力探针与证据链**立刻失真**。
⇒ **此项是并发改造的前置必做项**，不是可选项。

## 2. 目标语义（用户已确认，2026-09-22）

用户明确：**(A) 与 (B) 都要支持**。

| 语义 | 形态 | 特点 |
|---|---|---|
| **(A)** 账号 × 各自房间 | 小助理监 A 房、张老师监 B 房 | 天然正交、隔离干净、代价低 |
| **(B)** 多账号 × 同一房间 | 两个及以上账号同时盯**同一个房间** | 引入**重复发送**风险（同一句弹幕被多账号各私信一次 = 直接风控面） |

### 2.1 基础设施现状（有利条件，已实测）

- **BCC 已是每账号独立容器 + 独立端口**（本轮实测：小助理 `11231`、张老师 `12687` 各自存活）。
- **发送闸门是 per-account 限速**（`recv_daemon` 的 `_send_gate_acquire`）。
  ⇒ **无需重构浏览器/发送层**；缺口**只在编排层**（谁持有 N 个任务、状态如何隔离、如何展示）。

---

## 3. 决策（建议方案，待用户确认细节）

1. **编排层**：引入 `account → Engine` 的表（每账号一个引擎实例，各自持有 `EngineState`、
   `auth`、`LiveChatHook`、发送队列），替换 `app.state.adm` 单例。
2. **API 层**：端点增加 `acct` 维度（`/api/engine/{acct}/start|pause|resume|stop`，或 body 必带 `acct`）。
3. **冲突必须显式失败**（不再静默 `already`）：
   - 同账号重复启动 → `409`，语义「该账号已在监听」；
   - 语义 (A) 下同房间被另一账号占用 → 按用户选择返回 `409` 或允许（见 §4）。
4. **(B) 的发送规则 —— ✅ 用户已定（2026-09-22）**：
   > 用户原话：「多账号对同一直播间的**监听和发送，可以同时**进行，但必须经过
   > **沉淀池筛选**后发送，**禁止对同一用户双账号发送**，可以**交替发送或者轮次发送**。」

   落地要点（三条，缺一不可）：
   - **沉淀池必须跨账号**：同一用户在同一房间被**任一**账号发过后，其余账号不得再发；
   - **发送额度在账号间做交替/轮次分配**（而非各自独立计数）；
   - 监听（解密）**不设限制** —— 多账号可同时监听同一房间。

   🔴 **现状差距（实测，改造成本的主要来源）**：现有沉淀池 `dm_uid_sink` 主键为
   **`PRIMARY KEY (account, peer_uid)`**（`database.py:215`），注释原文「同一 **(account, peer_uid)**
   只保留一次有效记录」⇒ **账号是去重维度的一部分，跨账号天生不去重**。
   多账号并发下，同一用户会被每个账号各发一次 —— **正是用户要禁止的形态**。
   ⇒ 需把去重维度提升为**房间级跨账号**（如 `(room_id, peer_uid)` 唯一，记录承接账号与时间），
   并把「谁发」交给轮转分配器。**这是架构变更，不是配置。**
5. **归因层（前置必做）**：`[弹幕]` 行补账号字段（如 `[弹幕][账号=…]`），并让探针按账号分流统计。
6. **前端**：状态展示按账号分组（而非单一全局徽章）。

### 3.5 连接模式：**匿名 / 凭证** 由用户选择（并发上限随之不同）

> 用户原话：「直播监听的政策也得加一个区分，让用户选择到底是**匿名连接**还是**凭证连接**；
> **匿名连接可以规避同一平台多个直播间的监控风控问题**，匿名状态上限**可以设定为 4 个**；
> 但如果用**凭证去监听**的话，就**只能一个账号一个**。」

| 模式 | 并发上限 | 解密能力 | 风控面 |
|---|---|---|---|
| **匿名连接**（不带账号 cookie） | **≤ 4** 个房间同时 | ⚠️ **无**（按既有实测结论，未被服务端承认的会话，观众/弹幕身份被脱敏为 `111111`） | 不暴露账号 ⇒ **规避「同平台多房间监控」关联风险** |
| **凭证连接**（账号 .env） | **1 账号 1 任务** | ✅ 有（`[live-identity]` 承认） | 账号级关联风险，故不许多开 |

🔴 **必须让用户显式看到的取舍**：匿名模式**规避风控的代价是拿不到真实昵称/uid**
（身份脱敏）—— 它只适合**开播检测 / 在线人数 / 内容热度**这类不需要身份的用途。
若某房间需要真实昵称，就只能走凭证模式（1 账号 1 任务）。
⇒ UI 上选「匿名」时必须同时提示这一点，不能让它看起来「没有代价」。

**实现提示（SoC）**：模式开关与策略选择应走**现有统一配置中心**（`services/app_config.py`
的 `SECTIONS` + 前端 `UnifiedConfigSection.tsx` 自动生成表单，见 `12_业务域`/skill §十二），
**不要另造一套配置入口** —— 新增参数只加一项，前端零改动。

> 🔴 **规格修正（2026-09-22 v0.44.41 实施时实测发现，原文「前端零改动」不成立）**：
> `UnifiedConfigSection` 本身确为 schema 驱动（加字段即渲染），**但它的调用方
> `settings-page.tsx` 对每个 tab 用的是显式白名单** `onlySections={["live"]}`
> —— 新分区不在任何白名单里 ⇒ 后端加了字段，**UI 里看不到**。
> ⇒ 正确表述是：**新增字段零前端改动；新增分区需在目标 tab 的 `onlySections` 数组登记分区名（一行）**。
> 本次已按此接线（`live_orchestration` 登记进「直播监听」tab，仍不另造入口）。

| 项 | 决策 |
|---|---|
| 模式 | 匿名 / 凭证，**用户可选**（每任务粒度） |
| 匿名上限 | **4**（可配置，走统一配置中心） |
| 凭证上限 | **1 账号 1 任务**（硬约束） |

### 3.6 脱敏（无解密权）直播间处理策略 —— **必须入配置中心**（用户 2026-09-22 要求）

> 用户原话：「脱敏直播间通常就不在监听的范畴内……我给你发的这个直播间链接，是因为这是**自营**的
> 直播间，我拥有该直播间的**解密权限账号**；但**对其他直播间使用什么凭证，默认都是脱敏的**。
> 既然你也提到了这个问题，那么把这个**策略也写进配置中心的选择当中**。」

🔴 **语义修正（推翻本文早期「匿名/凭证」二分中隐含的「凭证即可解密」假设）**：

| 事实 | 说明 |
|---|---|
| 解密权 = **房间所有权关系** | 自营房间 ⇒ 有解密权；他人房间 ⇒ **默认脱敏**，**换任何凭证都拿不到真实昵称/uid** |
| 「脱敏」不是故障 | 是他人房间的**正常态**；不应被当作异常/风控信号处理 |
| 监听范畴 | **通常不含脱敏房间**（他人房间无监听价值） |

⇒ §3.5 的「匿名 vs 凭证」**不是**决定能否解密的变量（解密取决于房间归属），
它决定的是**是否暴露账号**（风控面）与**并发上限**。两者是**正交**的两件事。

**处置策略（入配置中心，用户可选；检测判据 = `[live-identity] 不具备解密权` 或弹幕 `uid=111111`）**：

| 选项 | 行为 | 适用场景 |
|---|---|---|
| **跳过（不建立/立即停止）** | 检测到脱敏即不监听 | 只做自营监听 —— ✅ **已定为默认**（符合「脱敏房间不在监听范畴」） |
| **仅统计** | 继续监听，只用在线数/热度/开播检测；**不采昵称、不发送私信** | 盯竞品热度 |
| **提示后由用户决定** | 弹提示「该房间无解密权」，由用户选继续/停止 | 半自动 |
| **降级为匿名模式** | 不暴露账号，走匿名（受 ≤4 上限） | 多房间开播检测 |

**实现提示**：与 §3.5 同 —— 走统一配置中心（`app_config.SECTIONS` + `UnifiedConfigSection.tsx`），
不另造入口。

### 3.1 铁律约束（改造时必须维持）

- 不得绕过统一发送闸门（禁止新增 imapi 直发旁路）。
- 不得为并发而新建 BCC 实例（单账号单容器铁律不变）。
- 资源获取失败必须**显式失败**并可观测，不得静默兜底。

## 5. 实施顺序（不可颠倒）

1. **前置**：`[弹幕]` 日志账号归因 + 探针按账号分流（否则后续所有读数不可信）。
2. **编排层**：`account → Engine` 表 + per-account `EngineState`；单账号行为必须**零回归**。
3. **API**：加 `acct` 维度 + 冲突显式失败（含回归测试：原有单账号调用逐字不变）。
3.5. **策略中心**（走统一配置中心 `app_config.SECTIONS`，前端零改动自动生成表单）：
   - 连接模式（匿名/凭证）+ 匿名并发上限（默认 4）
   - 发送轮转策略（按目标 / 按时间窗 / 按房间，默认按目标）
   - 脱敏处理策略（四选一，默认「跳过」）
   - 沉淀池：全局作用域 + 长冷却（默认 90 天，可配置含「永久」档）
   ⇒ ✅ **已实施（2026-09-22，v0.44.41，提交 `47368b2`）** —— 见 §7 实施记录
4. **(A)** 落地并实机验证两账号各自房间。
5. **(B)** 落地（含去重/单发送账号规则）+ 实机验证「无重复私信」 —— ✅ **已实施（2026-09-22，v0.44.42，提交 `eb5d5ab`）** —— 见 §7.2 实施记录
6. 文档/探针/ADR 状态收口。
