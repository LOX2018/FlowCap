# ADR-012：消息落库 Schema-as-Code —— 单一出口 + 类型注册表 + 未知类型安全降级

| 项 | 值 |
|---|---|
| **状态** | ✅ 已采纳（2026-09-25，用户拍板「一次做完整套」） |
| **决策者** | 用户（原话：「应该在规划和设计层次，就一并考虑好这些问题」） |
| **触发** | H-25（一）（二）连续两轮「发现污染 → 写侧打补丁 → 读侧打补丁」的被动循环 |
| **影响面** | `dm_messages` 7 处写入点、新增 `services/message_schema.py`、`api/messages.py`、`services/ai_reply.py`、前端、门禁 |
| **关联** | ADR-011（媒体 text/extra 契约）、H-25 |

---

## 1. 问题：我们一直在「数据层」救火，而病在「设计层」

H-25 连续两轮都是同一个形状：

```
出现新类型数据 → 没有归类规则 → 塞进已有字段（text）
  → 污染 AI prompt / 前端 / 导出 → 被发现 → 读侧加黑名单补救
  → 又出现另一种形态（本次：无方括号的系统文案 183 条）→ 再加一条黑名单
```

**这是「黑名单式打补丁」的必然结局**：黑名单只能覆盖**已经见过**的形态。

### 1.1 物理证据（实测，非推断）

| 证据 | 数值 |
|---|---|
| `dm_messages` 的**写入点** | **7 处**（`conversation_capture` ×2、`recv_daemon` ×3、`wp_recv`、`database`），**各自手写列名，无统一出口** |
| 库中 `msg_type` 取值 | **8 种**：`text`(755) / `7`(112) / `delivery_marker`(29) / `1`(4) / `0`(2) / `50010`(1) / `27`(1) / `15`(1) |
| **从未被显式规划过的类型** | **5 种**（`0`/`1`/`15`/`50010`/`delivery_marker`）共 **36 条** —— 全是「来了就塞」的产物 |
| 本次新发现的系统文案 | **183 条**（两种固定模板，含 `{{0}}` 占位符，全 `role='me'` + `msg_type='text'`） |

> **ADR-011 的 `recv_daemon` 硬编码 `extra="{}"` 缺陷，正是这 7 处分散写入的必然后果** —— 没有出口，就必然有副本，有副本就必然漏改。

---

## 2. 决定性洞察：真正要防的不是「某个类型」，而是「未知类型」

本次 183 条的关键不在「它是系统提示」，而在：**它是一种我们没见过、也没有规则处理的数据，却仍然被当成普通用户消息落进了 `text`**。

⇒ 治理目标不是「把已知黑名单列全」，而是：

> **任何未被类型注册表承认的数据，必须走安全降级路径，绝不允许以「疑似用户消息」的形态写进 `text`。**

这就是**前向兼容（forward compatibility）**：今天不认识的类型，明天补进注册表即可；但在补进去之前，它**不得污染**已有语义字段。

---

## 3. 决策：三层 Schema-as-Code

```
┌─ 层 1：类型注册表（SSOT）────────────────────────────┐
│  services/message_schema.py                          │
│  · MSG_TYPES：每个 msg_type 的语义 / 归属字段 / 渲染形态 │
│  · SYSTEM_TEXT_PATTERNS：平台提示文案模板（正则）        │
│  · classify(obj) → 返回 (kind, semantic_text, extra)   │
└──────────────────────────────────────────────────────┘
                        ↓ 所有写入必须过
┌─ 层 2：单一写入出口 ─────────────────────────────────┐
│  MessageRecord.build(...)  ← 7 处写入点全部收敛到此    │
│  · 未在注册表 → kind=Unknown → 强制降级：              │
│    text 只写语义标签，原始载荷进 extra.raw             │
└──────────────────────────────────────────────────────┘
                        ↓
┌─ 层 3：机械门禁（防复发）────────────────────────────┐
│  · G9  7 处写入点不得再手写列名（逐个断言调用统一出口）  │
│  · G10 未知类型必须降级（喂未知 msg_type → 断言不进 text）│
│  · G11 真实库：无「疑似系统文案」残留在 text            │
│  · 负控：把注册表条目删掉 → 门禁必须变红                │
└──────────────────────────────────────────────────────┘
```

### 3.1 字段契约（扩展 ADR-011）

| 字段 | 职责 | 不得承载 |
|---|---|---|
| `text` | **纯语义**：用户可见对话文本 或 语义标签 | base64 / URL / 原始 JSON / 平台提示原文 |
| `msg_type` | 类型码，**必须在注册表内** | 随手填的数值 |
| `extra` | 载荷容器（JSON） | —— |
| `extra.kind` | **新增**：语义分类（`user_text`/`media`/`system_notice`/`delivery_marker`/`unknown`） | —— |
| `extra.raw` | **新增**：未知类型的原始载荷（降级存放，供日后补入注册表时回溯） | —— |

### 3.2 读侧统一口径

AI prompt / 前端 / 导出三处**都改为按 `extra.kind` 白名单放行**，而非按 `text` 前缀黑名单排除：

```
白名单 = {user_text, media}      ← 只有这两类进 AI prompt 与前端会话流
其余（system_notice / delivery_marker / unknown）→ 不进 prompt、不进会话流
```

**这是从「排除已知坏」转为「只放行已知好」** —— 未知类型天然被挡在外面，无需事后补救。

## 4. 存量迁移（随本 ADR 一并执行）

| 批次 | 内容 | 处置 |
|---|---|---|
| A | 183 条平台提示模板（`对方回复…` / `…互关之前…`） | 标注 `extra.kind=system_notice`，`text` 保留（供前端可能的合规展示），**但读侧不再放行进 prompt/会话流** |
| B | 36 条未规划 `msg_type`（`0`/`1`/`15`/`50010`/`delivery_marker`） | 按注册表归类；无匹配者标 `unknown` + `extra.raw` 存原文 |
| C | 76 条 `[投递验证]` | 归入 `delivery_marker`（已是既有语义，补 `extra.kind` 标注） |

迁移脚本复用 ADR-011 的 `migrate_image_text_contract.py` 纪律：**dry-run 默认 / `--apply` 才写 / 写前自动备份 / 逐条判定 / 幂等 / 禁 LIKE 模糊删**。

## 5. 验收判据（可判定）

1. 7 处写入点**全部**调用统一出口（源码级断言，G9）。
2. 喂一个**注册表内不存在**的 `msg_type`（如 `99999`）→ 落库后 `text` 为语义标签、原文在 `extra.raw`、`extra.kind='unknown'`，**且读侧不放行进 prompt**（G10）。
3. 真实库扫描：`text` 中**无**平台提示模板残留被放行；AI 读侧扫全会话 → 系统文案泄漏 **0**。
4. 负控：从注册表删除一条已知类型 → 门禁**变红**。
5. 全量 pytest：新增门禁全绿，既有失败数**不增加**。

## 6. 遗留（诚实标注）

- 7 处写入点收敛属**架构级改动**，须全量回归 + 部署验证（用户择机打包）。
- 平台提示模板是**靠样本归纳**（本次两种），抖音若新增模板仍需补注册表 —— 但届时它会被**降级为 unknown 而非污染**，危害已从「污染」降为「不认识」。
