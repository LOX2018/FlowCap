# ADR-032 · 总览页信息重设计（业务漏斗口径 + 采集维度补齐）

> 状态：**Accepted**（用户 2026-09-30 拍板）→ 实施中
> 分支：`design/better-douyin` · 基线 **v0.45.110**
> 触发：用户原话「**根据项目内目前具备的功能，重新设计总览页面当中需要展示的信息，
> 而不是让你重新给我排版。目前项目内拥有的采集功能都没有进行体现。而且首栏上面的
> 代发私信 0/3 这很明显和现有版本不符**」

---

## 1. 背景：上一版是排版重构，不是信息设计

2026-09-30 前一次改动（`856b108`）把总览页从「7 张卡并列」改为三层架构，
但那只是**重新排版**——信息维度**一个没动**。用户随即指出两个硬缺陷。

## 2. 缺陷取证（Source → Propagation → Terminal）

### 缺陷 A：`0/3` 是「未启动引擎的占位上限」，不是业务量

```
backend/api/overview.py:67-68
    "sent":  adm.sent_count,     # 当前引擎**实例**的本次已发
    "limit": adm.limit,          # core/auto_dm.py:189  self.limit = settings.max_target
```

- `adm` 是 `app.state.adm`——**单个发送引擎实例**。引擎未启动时，
  `limit` 回落为配置默认值（实测 **3**），`sent_count` 为 0。
- ⇒ 总览恒显示 `0/3`，它描述的是「**一个不存在的任务的进度**」，与真实业务量无关。
- **污染面**：L1 核心指标条 + 「正在跑」分区的进度条，共 2 处。

### 缺陷 B：项目能力与总览展示严重错位

后端 **21 个路由模块 / 约 250 个端点**，总览页只覆盖了 4 项能力（私信 / 直播 / 账号 / 任务）。
侧栏 11 项功能中，**7 项在总览页零体现**：

| 实际能力 | 后端数据源 | 总览（改前） |
|---|---|---|
| **采集（内容浏览）** | `GET /api/crawl/history`（`crawl_history` 表） | ❌ 无 |
| 采集策略 | `/api/crawl_policy`(5) | ❌ 无 |
| 知识库 | `/api/ai/*`(61) | ❌ 无 |
| 模型链路 | `/api/model_hub`(11) | ❌ 无 |
| 通知 / IM | `/api/notify`(10) | ❌ 无 |
| 私信日统计 | `/api/open/stats/daily` | ❌ 无 |
| 直播间管理 | `/api/live_rooms`(6) | ❌ 无 |

**Terminal**：用户观感「总仪表台功能杂乱无序」+「采集功能完全没有体现」。

---

## 3. 决策（用户 2026-09-30 拍板，三项）

| # | 决策 | 取值 |
|---|---|---|
| **D1** | L1 指标口径 | **改为业务漏斗**：今日采集 / 今日评论 / 今日私信 / 活跃账号 |
| **D2** | 覆盖范围 | **按业务漏斗分区重排**，每分区只放最关键 1–2 个指标，**避免堆砌** |
| **D3** | 本次发送进度 | 由**后端新增聚合端点**提供「今日已发」，总览**不再直读引擎内存态** |

---

## 4. 架构决策：新增只读聚合端点 `GET /api/overview/funnel`

### 4.1 为什么必须新增端点（而不是前端拼装）

D3 要求「不直读引擎内存态」⇒ 数据必须由后端按**业务真值**聚合。
前端手上只有 `adm` 内存态与 `dm_messages` 计数，**无法自行完成清洗**。

### 4.2 契约（Canonical Contract）

```jsonc
GET /api/overview/funnel?tz=8
{
  "ok": true,
  "date": "2026-09-30",          // 统计日（按 tz 切）
  "tz": 8,
  "crawl": {
    "today_runs": 12,             // 今日采集轮次（crawl_history 行数）
    "today_results": 3480,        // 今日采集结果条数（sum(result_count)）
    "kinds": {"video": 8, "comment": 3, "user": 1}
  },
  "capture": {
    "today_comments": 921,        // 今日捕获评论（清洗后）
    "today_theirs": 410           // 今日客户来消息
  },
  "dm": {
    "today_sent": 267,            // 今日**真实**已发私信（清洗后，见 §4.3）
    "rejected": 12                // 今日被平台拒发（独立维度，不混入 sent）
  },
  "accounts": {
    "total": 2, "active": 2, "credential_ok": 2
  }
}
```

### 4.3 🔴 口径铁律：`role='me'` **不等于**真实已发私信

`dm_messages` 中 `role='me'` 包含**平台提示文案**（实测：某账号 183 条 `role='me'`
全是平台提示，非真实私信）。**不得**直接 `COUNT(*) WHERE role='me'`。

**唯一权威判据 = 复用既有清洗 SSOT，禁止自造**：

| 判据来源 | 用途 |
|---|---|
| `services/message_schema.py::SYSTEM_TEXT_PATTERNS` | 平台模板文案（`对方回复或关注你之前…`、裸 `{{0}}`） |
| `services/message_schema.py::NOISE_PREFIXES` | 已知噪音前缀（`[投递验证]`/`[系统提示]`/`[未知媒体]`…） |
| `services/delivery_verify.py::PLATFORM_REJECT_PREFIX` | 平台拒发文案（`对方回复或关注你之前`） |
| `services/dm_search.py:233-234` 既有读侧口径 | `msg_type <> '50001'` 且非 `[未知媒体]%` |

**`rejected` 独立成维度**：被拒发**不是**已发送。混入 `today_sent` 即是假成功
（违反项目铁律「禁止假成功」）。

### 4.4 为什么端点用 `GET` 且**零网络**

- 只读本地 SQLite（`crawl_history` / `dm_messages`），**零网络零浏览器**
  （沿用 `CapabilityHealthSection` 的探针铁律）。
- 可安全高频轮询；不发任何写操作、不触发捕获/昵称查询。

### 4.5 时区

`tz` 参数默认 `8`（中国时区），沿用 `dm_search.daily_stats` 的既有约定
（`tz_hours` 夹取 `[-12, 14]`）。**日切按本地时区**，不用 UTC——
否则「今日」在北京时间 08:00 前会错位到前一天。

## 5. 信息架构（D2：业务漏斗分区，每区最多 2 指标）

```
L0 待处理横幅（仅在确知异常时出现；不含 unknown/未校验）
─────────────────────────────────────────────────────────
L1 业务漏斗（四个环节，一条主线：入口 → 中间 → 出口 → 资源）
   ① 今日采集   ② 今日评论   ③ 今日私信   ④ 活跃账号
─────────────────────────────────────────────────────────
L2-① 入口 · 采集与内容      （采集轮次/结果 + 采集历史速览）
L2-② 触达 · 私信与直播      （今日私信 + 发送进度 + 直播在线 + AI 回复）
L2-③ 资源 · 账号与能力      （账号凭证 + 能力健康）
```

**分区命名依据**：动词性心智（对齐侧栏「任务/资产/记录」的既有约定），
用户读的是「我的获客链路走到哪一步」，而不是「哪个模块有数据」。

---

## 6. 不做的事（明确排除，防范围蔓延）

- **不**把侧栏 11 项全部搬上总览（用户明确「避免堆砌」）。
- **不**新增知识库/模型链路/通知/连麦/MCP 的展示——它们属配置与运维域，
  总览只做**业务漏斗 + 资源健康**。
- **不**改任何既有端点的契约（新增端点，旧端点原样保留）。
- **不**为排版改语义。

## 8. 验收判据（可机械验证）

1. `/api/overview/funnel` 返回 §4.2 契约的**全部字段**，且 `ok=true`。
2. `today_sent` **不含**平台提示文案：用 `SYSTEM_TEXT_PATTERNS` 构造的样本
   必须被排除（负控：去掉清洗 → 计数变大 ⇒ 证明清洗生效）。
3. 总览页 L1 **不再出现** `ov.sent`/`ov.limit`（grep 产物为 0）。
4. `tz` 边界：同一时刻 `tz=8` 与 `tz=0` 返回的 `date` 允许不同（日切正确）。
5. 全量 `tsc --noEmit` exit 0；`vite build` exit 0。
6. 六处版本齐平。
