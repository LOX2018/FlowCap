# ADR-027 · 留资处置铁律：**私信的唯一目的是留资**

> 状态：**Accepted**（用户 2026-09-29 拍板）
> 版本：v0.45.92 → **v0.45.93**
> 分支：`design/better-douyin`
> 触发：用户实测反馈（会话「668」截图 + 原话）
> 相关：ADR-025（命中库通用性门槛）、ADR-026（直播首触话术引导化）

---

## 0. 用户原话（判据来源）

> 「要知道私信的目的就是留资，这个对方的聊天内容如果是有明确的问题则先针对问题回复
> 体现专业性同时引导留资，但如果是这种对话对象，他的聊天内容没有明确目标的人群
> 直接引导留资就行，别说什么之后再联系，抖音是快平台，客户前一秒还在你这下一秒就去
> 别人那了，根本没有沉淀的必要。」

---

## 1. 实测事故（截图原文，会话「668」）

客户回「好」「单位给报了工伤，我下午去人社局问问」之后，AI 发出：

- 「好，问问进度。认定书下来第一时间通知我，我帮你算清赔偿清单。」
- 「我等你人社局问完的消息，认定书到手我就帮你算清单。」

⇒ **把客户放走**（等对方回头）。在抖音上等于丢单。

## 2. 三处根因（全在输入侧，不是模型不行）

| # | 根因 |
|---|---|
| ① | **Agent prompt 的漏斗是「先判断 → 再算清单 → 最后才要联系方式」**，且明写「被拒绝 N 次内不再索要，**安心解答**」⇒ 主动鼓励"不用急" |
| ② | **主兜底池 4 条全都不含索要**（都是「请您说下部位/材料」型）⇒ 模型不可用/被拦时，客户收到的回复**没有任何留资动作** |
| ③ | 系统侧**没有「这轮有没有索要」的机械判据** ⇒ 「以后再说」式收尾可畅通外发 |

## 3. 决策

### D1 判据：**不含索要 ⇒ 未推进留资**
与用户第 3 条机械规则字面一致。
> 曾用「无索要**且**无提问」的判据 → 实机打回：专业解释句里的疑问词会把「放走句」
> 判成合格（漏判）。故收敛为**只看有没有索要**。
> 两条易错常识：**「承诺给价值」≠「索要」**（「我帮你算清赔偿清单」是承诺，不是索要）；
> **放走语判据必须锚人称**（`等认定/等结果` 是陈述流程，合法；`等**你的**消息 /
> 通知**我** / 回头再说` 才是放走）。

### D2 处置顺序：**保专业性优先**
`定向重试` → `保留专业回答 + 末尾追加索要` → `整句替换为引导留资话术`。
> 为什么不能直接整句替换：用户要求「有明确问题则**先针对问题回复体现专业性**」，
> 整句换成通用留资话术会**丢掉专业回答**（实测发生）。故追加优先，替换兜底。

### D3 系统层覆盖，**不动用户资产**
新增 `_LEAD_DISPOSITION_RULES`，追加在 `build_system_prompt` **最末**
（紧贴 user 消息 + 显式「覆盖上文一切相反要求」）。
> **为什么不能改 Agent prompt**（与 ADR-026 D2 同一纪律）：它是**用户资产**
> （用户可自定义）；把诉求写进去 = 越权改动用户配置，且下次换 Agent 又会失效。
> 写在系统层才能保证「无论用户怎么写 prompt，留资铁律都成立」。

### D4 降级路径同受约束
终末 `fallback_reply` 也过同一判据（主兜底池 4 条全不含索要 ⇒ 一律换引导留资话术）。
> 与 H-24「通道静默无效」同族：**只修主路径、漏掉降级路径** = 缺陷从另一条路复发。

### D5 `max_lead_ask` 真接线
`_KV_ASK_COUNT` 由「预留未用」变为真计数（`_lead_ask_count`/`_bump_lead_ask`），
且**同时实现** prompt 里"被拒 N 次不再索要"的承诺 —— 否则会变成刷屏。

### D6 新增配置 `lead_first_reply`
「客户无明确问题」专用留资话术（用户可覆盖）。

## 4. 未触碰

- 发送/出队链、`max_reply_len` 语义（追加结果不过 `max_reply_len` —— 它约束模型输出，
  不约束护栏的补充动作；真实链在 `_generate_reply` 之后不再校验）。
- 「客户留资后只回确认」的既有行为。

## 5. 验证（全实跑）

| 层 | 结果 |
|---|---|
| `backend/test_lead_disposition_guard.py` | **10/10**。**两轮负控**：清空判据常量 → **5 项红**；断开调用点 → **G7 红**；均还原复绿 |
| `scripts/verify_lead_disposition_real.py`（真实网关） | **4/4 PASS**。样例见 §6 |
| 全量回归 | **1137** 项，唯一失败 = **基线既有**（`test_h29 G7` 读真实生产库） |

## 6. 实机产出样例（真实网关 agnes-2.5-flash）

| 客户 | 回复 |
|---|---|
| 「好」 | 「你这个情况得按你当地标准细算，留个手机号，算好我发你。」 |
| 「没下来」 | 「这种情况建议尽快申请工伤认定，以免过期。你留个手机号，我帮你看看现在补材料还来不来得及。」 |
| 「单位给报了工伤，我下午去人社局问问」 | 「单位申报后，人社局会出具受理回执，记得保存。方便留个手机号，我按你当地标准算份清单发你。」 |
| 「我这个情况能评几级」 | 「要判断等级得看治疗后遗留的功能障碍程度，不是按伤情名字对号入座。你把受伤部位、诊断结论发我，我帮你初步看下。方便留个手机号，我按你当地标准算份清单发你。」 |

⚠️ **实机验证抓出两处我自己写的缺陷**（已固化进脚本注释与用例）：
① 验证脚本**绕过 `_generate_reply` 直调模型** ⇒ 看到的是"未治理"输出（假失败）；
② 脚本对返回结果**二次 `validate_reply`** ⇒ `max_reply_len=60` 把护栏刚追加的索要句
截掉（假失败）。**教训：验证脚本必须走真实链路，且不得复制真实链之外的校验。**

## 7. 边界（诚实标注）

1. 本 ADR **不解决**"客户不回复"（那是触达质量/话术吸引力问题，另立议题）。
2. 主兜底池**保留原 4 条**（会话内承接场景仍可用），只在"未索要"时替换为引导留资。
3. 单次追加/替换**不区分客户情绪**（如已明确拒绝留资）—— `max_lead_ask` 只按次数兜底。
