# ADR-033 · 直播意向门归属 Agent 层 + 投递证据时间锚 + 失败可观测

- **状态**：Accepted
- **日期**：2026-09-30
- **版本**：v0.45.121
- **触发**：用户报障「系统性的 AI 回复发送功能性障碍」（4 症状）
- **相关**：ADR-007（沉淀池/高价值过滤）、C-06（契约）、ADR-026（投递真相）

---

## 1. 背景（用户报障原话）

> 「实时弹幕的表格会突然之间发生变化，将发言人的表格变宽；单位内容明显不属于工商的，
> 就不用发了。这些都不属于意向客户；发送失败，既没有显示失败缘由，也没有进入错误统计；
> 显示已送达，却没有对应的文案。这些问题都是属于系统性的 AI 回复发送功能性障碍」

取证后确认为 **5 个互相独立**的缺陷（含顺带抓出的字段漂移），分属呈现层、门控层、数据契约层。

---

## 2. 决策

### D1 · 意向判定归属 **Agent 层**（不在引擎内建行业规则）

| 选项 | 结论 |
|---|---|
| A. 引擎内置工伤关键词表 | ❌ 否决 —— 用户 2026-09-30 已明确「这是通用项目，机械门禁会丧失通用属性」 |
| B. 复用既有 `high_value_keywords`（阈值过滤） | ❌ 否决 —— 项目既有实现默认休眠（阈值 0 ⇒ 恒真），且 `score_text` 是**子串累加**：既放过含「等级」两字但与业务无关的闲聊，也误杀不含关键词的真实咨询；启停粒度是「全局配置」而非「每个 Agent」 |
| **C. 新增 Agent 级意向门，引擎只消费结论** | ✅ **采纳** |

- 配置落在 Agent：`intent_scope_enabled`(bool, 默认 **False**) / `intent_scope`(list[str], 默认 **[])。
- 引擎侧唯一动作 = **匹配**（`ai_reply.intent_in_scope`，SSOT）；**不含任何行业词**。
- 调度器只持有上层注入的回调 `DispatchCenter.intent_verdict`。

**默认语义（用户拍板）**：未配置 ⇒ 不启用（**零回归**）；配置了范围 ⇒ **未命中即不发**。

### D2 · 投递证据必须带**时间锚**

`delivery_state_of(..., after_ts)`：`after_ts>0` 时只统计**本次发送之后**到达的证据。

- 旧行为 = 只按 uid 宽匹配**全历史** ⇒ 该 uid 曾有过回声帧/投递标记，本次**全部**记录（含
  未发/失败行）都被判 `delivered`（实库实测：`verify:` 标记 61 / 回声 115 条，污染面极大）。
- 不传 `after_ts`（0）保持旧行为，供其它调用方零回归。

### D3 · 状态档优先级：**失败是确定的负向事实，不得被历史证据掩盖**

`displayStatus`：`rejected > fail > delivered > 调度状态`（原为 `delivered` 优先于 `fail`）。

### D4 · 失败必须可观测（用户原话「既没有显示失败缘由，也没有进入错误统计」）

- 新增 `SendRecord.attempted_content`（失败时 `content=None`，但**试发文案**仍保留）并下发前端；
- 表格「私信文案」格：失败行**优先渲染可读缘由**（不再只剩一个红标签）；
- 「错误」计数改与**表格同一判据**（`displayStatus(...)[1] === "danger"`），
  弃用 `/api/ai/status` 的 `errors`（那是 **AI 会话 worker** 计数，与直播发送链不通）。

### D5 · 列宽稳定（用户原话「表格会突然之间发生变化，将发言人的表格变宽」）

两张表格（直播页 / 查阅模式）统一 `table-fixed` + `colgroup` 固定列宽 —— 列宽与内容解耦。

### D6 · 投递标记补 `extra.kind`（H-29 单一出口契约违反，门禁抓出）

`delivery_verify.mark_delivery_verified()` 是**裸 SQL 写入点**，不经 `MessageRecord.build()`
⇒ 未写 `extra.kind`。后果：读侧按 `kind` 白名单放行时漏判该行，且
`test_h29_message_schema.test_g7_all_rows_labeled` 恒红。

- **写侧修复**：`extra` 增 `"kind": "delivery_marker"`。
- **存量修复**：生产库（张老师 `m17db0f8209156f26`）8 行按 **id 逐条**回填
  （只加缺失键、不删改其它字段、幂等），写前 `shutil.copy2` 备份并**读回比对字节数**；
  写后残留未标注 **0/1156**。这只是**旧库孤儿**，本批新写的行本就带 kind。

## 3. 后果

**正向**
- 意向过滤能力就绪但**默认休眠**（零回归）；行业范围由 Agent 配置决定 ⇒ 通用引擎不失通用。
- 「已送达却无文案」在数据层被根治（不再是呈现层的遮盖）。
- 失败可观测三件套齐：**缘由**（表格内）+ **试发文案**（`attempted_content`）+ **计数同源**。

**负向 / 权衡**
- 意向门是**子串匹配**，不做 LLM 精判（`judge_high_value` 仍在，未接线）⇒ 存在
  「含关键词但非意向」（假放行）与「换词表达」（假拦截）两种误差，用户可从 Agent 配置侧调词表。
- 时间锚依赖 `dm_messages.ts` 的写入时刻（WS 到达时刻）⇒ 若写入延迟跨过 `sent_at`，可能漏判
  （方向是「宁可少判送达」，不谎报 —— 与 `delivery_state_of` 既有「不臆断」纪律一致）。
- 列宽固定后，超长内容依赖 `truncate`（全文仍在 `title` 悬浮可见）。

## 5. 边界（诚实标注）

- **意向门未接入 LLM 精判**（ADR-007 Phase 4 的 `judge_high_value` 仍是独立能力）。
- 未做真机端到端（需开播 + 用户授权写接口）。
- 前端判据为**源码级**（本项目无前端单测资产，沿用 `test_h20` 既有范式）。
