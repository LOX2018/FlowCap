## 一、现状实测（先摆事实）

### 1.1 四大板块的策略**各存各的**，标签体系没接进去

| 板块 | 策略实际存在哪 | 是否受标签指引 |
|---|---|---|
| 直播监听策略 | `kv: live_room_configs`（`api/live_config.py:74`） | ❌ |
| 直播间管理 | `kv: live_rooms`（房间登记层，ADR-003） | ❌ |
| 视频采集策略 | **无独立配置**，只有结果表 `crawl_history` | ❌（连配置都没有） |
| 私信 WS 回复策略 | `ai_reply` 全局 / Agent 配置 | ❌（走 Agent，不属标签） |
| **私信发送与风控** | `app_config.send` | ✅ **唯一接入点** |

### 1.2 `app_config` 有 8 个 section，但标签只声明 3 个

```
app_config_schema.SECTIONS:
  general(7) / dm(4) / live(10) / live_orchestration(7)
  send(13) / notify(4) / capture(27) / automation(35)
        ↑ 8 个

config_tag.MANAGED_SECTIONS = ("send", "live", "capture")   ← 只 3 个
```

### 1.3 🔴 最关键的实测事实：**标签体系只有一处真实消费点**

```bash
grep -rn "scope_of\|tag_of(" --include=*.py backend/
  → services/dm_dispatch.py:120   ← 唯一一处
```

`config_tag.resolve()` 与 `resolve_all()` **定义了但无人调用**。
⇒ 所谓「标签指引」目前只在**发送风控**上生效，其余全是空头声明。

### 1.4 标签元数据过于笼统

- 只有 `{id, name, created_at, updated_at}`，**无业务维度**
- 新建占位符 `如：高频账号 / 保守账号` → 引导出的是**风控档位**，不是业务标签
- 账号绑定被切成两个独立下拉（TagSection 选标签 / AgentSection 选 Agent）

## 二、设计意图（回归本源）

`config_tag.py` 文件头既有约定（应保留）：

| | 管什么 |
|---|---|
| **Agent** | 「**回什么**」—— prompt / 知识库 / 话术 / 档位 |
| **标签** | 「**怎么发 / 怎么听 / 怎么采**」—— 各板块策略参数 |

**标签是指引，不存参数副本** —— 参数值仍由各原单位存储，标签只决定「读哪个 scope」。
这条零回归契约（未绑定 → scope=None → 读全局）必须**继续遵守**。

## 三、规划：三层标签指引体系

```
                     标签（Tag）
        ┌──────────────┼──────────────┐
     业务维度        板块绑定            参数 scope
   biz_line         send/live/         app_config
   scene            capture/dm/…       (section, scope=tg_xxx)
```

### 3.1 第一层：标签加业务维度（**已做，向后兼容**）

`save_tag()` 新增三个**可缺省**字段：

| 字段 | 含义 | 例 |
|---|---|---|
| `biz_line` | 行业线 | 工伤 / 车险 / 电商 |
| `scene` | 场景 | 四川 / 华东 / 直播间引流 |
| `sections` | 该标签适用板块（空 = 全部 MANAGED_SECTIONS） | `["send","live"]` |

未传时行为与改造前**逐字一致**（旧数据零回归）。

### 3.2 第二层：板块级绑定（**已做**，待接通）

新增 `{account: {section: tag_id}}` 绑定：

| 函数 | 作用 |
|---|---|
| `bind_section(account, section, tag_id)` | 绑单个板块（空 tag_id = 解绑） |
| `scope_of(account, section)` | 取 scope：**板块优先 → 回落整账号 → None(全局)** |
| `effective_bindings(account)` | 聚合展示（板块优先，回落整账号） |

### 3.3 第三层：把四大板块**真正接进来**（**未做，本规划核心**）

这是你要的"体系规划"主体。现状缺口与接法：

| 板块 | 缺口 | 接法建议 | 难度 |
|---|---|---|---|
| **私信发送风控** | 已接入 | 保持（`dm_dispatch.py:120`） | — |
| **私信 WS 回复策略** | 走 Agent 不走标签 | **两条路**：① 标签只管"接收/回复频率类参数"（如 `dm` section 的 4 个字段）；② 内容逻辑仍归 Agent。**不得越界管内容** | 低 |
| **直播监听策略** | 策略在 `live_room_configs`，标签接不进去 | 方案：**房间层引用标签**（`live_rooms` 每房间加 `tag_id`），而非账号级。因直播间是"一场一策" | 中 |
| **直播间管理** | 房间登记层（ADR-003）已有 | 同上，挂 `tag_id` 到房间 | 中 |
| **视频采集策略** | **连配置项都没有**（只有结果表） | 需**先建采集策略 schema**（`capture` section 已有 27 字段，可能已覆盖，需核对） | 中~高 |

### 3.4 前端：账号绑定的**一处聚合**（未做）

现状：`TagSection` 选标签、`AgentSection` 选 Agent，两个下拉互不相干。

建议形态（**一处配完**）：

```
账号：尚进工伤小助理
  ├─ 回复人格（Agent）  [工伤赔偿留资助手（唐律） ▾]
  ├─ 发送风控（send）   [工伤-四川 ▾]
  ├─ 直播监听（live）   [直播间引流 ▾]
  └─ 采集策略（capture）[默认 ▾]
```

## 四、🔴 必须先拍板的三个决策

| # | 决策 | 选项 | 我的建议 |
|---|---|---|---|
| **D1** | 直播策略按**账号**还是按**房间**绑标签？ | A 账号级（简单，但一场一策做不到）<br>B **房间级**（`live_rooms` 挂 tag_id） | **B**。直播间天然是"一场一策"，账号级会互相覆盖 |
| **D2** | 私信 WS 回复：标签管到哪一层？ | A 只管**频率类**参数（dm section）<br>B 连内容一起管 | **A**。内容归 Agent 是既有契约，越界会职责打架 |
| **D3** | 采集策略是否需要**新建**配置项？ | A 复用 `capture`（27 字段）<br>B **新建采集策略 schema** | **B（已核实，非推断）**：见下方 §4.1 |

### 4.1 D3 核实结论（实测，已消除"未核实"）

`capture` section 的 27 个字段**全部是"捕获与存储"类**，**没有一个属于"采集策略"**：

| 分类 | 数量 | 例 |
|---|---|---|
| 策略类 | 8 | `history_max`（历史补全会话数）、`probe_*`（探针巡检） |
| 存储类 | 4 | `userinfo_cache_sec`、`origin_image_ttl_days` |
| 其它（探针/图片） | 15 | `probe_nickname_healthy`、`image_force_hosted` |

⇒ **采集侧（关键词、目标范围、采集量上限、去重口径）目前零配置项**，
视频采集策略在 `app_config` 中**根本不存在**。这是体系缺口，不是"没接标签"的问题。
