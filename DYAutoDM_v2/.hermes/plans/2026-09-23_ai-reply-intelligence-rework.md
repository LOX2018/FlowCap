### 0.1 由 F7+F8 合成的根因（本轮最关键发现）

`_build_history` 只认 `msg_type='text'`，而**能触发 AI 回复的消息几乎全是最新的 WS 消息**（`msg_type='7'`）。
⇒ 恰恰是"新消息旁边的历史"一条都筛不出来，`history=[]`。

**表现即用户所述**：AI 每次只见当前一句 → "只根据最后一条信息回复、完全不像读过上下文"。
这不是"AI 笨"，是**上下文注入链路静默失效**。

## 一、四个缺陷的根因定级

| 用户反馈 | 根因（指到行） | 定级 | 修复难度 |
|---|---|---|---|
| ① 会话回复不看历史、只按最后一条 | **F7∧F8 上下文注入失效**（主因）+ F9 窗口过小（次因） | 缺陷 | 低 |
| ② 直播配了私信文本 → 沿用固定文本 | **F2∧F3∧F4∧F5：Agent scopes 默认不含 live** → AI 被静默关掉 | 缺陷 + 可观测性缺失 | 低 |
| ③ 直播 AI 只按单条弹幕随机生成 | **F10 缺"按人聚合"层**（非 bug，是能力缺失） | 能力缺口 | 中 |
| ④ 案例库解析差、QA 牛头不对马尾 | **F11 抽对无语义校验 + LLM 失败静默降级**（主因）+ F12 命中阈值过高（次因） | 缺陷 | 中 |

### 1.1 关于 ② 的重要澄清（避免误修）

用户直觉是"配了固定文本所以 AI 没生效"。但按 F6，调度顺序**本就是 AI 优先**。
真实链路是：**scopes 判定把 AI 关掉了**（F5），导致走了词库回落，看起来像"固定文本优先"。

⇒ 修法不是改调度顺序（改了也没用），而是 **① 修 scopes 默认值 ② 让"AI 未生效"在 UI 上可见**。
**这两件事必须先做实机确认**：读线上 kv_store 里 `ai_reply_config` 与各 Agent 的 `scopes` 实际值。

### 1.2 关于 ① 的诚实标注

`【代码事实】` F7/F8/F9 已可复跑验证。
`【推断】` "线上因此 history 恒空" —— 需在有真数据的库上跑一次 `msg_type` 分布统计才能坐实。
**design 分支的 `data/dyautodm.db` 当前 `dm_messages` 为 0 行，无法取证**，须到测试环境（主分支 `dyautodm_test` / `C:\temp\dyautodm_test`）验。

## 二、分批策略（为什么必须分两批）

### 红线（来自 F16）

`core/dispatch → dm_dispatch.submit_by_uid` 是**发送侧唯一风控闸门**。
用户补充需求里的「沉淀池 + 客源筛查」要改的正是这条路上的**出队顺序**。
一旦破坏闸门不变量，后果是**全账号级频控**，且不会报错。

### 分法

| 批次 | 内容 | 触碰发送路径？ | 版本增量建议 |
|---|---|---|---|
| **第一批（P1）** | ①③④ + ②的开关透明化 | ❌ 不碰。只决定"发出去的内容是什么" | patch +0.01 |
| **第二批（P2）** | 弹幕沉淀池 + 高价值筛查 + 按人聚合 | ✅ 触碰出队逻辑 | **架构变更**，走 ADR |

**判据**：P1 全程不改 `dispatch.py` / `dm_dispatch.py` 的出队与闸门分支。

## 三、第一批（P1）—— 纯缺陷修复，不动发送路径

### P1-1 · 会话回复上下文注入修复（对应缺陷 ①）

**设计契约**：AI 回复前必须读到该会话对象的**完整近期聊天记录**。

| 项 | 内容 |
|---|---|
| 改动点 | `_build_history`（`ai_reply.py:1319-1333`） |
| 修法 | ① 取消 `msg_type='text'` 硬筛，改为**排除式**：排除 `sticker/voice/image/video/read_receipt` 及数字串等价类（复用 `api/messages.py:158-166` 的映射表，**抽成单一 SSOT 常量**，不得抄第二份）<br>② `HISTORY_LIMIT` 改为读配置 `max_history`（F9，消除"配置项从未被读"的悬空契约）<br>③ 窗口内消息按 id 升序回传（已是，保持） |
| 验收判据 | 造一条含 `'7'` 的历史 → `_build_history` 返回条数 > 0（**修复前必为 0，构成 RED→GREEN**） |
| 回归风险 | 低。仅影响喂给模型的 history 内容 |

**⚠️ 待你定的口径**：窗口取多大？当前 6，配置里有 10。
建议 **默认 10**，但专业库 RAG 已占上下文（≤6000 字），需实测 token 不爆。

### P1-2 · 直播 AI 接线可观测化（对应缺陷 ②）

| 项 | 内容 |
|---|---|
| 改动点 | `core/auto_dm.py:380-391` + 前端直播页 |
| 修法 | ① `_make_gen_dm_message` 返回 None 时，**把原因带出去**（当前只 `logger.warning`，UI 无感）<br>② 直播页展示「AI 文案：已生效 / 未生效（原因：scopes 未含 live / 档位 kb_only / 未启用）」<br>③ 另修 **F4**：新建 Agent 时后端兜底 `scopes`（缺省 `["dm"]` → 建议改为继承全局默认或显式 require） |
| 验收判据 | 构造 scopes 不含 live 的 Agent → 直播页**显式显示**"AI 未生效：Agent 作用域未勾选直播监听" |
| 回归风险 | 低。纯可观测性 + 默认值 |

**⚠️ 待你定的口径**：新建 Agent 的 scopes 默认到底是 `["dm"]` 还是 `["dm","live","crawl"]`？
- 保守（现 `["dm"]`）：AI 默认只管私信，需用户显式勾选才进直播 —— 安全但易踩"开了没生效"
- 宽松（全选）：开箱即用，但**未经确认就把 AI 接到发送侧**，与 F16 红线的谨慎原则相悖
- **我推荐保守 + UI 强提示**（既守住红线，又消除静默失败）

### P1-3 · 案例库学习质量（对应缺陷 ④）

| 项 | 内容 |
|---|---|
| 改动点 | `reply_kb.learn_from_history`（`:201-271`） |
| 修法 | ① **抽对加语义校验**：them/me 之间不得跨越其它 them 消息（当前会跨 5 条不相关消息配成对 —— 这就是"牛头不对马尾"的直接来源）<br>② **LLM 失败不再静默降级**：改为返回 `{ok:false, reason:...}` 并在 UI 明示"本次未走 LLM 提纯"，而非静默写库<br>③ F12 阈值：字符集 Jaccard 0.85 对中文过严 → 建议**主用语义 embedding**（项目已有 `sem_threshold=0.40` 的 embedding 链路，见 `ai_reply.py:153-157`），字符 Jaccard 降级为辅 |
| 验收判据 | ① 造"them → them → me"序列 → 不得产出 (第1条them, me) 的错配<br>② 断网/坏 key → 返回 `ok:false` 且**库中无新增** |
| 回归风险 | 中。会改变入库内容，需提供"重学"入口并允许人工删改（现有 UI 已支持删改） |

### P1-4 · 档位语义复核（跨 ①②③ 的横切项）

`strict_level` 三档：`kb_only`（AI 完全不参与）/ `rag` / `free`。
若线上落在 `kb_only`，则 ①②③ 都会表现为"AI 没智能"。
⇒ P1 开工第一件事：**读 kv_store 实际值**，确认不是这个开关在作祟。

## 四、第二批（P2）—— 沉淀池 / 客源筛查 / 按人聚合（**需先拍板决策**）

### P2 的核心设计

```
live_hook 弹幕
      ↓
【新增】弹幕沉淀池（扩 dm_uid_sink，不新建平行表 —— 避免双写）
      ↓  按 peer_uid 聚合该人全部弹幕
【新增】价值打分
      ↓
【新增】出队排序：高价值优先（而非先到先发）
      ↓
dispatch.submit  →  dm_dispatch.submit_by_uid（闸门**不动**）
```

**关键约束**：P2 只改「谁先出队」，**不改闸门本身的限额与冷却**（F16 红线）。

### 🔴 待你拍板的三个决策（不定就没法动手）

**决策 1 · 高价值人群标签怎么定？**

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 可配置关键词权重表**（推荐） | 用户在设置里填行业词 + 权重（如"工伤/赔偿/多少钱"= 高价值，"666/来了"= 低价值） | 需用户自己配；零 token、快、可解释 |
| B. LLM 现判 | 每条弹幕问一次模型 | 烧 token、慢（私信有延迟抖动）、判定不可解释、失败要兜底 |
| C. A 为主 + B 增强 | 关键词先筛，命中模糊时问 LLM | 最复杂，但兼顾覆盖与成本 |

**决策 2 · 沉淀窗口多久？** 弹幕是流式的，"聚合某人的每条弹幕"要等多久才够？
- 短（30s）：快，但可能只抓到 1 条就出队 → 退化成现状
- 长（5min）：聚合充分，但**错过直播高峰的即时性**（用户要的是"趁热打铁"）
- 建议 **可配置，默认 60-90s**，且允许"高价值命中即提前出队"

**决策 3 · 未开 AI 时的价值筛选，是否也要按人聚合？**
你说的是"未开 AI → 优先发命中高价值标签的词汇"。
→ 这条**不需要**按人聚合（判定的是词，不是人），实现比开 AI 时简单得多。
→ 确认：是否接受"未开 AI 时仅做词级筛选、不做人格级分析"？
