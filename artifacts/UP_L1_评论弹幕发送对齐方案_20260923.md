## 〇、结论摘要

1. **两处改动都是"真 bug 修复"，但本项目当前 `sendMsgInRoom` / `publish_comment` 没有任何消费方**（API 层 `/api/live/danmaku` 是 TODO 假成功，无评论发布端点）。⇒ 现在实施**不修复任何用户可见功能**，只降低"将来启用时的返工量"。是否现在动手需用户拍板（见 §四·拍板项）。
2. **A1（弹幕）适用度最高、风险最低**：`Origin` 头错误（主站 → 直播域）是本项目**真实存在的缺陷**，一行可改；`with_bd(origin=…)` 在本项目**是空操作**（`with_bd` 签名支持 `origin`，但函数体不使用它，实测除 ECDSA 随机 k 外载荷完全相同）——所以那半句改动**照抄无意义、也无害**。
3. **A2（评论）分三类**：`text_extra` / `celltime` / `reply_to_reply_id` **适用且零风险**；`ticket_matches_session` **建议移植**（实测两个真实账号都会**通过**，不会 brick 功能）；`dtrait_*` 硬校验 **必须不移植**——本项目 auth 无 `dtrait_blob/profile/session_dtrait` 且 `.env.enc` 里也没有这些键，照抄会让 `publish_comment` **100% 抛异常**（静态可证）。
4. **不移植 dtrait 校验的后果不是"少一层保护"，而是"可能假成功"**：本项目 `safe_json` 遇空响应降级为 `{}`，`features._safe` 再包成 `{"ok": True, "data": {}}`（已实测复现）——写接口被风控拦成空 body 时，上层**看不到失败**。
5. **"去掉 random celltime 影响 a_bogus 一致性吗" → 不影响**。签名与发送编码都取自**同一个 dict**，随机值在多轮实测中 `splice_url(data) == requests 实际 form 编码` 恒成立；一致性由编码函数决定，与值是否随机无关。
6. **但发现一条同链路的既有 a_bogus 不一致（范围外，必须一并知道）**：本项目 `splice_url` 用 `urllib.parse.quote(v)`（**保留 `/`**），而 `requests` 发出去是 `%2F`；上游在 **`63ef397` 基线里就已修成 `quote(v, safe='')`**（`utils/dy_util.py:253`），本项目**从未移植**。⇒ 弹幕/评论正文含 `/`（如带链接）时，签名输入 ≠ 实际上线字节。
7. **两处改动都不含"发送闸门"**：本项目铁律「新增发送路径必须收敛到统一 per-account 限速闸门」。若启用弹幕/评论发送，闸门必须一并设计，否则等于新增直发旁路。

## 二、适用性判定（对任务四个指定问题的正面回答）

### Q1. 本项目 auth 是否有 `ticket_matches_session` / `dtrait_*`？
**都没有。** `[实测]` 对 `DouyinAuth()` 逐项 `hasattr`：
`ticket_matches_session=False`、`dtrait_blob=False`、`dtrait_profile=False`、`session_dtrait=False`、`session_dtrait_header=False`、`ecdh_key=False`、`publish_attempted=False`、`publish_server_verified=False`。
（`backend/builder/auth.py:14-26` 的属性清单只有 cookie/cookie_str/private_key/ticket/ts_sign/client_cert/ree_public_key/uid/_ttwid/_ms_cache/_ms_ts。）

**上游强校验逻辑要不要移植？分两半：**
- `ticket_matches_session` → **要移植**。实现只有 4 行（`4479ea7 builder/auth.py:994-1006`），且**实测两个真实账号都返回 True**（cookie 含 `bd_ticket_guard_ts_sign_id` 且 `ts_sign.startswith(sign_id)`）⇒ 移植不会 brick。
- `dtrait_*` 硬校验 → **不要移植**。本项目**没有任何 dtrait 能力来源**（auth 属性无、`.env.enc` 键无、BCC 采集链无）。照抄 = `publish_comment` 恒抛。

**不移植会怎样？** 分条说清：
- 不移植 `ticket_matches_session`：混用旧 `.env` 时服务端返 403 空响应/`status_code=4`，而本项目**没有 `check_risk_response`**，空 body 被 `safe_json` 变 `{}` → 上层 `{"ok": True}` `[实测]` ⇒ **故障不可辨**。
- 不移植 dtrait 硬校验：功能**仍可尝试**（这是对的，因为硬校验会让它彻底不可用）；但若服务端确实强校验 dtrait，失败形态是"200 + 空 body"→ 同样落进**假成功**。⇒ 正确解法不是 raise，而是**把失败显式化**（移植 `check_risk_response` + 返回体透出 status_code）。

### Q2. 本项目 `with_bd` 是否支持 `origin` 参数？
**签名支持，语义不支持。** `[实测]`
- `inspect.signature(Header.with_bd)` → `(self, api, auth, aid=6383, origin='https://www.douyin.com', timestamp=None, dtrait_timestamp=None, dtrait_randbytes=None, require_dtrait=False)`（`backend/builder/header.py:20-22`）。
- 但函数体**从未引用 `origin`**：无 `ecdh_key(aid=…, origin=…)`（上游在 `4479ea7 builder/header.py:45` 有），无 `origin` 分支。
- 实证：固定 `timestamp` 后分别以 `origin` = `www` / `live` / `creator` 构造头部，**除 `req_sign`（ECDSA 每次随机 k）外，client-data 载荷逐字段相同** ⇒ `origin` 对实际发出的请求**无影响**。
- 结论：上游那句 `with_bd(api, auth, origin=LIVE_URL)` 移植到本项目是**空操作**；"证书按直播域生成"这个真实收益**要靠移植 `ecdh_key` 才能拿到**（`4479ea7 builder/auth.py:1008+`，本项目缺，属另一条工作线）。

### Q3. 去掉 random celltime 会不会影响 a_bogus 签名一致性？
**不会。** `[实测]`
- 原理：`params.with_a_bogus(data)` 内部 `data = splice_url(data)`（`backend/builder/params.py:50-61`），随后 `requests` 用**同一个 dict** 编码 form body。签名输入与上线字节**同源同 dict**，与某个 value 是否随机无关。
- 实证：`comment_send_celltime/comment_video_celltime` 取 `random.randint(1000,20000)` 连跑 3 轮，`splice_url(data) == requests.models.RequestEncodingMixin._encode_params(data)` **恒 True**。
- **真正会破坏一致性的另有其事**（本次顺手发现，范围外）：
  - `text_extra = []`（list）→ 签名含 `text_extra=%5B%5D`，wire **丢掉该键** ⇒ 不一致（**适用 A2-1，必修**）。
  - `splice_url` 对 `/` 保留原字符而 `requests` 发 `%2F` ⇒ 正文含链接时不一致（**X3，上游 63ef397 已修，本项目未修**）。
  - 正文字符串含空格：`quote` 给 `%20`、`requests` 给 `+` ⇒ 不一致（**上游同样未修**，属上游级缺口）。
- ⇒ 结论重述：`celltime` 去随机是**服务端语义对齐**（上游注释：随机值会被当作"播放器内操作"），收益只能实机验证；而 `text_extra` 那一条才是**签名一致性 bug**。

### Q4. 写接口的验证判据（不接受静态结论）
见 §三 每步的"验证判据"。总原则三条（本项目铁律）：
1. **只信服务端回包 + 二次回读**，不信日志、不信 `{"ok": true}`（`scripts/diag/verify_text_send_delivery.py:1-20` 的既有定调）。
2. **写接口失败往往是"200 + 空 body"**，任何判据必须先能区分「空 body / 人机验证头 / 业务 status_code」三类（这正是 `check_risk_response` 的职责）。
3. **"跑完了"≠"发送成功"**：弹幕要在直播间重新拉到的弹幕流里看到自己；评论要用 `comment/list` 回读到该条。

## 四、风险与不做的后果

### 风险
| ID | 风险 | 说明（附证据） |

### 不做的后果（逐项）
- **不做 A1-1（Origin）**：弹幕发送继续带主站 Origin；上游注释称会得到"空响应或业务失败"。本项目无实测数据可证其当前是否真失败 `[待验]` ⇒ 现状是"未知是否可用"，而非"已知可用"。
- **不做 A2-1（text_extra）**：签名 body 与上线 form 永久不一致，评论区发布**必然**处于"签名对不上"的状态——这条不依赖 dtrait，属确定性缺陷。
- **不做 `check_risk_response`**：所有写接口（含既有私信链路以外的调用面）继续把风控 200+空 body 读成成功。
- **不做 A2-5（ticket_matches_session）**：混用旧凭证时，失败形态完全不可辨（这正是上游写那段注释要解决的问题）。
- **不做整个批次 P1**：评论发布能力保持"代码在、但从未跑通、也没有入口"的现状——属于**既有欠账**，不是本次新引入的。

### 需要用户拍板的问题（3 条）
1. **要不要现在启用"直播间弹幕发送"**？（决定批次 P0-4/P1-4 是否做；若不做，P0-1~P0-3 只是纯一致性/可观测性改进，可低优先）
2. **要不要启用"作品评论发布"**？若启用，`dtrait` 能力缺失是**硬前提**（需先解决 dtrait 素材来源），否则只能拿到"空响应 + 假成功"。是否接受"先上线、失败如实报错"？
3. **`splice_url` 的 `safe=''` 修复（X3）是否单独提一笔**？它影响面覆盖所有 `with_a_bogus` 接口，属跨链路改动，需单独决策。
