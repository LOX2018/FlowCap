## 二、每处决策点详细分析

### 1. `verify_account`（核心 — 收敛目标）

**文件**: `auto_dm/accounts.py:422`

**签名**: `verify_account(name=None, timeout=8, dm_loopback=False, auto_fix=True)`

**决策流程**:
1. `credentials_complete(env_path)` → 静态检查 .env 字段齐全性
2. `_load_auth_from_env(env_path)` → 还原 auth 对象
3. `uid_probe.get_uid(name)` → 读 uid 缓存（零网络默认）
4. uid 交叉验证（vs 历史 conv_id） → 身份漂移检测
5. wp 签名四件套检查 → `bool(ticket and ts_sign and client_cert and private_key and (web_protect_str or ree_public_key))`
6. 组合判据得出 wp level：ok / fail / warn / error
7. `auto_fix=True + dm_loopback=True + wp 失效` → 触发 auto_recapture
8. `dm_loopback=True` 时：调 `probe_im_write()` 判 dm 写能力

**返回**: `{ok, wp:{level,label,detail}, dm:{level,label,detail}, uid, auto_fix_triggered}`

### 2. `credentials_complete`（静态守卫）

**文件**: `auto_dm/accounts.py:988`

**签名**: `credentials_complete(env_path) -> (bool, str)`

**调用方**:
- `verify_account()` 内部（行 471）— 收敛 ✅
- `browser_daemon/main.py` 启动守卫（Popen 入口处 `sys.exit(2)`）— **独立未收敛**

**判据**: member_ctx 解密 → 检查 7 个字段全部非空：DY_COOKIES, DY_TICKET, DY_TS_SIGN, DY_CLIENT_CERT, DY_PRIVATE_KEY, DY_WEB_PROTECT, DY_KEYS

**与 verify_account 的关系**: `verify_account` 用它做前置过滤（不全直接 fail），但 browser_daemon 的调用绕过 `verify_account`。

### 11. `crawl._load_auth`（弱判据）

**文件**: `api/crawl.py:76`

**判据**:

## 三、收敛方案

### 目标

把所有 13 处的「凭证有效性判据」统一到**一个函数**，候选入口：

```python
auto_dm.accounts.verify_credential(name) -> CredentialVerdict
```

### 设计原则

1. **`verify_credential` 是唯一的「凭证有效性」入口**。所有模块（包括 browser_daemon 启动守卫）调用它来确定凭证是否可用。
2. **`credentials_complete` 降级为 `verify_credential` 的内部子步骤**，不再被外部直接调用。
3. **`probe_im_write` 的缓存并入 `verify_credential` 的返回结构**，消除双缓存不一致。
4. **`live_session_state` / `uid_identity_verdict` 维持独立**（它们判断的是**直播解密权**，不是通用凭证有效性；但底层探活应复用 `verify_credential` 的结果）。
5. **弱判据点（crawl/platform.auth_for/enrich_auth）改为调 `verify_credential` 的轻量模式**（例如 `verify_credential(name, probes=False)` 只做静态检查，零网络）。

### 需要改的调用点

| 级别 | 调用点 | 改动量 | 说明 |
|------|--------|--------|------|
| **A 类 — 直接替换** | `api/crawl.py:86-87` `_load_auth` 的凭证检查 | 小 | 将 cookie 检查替换为 `verify_credential(name, lightweight=True)` |
| **A 类 — 直接替换** | `auth_helper.py:71-74` `enrich_auth` 的四件套检查 | 小 | 替换为 `verify_credential(name, lightweight=True)`，仅在返回不全时才走 scan 路径 |
| **A 类 — 直接替换** | `api/platform.py:77-78` `_auth_for` 的 cookie 检查 | 小 | 替换为 `verify_credential(name, lightweight=True)` |
| **B 类 — 内部重构** | `auto_dm/accounts.py:988` `credentials_complete` | 中 | 改为 `verify_credential` 私有方法；browser_daemon 启动守卫改为调 `verify_credential`（或从 main.py 侧改为 backend 进程统一校验后透传令牌） |
| **B 类 — 内部重构** | `auto_dm/accounts.py:1049` `probe_im_write` 独立缓存 | 中 | 缓存并入 `verify_credential` 返回的 `dm` 子结构；外部调用方改读 `verify_credential().dm` |
| **B 类 — 内部重构** | `auto_dm/accounts.py:1176` `live_session_state` | 中 | 不合并（判据不同），但底层 `uid_probe.get_uid` 探活结果应统一从 `verify_credential` 的缓存读取 |
| **C 类 — 抽象层保持** | `api/accounts.py:281` `_cached_verify` TTL 缓存 | 小 | TTL 逻辑可保留（60s 轮询缓存），但底层的 `verify_account` 调用改为调 `verify_credential` |
| **C 类 — 无改动** | `account_status()` / `self-check` / `check_account` / `open-browser` | 无 | 它们已调 `verify_account`，改内部实现即可 |

### 函数签名建议

```python
def verify_credential(
    name: str,
    *,
    lightweight: bool = False,     # True=只做静态字段检查(零网络)，False=做完整双引擎
    force_probe: bool = False,     # 跳过缓存，强制真实探活
    timeout: float = 8,
    auto_fix: bool = True,         # 凭证失效时自动触发重捕
) -> dict:
    """账号凭证有效性判据——项目唯一**凭证有效性**决策入口。

    lightweight=True 时：
        - 仅调用 credentials_complete 判静态字段齐全性
        - 零网络、零探活、零 IM 写校验
        - 用于 crawl/platform/enrich_auth 等「只需知道凭证字段齐全」的路径

    lightweight=False（默认）时：
        - 同当前 verify_account 的完整双引擎校验
        - 含 wp 探活 + dm 写探针 + 身份漂移检测 + auto_fix

    返回 {ok, wp:{level,label,detail}, dm:{level,label,detail},
           uid, has_ticket, has_cookie, has_signature, has_web_protect,
           auto_fix_triggered}
    """
```

## 四、风险与注意事项

### 1. browser_daemon 启动守卫最难收敛

`browser_daemon/main.py` 在 `sys.exit(2)` 前调 `credentials_complete`，但 browser_daemon 是独立进程（不 import backend 模块）。解决方案：
- **方案 A**：browser_daemon 内复制一份 `_credentials_complete` 轻量版（仅 `parse_env_dict` + 字段检查，无网络），与 backend 的判据通过共享代码同步
- **方案 B**：把凭证校验提前到 backend 进程发起 spawn 之前（`ensure_bcc` 内先 `verify_credential` 检查，通过才 spawn），browser_daemon 自己不再守卫

推荐方案 A — 改动最小，且 browser_daemon 保持自守卫的防御纵深。

### 2. TTL 不一致问题

当前三层缓存 TTL 互不统一：
- `_cached_verify`: 60s（api/accounts.py）
- `probe_im_write`: 120s（auto_dm/accounts.py）
- `live_session_state`: 300s（auto_dm/accounts.py）

收敛后应统一：`verify_credential` 返回结构自带 TTL 元信息，调用方按需求缓存但不再独立探活。

### 3. `uid_identity_verdict` 不合并

它是「直播解密权」判据（合取），不是「凭证有效性」。它的底层探活结果应从 `verify_credential` 的缓存读取（零新增网络），但判断逻辑本身保持独立。

### 4. lightweiht 模式的返回值语义

`lightweight=True` 时，返回的 `dm` 子结构永远是 `unknown`（未校验）。调用方（crawl/platform）不应依赖 dm 结果。
