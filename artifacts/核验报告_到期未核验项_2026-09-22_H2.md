## 二、H-5 dev 控制台中文乱码 —— ⚠️ **上一会话判据面错位；本轮换到正确判据面后通过**

### 2.1 上一会话的判据面是错的
台账完成标准写「dev 控制台转发日志中 `\xef\xbf\xbd` 计数为 0」。上一会话取的是
`logs/run_*.log` 并把结果登记为闭环 —— 但**该文件由 Python 文件 sink 写出且自带 `encoding="utf-8"`
（`backend/main.py` loguru `logger.add("logs/run_{time:...}.log", encoding="utf-8")`），
按项目知识库明文记载「**run_*.log 文件一直是干净的，这是关键分化证据**」。
⇒ 在 `run_*.log` 上查 U+FFFD **必然恒为 0**，修复前后都一样，**不构成有效判据**（假绿）。

真正的乱码面是 **Rust 壳转发后端 stderr**：`src-tauri/src/sidecar.rs:208`
`log::info!("[backend] {}", String::from_utf8_lossy(&bytes))` —— 冻结态 stderr 被钉死为 GBK，
UTF-8 文本按 GBK 解 → 大批 U+FFFD。

### 2.2 换到正确判据面后的实测（独立复验）

| 判据面 | 修复前基线 | 本轮（v0.44.31） |
|---|---|---|
| Rust 壳转发 stderr（`[backend]` 行） | `_dev_console.log`：2176 行中 **292 行含 U+FFFD**（如「DYAutoDM ����������˿� 8000」） | `_h5_err.log`：**403 行中 0 行含 U+FFFD**，中文完整（「DYAutoDM 后端启动，端口 8000」） |
| 原始字节 `EF BF BD` 计数 | — | **0** |
| 判据面自证 | — | 403/404 行确为 `[..dyautodm_v2_lib::sidecar] [backend] ..` 前缀 = Rust 壳转发 |

**取证方式**：`Start-Process ... -RedirectStandardOutput/_h5_err.log -RedirectStandardError`
（上一会话用 `Start-Process` 未重定向 → 该判据面**根本没被观测**，这正是判据面错位的成因）。

**结论**：H-5 修复**真实有效**，但**台账的完成标准与证据取错了面**，需按本报告更正判据面
