## 〇 一句话结论与推荐

**结论：上游这套能力本身可用、工程量小（净增约 930 行、零新增第三方依赖），但它服务的业务面（给「PK 对手/贡献榜用户」发私信）对 DYAutoDM_v2 当前「直播弹幕→私信」主业没有命中场景，且与项目两条红线（昵称主动查、同账号凭证加频）存在擦边冲突。**

**推荐：🟡 观望（暂不移植），但先做一次「零风险验收」——只把 `static/PK.proto` + `PK_pb2.py` 作为**只读解码素材**纳入上游情报库，不在 backend 落任何联网方法；等出现真实业务诉求（如「对打赏/贡献用户定向私信」试点）时再按本文第二节的成本清单一次性落地。**

理由（扼要）：
1. **主链路已自洽**：弹幕私信所需的 uid/nickname/sec_uid 全部由 BCC 被动下发（`core/live_hook.py:414-463`），PK 榜数据不补任何当前缺失的能力。
2. **WS 侧的 PK 事件接近零成本**（已有 WS 长连接，只是多解几个 method），但**HTTP 侧的 PK 榜是新增主动请求**，直接触碰项目铁律（见第三节）。
3. **收益不确定、成本可逆**：PK 榜的对手/贡献用户是否为「有效获客对象」在业务上未验证；先观望不会损失能力，移植也不会带来立刻可用的闭环。

## 一 功能边界

### 1.1 能力清单（两半：WS 事件流 + HTTP 查询）

上游这套能力由**两条独立的取数通道**组成，边界不同：

| 通道 | 入口 | 数据来源 | 是否新增网络请求 |
|---|---|---|---|
| **A. WS 事件流** | `dy_live/pk.py` + `dy_live/server.py` 的 `on_pk_event` | 复用在用的直播 WS 长连接，服务端推送 | **否**（同一 socket，只是多解几种 method） |
| **B. HTTP 查询** | `dy_apis/douyin_api.py` 的 5 个方法 | `live.douyin.com` 的 REST 接口 | **是**（每次调用 1~6 个 GET） |

#### A. WS 事件流能拿到的（被动，零新增请求）

`dy_live/pk.py:12-17` 定义 4 类 PK 消息，`decode_pk_message` 归一化为结构化事件：

| method | 事件 type | 拿到什么 | 证据 |
|---|---|---|---|
| `WebcastLinkMicBattleMethod` | `start` / `status` | `battle_id`、`channel_id`、`start_time_ms`、`duration`、`battle_status` | `pk.py:69-82` |
| `WebcastLinkMicMethod`（仅 `message_type==202`） | `scores` | 双方**主播**的比分：`anchor_id` / `score` / `score_blur_text` / `score_relative_text` / `battle_rank` | `pk.py:58-62` |
| `WebcastLinkMicArmiesMethod` | `armies` | **单侧贡献快照**（`anchor_id` → 用户 uid/nickname/score，按分数排序）；`unassigned_armies` | `pk.py:63-68` |
| `WebcastLinkMicBattleFinishMethod` | `finish` | 结算比分 + 双方 `rank_list`（贡献榜）+ `end_reason` | `pk.py:75-80` |

`PKMessageHandler`（`pk.py:86-140`）额外提供：去重（`_remember`，512/128 上限）、`active` 局号跟踪、`context_battle_id` 推断。

#### B. HTTP 查询能拿到的

| 方法（上游 `douyin_api.py`） | 端点 | 拿到什么 |
|---|---|---|
| `get_live_room_enter` `:1672-1678` | `/webcast/room/web/enter/` | 房间资料：真实 `room_id`、`owner`（含主播 `nickname`）、`linker_map`（PK 频道 id） |
| `get_live_linkmic_list` `:1681-1691` | `/webcast/linkmic/list/` | 连麦快照：`battle_stats`（`battle_settings` + `user_infos` + `battle_scores` + `battle_armies`） |
| `get_live_pk_contribution_rank` `:1694-1705` | `/webcast/linkmic/battle/ranklist_armies/` | **本频道当前 PK 的单侧贡献榜**（上游 JSON 原样返回） |
| `get_live_pk_context` `:1708-1761` | 组合前两个 | PK 上下文：`battle_id` / `channel_id` / `finished` / `anchors`（双主播 uid+nickname+room_id） |
| `get_live_pk_rank` `:1764-1796` | 组合 | `state`（ok / not_in_pk / context_changed / api_error）、`context`、`context_after`、`ranks`（主播 uid → 原始响应） |

### 1.2 明确**拿不到**的 / 有坑的（务必写进设计契约）

1. **`battle_id` 在 WS 侧可能是推断值，不是服务端确认** —— 上游自己写明：
   > `dy_live/pk.py:3-5`：`Armies pushes are partial ranking snapshots, not the HTTP full contribution list. They do not carry a battle ID: context_battle_id is only an inference from a live, time-compatible lifecycle/score event, never a confirmed ID.`
   - `armies` 事件的 `battle_id` 恒为 `None`（`pk.py:56`），只有 `context_battle_id`（`pk.py:138`）是**按 `create_time` 与当前 `active` 局时间兼容性推断**的。消费方**不得**把它当服务端确认的局号归档。
2. **`armies` 是「贡献前三」快照，不是完整榜单** —— 上游 CLI 自述 `pk.py:158`「贡献前三（推送快照，非完整榜单）」；`is_complete` 恒 `False`（`pk.py:64`）。
3. **`score` 可能为 0 且无意义** —— `get_live_pk_contribution_rank` docstring `:1697-1699`：`users[].score=0 可能是接口未提供有效分数，不代表用户没有贡献`。
4. **`rank_list_v2` 未解析** —— `PK.proto:33-34` 注明「Other modes may use this schema; not verified」；`pk.py:68` 只透出 `has_unsupported_rank_list_v2` 布尔，**不能据此判断「无人贡献」**（`pk.py:165-166`）。
5. **贡献榜用户没有 sec_uid** —— `PK.proto:23-27` 的 `UserArmy` 只有 `user_id` / `score` / `nickname`，**没有 sec_uid**。而本项目私信派发主键是数字 uid（`core/live_hook.py:419-426` 用 `ChatMessage.user.id`），**uid 可用，但只有 uid 没有 sec_uid**（与弹幕消息相比缺一个字段）。
6. **`get_live_pk_rank` 一次调用会打 6 个请求**（`test_live_pk_api.py:57-73` 断言 `request.call_count == 6`：room → snapshot → 2×rank → room → snapshot），且**结果不是服务端原子快照**（`douyin_api.py:1768-1770`「查询前后局号一致，仍非服务端原子快照」）。
7. **HTTP 侧含真实昵称**：`get_live_pk_context` 会读对手主播的 `nick_name`（`douyin_api.py:1751-1754`）——**这是主动 HTTP 读昵称**（见第三节）。

### 2.2 依赖评估：`PK_pb2.py` 需要 protobuf 编译吗？proto 能直接用吗？

**实测结论（已本机验证）**：**不需要 `protoc`/`grpcio-tools`，不需要新增任何第三方依赖。**

- `static/PK_pb2.py:2-4` 头部自述由 protobuf 4.25.1 生成，但它是**自包含的**——`DESCRIPTOR` 以序列化字节内嵌（`PK_pb2.py:17`），运行期经 `_builder.BuildMessageAndEnumDescriptors` + `_descriptor_pool.Default().AddSerializedFile(...)` 动态构建，**不读取 `.proto` 文件**。
- 本项目 `requirements.txt:17` 已有 `protobuf>=5.0.0`，本机实测 `google.protobuf.__version__ == 6.33.5`；把上游 `PK_pb2.py` 单独拷到临时目录并 `from static import PK_pb2` → **serialize/parse 往返成功，4 个消息类均可实例化**（实测输出：`serialize/parse roundtrip OK` + `['LinkMicArmies','LinkMicBattle','LinkMicBattleFinish','LinkMicMethod']`）。
- **结论**：`PK.proto` 只是**可读的设计文档/溯源素材**（86 行、带字段号注释），拷进来便于审计，但**代码不依赖它**；`PK_pb2.py` 直接可用，零编译步骤、零新依赖。

### 2.3 与本项目现有直播模块的关系：重叠 / 互补 / 冲突

#### （a）与 `core/live_hook.py` —— **互补 + 一个必须处理的冲突**

- **互补**：`LiveChatHook` 继承 `dy_live.server.DouyinLive` 并**完整覆盖** `on_message`（`core/live_hook.py:388`），上游对基类 `on_message` 的改动（PK 分支，`server.py:72-84`）**不会自动进入本项目路径**。要在本项目拿到 PK 事件，**必须把 PK 分支写进 `core/live_hook.py:on_message`**（而不是改 `dy_live/server.py` 了事）。
- **冲突（必须一并修）**：本项目 `on_message` 的 `origin_bytes = gzip.decompress(frame.payload)` 是**无条件解压**（`core/live_hook.py:392`、`dy_live/server.py:66`），而上游 09-19 恰好把这里改成了**「先判 `hb`/`ack`/空 payload，再按 `\x1f\x8b` 魔数决定是否解压」**（`server.py:54-59`）：
  > `if frame.payloadType in ('hb', 'ack') or not frame.payload: return` / `if origin_bytes.startswith(b'\x1f\x8b'): origin_bytes = gzip.decompress(...)`
  - 本项目的 HK 帧是 `\x1f\x8b` 开头所以当前没炸，但**上游这次改动本身就是「心跳/未压缩帧会抛异常」的防御**。若移植 PK 能力（PK 事件可能走未压缩帧），**这条守卫必须一起移植**，否则会出现「整帧异常 → `[LIVE-008]` 连续 5 次 → 触发重扫」的连锁（`core/live_hook.py:495-520`）。**这是移植 PK 时最容易被忽略、也最容易踩的一个坑。**

#### （b）与 `dy_apis/client_live.py` —— **有重叠但不冲突，可复用签名底座**

- 现有 `get_rank_list`（`client_live.py:282-340`）是**直播间常规贡献榜**（`/webcast/ranklist/audience/`），**不是 PK 榜**；上游 `get_live_pk_contribution_rank` 打的是 `/webcast/linkmic/battle/ranklist_armies/` —— **两个不同接口**，不冲突（上游甚至在 `test_live_rank_api.py` 里把 `get_rank_list` 改成了 `get_live_contribution_rank` 的别名，那是上游内部重构，与本项目无关）。
- **可复用的底座齐全**：`client_live.py:37` 已有 `LIVE_HOST = 'live.douyin.com'`；`Params.with_a_bogus(host=LIVE_HOST)`（`builder/params.py:50`）签名路径与上游 `_get_live_web:1652` 完全同构；`HeaderBuilder` / `get_profile` / `auth.msToken` / `auth.cookie` 全部现成。**新增 5 个方法主要是机械照搬参数顺序**，无需新建签名基础设施。
- **一处已知本地差异**：上游 `_get_live_web:1663-1666` 有 `if hasattr(auth, 'request')` 分支（带 cookie 轮转吸收），本项目 `builder/auth.py` **只有 `cookie_str`、没有 `request` 方法**（grep `auth.request(` 于 `dy_apis/` 为空）。照搬上游时这一分支在本项目恒走 `else`（`requests.get(..., cookies=auth.cookie)`），**属无害但会静默走另一条路**，需在移植时显式确认（上游 `get_live_info` 也有同款分支，本项目 `client_live.py:84` 已删掉该分支）。

#### （c）与 `api/live.py` / `api/linkmic.py` —— **不冲突**

- `api/linkmic.py` 是**观众侧连麦**（`/webcast/linkmic_audience/*`，`client_live.py:394-559`），与**主播侧 PK** 是两条完全不同的链路，无重叠。
- `api/live.py` 的 `/ws` 是**空壳**（`:87-102` 三个 TODO），前端仍轮询；PK 事件若要上屏得先补这条 WS 推送链，属**额外成本**（不是 PK 本身带来的）。

## 三 风控风险评估

### 3.1 新增的网络请求盘点

| 触发路径 | 请求数 | 频率 |
|---|---|---|
| **WS 事件流（通道 A）** | **0**（复用现有 WS 长连接） | 服务端推，被动 |
| `get_live_room_enter` | 1 GET | 单次 |
| `get_live_linkmic_list` | 1 GET | 单次 |
| `get_live_pk_contribution_rank` | 1 GET / 侧 | 单次 |
| `get_live_pk_context` | 2 GET | 单次 |
| `get_live_pk_rank(side='current')` | 4 GET | 单次 |
| `get_live_pk_rank(side='both')` | **6 GET** | 单次 |

- 上游明确**不做自动轮询**：`douyin_api.py:1766`「side 为 current 或 both，**不自动轮询**」。
- **这些请求全部带账号凭证**（`auth.msToken` + `auth.cookie`，`_get_live_web:1651-1666`），与「复用凭证去查/发」是同一条风控面 —— **但注意判据**：本项目自己**已经在用同一账号凭证直调直播接口**（`client_live.py:335` 的 `get_rank_list` / `linkmicApply` / `sendMsgInRoom`），所以「带凭证打直播域 GET」本身**不是新增红线**，红线的关键是**「加频」与「用途」**。

### 3.2 是否触碰「昵称禁主动批量查」红线？

**判定：不属于「批量查」，但属于「主动 HTTP 读昵称」，擦边 —— 需用户拍板。**

- **不属于批量查**：项目红线（`dyautodm-dev-guards` §九）禁止的是「后端用 cookie **批量** `get_user_info` 查昵称」。PK 能力**没有任何按列表批量查昵称的动作**：贡献榜各用户的昵称是 WS 帧里被动下发的（`PK.proto:26` `UserArmy.nickname`）；HTTP 侧只有 `get_live_pk_context` 读**对手主播**（≤ 1 个对手 + battle 内 `user_infos`）的 `nick_name`（`douyin_api.py:1751-1754`），**量级是 1~2 个 PK 参与方，不是名单**。
- **但确实是主动 HTTP 读昵称**：对手主播昵称走的是 REST 响应体，不是 BCC 被动 hook。项目铁律「昵称唯一来源是 BCC 被动 hook / 读 IndexedDB」在字面上会被这条路径违反（尽管量级极小、且只读 PK 对手而非客户名单）。
- **建议**：若要落地，**只启用 WS 侧的 `armies`（nickname 由服务端推送，零主动请求），关闭 `get_live_pk_context` 对 `nick_name` 的读取**（或只取 uid、昵称留空），把「主动读昵称」这一条彻底规避。这样 PK 能力就 100% 落在被动面。

### 3.3 是否触碰「不新增主动请求 / 低频 WS」红线？

| 红线 | 判定 |
|---|---|
| **直播引擎是低频 WS 长连接，禁止高频轮询** | **通道 A 完全合规**（零新增请求）；**通道 B 若被定时器调用则违规** —— 上游设计为单次调用，落地时必须**禁止把它挂进任何 loop / `refetchInterval`**（本项目前端已有 5s 轮询的教训：`api/live.py` 前端 `refetchInterval: 5000`）。 |
| **不新增主动请求** | 通道 B 会新增，**擦边**。判据：本项目并非禁止一切主动请求（`linkmicApply`/`diggLiveRoom` 都是主动的），禁止的是**高频与无业务理由的主动请求**。PK 榜若只由用户显式点击触发（用户动作豁免，见 skill §〇·丁 规则 1），可接受；若后台自动跑，**违规**。 |
| **禁止无实机证据的静态改动** | 移植本身**无法先验**：这 5 个 HTTP 接口的真实可用性、是否被登录态/风控拦截，上游只在 mock 测试里验证过（`test_live_pk_api.py` 全是 `patch`），**没有上游的真机返回体**。落地前必须有一次真机取证。 |
| **单 profile / BCC 单例** | 这套 HTTP 能力**不经 BCC**（直连接口），不触碰浏览器锁；但 `get_live_pk_rank` 6 连发与 BCC 无关，**不会抢 profile**。 |

### 3.4 风控风险综合评级

| 项 | 评级 | 说明 |
|---|---|---|
| 通道 A（WS PK 事件） | 🟢 **低** | 零新增请求；唯一风险是帧解析异常（已有 `[LIVE-008]` 守卫） |
| 通道 B（HTTP PK 榜） | 🟠 **中** | 新增主动请求 + 主动读昵称；单次调用风险可控，**一旦被轮询即升级为红线** |
| 凭证面 | 🟡 **中性** | 与现有直播接口同一凭证、同一风控面，不额外放大；但 6 连发会稀释发送闸门之外的账号行为画像 |

**一句话**：WS 那半可以放心做；HTTP 那半要么只由用户显式点击触发，要么不做。

## 四 产品决策建议

### 4.1 本项目当前业务是否需要 PK 榜数据？

**当前不需要。** 本项目业务是「直播弹幕监听 → 命中规则 → 私信触达」（`core/live_hook.py` 把 `WebcastChatMessage` 推给 `dispatch.submit`）。这条链路的**目标客户 = 在公屏发过言的人**，uid/nickname/sec_uid 三件套齐备（`live_hook.py:419-426`），**已经能直发**，不需要任何额外查询。

PK 榜提供的是**另一类人群**：
- `scores` 事件 → 双方主播（不是客户）；
- `armies` / `finish.rank_list` → **PK 期间给主播打赏/贡献的用户**（可能是潜在客户，但**未在公屏发言**）；
- `get_live_pk_contribution_rank` → 同上，且**没有 sec_uid**（只有 uid + nickname）。

### 4.2 不做会损失什么？

- **损失的唯一场景**：「想对 PK 贡献榜/打赏用户定向发私信」——这是一个**可能更高质量**的获客面（愿意为直播间花钱的用户）。
- 除此之外**零损失**：弹幕私信主链路、连麦、常规贡献榜、礼物/进房/点赞/关注流全部不受影响。

### 4.3 做了能增强什么？

- **新增一个人群池**：PK 贡献用户（有 uid → 可走 `/send_by_uid`，`client_live.py` 同族已有该通路）。
- **直播监听页可上新数据**：PK 进度条、双方比分、贡献前三 —— 属**展示层增强**，对「私信转化」无直接贡献。
- **成本极低的副产品**：WS 侧的 PK 事件几乎免费（复用现有连接），可作为「直播信息流更丰富」的顺手收益。

### 4.4 推荐与理由

> ## 🟡 推荐：观望（不移植），但落一份「素材存档 + 触发条件」

| 方案 | 结论 | 触发条件 |
|---|---|---|
| **做（WS 侧）** | 可选，非必须 | 若产品需要「PK 榜上屏」做展示，可只移植通道 A（零风险） |
| **做（HTTP 侧）** | ❌ 暂不做 | 仅当出现**明确的「PK 贡献用户定向私信」业务需求**，且用户拍板接受「主动请求 + 主动读昵称」的擦边 |
| **观望** | ✅ **推荐** | 当前主业（弹幕→私信）不依赖 PK 数据；先存素材，零成本留后路 |
| **前置动作（必做）** | ✅ | ① 把 `PK.proto` + `PK_pb2.py` + `pk.py` 存入上游情报库（只读素材，不接入 backend）；② 把本次评估的「gzip 守卫」「battle_id 是推断值」「score=0 无意义」「贡献榜无 sec_uid」四条写进对应知识库文档，避免将来移植时重踩 |

**理由**：
1. **不做不会损失核心能力**，做了也不会立刻产生闭环收益 —— 决策权应交业务（见「需拍板问题」）。
2. **上游这套是为「自助 CLI 工具」设计的**（`print_pk_event` 直接 print，`on_pk_event` 只是可选回调），移植到本项目需要改造为「logger + 事件队列 + 前端消费 + 错误码六段契约」，集成成本大于算法成本。
3. **风控上 WS 侧零成本、HTTP 侧擦边**，正确做法是**分期**：先只纳素材、不落联网代码；真要上，先上零风险的 WS 侧。
