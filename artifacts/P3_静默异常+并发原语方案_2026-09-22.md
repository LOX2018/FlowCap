#### A 类：必须升 `logger.warning` + 计数（13 处）

6. `daemon/recv_daemon.py:96` — 版本探测第三步失败

**改造模板**：
```python

    logger.warning(f"[{TAG}] ...失败: {traceback.format_exc()}")
    __metrics_silent_errors.labels(module=__name__, site="...").inc()
```

#### B 类：保持 pass 但加计数器（约 30 处）

判据：**非核心路径，不阻塞业务流程，但需知道发生率**。

典型场景：
- `database.py:249-294` schema 迁移 ALTER TABLE（列已存在属正常，但其他异常不可见）
- `vbrowser_window.py:222,242` CDP session detach 清理（cleanup 路径）
- `daemon/browser_daemon.py:3062` shutdown 关闭浏览器（shutdown 路径）
- `main.py:43` stdout reconfigure（非核心）
- `services/ai_reply.py` 各空异常（AI 回复非阻塞降级）
- `utils/fingerprint.py` 各空异常（指纹采集非核心）

**推荐**：加 `__metrics_silent_errors` Prometheus counter + `traceback.format_exc()` debug 日志
```python
except Exception:
    _silent_errors_inc(__name__, "db_schema_migrate")
    if logger.isEnabledFor(logging.DEBUG):
        logger.debug(f"...: {traceback.format_exc()}")
```

#### C 类：保留现状（约 300 处）

判据：**for 循环内单元素解析失败继续处理下一个**，如：
- `auto_dm/im_protobuf.py` protobuf 消息循环内单条解析失败 → `continue`
- `auto_dm/origin_image_resolver.py` 图片解析循环单元素 → `continue`
- `dy_apis/client_user.py` 用户列表遍历单用户 → `continue`
- `utils/tls_policy.py` TLS 策略组合尝试
- `core/sender.py` 消息发送重试

特点：体量大但每个的上下文清晰；单条失败不影响整体；改成 log 会淹没日志。

**推荐**：仅对同一个循环连续失败 > N 次时才打出第一条 warning（rate-limited logging）。

### 1.5 裸 `except:` 特殊处置

### 2.4 原语冲突风险评估

#### 高风险（未保护的可变共享状态）

| # | 文件 | 变量 | 风险 |
|---|---|---|---|
| 1 | `services/probe.py` | `_STATE_RANK` | 模块级 dict，用于探活状态的等级打分。实际使用模式是**读后不回写**（`_STATE_RANK.get(r.get(...))`），但无 `threading.Lock` 保护。改良惰性只读，实测风险极低。 |
| 2 | `daemon/_verify_lease_lock.py` | `_old_lock` / `_old_lock_meta` / `_new_state` | 测试验证脚本，不属生产路径。忽略。 |

#### 中风险（跨模块锁交互）

不同模块入口持有不同锁类型，当模块 A（持 RLock）调用模块 B（也持 RLock）时，若 B 的回调再调回 A，存在**递归锁依赖**。典型路径：

```
browser_daemon（_lease_lock, RLock）
  → uid_probe（_registry_lock, Lock + _locks[x], Lock）
    → database（_lock, RLock）
      → 回调 browser_daemon
```

目前各模块都用 RLock（可重入），**递归死锁概率低**。但如果 `uid_probe._registry_lock` 是普通 `Lock`，而 `browser_daemon._lease_lock` 是 `RLock`，`uid_probe` 回调 `browser_daemon` 时若 `browser_daemon` 已经持锁再碰 `uid_probe._registry_lock` → **交叉死锁**。

#### 低风险（读多写少的配置表）

- `browser_gate.py:_PRIO_BY_PURPOSE` / `_SKIP_COOLDOWN_BY_PURPOSE` / `_TTL_LIMIT` — 初始化时填充，之后只读
- `dm_dispatch.py:_PRIO_BY_SOURCE` — 同模式（只读表）
- `ai_reply.py:_DEFAULT_CONFIG` — 只读配置表

### 2.5 统一方案建议

#### 规则 1：按访问模式选择原语

| 访问模式 | 推荐原语 | 禁忌 |
|---|---|---|
| 单函数内保护共享变量 | `threading.Lock` | — |
| 保护的方法调用链（A.foo → B.bar → A.baz） | `threading.RLock` | `Lock` 会产生死锁 |
| 异步上下文（`async def` 内） | `asyncio.Lock` | `threading.Lock` 会阻塞事件循环 |
| 资源池/限流 | `asyncio.Semaphore` | 不重复造轮子 |

#### 规则 2：模块级变量必须跟锁

每个 `_xxx = {}` 级别的模块变量必须在其所在模块有一个配对锁。远距离使用者（import 后直接 .update/clear）必须在同一锁保护下进行。

#### 规则 3：锁命名规约

```python
# 保护一组资源的锁
_xxx_LOCK: threading.RLock

# 保护胡字典的锁
_STATE: dict
_STATE_LOCK: threading.Lock  # 或 RLock
```

#### 规则 4：跨模块调用禁止同时持锁

如果 A 持有 `a_lock` 时调用了 `B.do_sth()`，B 必须在其文档/类型标注中声明该函数是否会尝试获取任何锁。无法声明时，A 应在调用 B 前释放 `a_lock`。
