## 三、读取端改动（`backend/api/accounts.py`）

### 3.1 新增统一判定函数 `_resolve_login_channel()`

优先级：**配置中心 `general.login_channel` → 环境变量 `DY_LOGIN_CHANNEL` → 旧环境变量 `DY_LOGIN_QR_BACKEND` → 兜底 `bridge`**。

### 3.2 一个必须说明的坑：为什么①**不用** `app_config.get("general", "login_channel")`

`get()` 的回落链是「存储 → 环境变量 → schema 默认」（见 `app_config.py:196-229`），而本字段的 schema 默认就是 `"bridge"` ⇒ **只要用户没在配置中心显式选过，`get()` 永远返回一个非空值 bridge 并短路**，第③步的旧环境变量就被永久遮蔽。

那等于**静默废弃既有环境变量接线**：用户设了 `DY_LOGIN_QR_BACKEND=api` 却仍走桥，且无任何告警 —— 直接违反「不破坏现有行为」。

故刻意改读 **`ac.section_stored("general")`**（只返回用户**显式保存过**的值，不含默认/环境变量；`app_config.py:99-105`），显式值为空才继续往下回落。

### 3.3 接线点（`_rpa_scan_login`）

原先第 254 行 `_backend = _os.environ.get("DY_LOGIN_QR_BACKEND", ...)` 替换为：

```python
try:
    _channel = _resolve_login_channel()
except Exception as _e_ch:
    logger.warning(f"[ACC-049] [scan] 账号 {name} 通道判定失败，回落接口桥: {_e_ch}")
    _channel = "bridge"

if _channel == "manual":
    logger.info(f"[scan] 账号 {name} 配置为「有头浏览器手动」通道，跳过接口桥/API，直接回落手动")
    return False

_backend = _channel      # 保持与既有下游代码/门禁断言兼容的变量名
if _backend == "api":
    ...  # 下游一行未改
```

- 配置中心不可用时（DB 未就绪等）**不阻断扫码**，继续回落到环境变量。
- 非法值（如 `quantum`）**忽略并继续回落**，不静默改语义（打 `[ACC-048]` 告警）。
- `_backend` 变量名刻意保留 ⇒ 既有门禁 `test_login_bridge_default_gate.py::test_a1` 的 `'_backend == "api"'` 断言**仍然成立**（已实测通过）。
- 新增错误码 `ACC-047/048/049`，全仓 grep 确认无冲突。

## 六、前端如何出现该选项（无需改前端）

**前提：该页面是 schema 驱动自动渲染。**

`frontend/src/components/settings/settings-page.tsx` 第 124 行：

```tsx
<UnifiedConfigSection {...props} onlySections={["general"]} />
```

链路：
1. 前端启动时拉后端 schema 接口（`app_config.schema()`，`app_config.py:286-307`）。
2. `UnifiedConfigSection` 按 `onlySections` 筛出 `general` 段，遍历 `fields` 渲染控件。
3. **`type=select` ⇒ 渲染下拉框**，选项直接取 `options` 的 `value`/`label`，初值取 `default`，鼠标悬停提示取 `hint`。

⇒ **后端加了字段，前端「配置中心 → 通用配置」就自动多出一个「凭证更新通道（扫码/短信）」下拉框**，三个选项即上面 schema 里那三条 label，`apply=hot` 也会由 UI 标出「保存后立即生效」。前端零改动。

## 七、风险与遗留

1. **`api` 选项不可用是既定事实，不是 bug**：2026-10-01 三轮实测，纯协议出码仅 3.5s，但二维码约 65 秒即被服务端判 expired（正常 5 分钟的 1/5，成因未确定）。label 已如实标注「无法完成登录」。**选它不会获得可用登录**，仅供对照实验 —— 若不想把实验通道暴露给最终用户，可从 `options` 里摘掉 `api`（读取端无需改）。
2. **`manual` 的实现语义**：当前是「`_rpa_scan_login` 直接返回 False」，由上层 `_do_scan` 已有的 else 分支走 `enrich_auth(force=True)` 有头兜底 —— **复用了既有兜底路径，未新建手动链路**。副作用：`st["path"]` 会先被置 `"rpa"` 再被改为 `"manual"`（既有行为，非本次引入），UI 上会短暂显示走的是 RPA。
3. **`hint` 文案较长**：下拉框提示较长，若前端 hint 区排版偏窄可能换行难看 —— 纯观感，不影响功能，需要的话可以精简。
4. **短信通道**：`_do_sms_scan` 未接入本开关。需求标题写了「扫码/短信」，但当前三个选项语义都是扫码/有头登录路径；如果短信验证码那条独立链路也要纳管，需要另加 option（`sms`）——**建议作为后续任务单独确认**，本次未做，避免超出改动面。
5. **并发改动提醒**：`backend/auto_dm/login_remote.py` 与 `backend/api/accounts.py` 的 `_do_scan`/`_do_sms_scan` 区段存在另一会话的进行中改动（profile 释放、短信落盘增强等）。本次在 `accounts.py` 的编辑与它们不重叠，但**提交时建议先 diff 确认不互相覆盖**。
