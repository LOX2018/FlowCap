## 1. F4 定时任务中心（新基建 · 最高风险）—— 8 条

### [P0] TS-1 · 内置 handler 未注册 + `start()` 无调用点 ⇒ F4 实为**空壳**

**证据**（✅实测复现）：
```
$ grep -rn "register_builtin_handlers|task_scheduler" --include="*.py" .
(空 —— 除模块自身与测试外，全仓 0 调用点)

main.py:580  from services import kb_maintain
main.py:581  kb_maintain.start_scheduler(...)      ← 只启动了 kb_maintain
```
**后果**：`_run_one` 走 `fn = _handlers.get(task.kind)` ⇒ 永远 `None` ⇒ 返回
「任务类型 X 无注册执行体」。即**F4 从未真正上线**，前端 `SchedulerSection`
呈现的是「手动可唤醒的空壳」。

**为何 P0**：这属于「能力在位但不可达」的**架构级" incomplete wiring**」——
比功能缺失更危险，因为它给出「功能已交付」的假象（前端 UI 完整、门禁全绿）。

---

### [P1] TS-2 · `_gate_for_send` 元组解包恒异常 ⇒ 三重闸门 100% 恒拒

**证据**（✅实测复现）：
```
$ python -c "..._gate_for_send(Task(kind='auto_dm_send', account='agA'))..."
结果 ok = False
reason  = 闸门检查异常，拒绝外发（fail-closed）: ValueError: too many values to unpack (expected 2, got 3)
```
**根因**（`task_scheduler.py:249`）：
```python
ok, why = quota.can_send()      # ← can_send 返回 3 元组 (ok, reason, 还需等待秒数)
```
而 `can_stranger_first()` 返回 **2 元组**（勿一刀切改）。

**双重危害**：
1. **当前**：三重闸门形同虚设（永远走不到），自动外发 100% 失败；
2. **修复时**：一旦有人把解包改成 3 元组「修好」它，TS-3（投递验证被击穿）
   **立即升级为真·风控漏洞** —— 自动外发将带着「假验证通过」真发出去。
   ⇒ **必须与 TS-3 同批修复**。

---

### [P1] TS-3 · 投递验证被击穿 —— `accepted`（入池）冒充 `delivery_verified`

**证据**（✅实测复现，源码 `task_scheduler.py:500-516`）：
```python
res = disp.submit_by_uid(task.account, uid, text, "scheduler")
ok = bool(getattr(res, "ok", False) or getattr(res, "accepted", False))
return {"ok": ok, "delivery_verified": ok,          # ← 入池即认「已验证」
        "detail": str(getattr(res, "reason", "") or "")}   # ← SubmitResult 无 .reason ⇒ 恒空
```
**全程未调用 `services.delivery_verify`**。

**违反**：用户铁律「**无回执不认成功**」（M-5）+ `requirement` 里明确的投递硬验证。
**后果**：只要 `submit_by_uid` 入池成功（尚未真发出、可能被风控静默丢弃），
任务就上报 `delivery_verified=True` —— **正是用户最痛恨的「假成功」家族**。

---

### [P1] TS-4 · `_tick` 重入保护竞态：早退 `return` 触发 `finally._schedule()`

**证据**（✅读码确证，`task_scheduler.py:317-322` + `357-360`）：
```python
try:
    with _lock:
        if _running:
            return              # ← 早退在 try 内
        _running = True
    ...
finally:
    with _lock:
        _running = False        # ← 被早退路径执行
    _schedule()                 # ← 又排一个 Timer
```
**后果**：本应「上一轮还在跑 ⇒ 安静早退」，实际却**清掉标志 + 再排一次定时器**
⇒ ① Timer **累积**（每轮多一个）；② `_running=False` 让后续 tick 又能进入
⇒ **同任务并发执行**（对自动外发 = 重复发私信）。

---

### [P1] TS-5 · `run_task_now` 对同一任务零锁

**证据**（子代理实测 4 路并发 → 同任务并发 4 次；本人已确认其调用链无锁）：
手动触发接口与 `_tick` **不互斥** ⇒ 前端连点「立即执行」即并发外发。

### [P2] TS-6 · 零持久化 —— 进程重启任务全丢

任务定义与状态**全部存内存字典**（`_tasks`），无 SQLite 落库 ⇒ 重启即全丢。
（对照：`live_rooms` / `crawl_policies` 都落了 kv。）

### [P2] TS-7 · 超时「已放弃本轮」但线程不可杀 ⇒ 僵尸线程

`threading` 无法强杀 ⇒ 超时后线程仍存活，持续占用资源并**可能在外发中途**。

### [P2] TS-8 · `Task.__init__(enabled=True)` —— 违反 D1「逐任务默认休眠」

**证据**（✅实测复现）：
```
auto_dm_send   enabled=True  needs_send=True   ← 新建即「已启用 + 会外发」
```
**风险链**：用户按 ADR-018 设 `DY_TASK_SCHEDULER_ENABLED=1`（**正常用法**）
→ 新建 `auto_dm_send` 任务不传 `enabled` → 立即 `enabled=True` → 到点自动外发。
ADR-018 D1 原文要求「**默认休眠 enabled=False，你要用再开**」，任务粒度被破坏。

---

### [P0·元发现] TS-9 · 守护 F4 的门禁 **7/7 全绿，但全部是源码字符串匹配**（假绿）

**证据**（✅实测复现）：
```
$ python test_task_scheduler_gates.py
  [PASS] G1~G7 全部通过
```
而同一份代码里：闸门实测 100% ValueError（TS-2）、投递验证被击穿（TS-3）。

**根因**：`test_task_scheduler_gates.py` 的判据全部形如
```python
s = _src(); ok = "can_send()" in s          # G5
ok = "if needs_send and REQUIRE_DELIVERY_VERIFY:" in s   # G6 ← 恰是缺陷代码的字符串
```
**最讽刺处**：G6 的 docstring（L90-93）自称「初版用常量名不行，已改为锚定执行分支」
—— 但它锚定的**仍是字符串**，而非**行为**。它匹配到了那段代码的**字面存在**，
而缺陷恰在于那段代码的**返回值语义错误**。

**⇒ 这是本项目「声明式规则=空架子」教训的第 N 次复现**：门禁必须锚定**行为**
（真调用、真断言返回值），不能锚定**源码文本的存在性**。
