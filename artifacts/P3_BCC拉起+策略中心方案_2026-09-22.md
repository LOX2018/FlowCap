## 一、BCC 拉起决策点（6 处收敛）

### 1.1 当前 BCC 拉起路径全景

```

──────           ───────        ───────       ───────       ────────       ───────
main.py          main.py        api/accts     各调用方      browser_daemon  api/messages
_auto_start      _prealign      /ensure-bcc   ensure_bcc/  _launch →       bcc_url
  ↓                ↓              ↓             ↓             ↓              ↓
```

### 1.3 收敛方案：全部收敛到 `browser_gate.ensure_browser`

#### 收敛原则

1. **`browser_gate.ensure_browser`** 作为**唯一的「拉起 BCC」门禁**，所有需要**确保 BCC 已运行**的路径都走它
2. 用户显式操作（「启动凭证守护」「打开指纹浏览器」）仍可走 `ensure_bcc`（绕过 gate 的租约竞争），但把 BCC 拉起的底层逻辑统一到 `daemon_launcher.ensure_daemons_for` → `acct_core.ensure_bcc` 这个 canonical 路径
3. 核心改动：`main.py` 的 `_auto_start_daemons` 和 `_prealign_daemons` 从直 spawn 改为走 `daemon_launcher.ensure_daemons_for`（已部分完成）

#### 6 处收敛方案

| # | 当前位置 | 当前行为 | 收敛动作 | 改动量 |
|---|---------|---------|---------|-------|
| ① | `main.py:293` `_spawn_sidecar` 直拉 BCC | 绕过所有保护（无冷静期、无防重复） | 改为 `ensure_daemons_for(names[0], wait=True, skip_cooldown=True)` | 小——3 行 |
| ② | `main.py:199` `ensure_daemons_for` 预对齐 | 已走 `daemon_launcher` → `ensure_bcc`，但未过 `browser_gate` | 可不改（gate 面向 runtime 租约，启动预对齐无须租约） | 0 行 |
| ③ | `daemon_launcher.py:186` `ensure_bcc` | de facto 拉起入口，gate 也走到这里 | **不做改动**——它是底层执行者，不是决策者 | 0 行 |
| ④ | `api/accounts.py:581` `ensure-bcc` 端点 | 用户显式，直接调 `ensure_bcc` | 不改——用户操作不应被 gate 守卫 | 0 行 |
| ⑤ | `api/accounts.py:692` open_fingerprint_browser | 同④ | 不改——扫码后回拉 BCC | 0 行 |
| ⑥ | `api/messages.py:110` gate 回退 | gate 失败时降级调 `ensure_bcc` | 不改——降级路径合理 | 0 行 |

#### 真正需要改的

真正的收敛动作实际只有 **① 一处**：消除 `main.py:293` 直 `_spawn_sidecar` 绕过 `ensure_bcc` 的结构性问题。其余 5 处要么已经走到了 canonical 路径（②③），要么因为语义差异（用户显式/降级回退）不应统一到 gate。

其余调用 `ensure_daemons_for` 的 10+ 个点（`api/accounts.py:214`、`api/messages.py:1608`、`auto_dm/accounts.py:659/1548/1657`）已经都在走 `daemon_launcher → ensure_bcc` 路径，不需要改动。

### 2.3 核心发现

1. **语义群高度离散**：37 个不同 timeout 值，没有单一值占主导
2. **单位不一致**：多数是秒（float），但 Playwright 相关用毫秒（30000=30s, 20000=20s, 25000=25s）
3. **top 3 已占 21%**：`15`（18次）、`0.3`（13次）、`60`（12次）——这些都是 BCC HTTP 通信和端口探活的固定值
4. **大量毫秒值**：30000(30s)×8、20000(20s)×6、25000(25s)×5、90000(90s)×2、45000(45s)×2 等，来自 Playwright/Puppeteer

### 2.4 最小策略中心设计

#### 配置项提案（6 项覆盖 ~80% 场景）

| 配置键 | 默认值 | 覆盖位置数 | 覆盖位置 |
|--------|-------|-----------|---------|
| `timeout.bcc_http` | 15 | ~18 | `_bcc_post` 调用、BCC HTTP 请求 |
| `timeout.port_probe` | 0.3 | ~13 | socket 端口探测 |
| `timeout.http_request` | 30 | ~12+11=23 | `requests.post`、HTTP GET/POST 一般请求 |
| `timeout.bcc_boot` | 60 | ~12 | BCC 拉起等待 `ensure_bcc` 的 `wait_ready` |
| `timeout.page_goto_ms` | 30000 | ~8+6+5=19 | Playwright `page.goto`（毫秒） |
| `timeout.scan_login` | 300 | ~4 | 扫码登录等待 |

这 **6 项**覆盖约 **89 处**（占 204 的 43.6%）。要覆盖 80%（~163 处）需要更多配置：

#### 扩展版（12 项覆盖 ~75%）

在前 6 项基础上增加：

| 配置键 | 默认值 | 新增覆盖数 |
|--------|-------|-----------|
| `timeout.http_long` | 120 | +4 |

### 2.5 合理建议

鉴于离散度高，**不推荐**做超大型策略中心。建议按「3 层级分类」处理：

#### 层级 A：系统默认值（集中定义 3 个）

```python
# services/timeout_policy.py
class TimeoutDefaults:
    BCC_HTTP_REQ   = 15.0    # BCC HTTP 请求（~18 处）
    FAST_PROBE     = 0.3     # 端口快速探活（~13 处）
    HTTP_REQ       = 30.0    # 通用 HTTP 请求（~23 处）
```

这些定义在 `services/app_config_schema.py` 的 `"general"` section 下，用 `env` 前缀覆盖。

#### 层级 B：按模块 overwrite（BCC 启动、Page goto）

在 `daemon_launcher.py` 和 `browser_daemon.py` 各自定义本模块专用的 timeout 常量，共 4~6 项。

#### 层级 C：调用点局部 override

对于用途特殊的超时（扫码 300s、resolve_url 30s、cookie 刷新 15s），保留局部定义，不做全局抽象——因为修改一处不影响其他。

现有 `SECTIONS` 的通用 section 可扩展为：

## 三、结论

### BCC 拉起收敛

- **真正需要改的仅 1 处**：`main.py:293` `_spawn_sidecar` 直拉 BCC → 改用 `ensure_daemons_for`。其余 5 处已走 canonical 路径或语义上不应收敛。
- 核心的 `browser_gate.ensure_browser` 作为**运行时租约门禁**已到位，但**启动时**的 BCC 拉起仍绕过了它。这是设计上的合理决定——启动时无租约概念。
- 10+ 个调 `ensure_daemons_for` 的点都是经过 `daemon_launcher → ensure_bcc` 的标准路径，无需改动。

### 策略中心

- **204 处 timeout（非 153）**，37 个不同值，高度离散
- Top 6 项覆盖 ~44%，Top 12 项覆盖 ~44%（收益递减）
- 建议 3 层分级：① 3 项系统默认（`SECTIONS` 通用 section）→ ② 模块级常量 → ③ 调用点局部 override
- 不推荐做全覆盖策略中心（20+ 配置项回报太低）
