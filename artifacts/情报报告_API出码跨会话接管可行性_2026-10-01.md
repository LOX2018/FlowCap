### 2.3 推断（明确标注）

**【推断 1】** 由 F4 + F5 + F6：ticket 是由**出码会话提交的那把 P-256 公钥**签发的。
若 B 会话（Camoufox）用**自己的** `bd_ticket_guard_client_data`（或根本没有该 cookie，
因为它是上游自己构造的、Camoufox 页面不会写）去轮询同一个 token，则：
- 最好情况：`status` 能读到（token 本身可能是全局的），但 `bd-ticket-guard-server-data`
  **不会签给 B 的公钥** ⇒ 按 F4 原文「拿不到 ticket/ts_sign ⇒ 后续 create_v2、发评论这类
  强校验接口就全都做不了」；
- 更可能情况：跨会话的 csrf / trace_id / ttwid 不一致被风控判为异常会话。

**【推断 2】** 由 F3：`biz_trace_id` 要求「query / 头 / cookie 三处同一个值」。
跨会话接管时，B 会话的 `biz_trace_id` 与 A 出码时下发的不同 ⇒ 三处仍然自洽（都在 B 侧），
但**与出码时的值不同**。这是否致命，**代码无证据**，需实验定性。

**【推断 3】** 「token 是全局的、只是 TTL 被压短」这一假设**不能排除**：
65 秒 TTL 与 token 是否绑定会话是**两个独立维度**（见 §5.2）。

## 3. `redirect_url` → 凭证（`_follow_login_redirect`）

> **代码事实**。`login_api.py:3351-3372`

```python
def _follow_login_redirect(self, auth, redirect_url, max_hops=5):
    """跟随登录重定向，把各跳的 Set-Cookie 都收进来。"""
    if not redirect_url:
        return
    headers = HeaderBuilder().build(HeaderType.DOC)
    url = redirect_url
    for _ in range(max_hops):
        resp = auth.request("GET", url,
                            headers=headers_with_cookie(headers.get(), scoped_cookies(auth)),
                            verify=False, timeout=20, allow_redirects=False)
        set_cookies = resp.cookies.get_dict()
        merge_set_cookies(auth, set_cookies)
        apply_ticket_guard(auth, resp.headers, set_cookies)
        if resp.status_code not in (301, 302, 303, 307, 308):
            break
        url = resp.headers.get("Location")
```

- **是否必须同一 cookie jar？** **代码事实：是**——`headers_with_cookie(..., scoped_cookies(auth))`
  把 `auth` 自己的整个 jar 发给每一跳（`allow_redirects=False`，手工逐跳收 `Set-Cookie`），
  且 `apply_ticket_guard` 把 ticket 写回 **这个 `auth`**。
- **若跨会话，凭证落到哪个会话？** **代码事实**：落到**执行 `_follow_login_redirect` 的那个 `auth`**
  （即 B/Camoufox 会话），因为 `merge_set_cookies(auth, ...)` / `apply_ticket_guard(auth, ...)` 的
  目标就是传入的 `auth`（`login_api.py:3362-3363`）。
  **【推断】** 但 ticket 是用**出码会话（A）的公钥**签的 ⇒ 即使 `sessionid` 落到 B，
  B 也**解不出/用不了** A 的 ticket ⇒ 凭证「半残」（cookie 有、ticket 四件套不可用）。
  这与 `backend\api\accounts.py:495-556` 的「sessionid + 四件套硬门禁」直接冲突（该门禁会判失败）。

## 5. 候选方案可行性评估

### 5.1 三选一结论

> **选：`token 绑定出码会话 ⇒ 候选方案不成立`**（带条件，见 5.3）
>
> 严格按证据等级表述：`bound-to-issuer-session`，但**属「代码事实 + 机制推断」，
> 缺上游原文直证**。

### 5.2 理由（逐条）

1. **P-256 公钥绑定是最硬的机制约束**（F4/F6）。`bd_ticket_guard_client_data` 是**上游自己
   用 `build_client_data_cookie(auth.private_key)` 构造**的（`login_api.py:1320`），
   **Camoufox 页面不会写这个 cookie**。B 会话要么没有它（⇒ 拿不到 ticket），
   要么有自己的（⇒ ticket 签错公钥）。runner 注释把这条钉死为「会话内状态，
   跨进程重建既脆弱又没必要」（`login_qr_api_runner.py:10-14`）。
2. **`redirect_url` 阶段必然跨 jar 断裂**（§3）。即使 `sessionid` 落到 B，
   `accounts.py` 的「sessionid + ticket 四件套硬门禁」会判失败。
3. **即使 token 是全局的，65 秒 TTL 也不会因此变长**。TTL 由**出码方式**决定，
   不是由**谁来轮询**决定。用 Camoufox 轮询一个 API 出的码，**码仍然是 65 秒到期**
   （TTL 在服务端随 token 下发，与轮询方无关）。⇒ **候选方案最核心的动机
   「API 快出码 + 浏览器长寿」在本方案下无法同时成立**：码的寿命跟着出码方走。
4. **身份矛盾仍然存在**。B 会话是 Firefox/Camoufox，而 token 由 Chrome 151 身份的 A 会话申请；
   `accounts.py:206-212` 已把「Chrome ⊗ Firefox 跨信号矛盾」列为默认关闭 API 通道的理由。
5. **收益已被现有方案覆盖**。`login_remote.py:1044-1059` 的**接口桥**已经在做
   「无头 Camoufox + 页面自己发 `get_qrcode` + 自维持 `check_qrconnect`」，
   且**不依赖 UI 坐标 / 对 DOM 改版免疫**。候选方案想拿的「浏览器会话真实性」，
   桥已经有了；候选方案引入的「跨会话 token 接管」是**额外风险，无额外收益**。

### 5.3 条件 / 保留

- 若实验证明「token 可被任意会话轮询且 `status` 正常推进」（§6 阶段 A 通过），
  则降级为 `uncertain` + 补阶段 B/C；
- 若连阶段 A 都失败（B 会话轮询返回非 `new`/直接 `expired`/`error_code!=0`），
  则 **确定性** 判 `bound-to-issuer-session`，候选方案彻底否决。

## 6. 最小实验设计（用于定性，不含糊）

> 目标：只回答一个问题——**A 会话出的 token，B 会话能否正常轮询**。
> **不需要真人在场扫码**（除阶段 C）。**不触发真实登录请求**（阶段 A/B 只读状态）。

### 阶段 A：跨会话轮询可读性（最小、可无人值守）★ 决定性

1. 用 `login_qr_api_runner.py` 的 A 会话（或等价脚本）跑 `bootstrap_auth()` + `get_qrcode()`，
   落盘：`token` + **A 的完整 cookie jar**（含 `passport_csrf_token`、`ttwid`、
   `biz_trace_id`、`bd_ticket_guard_client_data`、`s_v_web_id`、`msToken`）。
2. **另起一个 B 会话**：在**无头 Camoufox** 里打开 `https://www.douyin.com/?modal_id=login`
   （沿用 `login_remote.py:1050` 已验证的深链入口），让它自己 bootstrap（拿到 Firefox 侧的
   cookie）。
3. B 侧用 `page.evaluate(fetch(...))` **在页面上下文内**发一次
   `POST https://login.douyin.com/passport/web/check_qrconnect/`，
   body 只带 `token=<A 的 token>` + 其余固定字段，**cookie 由浏览器自动带（B 的 jar）**。
   ⇒ 这样既拿到「浏览器会话」身份，又不需要手工重签 sign/a_bogus（浏览器自带 SDK 环境）。
4. **判据**：
   - ✅ 返回 `error_code=0` 且 `data.status ∈ {new, scanned}` ⇒ **token 可读 ⇒ 阶段 B**
   - ❌ 返回非 0 / `status=expired`（且码龄 < 65s）/ 非 JSON ⇒ **绑定出码会话，方案否决**
5. **同时做对照**：同一时刻用 A 会话轮询**同一个 token**，
   比较两边 `status` 与 `error_code`。若 A 正常、B 异常 ⇒ **坐实绑定**。

### 阶段 B：码寿命是否随轮询方改变（回答「65 秒」）

- 在阶段 A 通过的前提下，让 **B 独占**轮询 A 出的码，记录 `status` 变 `expired` 的墙钟时间。
- 判据：**若仍是 ≈65.0s** ⇒ 证明 TTL 由**出码方**决定，与轮询方无关
  ⇒ **候选方案的核心收益（长寿）不存在**，方案无价值（即使技术上能跑通）。
  若显著 > 65s（如 300s）⇒ TTL 由轮询方决定，方案值得继续。

### 阶段 C：端到端（需真人在场扫码）

- 仅当 A、B 均通过才做。B 轮询 → 用户扫码 → `confirmed` →
  检查 `bd-ticket-guard-server-data` 是否下发、ticket 能否解出、cookie 是否含 `sessionid`。
- **关键判据**：即便 `sessionid` 有，**若 `ticket` 为空 ⇒ 凭证半残**（F4 已预言）。

### 成本控制

- 阶段 A/B **无需真人扫码**，可脚本化，单次 < 2 分钟。
- **不要**在阶段 A 之前做阶段 C（避免为取证付出真实扫码与风控成本）。
- 建议先加「runner 原始响应落盘」（`工作记忆\cases\...v0.45.147.md:96-98` 已提出此需求），
  让服务端原始字段（是否含 `expires`/TTL 字段）可读 —— 这可能**直接回答 65 秒的来源**，
  比阶段 B 更便宜。

## 7.  blockers / 待确认项

1. **无上游原文**：`check_qrconnect` 的会话绑定规则**未在任何注释中写明**，本报告该结论
   属推断，需 §6 阶段 A 定性。
2. **65 秒 TTL 的服务端原始响应未读到**：runner 的 `status.json` 只挑了部分字段
   （`login_qr_api_runner.py:154-156`），**未落原始响应**。
3. **`bd_ticket_guard_client_data` 是上游自造 cookie**，Camoufox 页面不会写
   ⇒ 跨会话接管在机制上天然缺这一环。
4. **身份矛盾未解决**：即便跨会话可行，出码身份（Chrome 151 + curl_cffi chrome150）
   与日常会话（Camoufox/Firefox 152）仍然矛盾（`backend\api\accounts.py:206-212`）。
5. **本报告未发起任何真实请求**，所有服务端行为判定均来自既有实测
   （`工作记忆\cases\2026-10-01_API扫码二维码65秒过期_指纹灌注对照_v0.45.147.md`）
   与代码事实，非本次新做实测。
