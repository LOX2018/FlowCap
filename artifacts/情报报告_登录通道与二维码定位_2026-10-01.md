## 1. 历史上试过的登录通道（逐条：结论 + 原因 + 证据）

### 通道 1 · 老 `enrich_auth` 有头弹浏览器手动扫码（`api/accounts.py` `/scan` → `_do_scan`）
- **结论**：✅ 长期可用（人工兜底基线），但**必须人在电脑前**（Session 0 不可用）。
- **原因**：有头 + 固定 profile，身份与环境一致，是最稳的人工路径。
- **证据**：
  - ADR-017（2026-09-26）§1.1 第 20 行：「扫码登录（有头窗口）| ✅ 已有 | `api/accounts.py:742 POST /{name}/scan` + `_do_scan` + `auth_helper.enrich_auth`」
  - ADR-017 第 67-76 行 `_do_scan` 既有行为：取 profile 独占锁 → 停守护 → `enrich_auth(force=True)` → 回拉守护；并注明「**不许破坏**」。
  - 台账 H-30（2026-09-26）：共同卡点原文「**须人工扫码（GUI，Session 0 不可用）**」。
  - ADR-034 §6 回退（第 163 行）：「RPA 失败自动回落『有头浏览器用户手动』（`_do_scan` 原手动分支**一行未改**）」。
  - v0.45.136 台账：默认路径曾是 `_do_scan` 旧默认 `path="manual"` → `enrich_auth(force=True)` 有头。

### 通道 2 · RPA 扫码（无头 Camoufox + DOM 锚点截图 + cv2 解码）
- **结论**：❌ **已废弃主用**，退为兜底。
- **原因**：主锚点 `#animate_qrcode_container img` 在抖音改版为 SVG 后**恒命中 0**；慢且随改版失效。
- **证据**：
  - ADR-034 第 41 行 D3：「`#animate_qrcode_container` 内是 **SVG（13 个 `<image>`）**，无 `<img>`；旧主锚点 `"#animate_qrcode_container img"` **恒命中 0**（`_live/live_report.json` 的 `qr_img=0`）」
  - 案例 `2026-09-30_更新凭证定位不准根治…v0.45.126.md` 第 55 行：`qr_img=0` / `qr_canvas_or_img=0`（二维码已无 img）
  - ADR-034 §4.3 改「容器栅格化」为兜底（第 95-96 行）

### 通道 3 · RPA 短信 / 验证码登录（`login_remote.do_sms_login`）
- **结论**：⚠️ **可用但未端到端验证**（始终缺真机收码）。路径本身两次被修：先补 `handle_one_click_login`，再补「零调用点」接线。
- **原因**：profile 记住账号时抖音弹「一键登录」面板，`input[name="normal-input"]` 不存在 ⇒ `fill_phone` 100% 失败。
- **证据**：
  - ADR-017 §8.2-A（第 450 行）：DOM 实测 `<div id="douyin_login_comp_btn_id">一键登录</div>` + `<p>登录其他账号</p>`，「此时表单锚点与『验证码登录』tab **都不存在** ⇒ 短信流程 **100% 失败**」
  - ADR-034 第 40 行 D2：`handle_one_click_login`（:426）**全仓 grep 仅自身**；`do_sms_login` 从不调用它
  - 台账历次「⏳ 剩余：短信收码全流程未端到端（需用户在场）」——**截至 2026-10-01 仍未闭环**

### 通道 4 · 纯 API 无浏览器（老 `login_api.dyGenerateInitData` / `dyGenerateQRcode`）
- **结论**：❌ **失败**（两处叠加：① 违反单 profile 铁律；② 接口侧 JS 挑战壳页 / ttwid 缺失）。
- **证据**：
  - ADR-017 §3.1 DEFECT-1（第 132-159 行）：`login_api.py:205` 未传 `user_data_dir` ⇒ `[BCC-058]` **100% 失败**
  - ADR-017 调研记录 第 12-17 行：匿名 msToken ❌、项目纯算 msToken ✅ 但 `_ttwid` 为空、调 `get_qrcode` ❌「返回 **9938 字节 JS 挑战壳页**（非 JSON）」、项目无 ttwid 生成器 ❌ ⇒ 「**纯接口方案否决**」

### 通道 5 · 上游 vendor 纯 HTTP 扫码（`login_api_vendor.VendorLoginApi` → `bootstrap_auth`/`get_qrcode`/`check_qrcode`，子进程隔离）
- **结论**：⚠️ **出码成功**（技术验证通过），但**身份层面被用户否为最优**——纯 HTTP 用 Chrome 身份，而运行 profile 是 Firefox（Camoufox），存在身份矛盾；2026-09-30 降为**显式开关** `DY_LOGIN_QR_BACKEND=api`。**结论≠上线主路径**。
- **证据**：
  - ADR-017 §8.1（第 393-400 行）：「扫码登录 → **API 路径**（上游 vendor）✅ 保留可用；短信 → 只走 RPA；短信 API 路径 ❌ **显式禁用**（AUTH-072）」
  - ADR-017 §8.1·乙（第 408-422 行）：即使 `dtrait`(820B) 与 `a_bogus` 全部还原，**业务层仍被 `bd_ticket_guard` 拦 `2156`**；反向印证「**RPA 是正确路线，不是权宜之计**」
  - ADR-034 §4.1（第 55-79 行）：必须**干净子进程**（vendor 与 backend 有 5 个同名顶层包 `dy_apis`/`builder`/`utils`/`dy_live`/`static`，同进程必然静默半坏，门禁 `test_h22_p4_audit_fixes.check_g1` 断言应用进程内调用必须抛 AUTH-073）
  - ADR-034 第 124 行形态对比表：纯 API 子进程 → 身份「🔴 Chrome⊗Firefox」⇒「出码可但身份存疑」
  - 台账 v0.45.133：「⑤ API 纯 HTTP 路径降为**显式开关**（`DY_LOGIN_QR_BACKEND=api`）」
  - ADR-034 §6 第 157-161 行诚实标注：**扫码 confirmed 全流程未端到端**；上游 login API 依赖 fpk1（本机无指纹采集）

### 通道 6 · 接口桥（Bridged API）——**当前默认主路径**（2026-09-30 用户拍板，2026-10-01 修「永不出码」）
- **结论**：✅ **当前最优形态**，正在用。无头 Camoufox 起页面 → **只被动 `context.on("response")`** 截页面自己发的 `get_qrcode` / `check_qrconnect`，二维码取自响应体 QR URL 再本地渲染 PNG。改版免疫 + 身份与运行 profile 一致（同为 Firefox）。
- **关键技术事实（本次 UI 坐标之争的核心）**：**必须【真实鼠标】点「登录」按钮才发 `get_qrcode`**。
- **证据**：
  - ADR-034 §4.6（第 112-132 行）用户原话与形态表
  - 台账 2026-10-01 v0.45.145 `cb90861` 三对照实测：
    - ① 只 goto `/?modal_id=login` ⇒ 被重定向到 `/jingxuan`，登录弹窗**不挂载** ⇒ 永无出码
    - ② **JS 合成 `el.click()`** ⇒ 返回 clicked 但**不发**接口（抖音忽略合成事件）
    - ③ **真实鼠标 `page.mouse.click(x,y)`** ⇒ 立刻截获 `get_qrcode` + 180×180 二维码容器 ✅
  - 修复：`_try_click_login`（真实鼠标带轨迹移动+点击）+ **点击后校验是否真出码、未出则重试**（实测首点 x=1532 落空、稳定后 x=1540，需重试）
  - 实证：修前 102.5s 超时 `ok=False`；修后 `get_qrcode token=2f5959c0a381507c73 error_code=0`，**29.9s · ok=True · via=bridge · qr.png 3220B**
  - 默认路径：台账 v0.45.136「改为：**默认走接口桥（无头）**，桥不可用 ⇒ **自动回落**有头手动（最初方案作兜底）」
  - **未闭环**：扫码 confirmed 全流程（需用户在场）；「点击后等 6s 判未出码」仍为**启发式阈值**；本批按用户指示**暂不部署**。

### 通道 7 · 短信 API（`send_sms_code` / `phone_login`）
- **结论**：❌ **显式禁用**（`NotImplementedError` AUTH-072），不论 dtrait 是否可生成。
- **证据**：ADR-017 第 395-400 行 + §8.1·乙（服务端侧 `bd_ticket_guard` 硬阻塞 `2156`）。

### 通道 8 · 粘贴板填验证码（Ctrl+V）
- **结论**：❌ **否决**（含阳性对照失败）。改用 `keyboard.type` 逐字。
- **证据**：ADR-017 §3.1.甲 修正表（第 185-200 行）：Ctrl+V「**连阳性对照（手机号框）都失败**」⇒ 整体不可用；采纳 `keyboard.type(code, delay)`（真实按键序列，风控风险最低）。

## 2. 「二维码定位」三种做法的项目结论（**本次争议焦点**）

| 做法 | 项目历史结论 | 证据 |
|---|---|---|
| **① DOM 锚点 + 元素截图 + cv2 解码** | 判据可靠，但**取码源脆弱**：锚点会随改版失效。且**像素统计判二维码假阳性 100%**，必须用「cv2 能否解码」作判据 | ADR-017 调研记录 第 60-74 行：「判据 | '黑白占比>85%+色数<32' ❌…真二维码反而被漏（带装饰边，色数 458）…**'cv2 能否解码' ✅ 唯一可靠**」；ADR-034 D3 锚点失效 |
| **② 屏幕上找坐标 / 目视 / 像素** | 明确否决 | 同上第 60-74 行「🔴 血泪教训：**像素统计判二维码，假阳性率 100%**」 |
| **③ 截接口响应（接口桥）** | ✅ **当前采用**。改版免疫 + 身份一致 | ADR-034 §4.6 第 124 行形态表；台账 2026-09-30 / 2026-10-01 |

**关于「分辨率 / 跨设备」的既有记载**（与用户质疑直接相关）：
- ✅【事实】项目**已知** viewport 决定 `screen`，且要求显式设置（不看本机分辨率）：`工作记忆/06_凭证与签名.md:868-878`「**`screen` 由 Playwright 的 `viewport` 决定，内核的 `--window-size` 会被它覆盖**」；表：`viewport={1440,900}` → `1440x900` ✅；未设则 `1280x720`（属明显自动化特征）。⇒ 接口桥/点击都在**固定 viewport 的虚拟页面**内，理论上不随本机分辨率变化。
- ⚠️【推断+部分事实】分辨率独立性**未被专门验证过**；但坐标本身**已被实测证明会落空**：台账 2026-10-01「实测首点 x=1532 落空、稳定后 x=1540，需重试」。⇒ **UI 坐标的脆弱点在本次真机已被实证，只是用「点了之后校验有没有真出码 + 重试」来兜，而不是靠坐标准确。**
- 【推断】全文检索未见「纯坐标 vs DOM」的系统性对比结论；现有定论是 **「改版免疫的定位顺序：确定性接口/入口 → 稳定 id → 容器栅格化/机械解码 → 文本兜底」**（ADR-034 §7-3，第 171 行）——**UI 坐标不在这个推荐序列里**。

## 3. 「本地 cookie 存在 ≠ 会话有效」铁律的出处与实证

**铁律原文**（`DYAutoDM_v2/knowledge/cases/rpa-sms-login-three-bugs.md:245`）：
> 「**铁律：见证凭证有效性的唯一可靠判据是服务端接口答复，不是 UI 状态。**」

**实证案例 1（最强，直接对比）** —— ADR-017 §8.2-C（第 452 行）：
> profile 有 **66 cookie + 8/8 登录标识 + UI 显示已登录**，但官方接口 `GET https://www.douyin.com/passport/account/info/v2/` 返回 `{"error_code":13,"description":"会话过期，请重新登录","user_id":0}` ⇒ 「**改用官方接口判据**（UI 状态**不可作判据**——Live-Instance Verification 铁律）」
> 同表 `rpa-sms-login-three-bugs.md:240-241`：「本地 cookie（66 个）+ UI 显示已登录 | ❌ **假象** / 官方 passport 接口 | ✅ 会话无效」

**实证案例 2（同源第二次复发，v0.45.136）** —— 台账 2026-09-30：
> 「② **谎报源头**：`_is_real_login` / `poll_bridge_confirmed` / `poll_qr_scanned` 判据均只看『**本地 cookie 存在**(sessionid/sid_tt)』——账号**陈旧** sessionid 常在 ⇒ **未扫码即假成功**、把过期凭证当新凭证落盘（真机日志：`检测到真实登录态（已扫码）` → 15s 后 `[AUTH-053] 会话未被服务端承认` → 仍宣称完成）」
> 修法：**服务端权威确认**（`passport/account/info/v2` → `user_id>0` 且无 `error_code`），cookie 存在**仅触发一次探活**。

**实证案例 3（历史最早，v0.43.0）** —— `工作记忆/06_凭证与签名.md:569-585`：
> `browser_daemon.scan_login()` 判据原为 `ok = bool(auth and getattr(auth, "cookie", None))` ——「**只要 `.env` 里存在 cookie 就报『刷新成功』**，完全不验证凭证是否真的有效」⇒ 熔断永不触发 ⇒ **155 次/日无限重启循环**。铁律：「**"没抛异常" ≠ "成功"**」。

**判据细化（2026-10-01，最新）** —— `工作记忆/cases/2026-10-01_账号能力矩阵_凭证有效性按用途分面_v0.45.142.md`：
> 「**「凭证有效」是歧义词**：同一份 cookie 在**不同服务端端点**上的裁决**互相独立**」（张老师主站判失效却仍能取直播数据；尚进各项正常却有直播域端点拒它）⇒ 应按**用途分面**判，5 面能力矩阵；**铁律：`unknown` 绝不折成 `fail`**。

## 4. 「抖音登录页改版导致 DOM 锚点全部失效」的记录

✅ **有完整记录，且是 ADR-034 的立项根因**。

- ADR-034 第 49-51 行 RCA：**「外部契约漂移（抖音登录页改版）：二维码由 `<img>` 改 SVG、tab 由具名改哈希类名。硬编码锚点必然失效。」**
- 具体失效清单（ADR-034 §2 D1/D3/D5 + 案例 v0.45.126 §3 取证）：

| 锚点 | 失效形态 | 证据位置 |
|---|---|---|
| `#animate_qrcode_container img` | 容器内已是 SVG，**`"#animate_qrcode_container img"` 恒命中 0**（`qr_img=0`） | ADR-034:41；案例 v0.45.126:55-56（`{svg:2, path:16, image:13}`） |
| `input[name="normal-input"]` | 一键登录面板下**不存在** ⇒ `fill_phone` 100% 失败 | ADR-034:39；案例 v0.45.126:53-54 |
| 「扫码登录 / 验证码登录」tab | 真实节点是 `<span class="C6OZQwMA">`（**哈希类名、无 id**），不可作点击锚点 | ADR-034:43（D5） |
| `#douyin_login_comp_btn_id` | **注释误标**：项目注释称其为「一键登录」，实测 `direct_text='登录'` | ADR-034:86-88；案例 v0.45.126:57 |

- 更早的同一病灶（2026-09-28）：ADR-023 §7 / 案例 `bcc-lazy-permanent-fail-and-login-routing.md:67-69`：
  > 「**抖音登录页 DOM 锚点已变**（`input[name="normal-input"]` 不存在、`扫码登录` tab 找不到）；属『外部契约漂移』，需真机按**不预设选择器、按内容特征**取证」
  - ADR-023 §4 D3/D4 明写「**本轮不修锚点**」⇒ 已登记为独立待办。
- 兜底层：`dom_locator.py`（2026-09-29 v0.45.94）Scrapling parser 自适应定位，仅当确定性判据失败时启用，**必须 fail-closed + 唯一性**（>1 即拒绝）。

## 5. ADR-017 / ADR-023 / ADR-034 拍板的【登录路径优先级】原文

### ADR-017（2026-09-26，IM 远程登录）
- §2.3 状态分流（第 110-124 行）原文：
  ```
  状态 A：全新账号（无任何登录态）
    → 优先【二维码】：截图 → 推送 IM → 用户扫码
    → 备用【验证码】：若二维码不可用，降级验证码
  状态 B：已有账号（登录态在，凭证过期）
    → 只用【验证码】：发短信 → 推送"输入验证码" → 用户回传 → 提交
  ```
  并：「**分支判定依据 = 账号当前状态，不是用户选择**」；用户要求原文「**应该自动判断，而不是让用户手动选择**」（第 122 行）。
- §8.1 决策 1 **能力边界**（第 391-400 行）原文表格：
  ```
  登录方式            归属路径                                    状态
  扫码登录            API 路径（上游 vendor login_api_vendor.py）  ✅ 保留可用
  短信（验证码）登录  只走 RPA 路径（login_remote.py）              ✅ RPA
  短信登录（API 路径）上游 send_sms_code / phone_login            ❌ 显式禁用
  ```
  并在注释中被 ADR-034 引述为：「**扫码登录 → API 路径（纯协议，快且轻）；短信登录 → RPA 路径（真浏览器，天然带全部指纹，无需 dtrait）**」（ADR-034 第 22-25 行）。
- §8.1·乙 追加：「**RPA 是正确路线，不是权宜之计**」（第 422 行）。
- **⚠️ 用户原话的拍板风格**（第 166-171 行）：「验证码的方式也可以采用 DOM 在哪里点击…通过**粘贴板的形式填入输入框**，然后点击登录」「**相当于 rpa 处理**」。

### ADR-023（2026-09-28，更新凭证分流）
- §1 第 14-16 行：分流判据是 ADR-017 §2.3 的自动机，**用户明确要求「应该自动判断，而不是让用户手动选择」**。
- §4 分流权威判据（第 73-78 行）：复用 `uid_identity_verdict()` 4 元组 —— `True` ⇒ 短信；`False`（`no_credential`/`not_logged_in`/`uid_drift`）⇒ 扫码；`None` ⇒ **诚实降级为扫码**（不假装知道状态）。
- §4 D5（第 71 行）：入口唯一化 + `msg` **如实标注实际路径**，缺手机号**如实上报**、「**绝不静默改走扫码**」。
- §4 D3/D4（第 70 行）：「**本轮不修锚点**」——本轮以**分流**避免把用户送进已知必败路径。
- §8-5（第 119-121 行）：「**文档写过的能力要能被机械检出『有没有落点』**（本项目已两次出现『契约只在注释里』的漂移）」。
- ❌ **未见**「API 优先 / RPA 兜底 / 手动最后」的字面排序——ADR-023 只管「走哪条认证流」与「失败可重试」，**不排通道优先级**。

### ADR-034（2026-09-30，定位不准根治）—— 唯一明确排了通道优先级的 ADR
- §4.1 标题原文（第 55 行）：「### 4.1 扫码：**优先上游 API（纯 HTTP）**，**RPA 降为兜底**」
- §4.6（第 114-125 行）**用户指正后改判**，给出三种形态的正确性层级对比：
  ```
  | 形态                  | 二维码来源              | 身份                | 判据稳健性        |
  | §4.3 DOM 截图 + cv2   | 像素                    | 同 Firefox ✅        | 脆（随改版失效）  |
  | §4.1 纯 API 子进程    | 协议响应                | 🔴 Chrome⊗Firefox   | 出码可但身份存疑  |
  | **§4.6 接口桥**       | **页面自发的 get_qrcode 响应** | 同 Firefox ✅  | **改版免疫 + 身份一致** |
  ```
  原文定性：「**这是正确性层级上的最优形态**（优于本文 §4.1 的 API 与 §4.3 的截图）」
- §6 回退链（第 162-163 行）：「API 失败自动回落 RPA，RPA 失败自动回落『有头浏览器用户手动』（`_do_scan` 原手动分支**一行未改**）」。
- §7-3 可迁移判据原文（第 171 行）：「**改版免疫的定位顺序**：确定性接口/入口 → 稳定 id → 容器栅格化/机械解码 → 文本兜底。**哈希类名与 `<img>` 锚点都是会静默失效的脆判据。**」
- **台账 v0.45.136 的最终落地排序**（比 ADR-034 正文更新）：
  > 「改为：**默认走接口桥（无头）**，桥不可用 ⇒ **自动回落**有头手动（最初方案作兜底）；新增显式 `mode=manual|browser` 直达有头。」

⇒ **合并后的现行优先级（事实层面）**：**接口桥（无头）> 有头手动浏览器；纯 HTTP API 降为显式开关（非默认）；RPA DOM 截图退为容器栅格化兜底。** ADL 里**没有**写死「API 优先 / RPA 兜底 / 手动最后」这句三字词原文；那套排序产生于 ADR-034 §4.1，**随后在 §4.6 被用户拍板推翻改序**。

## 6. 风控的实证判据：什么算真风控，什么不算

### ✅ 算真风控 / 硬阻塞的形态
1. **HTTP 403 + 46 字节非 JSON**（`Blocked by ArgusSecurityPlugin Uifid Not Found`）——这是本项目**唯一的、有明确定量的「真风控/真拦截」模板**：
   - `DYAutoDM_v2/docs/adr/ADR-014-content-panel-argus-403-fix.md:16-17`：5 个内容端点缺 secsdk 签名 ⇒ 「被 Argus 网关恒返 **HTTP 403**（46 字节 `Blocked by ArgusSecurityPlugin Uifid Not Found`），前端只收到空」
   - `DYAutoDM_v2/docs/design-contracts/C-02-content-collection.md:43`：「未接线的端点在上游策略漂移后会**静默 403**（返回 **46 字节非 JSON**）——这正是 2026-09-21『合集作品取不到』的根因类型」
   - ⇒ **判据模板：状态码 + 精确字节数 + 非 JSON 内容**，可机械核验，不依赖页面观感。
2. **服务端业务层拒绝**：`bd_ticket_guard` 返回 `2156`（即使签名全对），属服务端侧硬阻塞（ADR-017 §8.1·乙 第 415-419 行）。
3. **官方页面二级确认**：`login.douyin.com/passport/web/get_qrcode/` 返回「请使用已登录账号的设备扫码 / 为保障账号安全，请使用「抖音APP」扫码验证」+ `challenge/` 返回 passportiv 加密挑战模板（`工作记忆/06_凭证与签名.md` §【2026-09-13 抓包实证】第 528-536 行）。
4. **账号级限流**：`KICK`（同上第 192 行）——「剩余 `KICK` 是账号级风控限流，与签名无关，属另一个体系」。

### ❌ 不算风控（被证伪、已撤回的定性）
1. **`risk_level=no_risk` 却弹「您正在尝试访问的网站存在安全风险…已阻止此次访问」** —— **不是风控**，是「登录态失效 → passport 重新验证」的前端呈现（`工作记忆/06_凭证与签名.md` 第 530 行「**网站存在安全风险…已阻止此次访问」不是风控惩罚**」；第 563-565 行「**弹窗文案与后端风控判定解耦**…**不要被文案误导去修风控相关代码**」「**凭证失效会伪装成"风控弹窗"**」）。
2. **页面存在 `rmc-nocaptcha` iframe** —— **不是风控**。台账 2026-10-01 v0.45.145：
   > 「该 iframe 在**普通首页**与**登录页**上完全相同（w=0 h=0 visible=false display:none），是抖音**常驻隐藏安全组件**、非真人验证弹窗；两段错误代码已撤回（grep 计数 0）。**教训：不能以『存在某安全组件』推定『真人验证拦截』，须做阴性对照（正常页是否也有）。**」
3. **UI 昵称/字段表象**：`desensitized_nickname` / `is_anonymous` / `mystery_man`「**全不可作判据**」（`cases/2026-09-21_同机制下账号差异…md:100`）。

### 既有风控关键词 SSOT
`RiskControlError.KEYWORDS`（ADR-017 / 台账 v0.45.38）：命中后「**绝不关闭浏览器、绝不立即 raise**」，只告警一次并继续等用户验证（`工作记忆/06_凭证与签名.md:39-40` 同源铁律）。

## 8. 结论摘要（供下一步改「更新凭证」直接引用）

1. **现行默认路径 = 接口桥**（台账 v0.45.136 已改判，非 ADR-034 §4.1 的纯 API）。改 UI 坐标前请先确认这一点，不要回到已被推翻的形态。
2. **UI 坐标脆弱这件事，项目已在 2026-10-01 真机实证**（x=1532 落空），既有缓解手段是「**点击后校验是否真出码 + 重试**」，而非「让坐标更准」。
3. **确定性优先序列**（ADR-034 §7-3）：接口/入口 → 稳定 id → 容器栅格化 → 文本兜底。**哈希类名与 `<img>` 锚点是已知脆判据**。
4. **任何凭证成功的判据必须落到服务端**（`passport/account/info/v2` → `user_id>0` 且无 `error_code`）；本地 cookie 存在**只能触发一次探活**，不能宣告成功（三次复发的血案）。
5. **Token 判定不得跨进程/跨形态混用身份**：纯 HTTP 的 Chrome 身份 vs 运行 profile 的 Firefox 身份 = 已知矛盾（ADR-034 §4.6）。
6. **风控定性必须有阴性对照**：`rmc-nocaptcha` 型常驻组件 ≠ 真人验证；「46 字节非 JSON 403」才是可机械核验的拦截模板。
7. **仍未闭环（诚实标注）**：扫码 confirmed 全流程、短信收码全流程 —— **两者都需用户在场**，历史上从未端到端跑通过。
