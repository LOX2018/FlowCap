**建议动作（优先级从高到低）**

1. **立即（修复 §31.3，1 行级，不必升级）**：在 `add_init_script` hook 的**读取侧**改用主执行世界：
   `await page.evaluate(js, isolated_context=False)`（patchright 专有 kwarg，仅当 `DY_PW_BACKEND=patchright` 时可用）。须包一层兼容 helper，否则回退原生 playwright 时会 `TypeError`（§三.4）。
2. **加门禁**：把 §四 的「context 级 init script 两世界可见性探针」纳入现有 `env_audit` / 回归套件，防止再次出现「注入成功但读到空」的静默态（§四.4）。
3. **暂不升级**，直到满足 §〇 的「条件升判据」（下方）。

**条件升判据（满足任一才升级，且须同时执行 §三.5 的升级验收）**
- (a) 上游 patchright **1.62.x 线出现安全/兼容修复**，或本机 `patchright` 1.62.3 在升级 Playwright/Chromium 后**无法再启动**；
- (b) 本项目需要 Playwright **1.63.0 的新 API**（如 `locator.visible`、`frame_locator()` 跨帧、`opfs` storage state）——当前**无此需求**；
- (c) Camoufox 路线被否决、需回到 Chromium + JS 注入方案，且届时上游已给出真正修复 `add_init_script` 的版本（**届时必须先复验 §四 探针，再决定**）。

**升级红线（本次修正）**：patchright 与 playwright **必须同版演进**（patchright 版本号 = 镜像的 Playwright 版本号），**禁止只升其一**。
但**当前 Camoufox 生效期内这条红线与内核依赖直接冲突**：`camoufox 0.5.6` 钉了 `playwright (<1.63)`，所以「同版升到 1.63.0」**在本项目当下不可能合规执行**。⇒ **在 Camoufox 放宽 playwright 上界之前，playwright 线一律锁定 1.62.x，patchright 亦不单独升**（避免留下"patchright 1.63 + playwright 1.62"的双驱动不一致态）。

## 一 上游变更事实（附来源链接 / sha）

### 1.1 关键认知：patchright-python 不是「手写库」，而是**重打包构建器（harness）**

`Kaliiiiiiiiii-Vinyzu/patchright-python` 仓库**几乎不含业务源码**（v1.62.0 tag 全树仅 14 个文件：workflows / `patch_python_package.py` / `setup.py` 补丁 / README）。其发布流程（`.github/workflows/patchright_release.yml`，main 版）为：

1. 从 PyPI 解析**最新 stable `playwright` 版本号** → `utils/release_version_check.sh`；
2. `git clone https://github.com/microsoft/playwright-python --branch $playwright_version`；
3. 跑 `patch_python_package.py`：以 **AST 改写** 打补丁、把 `playwright` 包名/目录整体改为 `patchright`、重写 `pyproject.toml`/`setup.py`/PyInstaller hooks；
4. **npm 侧**取 `patchright-core@<version>`（`patchright` 驱动仓库的产物）替换 `playwright-core`，作为 `patchright/driver/` 打进 wheel；
5. 发布到 PyPI。

**推论（对本次评估至关重要）**：
- patchright 的版本号**镜像 Playwright 的版本号**；1.62.3 / 1.63.0 里的 `.3` / `.0` 是**补丁位**，与 Playwright 的补丁位无对应承诺。
- 因此 **GitHub Releases 只有一部分版本**，且**最新 tag 停在 `v1.62.0`**——「看 GitHub Release 判断最新版」在本仓库**不成立**（1.62.1/1.62.2/1.62.3/1.63.0 均无 Release）。**版本真源是 PyPI**（该 harness 已于 `dc3e22ef` 起用 PyPI 作唯一起点）。
- 真正影响运行时行为的补丁，**只存在于 `patch_python_package.py`**（+ 驱动仓库的 `patchright-core`）。所以「1.62.3 → 1.63.0 的实质变更」= 「**Playwright 1.62.0 → 1.63.0 的全部变更**」+ 「**驱动 patchright-core 1.62.3 → 1.63.0**」+ 「**harness 脚本变更**」。harness 脚本本身的变更**不进入已发布产物**（它只在构建时跑），故对运行时**无影响**。

### 2.4 项目生产路径现状（决定本次收益的关键）

- 已打包产物 `src-tauri/binaries/_internal/patchright/` 为 **1.62.3**（`driver/package/package.json` = `patchright-core 1.62.3`），且冻结副本中 `install_inject_route` 与 `ImplToApiMapping` **均存在**。
- **驱动不联网下载**：`patchright` 的 driver（node.exe + package）随 wheel 打包，项目又自带 `executable_path` → 上游「Fix Release / Migrate Driver」均**不改变本项目运行时**。

## 四 `add_init_script` 静默失效：复测方案（含已执行的实机结果）

### 4.1 机理（已由源码 + 实测共同确证）

patchright 为**避免 `Runtime.enable` 泄漏**，把 init script 从 CDP `Page.addScriptToEvaluateOnNewDocument`（落入**主世界**）改为 **Route 注入**：

- `BrowserContext.add_init_script` 首先 `await self.install_inject_route()`（`_browser_context.py`）；对每个 `resource_type == "document"` 且 `url.startswith("http")` 的请求执行 `route.fallback(patchrightInitScript=True)`；驱动侧把脚本**注入到页面主世界**。
- 同一改动把 `Page/Frame/Locator/JSHandle/Worker.evaluate*` 加上 `isolatedContext` 参数，**默认 `True` = 在隔离世界求值**。
- ∴ **init script 落在「主世界」，而 patchright 的 `evaluate()` 默认读「隔离世界」**。两侧 `window` 不同 → 项目读取 `window.__CAP_USERINFO__` / `window.__CAP_WP_MESSAGE__` 拿到 `undefined`/`{}` → 表现为「注入成功但读到空」，即 `08 §31.3`「静默失效」。
- 证据链：`browser_daemon_js.py:49-108`（hook 写 `window.__CAP_USERINFO__`）、`bcc_capture.py:215-216`（读 `window.__CAP_USERINFO__`）、`browser_daemon.py:1149-1150`（读 `window.__CAP_WP_MESSAGE__`）**均未传 `isolated_context`**。

**⚠️ 关键的负例教训（供复用）**：首轮我用「同一 context 另开 page」做负例 → 因 **context 级 init script 对新页同样生效**，负例被污染成 `INIT_OK`，一度误报"静默失效"。**负例必须用全新 context**，否则会把"正常生效"读成"失效"。这正是此类复测最容易踩的坑。

**两路证据统一（无矛盾）**：
- 本探针判据 = **页面自己（主世界/DOM）是否看见 init script** → 两版**都看得见** ⇒ 证明 **Route 注入本身正常**。
- 兄弟探针判据 = **patchright 的 `evaluate()` 默认世界能否读到** → 读到空 ⇒ 证明 **读取侧世界不匹配**。
- 合起来 = 「**写进主世界成功、默认从隔离世界读 → 读空**」的完整机理链（与 §4.1 一致）。⇒ 修复动作落在**读取侧**（§4.4 方案 A），**与 patchright 版本无关**。

### 4.4 修复方案与门禁

**方案 A（推荐，1 行级，1.62.3 即生效）**：读取侧走主世界，并兼容回退后端：

```python
# 追加到 backend/vbrowser.py（或 daemon 内共享 helper）
async def ev_shared_world(page, js: str, arg=None):
    """读取 context 级 init script 写在主世界的数据。

    patchright 的 init script 经 Route 注入落在**主执行世界**，而其 evaluate()
    默认在隔离世界求值 → 默认读不到（08 §31.3 静默失效根因）。故显式指定主世界；
    该 kwarg 为 patchright 专有，回退原生 playwright 时须降级（否则 TypeError）。
    """
    try:
        return await page.evaluate(js, arg, isolated_context=False)   # patchright
    except TypeError:
        return await page.evaluate(js, arg)                            # 原生 playwright
```
改造点：`bcc_capture.py:215`、`browser_daemon.py:1149,1152`（读 hook 对象的处）；`browser_daemon.py:888,945,1030,1392,1406` 中依赖 hook 结果的表达式同样适用。

**方案 B（不推荐）**：靠 DOM / 自定义事件把数据从主世界搬出——引入新可见痕迹，且与 `BCC-065/066` 冲突。
**方案 C（项目已选方向）**：Camoufox 路线（无 JS 注入，改用 Playwright 原生 WebSocket 事件，见 `browser_daemon.py:469-473`），使 Chromium hook 路径彻底退居回退。

**门禁（防复发，建议纳入 `env_audit` / 回归套件）**：以 `probe_page_selfcheck.py` 为样本，断言 **「页面主世界 `title == YES`」且「默认世界读取非 null」**——**两条必须同时成立**；只验前者会漏掉本事故（注入成功却读不到）。
